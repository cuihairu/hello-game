# 1. 总论与方法论

这一章不讨论某一个具体框架或引擎，而是讨论一件更根本的事：`面对一个游戏项目，技术负责人应该先看什么，再看什么`。

游戏行业最常见的误区，不是“技术不够新”，而是`问题定义错了`。很多讨论一上来就问：

- 要不要微服务
- 要不要 ECS
- 要不要 Redis
- 要不要 Lua 热更
- 要不要云原生

这些问题本身都不重要。真正重要的是：

- 玩家之间是否共享状态
- 交互是低频离散还是高频连续
- 判定是追求绝对公平还是允许体验优先
- 状态是一次性会话，还是要存活几个月甚至几年
- 产品是一次性售卖，还是长线运营、重活动、重商业化
- 团队有没有能力维护复杂方案

如果这些前置判断没做清楚，后面的技术选型再漂亮，也只是把资源花在错误的地方。

这一章的作用是给后面所有章节建立统一分析口径。读完这一章之后，至少应该能回答三件事：

1. 一个游戏项目的技术复杂度到底从哪里来。
2. 为什么同一个“RPG”标签下，项目的技术形态可能完全不同。
3. 如何从玩法出发，逐层推导到同步、服务拆分、数据模型和运维治理。
