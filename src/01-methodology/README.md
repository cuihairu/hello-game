# 1. 总论与方法论

游戏开发里的大多数技术分歧，表面上在争论引擎、语言、数据库、同步方案，实质上是在争论项目到底是什么问题。只要问题模型判断错了，后面的技术细节做得越精致，返工成本反而越高。

这一章不讲某个框架怎么用，而是先建立一套分析顺序：先看玩家在游戏里反复做什么，再看哪些状态必须共享、必须实时、必须长期保存，然后再看这些约束会把系统推向什么样的架构。只有顺序对了，后面的网络、战斗、服务拆分、数据和运维章节才有稳定前提。

这一章主要解决六类常见失误：

- 立项时先谈技术栈，最后才发现玩法根本不需要那套复杂系统。
- 把不同类型游戏混成一种问题，照搬别的项目架构。
- 只看单机开发效率，不看上线后的版本、运营、风控和恢复成本。
- 客户端、服务端、平台和运营边界划分不清，导致责任无法落地。
- 用互联网后端经验直接套游戏项目，忽略局内实时性和版本窗口。
- 团队复盘只记住结论，不沉淀触发条件、代价和适用边界。

如果读完本章只能记住一句话，那就是：游戏架构不是从中间件开始设计的，而是从玩法循环、状态归属和生命周期约束一路推出来的。
