# 如何系统化积累游戏开发经验

游戏开发经验如果只停留在“做过什么项目”，很快就会碎掉。更有效的积累方式是把项目经验抽成可复用的判断模板。

建议长期沉淀四类内容：

### 1. 问题模型

不要只记“某项目用了什么”，要记“它为什么会遇到这个问题”。

### 2. 选型理由

不要只记最终用了哪个方案，要记候选方案、约束条件和淘汰原因。

因为真正可复用的不是“我们当年用了 Redis”，而是“为什么那个场景下 Redis 比数据库直查更合适，代价又是什么”。

### 3. 事故模式

高价值经验往往不是成功案例，而是失败和事故。比如：

- 为什么某次热更新出问题
- 为什么某个同步模型在特定场景下失效
- 为什么某个服务拆分让协作成本暴涨

### 4. 检查清单

把易错点收敛成固定检查项，比“靠经验记得住”更可靠。

## 为什么很多团队积累不下来

因为经验只保存在人脑里，而不保存在结构化文档里。常见问题是：

- 方案只记结论，不记前提
- 事故只记现象，不记根因
- 复盘只停留在责备，不沉淀成检查项
- 文档按岗位写，导致跨边界问题没法完整复盘

## 一份可复用经验至少要包含什么

如果想让经验真正可复用，一篇沉淀至少要包含：

1. 业务背景和约束
2. 备选方案及淘汰理由
3. 最终方案及副作用
4. 线上表现和事故模式
5. 下次再做时会怎样改

这五项缺任何一项，经验都容易变成口耳相传的印象。

这也是本知识库后面保留“复盘与清单”章节的原因。知识不应该只帮助理解系统，也应该帮助减少犯错。
