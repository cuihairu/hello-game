# 12. 缓存、中间件与基础设施

这一章讨论的是：游戏后端常用的中间件和基础设施能力，应该放在什么位置、解决什么问题，以及哪些问题不该指望它们替你兜底。

中间件不是架构的中心，它们只是承载某些约束的工具。一旦把工具当成主角，系统很容易演变成“为了用某个组件而设计业务”。

## Redis、排行榜与锁

Redis 在游戏项目里非常常见，但常见不代表应该无边界使用。

它通常适合：

- 高频缓存
- 短期状态
- 排行榜
- 计数器
- 限流和轻量协调

它不适合直接承担：

- 所有核心业务权威状态
- 复杂关系查询
- 无约束的大对象长期存储

排行榜是 Redis 很典型的强项，因为它天然需要：

- 按分值排序
- 快速取 TopN
- 局部区间查询

但排行榜真正的难点往往不在“能不能排”，而在：

- 分数如何更新
- 是否允许并发重算
- 排行结果和奖励结算如何对齐

锁也是一样。分布式锁不是不能用，而是要非常谨慎。很多游戏逻辑如果已经有天然权威单元，例如房间、战斗实例、角色主线程，其实不应该再用分布式锁硬兜。

锁能解决的是资源争用问题，不能替代状态边界设计。

## singleflight、MQ 与事件流

中间件真正高价值的地方，通常在于削峰、去重和解耦。

### singleflight

适合处理“同一时刻大量重复请求打向同一资源”的问题，例如：

- 同一配置被反复拉取
- 同一玩家数据被并发查询
- 某热点对象被同时请求

它解决的是重复工作，不是根本性的容量问题。

### MQ

消息队列适合把主链路不必同步完成的工作移到异步路径，例如：

- 日志汇聚
- 异步通知
- 邮件发放
- 报表和分析

但 MQ 不是“把问题塞进去以后就没有问题了”。真正要处理的是：

- 消费延迟
- 重复消费
- 顺序语义
- 死信和积压

### 事件流

事件流更适合表达“系统里发生了什么”，尤其是在分析、审计和外围消费场景中很有价值。

但事件流一旦缺少语义治理，很容易变成谁都发、谁都订，最后没人说得清每个事件到底代表什么。

## 注册中心、负载均衡与一致性哈希

当服务多起来以后，基础设施必须帮助系统回答：

- 服务在哪
- 请求该打到哪
- 对象应该由谁负责

注册中心解决的是实例发现问题，但游戏系统通常还会多一层业务路由问题，例如：

- 某角色在哪个场景节点
- 某房间归哪个实例
- 某区服当前有哪些活跃节点

负载均衡也不能只看平均分布。对游戏来说，很多对象是有状态的，不能像无状态 Web 接口一样随便漂移。

一致性哈希这类方案的价值在于尽量减少对象重映射，但前提仍然是：

- 对象是否真的适合稳定绑定
- 节点变化时是否有迁移策略

基础设施只能帮助映射，不能替代对象生命周期管理。

## 对象存储、CDN 与资源分发

对客户端和长线运营项目来说，资源分发本身就是核心基础设施。

常见能力包括：

- 补丁包存储
- 大资源托管
- 静态文件分发
- 区域性加速

对象存储和 CDN 更适合承载大文件和静态资源，不应该被误当成随意可变的业务数据库。

真正难的部分通常是：

- 资源版本如何组织
- 客户端如何命中正确资源
- 回滚时如何保证资源和程序匹配
- 大规模更新时如何避免下载风暴

资源基础设施的价值，不只是“下载更快”，而是让发布、补丁和资源治理能长期稳定运行。
