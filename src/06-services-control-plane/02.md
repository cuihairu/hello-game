# 核心服务角色

一旦项目进入服务拆分阶段，最常见的混乱不是“服务太多”，而是大家嘴上都在说同样的名词，实际指的却不是同一类职责。有人说“房间服”，指的是局内状态推进；有人说“场景服”，指的是地图节点；有人说“活动服”，却既想管规则也想管进度也想发奖励。  
所以讨论核心服务角色，真正要做的是把常见服务按照职责和状态归属说清楚，而不是把服务名词堆出来。

## 为什么服务角色要单独讲

服务拆分方法论解决的是“为什么拆、按什么拆”；服务角色这一页解决的是“拆出来以后，哪些角色是常见稳定骨架，哪些边界最容易被做脏”。

因为在真实项目里，大多数系统最后都会落到几类典型角色上：

- 接入和会话类
- 实例和场景类
- 长期资产类
- 外围能力类
- 协调与治理类

如果这几类角色没有清楚分工，系统就会出现两个典型问题：

- 某个服务什么都管，最后成大杂烩。
- 名字看起来拆了，状态其实还缠在一起。

## 常见的核心服务角色

### 1. 网关 / 接入服务

职责通常包括：

- 连接管理
- 鉴权后的会话绑定
- 基础路由
- 心跳、踢线、限流、基础协议处理

它通常不应该承担：

- 重业务逻辑
- 高成本数据库操作
- 房间或世界状态推进

网关的价值在于连接和会话，不在于“顺便做业务”。

### 2. 账号 / 角色服务

这类服务通常负责长期身份和角色基线状态，例如：

- 账号信息
- 角色基础档案
- 登录入口和角色选择
- 局外基础资产入口

它更接近长期资产治理，不适合承担高频局内状态。

### 3. 匹配 / 调度服务

匹配服务不只是“凑局器”，它往往还承担：

- 分桶与匹配规则
- 房间创建请求
- 节点选择与分配
- 开局前状态协调

它是很多会话型游戏的第一道协调层。

### 4. 房间 / 副本 / 战斗实例服务

这类服务通常负责：

- 局内或副本内高频状态推进
- 玩家输入处理
- 广播、托管、重连上下文
- 结算前的权威运行时状态

这类服务的共同点是实例态强、生命周期相对短、和对局或副本边界高度绑定。

### 5. 场景 / 世界服务

它和房间服最大的区别，不在于名字，而在于：

- 状态是否长期存在
- 是否有公共场景和多人共存
- 是否承担跨区域迁移和世界状态维护

MMO、大地图、生存沙盒项目里，这类服务通常是主干。

### 6. 活动 / 任务 / 商店等外围业务服务

这些服务通常负责：

- 规则解释
- 活动进度
- 奖励发放请求
- 商店和任务状态

它们更适合围绕长期规则和配置治理组织，而不是绑进房间或世界推进主链路。

### 7. 排行 / 邮件 / 社交 / 聊天等公共能力服务

这些服务往往跨玩法、跨场景复用。它们的关键在于边界清楚：

- 排行更像读取和展示能力，不该反向侵入战斗主链路。
- 邮件和补偿更像长期资产外围投递链。
- 聊天与社交有自己的连接和广播模型，不适合和局内同步混成一锅。

### 8. 支付 / 订单 / 风控服务

这类服务通常并不在局内主链路上，但绝不能被当“辅助模块”。它们往往承担：

- 订单状态机
- 发货确认
- 审计
- 风控和异常处理

这类服务的边界通常比玩法服务更稳定。

### 9. 协调层 / 控制平面相关服务

很多项目早期没有这一层，后面一定会补。它们常见职责包括：

- 节点分配
- 区服路由
- 迁移和切流
- 扩缩容编排
- 全局配置下发
- 服务注册与健康管理

这类服务不直接推进业务状态，但往往决定整个系统能不能稳定运转。

## 服务角色之间最容易出现什么混淆

### 把长期资产和实例态混在一起

例如房间服直接持久化长期资产、活动服直接维护局内高频状态、账号服顺便推进副本进度。  
这种做法前期方便，后期边界会非常脏。

### 把规则解释和状态维护混在一起

例如活动服务既存配置、又跑进度、又发奖励、又做报表。  
这会让每次变更都牵一发动全身。

### 把网关做成业务总线

网关一旦承担过多业务逻辑，连接层和业务层的故障就会相互污染，排障也会变得困难。

## 角色不是越多越好，而是边界越稳越好

这里最容易陷入一个误区：既然能列出这么多服务角色，是不是项目就应该全部拆出来。并不是。真正该问的是：

- 这些角色是否已经有稳定职责和独立演进需求
- 拆出来是否能减少而不是增加跨服务抖动
- 是否值得独立扩缩容和治理

有些项目早期可能一个服务兼任多个角色，这是现实；关键是逻辑边界要先清楚，后续才有机会平滑拆出去。

## 一个更实用的理解方式

如果想快速建立直觉，可以把核心服务角色粗分成三层：

- 面向连接：网关、接入、会话层
- 面向运行时状态：房间、场景、战斗、匹配
- 面向长期资产和公共能力：账号、活动、支付、邮件、排行、风控

再在最上面补一层：

- 面向系统治理：协调层、控制平面、路由、编排、监控

这套分层不等于固定部署，但有助于团队避免“所有东西都叫业务服”。

## 更接近最佳实践的结论

核心服务角色真正重要的不是名字，而是每一类角色回答了不同问题：

- 谁维护连接和会话
- 谁推进高频运行时状态
- 谁维护长期资产和规则
- 谁负责系统级调度和编排

只要这几类责任被清楚区分，后续拆分和扩展会顺很多；如果它们长期混在一起，系统名字再多也只是大单体换壳。

## 常见误区

最常见的错误，是把服务名字当边界，以为有了“房间服”“活动服”“账号服”这些名词，边界就自然清楚了。另一类错误，是让某个服务同时承担连接、实例态和长期资产三种职责。第三类错误，是忽视协调层和控制平面角色，结果系统能跑业务，却没法稳定调度、迁移和恢复。
