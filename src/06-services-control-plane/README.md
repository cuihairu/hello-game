# 6. 服务拆分、分布式与控制平面

这一章讨论的不是“要不要微服务”这种抽象口号，而是游戏项目为什么会被迫进入服务拆分、拆到什么程度才合理，以及拆完以后系统怎样继续被组织、路由、编排和恢复。关键不在服务数量，而在状态边界、责任归属、路由关系和控制平面能力。

服务拆分最容易被说虚。很多团队嘴上讨论的是“分布式架构”，实际线上痛点却是：

- 房间、场景、活动、支付、排行到底谁负责什么状态
- 玩家从一个玩法跳到另一个玩法时由谁调度
- 节点扩缩容、迁移、跨服和重连到底谁在指挥
- 一条跨服务链路中间失败后怎么恢复

这些问题如果不写清楚，拆分只会把单体复杂度换成分布式复杂度。

- [服务拆分方法论](./01.md)：先从状态边界、失败域、扩缩容和组织协作出发，回答服务到底为什么拆、什么时候该拆。
- [核心服务角色](./02.md)：把网关、账号、匹配、房间、场景、活动、排行、支付等常见服务角色放回统一系统视角中理解。
- [协调层、跨服与控制平面](./03.md)：说明为什么一旦进入多玩法、多区服和动态扩缩容阶段，调度与编排能力会从附属模块变成主系统。
- [服务发现、路由与协作](./04.md)：讨论玩家请求和服务间调用到底如何找到正确节点、维持路由一致并减少链路耦合。
- [一致性、恢复与重连](./05.md)：把跨服务事务、幂等、补偿、状态恢复、玩家重连和故障切换放到同一条工程链里讨论。
