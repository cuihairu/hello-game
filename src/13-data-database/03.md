# 事务、一致性与分库分表

游戏系统里，一致性问题往往集中在资产和结算链路上。

只要涉及：

- 发货
- 扣费
- 增减货币
- 奖励发放
- 订单闭环

就必须明确事务边界。

首先要问的不是“数据库支不支持事务”，而是：

1. 哪些步骤必须原子
2. 哪些步骤可以异步补偿
3. 谁来记录最终权威结果

很多系统的问题不是没有事务，而是事务跨得太大，最后把整个链路锁死；或者事务跨得太小，结果需要靠人工补单。

分库分表也是类似。它不是性能灵药，只是把单点容量问题换成了路由、聚合、迁移和运维复杂度问题。

比较值得分的通常是：

- 天然按玩家或区服可切分的数据
- 访问热点明确的数据
- 历史体量增长非常快的数据

不值得过早分的通常是：

- 规模还没到的系统
- 关系很复杂、跨对象查询很多的系统
- 团队还没有稳定路由和运维能力的阶段
