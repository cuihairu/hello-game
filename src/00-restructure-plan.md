# 目录重构方案

这份文档只解决一件事：给知识库定义一版更稳定的一级目录边界。

这里先修正一个判断：这个仓库是知识库，不是真的书，所以不需要为了“像书”而强行压缩章节数。真正要压掉的是重复视角，不是信息量。

## 现状判断

当前仓库的问题不是“目录太多”，而是“一级目录混入了多种切分维度”。

主要表现为：

- 有的章节按技术层切，比如网络、同步、数据库、缓存
- 有的章节按业务对象切，比如通用服务、运营、平台 SDK
- 有的章节按分析视角切，比如游戏类型、问题模型、问题域归纳
- 有的章节按选型视角切，比如引擎、语言、工具生态
- 有的章节按经验沉淀切，比如实践、复盘、清单

这些维度都值得保留，但不应该全部平级并列。否则后面写正文时，天然会反复覆盖同一批内容。

## 重构原则

- 一级目录优先按稳定知识边界切，不按临时分析视角切
- 能独立长成体系的技术主线保留独立章节
- 重复视角降级到二级专题、附录或横向索引
- “游戏类型分析”保留，但不再拆成三套相似章节
- “引擎 / 客户端 / 脚本 / 语言 / 工具”允许拆开，但要有清晰边界
- “可观测 / 压测 / 容量 / 稳定性”视为同一治理链路

## 为什么这版更适合知识库

### 1. 保留了硬技术主线

网络、同步、运行时、服务架构、IPC 这些内容本来就能独立长成体系，不应该为了压缩而粗暴合并。

### 2. 只移除了重复视角

`08 / 09` 与 `02` 高度重合，`22` 与 `10 / 11 / 23` 高度重合。把它们从一级主线拿掉，不会损失信息，反而能减少后续重复写作。

### 3. 更符合“知识库”而非“教材”

知识库需要稳定索引，不需要过度追求线性阅读。18 章比 14 章更松弛，也更容易容纳后续扩展。

### 4. 方便后续真正重写正文

当前 23 章基本都还是提纲页。先把一级边界定稳，后面每章再往下拆专题时，就不会一直碰到“这段该写到哪”的问题。

## 迁移顺序

不建议现在就一次性重命名全部文件。更稳的做法是：

1. 先把新目录作为上位结构固定下来
2. 逐章审查旧内容，判断保留、合并、降级还是废弃
3. 正式重写正文时，再统一做文件迁移和 `SUMMARY` 重排

## 当前建议

在正文没有重写前，先保留现有文件编号，把这份方案作为新的目录约束。

等开始正式重写时，再统一做：

- 章节合并
- 文件重命名
- 索引页补充
- `SUMMARY.md` 重排
