# 18. 选型、实践、复盘与清单

这一章不是再引入新主题，而是把前面所有主线收束成可复用的工程判断。

如果前面的章节负责解释“系统为什么会变成这样”，这一章负责回答“面对一个新项目时，应该如何少走弯路”。

## 引擎、语言与技术选型

技术选型最容易犯的错，是把“流行”“性能宣传”“别人用过”当成核心依据。

真正应该优先考虑的维度通常是：

1. 项目主导问题是什么
2. 平台约束是什么
3. 团队最强和最弱的能力在哪里
4. 产品是验证型、首发型还是长线型
5. 当前阶段最怕的是慢开发还是慢演进

例如：

- 强表现 3D 项目和轻量小游戏，对引擎的要求完全不同
- 强实时战斗项目和长周期运营项目，对服务端语言和运行时偏好也会不同
- 一个团队如果没有成熟基础设施能力，就不应该靠概念硬上复杂分布式架构

成熟的选型，不是选“最强”的，而是选“最匹配且最可维护”的。

## 架构模式与选型对照

很多架构模式本身都成立，问题在于用在了错误阶段或错误问题上。

例如：

- 单体或模块化单体更适合验证期和边界尚未稳定的系统
- 房间权威单线程更适合大量局内逻辑
- 分布式控制平面更适合多节点、多区服、跨服协作明确存在的产品
- 事件流和异步链路更适合外围分析和通知，而不是主链路关键判定

真正高质量的判断，不是给出唯一模式，而是能说清楚：

- 当前为什么选它
- 不选其他方案的原因是什么
- 这个方案什么时候会开始失效

只要这三个问题说不清，架构决策很可能只是风格偏好。

## 关键问题清单

面对一个新项目，最值得反复检查的不是“用了哪些组件”，而是以下问题有没有提前回答。

### 玩法与交互

- 核心交互是离散还是连续
- 共享状态范围有多大
- 公平性和实时性要求有多高

### 服务与状态

- 哪些状态必须权威维护
- 谁拥有这些状态
- 异常退出时如何恢复

### 版本与内容生产

- 哪些变化靠代码发版
- 哪些变化靠配置和资源
- 新旧版本允许共存多久

### 运营与商业化

- 活动和商业化能力是否前置设计
- 埋点口径是否统一
- 经济和风控是否有观察面

### 稳定性与治理

- 有没有明确的观测面
- 有没有压测和容量认知
- 关键操作是否可审计

这类清单的价值，在于让团队别总在同一个地方重复犯错。

## 分析框架、误区与失败案例

大多数工程失败，不是因为没人懂技术，而是因为判断顺序错了。

最常见的误区包括：

- 还没想清玩法问题，就先做大而全架构
- 把所有问题都归结为“性能不够”
- 过早平台化
- 过晚治理化
- 把发布、运营、合规当成后期补丁

还有一类典型失败，是把局部正确放大成全局方案。

例如：

- 某个中间件在一个链路里有用，就开始全系统滥用
- 某个同步方案在一种玩法里成立，就拿去覆盖所有实时问题
- 某种热更新能力解决了效率问题，却没有同步补上版本治理和回滚机制

失败案例真正有价值的地方，不是“当时做错了什么”，而是能不能抽出背后的判断错误。

## 个人查漏补缺清单

如果这套知识库要长期维护，最终一定要回到“我自己哪里还缺”。

比较值得长期追问自己的问题包括：

- 我是否只会描述技术名词，却说不清问题模型
- 我是否在某一类项目上经验很深，但跨类型迁移能力很弱
- 我是否更擅长搭系统，却不擅长治理系统
- 我是否只关注开发期，不关注运营期和事故期
- 我是否能把一次项目经历沉淀成通用判断模板

知识库真正的价值，不是写满，而是让后续每次做项目时，判断更快、更稳、更少自我欺骗。
