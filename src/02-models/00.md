# 常见玩法类型概览

如果第 2 章一上来就只讲“不要按 RPG、FPS、SLG 分类”，读者不满是正常的。因为玩法类型本来就是行业里最稳定、最常用、最接近日常沟通的一层语言。玩家、策划、制作人、发行、媒体、招聘、投资人，几乎都先用这一层说话。  
越是共识，越应该先讲清楚。

真正的问题从来不是“玩法类型有没有价值”，而是：

- 它能解决到哪一层
- 它不能越权替代哪一层
- 它怎样映射到后面的技术问题模型

这一页不打算做百科词条，而是把玩家最熟悉的主流玩法分类讲到能直接服务后文。

## 为什么这一页必须先讲

玩法类型至少承担四个现实职责。

### 1. 它是玩家和市场最通用的入口

你说“这是个 MOBA”“这是个 MMO”“这是个放置卡牌”“这是个刷宝 ARPG”，对方哪怕不是工程师，也会立刻脑补出一套体验预期。

### 2. 它是团队早期最快的沟通语言

立项、竞品、融资、招聘、发行对外沟通，很少有人一开始就说“这是一个持续在线世界型 + 高频对象 + 长周期成长型产品”。  
大家先说的还是玩法外形。

### 3. 它确实能提示技术压力

哪怕不够精确，MOBA 一定会让人想到同步和裁决，MMO 一定会让人想到世界状态和迁移，放置一定会让人想到长期资产和离线结算。  
这层提示是真实存在的。

### 4. 它是新人建立直觉的第一层

大多数人不会一上来就从“单写者模型”“状态归属”“逻辑时间”进入思考，而是先从熟悉的玩法外形进入，再逐步理解背后的问题结构。

所以正确做法不是删掉玩法分类，而是：

1. 先把玩家共识层讲清楚
2. 再说明为什么共识层还不够
3. 最后把它映射到问题模型层

## 先给一张更实用的总表

| 派对 / 房间制轻竞技 | 快速开局、多人同房、局内欢乐 | 匹配、组房、开局、散局 | 快速建房、广播、断线重连 |
| MOBA | 手感、公平、技能博弈、团战 | 补刀、游走、技能、资源争夺 | 同步、裁决、回放、反作弊 |
| FPS / TPS / 吃鸡 / 战术射击 | 命中、视角、反应、枪感 | 瞄准、射击、掩体、缩圈 | 命中判定、弱网、Lag Compensation |
| 格斗 / 竞速 / 体育对抗 | 帧感、先后手、读招、极限操作 | 输入、对抗、碰撞、结果裁决 | 回滚、确定性、输入延迟 |

| 卡牌 / CCG / 自走棋 | 构筑、随机、运营、阵容 | 抽卡、出牌、站位、回合结算 | 状态机、RNG、日志回放、经济系统 |
| 回合制 RPG / 战棋 | 回合顺序、数值、效果链 | 行动点、技能、轮转、判定 | 状态机、效果结算、断点恢复 |

| ARPG / 刷宝 / 副本驱动 | 手感、Build、掉落、刷图 | 战斗、刷本、掉宝、成长 | 技能系统、房间副本、掉落审计 |
| 放置 / 经营 / 模拟养成 | 长线积累、离线收益、活动循环 | 收益、升级、派遣、任务 | 资产一致性、离线结算、配置运营 |
| SLG / 4X / 赛季沙盘 | 城建、联盟、行军、赛季 | 建造、屯兵、出征、占地 | 持续世界、异步交互、联盟协作 |
| 生存 / 建造 / 沙盒 | 采集、建造、世界持久化 | 采集、合成、建造、防守 | 对象持久化、区域负载、共享状态 |
| Roguelike / Roguelite | 随机局、反复开局、局外成长 | 探索、战斗、随机事件、结算 | 程序生成、种子、局内外进度切分 |
| UGC / 平台生态 | 创作、分享、分发、交易 | 生产内容、消费内容、社交传播 | 审核、权限、沙盒隔离、生态治理 |

这张表不能替代后文，但它已经比“玩法名字列表”更有用，因为它把玩家理解和技术警报绑到一起了。

## 1. 棋牌 / 桌面对局

这类产品包括麻将、斗地主、德州、象棋、围棋、五子棋，以及各种牌桌变体。它们未必强调低延迟手感，但极度强调：

- 轮次顺序是否可信
- 发牌和随机是否可信
- 托管是否合理
- 断线重连后局面是否一致
- 结算是否可审计

玩家对这类游戏的耐受度和强实时竞技完全不同。玩家可以接受多等几百毫秒，不会接受：

- 出牌顺序出错
- 手牌信息泄漏
- 结算少算
- 争议局没有证据

所以技术上第一警报不是“延迟”，而是：

- 房间和牌桌状态机
- 防作弊与随机可信性
- 过程日志
- 断线托管和争议复盘

最常见误判，是因为它看起来操作简单，就误以为服务端也可以很轻。实际上，这类产品往往在`权威裁决`和`证据留存`上要求非常硬。

## 2. 派对 / 房间制轻竞技 / 休闲乱斗

这一类玩家最先想到的是“开一局快不快”“能不能和朋友马上玩起来”“掉线回来是不是还能继续”。它通常有几个特点：

- 一局边界明确
- 玩家关系主要发生在局内
- 局外长期状态相对轻
- 高峰时房间创建和回收频繁

玩家真正感知最强的点通常是：

- 匹配等待时间
- 组房和拉人体验
- 开局成功率
- 局内广播和同步是否顺畅
- 掉线后能否重连或托管

技术上第一警报往往是：

- 匹配和组房
- 房间生命周期
- 快照和重连
- 房间广播效率
- 散局、结算和异常销毁

这类项目最常见的错误，是把“轻竞技”误解成“后端逻辑也轻”。结果上线后最先炸的，往往不是玩法，而是开局链路和房间尾部状态清理。

## 3. MOBA

MOBA 的玩家共识非常稳定：对线、打野、推塔、团战、技能命中、资源争夺、经济差、视野、节奏。  
这意味着玩家天然会把下面这些东西当成玩法的一部分：

- 技能是否顺手
- 操作延迟能不能接受
- 裁决是否公平
- 观战和回放能不能站得住
- 作弊和代打是否可控

MOBA 的技术压力不是“有 PVP”这么简单，而是：

- 玩家输入的时间差足以直接改变结果
- 同屏多人交互密集
- 技能、Buff、位移、投射物时序复杂
- 争议判定必须可解释

所以它对技术的第一要求通常是：

- 同步模型定得够早
- 技能系统和网络模型一开始就协同
- 回放、观战、裁决链路不是附属功能
- 反作弊不是上线后补丁

把 MOBA 只理解成“5v5 对战”完全不够。它更准确地说，是`强实时团队对抗 + 复杂技能系统 + 长对局裁决`的组合问题。

## 4. FPS / TPS / 吃鸡 / 战术射击

玩家对这类产品最敏感的不是技能条，而是：

- 枪感
- 命中反馈
- 身位是否合理
- 视角是否公平
- 网络抖动时到底是谁先看到谁

这类产品的技术压力比一般“实时对战”还更偏底层，因为它会直接把下面的问题推到最前台：

- 命中判定到底由谁说了算
- 如何做 Lag Compensation
- 如何在服务端权威和本地即时反馈之间取平衡
- 如何治理外挂、透视、自瞄、加速

如果是战术竞技或大地图吃鸡，还会叠加：

- 大地图分区和兴趣管理
- 大量对象与拾取状态
- 缩圈和全局事件
- 大量玩家同时接入

所以玩家说“这是个射击游戏”，对技术的含义远不止“同步做重一点”，而是整个接入、战斗、判定、反作弊、观战链路都要前置设计。

## 5. 格斗 / 竞速 / 体育对抗

这类产品玩家最在意的是“帧感”。  
格斗玩家会在意出招、受击、先后手、压起身、确认；竞速玩家会在意转向、碰撞、物理、排名；体育对抗玩家会在意动作衔接、判定和对抗公平。

它们经常具备两个共同特点：

- 人数规模不一定大
- 但对输入延迟和时序稳定性极度敏感

这意味着技术设计通常不会被“大世界复杂度”压垮，而会被：

- 回滚和重演
- 确定性
- 输入缓冲
- 帧级裁决

这些问题压垮。

最常见误判，是因为玩家数量少、地图小，就以为服务端压力不大。实际上，这类项目最贵的地方往往不在“量”，而在“时序要求极硬”。

## 6. RTS / 即时战术

RTS 在玩家视角里，最关键的词通常是：

- 资源采集
- 建造
- 编队
- 多单位操作
- 全局策略和局部微操

它的技术压力和 MOBA、FPS 不完全一样。RTS 更容易遇到的是：

- 单位数量大
- 命令密度高
- 路径和碰撞复杂
- 局势状态量大
- 回放和重演价值高

所以这类玩法天然会把注意力拉向：

- 命令同步或局部权威同步
- 路径系统
- 大量单位的批处理更新
- 程序确定性

RTS 的“实时”不是只看人类手感，它还很看重系统能否承载`大规模同类对象的持续推进`。

## 7. 卡牌 / CCG / 自走棋

很多人一看到卡牌，就误以为技术一定轻。这个判断经常是错的。  
卡牌、自走棋、Deck Builder、构筑对战这类产品，玩家通常在意：

- 抽卡和随机是否可信
- 构筑深度和数值平衡
- 回合结算是否清楚
- 阵容和经济系统是否成立

从技术上看，这类项目不一定强实时，但非常强调：

- 状态机是否可靠
- 随机种子和随机过程是否可复盘
- 效果链和触发链是否可解释
- 长期卡池和养成数据是否稳定

如果是自走棋，还会再叠加：

- 回合推进
- 自动战斗模拟
- 局内经济
- 多阶段同步广播

所以卡牌项目的难点经常不是网络延迟，而是`复杂状态结算 + 长期经济系统 + 数值驱动内容爆炸`。

## 8. 回合制 RPG / 战棋 / 回合策略

这类玩法玩家并不苛求 50 毫秒的操作反馈，但会非常在意：

- 回合顺序对不对
- 效果结算是否合理
- 技能说明和实际效果是否一致
- 长战斗过程能不能清楚复盘

它的核心循环通常围绕：

- 回合轮转
- 技能和状态结算
- 队伍成长
- 关卡和数值对抗

技术上常见第一警报是：

- 显式状态机
- 效果链和 Buff 结算顺序
- 长战斗日志
- 断点恢复
- 配置和脚本驱动

最常见误判，是因为“不是实时”就低估它的复杂度。实际上，回合制一旦技能、Buff、被动、触发器多起来，结算链本身就足以成为一套独立的运行时问题。

## 9. MMORPG / 大世界在线

MMO 在玩家脑子里意味着的从来不只是“人多”，而是：

- 长期角色
- 持续世界
- 公会和社交
- 交易与经济
- 活动与赛季
- 跨副本、跨玩法、跨场景接起来

这类产品真正重的地方通常不是单场战斗，而是：

- 世界状态长期存在
- 玩家不在线时状态也要说得通
- 多个系统围绕同一份角色资产和世界资产协作
- 运维、扩容、跨服、迁移、恢复压力都大

所以玩家说“这是 MMO”，对技术的含义通常包括：

- 分区分片和场景服务
- 角色迁移
- 长期资产托管
- 公会、邮件、交易、活动等外围系统变重
- 大量线上治理和运维能力前置

MMO 最大的误判，是把它只看成“多一些地图和副本”。实际上它是一种`持续在线社会系统`。

## 10. ARPG / 刷宝 / 副本驱动

ARPG 玩家在意的通常是三个东西同时成立：

- 战斗动作反馈要爽
- Build 和技能构筑要丰富
- 掉落和成长回报要有驱动力

这类项目技术上经常是组合型高压：

- 战斗部分有强实时诉求
- 技能、Buff、词缀、被动链复杂
- 局外长期资产又很重
- 副本和房间生命周期频繁

也就是说，它经常不是“实时游戏”或者“成长游戏”二选一，而是同时要：

- 处理同步和技能系统
- 处理掉宝和资产审计
- 处理副本房间
- 处理赛季和长线运营

这就是为什么简单一句“这是 RPG”几乎没有任何技术信息量。ARPG 的核心麻烦，在于它把`强实时 + 长成长 + 高内容密度`绑在了一起。

## 11. 放置 / 经营 / 模拟养成

这类产品玩家通常最看重：

- 进度有没有稳定积累
- 离线收益是否合理
- 活动循环是否持续提供目标
- 数值成长是否顺畅

这类玩法不太怕 100 毫秒网络延迟，但极度怕：

- 少发奖励
- 活动配置错
- 计时器错乱
- 资源被吞或被多发

技术上第一警报通常是：

- 长期资产一致性
- 离线结算
- 配置和活动系统
- 审计、补偿和回滚
- 时间作弊和脚本外挂

它真正难的，不是战斗同步，而是`持续运营的数据正确性`。

## 12. SLG / 4X / 赛季沙盘

SLG 玩家最熟悉的语言是：

- 城建
- 兵种
- 行军
- 占地
- 联盟
- 赛季
- 州战 / 国战 / 外交

它看起来不像 MMO，但技术上有很多地方和 MMO 一样重，甚至更容易把系统拉长。因为它通常同时具备：

- 长期持续世界
- 大量异步交互
- 联盟级组织关系
- 赛季重置和规则切换
- 大量定时器、行军、集结、驻防、攻城行为

它的技术第一警报通常是：

- 世界状态分区
- 大量长定时任务
- 联盟和关系链
- 异步冲突裁决
- 赛季和跨赛季迁移

最常见误判，是把 SLG 当成“经营 + 战斗”的普通叠加，低估它其实更像`持续在线世界 + 长线数据系统 + 大规模异步社会图谱`。

## 13. 生存 / 建造 / 沙盒

玩家看到这类玩法，第一反应通常不是数值，而是：

- 采集和制造
- 建造和破坏
- 持续世界
- 基地与防守
- 共享对象和地形改造

技术上的压力会迅速集中到：

- 世界对象数量
- 建造状态持久化
- 区域模拟和负载划分
- 多人协作和冲突
- 资源组织与流式加载

如果还是多人在线沙盒，就还要再叠加：

- 权限体系
- 破坏与恢复
- 世界清理
- 服务器容量和区域热度治理

所以生存沙盒真正难的，往往不是“战斗够不够好”，而是`世界对象能不能长期稳定存在并被多人共享`。

## 14. Roguelike / Roguelite / 地牢闯关

这类玩法玩家通常最看重：

- 重开速度
- 随机感是否有趣
- 局内选择是否形成独特构筑
- 局外成长有没有持续动力

技术上它看起来比 MMO、SLG 小，但也有自己的明显特点：

- 程序生成和随机种子
- 局内状态和局外成长的切分
- 快速开局和快速重开
- 回放、Debug 和种子复现价值高

如果它是联网 Roguelite，还会叠加：

- 房间生命周期
- 合作同步
- 掉线重连
- 掉落与奖励审计

这类玩法最容易被低估的地方，是“随机内容看起来轻，实际上生成、复现和局内局外切分都很考验系统边界设计”。

## 15. UGC / 平台生态 / 创作驱动

一旦玩法中心从“玩官方内容”转向“创作、分享、交易、协作、传播内容”，产品本质就已经部分平台化了。  
这类项目的玩家共识通常是：

- 我不只是在玩
- 我还在做内容、发内容、消费别人内容
- 内容本身可能成为交易和社交对象

技术边界因此会彻底变化。第一警报通常是：

- 内容审核
- 创作者权限
- 脚本和沙盒隔离
- 资源分发
- 举报和治理
- 收益结算和生态规则

UGC 项目最常见的误判，是把它当成“游戏 + 编辑器”。实际上只要生态开始自增长，它就已经部分变成了`平台工程问题`。

## 为什么同样叫 RPG，技术形态却可能完全不同

“RPG”是最容易误导架构讨论的词之一。因为它只是一个非常宽的玩家感知标签，里面可能装进：

- 回合制 RPG
- ARPG
- MMORPG
- 单机剧情向 RPG
- Roguelite RPG
- 放置养成 RPG

这些项目的技术重心可能分别落在：

- 状态机和数值结算
- 强实时战斗
- 持续世界和跨服
- 内容管线和剧情脚本
- 程序生成与局内局外切分
- 长期资产与活动系统

也就是说，玩家标签可以帮助你进入问题，但绝不能替代问题分析本身。

## 更合理的做法：保留玩家分类，再下钻到问题模型

更合理的写法，不是“玩家分类不重要”，而是把分类拆成两层。

### 第一层：玩家 / 市场共识层

这一层负责回答：

- 这是什么类型的游戏
- 玩家大概期待什么
- 团队平时怎么称呼它

这一层就应该老老实实讲：

- MOBA
- FPS
- MMO
- 卡牌
- SLG
- ARPG
- 放置
- 派对
- 生存
- UGC

### 第二层：技术问题模型层

这一层负责回答：

- 主导复杂度压在哪
- 最贵的故障是什么
- 架构应该先围绕哪条链路设计

这一层更适合用后面第 2 章里的术语：

- 单局房间型
- 强实时对战型
- 持续在线世界型
- 长周期成长与异步交互型
- 经济与平台型
- 高频对象与重表现型

第一层负责让人进门，第二层负责让人做设计。少了第一层，读者会觉得生硬；少了第二层，设计就会失真。

## 第 2 章应该怎样继续读

比较顺的阅读顺序应该是：

1. 先看这一页，建立玩家共识层直觉。
2. 再看 [游戏类型的分类方法](./01.md)，理解为什么技术上不能停在玩家标签。
3. 然后进入后面的几个问题模型页，判断自己的项目主导复杂度到底压在哪。

这样结构才是顺的。  
先承认共识，再解释共识为什么还不够，最后进入技术模型。

## 更接近最佳实践的结论

应该讲玩法类型，而且要认真讲。  
因为它承担的是：

- 玩家共识入口
- 团队沟通语言
- 前期直觉建立
- 技术风险的第一层预警

但玩法类型不能直接替代架构分析。它更像入口地图，不是最终施工图。  
真正稳的写法，是先把这层地图画清楚，再继续下钻到后面的技术问题模型。
