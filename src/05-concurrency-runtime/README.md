# 5. 执行模型与运行时

这一章关注的不是“会不会用多线程”这种表层问题，而是服务端和引擎内部到底如何推进逻辑、组织状态、切分调度单位、控制并发和消化高峰。线程、协程、Actor、任务队列、Tick 驱动、背压和锁竞争，最后都在回答同一个问题：怎样让系统在高负载下仍然保持可预测、可恢复、可调试。

很多线上故障看起来像业务 Bug，根因其实是运行时组织方式先错了：

- 状态跨线程乱飞，时序不可推理。
- 某些慢任务拖住主循环。
- 高峰来了以后队列无边界增长。
- 锁竞争把吞吐和抖动一起拖垮。

所以这一章真正要解决的，不是某种“更先进模型”的崇拜，而是让你能判断：不同问题模型下，应该用什么运行时组织方式承载核心状态，哪些工作应该顺序推进，哪些工作值得并行，哪些工作应该异步外包但不能反向污染主链路。

如果只讲“线程、协程、Actor”几个词，这一章的标准是不够的。更合理的顺序是：

- 先建立并发模型谱系，知道不同模型到底在解决什么问题。
- 再回到游戏项目里最常见的几类主运行时组织方式。
- 然后讨论协程、状态机、任务队列、Tick、背压和锁这些运行时细节怎样共同决定线上稳定性。
