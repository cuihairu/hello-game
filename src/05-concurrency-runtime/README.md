# 5. 执行模型与运行时

这一章关注的不是“会不会用多线程”这种表层问题，而是服务端和引擎内部到底如何推进逻辑、组织状态、切分调度单位、控制并发和消化高峰。线程、协程、Actor、任务队列、Tick 驱动、背压和锁竞争，最后都在回答同一个问题：`怎样让系统在高负载下仍然保持可预测、可恢复、可调试。`

如果这一章只讲“线程、协程、Actor”几个词，标准是不够的。并发模型本来就应该先讲谱系，再讲游戏化落点。像《Seven Concurrency Models in Seven Weeks》这类材料有一个很大的价值：它把常见并发模型拆成了线程与锁、函数式、身份与状态分离、Actor、CSP、数据并行、Lambda 架构这些不同立场。  
游戏工程当然不会把它原样照搬，但如果连这层坐标系都没有，后面的运行时讨论就很容易只剩工具名词，没有判断力。

执行模型之所以重要，是因为很多线上故障看起来像业务 Bug，根因其实是运行时组织方式先错了：

- 状态跨线程乱飞，时序不可推理
- 某些慢任务拖住主循环
- 高峰来了以后队列无边界增长
- 锁竞争把吞吐和抖动一起拖垮

这一章真正要解决的，不是某种“更先进模型”的崇拜，而是让你能判断：不同问题模型下，应该用什么运行时组织方式承载核心状态。

## 本章文章

- [并发模型总览：从七周七并发到游戏运行时](./00.md)：先把常见并发模型的谱系摆出来，再说明游戏项目通常只会局部借用哪些思想，哪些模型适合主运行时，哪些更适合工具链、数据处理或外围系统。
- [单线程、多线程与 Actor](./01.md)：把游戏里最常被拿来做主运行时的三类执行组织方式拆开，说明它们在状态隔离、吞吐、时序可推理性上的根本差异。
- [协程、状态机与任务队列](./02.md)：讨论异步流程该怎样表达，什么时候协程更自然，什么时候显式状态机或任务队列反而更稳。
- [Tick 驱动与逻辑执行](./03.md)：把逻辑时间、调度周期、帧预算、主循环和批处理更新放回同一条运行时链路里讨论。
- [流控、背压与稳定性机制](./04.md)：说明高峰流量和慢消费者到来时，系统应该怎样限速、排队、丢弃、降级，而不是无限堆积。
- [锁竞争与性能代价](./05.md)：讨论共享状态、锁粒度、争用、缓存抖动和尾延迟为什么会把“理论并行”变成现实阻塞。
- [Epoch-driven Actor / Channel Runtime](./06.md)：以 `Epoch` 为例，说明一种强调确定性、顺序执行、固定线程和低抖动的运行时为什么适合某些游戏问题模型。
