# 9. 脚本、热更新与逻辑扩展

这一章讨论的是长线游戏里最典型的一条演进路线：为了提高迭代速度和线上修复能力，系统会逐步引入脚本层、配置驱动和热更新机制。

边界约束：

- 这里主要处理宿主与脚本的边界、扩展机制和热更新风险
- 版本体系、灰度和发布流程统一放到第 10 章

脚本和热更新从来不是免费的灵活性，它们是在“开发效率、线上风险、运行时复杂度”之间重新做平衡。

## 脚本层定位与语言选择

游戏项目喜欢脚本层，通常不是因为“脚本更高级”，而是因为它能把变化频率高的逻辑从底层宿主中剥出来。

比较适合放进脚本层的通常是：

- 高频变化的业务逻辑
- 活动或玩法扩展逻辑
- 表现层控制逻辑
- 部分 AI、事件和流程控制

不适合随意放进脚本层的通常是：

- 对性能极其敏感的核心循环
- 对安全和权威要求极高的关键结算
- 强依赖底层运行时细节的模块

语言选择时，要看的不是语法喜好，而是：

- 与宿主集成成本
- 团队熟悉度
- 调试能力
- 性能边界
- 热更新支持能力

真正成熟的判断，不是“全部脚本化”或“绝不脚本化”，而是明确哪些逻辑值得被抽出去。

## 宿主运行时与脚本 VM 集成

一旦引入脚本层，真正的难点不在脚本文件本身，而在宿主如何和脚本 VM 协作。

必须回答的问题包括：

1. 谁创建脚本环境
2. 生命周期如何管理
3. 宿主暴露哪些 API 给脚本
4. 脚本错误如何隔离
5. 脚本状态如何和宿主状态对齐

集成做得不好的常见后果是：

- 脚本能随意碰宿主内部状态
- 出错时整个运行时一起崩
- 调试时看不清宿主和脚本边界
- 性能问题无法定位

所以脚本 VM 最重要的不是“能跑起来”，而是边界清楚、错误可控、资源可回收。

## 配置驱动与脚本驱动

配置驱动和脚本驱动经常被放在一起讨论，但它们解决的问题不同。

### 配置驱动

更适合表达：

- 静态规则
- 数值参数
- 表格化内容
- 可校验关系

优点是：

- 更容易校验
- 更容易追踪
- 更适合批量管理

### 脚本驱动

更适合表达：

- 流程控制
- 条件组合
- 动态行为
- 无法被简单表格表达的逻辑

优点是：

- 灵活
- 表达能力强
- 适合快速迭代复杂规则

真正成熟的系统通常不是二选一，而是明确边界：能用配置描述的，不要轻易升到脚本；必须用脚本表达的，也要尽量限制作用域。

## 热更新体系

热更新的本质不是“线上不用发版”，而是把一部分变化从高成本发布通道转移到低成本通道。

常见热更新对象包括：

- 资源
- 配置
- 脚本
- 部分宿主可插拔逻辑

热更新的收益很明显：

- 迭代更快
- 事故修复更快
- 平台审核压力更小

但风险同样明显：

- 版本组合暴增
- 新旧逻辑并存
- 回滚更复杂
- 线上问题更难复现

因此热更新系统必须先把这些问题考虑进去：

1. 更新对象的边界是什么
2. 热更后的状态如何切换
3. 是否允许中途替换正在运行的逻辑
4. 出问题后怎么回滚
5. 如何保证客户端、资源、配置、脚本之间的依赖关系

很多团队把热更新当成“效率神器”，最后却在事故处理时付出更大代价。真正成熟的热更新体系，不是更自由，而是更可控。
