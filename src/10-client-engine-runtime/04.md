# 脚本语言与 ECS

脚本层和 ECS 在客户端里经常被一起讨论，但它们解决的其实不是同一个问题。脚本层更关心的是迭代速度、热修复能力和业务开发效率；ECS 更关心的是数据组织、系统分工和高频对象更新成本。把这两者简单打包成“新架构方案”，通常会让团队高估收益、低估代价。

所以这一节真正要回答的是：为什么客户端会想引入脚本层，为什么有些项目会转向 ECS，以及它们各自适合解决哪一类复杂度。

## 为什么脚本层会反复出现

客户端项目一旦进入长期运营和频繁迭代阶段，纯原生代码往往会承受很大压力：

- 编译和打包慢
- 小改动发版成本高
- 业务层改动和引擎层耦合太紧
- 热修复窗口有限

脚本层的价值，通常在于把高频变化的业务逻辑从较重的构建链中解耦出来，让部分模块可以更快迭代、更快修复、更快验证。

但脚本层不是白送收益。你得到的是灵活性，同时也会背上：

- VM 集成和宿主绑定成本
- 调试链路变复杂
- 性能边界需要重新划
- 代码规范和安全边界更难统一

## 为什么 ECS 会被拿出来讨论

传统对象式组织在内容规模较小、交互较简单时通常足够直观，但一旦对象数量、状态种类和更新频率上来，问题会越来越明显：

- 对象层级过深
- 组件耦合难拆
- 高频更新时缓存局部性差
- 系统行为和数据分布难以观察

ECS 的价值在于把“数据是什么”和“系统如何处理数据”拆开，让高频批处理、规则组合和运行时观察变得更明确。

## 脚本层和 ECS 不该被当成同一件武器

脚本层更适合解决这些问题：

- 业务模块高频变动
- 热更新和快速修复
- 策划或业务开发参与度更高
- 客户端逻辑需要更快试错

ECS 更适合解决这些问题：

- 对象数量多
- 状态更新频繁
- 规则组合复杂
- 需要更清楚的数据访问路径

一个系统可以同时使用脚本层和 ECS，但不能因为它们都“看起来更灵活”，就默认值得一起引入。

## 真正难的是边界，而不是接入

无论是脚本层还是 ECS，最难的通常都不是技术接入，而是边界划分：

- 哪些模块适合脚本化，哪些必须留在原生层
- 哪些系统适合 ECS，哪些依旧用对象式更直观
- 脚本层和引擎 API 的暴露面控制到什么程度
- ECS 是否真的覆盖了高频路径，而不是只增加抽象层

边界没划清时，常见结果是：

- 一半逻辑在脚本，一半逻辑在原生，调试要来回跳
- ECS 只包住表面结构，热点仍然在老路径里
- 项目为了“统一架构”强推不适合的模块改造

## 一个更稳妥的落地方式

比较稳妥的做法通常不是全量重构，而是先挑最合适的切入点：

- 用脚本层承接高频变更的 UI、配置驱动逻辑或活动逻辑
- 用 ECS 承接对象量大、更新频率高的运行时部分
- 保留原生层承接性能敏感、平台相关和底层引擎集成能力

这样做的好处是，每一层都围绕自己最擅长的问题展开，而不是为了架构统一感去做全面迁移。

## 常见误区

最常见的错误，是把脚本层当成纯粹的开发提效工具，却不补调试、监控和宿主边界治理。第二类错误，是把 ECS 当成现代化标签，没搞清楚项目真正的性能热点和数据组织问题就强推改造。第三类错误，是同时引入脚本层和 ECS，却没有清楚划分它们各自负责什么，最后只是把复杂度拆成了更多层。
