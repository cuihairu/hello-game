# 附录 A2. 按问题域归纳各类游戏

这一页保留为横向归纳索引，不再作为一级主线章节。

它和第 2 章的区别在于：第 2 章强调问题模型如何形成，这一页强调`不同品类最后会在什么工程问题上收敛`。

## 单局房间型架构

这类架构的共同点通常是：

- 房间或对局是权威单元
- 生命周期短
- 对局开始和结束边界清楚
- 状态主要围绕房间推进

因此无论是棋牌、轻卡牌还是派对玩法，经常都会在以下能力上收敛：

- 匹配和建房
- 房间逻辑实例
- 广播与重连
- 结算和回放

它们的差异主要体现在玩法规则，而不是主干服务结构。

## 强实时对战型架构

这类架构最终会围绕“连续时间下的共享状态推进”收敛。

共同问题通常包括：

- 输入采样与对齐
- 时间推进
- 预测与纠正
- 服务器权威判定
- 观战与裁决

无论外表是射击、格斗还是 MOBA，只要核心链路依赖高频实时交互，系统最终都会在同步和判定链上投入大量设计成本。

## 持续在线世界型架构

这类架构最终会收敛到“长期状态组织和分布式治理”。

共同问题通常包括：

- 世界 / 场景分片
- 在线对象路由
- 跨节点迁移
- 长生命周期状态恢复
- 多区服和跨服组织

这类系统最大的工程特征，是服务结构和运维治理会持续演化，而不是一开始就固定下来。

## 长周期成长型架构

这类架构通常在实时链路上未必最复杂，但会在外围系统上持续增重。

共同问题通常包括：

- 配置和内容生产
- 成长与养成建模
- 活动与商业化
- 数据分析
- 版本协同

很多卡牌、经营、放置、养成型产品，虽然玩法差异很大，但在工程侧最终会越来越像“内容驱动 + 数据驱动 + 运营驱动”的系统。

## 高频对象与经济平台型架构

这一类其实包含两种不同但都容易被低估的复杂度来源。

### 高频对象型

典型问题包括：

- 大量对象更新
- 高密度表现
- 带宽与 CPU 双重压力
- 客户端和服务端对象抽象差异

### 经济 / 平台型

典型问题包括：

- 资产记账
- 交易与审计
- 风控与治理
- 平台能力接入
- 外部生态约束

两者看起来很不一样，但共同点在于：复杂度往往不来自“多几个业务接口”，而是来自系统核心约束被重新定义。

## 这页的用途

这页适合在两种时候使用：

1. 当你想判断两个不同品类是否会共享同一类架构问题
2. 当你已经被“游戏类型名词”干扰，想回到更抽象的问题域看系统

它不是替代主线，而是帮助你从更高一层观察“哪些问题会反复出现”。如果一页内容无法回收成问题域，那通常说明你的分类还停留在表面品类。
