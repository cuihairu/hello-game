# 附录 A4. 压测、容量规划与扩缩容

这一页作为第 16 章的专题补充，专门把容量和扩缩容问题展开，因为这类问题在游戏项目里往往比通用后端更具场景性。

## 压测与容量规划

压测不是做一个峰值数字，而是建立“系统什么时候、因为什么、以什么形式先出问题”的认知。

真正有价值的压测目标包括：

- 找出第一个瓶颈点
- 识别延迟和吞吐的拐点
- 理解不同子系统的极限差异
- 验证故障时的表现而不只是正常时表现

容量规划则要把这些结果映射回业务现实，例如：

- 晚间高峰
- 新活动开启
- 区服合并
- 大版本回流

如果压测结果不能映射到真实玩家行为模型，最终就只是一张实验室数据表。

## 扩容、缩容与动态加服

扩容和缩容在游戏项目里，从来不是对称问题。

扩容通常更容易，因为你是在往系统里加资源；缩容更难，因为你必须处理：

- 正在运行的会话
- 正在推进的房间或场景
- 状态迁移
- 节点优雅退出

动态加服也不是简单起机器，而是要回答：

- 新实例何时接流量
- 老实例何时不再分配新对象
- 路由如何切换
- 玩家和对象是否要迁移

如果没有明确生命周期策略，扩缩容最后会变成运营手工调度。

## 分区、迁移、合服与下线

很多系统早期只考虑“怎么上线”，却没考虑“将来怎么挪”。

但长线产品里，分区、迁移、合服和下线几乎是必然问题。

这些问题共同要求系统明确：

- 对象归属如何表示
- 状态如何导出和恢复
- 迁移窗口如何组织
- 迁移失败如何回退

合服尤其容易暴露设计问题，因为它会逼你处理：

- ID 冲突
- 排行合并
- 社交关系重建
- 经济与活动数据对齐

很多架构平时看起来能跑，一到合服就暴露出“根本没考虑对象迁移和命名空间”的问题。

## 平台化运维与多地域架构

当产品规模继续变大，容量问题就不再只是“再加几台”，而会进入平台化和地域性治理阶段。

重点问题通常包括：

- 资源调度自动化
- 部署与回收自动化
- 多机房和多地域流量组织
- 跨地域延迟与容灾
- 不同地域版本和配置协同

平台化的真正目标，不是把所有机器都塞进一个平台，而是让常规运维动作从“经验操作”变成“可重复流程”。

对游戏项目来说，容量治理最终不是算力问题，而是状态治理问题。只要状态迁移、实例接流、节点摘除这些动作不清楚，机器再多也不稳。
