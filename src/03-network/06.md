# 可靠性、顺序与兼容性

“可靠送达”“顺序正确”“跨版本兼容”这三个词经常被一起提，但它们不是一件事。可靠不代表有序，有序不代表兼容，兼容更不意味着业务语义不会被误用。把这三件事混在一起，是很多网络设计和协议治理问题的起点。

## 先拆开三种语义

### 可靠性

关注的是消息最终有没有被送达、处理或确认。  
典型场景：

- 支付结果
- 资产发放
- 结算确认
- 关键状态迁移

### 顺序

关注的是消息以什么相对次序被消费。  
典型场景：

- 连续输入帧
- 聊天消息
- 房间事件序列
- 同一对象的状态变化

### 兼容性

关注的是不同版本的客户端和服务端能否对同一条消息保持一致理解。  
典型场景：

- 灰度发布
- 多端并行
- 渠道包延迟更新
- 热更新与旧包共存

这三者虽然会互相影响，但必须分开治理。

## 为什么不同消息要不同语义

同一个项目里，不同消息对这三种语义的需求差异很大：

- 角色资产变更：必须可靠，通常还要幂等，顺序往往也重要。
- 位移同步：新消息通常比旧消息更重要，晚到的旧消息可能应当直接丢弃。
- 聊天消息：通常需要相对顺序，但不应阻塞战斗主链路。
- 活动通知：可以稍晚，可以重试，但不值得拖累高频交互。

如果把所有消息都套进同一语义，系统会在不必要的地方付出时延和复杂度。

## 可靠性的工程问题，不只是重发

很多人一想到可靠性，就想到“没收到就重发”。这只解决了一小部分问题。真正的可靠语义通常还包括：

- 有没有唯一请求 ID 或消息 ID
- 重复到达时是否能幂等处理
- 服务端处理成功但回包丢了怎么办
- 客户端超时重试时会不会导致重复副作用

换句话说，可靠性的核心不只是传输，而是`最终处理语义是否可靠`。

## 顺序也不是只有“全局有序”这一种

顺序最容易被过度简化。真实项目里通常更常见的是：

- 同一连接内相对顺序
- 同一对象或同一房间内局部顺序
- 同一玩家操作流顺序

并不是所有消息都需要全局总顺序。事实上，过度追求全局顺序往往会带来很高成本和没必要的阻塞。

例如：

- 同一个角色的移动更新需要局部顺序。
- 两个独立系统的外围通知未必需要相互保序。
- 新位置到来后，旧位置更新可以直接作废。

## 兼容性不能靠传输层“顺便解决”

兼容性经常被错误地打包进“可靠协议”里。实际上它是更高层的契约治理问题，通常依赖：

- 版本协商
- 字段默认值
- 向前/向后兼容规则
- 枚举扩展规则
- 兼容窗口管理

这和 TCP 还是 UDP 没有直接关系。传输层能送过去，不代表接收方就理解得对。

## 最常见的组合策略

成熟系统通常不会给所有消息统一上“可靠 + 有序 + 兼容”三件套，而是按类型组合：

- 关键控制消息：强调可靠、幂等、明确回执。
- 输入或状态消息：强调时效性，可能允许覆盖旧值或局部顺序。
- 外围通知消息：强调最终送达，但不阻塞主链路。
- 跨版本高风险消息：强调协议治理和兼容窗口。

这种分层的好处是，系统不会在所有地方都背最高成本。

## 和业务层怎么分工

一个更现实的看法是：

- 传输层或协议层可以帮你承载部分可靠和顺序语义。
- 业务层必须自己定义幂等、覆盖、过期和补偿规则。
- 兼容性治理通常属于协议契约和版本管理层。

如果这三层责任不分，最后一定会出现一种局面：  
传输层觉得问题在业务层，业务层觉得问题在协议层，出了事故谁都解释不清。

## 一个更实用的判断问题

设计某条消息时，可以强制自己回答：

- 如果这条消息丢了，会发生什么。
- 如果它重复到了，会发生什么。
- 如果它晚到了，还要不要处理。
- 如果它和上一条顺序反了，会不会出事。
- 如果旧客户端收到它，会不会误解。

这几个问题答完，消息语义通常就清楚很多。

## 更接近最佳实践的结论

比较稳妥的做法通常是：

- 把可靠、顺序、兼容三件事拆开治理。
- 按消息类型定义不同语义，而不是统一求全。
- 让业务层显式处理幂等、覆盖、过期和补偿。
- 让协议层和版本层专门负责兼容规则。

这样系统的复杂度虽然不会消失，但至少会放在正确位置。

## 常见误区

常见误区是要求“所有消息都可靠、都有序、都兼容”，结果代价极高且并不必要。另一类误区，是完全不区分语义，把问题留给业务代码补救，最终每个模块都各自发明一套重试和幂等逻辑。第三类误区，是把兼容性误当成传输问题，结果新旧版本一起上线时整条链路都开始抖。
