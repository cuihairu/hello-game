# 游戏网络基础

游戏网络的难点，从来不只是“网络会抖”这句常识，而是玩家交互同时带着时间敏感性、长连接状态、多种消息语义和持续演进的版本环境。登录、匹配、局内输入、聊天、活动通知、支付回调和资源下载虽然都经过网络，但它们对延迟、顺序、重试和失败恢复的要求完全不同。只要把这些东西混在一起处理，主链路迟早会被拖垮。

## 为什么游戏网络不能照抄普通业务系统

普通业务系统很多时候可以把一次请求视为独立事务：发请求，等结果，失败就重试。游戏系统则不同。它经常同时存在：

- 长连接上的高频交互
- HTTP 或下载链路上的静态资源和外围请求
- 会影响当前对局的主链路消息
- 可以晚一点送达的外围通知和社交消息

也就是说，游戏网络不是一条链，而是一组链路并存。它的设计价值不在于“统一”，而在于`把不同语义的流量放在合适的地方`。

## 先区分三件事：连接、会话、消息

很多网络设计问题，起点都是把连接、会话和消息混成一个概念。更稳妥的理解方式是：

- 连接：TCP、UDP、WebSocket 或其他载体上的物理或逻辑通道。
- 会话：这个玩家当前在和哪条业务链路交互，例如登录态、房间态、世界态。
- 消息：在连接和会话中流动的最小业务单位，例如输入、广播、通知、回包。

这三者为什么必须拆开？因为它们的生命周期不同：

- 连接可能断，但会话未必失效。
- 会话可能迁移，但连接未必重建。
- 某条消息失败，不一定意味着整条会话失败。

一旦团队用同一个词描述三件事，后面关于重连、路由、踢线和恢复的讨论就会越讲越乱。

## 游戏网络里最常见的消息类型

从工程角度看，先分清消息类型比先分协议更有价值。一个项目里通常至少存在以下几类消息：

- 强控制类：登录、鉴权、进房、结算确认、支付结果、关键资产变更。
- 强实时类：位移输入、技能输入、朝向、开火、局内状态变化。
- 弱实时类：房间准备状态、队友位置、频道更新、部分社交状态。
- 外围通知类：邮件、活动红点、公告、好友上线、排行榜刷新。
- 大包下载类：热更新资源、配置、战报文件、回放文件。

这些消息在延迟、可靠性、优先级和重试语义上完全不同。游戏网络设计的第一原则，就是不要试图用一种消息处理方式把它们全部兜住。

## 接入层真正要做什么

很多团队会把接入层理解成“收包转发的薄壳”。这在简单系统里勉强成立，在长连接、高频交互、重连恢复和多种协议共存的项目里通常不够。接入层至少要关心：

- 连接建立、断开、心跳和超时
- 登录态和会话绑定
- 路由到正确房间、场景或业务节点
- 基础限流、黑名单和异常包处理
- 连接级写缓冲和背压
- 链路质量指标与重连提示

关键点是：接入层应该理解连接和会话，但不应该承载重业务逻辑。否则它一旦变慢，整条主链路都跟着抖。

## 一个更贴近真实工程的链路拆法

成熟项目通常不会追求“一种协议走天下”，而是链路分层：

- 长连接承载登录后高频交互和推送。
- HTTP 或下载链路承载资源、配置和较大的外围数据。
- 强实时消息按更严格的时延和优先级处理。
- 强可靠消息按确认、幂等和补偿链路处理。

这种设计的核心不是“多用几种技术”，而是承认不同消息失败后代价不同。你不应该让聊天消息的拥塞拖慢局内输入，也不应该让一条资源下载把房间广播卡住。

## 为什么移动网络会放大这些问题

游戏网络一旦进入真实移动环境，很多实验室里看不出的现实会被放大：

- Wi-Fi 和蜂窝切换频繁
- 地铁、电梯、地下车库导致抖动和短时断流
- 后台切前台打断连接
- 同一城市不同运营商链路差异很大
- 玩家设备性能会影响发包和收包节奏

所以游戏网络设计的目标，不是幻想网络稳定，而是承认波动是常态，并提前准备：

- 心跳和超时策略
- 快速重连
- 会话恢复
- 关键消息的幂等处理
- 重连后状态对齐

## 网络问题为什么会伪装成业务 Bug

线上大量“技能没放出来”“房间突然错乱”“角色位置飘”“通知延迟很久才到”的问题，看起来像业务逻辑错了，实际上可能是：

- 会话路由错了
- 某类消息优先级不合理
- 写缓冲积压导致高频消息被拖延
- 弱网下没有区分可丢消息和必达消息
- 重连后会话恢复不完整

这也是为什么网络层必须被当成主链路基础能力，而不是后面出问题再排查的底层细节。

## 应该先建立什么样的网络观

比较稳妥的工程观通常包括：

- 网络不是一条统一管道，而是多种语义链路叠加。
- 先按消息语义分层，再按协议和传输手段落地。
- 连接、会话、消息要严格区分。
- 主链路消息和外围消息必须隔离优先级和失败语义。
- 重连、切网、弱网、异常包处理要当常态设计，不是边缘 case。

## 更接近最佳实践的结论

游戏网络基础最重要的不是选择某个“最佳协议”，而是先把下列几件事做清楚：

- 哪些消息属于主链路，哪些属于外围链路。
- 哪些链路需要长连接，哪些用请求响应更合适。
- 连接、会话、消息三层如何映射。
- 接入层承担哪些职责，不承担哪些职责。
- 弱网和重连时，哪类状态可以恢复，哪类需要重新协商。

只有这些边界清楚了，后面再谈 I/O 模型、传输层、广播、兼容和重连，才不会各自为战。

## 常见误区

最常见的误区，是把“游戏网络”理解成“都走 socket 就行”，忽视接入、路由、压缩、兼容和异常包处理。另一类误区，是把所有消息都做成同一优先级和同一重试策略，结果主链路被外围流量拖慢。第三类误区，是只在稳定网络下看系统表现，完全不把切网、重连和后台切前台当日常流量去设计。
