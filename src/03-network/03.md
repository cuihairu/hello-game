# 传输层与接入协议选择

TCP、UDP 以及运行在它们之上的 WebSocket、KCP 类封装、QUIC 类方案，并没有抽象意义上的输赢。真正的问题不是“哪种协议先进”，而是：你的主链路更怕什么，团队能长期维护什么，目标平台和网络环境又允许你承担什么复杂度。

## 先别从协议名开始，从消息语义开始

传输层选择最常见的误区，就是一上来讨论“到底 TCP 还是 UDP”。更有用的顺序应该是：

1. 先看消息语义。
2. 再看传输需求。
3. 最后再看协议和封装。

例如：

- 登录鉴权、支付结果、角色资产变更更看重可靠性、幂等和明确确认。
- 局内位移、朝向、部分输入更看重时效性，旧消息过时后价值迅速下降。
- 聊天、邮件、通知通常可以接受较大延迟，但不能轻易丢失。
- 资源下载、战报文件、回放文件更适合稳定吞吐，不适合和实时链路混跑。

一旦先按语义分层，很多“协议争论”会自然收敛。

## TCP 的真实价值和真实代价

TCP 的最大价值，不是“老牌可靠”，而是它把很多基础语义交给内核和成熟协议栈处理了：

- 有连接
- 有序
- 可靠
- 流量控制
- 拥塞控制

这会极大降低接入层和业务层自定义协议的负担，所以大量控制类消息、会话类消息、外围推送、一般房间交互都非常适合在 TCP 或 WebSocket 之上跑。

但 TCP 也有明显代价：

- 头阻塞问题会放大混合语义消息的影响
- 旧消息可能拖慢新消息
- 你很难让不同消息天然拥有不同可靠语义
- 某些高频、低价值、过时即可丢弃的消息在 TCP 上成本并不理想

这并不意味着 TCP 不好，而是说明不要把所有东西塞进一条 TCP 语义里。

## UDP 的真实价值和真实代价

UDP 的核心价值，在于它给了你更低层级的控制权。你可以自己决定：

- 哪些消息可靠
- 哪些消息过时就丢
- 哪些消息必须保序
- 哪些消息可以覆盖旧值

这对强实时输入、局部状态同步和一些需要自定义传输语义的场景很有吸引力。

但 UDP 的代价也非常真实：

- 丢包、乱序、重传、拥塞控制都要自己处理或引入封装
- NAT、网络策略和不同平台行为更复杂
- 工具链、监控和排障门槛更高
- 团队必须长期维护一套传输语义，而不是一次接完就结束

所以 UDP 不是“更底层所以更强”，而是“更自由所以更贵”。

## 为什么很多项目会走混合路线

真实项目里，最常见的不是纯 TCP 或纯 UDP，而是混合使用：

- 登录、支付、外围控制消息走 TCP / WebSocket
- 局内输入或状态同步走 UDP 或其封装
- 大文件和资源下载走 HTTP/CDN

这种方案的好处在于：

- 每条链路都可以按自身语义优化
- 主链路和外围链路更容易隔离
- 不同平台和网络环境下更容易做降级

但它也带来新的挑战：

- 会话和身份如何在多链路之间统一
- 异常时如何回退和切换
- 监控和排障如何统一视图

所以混合路线不是“复杂但高级”，而是“更接近现实，但必须把边界补齐”。

## 在移动网络环境里要特别看什么

传输层选择一旦落到真实移动网络，几个问题会特别突出：

- 丢包不是均匀发生的，往往是突发抖动
- 切网和后台切前台会导致连接状态变化
- 不同运营商和地区链路表现差异很大
- 某些协议封装在不同平台上的兼容与运维成本差异明显

所以选择传输层时，除了理论时延和带宽外，还要问：

- 弱网时会怎样退化
- 切网时会怎样恢复
- 监控里能否看出问题发生在哪一层
- 你的团队是否真的有能力维护这套链路

## 传输层不该替业务偷懒

一个非常常见的错误，是希望“选对协议以后，业务层很多问题就自动没了”。现实并不是这样。无论选哪种协议，业务层仍然要自己回答：

- 消息是否幂等
- 状态如何恢复
- 老消息过来了怎么办
- 重试和重复送达如何处理
- 新旧版本如何兼容

传输层能帮你承载语义，不能替你定义语义。

## 一个更实用的选择框架

决定传输层时，可以先问下面几组问题：

- 这类消息更怕丢，还是更怕晚。
- 旧消息过时后还有没有价值。
- 是否需要严格保序，还是只要局部顺序。
- 是否可以接受额外开发和维护一套自定义语义。
- 当前团队对弱网、监控、排障和平台兼容的掌控力够不够。

这些问题答清楚以后，协议选择会比空谈“低延迟”和“可靠性”更扎实。

## 更接近最佳实践的结论

比较稳妥的做法通常不是迷信某个协议，而是：

- 先按消息语义分层
- 再按链路目标选择传输方式
- 最后评估团队能不能承受长期维护成本

如果项目以控制消息、房间管理和一般广播为主，TCP 往往足够好；如果局内存在大量时效性极强、过时即可丢弃的消息，UDP 或其封装才更有讨论意义；如果项目本身并不强实时，没必要为了“看起来高级”背上 UDP 语义维护成本。

## 常见误区

常见误区包括把 UDP 神化成“天然低延迟万能解”，或者把 TCP 视为“足够好所以什么都能做”。另一类误区，是只按协议名做决策，不按消息语义和维护能力做决策。第三类误区，是希望传输层替业务层解决幂等、恢复和兼容问题，结果最后还是在业务层反复打补丁。
