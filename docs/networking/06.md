# Reliability, Ordering, and Compatibility

## Category

networking / transport semantics. Node position: split reliability, ordering, and compatibility into three independent semantics, each decided separately.

## Definition


"Reliably delivered", "correctly ordered", and "compatible across versions" are three phrases often mentioned together, but they are not one thing. Reliable does not mean ordered, ordered does not mean compatible, and compatible certainly does not mean the business semantics will not be misused. Conflating these three is the starting point of many networking-design and protocol-governance problems.


## Problem

Reliable, ordered, compatible — when all three are discussed at once, "is this message actually allowed to be lost" becomes each person talking past the other; most troubleshooting arguments start here. Split the semantics first, then talk strategy.


### Split the three semantics apart first

### Reliability

Concerned with whether a message is ultimately delivered, processed, or acknowledged. Typical scenarios include:

- Payment results.
- Asset fulfillment.
- Settlement confirmation.
- Key state migration.

### Ordering

Concerned with what relative order messages are consumed in. Typical scenarios include:

- Continuous input frames.
- Chat messages.
- Room event sequences.
- State changes of the same object.

### Compatibility

Concerned with whether clients and servers of different versions keep a consistent understanding of the same message. Typical scenarios include:

- Gray release.
- Multi-client parallelism.
- Delayed channel-package updates.
- Hot updates coexisting with old packages.

The three influence each other, but must be governed separately.

### Why different messages need different semantics

Within the same project, different messages have very different needs for these three semantics:

- Character asset changes must be reliable, usually also idempotent, and ordering often matters too.
- Movement sync cares more about newer messages; late-arriving old messages should usually just be dropped.
- Chat messages usually need relative ordering, but should not block the combat primary path.
- Event notifications can arrive a bit late and can be retried, but are not worth dragging down high-frequency interaction.

If every message is forced into the same semantics, the system pays extra latency and complexity in places where it is unnecessary.

### The engineering problem of reliability is not just retransmission

Many people, upon hearing reliability, think "if not received, retransmit". That only solves a small part of the problem. True reliability semantics usually also include:

- Is there a unique request ID or message ID.
- Can duplicate arrivals be handled idempotently.
- What if the server processed successfully but the reply was lost.
- Will client timeout retries cause duplicate side effects.

In other words, the core of reliability is not just transport, but whether the ultimate processing semantics are reliable.

### Ordering is not only global ordering

Ordering is the most easily oversimplified. What is more common in real projects is:

- Relative ordering within the same connection.
- Local ordering within the same object or the same room.
- Ordering of one player's action stream.

Not every message needs a global total order. In fact, over-pursuing global ordering often brings very high cost and unnecessary blocking.

For example:

- Movement updates for the same character need local ordering.
- Notifications between two independent peripheral systems do not necessarily need to preserve ordering relative to each other.
- Once a new position arrives, an old position update can be voided entirely.

### Compatibility cannot be solved as a side effect of the transport layer

Compatibility is often mistakenly bundled into "a reliable protocol". In reality it is a higher-level contract-governance problem, usually depending on:

- Version negotiation.
- Field default values.
- Forward and backward compatibility rules.
- Enumeration extension rules.
- Compatibility window management.

This has no direct relationship with whether it is TCP or UDP. The transport layer delivering it does not mean the receiver understood it correctly.

### Common combination strategies

Mature systems usually do not apply the "reliable + ordered + compatible" triple uniformly to all messages, but combine by type:

- Key control messages: emphasize reliability, idempotency, and explicit acknowledgment.
- Input or state messages: emphasize timeliness, allowing old values to be overwritten or requiring only local ordering.
- Peripheral notification messages: emphasize eventual delivery, but do not block the primary path.
- High-risk cross-version messages: emphasize protocol governance and compatibility windows.

The benefit of this layering is that the system does not pay the highest cost everywhere.

### How should the business, protocol, and transport layers divide the work

A more realistic view is:

- The transport or protocol layer can carry part of the reliability and ordering semantics.
- The business layer must define its own idempotency, overwrite, expiration, and compensation rules.
- Compatibility governance usually belongs to the protocol contract and version-management layer.

If these three layers of responsibility are not separated, you end up in a situation where the transport layer thinks the problem is in the business layer, the business layer thinks the problem is in the protocol layer, and when an incident happens nobody can explain it.

### A more practical set of judgment questions

When designing a message, force yourself to answer:

- What happens if this message is lost.
- What happens if it arrives duplicated.
- What if it arrives late — should it still be processed.
- What if its order is reversed relative to the previous one — will anything break.
- What if an old client receives it — will it be misread.

Answer these and the message semantics are usually much clearer.

### Common pitfalls

- Requiring "every message reliable, ordered, and compatible", ending up with extremely high cost and no necessity.
- Not distinguishing semantics at all and leaving the problem to business code to patch, so every module ends up inventing its own retry and idempotency logic.
- Mistaking compatibility for a transport problem, so when old and new versions ship together the whole path jitters.

What this page really wants to emphasize is not the definitions of the three concepts, but that complexity must be layered, and each message should only pay the semantic cost it is worth paying.

### Case study: a "one extra item claimed after reconnection" investigation into duplication and ordering

> This case is a demonstration example (not drawn from a real project); numbers are rounded and simplified. It takes this page's "The engineering problem of reliability is not just retransmission", "Ordering is not only global ordering", and "A more practical set of judgment questions" into deep water: the transport layer kept retransmitting, but the books did not balance — this is an investigation into duplicate side effects and stale-value overwrites during weak-network periods, and a full unfolding of "how to label each kind of message with its semantics".

**Background and symptoms**: A certain idle-farming mobile game with frequent reconnections in subway and elevator scenarios. End-of-month reconciliation found the settlement reward ledger had **217** more entries than the client's credit records, a duplication rate of **0.9**%; the same period saw **340** daily complaints about "position rollback" and "progress reversal". Both problems concentrated within the **10**-second window after reconnection.

### Step one: symptoms and metrics — first bucket by "lost, duplicated, arrived late"

Reconciliation metric: **24100** reward-ledger entries, **23883** credited to clients, a difference of **217**; sampling **20** duplicated entries for comparison, the server received every one of them twice, processed them twice, and paid out twice.

Idempotency metric: the two duplicated requests had identical content, but the server had no unique request ID and could not distinguish "a new request" from "a retry" — the transport layer faithfully retransmitted, and the business layer accepted every one.

Ordering metric: in samples of position-rollback complaints, the client received the new position first and the old position later, and the old position packet directly overwrote the new one — movement-sync packets had no timestamp and no overwrite rule.

### Step two: layered attribution — going through this page's three-layer division of labor

```text
月末差异账 217 笔重复 + 340 单回退  归因
  回包丢失 + 客户端超时重试，业务层无幂等     217 笔重复的全部来源
  位移包无版本号，旧值覆盖新值                340 单回退的全部来源
  传输层可靠 ≠ 业务可靠：重发解决送达，不解决重复
```

Investigation path: the transport-layer retransmission worked normally (everything that should arrive did); the protocol layer had not lost fields either; the problem was in the business layer — the reward interface had no idempotency table, and movement sync had no local ordering or overwrite rules. This is exactly what this page says: "the transport layer thinks the problem is in the business layer, the business layer thinks the problem is in the protocol layer, and when an incident happens nobody can explain it".

### Step three: root cause — only half of reliability done, and ordering not done at all

Reliability only did retransmission at the transport layer, and the business layer had no idempotency: after a reply was lost, the client retried on timeout, and the server treated the retry as a new request and paid out the reward again. On ordering, the only goal was "get everything delivered"; local ordering for the same object and overwrite rules for late-arriving old values were never defined at all. The two gaps stacked, and the weak-network reconnection window became a hotspot for both duplication and rollback.

### Step four: remediation and write-back — labeling each message's semantics with this page's five questions

1. Add unique request IDs and an idempotency table to reward-class messages: duplicate arrivals directly return the first processing result instead of paying out again; replies carry the same ID so the client can reconcile by ID.
2. Give movement and state messages timestamps and sequence numbers: late-arriving old values are dropped outright, old values are voided once a new value arrives, handling follows local ordering per object, with no global sort.
3. Label semantics per kind using this page's five questions: what happens if lost, what happens if duplicated, should late arrivals still be processed, does reversed order break something, will an old side misread it — write each message kind's answers into the protocol review sheet.

Verification ledger: duplicate payouts **217** → **0**; position-rollback complaints **340** per day → **12** per day; reconciliation discrepancy rate **0.9**% → **0.01**%; in its first month the idempotency table matched **31,000** duplicate requests, all correctly returning the first result.

**Write-back checklist**:

| Write-back item | Action | Written back to |
|-----|------|--------|
| Unique request IDs and idempotency table | Reward and settlement messages carry unique IDs; the server is idempotent by ID and returns the first result on duplicate arrival | The engineering problem of reliability is not just retransmission |
| State overwrite rules | Movement and state packets carry timestamps and sequence numbers; late-arriving old values dropped outright; locally ordered per object | Ordering is not only global ordering |
| Five-question semantic labels | The protocol review sheet labels each kind by the five questions — lost, duplicated, late, reversed, old — and answers update with protocol changes | A more practical set of judgment questions |
| Acknowledgment and compensation | Key asset messages define acknowledgment semantics explicitly: when a successful reply is lost, verify and compensate by ID rather than retransmitting blindly | Common combination strategies |

### Three lessons from the case

1. **Retransmission solves delivery, not duplication; idempotency must land in the business layer**. The transport layer kept working faithfully, yet the books were still wrong — reliability asks whether "the ultimate processing semantics are reliable", not "whether the packet was sent several times".
2. **Design ordering locally per object; global ordering's cost is not worth it**. The entire root cause of position rollback was the absence of a "new value arrives, old value voided" rule — one overwrite rule is worth an entire global sort.
3. **Semantic labeling must happen before the incident; the five questions are the shortest checklist**. Answer the five — lost, duplicated, late, reversed, old — and the semantic differences between reward-class and movement-class become obvious at a glance, without waiting for a reconciliation discrepancy to teach you.
