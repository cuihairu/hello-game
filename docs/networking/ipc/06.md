# How to Choose a Communication Approach

## Category

networking / IPC. Node position: the four-step selection order — define semantics → judge command or event → pick the approach by nature → then look at non-functional cost.

## Definition

The most common failure in communication-approach selection is not that it is technically impossible, but that component comparison begins before the problem is even defined. Kafka, RabbitMQ, Redis Stream, gRPC, in-process queues, and task systems each have their value, but they suit different semantics. Selecting only by product brand usually ends in a system that "works, but nobody can explain why it works that way."

The truly reliable selection order should always come before middleware names.

## Problem

Starting component comparison before the problem is defined ends in a "works but nobody can explain why it works that way" system — most selection rework comes from this.

### Step one: define the link semantics first

Before discussing any approach, write the following down clearly:

- Must the caller obtain a result synchronously
- Single consumer or multiple consumers
- Are backlog and latency allowed
- Must ordering be preserved
- Is duplicate delivery allowed
- After a failure, is it an immediate error, a later retry, or manual compensation

If these questions are not yet answered, going on to discuss MQ, RPC, or an event bus is basically doing the design backwards.

### Step two: judge whether this link is more like a command or more like an event

If it is more like a command — that is, "please do this thing for me now and give me a definite result" — it usually leans toward a synchronous call or a synchronous entry plus asynchronous post-processing.  
If it is more like an event — that is, "this thing already happened, you all handle it as needed" — it usually leans toward event broadcast, asynchronous consumption, or publish/subscribe.

Many systems get built wrong because commands and events are mixed. The caller says they are sending an event, but in fact they are waiting for the other side to give a commitment immediately.

### Step three: pick the approach by the link's nature

### In-process or same-machine high-frequency collaboration

If you are after extremely low latency, shared context, and minimal serialization cost, prefer in-process queues, a local event bus, or lighter local IPC, rather than reaching for a cross-machine Broker first.

### Strongly interactive service calls that need immediate feedback

These links are usually better suited to synchronous RPC, because the caller needs a definite success or failure, and troubleshooting and link explainability matter more than "looking more decoupled."

### Links that need peak shaving, buffering, or multi-consumer fan-out

These links are usually better suited to Broker-style message systems, because what you actually want is not one function call, but a queue, persistence, subscription fan-out, and consumption decoupling.

### Links that take a long time but need an immediate response at the entry

These links suit a synchronous request acceptance followed by asynchronous entry into the background task system. The key is not merely switching to asynchronous; it is making explicit that "the request has been accepted" and "the task has completed" are two different things.

### Step four: then look at the non-functional cost

Even when the link semantics match, the approach still has to survive these real cost checks:

- Deployment and operations complexity
- Protocol compatibility and version-evolution cost
- Monitoring, tracing, and troubleshooting capability
- The team's familiarity with the approach
- Failure recovery, replay, and audit support

Many selections are theoretically correct but fail on landing, not because the approach is no good, but because the team was not ready to bear the governance cost it comes with.

### A more practical selection order

The steadier order is usually:

1. First define the link semantics and the cost of failure.
2. Then distinguish whether it is command-type or event-type.
3. Then judge whether it leans more toward low latency or more toward high throughput.
4. Only last, among the candidate components, pick the one with the lowest governance cost.

The core of this order is not letting middleware capability reshape the business boundary in return.

### What the different approaches are truly good at

- An in-process event bus is good at low-cost module decoupling, but not good at cross-process reliable governance.
- Synchronous RPC is good at clear interaction and real-time feedback, but not good at peak shaving and multi-consumer broadcast.
- Broker-style MQ is good at asynchronous decoupling, peak shaving, and fan-out, but not good at real-time primary-path control.
- A background task system is good at long-running handling, but not suitable to be disguised as a request that finishes immediately.

Once these boundaries are clear, many selections are actually not that hard.

### Common pitfalls

The most common error is doing selection as a product comparison rather than a problem comparison. The second error is that because some middleware already has experience inside the company, all links are forcibly shoved into the same model. The third error is choosing the right semantics for the approach but never making up monitoring, replay, dead letters, retries, and compatibility governance, so in the end the system only has the capability "can send messages," not the capability "can be operated steadily."

### Practical case: a reversed-selection-order investigation where "the middleware was fixed first and the scenario searched for afterwards, and four links were torn down and redone"

> This case is a demo example (not drawn from a real project), with numbers rounded and simplified. It takes this page's "Step one: define the link semantics first", "Step three: pick the approach by the link's nature", and "Step four: then look at the non-functional cost" into deep water: the order was reversed, and the component reshaped the business in return — this is the order investigation into selection rework, and the full unfolding of "not letting middleware capability reshape the business boundary in return."

**Background and symptoms**: A company's tech-stack meeting ruled "all new links default to Kafka," and **12** new link proposals directly reused that, with not one of the six link-semantics questions answered. After launch, instance enter/exit confirmation P99 rose from **35** ms to **780** ms; weekly operations troubleshooting tickets reached **45** — **19** replay backfills, **14** manual dead-letter handlings, **12** retry storms; **4** links with mismatched semantics were torn down and redone, wasting **5** weeks, and selection issue tickets totaled **40**.

### Step 1: Symptoms and definitions — three ledgers: feedback, governance, and rework

Feedback definition: instance enter/exit confirmation P99 rose from **35** ms to **780** ms — a strongly interactive link first had to write a topic and then wait for a consumer acknowledgment, and troubleshooting and link explainability both got worse.

Governance definition: **45** weekly operations tickets, of which **19** are replay backfills, **14** are manual dead-letter handlings, and **12** are retry storms — **19 + 14 + 12 = 45**, all ledgers for governance capability that was never made up.

Rework definition: of **12** proposals, **4** were torn down and redone, wasting **5** weeks; the **40** selection issue tickets form the attribution base count.

### Step 3: Root cause — the order was reversed, and the component defined the business in return

This page's Problem section says in its own words: starting component comparison before the problem is defined ends in a "works but nobody can explain why it works that way" system — most selection rework comes from this. The root cause is that step one was skipped: comparing components before the semantics are defined means allowing middleware capability to reshape the business boundary in return.

### Step 4: Handling and backfill — put the order back the right way up

1. Order corrected: a proposal first answers the six semantics questions and the cost of failure, then judges command or event, then fixes the latency-or-throughput leaning, and only last compares governance cost among the candidate components.
2. Approaches by nature: in-process queues and a local event bus for high-frequency collaboration, synchronous RPC for strong interaction, Broker-style message systems for peak shaving and fan-out, and a background task system for long-running handling.
3. Governance cost into acceptance: if the five — operations, compatibility, monitoring, familiarity, replay — are not all present, the selection is not considered complete.

Review ledger: instance enter/exit confirmation P99 **780** ms → **35** ms; reworked links **4** → **0** (after remediation, **12** new proposals with zero rework); weekly operations tickets **45** → **6**.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Six semantics questions | Synchronous result, single/multi-consumer, backlog, ordering, duplication, failure destination — write these down first | Step one: define the link semantics first |
| Command/event judgment | Commands go through a synchronous entry; only events go through broadcast and asynchronous consumption | Step two: judge whether this link is more like a command or more like an event |
| Nature to approach mapping | High-frequency collaboration, strong interaction, peak-shaving fan-out, and long-running handling each pick their own approach | Step three: pick the approach by the link's nature |
| Governance cost acceptance | If operations, compatibility, monitoring, familiarity, and replay — five items — are not all present, the project is not closed | Step four: then look at the non-functional cost |

### Three lessons from the case

1. **Selection is a problem comparison, not a product comparison** — a brand-first system works, but nobody can explain why it works that way.
2. **Company experience is a floor for governance, not an answer for the form** — path dependence shoves all links into the same model.
3. **Get the semantics right before talking components, and incomplete governance does not count as done** — once the order is reversed, the component defines the business in return.
