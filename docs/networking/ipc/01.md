# IPC Basics and Scenario Boundaries

## Category

networking / IPC. Node position: after the system is split apart, the semantic boundary for passing state and actions across boundaries.

## Definition

What IPC and message systems actually solve is not the abstract question of "how do processes talk to each other," but how state and actions get passed across boundaries once the system is split apart. Once processes, threads, and services are split, anything that a single in-process function call used to finish turns into the more concrete set of problems below:

- Does the caller have to wait synchronously for a result
- What to do when a message arrives more than once
- Whether recovery is still possible once ordering is wrong
- When the downstream cannot keep up, does the upstream block, drop, or back up
- After a link fails, who compensates and retries

So discussing IPC must not start from "is there a message queue," but from "what semantics is actually being passed across this boundary."

### Why a split system must take IPC seriously

In a single-process system, communication between modules is mostly in-process calling; failure semantics are relatively simple and state visibility is more direct. Once a system moves to multi-process or multi-service, the problems at the boundary multiply immediately:

- Calls are no longer free — serialization, copying, scheduling, and network latency all show up
- Failure turns from "throw an exception" into "timeout, duplication, disorder, half-success"
- Troubleshooting turns from reading a local stack into chasing cross-process links
- Version evolution starts to involve protocol compatibility and canary windows

In other words, IPC is not simply a different API; it is the first time module boundaries truly expose their cost.

## Problem

### Which problems are naturally suited to messaging

The scenarios where messaging is most valuable usually have the following characteristics:

- The producer does not have to wait synchronously for a result
- Consumers are allowed to process at their own pace
- The link cares more about peak shaving and decoupling than about the lowest latency
- The same event needs to be reused by multiple downstreams
- A downstream failure should not directly drag down the upstream main flow

Typical examples include:

- Log collection and event tracking reporting
- Record, ranking, and report updates after combat ends
- Mail, push, compensation, and notifications
- Peripheral coupling for operational campaigns
- Cross-process background task dispatch

These links are essentially more like "publish the fact, then let each downstream handle it itself."

### Which problems should not be casually made message-driven

If a link simultaneously demands the following characteristics, be very cautious:

- Strong real-time
- Strong ordering
- Strong interactive feedback
- Highly coupled context
- Hard to compensate after an error

For example:

- In-match combat input handling
- Per-frame object sync
- Real-time switching of scene control authority
- Key interactions where the player must get a definite result immediately after clicking

If these links are crudely refactored into message-queue-driven, the system often loses explainability. Latency turns from millisecond-level tail jitter into backlog uncertainty, and errors turn from "fail immediately" into "only realizing a few seconds later that some consumer did not handle it well."

### IPC is not only one form: MQ

Many teams only think of message queues when they talk about IPC — a typical pitfall. In real engineering the common forms include at least:

- In-process event bus
- Local IPC such as shared memory, pipes, and sockets
- Synchronous calls such as RPC or gRPC
- A hybrid mode of RPC combined with background tasks
- Broker-based asynchronous message systems

They solve different problems. Whether to introduce a Broker depends on whether what you actually want is low-latency calls, decoupling across boundaries, broadcast capability, or peak shaving and buffering capability.

### When judging a scenario boundary, look at these four things first

### 1. Does the caller have to know the result immediately?

If the result must be known immediately, the link usually leans more toward synchronous calls; if you only need to hand the event over reliably and can look at when the downstream finishes processing later, messaging is more suitable.

### 2. Who bears the cost of failure?

Some failures must be fed back to the player directly, such as a failed purchase or a failed instance entry; some failures can go into compensation or retry, such as a ranking refresh, report update, or push delivery. Different failure costs usually mean different communication methods.

### 3. How strong are the ordering and idempotency requirements?

If a message being duplicated once or out of order once would directly break state, it means this boundary still needs stronger control and is not suitable for casual asynchronization.

### 4. Is the link single-consumer or multi-consumer?

If an event naturally needs to be consumed by multiple systems, messaging is clearly more natural; if it is just one caller waiting for one processing result, forcing MQ onto it is often only introducing extra complexity.

### A boundary judgment closer to engineering reality

IPC links can be roughly split into two categories:

- Command-type links: more like "please do this thing for me now and return a definite result"
- Event-type links: more like "this thing already happened, each of you decide how to handle it"

Many communication designs go wrong precisely because commands and events are not distinguished. Disguising a command as an event makes the caller lose determinism; disguising an event as a command makes the system carry unnecessary synchronous coupling.

### Common pitfalls

The most common error is going straight to MQ the moment cross-process communication is mentioned, treating the message system as a universal bus. The second error is looking only at middleware capability without looking at the link's own state semantics, failure cost, and compatibility window. The third error is not distinguishing command-type and event-type boundaries, so synchronous and asynchronous semantics get mixed together and the system becomes harder and harder to explain.

### Practical case: an instance-entry boundary misjudgment investigation where "clicking enter instance gives no response, and failure is only reported ten seconds later"

> This case is a demo example (not drawn from a real project), with numbers rounded and simplified. It takes this page's "When judging a scenario boundary, look at these four things first", "IPC is not only one form: MQ", and "A boundary judgment closer to engineering reality" into deep water: a command-type link was sent out as if it were an event — this is the investigation into the dangling instance-entry feedback, and the full unfolding of "disguising a command as an event makes the caller lose determinism."

**Background and symptoms**: An MMO cut the "enter instance" interaction link wholesale from synchronous RPC to MQ asynchronous delivery. Before the change, click-to-definite-feedback P99 was **180** ms; after the change, players on average waited **2.6** seconds before getting an acknowledgment, and in failure cases the prompt only appeared after **10** seconds; instance-entry failure tickets rose from a daily average of **30** to **420**; one link-problem localization dragged from **10** minutes to **2** hours.

### Step 1: Symptoms and definitions — split "no response" into three ledgers

Feedback definition: a player clicks "Enter instance" → the UI receives a definite success or failure, and only then is this interaction complete. Record the three ledgers separately:

- **Feedback ledger**: before the change P99 **180** ms, after the change an average of **2.6** seconds, with failure feedback dragged out to **10** seconds.
- **Failure ledger**: failure tickets daily average **30** → **420**, most of them repeated clicks and follow-up questions after "clicking with no response."
- **Troubleshooting ledger**: the link went from reading a local stack to chasing cross-process links; one localization **10** minutes → **2** hours.

### Step 2: Layered attribution — item by item against this page's four questions

Item by item: the answer to the first question "Does the caller have to know the result immediately?" is "must," yet the link was sent out as an event; the answer to the second question "Who bears the cost of failure?" is "feedback the player directly," yet the failure went into a compensation queue; the single-consumer link from the fourth question was forced onto MQ. All three categories are present, and the "disguising a command as an event" line accounts for the largest share.

### Step 3: Root cause — the form was chosen before the four questions were answered

This page says in its own words: disguising a command as an event makes the caller lose determinism; latency turns from millisecond-level tail jitter into backlog uncertainty. The team first settled on "full messaging" and only then looked at the links, which is equivalent to disguising the command "do this for me now and return a definite result" as the event "this thing already happened, each of you decide how to handle it" — determinism vanished on the spot, and feedback became queueing.

### Step 4: Handling and backfill — return form selection to semantics

1. Link rollback: instance entry, purchase, and entering-scene confirmation revert to synchronous RPC; log, ranking, and push-type links keep messaging; each hybrid form returns to its place.
2. Four questions into review: a new link proposal first answers the four questions "know the result immediately, cost of failure, ordering and idempotency, single/multi-consumer," and the command-type vs. event-type judgment is written into the link document.
3. Form inventory restored: in-process bus, local IPC, RPC, Broker, and background tasks divide labor by semantics; "the moment cross-process communication is mentioned, go straight to MQ" is forbidden.

Review ledger: instance-entry feedback P99 **2.6** seconds → **170** ms; failure tickets **420**/day → **25**/day; link localization **2** hours → **8** minutes.

### Three lessons from the case

1. **"Can we get the result immediately" comes before "which middleware"** — choosing the form before the four questions are answered is doing the design backwards.
2. **The cost of failure decides the feedback channel** — failures that must be fed back to the player directly went into a compensation queue; the problem was only exposed later.
3. **Single-form is a troubleshooting cost** — five IPC forms collapsed into one, and troubleshooting went from reading a local stack to chasing cross-process links.
