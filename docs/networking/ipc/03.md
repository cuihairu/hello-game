# Primary Path vs. Peripheral Path

## Category

networking / IPC. Node position: the discrimination and discipline for the primary path (synchronous, deterministic) and the peripheral path (event-driven, compensatable).

## Definition

Where message systems most often get done wrong is not in the peripheral toolchain, but in being overused on the primary path. Many teams see that an MQ can shave peaks and decouple, and then want to event-drive the main flow too, turning an originally clear interaction into a black box that "may eventually succeed, but nobody can say when."

So when discussing message systems, the primary path and the peripheral path must be separated first.

### What is the primary path

The primary path usually refers to those paths that directly determine the current player experience, current instance state, and current interaction result, such as:

- Logging in and entering the game
- Matchmaking into a session
- Key operations inside a room
- Instance creation and entry
- Authoritative settlement at the end of combat

These paths usually share several characteristics:

- Latency-sensitive
- A definite result is required
- Failures must be fed back promptly
- Strong ordering and strong state dependencies often exist

This means the primary path values determinism more than maximum throughput.

### What is the peripheral path

The peripheral path usually refers to the follow-up handling that revolves around a primary fact, such as:

- Record archival
- Ranking refresh
- Achievement updates
- Mail and push
- Operational reports
- Event tracking and auditing

These paths usually can finish a little later, allow asynchronous retry, and are better suited to parallel handling by multiple consumers. What they actually pursue is decoupling and scalability, not the lowest latency inside the current interaction.

### Why the primary path cannot simply copy MQ thinking

If the primary path is over-messaged, common problems appear immediately:

- The player's request has already returned, but the system is still queueing internally and the final result is unknown
- Some key consumer backs up, and the primary-flow semantics start to drift
- A slight ordering disruption makes the runtime state inexplicable
- During troubleshooting you can only see "the message was sent," with no idea why the player still has not entered the room

In other words, what the primary path fears most is not coupling, but losing determinism.

## Problem

### Why the peripheral path is often better suited to events

The peripheral path is more suitable for message-driven handling because it naturally has these conditions:

- The primary fact has usually already been produced
- Multiple downstreams will handle the same fact in different ways
- A downstream failure should not directly block the primary path
- Peak shaving, retry, and delayed consumption are allowed

For example, once a battle has been formally settled, record, ranking, achievement, and report can all unfold asynchronously around the fact that "the settlement result is confirmed." This neither makes the primary settlement path carry all the peripheral cost, nor lets each peripheral system couple back into the main flow.

### A steadier way to split it

In real engineering, the steadier approach is usually not "primary path fully synchronous" or "fully asynchronous," but layering:

- Key decisions and authoritative state on the primary path complete synchronously
- Once the primary fact is settled, it is broadcast to peripheral systems as an event
- Each peripheral system consumes, retries, and compensates at its own pace

The core of this kind of layering is to first define "at which step does the business count as established," and then define "which follow-up handling can leave the current interaction moment."

### The easiest points to get wrong

### Using a message queue to carry a real-time control flow

If things like room input, real-time sync, or key control-authority switching have to pass through a Broker, no matter how good the queue is it cannot save a mismatched link.

### Broadcasting peripheral events before the primary fact has settled

If the upstream itself has not yet confirmed the final result and already sends the event to a pile of consumers, then a rollback later will plunge all peripheral systems into compensation hell.

### Peripheral systems coupling back and stalling the main flow

The most common form is that ranking, reports, and notifications — things that should be handled asynchronously — are designed as a precondition for primary-path success. This way the primary path and the peripheral path get tied together again.

### A simple decision standard

To judge whether a link leans primary or peripheral, ask three things first:

- Does the player have to know the result immediately
- Does the current runtime state have to converge immediately
- Is a downstream failure allowed to not block the current main flow

The stronger the first two, the more it leans primary; the stronger the last one, the more it suits event-driven peripheral handling.

### Common pitfalls

The most common error is treating message-driven as a symbol of architectural advancement and wanting to uniformly refactor even the primary path into an asynchronous system. The second error is not defining clearly "when does the primary fact count as established," so the primary path and peripheral path hang in the air together when a failure occurs. The third error is that peripheral systems are nominally asynchronous but in fact still decide whether the main flow succeeds, so in the end neither decoupling nor risk reduction is achieved.

### Practical case: a peripheral-coupling-back investigation where "the fight is over but no settlement comes out"

> This case is a demo example (not drawn from a real project), with numbers rounded and simplified. It takes this page's "Peripheral systems coupling back and stalling the main flow", "A steadier way to split it", "A simple decision standard", and "Common pitfalls" into deep water: what the primary path fears most is not coupling, but losing determinism — this is the investigation into the dangling settlement link, and the full unfolding of "peripheral systems are nominally asynchronous but in fact decide whether the main flow succeeds."

**Background and symptoms**: A competitive title, whose settlement link was originally P99 **320** ms. A new version shipped "settle and push the battle report at once": two steps were added serially inside the settlement transaction — a synchronous ranking refresh and a synchronous battle-report notification send. Three days after launch, at the evening peak (stacked with an operational push campaign), settlement P99 spiked to **4.8** seconds — roughly **15** times higher, and the timeout rate rose from **0.2**% to **6.1**%; customer support received **1700** tickets of "the fight is over but no settlement comes out." Combat itself was entirely normal; what was slow was the "after the fight" segment.

### Step 1: Symptoms and definitions — first turn "no settlement" into a breakable latency ledger

Unified definitions: settlement latency = combat end-state determination → settlement confirmation returned to the client. Record the three ledgers separately:

- **Combat side**: end-state determination P99 **80** ms, on par with the version before — combat did not slow down
- **Settlement side**: settlement confirmation P99 **4.8** seconds — the dangling point is here
- **Storage side**: settlement transaction commit P95 **35** ms, no lock waiting — the database did not drag it down

Combat is fast, the transaction is fast, and only "confirmation" is slow — the dangling point is neither in computation nor in storage, but in the synchronous external calls outside the settlement transaction.

### Step 2: Layered attribution — a dangling ledger from combat to external calls

```text
战斗层   终局判定 P99 80ms、判罚重算 0 起——排除战斗逻辑
存储层   结算事务提交 P95 35ms、无锁等待——排除数据库
外部账   结算确认里串行两次外部同步调用：
         排行刷新 P99 1.2s + 战报通知 P99 3.4s，通知服务被运营推送打满、重试堆积
时间账   80ms + 35ms + 1.2s + 3.4s ≈ 4.7s ≈ 结算 P99 4.8s——账能对上
```

Ledger convergence: the two external synchronous calls total **4.6** seconds, about **96**% of settlement latency — the main flow was queueing on behalf of the peripheral.

### Step 3: Root cause — the peripheral was made a precondition for main-flow success

Measured against this page's "The easiest points to get wrong," this is the standard form of "peripheral systems coupling back and stalling the main flow": ranking and notifications — things that should be handled asynchronously — were designed as a precondition for settlement success. Checking the battle-report push against the three questions of "A simple decision standard": does the player have to know the result immediately (no, being late by a few minutes is imperceptible); does the runtime state have to converge immediately (no, the battle report does not affect the match); is a downstream failure allowed to not block the main flow (it must be allowed, the notification service should not hold settlement hostage) — all three questions point to "this should be made asynchronous," yet all were serialized synchronously. "When does the primary fact count as established" was never defined either: as soon as the settlement transaction commits, the win/loss and rewards are actually already established, and ranking and the battle report are only follow-up handling around the primary fact — the third pitfall, "peripheral systems are nominally asynchronous but in fact decide whether the main flow succeeds," comes true word for word.

### Step 4: Handling and backfill — return as soon as the primary fact settles; the peripheral turns to events and self-heals

The fix: the settlement transaction commits (win/loss persisted + rewards credited) and returns to the client immediately — the primary fact has settled; ranking refresh and battle-report notification change to subscribing to the "settlement succeeded" event, each consuming, retrying, and compensating on its own, with notification failures going to a compensation queue and not rolling back the settlement; ranking latency moves to minute-level visibility (the product side confirms this is acceptable). Review: settlement P99 **4.8** seconds → **350** ms, timeout rate **6.1**% → **0.3**%, and all **1700** tickets closed out one by one (settlement and battle reports re-issued for every dangling match).

**Backfill checklist**:

| Landing point | Action | Backfill location |
|-----|------|--------|
| Primary-fact definition | "When does the primary fact count as established" written into the link document: established at transaction commit, and the peripheral is never a precondition | A steadier way to split it |
| Precondition dependency audit | Any new feature entering the settlement link must answer the three questions; synchronous calls to peripheral ranking/notification are forbidden | Peripheral systems coupling back and stalling the main flow |
| Event-driven refactor | Primary-fact event broadcast + peripheral self-subscription; failure retry and compensation never roll back the main transaction | Why the peripheral path is often better suited to events |
| Dangling monitoring | The dangling rate of "the request returned but the result did not land" goes on the dashboard; the primary-path board is separated from the combat side | Why the primary path cannot simply copy MQ thinking |

### Three lessons from the case

1. **The primary path's enemy is not coupling, it is losing determinism** — synchronizing the peripheral in serial means loading the shakiest downstream onto the link that fears jitter most.
2. **"When does the primary fact count as established" must come before the architecture discussion** — if the fact is not defined clearly, a failure hangs the primary path and the peripheral together in the air.
3. **The three-question standard is the ticket for new features to enter a link** — things the player does not need to know immediately should not make the person who just finished fighting wait for them.
