# Message Semantics, Idempotency and Ordering

## Category

networking / IPC. Node position: the convergence of delivery semantics (at-most / at-least / exactly-once) and business semantics (idempotency, ordering, unique identity).

## Definition

What is really hard about message systems is usually not "can it be sent," but "what semantics does it actually count as after being sent." If one delivery fails, can it be retried; if one message is duplicated, does it produce side effects; if two events arrive in the wrong order, can the system still explain itself.

These questions are often discussed separately, but in production they almost always appear together. Because as long as a system has retries, it will have duplicates; as long as there is concurrency and buffering, it will have disorder; and as long as there is asynchronous handling, you must discuss how business semantics actually converge.

### First distinguish "delivery semantics" from "business semantics"

Many teams start by discussing "at-least-once," "at-most-once," and "exactly-once," but what actually affects the business is what side effects are produced after a message arrives.

For example:

- At-least-once delivery may still be business-safe, as long as consumption is idempotent
- At-most-once delivery looks non-duplicative, but it may drop a key fact outright
- So-called exactly-once, even if the substrate supports it with best effort, still usually requires the business side to handle duplicate awareness and replay problems

So delivery semantics is only infrastructure semantics; whether the business is ultimately correct still depends on the idempotency design and the way state converges.

## Problem

### Why idempotency is almost a mandatory capability

As long as any one of the following exists in the system, idempotency is almost certainly needed:

- Message retry
- A consumer re-pulling after a timeout
- The upstream sending again because it never got an acknowledgment
- A client or task scheduler actively replaying

This means many important operations must answer one question: what happens if the same thing is handled twice.

Typical examples include:

- A combat settlement event is consumed more than once — are rewards issued twice
- A payment callback arrives more than once — are goods shipped twice
- An achievement progress update is triggered more than once — does it accumulate incorrectly

Without an idempotency design, an asynchronous system easily manufactures duplicate side effects the moment it enters a recovery flow.

### Why ordering is always more expensive than imagined

Many teams naturally assume "the order messages are sent is the order they are handled." This may barely hold in single-threaded, low-concurrency, no-retry situations, but once partitions, parallel consumption, failure retry, and backlog recovery are introduced, the cost of ordering rises quickly.

The question to actually ask is not "can ordering be preserved," but:

- Do you need global ordering, or only local ordering
- Ordering per player, per room, or per order
- Whether disorder can self-correct via version numbers, timestamps, or a state machine

The wider the ordering requirement, the worse the system's throughput and scalability usually are; the narrower the ordering requirement, the easier the system is to scale in parallel.

### A more realistic approach is to narrow the ordering scope

In real engineering, the steadier way is usually not to pursue global strict ordering, but to narrow the ordering scope. For example:

- Ordering for asset operations of the same player
- Ordering for settlement events of the same room
- Ordering for state transitions of the same order

This keeps the necessary semantics without tying the whole system to single-threaded handling.

### When designing message semantics, settle "unique identity" first

For idempotency and ordering to actually land, the business first needs a clear unique identity. For example:

- A combat settlement ID
- A business order number for a transaction
- A unique request number for a reward grant
- A transaction number for a migration operation

Without these unique identifiers, the system cannot tell "this is a new message" from "an old message being replayed," and idempotency and compensation afterwards have nothing to stand on.

### A consumption strategy closer to engineering practice

A steadier consumption design usually includes several things at the same time:

- Deduplication based on a business ID
- A state machine to judge whether the current message can still take effect
- Local ordering maintained within the necessary range
- A defined retry, delay, or dead-letter destination for messages that cannot be handled immediately

The point of this kind of design is not to chase some theoretically perfect semantics, but to let the system still converge when duplicates, disorder, and failures occur at the same time.

### Why "exactly-once" is so often misunderstood

What is most easily deified in engineering is "exactly-once." It is not worthless — it is often wrongly understood as "as long as the substrate supports it, the business does not need to think about duplicates or idempotency anymore." In reality, a complete business link crossing services, storages, and consumers very rarely can make all side effects absolutely unique. Often the more reliable approach is instead:

- The substrate accepts at-least-once
- The business layer is explicitly idempotent
- The audit layer keeps traceable records

This combination is usually more landable than blindly chasing "never duplicate."

### Common pitfalls

The most common error is treating substrate delivery semantics as a guarantee of business correctness. The second error is demanding global ordering for all messages, which locks the system's concurrency capability completely. The third error is having no unique business identifier and no state-machine constraint, so the moment duplicates, disorder, and retries arrive, business side effects lose control immediately.

### Practical case: a missing-unique-identity investigation where "a reward was issued twice, and achievement progress even went backwards"

> This case is a demo example (not drawn from a real project), with numbers rounded and simplified. It takes this page's "Why idempotency is almost a mandatory capability", "A more realistic approach is to narrow the ordering scope", and "When designing message semantics, settle 'unique identity' first" into deep water: retries necessarily exist, and duplication is the consequence of no defense — this is the duplication and disorder investigation for reward granting, and the full unfolding of "as long as a system has retries, it will have duplicates; as long as there is concurrency and buffering, it will have disorder."

**Background and symptoms**: A project changed reward granting and achievement progress consumption to multi-partition parallel consumption to chase throughput, with the retry strategy left on as usual: duplicate reward issuance reached **217** incidents per day on average, and achievement-progress disorder tickets reached **83** per day on average (**54** cross-partition parallel disorder + **29** old-event replay during backlog recovery), the two ledgers totaling **300** incidents; on the big-promotion day **180,000** point-currency was issued in duplicate, and a batch of players' achievement progress went backwards.

### Step 1: Symptoms and definitions — three ledgers: duplication, disorder, and the base count

Duplication definition: the same grant being handled twice counts as one duplication, reaching **217** per day on average, all from timeout re-pulls and failure retries — with no unique business identifier, retry equals duplication.

Disorder definition: a progress event arrives first and an unlock event arrives later and is rejected by the state machine, reaching **83** per day on average, of which **54** are cross-partition parallel disorder and **29** are old-event replay during backlog recovery — what the player sees is progress going backwards.

Base count definition: **217 + 54 + 29 = 300** incidents form the attribution base count, apportioned three ways at **72**% / **18**% / **10**%.

### Step 2: Layered attribution — investigated against this page's idempotency and ordering checklists

```text

  无唯一业务标识，重试即重复发奖    72%
  跨分区并行，进度与解锁事件乱序    18%
  积压恢复重放，旧事件覆盖新事件    10%
```

Item by item: the four idempotency triggers this page lists (message retry, timeout re-pull, upstream duplicate send, active replay) hit the first two; the ordering scope was not narrowed, and multi-partition parallel consumption scattered per-player ordering; backlog-recovery replay had no state machine to catch it, and old progress events pushed new events out. All three categories are present, and the no-unique-identifier line accounts for the largest share: **217 + 54 + 29 = 300**, **72**% + **18**% + **10**% = 100%, and the ledger closes.

### Step 3: Root cause — without unique identity, neither idempotency nor ordering can be discussed

This page says in its own words: as long as a system has retries, it will have duplicates; as long as there is concurrency and buffering, it will have disorder. Without these unique identifiers (settlement ID, order number, reward request number, migration transaction number), the system cannot tell "this is a new message" from "an old message being replayed" — delivery semantics is only infrastructure semantics, and business correctness still depends on the idempotency design and state convergence.

### Step 4: Handling and backfill — take unique identity and scope back together

1. Unique identity first: the four kinds — settlement ID, order number, reward request number, migration transaction number — are all mandatory; the consumer deduplicates by business ID and uses a state machine to judge whether the current message can still take effect.
2. Ordering scope narrowed: only local ordering per player, room, and order; the "global ordering" default is removed, restoring parallel scaling capability.
3. Semantics combination landed: the substrate accepts at-least-once, the business layer is explicitly idempotent, the audit layer keeps traceable records, and the destinations for retry, delay, and dead letters are explicit.

Review ledger: duplicate reward issuance **217**/day → **3**/day; progress disorder tickets **83**/day → **2**/day; idempotency-key coverage on key links **0**% → **100**%.

### Three lessons from the case

1. **Retries exist by default; duplication is the consequence of no defense** — without unique identity, the recovery flow itself is a reward-issuance incident.
2. **Global ordering is a tax on throughput** — the wider the ordering requirement, the worse the system's throughput and scalability usually are; ask first who actually needs ordering preserved.
3. **Delivery semantics is not the same as business correctness** — at-least-once plus idempotency plus auditing is more landable than deifying "exactly-once."
