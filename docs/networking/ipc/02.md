# Communication Patterns

## Category

networking / IPC. Node position: classify communication patterns by semantics (wait for a result or not, whether the receiver is unique, whether it is a broadcast, how a failure is counted), and only then talk about components.

## Definition

Once the system boundary is clear, the next step is not "which middleware to use," but "what communication pattern should this boundary actually adopt." Getting the pattern wrong means that even the most mature component only stably amplifies the error.

The distinction that is actually valuable is not by product name, but by semantics: whether the caller has to wait for a result, whether the receiver is unique, whether the message is naturally a broadcast, and after a failure whether it is an immediate error, a later compensation, or a silent retry that is allowed.

## Problem

"Which middleware" is the last question that should be answered. Getting the pattern classification wrong means even the most mature component only stably amplifies the error: where a result should be waited for, fire-and-forget is used, and settlement becomes mysticism.

### The most common classes of communication pattern

### Synchronous request-response

This is the most intuitive pattern. The caller issues a request, waits for a definite result, and then decides the next step. It suits:

- A player action must be fed back immediately
- Upstream and downstream must share the same interaction context
- An error needs to terminate the current flow immediately
- The call result directly affects the current primary path

Its advantages are clear semantics and being easiest for the caller to understand; its disadvantages are strong coupling, latency being exposed directly, and downstream jitter reaching upstream immediately.

### Asynchronous delivery

The caller hands over a task or event and does not wait synchronously for processing to finish. This suits:

- The caller cares more about "it got delivered" than about "it got finished immediately"
- Downstream can consume later
- Peak shaving or buffering is needed
- The link allows retry and compensation

Its advantages are strong decoupling and buffering; its disadvantages are that the link becomes less intuitive, and troubleshooting, ordering, duplicate handling, and receipt confirmation all become more complex.

### Publish/subscribe

After an event occurs, multiple subscribers may all need to know about it and each do their own handling. For example, after combat ends, record, ranking, achievement, report, and notification all need to be triggered. This pattern suits:

- One fact needs to be reused by multiple systems
- Upstream does not want to know which downstreams exist
- Downstream processing paces can be independent of each other

Its cost is that the event contract needs to be stable long-term; otherwise one field or semantic change affects multiple consumers at the same time.

### Request accepted + finished in the background

This is a very common hybrid pattern. The entry first synchronously confirms "the request has been accepted," and the real heavy operation completes asynchronously in the background. It suits:

- The player needs acceptance feedback immediately
- Background processing takes a long time
- The final result can be queried or pushed later

For example asset import, ranking recalculation, large settlement archival, and offline re-delivery. The key here is not the pattern itself, but that the system must clearly distinguish "accepted successfully" from "processed successfully."

### What to look at first when selecting a pattern

### Must the same interaction moment be shared?

After a player clicks a button, if they must know success or failure immediately, it leans synchronous. If the caller only needs to make sure the event was reliably accepted, and when downstream finishes does not affect the current interaction, it leans asynchronous.

### Is there only one downstream?

When one request maps to one definite handler, a synchronous call is often simpler; when one fact needs to be perceived by multiple downstreams at the same time, events or publish/subscribe are usually more natural.

### Must a failure be exposed immediately?

Some failures must be returned within the current interaction, such as a failed instance entry or a failed purchase; some failures can recover later, such as a failed report aggregation or a failed notification send. Different timings of failure exposure usually mean different communication patterns.

### Can the system tolerate backlog and latency uncertainty?

The cost of an asynchronous system is not "slower," but "the moment of completion is uncertain." If the business fundamentally cannot tolerate that uncertainty, it should not be made message-driven just for the sake of so-called decoupling.

### Common pattern combinations

In real projects, communication patterns rarely exist alone; they usually appear in combination:

- Synchronous entry + asynchronous post-processing
- Command call + event broadcast
- Local synchronous advance + cross-system asynchronous coupling

For example, room settlement might first synchronously produce the authoritative result, then asynchronously broadcast it to the ranking, achievement, and report systems. The benefit of this is that the primary path stays explainable while the peripheral path also gains decoupling.

### Changing the communication pattern is essentially moving complexity

Many teams mistakenly believe that changing a synchronous call to asynchronous lowers complexity. In reality you have only moved the complexity from "waiting during the call" into:

- Receipt confirmation
- Retry logic
- Message ordering
- Consumer idempotency
- Compensation and auditing
- Latency observation and backlog governance

So a communication pattern is not "synchronous is old, asynchronous is advanced," but "which layer should bear the complexity."

### Common pitfalls

The most common error is understanding asynchronous as an architecture upgrade and moving any link to messaging as soon as one is seen. The second error is using one fact as both a command and an event, so the caller both wants a synchronous result and pretends to be decoupled. The third error is only drawing a pattern diagram at design time without supplementing confirmation semantics, failure semantics, and observability, so in the end every pattern becomes an unstable hybrid.

### Practical case: a communication-pattern mismatch investigation where "clicking a redemption code gives no receipt, and the player clicks six times in a row"

> This case is a demo example (not drawn from a real project), with numbers rounded and simplified. It takes this page's "What to look at first when selecting a pattern", "Request accepted + finished in the background", and "Changing the communication pattern is essentially moving complexity" into deep water: where a result should be waited for, fire-and-forget is used — this is the investigation into the dangling redemption receipt, and the full unfolding of "getting the pattern classification wrong means even the most mature component only stably amplifies the error."

**Background and symptoms**: A distribution platform changed its redemption-code link from synchronous request-response to fire-and-forget delivery, under the slogan "full asynchronization." Before the change, submit-to-receipt P99 was **240** ms; after the change, players clicked "Redeem" and got no receipt, with the screen refreshing on average only after **4.1** seconds, and **1.2**% of redemption requests left dangling with no receipt; players assumed it had not succeeded and submitted repeatedly, with a single player clicking up to **6** times in a row, and duplicate-submission tickets reaching **260** per day on average.

### Step 1: Symptoms and definitions — three ledgers: receipt, duplication, and dangling

Receipt definition: a player clicks "Redeem" → the UI receives a definite success or failure, and only then is this interaction complete. Record the three ledgers separately:

- **Receipt ledger**: before the change P99 **240** ms, after the change an average of **4.1** seconds — what the player sees is "processing," and what they think is "did it not go through."
- **Duplication ledger**: no receipt forces duplicate submission, tickets reaching **260** per day on average, with a single player clicking up to **6** times.
- **Dangling ledger**: **1.2**% of requests were delivered but had neither a receipt nor a failure record, so reconciliation can only be done by manual fishing.

Item by item: the answer to the first question "Must the same interaction moment be shared?" is "must," yet the link used asynchronous delivery; the acceptance/processing separation required by "Request accepted + finished in the background" was not done; of the complexity-moving checklist (receipt confirmation, retry logic, message ordering, consumer idempotency, compensation and auditing, latency observation and backlog governance), not one item was taken up. All three categories are present, and the interaction-moment mismatch line accounts for the largest share.

### Step 3: Root cause — pattern classification comes before component, and the order was reversed

This page's Problem section says in its own words: getting the pattern classification wrong means even the most mature component only stably amplifies the error — where a result should be waited for, fire-and-forget is used, and settlement becomes mysticism. The team first settled on "full asynchronization" and only then looked at the interaction, without answering "must the same interaction moment be shared," and treated redemption, which must produce a result on the spot, as an event that could be consumed later.

### Step 4: Handling and backfill — take the complexity-moving ledgers back

1. Pattern rollback: redemption submission reverts to synchronous request-response to get a receipt on the spot; asset import and ranking recalculation move to "request accepted + finished in the background," with acceptance and processing separated.
2. Moving checklist taken up: the six items — receipt confirmation, retry logic, message ordering, consumer idempotency, compensation and auditing, latency observation and backlog governance — each get an owner.
3. Four questions into review: whether the interaction moment is shared, whether the downstream is unique, whether the failure is exposed immediately, and whether backlog can be tolerated; answer them all before selecting a pattern.

Review ledger: redemption receipt P99 **4.1** seconds → **180** ms; duplicate-submission tickets **260**/day → **11**/day; no-receipt dangling **1.2**% → **0.03**%.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Interaction-moment four questions | Links that must share the interaction moment ban fire-and-forget | What to look at first when selecting a pattern |
| Acceptance/processing separation | Synchronous returns "accepted" first; background completion sends a separate result notification | Request accepted + finished in the background |
| Complexity-moving checklist | Receipt, retry, ordering, idempotency, compensation, and observability — six items each placed | Changing the communication pattern is essentially moving complexity |
| Pattern combination baseline | Synchronous entry plus asynchronous post-processing as the default; commands and events sent separately | Common pattern combinations |

### Three lessons from the case

1. **Asynchronous is not an architecture upgrade, it is moving complexity** — with no one taking up the moving checklist, receipt and idempotency become dangling ledgers.
2. **The receipt is part of the interaction** — when a player clicks, there must be a definite result; duplicate submission is the inevitable consequence of a missing receipt, not a player problem.
3. **Pattern classification comes before component selection** — get the classification wrong, and even the most mature component only stably amplifies the error.
