# I/O Models and Event Notification

## Category

networking / networking fundamentals. Node position: the I/O organization of the access layer — the foundation for connection cost, backpressure propagation, and fault isolation.

## Definition


The access layer faces not a few short connections but large numbers of long-lived connections, continuous event streams, and high-frequency writes. The I/O model looks like a low-level implementation detail, but in practice it directly determines connection cost, latency jitter, thread utilization, how backpressure propagates, and the ability to isolate faults. Many issues like "occasional freezes at peak", "the whole layer slowing down on weak networks", and "broadcast jitter after a large reconnection wave" trace back not to business logic but to the I/O organization going out of control first.


### Why the I/O model is more sensitive in games

A game access layer typically bears several kinds of pressure at once:

- Large connection counts, with long lifecycles.
- Write traffic that comes not only from replies but also from push, broadcast, and event dispatch.
- Weak-network connections that make write buffers, timeouts, and retries more complex.
- Some messages demand extremely low latency and cannot be held up by peripheral traffic.

So the I/O model is not just about "how packets are received"; it decides:

- Who maintains connection state.
- Who reads and writes the socket.
- Who handles encoding and decoding.
- Who does session binding and routing.
- Who executes the business.
- Who absorbs backpressure.

If these responsibilities are not separated, peak load will inevitably make them drag each other down.

## Problem


### The most common mistake: letting the connection thread also do heavy business

To keep things simple early on, many systems have the thread responsible for receiving packets also finish:

- Protocol parsing.
- Session validation.
- Executing business logic.
- Querying a database or calling a remote service.
- Then writing the result back to the connection.

This saves effort at small scale, but it is dangerous under high connection counts and peak traffic. Because the moment any one of these steps slows down, the per-connection thread gets held up, and then:

- Packet reception becomes untimely.
- Write buffers pile up.
- Heartbeat and timeout judgments go wrong.
- The event loop jitters as a whole.

So mature systems usually separate connection I/O from heavy business logic explicitly.

### Common I/O organization patterns

### Blocking, or one thread per connection

Intuitive in concept, but once connection counts rise, thread and memory cost quickly get out of hand. It suits small scale or special purposes, not a high-concurrency long-connection primary path.

### Event-driven

Manages large numbers of connections uniformly through mechanisms such as `epoll`, `kqueue`, and IOCP; suited to high connection-density scenarios. It solves the cost of "waiting for I/O", but it does not automatically solve business execution or backpressure.

### Event-driven plus a business execution layer

This is the common approach closer to real projects. I/O threads handle connections, reads and writes, and basic dispatch; business threads or back-end services handle time-consuming logic. The key benefit is not having more threads, but localizing the risk that "one heavy request drags down the whole layer".

### The kinds of work that should really be distinguished in the access layer

A fairly solid split is usually:

- I/O threads: handle connection establishment, teardown, read/write readiness, and write-buffer flushing.
- Encoding/decoding layer: handle packet boundaries, protocol headers, compression and decompression, and message parsing.
- Session layer: do player binding, login-state validation, and basic routing.
- Business execution layer: handle real business logic, database queries, and cross-service calls.
- Write-back layer: deliver business results back to the connection according to priority and backpressure policy.

The value of doing this is that when any layer slows down, it is easier to isolate locally rather than immediately polluting the entire access path.

### Why write buffers and backpressure will sooner or later become the main problem

In a game access layer, slow-receiving connections are easy to notice, but slow-writing connections are more dangerous. Especially under room broadcast, push storms, and weak-network conditions, write buffers are easiest to accumulate. Typical problems include:

- A weak-network connection cannot send out for a long time, and the buffer keeps growing.
- When broadcasting to a whole room, the slowest few connections hold it up.
- The business layer keeps producing messages while never noticing that the write queue has already piled up.
- During login storms and reconnection storms, a large number of connections establish and write their first packet at once, creating a high short-term shock.

So the access layer must have an explicit backpressure policy:

- A per-connection write-buffer cap.
- A drop, degrade, or kick policy after exceeding the cap.
- Isolation between high-priority and low-priority messages.
- Batch control and tiered sending during broadcast.

Without these policies, the system will show the classic live symptom of "not fully down, but getting slower and slower".

### Event notification is not just an operating-system interface

Many people understand event notification as only `epoll` or `kqueue`. In real engineering it also includes how the application layer propagates state changes:

- How a disconnected connection notifies the session layer.
- How a session migration notifies the routing layer.
- How write-buffer backlog notifies the business layer to shed load.
- How a business result notifies the write-back layer.

If these notification semantics are not unified, the system will easily suffer:

- The connection is already disconnected, but the business keeps running.
- The player has already migrated to a new node, but the old node is still writing packets.
- Backpressure has already occurred, but the business layer keeps producing messages at high frequency.

So event notification includes both OS-level events and in-application state-propagation mechanisms.

### What to actually watch during peak scenarios

The I/O model usually turns from a low-level detail into the main problem in these scenarios:

- Peak login and mass reconnection.
- Many rooms starting matches and broadcasting at the same time.
- Push storms caused by events going live.
- The proportion of weak-network users suddenly rising.
- Some downstream service slowing down, causing the business execution layer to pile up.

At that point what truly matters is not average throughput, but:

- Event-loop jitter.
- Per-connection write-buffer length.
- Business execution queue backlog.
- Connection establishment and teardown rates.
- Heartbeat timeout and false-kick rates.

### A more solid set of principles

The access layer should do light, stable work rather than "happen to do a bit of everything". A fairly solid set of principles is usually:

- I/O threads do no heavy logic.
- Encoding/decoding and basic validation stay as linear and controllable as possible.
- The session layer does only necessary binding and routing.
- Heavy operations go to the business execution layer or back-end services.
- The write-back path is governed separately for priority and backpressure.

The core of these principles is not a worship of performance, but fault isolation.

### Common pitfalls

- Treating the access thread as a universal executor; any slow logic causes global write blocking.
- Only looking at average throughput, not peak jitter or write-buffer backlog, so the live behavior ends up as "occasional freezes".
- Not layering connection events, session events, and business events, so disconnection, migration, and write-back contaminate each other.

What the I/O model really needs to answer is not "which advanced pattern should we use", but exactly how to cut apart the responsibilities among connection, protocol, business, and write-back.

### Case study: an "ever-slower evening peak, mass heartbeat false-kicks" investigation into confused access-layer responsibilities

> This case is a demonstration example (not drawn from a real project); numbers are rounded and simplified. It takes this page's "The most common mistake: letting the connection thread also do heavy business", "Why write buffers and backpressure will sooner or later become the main problem", and "A more solid set of principles" into deep water: the packet-receiving thread conveniently did the business too — this is an investigation into responsibilities not being cut apart in the access layer, and a full unfolding of "fault isolation comes before worship of performance".

**Background and symptoms**: The access layer of a certain room-based mobile game "had the packet-receiving thread also finish" **5** kinds of heavy business: protocol parsing, session validation, executing business logic, querying the database and calling remote services, then writing the result back. Event-loop jitter at the evening peak was **350** ms, per-connection write-buffer peak was **8000** entries, and one night saw **900** heartbeat false-kicks.

### Step one: symptoms and metrics — first see which layer is slow

Impact-scope metric: during the **350** ms of event-loop jitter, untimely packet reception, write-buffer pileup, and heartbeat/timeout misjudgments appeared together; the whole layer slowed down together rather than a single connection failing.

Responsibility metric: the I/O thread carried **5** kinds of heavy business; any step being slow (one database query, one remote call) held up the per-connection thread, and every connection queued behind it waited along.

### Step two: layered attribution — going through this page's access-layer responsibility list

```text
晚高峰整层变慢归因  占比
  连接线程顺手做重业务、查库混进 I/O 线程    55%
  写缓冲无上限、背压策略缺失                27%
  连接事件、会话事件、业务事件分层不清      18%
```

Item-by-item comparison: all five kinds of work listed on this page were in the I/O thread (protocol parsing, session validation, business execution, database queries and remote calls, writing back to the connection); write buffers had no cap and no drop policy, so room broadcast was held up by the slowest few connections; disconnection, migration, and write-back contaminated each other. All three classes were present, and the heavy-business-in-the-wrong-thread item had the largest share.

### Step three: root cause — the access thread was treated as a universal executor

The first common pitfall on this page: treating the access thread as a universal executor, so any slow logic causes global write blocking. The result is the classic live symptom of "not fully down, but getting slower and slower" — average throughput still looked acceptable, while peak jitter and write-buffer backlog had already destroyed the experience.

### Step four: remediation and write-back — cutting responsibilities into five layers

1. Five-layer split: I/O threads only manage connection read/write and write-buffer flushing; encoding/decoding, session binding, business execution, and write-back each become independent layers, with all heavy operations moved out.
2. Write-buffer cap and backpressure: a per-connection write-buffer cap, with drop, degrade, or kick handling beyond it; high- and low-priority messages isolated, broadcast sent in batches and tiers.
3. Access-layer principles enter review: I/O threads do no heavy logic, the session layer does only necessary binding, the write-back path is governed separately for priority and backpressure — the core of these principles is not a worship of performance, but fault isolation.

Verification ledger: event-loop jitter **350** ms → **3** ms; per-connection write-buffer peak **8000** entries → **600** entries; heartbeat false-kicks **900** → **4**; all **5** kinds of heavy business moved out of I/O threads.

**Write-back checklist**:

| Write-back item | Action | Written back to |
|-----|------|--------|
| Five-layer responsibility split | I/O, encoding/decoding, session, business execution, and write-back isolated as five layers | The kinds of work that should really be distinguished in the access layer |
| Write-buffer backpressure cap | Per-connection cap + drop/degrade beyond the cap + high/low priority isolation | Why write buffers and backpressure will sooner or later become the main problem |
| Access-layer principle review | I/O threads do no heavy logic; heavy operations go to the business execution layer | A more solid set of principles |
| Event-layering sentinel | Connection, session, and business events notify in separate layers; disconnection, migration, and write-back do not contaminate each other | Common pitfalls |

### Three lessons from the case

1. **Average throughput deceives; peak jitter tells the truth**. Throughput alone will not reveal write-buffer backlog, so the live behavior ends up as "occasional freezes".
2. **The closer the packet-receiving thread sits to business logic, the worse the fault isolation**. Any slow step holds up the per-connection thread and the whole layer slows down together.
3. **Cutting apart responsibilities is fault isolation, not a worship of performance**. Five layers each own one segment, so when any layer slows down it is easier to isolate locally.
