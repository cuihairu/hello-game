# 传输层与接入协议选择

TCP、UDP，以及运行在它们之上的 WebSocket、KCP 类封装、QUIC 类方案，并不存在抽象意义上的“最优解”。真正的问题不是哪种协议更先进，而是你的主链路更怕什么，目标平台和网络环境允许什么，团队又能长期维护哪种复杂度。

## 不要先从协议名开始，要先从消息语义开始

传输层讨论最常见的误区，就是一上来就问“到底 TCP 还是 UDP”。更有用的顺序应该是：

1. 先看消息语义。
2. 再看传输需求。
3. 最后才看具体协议和封装。

例如：

- 登录、鉴权、支付结果、关键资产变更更看重可靠、幂等和明确确认。
- 局内位移、朝向、部分输入更看重时效性，旧消息过时后价值很低。
- 聊天、邮件、通知可以接受更大延迟，但不能轻易丢失。
- 资源下载、回放文件、战报文件更适合稳定吞吐，不适合和实时链路混跑。

一旦先按消息语义分层，很多“协议争论”会自然收敛。

## TCP 真正解决什么，又带来什么

TCP 的价值，不只是“可靠”，而是它把很多基础语义交给成熟协议栈处理了：

- 有连接。
- 有序。
- 可靠。
- 流量控制。
- 拥塞控制。

这会显著降低接入层和业务层自己维护传输语义的成本。所以大量控制类消息、会话类消息、外围推送、一般房间交互都很适合跑在 TCP 或 WebSocket 之上。

但 TCP 也有明确代价：

- 头阻塞会放大混合语义消息之间的相互影响。
- 旧消息可能拖慢新消息。
- 很难让不同消息天然拥有不同可靠语义。
- 某些高频、低价值、过时即可丢弃的消息，在 TCP 上成本并不理想。

这不意味着 TCP 不好，而是说明不要把所有链路都塞进同一种 TCP 语义里。

## UDP 真正解决什么，又让你多承担什么

UDP 的核心价值，在于它给了你更低层级的控制权。你可以自己决定：

- 哪些消息可靠。
- 哪些消息过时就丢。
- 哪些消息必须保序。
- 哪些消息可以覆盖旧值。

这对强实时输入、局部状态同步和需要自定义传输语义的链路很有吸引力。

但 UDP 的代价也非常现实：

- 丢包、乱序、重传、拥塞控制都要自己处理或引入额外封装。
- NAT、网络策略和不同平台行为更复杂。
- 工具链、监控和排障门槛更高。
- 团队必须长期维护一套传输语义，而不是一次接完就结束。

所以 UDP 不是“更底层所以更强”，而是“更自由所以更贵”。

## 为什么很多项目会走混合路线

真实项目里，最常见的不是纯 TCP 或纯 UDP，而是混合使用：

- 登录、支付、外围控制消息走 TCP / WebSocket。
- 局内输入或状态同步走 UDP 或其封装。
- 大文件和资源下载走 HTTP / CDN。

这种路线的好处在于：

- 每条链路都可以按自身语义优化。
- 主链路和外围链路更容易隔离。
- 不同平台和网络环境下更容易做降级。

但它也引入新的问题：

- 会话和身份如何在多链路之间统一。
- 异常时如何回退和切换。
- 监控与排障如何统一视图。

所以混合路线不是“更高级”，而是“更贴近现实，但边界必须补齐”。

## 移动网络环境下真正要看的不是理论时延

传输层选择一旦落到真实移动网络，几个问题会特别突出：

- 丢包往往不是均匀发生，而是突发抖动。
- 切网和后台切前台会导致连接状态频繁变化。
- 不同运营商、地区和机型表现差异很大。
- 某些协议封装在不同平台上的兼容与运维成本差异明显。

所以选择传输层时，除了看理论 RTT 和带宽，还要问：

- 弱网时会怎样退化。
- 切网时会怎样恢复。
- 监控里能否看出问题发生在哪一层。
- 团队是否真的有能力维护这套链路。

## 传输层不能替业务偷懒

另一个常见误区，是希望“协议选对了，业务层很多问题就自动没了”。现实并不是这样。无论选哪种协议，业务层仍然要自己定义：

- 消息是否幂等。
- 状态如何恢复。
- 老消息晚到后怎么处理。
- 重试和重复送达如何处理。
- 新旧版本如何兼容。

传输层能承载部分语义，不能替你定义最终业务语义。

## 一套更实用的选择框架

决定传输层时，可以先强制回答下面几组问题：

- 这类消息更怕丢，还是更怕晚。
- 旧消息过时后还有没有价值。
- 是否需要严格保序，还是只要局部顺序。
- 是否值得为这类消息承担额外传输语义维护成本。
- 当前团队对弱网、监控、排障和平台兼容的掌控力够不够。

这些问题答清楚以后，协议选择会比空谈“低延迟”和“可靠性”扎实得多。

## 常见误区

- 把 UDP 神化成“天然低延迟万能解”，忽略它真正昂贵的是长期维护成本。
- 把 TCP 当成“足够好所以什么都能做”，最后让不同语义消息互相拖累。
- 只按协议名做决策，不按消息语义、网络现实和团队能力做决策。

传输层选择真正要做的，不是挑一个听起来更先进的名字，而是让每类消息跑在自己值得付成本的链路上。
