# Transport Layer and Access Protocol Selection

## Category

networking / access protocols. Node position: choose the transport layer and protocol starting from message semantics, not from protocol names.

## Definition


TCP, UDP, and the things that run on top of them — WebSocket, KCP-style wrappers, QUIC-style schemes — have no abstract "optimal answer". The real question is not which protocol is more advanced, but what your primary path fears most, what the target platforms and network environment allow, and which level of complexity the team can maintain long-term.


## Problem

Comparing protocols before link semantics are settled is the main source of selection rework: pick WebSocket first, and later discover that frame sync (lockstep) needs an unreliable channel; adopt KCP first, and then find nobody has written the weak-network reconnection logic. Answer "what does this path fear most" first, then talk protocols.


### Do not start from protocol names; start from message semantics

The most common mistake in transport-layer discussion is opening with "TCP or UDP, definitively". A more useful order is:

1. Look at message semantics first.
2. Then look at transport requirements.
3. Only then look at the specific protocol and wrapper.

For example:

- Login, authentication, payment results, and key asset changes care most about reliability, idempotency, and explicit acknowledgment.
- In-match movement, facing, and some inputs care most about timeliness; once stale, old messages carry little value.
- Chat, mail, and notifications can tolerate larger delays but must not be easily lost.
- Resource downloads, replay files, and combat-report files are better suited to steady throughput, not to being mixed onto a real-time path.

Once you layer by message semantics first, many "protocol debates" naturally converge.

### What TCP really solves, and what it brings

TCP's value is not just "reliability"; it hands many foundational semantics to a mature protocol stack:

- Connection-oriented.
- Ordered.
- Reliable.
- Flow control.
- Congestion control.

This significantly lowers the cost of the access layer and business layer maintaining transport semantics themselves. So a large amount of control-class messages, session-class messages, peripheral push, and ordinary room interaction are well suited to run on top of TCP or WebSocket.

But TCP also has clear costs:

- Head-of-line blocking amplifies the mutual influence of messages with mixed semantics.
- Old messages can slow down new messages.
- It is hard for different messages to naturally carry different reliability semantics.
- Some high-frequency, low-value, stale-and-discardable messages are not cost-ideal on TCP.

This does not mean TCP is bad; it means you should not stuff every path into the same TCP semantics.

### What UDP really solves, and what it makes you take on

UDP's core value is that it gives you control at a lower level. You decide for yourself:

- Which messages are reliable.
- Which messages get dropped once stale.
- Which messages must stay ordered.
- Which messages can overwrite older values.

This is attractive for strong real-time input, local state sync, and paths that need custom transport semantics.

But UDP's costs are also very real:

- Packet loss, reordering, retransmission, and congestion control must all be handled yourself or via extra wrappers.
- NAT, network policies, and different platform behaviors get more complicated.
- Tooling, monitoring, and debugging thresholds are higher.
- The team must maintain a set of transport semantics long-term, not once at integration and then done.

So UDP is not "lower level, therefore more powerful"; it is "more freedom, therefore more expensive".

### Why many projects go hybrid

In real projects, the most common approach is not pure TCP or pure UDP but a hybrid:

- Login, payment, and peripheral control messages go over TCP / WebSocket.
- In-match input or state sync goes over UDP or a wrapper of it.
- Large files and resource downloads go over HTTP / CDN.

The benefits of this route are:

- Each path can be optimized for its own semantics.
- Primary and peripheral paths are easier to isolate.
- Degradation is easier across different platforms and network environments.

But it also introduces new problems:

- How sessions and identity unify across multiple paths.
- How to fall back and switch on exceptions.
- How monitoring and debugging unify into one view.

So the hybrid route is not "more advanced"; it is "closer to reality, but the boundaries must be filled in".

### On real mobile networks, what matters is not theoretical latency

Once transport selection lands on a real mobile network, several problems stand out:

- Packet loss is often not uniform but comes in bursty jitter.
- Network switching and background-to-foreground transitions cause frequent connection state changes.
- Carriers, regions, and device models behave very differently.
- Some protocol wrappers differ markedly in compatibility and operational cost across platforms.

So when choosing a transport, besides theoretical RTT and bandwidth, also ask:

- How does it degrade on weak networks.
- How does it recover after a network switch.
- Can monitoring show which layer a problem happened in.
- Whether the team can genuinely maintain this path.

### The transport layer cannot do the business layer's homework

Another common mistake is hoping that "once the protocol is chosen right, many business-layer problems disappear automatically". Reality is not like that. Whichever protocol you choose, the business layer still has to define itself:

- Whether messages are idempotent.
- How state recovers.
- What to do when an old message arrives late.
- How retries and duplicate deliveries are handled.
- How old and new versions stay compatible.

The transport layer can carry some semantics, but it cannot define your final business semantics for you.

### A more practical selection framework

When deciding the transport layer, first force answers to the following groups of questions:

- Does this kind of message fear loss more, or fear lateness more.
- Does an old message still have value once stale.
- Is strict ordering needed, or only partial ordering.
- Is it worth taking on extra transport-semantics maintenance cost for this kind of message.
- Whether the team's grip on weak networks, monitoring, debugging, and platform compatibility is sufficient.

Once these questions are answered clearly, protocol selection becomes far more solid than empty talk about "low latency" and "reliability".

### Common pitfalls

- Deifying UDP as a "naturally low-latency universal solution", ignoring that what is truly expensive is the long-term maintenance cost.
- Treating TCP as "good enough so it can do anything", ending up with different semantic messages dragging each other down.
- Making decisions by protocol name alone, not by message semantics, network reality, and team capability.

What transport-layer selection really does is not pick a name that sounds more advanced, but let every kind of message run on a path worth paying for.

### Case study: an investigation into "protocol fixed first, semantics patched later, two rounds of selection rework"

> This case is a demonstration example (not drawn from a real project); numbers are rounded and simplified. It takes this page's "Do not start from protocol names; start from message semantics", "Why many projects go hybrid", and "A more practical selection framework" into deep water: the first sentence of the project kickoff was "TCP or UDP" — this is an investigation into selection driven by protocol names, and a full unfolding of "answer what the path fears most first".

**Background and symptoms**: At kickoff, a certain competitive mobile game decreed "WebSocket across the board", stuffing **4** kinds of message semantics (login/payment, in-match input, peripheral notifications, large file downloads) into the same reliable channel; when frame sync (lockstep) testing began, head-of-line blocking dragged down input, and the weak-network room input latency peaked at **800** ms. After switching to a KCP wrapper, nobody had written the weak-network reconnection logic; the two rounds of protocol selection added up to **3** weeks of rework.

### Step one: symptoms and metrics — first tell which kind of message is waiting

Impact-scope metric: the weak-network room input latency peaked at **800** ms, experienced as "the skill button does nothing"; login/payment and resource downloads shared one queue with in-match input, waiting on each other.

Selection metric: the kickoff review records contained only the "TCP or UDP" debate, with not a single path defined by message semantics — this page puts it bluntly: answer "what does this path fear most" first, then talk protocols, and that step was skipped at kickoff.

### Step two: layered attribution — going through this page's selection framework

Item-by-item comparison: four kinds of semantics shared one channel, and this page says "you should not stuff every path into the same TCP semantics"; old messages slowed down new ones, with high-frequency low-value input queueing along; after switching to KCP, retransmission and network-switch recovery had no owner. All three classes were present, and the semantics-not-settled item had the largest share.

### Step three: root cause — starting from protocol names instead of message semantics

The first sentence of the selection meeting was "TCP or UDP", not a look at message semantics first. This page's order — message semantics first, then transport requirements, finally the specific protocol — was skipped entirely; when UDP came in, only "lower level, therefore more powerful" was seen, not "more freedom, therefore more expensive": packet loss, reordering, retransmission, and congestion control all had to be maintained by the team long-term.

### Step four: remediation and write-back — re-splitting paths by semantics

1. Semantic layering first: login, payment, and key assets go over TCP / WebSocket; in-match input and state sync go over a UDP wrapper, discarded once stale; chat and mail tolerate delay but are not lost; large files go over HTTP / CDN — each of the four message kinds takes its own path.
2. Fill in the three new problems of the hybrid route: unified multi-path session identity, exception fallback and switching, and a unified monitoring and debugging view.
3. Put the selection framework's five questions into kickoff: fears loss or lateness more, whether stale messages still have value, strict or partial ordering, whether the maintenance cost is worth it, whether the team's grip is sufficient — answer clearly before fixing the protocol.

Verification ledger: weak-network input latency peak **800** ms → **60** ms; the two rounds of protocol-selection rework **3** weeks → **0** weeks; all **4** kinds of message semantics routed per the framework.

**Write-back checklist**:

| Write-back item | Action | Written back to |
|-----|------|--------|
| Semantic layering first | Fix what each message kind fears — loss or lateness — before talking protocol names | Do not start from protocol names; start from message semantics |
| Hybrid route boundaries | Control over TCP / WebSocket, real-time over a UDP wrapper, files over CDN, plus the three new problems filled in | Why many projects go hybrid |
| The selection framework's five questions | Fear loss or lateness, stale value, ordering, maintenance cost, grip — answer clearly before deciding | A more practical selection framework |
| Protocol-name review sentinel | Ban decisions by protocol name alone; decide by semantics, network reality, and team capability | Common pitfalls |

### Three lessons from the case

1. **A protocol name is not the basis for selection; message semantics are**. Without layering by semantics, protocol debates forever spin between taste and seniority.
2. **Reliability is not free, and neither is freedom**. TCP's head-of-line blocking has a cost, and UDP's maintenance cost is higher — more freedom, therefore more expensive.
3. **The transport layer cannot do the business layer's homework**. Idempotency, state recovery, late-arriving messages, retry deduplication, version compatibility — the business layer cannot dodge a single one.

## Used By
