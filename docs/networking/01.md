# Game Networking Fundamentals

## Category

networking / networking fundamentals. Node position: treat the multiple kinds of traffic running on the same server as traffic with different semantics — the master outline for the rest of this tree.

## Definition


The genuinely hard part of game networking is not the common-knowledge fact that "networks jitter", but that the system carries multiple kinds of traffic with completely different semantics at the same time. Login, matchmaking, in-match input, chat, settlement confirmation, event notifications, payment results, and resource downloads all go through the network, but the latency, ordering, reliability, and failure-recovery behavior they demand are entirely different. If the team does not separate these semantics from the start, it is only a matter of time before problems like "chat slowing down combat", "the download path affecting broadcast", and "session misalignment after reconnection" show up.


### Why game networking cannot just copy ordinary business systems

Many ordinary business systems treat a single request as an independent transaction: send the request, wait for the result, retry on failure. Game systems, however, often have several of the following at the same time:

- Continuous interaction over a long-lived connection.
- High-frequency input and broadcast during a match.
- Out-of-match notifications, social features, and peripheral push.
- Resources, configuration, and large-packet data over HTTP or download paths.

So game networking is not a "unified request channel" but a set of coexisting paths with different semantics and different costs. The design focus is not unified handling, but placing each semantic onto the right path.

## Problem


### Separate three things first: connection, session, message

Much of the confusion in networking design discussions comes from "the connection dropped", "the session is gone", and "the message never arrived" being treated as the same kind of problem. A more solid layering is:

- Connection: the physical or logical channel on TCP, UDP, WebSocket, or some other carrier.
- Session: which business context the player is currently bound to, such as login state, room state, or world state.
- Message: the smallest business unit flowing within a connection and session, such as input, broadcast, notification, or reply.

The reason they must be separated is that their lifecycles differ:

- A connection may drop, but the session need not become invalid.
- A session may migrate, but the connection need not be rebuilt.
- One message failing does not necessarily mean the whole session failed.

Reconnection, kicks, routing, and session recovery are all, at heart, about handling the mapping between the different lifecycles of these three.

### Layering by message semantics first matters more than discussing protocols first

From an engineering-practice standpoint, the first thing game networking should do is not to settle TCP versus UDP, but to separate message semantics first. Commonly there are at least the following categories:

- Strong control messages: login, authentication, joining a room, settlement confirmation, key asset changes.
- Strong real-time messages: movement input, skill input, facing, firing, in-match high-frequency state changes.
- Weak real-time messages: ready state, some position updates, channel state, small-scope sync.
- Peripheral notification messages: mail, red-dot badges, announcements, friend-online, event refresh.
- Large-packet transfer messages: hot-update resources, configuration, combat reports, replay files.

These messages differ entirely in priority, reliability, discardability, and retry semantics. The first principle of game-networking design is not to try to cover all messages with one handling approach.

### What the access layer actually carries

The access layer can be very thin in a simple system, but in a high-frequency long-connection system it cannot be just a "receive-and-forward shell". At minimum it must handle:

- Connection establishment, teardown, heartbeat, and timeouts.
- Binding login state to the player session.
- Routing to the correct room, scene, or business node.
- Basic rate limiting, blacklists, and abnormal-packet handling.
- Write buffers, backpressure, and link-quality observation.

But the access layer also has clear boundaries: it should understand connections and sessions, and should not carry heavy business logic. Otherwise, the moment it slows down, the entire primary path jitters along with it.

### A path split closer to real engineering

Mature projects rarely aim for "one protocol to rule them all"; they layer by path instead:

- Long-lived connections carry high-frequency interaction and push after login.
- Request-response paths carry resources, configuration, and peripheral control requests.
- Strong real-time messages are handled with stricter latency and priority.
- Strong reliability messages are handled with acknowledgment, idempotency, and compensation paths.

The point of this split is not technological variety, but recognizing that different messages cost differently when they fail. You should not let a backlog of chat messages slow down in-match input, nor let a large download clog room broadcast.

### Why mobile networks amplify the problems

In a real mobile network environment, many problems that are not obvious in the lab get amplified:

- Frequent Wi-Fi and cellular switching.
- Subways, elevators, and underground garages causing short outages and jitter.
- Background-to-foreground transitions interrupting connections.
- Wide variation in link quality between carriers in the same city.
- Device performance also affecting the send/receive rhythm.

So the goal of game-networking design is not to imagine a stable network, but to accept that fluctuation is the norm and prepare in advance:

- Heartbeat and timeout strategies.
- Fast reconnection.
- Session recovery.
- Idempotency for key messages.
- Post-reconnection state renegotiation or snapshot alignment.

### Why networking problems often masquerade as business bugs

A large number of live issues like "the skill did not fire", "the room got scrambled", "position drifting", and "the notification arrived very late" look like business-logic errors, but may actually be:

- Session routing was wrong.
- A message category had an unreasonable priority.
- A write-buffer backlog slowed down high-frequency messages.
- On weak networks, discardable and must-arrive messages were not layered.
- Post-reconnection session recovery was incomplete.

This is why the network layer must be treated as a primary-path capability, not as a low-level detail to investigate only after something breaks.

### Building a more solid network view

A fairly solid engineering view usually includes:

- The network is not a single unified pipe, but a stack of multiple semantic paths.
- Layer by message semantics first, then implement by transport.
- Connection, session, and message must be strictly distinguished across three layers.
- Primary-path and peripheral messages need isolated priority and failure semantics.
- Weak networks, network switching, reconnection, and abnormal-packet handling should be designed for as steady-state conditions.

### Common pitfalls

- Treating "game networking" as "just use a socket for everything", ignoring routing, compression, rate limiting, compatibility, and abnormal-packet handling.
- Making all messages the same priority and the same retry strategy, so the primary path gets dragged down by peripheral traffic.
- Only observing the system on stable networks, without designing for network switching, reconnection, and background-to-foreground as daily traffic.

The most important thing about game-networking fundamentals is not to pick a "best protocol" first, but to first spell out the primary-path messages, peripheral paths, connection mapping, and recovery semantics.

### Case study: a "skill occasionally won't fire" incident where the primary path was dragged down by peripheral traffic

> This case is a demonstration example (not drawn from a real project); numbers are rounded and simplified. It takes this page's "Separate three things first: connection, session, message", "Layering by message semantics first matters more than discussing protocols first", and "Why networking problems often masquerade as business bugs" into deep water: every business metric green while the player experience is collapsing — this is an investigation into the primary path being dragged down by peripheral traffic during the evening peak, and a full unfolding of "how to get messages of different semantics onto their own paths".

**Background and symptoms**: A certain MMO mobile game with **150,000** DAU and **400,000** matches per day. Three weeks after launch, support started receiving tickets for "skill occasionally won't fire" and "position occasionally drifts", stabilizing at **900** tickets per day, while business metrics such as hit rate, win rate, and match duration were all normal — exactly what this page describes as "looking like a business-logic error". Tickets concentrated in the evening peak **20:00–22:00** and were nearly zero at off-peak.

### Step one: symptoms and metrics — turning "occasional" into a measurable evening-peak delta

Client instrumentation metric: skill commands are sent from the client **100**% of the time, with complete send timestamps — the problem is not in client logic.

Path latency metric: server receive timestamp minus client send timestamp; P99 rose from **45** ms at off-peak to **260** ms at peak. The same code under **3** rounds of off-peak load testing was always **45** ms.

Three-things metric: during peak, connections did not drop and sessions did not fall away, only messages arrived late — with connection, session, and message separated, the disease is in the message layer.

### Step two: layered attribution — going through this page's five message-semantic categories in turn

```text
技能指令晚到 260ms  归因
  外围通知与局内输入同队列同优先级        62%  →  161ms
  晚高峰活动刷新把接入层写缓冲顶满          27%  →  70ms
  热更资源大包与局内广播共用一条 TCP 连接    11%  →  29ms
```

Investigation path: first check business logic (hit rate normal, ruled out); then check session routing (room binding unchanged, ruled out); finally check the access-layer queue — in the queue, in-match input, chat, marquee announcements, event refresh, and hot-update downloads were mixed at the same priority in the same queue; once the evening-peak event refresh kicked in, queue backlog peaked at **12,000** entries, and the in-match input waiting behind them was dragged down along with it.

### Step three: root cause — all messages at the same priority and the same retry strategy

The access layer was just a "receive-and-forward shell" with no layering by message semantics: strong real-time messages and peripheral notification messages were crammed into the same queue, first-come-first-served, and the peripheral-message backlog transferred directly into queueing latency for in-match input. Large downloads went over the same TCP connection, further squeezing the buffer. This is exactly what this page says: "you should not let a backlog of chat messages slow down in-match input, nor let a large download clog room broadcast".

### Step four: remediation and write-back — three changes, paths split by semantics

1. Path split: in-match strong real-time messages go over an independent high-frequency channel; peripheral notification messages go into a degraded queue; hot-update resources and large packets go over an independent HTTP path, no longer sharing a connection with in-match broadcast.
2. Add message-semantic tags and priority queues to the access layer: the five categories — strong control, strong real-time, weak real-time, peripheral notification, large-packet transfer — queue separately, and when a high-priority queue fills up, peripheral messages are dropped directly instead of accumulating.
3. Idempotency for key messages plus snapshot alignment after reconnection: skill input carries a sequence number; after reconnection the server sends down a room snapshot and the client re-aligns using the snapshot as the baseline, no longer re-sending item by item.

Verification ledger: skill-command P99 latency **260** ms → **52** ms; support tickets **900** per day → **60** per day; access-layer queue backlog peak **12,000** entries → **800** entries.

**Write-back checklist**:

| Write-back item | Action | Written back to |
|-----|------|--------|
| Five-category message-semantic labels | In protocol review, label each message category's priority, reliability, and discardability, and write it into the review template | Layering by message semantics first matters more than discussing protocols first |
| Access-layer priority queues | The access layer splits queues by semantic tag; peripheral messages are dropped directly when a high-priority queue fills up | What the access layer actually carries |
| Independent path for large packets | Hot-update resources, configuration, and combat reports go over an HTTP path, physically isolated from in-match broadcast | A path split closer to real engineering |
| Reconnection snapshot alignment | After reconnection the server sends down a room snapshot and the client re-aligns using the snapshot as the baseline | Why mobile networks amplify the problems |

### Three lessons from the case

1. **When networking problems masquerade as business bugs, first separate connection, session, and message, then talk about business logic**. In this case hit rate was all green while tickets climbed; separating the three things revealed the disease was late-arriving messages, not business code.
2. **Primary-path and peripheral messages must have isolated priority and failure semantics**. Same queue, same strategy, and the peripheral backlog transfers into primary-path latency — layering is not an optimization item, it is the prerequisite for whether the primary path can survive.
3. **Design weak networks and peaks as steady-state conditions, not to laboratory-environment acceptance criteria**. **3** rounds of off-peak load testing all green, and the peak collapsed on day **1** — acceptance metrics must be built around the evening-peak traffic structure.
