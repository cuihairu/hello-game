# Data Frames and Protocol Contracts

## Category

networking / protocol contracts. Node position: treat packet-body design, evolution discipline, and exception handling as a long-term contract between client, server, and toolchain, and govern it as such.

## Definition


A protocol packet body is more than a byte format; it is also a long-term contract between client, server, access layer, toolchain, gray-released versions, and back-office systems. Many live incidents are not caused by the network going down, but by different versions, modules, and platforms reaching different understandings of the same message.


### Why protocol problems always get heavier later

At the start of a project, protocols usually look simple:

- Assign a message number.
- Put in a few fields.
- Local integration works.

But game project protocols almost certainly keep evolving. Sooner or later you will meet:

- New fields being added.
- Old fields being deprecated.
- Enumerations being extended.
- Compression, encryption, or packet-header strategy changing.
- Hot updates and channel builds coexisting.
- Client and server versions not being perfectly in sync.

If the protocol lacks contract awareness at this point, the system can only rely on a very fragile assumption: every participant upgrades together forever, and never misreads a field.

## Problem


### What a protocol contract really contains

A mature protocol contract is usually not just "what the fields look like"; it should contain at least:

- The business semantics of a message number or message type.
- Request and response structure definitions.
- Field meanings, default values, and optionality rules.
- Enumeration extension rules.
- Error-code semantics.
- Compatibility windows and version negotiation.
- Handling of abnormal packets and illegal values.

In other words, what a protocol contract really defines is: how different parties keep a consistent understanding of the same message.

### Why game protocols are harder to govern

A game protocol usually has far more participants than an ordinary interface system:

- Multiple platform clients.
- Access layer and gateway.
- Multiple back-ends: room servers, world servers, event servers.
- Automated tests, packet capture and replay, and debugging tools.
- GM or operation back offices.

Once there are many participants, protocol instability costs not just a failing interface but drags the whole primary path into a compatibility and regression quagmire.

### What really matters when designing packet bodies

### 1. The outer packet header must be stable

Most projects have their own outer packet header, used to carry:

- Message number or routing key.
- Session identifier.
- Sequence number or request ID.
- Compression flag.
- Encryption flag.
- Length field.

The most important thing about the header is not complexity but stability. Once it changes frequently, the access layer, packet-capture tools, debugging tools, and abnormal-packet handling logic all jitter along with it.

### 2. The business payload must have clear semantics

The payload is usually where protobuf, a custom binary structure, or another serialization format is the main body. What matters most here is not syntactic elegance, but:

- Whether fields have clear semantics.
- Whether default values are safe.
- Whether old and new versions can still work when meeting an unknown field.
- Whether old logic stays stable after a field is removed.

### 3. Error returns must be layered

Many protocol problems actually stem from error returns not being systematic. A more solid approach is usually to distinguish:

- Protocol-layer errors.
- Session-layer errors.
- Business-layer errors.

Otherwise, when the client receives a failure result, it has no idea whether to reconnect, retry, re-login, or just notify the player.

### What protocol evolution fears most

What protocol evolution fears most is not that fields multiply, but that changes happen without rules. Typical disasters include:

- The server assumes a new field always exists, but old clients never send it at all.
- After a new enum value is added, the old side treats it as an illegal value.
- A field changes from optional to required with no compatibility window.
- The same message number is given different business meanings across versions.

These problems may be unobvious in a uniform single-version environment, but as soon as they enter gray release, multi-client parallelism, and delayed channel review, incidents are easy.

### Protocol governance is not a serialization-format selection question

Choosing protobuf, flatbuffers, or a custom binary structure is all fine; what really determines the system's lifespan is often not the format itself but whether governance rules exist. A fairly solid governance usually includes:

- Explicit rules for adding and deprecating fields.
- Not easily reusing old message numbers.
- Keeping compatibility windows.
- Protocol changes accompanied by documentation and tests.
- Automatic checks of differences between old and new protocols.

If these rules do not exist, the protocol will slowly rot even if the format itself is mature.

### What must be answered in advance when multiple versions coexist

As long as a project has:

- Gray release.
- Delayed channel review.
- Hot updates.
- Different platforms with different release cadences.

then you must answer in advance:

- When client and server versions do not match, who rejects whom first.
- Which protocols must be upgraded in strict sync.
- Which protocols can transition smoothly via default values and compatibility fields.
- Whether a room may hold both old and new versions.

If these questions are not written into rules ahead of time, you end up relying on "everyone be careful at release time".

### Abnormal packets and illegal values cannot rely on trust alone

There are many sources of abnormal packets in the game environment:

- Client bugs.
- Version incompatibility.
- Cheating tools tampering.
- Link truncation or incorrect packet assembly.

So the protocol layer must have an explicit illegal-packet handling strategy, such as:

- Drop.
- Rate limit.
- Disconnect.
- Record an audit log.
- Trigger a higher-level reconnection or re-login.

This is not a security bonus question; it is part of stability governance.

### Common pitfalls

- Treating the protocol as an internal implementation detail, so changing a field only needs "local integration to pass".
- Frequently changing packet bodies without version negotiation and a compatibility window, dragging client, access layer, and server into a regression quagmire together.
- Watching only the serialization format and not doing protocol governance, so the system eventually dies on evolution rules.

What data-frame design really governs is not "how the bytes are arranged" but how a protocol, as a long-term contract, evolves stably.

### Case study: a "new version gray release, all old clients fail en masse" investigation into field changes

> This case is a demonstration example (not drawn from a real project); numbers are rounded and simplified. It takes this page's "What protocol evolution fears most", "Error returns must be layered", and "What must be answered in advance when multiple versions coexist" into deep water: new and old packages each at **5**% gray, yet failure rates differ by two orders of magnitude — this is an investigation into the protocol compatibility window during gray release, and a full unfolding of "how to make protocol changes not drag multi-platform into a regression quagmire".

**Background and symptoms**: A certain card mobile game shipped a new version, with **5**% gray on the new package and **95**% on existing old packages. Within **2** hours of the gray starting, the old clients' room-join failure rate spiked to **3.8**% while the new package was only **0.02**%; support's phrasing was "after updating I still can't get in". Client errors were uniformly "network error, please re-login", and re-login QPS peaked at **4200** — **7**× normal — and the re-login storm in turn squeezed the login path.

### Step one: symptoms and metrics — first bucket by version, then layer by error

Version bucketing metric: the **3.8**% failure rate was entirely concentrated in the two older versions (the package from two weeks ago and last week's), while the new package's **0.02**% was level with the historical baseline — the problem is only in the version difference, not the path.

Error layering metric: server logs split these failures three ways — **71**% room-join message parse failures (protocol layer), **22**% disconnections on receiving an unknown enum value (protocol layer), **7**% valid session but business rejection (business layer). And the client displayed all three errors identically as "network error, please re-login", because error codes were not layered.

Packet-capture metric: capturing the same room-join message from the new and old packages and comparing, the same message number but a different payload structure.

### Step two: layered attribution — comparing item by item against this page's evolution disaster list

```text
旧端进房失败 3.8%  归因
  新字段从可选变必填，旧端不发送解析失败    71%  →  2.7 个百分点
  枚举新增值被旧端当非法值断连             22%  →  0.8 个百分点
  错误码不分层放大成重登风暴                7%  →  0.3 个百分点
```

Item-by-item comparison: the server added a `season` field to the room-join message and parsed it as required, but the old side never sent that field at all — **71**% of the failures hit this page's disaster list item one directly, "the server assumes a new field always exists, but old clients never send it"; the same release also extended the room-type enum, and the old side treated the new value as illegal and disconnected, hitting item two.

### Step three: root cause — no compatibility window, no version negotiation, error codes not layered

This release changed both field requiredness and enum values at once, and both changes went live on "local integration passes": no compatibility window, no version-negotiation rules, and error returns not split into protocol layer, session layer, and business layer. The three gaps stacked, and a field addition that could have transitioned smoothly became old-side disconnections plus a re-login storm.

### Step four: remediation and write-back — stop the bleeding first, then get the rules on record

1. Stop the bleeding: roll back the requiredness of the room-join message, return `season` to optional with a safe default value, and have new enum values go to the old side over the old message number — failure rate fell back to **0.05**% within **30** minutes.
2. Three-tier error codes: protocol layer (parse failure → reconnect), session layer (session invalid → re-login), business layer (business rejection → UI prompt); the client decides its action by layer and no longer re-logins uniformly.
3. Rules on record: new fields default to optional, deprecation is marked before deletion, enum extensions must carry an old-side handling strategy, and the compatibility window is at least one version cycle — written into the protocol change checklist, with every protocol PR attaching an old-versus-new diff comparison test.

Verification ledger: old-side room-join failure rate **3.8**% → **0.05**%; re-login QPS peak **4200** → **300**; support tickets caused by disconnections cleared to zero; the next release re-checked on the same metrics, with both older package tiers below **0.1**% failure within the compatibility window.

**Write-back checklist**:

| Write-back item | Action | Written back to |
|-----|------|--------|
| Field add/deprecate rules | New fields default to optional with a safe default; deprecation is marked before deletion, and old-side references are checked before removal | What a protocol contract really contains |
| Three-tier error codes | Protocol layer / session layer / business layer coded separately; the client decides reconnect, retry, re-login, or prompt by layer | Error returns must be layered |
| Compatibility window and version negotiation | A compatibility window of at least one version cycle; when multiple versions coexist, who rejects whom first is written into rules in advance | What must be answered in advance when multiple versions coexist |
| Abnormal-packet handling strategy | Illegal values handled by tiered drop, rate limit, disconnect, audit — no longer disconnect uniformly | Abnormal packets and illegal values cannot rely on trust alone |

### Three lessons from the case

1. **A protocol is a long-term contract; before changing a field, ask what happens to the old version**. "Local integration passes" validates a single-version environment; once gray release begins it is a multi-version environment — requiredness changes and enum extensions both need an old-side strategy.
2. **Without layered error codes, the client can only re-login uniformly, and a re-login storm hurts more than the original fault**. This case's **7**% of business-layer errors amplified into **7**× re-login QPS; layered error codes are a stop-the-bleeding measure, not just an experience improvement.
3. **Gray release is the compatibility window; rules must be written in advance, not "everyone be careful at release time"**. Field, enum, and error-code compatibility rules recorded as a checklist is what withstands stacked channel-review delays and hot-update windows.
