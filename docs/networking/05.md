# Message Patterns and Event Dispatch

## Category

networking / message patterns. Node position: the boundaries and division of labor among request-response, push, broadcast, subscription, and internal event streams.

## Definition


Request-response, server push, room broadcast, world broadcast, subscription dispatch, and internal event streams are not just differences in communication style; they decide how the system organizes state propagation. Choose the wrong message pattern and complexity lands in the wrong place: either the primary path is hijacked by peripheral traffic, or every business module invents its own set of message semantics.


### Why message patterns must be split by semantics

Game paths naturally contain several completely different interactions at once:

- Request-response of the "I initiate an action and wait for a definite result" kind — login, purchase, joining a room.
- Push of the "the server proactively tells you what happened" kind — room state changes, combat events, position updates.
- Broadcast when multiple players share state in a room or scene.
- Peripheral notifications such as events, mail, and friend-online.
- Asynchronous events inside the service, such as notifying the battle-record, event, instrumentation, or audit systems after settlement.

If all these interactions are made one single pattern, problems will inevitably accumulate.

## Problem


### What request-response suits, and what it does not

Request-response is best suited to scenarios needing clear cause-and-effect and a definite receipt:

- Login.
- Joining a room.
- Purchase.
- Gacha draws.
- Claiming rewards.
- Fetching configuration.

Its value lies in:

- Clear causality.
- Clear error handling.
- Easier client state-machine organization.

But it does not suit carrying continuous state sync and high-frequency broadcast. Because once "state changes" are also forced into "send a request and wait for a reply", the system becomes long-winded and bloated with replies, and the server pays the cost of a large number of meaningless acknowledgments.

### Push and broadcast are unavoidable in games

As soon as players need to share the same space, the same room, or the same event state, the server necessarily needs to push state and events proactively. Typical scenarios include:

- Other players' ready-state changes in the room.
- Skill hits, HP changes, and object creation/destruction in combat.
- Scene channels and world-level public events.
- Event opening, closing, and settlement.

The essence of broadcast is not "send to everyone", but "who should know what changed". If this step is designed poorly, both bandwidth and client consumption cost spiral out of control.

### Do not mix internal event streams and the external protocol layer into one

Inside the service, event dispatch is also needed, for example:

- Triggering battle-record writes after settlement completes.
- Triggering fulfillment and audit after a successful payment.
- Triggering quest and achievement progress after a player levels up.

These internal event streams and the network protocol layer toward clients should not be conflated into one concept. The reason is simple:

- Internal events care more about decoupling, retry, idempotency, and asynchronous consumption.
- External protocols care more about latency, reply semantics, session state, and player experience.

Forcibly unifying the two into one "universal message framework" usually ends up serving neither side well.

### What broadcast should consider first

What is truly expensive about broadcast is not just sending it out, but:

- To whom it is sent.
- At what granularity.
- How often it is sent.
- How the client consumes it.

A fairly solid broadcast design usually layers first:

- Must-receive broadcast to everyone in the room.
- Local-object broadcast within the room.
- Scene- or channel-level broadcast.
- Peripheral broadcast that can be delayed, merged, or degraded.

Without this layering, the system quickly degenerates into "send the full state on every change, and let whoever uses it filter it themselves".

### Why event-dispatch boundaries easily lose control

Once message patterns have no boundaries, the most common symptoms are:

- The client passively waits for too many replies for a single result.
- The server maintains several similar broadcast logic sets at once.
- One simple state change triggers large downstream sync jitter.
- Peripheral systems intrude into the primary path just to consume events.

So mature systems usually deliberately distinguish:

- Primary-path request-response.
- Primary-path state push.
- Room or scene broadcast.
- Background asynchronous events.

The concepts look like they multiplied, but in practice this reduces long-term system chaos.

### A division of labor closer to practice

A fairly solid design is usually:

- Strong interactive flows stay as explicit request-response.
- Combat and room state changes use push or broadcast.
- Peripheral linkage goes through asynchronous event streams.
- Do object layering and recipient culling before broadcast.
- Make clear to the client which messages will arrive proactively, and which it must initiate a request for.

The benefits of doing this are:

- A more controllable primary path.
- More decoupled peripheral paths.
- Easier isolation of performance and priority.

### Message patterns directly shape service boundaries

This is not an abstract discussion. The message patterns you adopt usually map directly onto how services are organized:

- If everything goes through synchronous request-response, services become more tightly coupled.
- Once state sync and event streams are layered, peripheral services are more easily made asynchronous.
- Once broadcast semantics are explicit, the responsibilities of room servers and scene servers become clearer.

In other words, message patterns are not a communication aesthetic; they are part of service-boundary design.

### Common pitfalls

- Stuffing all messages into a unified dispatch framework, ending up with neither path boundaries nor priority isolation.
- A broadcast strategy as crude as "send the full state on every change", dragging both the network and clients into high-cost updates.
- Mixing internal event streams and the client protocol layer into one, so neither asynchronous decoupling nor real-time feedback is done well.

What message-pattern design really needs to answer is not "which style to choose", but through which propagation channel each kind of state change should leave the current module.

### Case study: a "one universal message framework drags down the primary path and the periphery together" investigation into boundary loss of control

> This case is a demonstration example (not drawn from a real project); numbers are rounded and simplified. It takes this page's "Why message patterns must be split by semantics", "What broadcast should consider first", and "A division of labor closer to practice" into deep water: all messages went into the same framework — this is an investigation into message patterns without boundaries, and a full unfolding of "each kind of state change takes its own propagation channel".

**Background and symptoms**: A certain project stuffed **5** kinds of messages (request-response, state push, room broadcast, peripheral notifications, internal events) into the same dispatch framework, with no path boundaries and no priority isolation. At the evening peak, combat-push latency P99 was **1200** ms, with instrumentation and audit events squeezing the same queue as skill results; room broadcast "sent the full state on every change", and **70**% of bandwidth was taken by full-state broadcast.

### Step one: symptoms and metrics — first see who is squeezing whom

Impact-scope metric: combat-push latency P99 **1200** ms, seen by players as HP changes arriving half a beat late; peripheral events and primary-path messages shared a queue, waiting on each other.

Broadcast metric: full-state broadcast took **70**% of bandwidth; the client passively waited for too many replies for a single result, and had to filter them once more locally.

### Step three: root cause — treating message patterns as a debate over communication style

This page's Problem puts it directly: choose the wrong message pattern and complexity lands in the wrong place — either the primary path is hijacked by peripheral traffic, or every business module invents its own set of message semantics. The team treated "which style to choose" as an aesthetic question and never answered through which propagation channel each kind of state change should leave the current module.

### Step four: remediation and write-back — splitting propagation channels by semantics

1. Five kinds, each on its own: strong interactive flows stay explicit request-response; combat and room state go through push or broadcast; peripheral linkage goes through asynchronous event streams; do object layering and recipient culling before broadcast.
2. Four-tier broadcast culling: must-receive for the whole room, room local objects, scene/channel level, and degradable peripheral broadcast, controlling granularity and frequency tier by tier.
3. Primary-path priority isolation: request-response, state push, room broadcast, and background asynchronous events governed as four separate paths, with the client clear about which messages arrive proactively and which require initiating a request.

Verification ledger: combat-push latency P99 **1200** ms → **40** ms; full-state broadcast bandwidth share **70**% → **18**%; all **5** kinds of messages routed by semantics.

### Three lessons from the case

1. **The essence of broadcast is not "send to everyone" but "who should know what changed"**. Leave this unanswered, and both bandwidth and client consumption cost spiral out of control.
2. **Message patterns are not a communication aesthetic but part of service-boundary design**. How messages travel is how services split.
3. **Internal and external events must be two separate sets**. Internal events care about decoupling, retry, idempotency; external protocols care about latency, reply semantics, and experience — mixed into one, neither is done well.
