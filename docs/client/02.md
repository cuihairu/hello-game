# Client-Server Boundary and Network Layer

## Category

client / client-server boundary. Node positioning: draws the line clearly among the presentation logic, interaction logic, and authority logic layers — adjudication, prediction, rollback, and disconnection recovery all presuppose this boundary.

## Definition


Many client architecture problems, on the surface they look like "the network is unstable" or "the server-side logic is too heavy," but in essence it is really that the client-server boundary was never drawn. After a player clicks once, does the client respond first and the server confirm afterward, or must it wait for the authority to return; can the client predict, cache, and replay; after a reconnect, whose state is the source of truth — none of these questions belongs to the network layer alone. They are boundary problems.

If the client-server boundary is not defined clearly, the most common consequence is not that some feature fails to ship, but that the system lives long term in a chaotic state of "sometimes the client decides, sometimes the server decides."

## Problem

On the surface it is "the network is unstable" and "the server logic is too heavy"; in essence the boundary is not drawn: can the client predict, cache, replay, and after a disconnect whose state wins, and for a single click does it respond first or wait for the authority to return. A project with an unclear boundary is either punched through by cheating (adjudication on the client) or dragged down by experience (waiting for the server for everything).


### Why the client cannot be treated as just a display

The client naturally holds a lot of local capability:

- input and immediate feedback
- local UI state and interaction rhythm
- local caching and asset scheduling
- visual prediction, interpolation, and presentation correction
- experience fallback during disconnect, weak network, and retries

If none of these capabilities are used at all, the experience is poor; if they expand without a boundary, they start invading adjudication and authoritative state. So the real difficulty has never been "should the client do logic," but "what kind of logic should the client do."

### The most important boundary: presentation logic, interaction logic, and authority logic

A fairly safe way to understand this is to separate the three kinds of logic first:

- Presentation logic: effects, animation, camera, UI transitions, local hints
- Interaction logic: input response, page state, local validation, local prediction
- Authority logic: asset changes, combat adjudication, matchmaking results, room state, payment results

The first two can often stay on the client in exchange for a fluid experience; the third usually must be decided by the server or an authoritative runtime. The problem often lies in the boundary being unclear — some authoritative judgment quietly grows into the client, and later the server patches it up.

### What the network layer really solves is not send/receive but state convergence

The network layer of course handles protocol, serialization, reconnect, heartbeat, timeout, and weak network, but the more fundamental question is:

- how local state aligns with remote authoritative state
- how to reclaim a prediction once the client predicted wrong
- which state is allowed to keep advancing locally during a disconnect
- after reconnect, does it pull a snapshot, catch up increments, or re-enter

In other words, the most critical thing about the network layer is not "sending the data to the other side" but having client and server converge on the same state semantics.

### Which capabilities suit the client

What suits the client are usually those capabilities that clearly improve experience but do not decide final adjudication, such as:

- local pre-play of animation windup and hit presentation
- UI state machine and interaction flow
- path preview, skill indicators, local hints
- asset caching and resume-from-breakpoint
- hints and degraded experience under weak network

The value of this class of capability lies in reducing the wait the player perceives, not in replacing authoritative judgment.

### Which capabilities must be handled cautiously on the client

The following capabilities, if they grow on the client long term, usually bring fairness and consistency risk:

- settlement of key economic assets
- final hit, damage, and displacement adjudication in combat
- cheat-sensitive visibility judgment
- ranking and matchmaking result confirmation
- permission checks and order confirmation

Some projects, to speed things up, put part of the rules on the client to trial-run first, but without a clear server confirmation and reclamation path, they will sooner or later run into problems in cheating, rollback, and version compatibility.

### Disconnect, weak network, and reconnect truly expose the boundary design

Under normal network, many boundary problems are masked. What can really expose system quality is often these scenarios:

- packet loss and high latency
- foreground/background switching
- network blips
- protocol compatibility during version switching
- state recovery after reconnect

Whenever these scenarios frequently produce problems like "the picture recovered but the state is wrong," "the client showed success but the server never recorded it," or "after reconnect the position and health are messed up," it is usually not a simple network bug but rather that the boundary was never formally designed.

### A safer client-server split

The safer approach usually is:

- the client is responsible for interaction experience and presentation fluidity
- the server is responsible for critical adjudication and authoritative state
- the network layer is responsible for protocol, reconnect, and state sync semantics
- the project-layer framework is responsible for making prediction, confirmation, rollback, and recovery into formal mechanisms

The core of this is not "who does more work" but avoiding adjudication authority drifting between client and server.

### Common Pitfalls

The most common error is reading "the client needs to be more fluid" as "the client should decide more things." The second type of error is treating the network layer as just protocol send/receive, without putting prediction, confirmation, rollback, and reconnect back into one state design. The third type of error is only looking at the happy path day to day, and only discovering when weak network, disconnect, and version compatibility break that client and server actually never had unified state semantics.

### Case Study: An Adjudication-Drift Investigation of "The Client Said Success, the Server Never Recorded It"

> The case is a demonstration example (not drawn from a real project); numbers are rounded for simplicity. It puts this page's "The most important boundary: presentation logic, interaction logic, and authority logic," "Which capabilities must be handled cautiously on the client," "Disconnect, weak network, and reconnect truly expose the boundary design," and "Common Pitfalls" into the deep end: purchase and settlement each tell their own story — this is a reconciliation investigation of adjudication drift, and the full unfolding of "avoiding adjudication authority drifting between client and server."

**Background and symptoms**: An action mobile game with paid items. Two weeks after launch, customer complaints clustered in one pattern: the client popped up "purchase successful," while the authority side found no such order. Weekly reconciliation mismatched **143** orders; reconnect state-corruption tickets made up **62%**, all in the "picture recovered but state is wrong" pattern; **27** ranking settlement disputes were filed, and review found that in **19** of them the settlement judgment had at the time been trial-run on the client first.

### Step 1: Symptoms and Metrics — Split "Showed Success but Never Recorded" Into Two Ledgers

Authority metric: weekly reconciliation mismatched **143** orders; the client transaction log was compared order by order with server orders, and **91** orders existed on the client but not on the authority side — all mismatched orders fell in the order-confirmation category.

Recovery metric: reconnect state-corruption tickets made up **62%**; after reconnect, both sides recovered according to their own semantics, with the picture returning first and authoritative state arriving late or never.

Item-by-item comparison: this page's caution list — settlement of key economic assets, final combat hit and damage adjudication, cheat-sensitive visibility judgment, ranking and matchmaking result confirmation, permission checks and order confirmation — all **91** mismatched orders stepped on the "permission checks and order confirmation" item; within the three kinds of logic, authority logic grew into the client.

### Step 3: Root Cause — Treating "More Fluid" as "Local Gets the Say"

Under pressure for "the client needs to be more fluid," the project adjudicated purchase deals on the client first and had the server back-fill them afterward, and when back-filling failed, relied on hotfixes to patch up. This page states the consequence directly: the system lives long term in a chaotic state of "sometimes the client decides, sometimes the server decides." Disconnect scenarios further amplified the problem — the third type in this page's common pitfalls, "only looking at the happy path day to day, and only discovering when weak network, disconnect, and version compatibility break that client and server actually never had unified state semantics," is fulfilled word for word: after reconnect there was no unified state semantics, and mismatched orders and corruption tickets all surfaced together.

### Step 4: Remediation and Write-Back — Pinning Adjudication Authority Back to the Authority Side

1. Authority first: purchase, settlement, and ranking confirmation only emit server results; the client deal popup is changed to "submitted, awaiting authority confirmation," and no asset presentation is released before the authority confirms.
2. Prediction reclamation: local pre-play does only presentation logic; confirmation and rollback go through the same state machine; on timeout it rolls back per the authoritative result, and no client result is allowed to silently take effect.
3. Unified reconnect semantics: reconnect first pulls the authoritative snapshot and then fills in increments; both sides' recovery metrics are written into one state design; protocol compatibility during version switching is tested together with the reconnect window.

Recheck ledger: weekly reconciliation mismatched orders **143** → **6**; reconnect state-corruption ticket share **62%** → **7%**; ranking settlement disputes **27** → **2**.

| Write-back item | Action | Write-back location |

| Authority first | Purchase and settlement only emit server results; the client popup waits for authority confirmation | The most important boundary: presentation logic, interaction logic, and authority logic |
| Caution list review | Register the adjudication owner item by item for economic settlement, hit adjudication, and permission checks | Which capabilities must be handled cautiously on the client |
| Prediction reclamation path | Local pre-play rolls back per the authoritative result on timeout; confirmation goes through the same state machine | What the network layer really solves is not send/receive but state convergence |
| Reconnect state semantics | Reconnect first pulls the authoritative snapshot then fills increments; recovery metrics designed once | Disconnect, weak network, and reconnect truly expose the boundary design |

### Three Lessons From the Case

1. **Fluidity is not adjudication** — what is valuable about the client is reducing the wait the player perceives, not deciding things on behalf of the authority.
2. **Reconciliation mismatches are the boundary's health report** — every order "on the client, not on the authority" is empirical evidence of adjudication drift.
3. **Disconnect and reconnect expose every boundary that was never designed** — unified state semantics must be written into the design first, not waited for to be flagged by weak-network tickets.
