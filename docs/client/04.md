# Scripting Language and ECS

## Category

client / scripting and ECS. Node positioning: the scripting layer solves iteration speed and hot fixes; ECS solves data organization and high-frequency update cost — two problems, two weapons; sort them out first, then talk about adopting them.

## Definition


The scripting layer and ECS are often discussed together in the client, but they are not actually solving the same problem. The scripting layer cares more about iteration speed, hotfix capability, and business development efficiency; ECS cares more about data organization, system division of labor, and high-frequency object update cost. Bundling these two simply as a "new architecture solution" usually makes the team overestimate the gains and underestimate the costs.

So what this section really has to answer is: why does the client want to introduce a scripting layer, why do some projects turn to ECS, and what kind of complexity each is suited to solve.

## Problem

The two are often packaged as a "new architecture solution" and adopted together, with the result that gains are overestimated and costs underestimated: an ECS refactor treated as a performance silver bullet fails to bring frame rate back and instead drags the team into the learning cost of data organization; treating the scripting layer as a universal hotfix channel leaves business logic without the protection of types and the toolchain. What is really hard is the boundary, not the adoption.


### Why the scripting layer keeps showing up

Once a client project enters long-term operations and frequent iteration, pure native code often comes under great pressure:

- compilation and packaging are slow
- the cost of releasing small changes is high
- business-layer changes are too tightly coupled to the engine layer
- the hotfix window is limited

The value of the scripting layer usually lies in decoupling high-frequency-changing business logic from the heavier build chain, so that some modules can iterate faster, be fixed faster, and be validated faster.

But the scripting layer does not give gains for free. What you get is flexibility, and at the same time you take on:

- VM integration and host binding cost
- a more complex debugging chain
- performance boundaries that need to be redrawn
- code conventions and security boundaries that are harder to unify

### Why ECS gets brought up for discussion

Traditional object-oriented organization is usually intuitive enough when content scale is small and interactions are simple, but once object count, state variety, and update frequency ramp up, the problems become increasingly obvious:

- object hierarchies too deep
- component coupling that is hard to separate
- poor cache locality during high-frequency updates
- system behavior and data distribution that are hard to observe

The value of ECS lies in separating "what the data is" from "how the systems process data," making high-frequency batch processing, rule composition, and runtime observability clearer.

### The scripting layer and ECS should not be treated as the same weapon

The scripting layer is better suited to solve these problems:

- high-frequency changes in business modules
- hot updates and fast fixes
- higher involvement from planners or business developers
- client logic needing faster trial and error

ECS is better suited to solve these problems:

- many objects
- frequent state updates
- complex rule composition
- needing clearer data access paths

A system can use both the scripting layer and ECS, but it should not default to adopting them together just because both "look more flexible."

### What is really hard is the boundary, not the adoption

Whether scripting layer or ECS, the hardest part is usually not technical adoption but the boundary split:

- which modules suit scripting and which must stay in the native layer
- which systems suit ECS and which remain more intuitive with object-oriented
- to what extent should the scripting layer's exposure surface of engine APIs be controlled
- whether ECS really covers the high-frequency paths, rather than just adding an abstraction layer

When the boundary is not drawn clearly, common results are:

- half the logic in scripts and half in native, with debugging jumping back and forth
- ECS only wraps the surface structure, with hotspots still on the old paths
- the project force-migrating unsuitable modules for the sake of "a unified architecture"

### A safer way to land it

The safer approach is usually not a full refactor but picking the most suitable entry point first:

- use the scripting layer to carry high-frequency-changing UI, configuration-driven logic, or event logic
- use ECS to carry the runtime portions with large object counts and high update frequency
- keep the native layer to carry performance-sensitive, platform-specific, and low-level engine integration capabilities

The benefit of doing this is that each layer unfolds around the problem it is best at, rather than doing a full migration for the sake of an architectural sense of unity.

### Common Pitfalls

The most common error is treating the scripting layer as a pure development-efficiency tool while failing to add debugging, monitoring, and host-boundary governance. The second type of error is treating ECS as a modernization label, force-migrating without figuring out the project's real performance hotspots and data organization problems. The third type of error is adopting both the scripting layer and ECS without clearly dividing what each is responsible for, ending up merely splitting complexity into more layers.

### Case Study: An ECS Boundary Investigation of "Three Months of Refactoring, Frame Rate Never Came Back"

> The case is a demonstration example (not drawn from a real project); numbers are rounded for simplicity. It puts this page's "Why ECS gets brought up for discussion," "What is really hard is the boundary, not the adoption," "A safer way to land it," and "Common Pitfalls" into the deep end: architectural modernization is not a performance solution — this is a client frame-cost attribution investigation, and the full unfolding of "ECS only wraps the surface structure, hotspots still on the old paths."

**Background and symptoms**: A competitive project with dense on-screen units. With **200** units on screen, frame cost P95 is **18** ms (60 FPS budget 16.6 ms), and dropped-frame feedback concentrates in the melee brawls. The team attributes it to "object-oriented architecture is too old," kicks off a full ECS refactor, and invests **3** months migrating **5** systems — movement, pathfinding, state machines and others — into ECS. After the refactor, retesting with the same load model: frame cost P95 is **21** ms — not lower but higher, by **3** ms; and debug breakpoints still have to jump back and forth across the three layers of scripts, ECS, and native.

### Step 1: Symptoms and Metrics — First Break "Frame Rate Never Came Back" Into the Frame-Cost Ledger

Unified metric: frame cost = P95 of total main-thread logic and presentation time per frame, same load model (200 on-screen units in a melee for 5 minutes). One entry recorded before and one after the refactor:

- **Before refactor**: P95 **18** ms
- **After refactor**: P95 **21** ms, increment of **3** ms

The increment is not evenly distributed: the per-frame profiler compared system by system, and the systems covered by the refactor update quickly on their own; the time is spent where ECS never touched — layer first, then tally the hotspots.

### Step 2: Layered Attribution — The Frame-Cost Ledger From System Updates to the Presentation Layer

```text
ECS side  Movement/pathfinding/state machines and 5 systems complete migration; system updates total 4ms — the part the refactor covered
Hotspot ledger  Presentation layer totals 15ms: animation evaluation 6ms + effect tick 5ms + UI refresh 4ms — never entered ECS
Copy ledger  Presentation layer reads the full ECS state snapshot every frame, 2ms — the cost of a new abstraction layer added by the migration
Time ledger  4ms + 15ms + 2ms = 21ms — still 3ms more than the 18ms before the refactor
```

Ledger summary: the system updates the refactor covered account for only **4** ms of frame cost (about **19**%); the real hotspot is the **15** ms of presentation layer that ECS never touched (about **71**%); the **2** ms of cross-layer snapshot copying is pure new cost — on this chain ECS only added an abstraction layer.

### Step 3: Root Cause — Treating ECS as a Modernization Label

Against this page's "What is really hard is the boundary, not the adoption" four questions: which systems suit ECS was never answered (the presentation-layer hotspots are not a data-organization problem); "whether ECS really covers the high-frequency paths, rather than just adding an abstraction layer" — the **2** ms copy ledger is precisely the empirical form of "only adding an abstraction layer." Of the three consequences in this page's "when the boundary is not drawn clearly," two hit: ECS only wraps the surface structure, hotspots still on the old paths; the project force-migrating unsuitable modules for the sake of "a unified architecture." The hot update scripting layer launched at the same time also never drew a clear line with ECS on what each was responsible for — the second type in this page's common pitfalls, "treating ECS as a modernization label," and the third, "adopting both the scripting layer and ECS without clearly dividing what each is responsible for," are fulfilled word for word, ending up merely splitting complexity into more layers.

### Step 4: Remediation and Write-Back — Hotspots to Hotspots, Boundaries to Boundaries

Fix: shrink ECS back onto this page's "safer way to land it" track — keep only the runtime subset with large object counts and high update frequency (on-screen small mobs and bullet-hell); govern the presentation-layer hotspots item by item per the ledger: downsample animation evaluation, batch effect ticks, UI dirty-region refresh; change cross-layer full snapshots to incremental views. Recheck: frame cost P95 **21** → **13** ms (below the pre-refactor **18**), **200** → **400** on-screen units stable at **60** FPS; after registering each layer's scope across the three layers, debugging locates by layer and no longer jumps around.

**Write-back list**:

| Landing point | Action | Write-back location |
|-----|------|--------|
| Hotspots first | Produce a frame-cost attribution ledger before introducing ECS; do not start if hotspots are not on the high-frequency path | Why ECS gets brought up for discussion |
| Boundary registry | Write the three-layer scope — scripting / ECS / native — into the project-layer framework conventions | A safer way to land it |
| Abstraction layer audit | Count cross-layer snapshot copying into the frame-cost ledger; change full reads to incremental views | What is really hard is the boundary, not the adoption |
| Refactor stop-loss | Set a frame-cost acceptance line for architecture refactors; trigger a rollback review if not converging in two weeks | Common Pitfalls |

### Three Lessons From the Case

1. **Architectural modernization is not a performance solution** — ECS answers "how to organize data," it does not automatically answer "where frame cost goes."
2. **Have the hotspot ledger first, then talk refactoring** — force-migrating without attribution is splitting complexity into more layers.
3. **Boundaries are harder than adoption** — before each of the three layers is in place, no single layer alone can save the frame rate.
