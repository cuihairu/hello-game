# 脚本语言与 ECS

脚本层和 ECS 在客户端里经常被一起讨论，但它们解决的其实不是同一个问题。脚本层更关心的是迭代速度、热修复能力和业务开发效率；ECS 更关心的是数据组织、系统分工和高频对象更新成本。把这两者简单打包成“新架构方案”，通常会让团队高估收益、低估代价。

所以这一节真正要回答的是：为什么客户端会想引入脚本层，为什么有些项目会转向 ECS，以及它们各自适合解决哪一类复杂度。

## 为什么脚本层会反复出现

客户端项目一旦进入长期运营和频繁迭代阶段，纯原生代码往往会承受很大压力：

- 编译和打包慢
- 小改动发版成本高
- 业务层改动和引擎层耦合太紧
- 热修复窗口有限

脚本层的价值，通常在于把高频变化的业务逻辑从较重的构建链中解耦出来，让部分模块可以更快迭代、更快修复、更快验证。

但脚本层不是白送收益。你得到的是灵活性，同时也会背上：

- VM 集成和宿主绑定成本
- 调试链路变复杂
- 性能边界需要重新划
- 代码规范和安全边界更难统一

## 为什么 ECS 会被拿出来讨论

传统对象式组织在内容规模较小、交互较简单时通常足够直观，但一旦对象数量、状态种类和更新频率上来，问题会越来越明显：

- 对象层级过深
- 组件耦合难拆
- 高频更新时缓存局部性差
- 系统行为和数据分布难以观察

ECS 的价值在于把“数据是什么”和“系统如何处理数据”拆开，让高频批处理、规则组合和运行时观察变得更明确。

## 脚本层和 ECS 不该被当成同一件武器

脚本层更适合解决这些问题：

- 业务模块高频变动
- 热更新和快速修复
- 策划或业务开发参与度更高
- 客户端逻辑需要更快试错

ECS 更适合解决这些问题：

- 对象数量多
- 状态更新频繁
- 规则组合复杂
- 需要更清楚的数据访问路径

一个系统可以同时使用脚本层和 ECS，但不能因为它们都“看起来更灵活”，就默认值得一起引入。

## 真正难的是边界，而不是接入

无论是脚本层还是 ECS，最难的通常都不是技术接入，而是边界划分：

- 哪些模块适合脚本化，哪些必须留在原生层
- 哪些系统适合 ECS，哪些依旧用对象式更直观
- 脚本层和引擎 API 的暴露面控制到什么程度
- ECS 是否真的覆盖了高频路径，而不是只增加抽象层

边界没划清时，常见结果是：

- 一半逻辑在脚本，一半逻辑在原生，调试要来回跳
- ECS 只包住表面结构，热点仍然在老路径里
- 项目为了“统一架构”强推不适合的模块改造

## 一个更稳妥的落地方式

比较稳妥的做法通常不是全量重构，而是先挑最合适的切入点：

- 用脚本层承接高频变更的 UI、配置驱动逻辑或活动逻辑
- 用 ECS 承接对象量大、更新频率高的运行时部分
- 保留原生层承接性能敏感、平台相关和底层引擎集成能力

这样做的好处是，每一层都围绕自己最擅长的问题展开，而不是为了架构统一感去做全面迁移。

## 常见误区

最常见的错误，是把脚本层当成纯粹的开发提效工具，却不补调试、监控和宿主边界治理。第二类错误，是把 ECS 当成现代化标签，没搞清楚项目真正的性能热点和数据组织问题就强推改造。第三类错误，是同时引入脚本层和 ECS，却没有清楚划分它们各自负责什么，最后只是把复杂度拆成了更多层。

## 实战案例：一次「重构三个月，帧率没救回来」的 ECS 边界排查

> 案例为教学示例（非摘自真实项目），数字经过取整简化。它把本页「为什么 ECS 会被拿出来讨论」「真正难的是边界，而不是接入」「一个更稳妥的落地方式」「常见误区」用到深水区：架构现代化不等于性能方案——这是客户端帧耗的归因排查，也是「ECS 只包住表面结构，热点仍然在老路径里」的完整展开。

**背景与现象**：一款同屏单位密集的竞技项目，同屏 **200** 单位时帧耗时 P95 **18** 毫秒（60 FPS 预算 16.6 毫秒），掉帧反馈集中在混战团。团队归因「对象式架构太老」，立项全量 ECS 重构，投入 **3** 个月把移动、寻路、状态机等 **5** 个系统迁入 ECS。重构完成后用同一压测模型复测：帧耗 P95 **21** 毫秒——不降反升，多 **3** 毫秒；调试断点还要在脚本、ECS、原生三层来回跳。

### 第一步：现象与口径——先把「帧率没救回来」拆成帧耗账

口径统一：帧耗时 = 主线程每帧逻辑与表现总耗时 P95，同一压测模型（同屏 200 单位混战 5 分钟）。重构前后各记一笔：

- **重构前**：P95 **18** 毫秒
- **重构后**：P95 **21** 毫秒，增量 **3** 毫秒

增量不是均匀分布的：逐帧 profiler 按系统分段对照，被重构覆盖的系统更新本身很快，时间花在 ECS 没碰的地方——先分层，再算热点账。

### 第二步：分层归因——从系统更新到表现层的帧耗账本

```text
ECS 侧   移动/寻路/状态机等 5 系统完成迁移，系统更新合计 4ms——重构覆盖的部分
热点账   表现层合计 15ms：动画评估 6ms + 特效 tick 5ms + UI 刷新 4ms——没进 ECS
拷贝账   表现层每帧全量读 ECS 状态快照 2ms——迁移新增的抽象层成本
时间账   4ms + 15ms + 2ms = 21ms——比重构前 18ms 还多 3ms
```

账本收束：重构覆盖的系统更新只占帧耗 **4** 毫秒（约 **19**%），真热点是 ECS 根本没碰的表现层 **15** 毫秒（约 **71**%）；跨层快照拷贝 **2** 毫秒是纯新增成本——ECS 在这条链路上只增加了抽象层。

### 第三步：根因——把 ECS 当成了现代化标签

对照本页「真正难的是边界，而不是接入」的四问：哪些系统适合 ECS 没答（表现层热点不在对象组织问题里）；「ECS 是否真的覆盖了高频路径，而不是只增加抽象层」——**2** 毫秒拷贝账正是「只增加抽象层」的实测形态。本页「边界没划清时」的三种后果中了两种：ECS 只包住表面结构，热点仍然在老路径里；项目为了「统一架构」强推不适合的模块改造。同期上线的热更脚本层又没和 ECS 划清各自负责什么——本页常见误区第二类「把 ECS 当成现代化标签」与第三类「同时引入脚本层和 ECS，却没有清楚划分它们各自负责什么」逐字应验，最后只是把复杂度拆成了更多层。

### 第四步：处置与回填——热点归热点，边界归边界

修法：ECS 收缩回本页「更稳妥的落地方式」的正轨——只保留对象量大、更新频率高的运行时子集（同屏小怪与弹幕）；表现层热点按账本逐项治理：动画降频评估、特效 tick 合批、UI 脏区刷新；跨层全量快照改增量视图。复核：帧耗 P95 **21** → **13** 毫秒（低于重构前的 **18**），同屏 **200** → **400** 单位稳定 **60** FPS，三层承接范围登记后调试按层定位、不再乱跳。

**回填清单**：

| 落点 | 动作 | 回填处 |
|-----|------|--------|
| 热点先行 | 引入 ECS 前先出帧耗归因账，热点不在高频路径不开工 | 为什么 ECS 会被拿出来讨论 |
| 边界登记 | 脚本/ECS/原生三层承接范围写进项目层框架约定 | 一个更稳妥的落地方式 |
| 抽象层审计 | 跨层快照拷贝计入帧耗账，全量读改增量视图 | 真正难的是边界，而不是接入 |
| 重构止损 | 架构重构设帧耗验收线，两周不收敛即触发回滚评审 | 常见误区 |

### 案例的三个教训

1. **架构现代化不是性能方案**——ECS 回答「数据怎么组织」，不自动回答「帧耗花在哪」。
2. **先有热点账，再谈重构**——没有归因的强推改造，是把复杂度拆成更多层。
3. **边界比接入难**——三层各就各位之前，任何单独一层都救不了帧率。
