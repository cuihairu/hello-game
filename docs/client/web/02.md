# WebGL Rendering Pipeline and Performance Attribution

## Category

client / Web frontend. Node positioning: hand over the GPU pipeline — rendering pipeline, shaders, scene graph, DrawCalls and textures are the prerequisite for using any 3D engine without getting "black-box disease."

## Definition


Canvas 2D hands all drawing detail over to the browser; WebGL hands the GPU directly to the developer: underneath the same 2D canvas interface runs a real graphics pipeline. Writing games directly with WebGL is rare (the workload is huge), but understanding its pipeline and shaders is the prerequisite for not getting "black-box disease" with any 3D engine (Three.js, Cocos, Unity WebGL).

## Problem

Writing games directly with WebGL is rare, but using an engine fluently does not mean understanding the pipeline: why are DrawCalls expensive, why do textures eat memory, what can a shader do — without this, performance problems can only be guessed at. Understanding the pipeline is a prerequisite, not an optional, for using Three.js/Cocos/Unity WebGL.


### Rendering Pipeline: How Data Becomes Pixels

What WebGL does each frame can be summarized as one pipeline: the CPU prepares vertex data and textures and submits them to the GPU; the GPU runs each vertex through the vertex shader to transform it from model space to clip space, primitive assembly and rasterization turn triangles into individual pixels, and the fragment shader then decides each pixel's final color, after which depth testing and blending write to the canvas. Two key facts:

- **Shaders are small programs that run on the GPU**, executed in massive parallelism per vertex, per pixel — heavy work like "loop ten thousand times" in CPU code is almost free inside a vertex shader
- **The number of CPU submissions per frame (DrawCalls) is one of the main bottlenecks**: the GPU computes fast, but the coordination cost of "submitting a thousand small tasks" hits its ceiling first

### Shader Stages and Material Cost

There are two kinds of shader. The vertex shader takes vertex attributes (attribute) and outputs clip-space coordinates; the fragment shader outputs a pixel color. Values are passed between them via varying (automatically interpolated during rasterization), and global parameters are passed from the CPU as uniform. A minimal compilable pair:

```glsl
// 顶点着色器：把顶点从模型空间带到裁剪空间
attribute vec3 aPos;
void main() {
  gl_Position = vec4(aPos, 1.0);
}
```

```glsl
// 片元着色器：每个像素输出一次颜色
precision mediump float;
uniform vec3 uColor;
void main() {
  gl_FragColor = vec4(uColor, 1.0);
}
```

In a real project the vertex shader also has to multiply by the three matrix groups of model, view, and projection (MVP transform), and the fragment shader does sampling and lighting — but the division of labor "vertex decides position, fragment decides color" never changes from start to finish. Shader code runs on the GPU, and debugging is far harder than on the CPU: writing color output is the fragment shader's most commonly used "print statement."

### Three.js: Wrapping the Pipeline into a Scene Graph

Three.js is the most commonly used 3D library on the Web: it wraps shaders, matrices, and buffer management into a scene graph — put objects into the scene and the renderer walks and draws them every frame. A minimal runnable scene needs only the five-piece set (scene, camera, mesh, material, renderer):

```html
<script type="module">
  import * as THREE from 'https://unpkg.com/three@0.160.0/build/three.module.js'
  const renderer = new THREE.WebGLRenderer({ antialias: true })
  renderer.setSize(innerWidth, innerHeight)
  document.body.appendChild(renderer.domElement)
  const scene = new THREE.Scene()
  const camera = new THREE.PerspectiveCamera(60, innerWidth / innerHeight, 0.1, 100)
  camera.position.z = 5
  const mesh = new THREE.Mesh(
    new THREE.BoxGeometry(1, 1, 1),
    new THREE.MeshNormalMaterial(), // 按法线着色，无需打光即可看到立体
  )
  scene.add(mesh)
  function frame(t) {
    mesh.rotation.y = t / 1000
    renderer.render(scene, camera)
    requestAnimationFrame(frame)
  }
  requestAnimationFrame(frame)
</script>
```

Save as an HTML file to run (requires network to load the library). Materials decide whether to use lighting: `MeshBasicMaterial` is unlit and cheapest; `MeshStandardMaterial` uses physical lighting, most realistic and most expensive. The number of lights and real-time shadows is the first big variable of 3D game frame cost.

### DrawCalls, Batching, and Instancing

"Ten thousand units on screen" is often not the problem on the GPU side, it is on the CPU submission side. Three levels for lowering submission cost: batching (merging objects with the same material into one submission), instancing (one submission describing N instances of a template, WebGL has a native instancing extension, and Three.js provides InstancedMesh), and LOD (swap to a low-poly model at distance). To judge rendering-side performance problems, first look at two things: the number of DrawCalls and the number of triangles — the former reflects submission pressure, the latter reflects GPU pressure.

### Textures and Assets

Textures are the biggest chunk of memory in a 3D game. Three things to watch on mobile: size budget (a single 2048×2048 RGBA texture is 16MB of VRAM to start with), compression formats (each platform has different GPU texture compression formats, and decompress-then-upload is far cheaper than real-time PNG decoding), and model format (glTF is the de facto standard on the Web side, and coordinate units and axis conventions must be unified at export time). Loading, decoding, and uploading of textures and meshes should all be queued asynchronously, to avoid concentrated submissions in one frame causing stutter.

### Common Pitfalls

- **new-ing objects every frame**: vectors, matrices, and color objects created casually inside loops — GC jitter, the same disease as Canvas 2D
- **Putting logic into the render loop**: damage settlement and AI decisions placed inside render callbacks, so frame-rate fluctuation directly changes game outcomes — the logic layer and the presentation layer must be separated (see [this chapter's page 06](/client/web/06))
- **Ignoring pixelRatio**: 3D renders full-screen on high-DPI displays; when necessary, actively cap the render resolution in exchange for frame rate — the most common tradeoff on mobile
- **No size cap on textures**: art's original images go straight in, and VRAM instantly multiplies several times over
- **Only testing the models you have on hand**: GPU differences are far larger than CPU differences; low-end devices need to enter the test pool early

### Case Study: A Rendering Attribution Investigation After "Full Frames on Flagships, 22 Frames on Low-End Once Combat Starts"

> The case is a demonstration example (not drawn from a real project), with numbers rounded for simplicity. It takes this page's "Rendering Pipeline: How Data Becomes Pixels", "DrawCalls, Batching, and Instancing", and "Textures and Assets" to the deep end: the GPU is not broken, the ledger does not add up — this is attribution for submission pressure and VRAM accounting, and a complete unfolding of "look at DrawCalls and triangle count first."

**Background and Symptoms**: A 3D mini-game launched with **1200** units on screen: flagships held **60** frames throughout, mid-range machines dropped to **22** frames once combat started. Frame capture gave two ledgers: **1850** DrawCalls and **480**k triangles; **210** MB of texture VRAM, of which just 4 uncompressed 2048×2048 RGBA originals from art took **64** MB — a single 2048×2048 RGBA texture starts at 16MB of VRAM.

### Step One: Symptoms and Baselines — Separate the Submission Ledger from the VRAM Ledger

Submission baseline: **1200** units each with their own mesh and material, **1850** DrawCalls; the same-spec scene measured at **130** after batching — the coordination cost on the submission side hit its ceiling first.

VRAM baseline: of **210** MB of textures, **64** MB came from 4 uncompressed originals; against a mobile VRAM budget of **256** MB on mid-range machines, textures ate more than four-fifths, pressuring both bandwidth and memory.

Lighting baseline: a real-time directional light + **4** point lights + real-time shadows across the whole scene, with multi-light per-pixel computation going straight into the fragment shader.

### Step Two: Layered Attribution — Checked Against the Page's Two Key Facts

```text
渲染掉帧归因  占比
  DrawCall 提交压力，千级小任务协调成本    45%
  纹理超预算，未压缩原图吃满显存与带宽    33%
  实时阴影与多光源，片元侧第一大变量      22%
```

Item by item: the 1850 submissions correspond to "the number of CPU submissions per frame (DrawCalls) is one of the main bottlenecks"; the **64** MB of uncompressed originals corresponds to "no size cap on textures: art's originals go straight in, and VRAM instantly multiplies several times over"; real-time shadows stacked with 4 point lights corresponds to "the number of lights and real-time shadows is the first big variable of 3D game frame cost."

### Step Three: Root Cause — Only the Triangle Count Was Looked At, Not the Submission Count

The team's frame capture only reported "triangles **480**k, not many," treating the GPU as the sole bottleneck. This page says to check two things first on the rendering side: DrawCall count and triangle count — the former reflects submission pressure, the latter reflects GPU pressure. **480**k triangles is a light load for a mid-range GPU, while **1850** DrawCalls is a heavy load for the CPU submission side; only one of the two ledgers was checked, so the optimization direction pointed at the wrong layer.

### Step Four: Remediation and Backfill — Push the Ledgers Back at Three Levels

1. Batching and instancing: same-template units switched to InstancedMesh, one submission describing N instances; DrawCalls **1850** → **130**.
2. Texture governance: cap **2048** to **1024**, convert to GPU compression formats, load asynchronously in a queue; VRAM **210** → **58** MB.
3. Light relief: real-time shadows switched to baked, point lights **4** → **1**; fragment-side load cut by more than half.
4. Test pool moved earlier: low-end devices must enter the test pool in advance, mid-range frame rate goes into daily smoke, and regressions like **22** frames become visible within the week.

Recheck ledger: DrawCalls **1850** → **130**; texture VRAM **210** → **58** MB; mid-range entering combat **22** → **53** frames; flagships unchanged at **60** frames throughout.

**Backfill Checklist**:

| Backfill Item | Action | Backfilled To |
|-----|------|--------|
| Submission ledger | Frame capture reports DrawCalls and triangles as two separate items, attributed separately | DrawCalls, Batching, and Instancing |
| VRAM ledger | Set a size cap and compression format for textures; originals do not enter the package | Textures and Assets |
| Lighting budget | Real-time shadows and light count go into the performance budget; over-budget goes to baking | Rendering Pipeline: How Data Becomes Pixels |
| Device test pool | Low- and mid-range models enter smoke early; frame-rate thresholds enter the pipeline | Common Pitfalls |

### The Three Lessons of the Case

1. **DrawCalls and triangles are two ledgers** — the former reflects submission pressure, the latter reflects GPU pressure; checking only one means optimizing the wrong layer.
2. **VRAM is a budget, not surplus** — one 2048 RGBA texture starts at 16MB, and putting originals straight in is doubling.
3. **Device differences are bigger than imagined** — full frames on a flagship prove nothing about pipeline health; low-end devices must enter the test pool early.
