# Mini-Game Platforms and the Browser Environment

## Category

client / Web frontend. Node positioning: a mini-game is not an H5 page — the runtime model of the built-in App environment, package size and subpackages, lifecycle, social capabilities, and a compliance comparison table.

## Definition


Mini-game platforms (with WeChat Mini Games as the representative) made "tap to play" the default form: no install, no URL, distributed through social chains. They run inside a built-in App environment, not a full browser — the development model has substantive differences from H5 pages. This page explains the runtime environment, package size, and lifecycle; for the platform operations and channel perspective, see [Chapter 15 "Platform Ecosystem, Channels, and SDKs"](/industry/platforms/).

## Problem

Approaching mini-games with H5 instincts hits a wall in four places: no full browser API (DOM/BOM missing), hard caps on package size and subpackages, a different lifecycle when going to the background (pause semantics for audio and timers), and social and compliance features being platform-mandated (isolated rendering in the open data domain, real-name and anti-addiction). These differences are at the development-model level, not compatibility nitpicks.


### A Mini-Game Is Not an H5 Page

Running an H5 game in a browser, JS can access the full DOM, BOM, and various Web APIs; the mini-game environment deliberately cuts these away — no DOM, no full capability of `window`/`document`, no entry point for jumping to arbitrary URLs. The platform provides a thin adaptation layer: a canvas (Canvas), basic file system, and network and audio interfaces, and the engine (such as Cocos Creator) works on top of that adaptation. Direct implications for development:

- **UI and rendering go through the engine or Canvas; there is no shortcut of "copying a DOM component"** — third-party libraries must be confirmed free of DOM dependencies
- **One adaptation layer per platform**: the value of a cross-platform framework lies here, but the API coverage of the adaptation layer and consistency across platforms must be measured per platform
- **Browser-specific capabilities (some debugging tools, desktop features) are unavailable inside the platform**, and debugging must be done in the platform's developer tools

### Package Size, Subpackages, and First Screen

Mini-games have hard caps on package size, and the caps for the main package and total package differ and change with platform versions (defer to the platform's current documentation). The engineering response is a fixed three-pronged approach:

- **Only what the first screen needs goes in the main package**: the startup scene, core scripts, minimal assets; the smaller the main package, the faster first-screen entry, the higher the conversion
- **Subpackages split by gameplay and scene**: assets and logic pushed down per module, loaded on demand at runtime — subpackage granularity is the balance point between "the player's first wait" and "the number of loads during runtime"
- **Remote assets absorb the overflow**: assets beyond the total-package cap go to a CDN, combined with the load budget and lifecycle management of [Chapter 8 page 03](/client/03)

Package-size governance must set asset grouping rules at project kickoff; a pre-release "package slimming week" is usually already rework.

### Lifecycle and Going to the Background

A mini-game's lifecycle is driven by platform events: launch, foreground (`onShow`), background (`onHide`), destruction. When going to the background, the render loop pauses and the network may drop — this is exactly the source of the scenario in [thematic note 03 "Misjudged Offline on Backgrounding"](/24-game-types-architecture/03-frontend-engines). Engineering points: on `onHide`, save key state and pause timers (use an in-game clock rather than wall-clock, avoiding "a night of stamina deducted" on returning to the foreground); on `onShow`, validate the session and pull incrementally; any "immediately full reconnect on return" strategy must first pass the session-idempotency checkpoint (see the session and authentication page in [Chapter 15](/industry/platforms/)).

### Difference Table Against the Browser Environment

| Dimension | Browser H5 | Mini-Game Platform |
|------|-----------|------------|
| Host | Full browser | Built-in App environment + adaptation layer |
| DOM/BOM | Fully available | Essentially unavailable |
| Entry | URL share/search | Social chain/platform hub |
| Storage | Cookie/LocalStorage/IndexedDB | Platform key-value and file interfaces, limited capacity |
| Network | Free requests | Platform interfaces, domains must be registered on the platform |
| Audio | Autoplay restricted | Unlocked after first interaction, interfaces differ |
| Distribution and login | Self-built | Platform identity and friend relationships |

Storage and network differences are the easiest to underestimate: key-value storage is small in capacity and mostly synchronous; it is fine for storing configuration and progress, not viable as a database (see the boundaries in [Chapter 11 "Data Modeling and Databases"](/database/)); network domains that are not registered produce a white screen outright, the highest-frequency pitfall during integration.

### Social Capabilities and Compliance

The unique value of mini-game platforms is the social chain: friend rankings and group challenges depend on the platform's open data domain mechanism — friend relationship data is rendered in an isolated environment, the developer cannot obtain the details and can only display them per the platform interfaces. This is the technical precondition for "leaderboards are growth" gameplay. On the compliance side, requirements such as real-name, anti-addiction, and probability disclosure are mandatory on the platform; wiring in platform capabilities means wiring in compliance (see [Chapter 17 "Security, Risk Control, and Compliance"](/server/security/)).

### Common Pitfalls

- **Writing mini-games with H5 habits**: DOM-thinking UI approaches and ungrouped asset references mean wholesale rework on the platform
- **Packing the main package full**: unrestrained first-screen assets directly hurt entry conversion
- **Not handling backgrounding**: timers on wall-clock, no state validation on return, and work orders plus resource-farming exploits arrive together
- **Treating platform storage as a database**: neither capacity nor the synchronization model supports it, and this is how work orders for lost player progress happen
- **Ignoring the review cycle**: mini-game versions must also pass platform review, and release cadence must count in review time

### Case Study: A Port Investigation After "H5 Moved into a Mini-Game, 8-Second White Screen on First Load"

> The case is a demonstration example (not drawn from a real project), with numbers rounded for simplicity. It takes this page's "A Mini-Game Is Not an H5 Page", "Package Size, Subpackages, and First Screen", and "Lifecycle and Going to the Background" to the deep end: passing a platform with H5 instincts, four walls hit at once — this is attribution for porting debt, and a complete unfolding of "the three-pronged approach to package size."

**Background and Symptoms**: An H5 game ported to WeChat Mini Games: **8** seconds of white screen on first load, entry conversion **41**% (competing products at **68**%); main package **7.8** MB, nearly double the current main-package cap for the period (**4** MB, defer to platform documentation); during integration, **5** API domains unregistered produced white screens outright; two weeks after launch, **130** work orders of "left in the background overnight and a night's stamina was deducted."

### Step One: Symptoms and Baselines — Separate the White-Screen, Package, and Lifecycle Ledgers

Environment baseline: **7** of **26** third-party libraries had DOM dependencies; the platform environment cut the DOM away, so running threw errors and white-screened — a platform is not an H5 page, and there is no shortcut of "copying a DOM component."

Package baseline: of the **7.8** MB main package, **3.1** MB was uncompressed audio and **2.4** MB ungrouped textures — only the startup scene and core scripts are needed for the first screen, and neither of those two blocks qualifies.

Lifecycle baseline: timers ran on wall-clock and did not pause on backgrounding; no session validation or incremental pull on return, and all **130** work orders were the same shape.

### Step Three: Root Cause — Porting Was Treated as "Switching the Build Target," When Environment Differences Are Development-Model-Level

The project scheduled the port as a two-week "adaptation period," but in reality, approaching mini-games with H5 instincts hits a wall in four places: no full browser API, hard caps on package size and subpackages, a different backgrounding lifecycle, and social and compliance being platform-mandated — these are development-model-level differences, not compatibility nitpicks. Asset grouping rules were only added before release; the pre-release "package slimming week" this page warns about is usually already rework, and this project lived it out for a whole week; nobody managed the network domain registration list, and every highest-frequency integration pitfall was stepped on.

### Step Four: Remediation and Backfill — The Three Prongs Plus a Checklist

1. Clear DOM dependencies: replace or encapsulate the **7** DOM-dependent libraries, confirming no DOM dependencies before any third-party library is added; **7** → **0**.
2. Package three prongs: only first-screen essentials in the main package, gameplay and scenes split into subpackages, overflow to a CDN; main package **7.8** → **3.2** MB, first-screen white screen **8** → **1.9** seconds.
3. Domain registration: the platform domain list checked against the build flow, missed registrations **5** → **0**.
4. Lifecycle fixes: save state and pause timers on onHide (in-game clock), validate session and pull incrementally on onShow; stamina work orders **130** → **0**.

Recheck ledger: main package **7.8** → **3.2** MB; first screen **8** → **1.9** seconds; entry conversion **41**% → **63**%; DOM-dependent libraries **7** → **0**; missed domain registrations **5** → **0**; stamina work orders **130** → **0**.

| Backfill Item | Action | Backfilled To |
|-----|------|--------|

### The Three Lessons of the Case

1. **A mini-game is not an H5 page** — DOM-thinking libraries and approaches mean wholesale rework on the platform.
2. **The smaller the main package, the faster first-screen entry, the higher the conversion** — asset grouping is decided at project kickoff; a slimming week is usually already rework.
3. **Timers run on an in-game clock** — wall-clock plus no backgrounding handling, and work orders plus resource-farming exploits arrive together.
