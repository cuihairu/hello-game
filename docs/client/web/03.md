# Game Engines and Cocos Creator

## Category

client / Web frontend. Node positioning: use Cocos Creator as the vehicle for explaining how an engine works — nodes/components/prefabs/adaptation/build all have counterparts in the vast majority of engines.

## Definition


An engine solves the engineering problem of "assembling the shared infrastructure of rendering, scenes, assets, and adaptation." One of the most mainstream routes on the Web game side is Cocos Creator: a TypeScript stack, a well-developed build chain for mini-game platforms, and coverage of both 2D and light 3D. This page uses it as the vehicle to explain how an engine works clearly — these concepts (nodes, components, prefabs, adaptation) have counterparts in the vast majority of engines.

## Problem

An engine solves the shared infrastructure of rendering, scenes, assets, adaptation, and multi-platform builds for you, but it does not solve module boundaries, network layer design, state management, and performance budgets for you — those remain project-level matters. Treating the engine as the architecture, the project gets stuck at "the engine is enough but increasingly hard to change"; a build artifact exceeding the package-size cap, and asset grouping not decided early, are the most common release-time blockers.


### What the Engine Solves for You

Against the conclusion of [Chapter 8 "Client Architecture and Engine Systems"](/client/01): the engine is the foundation and public utility, not the project architecture. An engine like Cocos Creator solves the renderer for you (2D/3D dual pipeline), scene and node management, the asset pipeline (import, packing, release), the UI system, screen adaptation, and multi-platform builds; it does not solve module boundaries, network layer design, state management, and performance budgets for you — those remain project-level matters.

### Nodes, Components, and Scenes

An engine organizes the game world into a scene tree: nodes (Node) hang off the tree, components (Component) provide behavior. A node can have a render component (sprite, model), a physics component, and any number of custom script components. Script components have a clear lifecycle:

```ts
import { _decorator, Component } from 'cc'
const { ccclass, property } = _decorator

@ccclass('Spin')
export class Spin extends Component {
  @property
  speed = 90 // 度/秒，可在编辑器面板调整

  update(deltaTime: number) {
    this.node.angle += this.speed * deltaTime // 2D 旋转
  }
}
```

Attach the script to a node and it takes effect. `update` is called every frame; `onLoad`/`start` are called once during initialization. The key point and the pitfall share a root: `update` is a hot path, and doing node lookups every frame (`getChildByName`, `getComponent`) is the most expensive habit for newcomers — lookup results should be cached as members in `onLoad`/`start`.

### Prefabs and Object Pools

A prefab is the serialized template of "a configured node subtree": save finished bullets, enemies, and UI entries as prefabs, then instantiate them at runtime. It is the atomic unit of asset organization and the precondition for object pools — frequently spawned and destroyed objects (bullets, floating text, list items) should be taken from a pool and returned when done, to avoid the allocation and initialization jitter of repeated instantiation. To judge whether a prefab design is good, look at two things: whether it depends only on its own configuration (rather than global lookups in the scene), and whether it still needs lots of manual configuration after instantiation (if it does, the template split is wrong).

### Screen Adaptation

The shared problem of Web and mini-game platforms is: you do not know what screen the player is using. Three layers of adaptation tooling: design resolution (build the UI against one reference size, and the engine scales it according to a strategy), adaptation strategy (`fitWidth`/`fitHeight`/`fitWidthAndHeight`, deciding which side is cropped and which is kept), and Widgets with anchors (pin elements to the edge, corner, or center of the parent container, combined with safe-area handling for notch screens). Adaptation acceptance criteria are hard: run the widest and the tallest target devices once each, with UI elements not cropped, not overlapping, and clickable regions not crossing the safe area.

### Building to Mini-Game Platforms

Cocos Creator's build chain can directly produce projects for each mini-game platform and Web pages. What happens at build time is worth knowing: assets are compressed and split by rules, scripts are compiled and packed, and a platform adaptation layer is generated. A build artifact exceeding the package-size cap is the most common release blocker, with the source usually in uncompressed audio and ungrouped textures — asset grouping (which go into the main package, which into remote packages) must be decided early in the project, not patched before release (see [Chapter 8 page 03 asset systems](/client/03)).

### Common Pitfalls

- **Treating the engine as the architecture**: all logic piled into a few large components, the node tree growing into spaghetti — the engine only gives you attachment points, you still do the layering yourself (see this chapter's page 06)
- **Lookups and allocations in `update`**: three taboos on the hot path — lookup, new, log
- **Testing adaptation on only one screen**: the dev machine's screen is the entire test set, and only at release do you find notch-screen buttons have been eaten
- **Prefabs depending on scene globals**: a prefab cannot be used once it leaves its original scene, meaning dependencies have not been converged onto configuration and its own subtree
- **Using the engine without understanding numbers**: animation, easing, and physics parameters are all numerical work, and the engine exposes all of these knobs — if you do not understand them you just guess

### Case Study: An Architecture Gap Investigation After "The Engine Is Enough, But Changing One Campaign Button Means Touching 23 Files"

> The case is a demonstration example (not drawn from a real project), with numbers rounded for simplicity. It takes this page's "Nodes, Components, and Scenes", "Screen Adaptation", and "Common Pitfalls" to the deep end: everything is buildable, but increasingly impossible to change — this is attribution for treating the engine as the architecture, and a complete unfolding of "the engine is the foundation, not the project architecture."

**Background and Symptoms**: A Cocos Creator project **9** months in had **2400** nodes in its largest UI scene, tree depth **14**; business logic scattered across **87** components with **310** cross-component direct references. One requirement to "change a campaign button's position" dragged in **23** files and cost **3** person-days; meanwhile the first real-device test on a notch screen found **17** UI crops — the dev machine had been tested end to end without a single real-device run.

### Step One: Symptoms and Baselines — Measure Change Radius and Adaptation Debt Separately

Change baseline: **87** components, **310** cross-component direct references, and moving one button requires tracing **14** levels of node tree; **19** of the **23** changed files were merely "reverting someone else's hardcoded coordinates."

Hot path baseline: the main scene does `getChildByName`/`getComponent` lookups **620** times per frame — this page calls out three taboos on the hot path — lookup, new, log — and lookup alone counts as one.

Adaptation baseline: the adaptation test set was only the dev machine's **1920×1080**; the first real-device test showed **17** crops concentrated on the notch and gesture-bar sides, with clickable regions crossing the safe area in **6** places.

### Step Two: Layered Attribution — Checked Against the Page's Common Pitfalls List

```text
改不动归因  占比
  把引擎当架构，逻辑全堆在大组件里        47%
  update 热路径查找，每帧 620 次没缓存    31%
  适配只测开发机一屏，真机欠账后置        22%
```

Item by item: the node tree grown into spaghetti with logic all in a few large components hits "treating the engine as the architecture: the engine only gives you attachment points, you still do the layering yourself" squarely; **620** lookups per frame hits "`update` doing lookups and allocations" squarely; **17** crops hits "testing adaptation on only one screen: the dev machine's screen is the entire test set" squarely.

### Step Three: Root Cause — The Engine Provides Attachment Points; the Project Mistook Them for Architecture

An engine solves the shared infrastructure of rendering, scenes, assets, adaptation, and multi-platform builds for you, but it does not solve module boundaries, network layer design, state management, and performance budgets for you. The project mistook "components can be attached" for "components should be attached": module boundaries were never drawn, and **310** cross-component direct references are evidence that boundaries do not exist; prefab design was never converged, so they cannot be reused once out of their original scene. Change radius spreads exponentially along the reference graph, and most of the **23** files were passively caught up — this is exactly the standard shape of "the engine is enough but increasingly hard to change."

### Step Four: Remediation and Backfill — Return Attachment Points to the Engine, Put Architecture Back in the Project

1. Slim down components: converge business logic into **34** module components, replacing cross-component direct references with events and explicit interfaces; **310** direct references → **52**.
2. Cache lookups: cache node and component references as members in `onLoad`/`start`, lookups per frame **620** → **40**.
3. Adaptation checklist: per this page's acceptance criteria — run the widest and the tallest target devices once each, UI elements not cropped, not overlapping, clickable regions not crossing the safe area — into smoke tests, keeping a safe area on both the notch and gesture-bar sides; **17** crops → **0**.
4. Converge prefabs: prefabs depend only on their own configuration and subtree, and the **11** with wrong template splits are re-split.

Recheck ledger: changing the campaign button **23** files **3** person-days → **4** files **0.5** person-days; lookups per frame **620** → **40**; real-device crops **17** → **0**; main-scene nodes **2400** → **900**.

**Backfill Checklist**:

| Backfill Item | Action | Backfilled To |
|-----|------|--------|
| Component slimming | Converge business logic into module components; cross-component goes through events and interfaces | Nodes, Components, and Scenes |
| Lookup caching | Cache references in onLoad; hot path bans lookup, new, and log | Nodes, Components, and Scenes |
| Adaptation acceptance | Run the widest and tallest devices once each, keep enough safe area on both sides | Screen Adaptation |
| Prefab convergence | Depend only on own configuration and subtree; re-audit template splits | Prefabs and Object Pools |

### The Three Lessons of the Case

1. **The engine is foundation and public utility, not project architecture** — if module boundaries are never drawn, the component tree grows into spaghetti for you.
2. **update is a hot path** — the three taboos of lookup, new, and log; **620** lookups per frame is repaying the debt of those three taboos every frame.
3. **Adaptation acceptance criteria are hard** — run the widest and the tallest devices once each; all green on the dev machine does not mean any real device goes uncropped.
