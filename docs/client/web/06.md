# Client Internal Layering: Rendering, Logic, and Assets

## Category

client / Web frontend. Node positioning: one more layer inside the client process — the responsibilities and boundaries of rendering, logic, and asset loading; layering directly determines whether replay, reconnect, performance attribution, and multi-target reuse can be done.

## Definition


[Chapter 8 page 02](/client/02) draws the boundary between client and server (presentation logic, interaction logic, authoritative logic). This page goes one layer inward: inside the client process, how the rendering layer, logic layer, and asset loading layer are divided, and where the boundaries are. Layering is not aesthetics — it directly determines whether four things can be done: replay, reconnect, performance attribution, and multi-target reuse.

## Problem

An unlayered client cannot do any of the four things: replay (logic not reproducible), reconnect (no state to restore from), performance attribution (rendering and logic mixed in one loop), and multi-target reuse (logic welded to rendering APIs). Pushing damage settlement into a render callback means frame-rate fluctuation directly changes game outcomes — layering is not aesthetics, it is the foundation of these capabilities.


### The Responsibilities of the Three Layers

- **Logic layer**: holds game state and executes rules. It knows "health went from 100 to 60," it does not know "where to draw the health bar." Ideally it is pure computation: inputs (commands + frame step) → state transition + event list
- **Rendering layer**: draws the state. It reads state and consumes events, producing presentation (animation, particles, sound, floating text). It does not adjudicate any rule and does not hold authoritative state
- **Asset loading layer**: manages the lifecycle of assets (load, reference count, release, budget). It is called by the other two layers and never depends back on any business module

To judge whether the split is right, look at the direction of the data flow: **logic → state/events → rendering**, one-way. Code in the rendering layer that "mutates game state," or code in the logic layer that "reads UI controls," means it is broken.

### Fixed Timestep and Presentation Interpolation

For the logic layer to be reproducible (replay, anti-cheat verification, and reconnect all depend on the same inputs producing the same results), it must use a fixed timestep rather than the fluctuating real frame interval — only under a fixed step is "the same command sequence" well-defined (see [Chapter 4 determinism and numerical consistency](/server/sync/06)). Rendering can run at the real frame rate, interpolating between two logic frames:

```js
const STEP = 1 / 60
let acc = 0
let last = performance.now()
function frame(now) {
  acc += Math.min((now - last) / 1000, 0.25) // 上限防切后台回来的巨帧
  last = now
  while (acc >= STEP) {
    update(STEP) // 逻辑：固定步长，可复现
    acc -= STEP
  }
  render(acc / STEP) // 渲染：多余的时间交给插值
  requestAnimationFrame(frame)
}
requestAnimationFrame(frame)
```

This is the classic accumulator pattern: logic steps every 1/60 second (taking several steps if behind, spinning idle if ahead), rendering runs every frame, and uses `acc / STEP` as the interpolation coefficient to transition between the preceding and following logic states. Without this layer, higher frame rate means faster, returning from background teleports, and replays do not line up — three classes of production problem share one root.

### Events: The Formal Channel Between Layers

The logic layer should not call `ui.showDamage()` directly; it emits an event ("entity 12 took 30 damage"), and the rendering layer subscribes and decides the presentation. The decoupling events bring has a cost: timing becomes non-obvious and debugging chains get longer. Governance principle: events carry "facts that have happened" (past tense), not "please do X" (commands); consumers of the same fact each interpret it themselves, rather than the logic layer crafting an event per consumer.

### Asset Loading: Budget and Lifecycle

The core mechanisms of the asset layer are reference counting and budget: load the combat asset set on entering combat, release by count on leaving, and manage resident assets (UI backdrop, shared sound effects) separately. Two common breakpoints: loading happening at the point of use (loading skill effects only on entering combat, perceived by the player as stutter) and release without reconciliation (loaded but not released, memory rising monotonically). Engineering-wise, building a checklist of "which assets a gameplay session needs," preloading at session start and reconciling and releasing at the end, is the first step most teams take to get out of "the more you play, the slower it gets" (see [Chapter 8 page 03 asset systems and tooling](/client/03)).

### Layering and Regression: How Each Layer Is Verified

The value of layering must be realized through testing: the logic layer is pure computation, allowing render-free unit tests and full-playback comparison (seed + command stream → state hash); the rendering layer is hard to automate, so settle for spot-check snapshots of "state to presentation"; the asset layer gets load reconciliation tests (counts return to zero at session end). The layered thinking in [thematic note 20 "Game Testing and Quality Assurance"](/24-game-types-architecture/20-game-testing) holds equally for the client.

### Common Pitfalls

- **The rendering layer storing game state**: taking damage in an animation callback, floating-text objects holding authoritative values — once presentation and state write to each other, replay and reconnect can never be right
- **The logic layer touching presentation objects**: `node.position = ...` in rule code — that line is neither unit-testable nor replayable
- **Using the real frame interval for rule computation**: critical hit probability and movement integration depending on frame duration, so frame-rate fluctuation directly changes game outcomes
- **Events everywhere**: everything is an event, and a ten-line job wraps around three buses — events are for decoupling boundaries; call directly within a module
- **Asset release left to conscience**: without reference counting and reconciliation, "the more you play, the slower it gets" is only a matter of time

### Case Study: A Missing-Layer Investigation After "The Same Recording, Two Different Results on Two Machines"

> The case is a demonstration example (not drawn from a real project), with numbers rounded for simplicity. It takes this page's "The Responsibilities of the Three Layers", "Fixed Timestep and Presentation Interpolation", and "Events: The Formal Channel Between Layers" to the deep end: replay impossible, reconnect unholdable, slower the more you play — attribution for three classes of production problem sharing one root, and a complete unfolding of "layering is not aesthetics."

**Background and Symptoms**: When the client assessed adding a replay feature, it found that the same recording produced different results on a **60** FPS machine and a **30** FPS machine — critical hit rate configured at **15**%, measured **21.4**% on the **30** FPS machine and **14.8**% on the **60** FPS machine; reconnect state had no way to recover, with **410** reconnect-failure work orders; playing **24** rounds in a row (about 2 hours) raised memory from a baseline of **640** MB to **1.07** GB, and low-end machines were reclaimed by the system.

### Step One: Symptoms and Baselines — Split the Determinism, Recovery, and Memory Ledgers

Determinism baseline: critical hit judgment used the real frame interval for rule computation — the frame interval fed the random seed derivation, so changing frame rate changed the probability; the **21.4**% on the **30** FPS machine differed from the configured **15**% by **6.4** percentage points.

Recovery baseline: damage settlement was written in a render callback, with state scattered across UI controls — after a disconnect there was no recoverable game state at all, and **410** reconnect failures.

Memory baseline: skill effects loaded only on entering combat, with no reconciled release on leaving; **18** MB residue per round, **432** MB accumulated over **24** rounds, plus the **640** MB baseline reaching **1.07** GB.

### Step Three: Root Cause — The Direction of the Data Flow Was Reversed, One-Way Becoming Mutual Writes

To judge whether the split is right, look at the direction of the data flow: logic → state/events → rendering, one-way. In this project the rendering layer took damage and the logic layer read UI controls, breaking both directions at once. The logic layer had no fixed timestep, rule computation hung on the real frame interval, and the premise on which replay, anti-cheat verification, and reconnect all depend — "the same command sequence produces the same results" — was false from day one: higher frame rate means faster, returning from background teleports, and replays do not line up — three classes of production problem sharing one root.

### Step Four: Remediation and Backfill — Establish the Boundaries Across the Three Layers

1. Fixed timestep: the logic layer switched to the accumulator pattern with a **STEP = 1/60** fixed step, and rendering interpolates at the real frame rate; critical hit rate on the **30** FPS machine **21.4**% → **15.1**%, both machines consistent.
2. Settlement back to the logic layer: rule computation and state transitions only in the logic layer, the rendering layer only reads state and consumes events; **96** places calling `ui.showDamage` directly were changed to event subscriptions — events carry "facts that have happened" (past tense), not "please do X" (commands).
3. Session asset checklist: preload the combat asset set on entering combat, release by reconciled reference count on leaving; residue per round **18** → **0.3** MB (**432** → **7.2** MB over **24** rounds), steady state **1.07** GB → around **650** MB.
4. Layered regression: render-free unit tests for the logic layer plus full-playback comparison (seed + command stream → state hash), and a session-end counts-to-zero test for the asset layer.

Recheck ledger: critical hit rates on both machines **21.4**% / **14.8**% → **15.1**% / **15.0**% (configured **15**%); reconnect-failure work orders **410** → **37**; residue per round **18** → **0.3** MB; full-playback state hashes consistent across both machines.

**Backfill Checklist**:

| Backfill Item | Action | Backfilled To |
|-----|------|--------|
| Fixed timestep | accumulator with a fixed step, rendering interpolates, rules never touch the real frame interval | Fixed Timestep and Presentation Interpolation |
| One-way data flow | Settlement only in the logic layer; the rendering layer reads state and consumes events | The Responsibilities of the Three Layers |
| Event protocol | Events carry facts that have happened, not commands | Events: The Formal Channel Between Layers |
| Asset reconciliation | Preload at session start, reconcile and release at the end, counts-to-zero in the tests | Asset Loading: Budget and Lifecycle |

### The Three Lessons of the Case

1. **Layering is not aesthetics, it is the foundation of replay and reconnect** — the moment presentation and state write to each other, replay and reconnect are both out.
2. **Only under a fixed step is "the same command sequence" well-defined** — real frame interval in the rules means frame rate is a hidden rule parameter.
3. **Asset release relies on reconciliation, not conscience** — **18** MB per round is inconspicuous, but **24** rounds push a low-end machine out of the process.
