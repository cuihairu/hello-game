# H5 and Canvas 2D Rendering Fundamentals

## Category

client / Web frontend. Node positioning: the minimal foundation of Web game rendering — where frames come from, where the cost of drawing one stroke is, and when you should cache; the prerequisite course for WebGL and engines.

## Definition


Canvas 2D is the lightest entry point into game rendering on the Web: one canvas element plus a frame loop is enough to run a complete 2D game. It does not solve asset management, scene organization, or physics simulation, but it is the foundation that must be established before understanding anything heavier (WebGL, engines) — where frames come from, where the cost of drawing a stroke is, and when you should cache.

## Problem

Canvas 2D is the easiest to get started with, and therefore the most easily underestimated: DPR adaptation, draw cost inside the frame loop, and caching strategy for text and images — the debt erupts at the moment of "low-DPI acceptance all green, launch-day feedback piling up." First lesson of rendering debugging: look at "how many times did we draw" before looking at "how expensive is each draw."


### Canvas, Coordinate System, and Device Pixel Ratio

Canvas has two sets of dimensions: the internal pixel size of the canvas (the `width`/`height` attributes) and its display size in the page (the CSS size). When the two disagree, the browser stretches the image. On high-DPI screens, if the canvas pixel size only equals the CSS size, one canvas pixel has to cover multiple physical pixels and the image turns blurry — this is the most common root cause of "Canvas renders blurry." The standard practice is to scale the canvas up by the device pixel ratio (`devicePixelRatio`), then use a coordinate transform to keep the drawing logic in one single size set:

```js
function fitCanvas(cv) {
  const dpr = window.devicePixelRatio || 1
  const { width, height } = cv.getBoundingClientRect()
  cv.width = Math.round(width * dpr)
  cv.height = Math.round(height * dpr)
  cv.getContext('2d').scale(dpr, dpr)
}
```

After this, all drawing logic is written in CSS pixel coordinates, and `scale` takes care of mapping to physical pixels. The coordinate origin is at the top-left and the y axis points down — opposite to math textbooks and to the "y up" of most game engines, and the place where physics simulation most easily goes wrong.

### Frame Loop: requestAnimationFrame

Browsers drive rendering with `requestAnimationFrame` (rAF): it calls back before each frame is painted, and it is called as fast as the screen refreshes (commonly 60Hz, 120Hz or higher on high-refresh screens), automatically pausing when the page goes to the background. Inside the frame loop you must drive motion with delta time, not "move a fixed number of pixels every frame" — the latter gets proportionally faster on high-refresh screens:

```html
<canvas id="cv" width="480" height="270" style="width:100%"></canvas>
<script>
  const cv = document.getElementById('cv')
  const ctx = cv.getContext('2d')
  let x = 0
  let last = performance.now()
  function frame(now) {
    const dt = (now - last) / 1000
    last = now
    x = (x + 120 * dt) % cv.width // 每秒 120 像素，与帧率无关
    ctx.clearRect(0, 0, cv.width, cv.height)
    ctx.fillRect(x, cv.height / 2 - 10, 20, 20)
    requestAnimationFrame(frame)
  }
  requestAnimationFrame(frame)
</script>
```

Save this as an HTML file and open it directly to run. Delta-time driven, rAF driven, clear-then-paint every frame — these three things are the minimal skeleton for any Web game at runtime (including those built with an engine).

### Draw Cost and Batching

Every draw in Canvas 2D carries a fixed overhead, and the bulk of the cost is usually not "how much area was painted" but "how many times the state was switched": changing the fill color, changing the font, changing the transform matrix, changing the clip region — each switch can break the browser's internal batching. Cost-reduction levers, ordered by payoff:

- **Sprite atlas**: merge small images into one large image and use `drawImage` to pick from coordinates — fewer texture source switches; this is the default shape of 2D game asset organization
- **Offscreen cache**: pre-render complex combinations that do not change (a static background, a piece of stroked text) onto an invisible canvas, then paste it with a single `drawImage` in the main loop
- **Dirty rectangles**: only repaint the minimal region that changed; suited to screens dominated by UI with little motion; full-screen scrolling games cannot use it
- **Reduce state switches**: group drawing by fill color and by atlas, rather than painting in random object order

Canvas 2D has no explicit DrawCall concept, but the intuition "state switches are expensive, batching is cheap" runs through to WebGL (see the next page).

### Text and Images

`fillText` drawing text directly is convenient but on the slow side: font rasterization, line breaking, and stroking all happen inside each call. Fixed copy that shows up frequently in the UI (numeric labels, button text) should be pre-rendered into bitmaps or a font atlas. Image assets need attention to decoding timing — `drawImage` on an `<img>` that has not finished decoding causes first-frame stutter; painting once to an offscreen canvas after the asset is created (or using `createImageBitmap`) lets you absorb the decoding cost early.

### Common Pitfalls

- **Repainting everything in full every frame**: when there are many on-screen elements, first figure out "what changed"; dirty regions and layered canvases (separate canvases stacked for background/entities/UI) pay off more than squeezing per-item performance
- **Ignoring device pixel ratio**: if the dev machine is low-DPI you cannot see the problem, and on users' phones the whole thing turns blurry
- **Creating objects inside the frame loop**: new arrays, closures, and temporary canvases every frame add GC pressure, showing up as periodic frame jitter
- **Using setInterval for the frame loop**: it is unrelated to screen refresh, does not stop in the background, and intervals are not guaranteed — the frame loop should use rAF only
- **Using delta time directly for physics integration**: when per-frame duration fluctuates a lot the simulation becomes unstable; regular arithmetic should switch to a fixed timestep (see [this chapter's page 06](/client/web/06))

### Case Study: A Canvas Rendering Investigation After "Low-DPI Acceptance All Green, 58 Feedback Items on Launch Day"

> The case is a demonstration example (not drawn from a real project), with numbers rounded for simplicity. It takes this page's "Canvas, Coordinate System, and Device Pixel Ratio", "Frame Loop: requestAnimationFrame", "Draw Cost and Batching", "Text and Images", and "Common Pitfalls" to the deep end: a canary-release incident in a self-built Canvas 2D H5 game that settles the debt on the three questions — where do frames come from, where is the cost of drawing a stroke, and when should you cache — all at once.

**Background and Symptoms**: A team's self-built Canvas 2D H5 game went to canary; acceptance on the dev machine (low-DPI, **60**Hz) was all green, and launch day brought two kinds of feedback: **37** reports of a blurry image and **21** of "the character runs fast on new phones"; the team-fight scene (**200** entities) also had periodic frame drops once every **2** seconds, with frame rate falling to **28**. Investigation found three things: the canvas pixel size was set directly equal to the CSS size with no device pixel ratio handling at all; the frame loop moved a fixed number of pixels every frame — the character moved **4** pixels per frame with no delta time; drawing was a full repaint in random object order, and additionally called `fillText` once each for **40** numeric labels every frame, with the frame loop creating new temporary arrays and closures every frame.

### Step One: Symptoms and Baselines — First Separate "Who Is Getting Faster" from "Who Is Turning Blurry"

Unify the baseline: use "same device, same scene" as the retest standard, and account for the two kinds of feedback separately, starting with two ledgers:

- **Speed ledger**: **4** pixels per frame × **60**Hz = **240**px/s, × **120**Hz = **480**px/s, exactly **2**x — consistent with the distribution of the "runs fast on new phones" feedback (concentrated on high-refresh models)
- **Clarity ledger**: canvas pixels = CSS size, so on a DPR **3** screen one canvas pixel spreads across **3** × **3** = **9** physical pixels — blurry

The speed ledger is a refresh-rate ledger, the clarity ledger is a size ledger; the frame drops are a third ledger — drawing and GC. The three ledgers are independent of one another and each has its own fix.

### Step Two: Layered Attribution — From Two Kinds of Feedback to Four Rendering Ledgers

```text
尺寸账   画布像素 = CSS 尺寸，无 DPR 处理——DPR 3 的屏上 1 画布像素摊 9 个物理像素
速度账   每帧固定 4 像素：60Hz 240px/s、120Hz 480px/s——高刷屏等比例变快
绘制账   200 实体乱序全量重绘、每帧 40 次 fillText，帧内状态切换上百次
抖动账   帧循环每帧新建数组与闭包，每 2 秒一次 GC，帧率掉到 28
```

The ledgers converge: **2**x speed is the speed ledger, **9**x pixel spreading is the size ledger, **28** frames is the drawing ledger plus the jitter ledger — all four ledgers share one root: where do frames come from, where is the cost of drawing a stroke, and when should you cache — three questions, not one of them asked at project kickoff.

### Step Three: Root Cause — Three Foundation Questions, Not One of Them Asked

Against this page's "Canvas, Coordinate System, and Device Pixel Ratio": if the canvas pixel size only equals the CSS size, one canvas pixel has to cover multiple physical pixels and the image turns blurry — this project verified that line by line, while not a single line was written of the standard practice of scaling the canvas by device pixel ratio (`devicePixelRatio`) and then using a coordinate transform to keep the drawing logic in one size set. Against "Frame Loop: requestAnimationFrame": this page requires the frame loop to drive motion with delta time rather than "move a fixed number of pixels every frame," and this project was exactly the latter; of the three-part minimal skeleton — delta-time driven, rAF driven, clear-then-paint every frame — only clear-then-paint was done. Against "Draw Cost and Batching": this page puts it directly — the bulk of the cost is usually not "how much area was painted" but "how many times the state was switched"; this project painted **120** scattered images in random order, redrew the static background every frame, and re-rasterized **40** pieces of fixed copy every frame, using none of the three levers: merging small images into one large image (sprite atlas), pre-rendering non-changing complex combinations (a static background, a piece of stroked text) onto an invisible canvas (offscreen cache), and "grouping drawing by fill color and by atlas rather than painting in random object order" (reduce state switches); dirty rectangles only repaint the minimal changed region, but a full-screen scrolling gameplay would not use them anyway, so that does not count as debt. Against "Text and Images": fixed copy that shows up frequently in the UI (numeric labels, button text) should be pre-rendered into bitmaps or a font atlas — not done; images were not pre-decoded either — the first `drawImage` on entering combat hit undecoded assets and stalled the first frame by **300**ms, something that could have been absorbed early. Three of the five "Common Pitfalls" hit verbatim: full repaint every frame; ignoring device pixel ratio — if the dev machine is low-DPI the problem is invisible, and it is blurry across the board on users' phones, which is exactly how acceptance was done here; creating objects inside the frame loop — new arrays, closures, and temporary canvases every frame add GC pressure and show up as periodic frame jitter, matching the drop every **2** seconds exactly.

### Step Four: Remediation and Backfill — Settle the Three Ledgers Separately

The fixes come in two stages. Emergency: **T+0** closes size and speed — all three lines of `fitCanvas` in place (canvas scaled by DPR plus `scale`, drawing written uniformly in CSS pixels), motion switched to delta time with the meaning fixed at **240** pixels per second, retesting **60**Hz and **120**Hz both give **240**px/s with a speed difference of **0**; **T+1** stops the bleeding on drawing — **120** scattered images merged into **1** atlas, the static background pre-rendered to an offscreen canvas, **40** fixed copy labels pre-rendered into bitmaps (`fillText` per frame **40** → **0** calls), draws sorted and grouped by atlas and by layer, in-frame state switches dropping from **110** to **8**, team-fight frame rate returning from **28** to **56**; frame-loop objects hoisted out for reuse, the once-every-**2**-seconds GC jitter going to **0**; images switched to `createImageBitmap` pre-decoding, first-frame stall on entering combat compressed from **300**ms to under **16**ms. One institutional step: write "DPR handling, delta time, atlas and offscreen cache, zero new allocations in the frame loop, pre-rendered fixed copy" into the H5 rendering checklist and gate code review on it. Recheck: on three retest machines (**60**Hz mid-range, **120**Hz high-refresh, DPR **3** model) speed was consistent at **240**px/s (difference **0**), blurry-image and speed-change feedback was **0** items, team fight stable at **56** frames, **0** GC frame drops within **2** minutes; the following **2** new gameplay modules built against the checklist had **0** recurrences.

**Backfill Checklist**:

| Landing Point | Action | Backfilled To |
|-----|------|--------|
| DPR closeout | fitCanvas scales the canvas by DPR, drawing unified to CSS pixel coordinates | Canvas, Coordinate System, and Device Pixel Ratio |
| Frame loop skeleton | delta time drives motion, rAF driven, clear-then-paint every frame | Frame Loop: requestAnimationFrame |
| Draw batching | scattered images into an atlas, static layers offscreen-cached, grouped drawing by atlas | Draw Cost and Batching |

### The Three Lessons of the Case

1. **All green on the dev machine does not mean all green on player devices** — the two things invisible at low-DPI **60**Hz (DPR, refresh rate) arrived on launch day as **37** blur reports plus **21** speed-change reports.
2. **Rendering cost is in the switches, not the area** — **200** entities painted in random order versus **1** grouped atlas draw produce an identical picture with frame rate differing by half (**28** versus **56**).
3. **Ask "is this done every frame?" about everything inside the frame loop** — objects created every frame became GC jitter once every **2** seconds, and the **40** labels repainted every frame became **40** pointless rasterizations.
