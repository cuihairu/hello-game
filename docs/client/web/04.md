# The Game UI System

## Category

client / Web frontend. Node positioning: game UI and application UI share a base but have different objective functions — the HUD reads state to render, the menu flow runs on a screen stack, lists control memory, and adaptation leaves a safe area.

## Definition


Game UI and application UI share one technical base (layout, text, input), but their objective functions are completely different: application UI pursues information efficiency and consistency, game UI pursues immersion and feel — it is either invisible (the HUD is only read when needed) or it is itself gameplay (inventory tidying, gear comparison). This page lays out the game UI system for the Web and mini-game side across four blocks: HUD, menu flow, lists, and adaptation.

## Problem

Application-UI instincts carried straight into game UI cause accidents: the HUD is driven directly by game logic (it should read state to render), lists are all built at once (memory and stutter), the back key is not wired to the screen stack (it exits the game directly), and irregular screens have no safe area (buttons blocked by the notch). Game UI is either invisible or is itself gameplay, so the implementation path differs.


### HUD: A Layered Dashboard

The HUD (Heads-Up Display) is the information layer that lives permanently on top of the gameplay view: health bars, minimaps, skill cooldowns, damage floating text. The first principle of organizing a HUD is layering:

- **Persistent layer**: health bars, resource bars, core action buttons — fixed positions, extremely low density; the player should be able to read them within half a second
- **Situational layer**: objective hints, interaction prompts, quest tracking — appears only when relevant, and disappears crisply
- **Feedback layer**: damage numbers, status icons, achievement notices — short-lived; watch the stacking cap and batching (merging same-kind floating text is a mature practice)

The key to HUD implementation is "read state to render": refresh the display every frame from game state, rather than having game logic drive UI controls directly — this is exactly the projection of [client layering](/client/web/06) onto the UI. A health bar shrinking from 100 to 0 every frame is fine, but "who took the damage and why" should not appear in UI code.

### Menu Flow and the Screen Stack

Menus (main screen, settings, inventory, shop) are almost always organized as a screen stack: pushing settings onto the stack on open, popping on back, the lower screen persists but is not refreshed. Stack management must handle four things: loading and releasing (load assets when pushed, release by reference count when popped, see [Chapter 8 page 03](/client/03)), input focus (buttons underneath a modal must not be clickable — the mask is not just visual), the back key (the Web browser's back button and mini-game platform back gestures must be wired to the screen stack, not to exiting the game), and state restoration (switching back from combat to the main screen, the UI must reflect the latest state, not a cached snapshot).

### Grid Lists and Large Numbers of Entries

Inventories, friend lists, and leaderboards are high-frequency accident zones: hundreds to thousands of entries, each a composite node with an icon, text, and buttons. The solution is virtual scrolling — create real nodes only for the visible region (plus a small buffer of rows), reusing pooled nodes to update content while scrolling. Three supporting pieces: fixed row height (or an estimable height; dynamic height needs a measurement cache), asynchronous icon loading (when scrolling fast, load only the images at the eventual resting position), and scroll position restoration (return to the same place on re-entering). The test of whether a list implementation passes: scroll ten thousand entries without stuttering, flickering, or duplication.

### Multi-Resolution and Safe Areas

Multiple resolutions on the Web side, multiple device models on the mini-game side, and UI adaptation uses the same toolkit: anchor positioning (nine-grid corners plus center), nine-slice images (rounded corners and strokes do not deform under stretching), safe areas (no interactive elements inside the notch and gesture-bar regions; platforms provide safe-area queries, leave enough margin on both sides), and font-size hierarchy (three tiers of title, body, and auxiliary information; across resolutions only the layout scales down, never the font-size floor). Converting world coordinates to screen coordinates is the fundamental operation for UI following 3D/2D objects (floating health bars, floating text); the minimal model for a 2D orthographic camera:

```js
// 假设：相机居中，zoom 为「屏幕像素 / 世界单位」，屏幕 y 轴向下而世界 y 轴向上
function worldToScreen(wx, wy, camera, viewport) {
  return {
    sx: (wx - camera.x) * camera.zoom + viewport.width / 2,
    sy: viewport.height / 2 - (wy - camera.y) * camera.zoom,
  }
}
```

In a real engine use the engine's camera conversion interface, but writing it yourself once is the best way to understand "once the camera changes, everything must be recomputed" — in the same frame the camera moves, following UI must refresh synchronously.

### Common Pitfalls

- **Logic mutating UI directly**: `label.string = ...` scattered everywhere in game code; once you need replays, reconnects, or localization, the whole UI must be chased by hand for state — the UI should be derived from state
- **Full refresh every frame**: unchanged screens are still rebuilding layout and burning CPU — mark dirty only when something changed, then re-layout
- **Handling only one side of the safe area**: only the notch side is reserved, and gesture-bar-side buttons get eaten
- **No pooling for lists**: opening an inventory builds five hundred nodes, and low-end machines freeze outright
- **Treating fonts as ordinary images**: add a language, change a font size, and the font atlas has to be rebuilt — the font approach must be decided at project kickoff (static atlas or runtime rendering)
- **Ignoring input latency**: button response over 100 milliseconds produces a "not responsive" feel; UI interaction is more sensitive than frame rate

### Case Study: A UI System Investigation After "Opening the Inventory Freezes It, and Localization Takes 9 Person-Days"

> The case is a demonstration example (not drawn from a real project), with numbers rounded for simplicity. It takes this page's "Grid Lists and Large Numbers of Entries", "HUD: A Layered Dashboard", and "Menu Flow and the Screen Stack" to the deep end: a single screen failing in four ways at once — this is attribution for list pooling and read-state rendering, and a complete unfolding of "the UI is derived from state."

**Background and Symptoms**: An inventory of **640** entries froze on open: **2.8** seconds to open on low-end machines, dropping to **18** frames on mid-range; adding localization meant chasing state by hand across the whole UI for **9** person-days; player reports of "mistakenly tapping back and exiting the game outright" made up **11**% of sessions, with **86** complaints about mis-taps in the notch and gesture-bar regions.

### Step One: Symptoms and Baselines — Log the Four Failures Separately

List baseline: all **640** entries built as nodes at once, each a composite node with an icon, text, and buttons; icons decoded synchronously, filling low-end memory directly.

State baseline: logic-mutates-UI calls like `label.string = ...` scattered across **214** places — each new scenario for localization, replays, and reconnects had to chase state by hand again.

Refresh baseline: the main screen rebuilt layout in full every frame, re-laying out even with no change, taking **31**% of CPU.

Stack baseline: the browser back button and platform back gesture were not wired to the screen stack, and accidental exits made up **11**% of sessions; the safe area reserved only the notch side, with **86** mis-taps on the gesture-bar side.

### Step Three: Root Cause — The UI Was Built as Application UI, Without a One-Way Data Flow from State to Presentation

Game UI is either invisible or is itself gameplay, and its implementation path differs from application UI. This project's UI had logic driving controls directly rather than reading state to render every frame: once you need replays, reconnects, or localization, the whole UI must be chased by hand for state — this page closes on one line: the UI should be derived from state. The **214** direct mutations are the chain reaction of "read state to render" never landing. On the list side, "hundreds to thousands of entries" was treated as a small application-side list, and virtual scrolling and pooling never entered the design.

### Step Four: Remediation and Backfill — Close It Off at Four Levels

1. List pooling: virtual scrolling creates real nodes only for the visible region (plus a small buffer of rows), with asynchronous icon loading and fixed row height; **640** nodes → **14** pooled nodes, open time **2.8** → **0.2** seconds.
2. Read-state rendering: the HUD and menus were changed to derive from state every frame, **214** direct mutations → **0**; localization integration **9** person-days → **1**.
3. Dirty-flag refresh: unchanged screens stop rebuilding layout, main-screen CPU **31**% → **9**%.
4. Stack and safe area: the back key is wired to the screen stack rather than exiting the game, with enough safe-area margin on both sides; accidental exits **11**% → **1.2**%, mis-tap complaints **86** → **0**.

Recheck ledger: inventory nodes **640** → **14**, open time **2.8** → **0.2** seconds; direct UI mutations **214** → **0**; main-screen CPU **31**% → **9**%; accidental exits **11**% → **1.2**%.

### The Three Lessons of the Case

1. **No list pooling is an accident** — virtual scrolling builds nodes only for the visible region, so scrolling ten thousand entries is stutter-free, flicker-free, and duplicate-free.
2. **The UI is derived from state** — having logic mutate controls directly saves the moment but comes back to find you every time with localization, replays, and reconnects.
3. **The safe area needs both sides** — reserving only the notch side still leaves gesture-bar-side buttons getting eaten.
