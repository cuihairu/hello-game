# Topical Expansion of the Main Line

The main line is organized by causal chain: first the problem model, then a layer-by-layer expansion of networking, sync, execution model, data, release, and operations, each chapter explaining "why it takes this shape." This organization suits building understanding but is less suited to another scenario — you've already read the main line and now need to quickly extract one class of content from the whole book to use. Topical expansion is prepared for that scenario: it compresses content that spans chapters into the same viewpoint, sacrificing the derivation process while keeping the conclusions and trade-offs.

## Division of labor between the main line and topics

Understanding the division of labor keeps you from misusing them:

- The main line answers "why": why a design takes this shape, where the constraints come from, what the derivation of the trade-off is.
- A topic answers "what's there": under the same viewpoint, what conclusions different projects and different paths have compressed into.

The main line expands along chapter dependencies; topics are for horizontal retrieval by problem. Treating a topic as complete background will leave out the causal chain; treating the main line as a handout to consult on demand may also fail to surface a specific step. In project work, the two kinds of material respectively carry judgment context and on-site verification.

## What topics are in the appendix

The knowledge base's appendix carries five classes of topical expansion:

- Game type topic: by room-based, hard real-time, persistently online, and long-term growth types, centrally answering "where this class of product concentrates its complexity."
- Problem-domain consolidation: reclustering different games by problem domain, compressed into a horizontal quick reference of profiles, constraints, solution shapes, and characteristic pitfalls.
- Config pipeline topic: extracting config tables, data-driven design, and R&D collaboration out of the chapters into one complete standalone path.
- Capacity scaling topic: collecting load testing, capacity planning, scaling, and migration into a special reference for pre-launch and operational phases.
- Engine language tools topic: returning selection to its business and team context as background material for selection discussions.

These topics share a common trait: each one can find scattered corresponding content in the main line. What a topic does is rearrange them under the same viewpoint and add the horizontal comparisons the main line cannot conveniently expand.

## How to read the game type topic

When reading a game type topic, an effective posture is to use your own project as a reference point:

- First read the section on "where this product is truly hard," and check whether your project's pain point lands in the same place.
- Then read the solution shapes and characteristic pitfalls, marking which you've already handled and which are blind spots you haven't yet met.
- When you meet a point that needs expansion, return to the corresponding directory in the main line to fill in the causation, rather than staying at the topic's conclusion layer.

The game type topic can also serve competitive analysis and project kickoff discussions: comparing a target product's design selling points against a category's difficulty distribution can often reveal what will consume your team over the coming years.

## How to read the problem-domain consolidation

Problem-domain consolidation is an abstraction one level above the game type topic: it clusters not by gameplay nouns but by the shape of the technical problem. Suitable moments to use it include:

- Project review: run your project against the profile to confirm the judgment about the dominant problem domain hasn't drifted.
- Solution review: use the common solution shapes in the profile as a comparison, checking whether your solution missed this domain's routine constraints.
- Cross-team communication: a problem-domain profile makes it easier for different roles to converge on the same picture than a category noun does.

Worth noting when reading: every constraint in the profile has a complete derivation in the main line; the quick-reference page gives a hint, not an argument. When you find a constraint you don't understand, the correct move is to return to the main line to catch up, not treat the hint as dogma.

## How to read the engineering-pipeline topics

The config pipeline and capacity scaling topics expand engineering paths that cut across several main-line threads. They are read differently from the game type topic and suit reading by process stage:

- The config pipeline topic advances along "what goes into a table, how it's validated, how it's released, how it's rolled back," suitable for picking up by stage when building or governing a config flow.
- The capacity scaling topic advances along "business metrics, load conversion, measured load testing, scaling contingency plans," suitable for reading end to end during launch preparation and long-term operational governance.

Usage density for these topics usually peaks in specific periods: capacity is concentrated-consulted before a version launch, configuration is concentrated-consulted during system buildout. A common rhythm is to read through once for a map in ordinary times, then drill into the relevant sections when the moment arrives.

## How to read the selection-background topic

The engine language tools topic has yet another character; it doesn't provide a decision conclusion, it provides decision background:

- Dimensions like commercial terms, ecosystem maturity, and team fit usually need ready-made horizontal material in a selection discussion.
- The topic has no "which one to choose" answer, because it deliberately leaves the judgment to the constraints of the specific project.

Bringing the relevant pages in as background material before a selection meeting reduces disputes run on impression alone; this material can also serve onboarding, showing the scope of the tool ecosystem.

## Turning topics into working material

Topic pages are designed to be extractable; common uses include:

- Review material: take a page from a problem-domain profile as the basis for a review comparison table.
- Internal sharing: build a talk around one topic as a skeleton and fill in instances from your own project.
- Training material: newcomers read a topic first to build a map, then return to the main line by map to catch up — more efficient than reading the main line straight through.
- Retrospective index: during an incident retrospective, use a topic page to quickly confirm whether the common pitfalls of similar projects are covered.

All these uses share one prerequisite: the user has a basic impression of the main-line content. The prerequisites a topic compresses away are exactly the part most easily overlooked when using the topic.

## When to retreat back to the main line

Two signals say it's time to retreat from the topic back to the main line:

- You find you're left with categories but no causation: you can state the labels of each class of project but can't say why a constraint holds.
- You find conclusions in conflict: a topic page's conclusion doesn't match your project's actual observations, and you need to return to the main line to check the difference in premises.

Retreating to the main line isn't a detour; a topic is anchored on the main line by design. A team that only reads topics without the main line will see its discussions degenerate into label-swapping; a team that has read the main line and then uses topics frequently is when a topic delivers its value as an index.

## Common pitfalls

- Only consulting topic labels while skipping the relevant causal background.
- Treating a topic as a handbook and rummaging blindly under time pressure, then blaming the topic for being useless when the target isn't found.
- Using topic conclusions to drive decisions directly, skipping the corresponding premises in the main line.
- Assuming a topic covers the whole main line, ignoring the details and exceptions the compression necessarily drops.
- Using only topics, not the main line, in sharing and training — newcomers build a label system rather than an understanding system.

Topical expansion is a shortcut prepared for those who have already walked the main line. A shortcut is fast, on the condition that you've already walked the road once completely; for someone who hasn't, the shortcut is just a line on the map that doesn't go through.
