# 6. 服务拆分、分布式与控制平面

很多团队第一次认真面对分布式，不是因为想“架构升级”，而是因为旧系统已经撑不住现实压力了。房间服和活动服的负载曲线完全不同，跨服玩法开始上线，热点场景需要迁移，节点故障不能再靠人工救火，玩家断线重连也不能继续靠碰运气。

这时真正的问题不是“要不要微服务”，而是下面这些更具体的工程问题：

- 哪些状态必须放在一起维护，哪些状态可以拆开治理
- 哪些节点应该独立扩缩容，哪些故障必须被局部隔离
- 玩家、队伍、房间、场景在跨节点迁移时由谁调度
- 路由、发现、切流、摘流、维护态这些能力由谁统一管理
- 一条跨服务链路失败后，系统怎样恢复到可解释状态

如果这些问题没有先回答清楚，所谓“服务拆分”往往只是把单体里的复杂度改名成了网络复杂度、链路复杂度和恢复复杂度。

这一章不是按中间件名词展开，而是按系统进入分布式之后最先暴露的几类问题展开：边界如何画，角色如何分，控制平面为什么会从附属能力变成主系统，路由和发现为什么会成为核心基础设施，以及一致性、重连和恢复为什么必须从一开始就被正式设计。

- [服务发现、路由与协作](./04.md)：讨论请求如何找到正确目标、绑定关系如何维护，以及服务之间怎样协作才不会把路由逻辑散落一地。
