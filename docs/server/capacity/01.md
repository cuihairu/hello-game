# Load Testing and Capacity Planning

## Category

server / capacity subtree. Node positioning: capacity is a deduction chain, not a guess -- business metrics -> system load -> back-inferred from measured single-node capacity; the knee point and safe water level, headroom for failure, elasticity for growth. Master outline of the capacity subtree.

## Definition


Capacity planning is often treated as a resource problem of "guessing the number of machines to open a server," when in fact it is a deduction chain: start from business metrics, convert them into system load, then back-infer the resource scale from a measured single-node capability. If any link in the chain relies on guessing, the last link will pay the error back in the form of an incident. A launch surge that takes down login, a database that falls over first on event night, a bottleneck that quietly moves elsewhere after scale-out -- traced to the root, it is often the deduction chain breaking at some middle link.

Load testing is the only link in this chain that supplies measured data, but it is easily turned into a performance show: run out a good-looking peak number, then write it into the report. What load testing really should answer are three plain questions -- how much can a single node actually hold, which component is the bottleneck, and how much headroom should be left. A load test that cannot answer these three questions cannot support capacity decisions no matter how pretty the numbers look.

## Problem

Treating capacity as a resource problem of "guessing the number of machines to open a server" breaks the chain: if any link -- business-volume conversion, load-test distortion, knee-point judgment -- relies on guessing, the error will be paid back as an incident at the last link: a surge that takes down login, a database that falls over first on event night, a bottleneck that moves elsewhere after scale-out.


### Start from business metrics, not from machines

Every capacity question can ultimately be traced back to a set of business-side numbers; having this set first is what enables all the subsequent conversions:

- User scale: registration count, DAU, peak concurrent online; of these, peak online is the primary input to capacity calculation.
- Temporal distribution: the shape of the evening peak, the amplification factors for weekends and holidays, the concentrated influx on launch day one.
- Behavior composition: what players do after logging in; the frequency differences between behaviors determine the shape of the load.
- Operations events: pre-registration launches, version updates, large events -- which moments will see multiplied traffic.

These numbers are often not in the hands of the technical team but in the expectations of publishing and operations. The first step of capacity planning is therefore an alignment: translating operational expectations into inputs the technical side can digest. Skip this step and every subsequent load test and estimate is built on self-imposed assumptions; however accurate the test, it will have tested the wrong thing.

### Converting from business volume to system load

Once you have the business metrics, the next step is to convert "how many people are playing" into "what the system bears." This layer of conversion is usually expanded in basic units:

- Per-player session: connections held after login, heartbeat frequency; these determine the connection and packet pressure on the gateway.
- Per-player request frequency: the call frequency of each system operation, aggregated into requests per second per service.
- Per-player resident memory: the footprint of session context, cached data, and vision lists; multiplied by peak online it is the memory requirement.
- Per-player bandwidth: the downlink traffic of state sync; this determines egress bandwidth and broadcast cost.
- Per-player persistent writes: the write-to-disk frequency multiplied by online count, giving the database's write pressure.

These "per-player" parameters are the base units of the whole deduction chain, and their values should come from measured load testing or experience with similar products, not from guessing. Per-player resident memory in particular: many services hit the memory wall before the compute wall, and if this parameter is estimated wrong, the single-node online ceiling is wrong as a whole.

### The point of load testing is not to chase the peak

Load testing easily drifts toward "pushing for a maximum concurrency number," but what capacity decisions actually need is different information:

- Single-node capacity: how many players a single process can stably serve under acceptable latency and error rate.
- Bottleneck localization: whether compute, memory, bandwidth, storage, or a downstream dependency tops out first determines what to scale out.
- Behavior differences: which operations are especially expensive, and worth dedicated optimization or rate limiting.
- Parameter calibration: the measured per-player metrics replace the estimates and correct the capacity model.

A habit worth building is to annotate each load-test conclusion with its conditions: what behavior distribution, what data scale, what hardware spec, what acceptance criteria. A capacity number without conditions does not hold in a different scenario, yet is often cited as a universal conclusion in the next product.

### Common sources of load-test distortion

Load-test results disagreeing with production behavior is the most common plot in capacity incidents. The sources of distortion are fairly concentrated:

- Unrealistic bot behavior: bots that only send login and heartbeat can measure a ceiling several times higher than real mixed load.
- Insufficient data scale: an empty database and one with hundreds of millions of rows behave completely differently on queries; the slowest paths are often only exposed by data volume.
- Inconsistent environment specs: the test environment has better hardware, a closer network, and fewer dependencies, so moving its numbers straight into production is an overestimate.
- Only the single point is pressed: one service is loaded to the brim while the real behavior of other components in the chain has never been verified.
- Wrong peak shape: a uniform ramp cannot produce the steep surge of a launch moment, and the surge is precisely the main threat in the launch scenario.

The approach to distortion is not to make load testing infinitely close to reality, but to cross-validate the key assumptions: for the parts in doubt, backfill the model with shadow traffic or real data from the gray-release window. The deviation between the initial values a load test gives and the measured production values is itself the calibration material for the next round of planning.

### Knee point and safe water level

The most valuable part of load-test data is often not the maximum value but the knee point: the place where latency turns from linear growth into nonlinear spike as load keeps rising. Past the knee point, the system enters a region where throughput does not grow and latency explodes, and piling on more traffic only piles up the queue.

Production load water levels are usually set by reference to the knee point:

- Normal load is held a good distance below the knee point, leaving room to absorb bursts.
- Peak periods may approach the knee point, but must have a clearly defined alert water level.
- Any service that runs long-term near the knee point is a candidate for the next capacity incident.

Set the safe water level too full and you have spent the fault-tolerance margin; set it too empty and cost cannot be pushed down. There is no universal answer to this balance; it is usually set by the business's sensitivity to latency and the cost of recovering from a failure. The harder a component is to scale out quickly, the more conservative the water level should be.

### Headroom for failure, elasticity for growth

Two kinds of "extra reserved resources" in capacity planning are often conflated, when their purpose and source are both different:

- Failure headroom: so that traffic can be absorbed when one machine dies or one availability zone is lost. It is static redundancy, present in proportion to deployment scale.
- Growth reservation: the scale-out window for when user volume rises. This is better carried by elastic scale-out capability rather than by machines kept on standby.

Converting growth demand into standing headroom is one of the most common ways to waste cost; conversely, treating failure headroom as elasticity headroom is a common cause of death in launch incidents -- when traffic arrives, you do not even have the allowance for one machine to fail. Keep the two ledgers separate and both budget and risk land in the open.

### The capacity model needs post-launch calibration

A pre-launch capacity model is essentially a set of assumptions awaiting verification. The behavior distribution of real users is almost certainly different from the load-test model: some idle, some pay, some climb leaderboards in the middle of the night, some rush levels on launch day. Launch is therefore only a shift point in capacity work, not the end:

- Compare estimates with measurements: how far each service's real load shape and each per-player parameter's actual value differ from the model.
- Watch the component approaching its water level fastest: it is often the most underestimated item in the model.
- Record measured data from major events: launches, major versions, and large events are natural high-quality load tests, and the data should be accumulated.

A continuously calibrated capacity model will give a more accurate contingency plan before the next major event; a model never calibrated will have its debt collected all at once at the first major deviation.

### When capacity planning needs to be redone

A capacity model has clear failure signals; when they appear it is usually worth tearing up and recalculating rather than patching:

- Major changes to the gameplay structure: a newly added heavy gameplay mode or a changed core loop, with the behavior distribution rearranging as a result.
- Architectural adjustments: service splits, storage migrations, protocol rewrites; both single-node capacity and bottleneck location will move.
- Changes in user composition: new user cohorts brought in by version migration, behavior differences after cross-platform release.
- Repeated performance surprises: the same class of problem recurring means the model and reality have fallen out of sync.

Redoing the plan does not mean tearing down everything; most of the time it means remeasuring key parameters and recalculating bottleneck items. But be wary of extrapolating an old model to a new scenario: reusing the old behavior distribution after the gameplay has changed is a high-incidence way for capacity estimates to miss.

### Common pitfalls

- Starting from machines rather than from the business, fixing the budget first and then back-deriving conclusions of hundreds of thousands of concurrent online.
- Using a login load test in place of a full-behavior load test: login holds, and the first peak after entering the server does not.
- Load-testing on an empty database, so query paths slow down across the board once data volume comes up, exposed only at launch.
- Treating the load-test peak as safe capacity, leaving no water level below the knee point.
- Mixing failure headroom and growth reservation in one ledger, with both cost and risk running out of control.
- Never calibrating the model after launch, so the second server opening still uses the first one's wrong parameters.

Whether capacity planning was done well is invisible in normal times; it only shows up in a few moments: the moment of server opening, the moment an event opens, the moment user volume doubles. None of these moments allows time for a crash course; the only thing to rely on is how solid that earlier deduction chain was.

### Practical case: triaging a capacity-deduction chain break at "ten minutes into server opening, login falls first"

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes this page's "Common sources of load-test distortion," "Knee point and safe water level," and "Headroom for failure, elasticity for growth" into deep water: the load-test numbers were beautiful, and the debt came due ten minutes into the launch -- this is the triage of a deduction chain breaking at one middle link, and also a full unfolding of "how to make load testing support capacity decisions."

**Background and symptoms**: a mobile game with **600,000** pre-registrations, peak online **150,000** on launch day. Ten minutes into the launch the login service collapsed, and two emergency batches of machines were needed to stabilize it; the surge lasted **40** minutes -- yet the load-test report stated a single-node login capacity of **80,000** connections, and the machine count was calculated from this number times a safety factor.

### Step 1: symptoms and caliber -- first align the load-test numbers with the production numbers

Load-test caliber: bots only sent login and heartbeat, pushing out **80,000** connections per node; real players fire four kinds of requests within **30** seconds of logging in -- profile pull, announcement, friends, and leaderboard -- and a node of the same spec could only stably hold **21,000** online in measurement: a ceiling gap of nearly **4**x.

Water-level caliber: normal load ran near the knee point with no alert water level defined; the launch surge was provisioned for the average rather than the peak, and failure headroom and growth reservation were mixed into one ledger.

### Step 2: layered attribution -- compare against this page's distortion-source checklist

```text
Capacity incident attribution  share
  Unrealistic bot behavior, only login and heartbeat pressed      54%
  Empty-database load test, insufficient scale hid slow paths      27%
  Inconsistent environment specs, test numbers moved to prod      19%
```

Item-by-item comparison: the main cause of the **4**x ceiling gap is unrealistic bot behavior -- this page says bots that only send login and heartbeat can measure a ceiling several times higher than real mixed load; profile queries on a **30 million**-row database ran **6**x slower than on an empty database -- hitting insufficient data scale; the unconditional **80,000** was cited as a universal conclusion -- hitting this page's point that a number does not hold when the scenario changes.

### Step 3: root cause -- the deduction chain broke at the conversion, and load testing became a performance show

The conversion from business metrics to system load skipped the behavior-composition link: it never first asked "what do players do after logging in," so the bots pressed the cheapest behavior directly. The load test answered "what is the peak" but not "where is the bottleneck" or "how much headroom" -- of the three questions only one was answered, and no matter how pretty the numbers, they cannot support capacity decisions.

### Step 4: remediation and backfill -- reconnect the broken links one by one

1. Make bot behavior realistic: replay against the real behavior distribution of similar products, schedule the four post-login request types at measured frequencies, and scale the data up to production grade.
2. Set water levels at the knee point: remeasurement found the true single-node knee at **30,000** online; hold normal load below **70**% of the knee point, and set the alert water level at **85**%.
3. Split the headroom and elasticity ledgers: keep failure headroom for one machine dying, hand growth elasticity to dynamic server addition, and keep the two ledgers separate.
4. Post-launch calibration: backfill the measured per-player parameters from this launch into the capacity model, as contingency input for the next major event.

Recheck ledger: single-node capacity **80,000** (inflated) -> **21,000** (measured caliber); the expansion pack's second server opening peaked at **220,000** online, login P99 stayed at **420** milliseconds steady throughout, with zero emergency scale-outs.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Behavior-composition input | Before capacity calculation, first gather what players do after logging in, then set the bot behavior distribution | Start from business metrics, not from machines |
| Annotate load-test conditions | Each load-test conclusion marks behavior distribution, data scale, hardware spec, and acceptance criteria | The point of load testing is not to chase the peak |
| Knee-point water level | Normal load <= 70% of the knee point, alert at 85%, services running long-term near the knee point go into remediation | Knee point and safe water level |
| Split headroom and elasticity ledgers | Failure headroom as static redundancy, growth reservation via elasticity, budget and risk booked separately | Headroom for failure, elasticity for growth |

### Three lessons from the case

1. **A load-test ceiling is a conditioned number.** The **80,000** from pressing only login becomes **21,000** under real mixed load; a capacity number without conditions does not hold when the scenario changes.
2. **If one link of the deduction chain breaks, the last link pays it back with an incident.** Behavior composition never entered the model, so the launch surge paid the error back as dropped connections.
3. **A peak is not safe capacity.** Running near the knee point with no alert water level is spending the fault-tolerance margin in advance.
