# Partitions, Migration, Server Merge, and Decommission

## Category

server / capacity subtree. Node positioning: server merges and migration are irreversible, asset-grade operations -- partition design determines migration cost, ID collisions, referential integrity, mapping tables kept permanently, and the write-freeze / dry-run / verification discipline.

## Definition


Server merges and migration are the most dangerous class of operations in a game's lifecycle: however stable the system runs day to day, these events put it under full interrogation -- is data ownership clear, will IDs collide, is referential integrity intact, does a way back exist. Migration incidents are unlike ordinary failures: they are often irreversible, and one occurrence is an incident at the level of player assets. So the core craft of this domain lies almost entirely in the work done before you act.

The initial design of the partitioning determines the cost of migration years later -- a textbook decision that is invisible at the start and unchangeable at the end. This piece runs from partition design through merge execution to decommissioning and archiving, with one thread running through it all: make the identity and ownership of data clear from day one.

## Problem

Migration incidents are unlike ordinary failures: they are often irreversible, and one occurrence is an incident at the level of player assets. ID collisions are the most typical hidden conflict, referential integrity determines migration quality, and a migration with no way back is not worth discussing -- the core craft lies almost entirely before you act.


### Partition design determines migration cost

Whether data carries a "which game server does this belong to" marker from birth determines whether a future merge is a move or a rebuild:

- Data carries the server dimension natively: the player ID encodes the server number, or every table has a server field; on merge, data from different servers naturally does not conflict, and the merge degenerates into a mostly logical merge that only works around name clashes.
- Data has only a global auto-increment identity: different servers' IDs each grow from the same starting point and are guaranteed to collide on merge, forcing a full remap.

The former's cost is paid once at system design time; the latter's is paid repeatedly at every merge, with long-term risk attached. This is the highest-return early decision in capacity and partition design. Projects already in the latter state still deserve to add the server dimension at the next scale-out; the later it is added, the more data has accumulated and the higher the price.

### ID collisions: the most typical hidden conflict

The visible conflicts of a merge are easy to handle: duplicate player names, duplicate guild names, solved with a suffix or a free rename. The truly dangerous ones are the hidden conflicts, the most typical of which is the ID collision:

- Both servers' player IDs auto-increment from their own starting points, so after the merge one ID points to two different people.
- Collisions, unlike name clashes, cannot be enumerated in advance; they usually surface only at merge execution.
- The handling is usually to offset one server's IDs wholesale, taking the offset as the target server's current maximum plus a safety margin.

Offset remapping sounds like just adding a number, but it means rewriting the primary and foreign keys of all the source server's data. It is surgery touching every data table; miss any one spot and the symptom does not appear immediately, but rather surfaces over the following weeks as scattered complaints such as "mail sent to someone who does not exist" or "a stranger appeared in my friend list."

### Referential integrity determines migration quality

The difficulty of remapping is not the mapping itself but referential integrity -- every place that references an old ID must be rewritten in step:

- Direct references: mail recipients, friend relations, guild members, mentor-apprentice relations.
- Indirect references: leaderboard snapshots, order records, log streams, customer support tickets.
- References embedded in content: player identifiers appearing in announcement bodies, compensation lists, and mail copy.
- References inside free text: other-player identifiers mentioned in player-written content such as message boards and signatures, which can almost only be covered by sampling and after-the-fact compensation.

Integrity is guaranteed not by care but by mechanism. The common practice is to route all data access through a unified identifier layer and, at migration, change only that layer and the underlying data; the migration script rewrites by full scan rather than enumerating a table list from memory; after rewriting, compare row counts and samples, and only let the merge through when the sum of source-side row counts matches the target side. The root cause of a missed rewrite is almost always "a data copy nobody knows about exists," and a full scan is the only means that can catch it.

### Why the mapping table is worth keeping permanently

After migration completes, the old-to-new ID mapping table looks useless, yet it is the translation dictionary for all later work:

- Customer support tickets and player complaints use old IDs and must be translated to the new identity when handled.
- Historical logs and transaction records are written under old IDs; troubleshooting and audits must look them back up.
- A second merge, data repair, and compensation issuance all depend on the mapping table to locate historical ownership.

The usual recommendation is to keep the mapping table until end of product life. It takes no part in business reads and writes, costs little, and once lost, the right to interpret historical data is lost permanently. Many teams have learned this the hard way: at the first merge they cleaned up the mapping as "temporary data," and years later had no way to start when handling a historical dispute.

### Merge timing and the pre-merge inventory

When to merge and which servers to merge is usually decided by activity data, but the technical pre-merge inventory equally decides success or failure:

- Inventory the data model differences between the two sides: if the two servers ran different versions, config batches and fields may not match.
- Inventory special data: cross-server assets, time-limited event progress, unexpired time locks; confirm the merge semantics for each class.
- Inventory historical leftovers: abandoned tables and temporary data never cleaned will all surface during the migration scan.
- Choose a low-peak window: merge downtime is hard to avoid, and the quieter the window, the fewer players wait.

What the inventory produces is a difference list and a set of item-by-item decisions, not a general-purpose migration script. Scripts can be reused; decisions cannot -- a common cognitive mismatch in merge projects.

### Execution discipline: freeze writes, dry run, verify

The technical difficulty of migration execution is not high; the risk concentrates in operational discipline. A few disciplines proven over and over:

- Freeze writes before migrating: confirm all writes have been flushed and no residual connections remain before moving anything. Migrating while writing is the root of data inconsistency.
- Dry run first: the migration script supports a rehearsal mode that prints what will be rewritten, merged, and deleted; a human confirms before the real run.
- Row-count verification: record the before/after row-count relation for every table; any mismatch aborts the server opening.
- Treat the rollback script as equal to the migration script: on migration failure you must be able to return wholesale to backup, and the rollback path must have genuinely been rehearsed.
- Leave buffer inside the window: reserve migration duration at the drill value plus headroom; do not squeeze verification time to the limit.
- Two-person review for high-risk steps: bulk rewrites and deletions are executed only after a second person confirms the parameters.

What these disciplines share is paying more cost up front to retire irreversible risk. Most migration problems are the interest on "I wanted to skip one step at the time."

### Conflict handling and compensation

Beyond IDs, a merge faces a batch of social and economic conflicts; the rules should be announced before the merge rather than explained afterwards:

- Name clashes: player names and guild names get a server-number suffix, usually paired with a free rename item.
- Leaderboards: recalculated after the merge; historical rankings kept as an archive.
- Mail and assets: each side keeps its own, merged under the account, never overwriting each other.
- Contested resources: territories, boss ownership, time-limited event progress each need a defined merge rule; the dispute-prone ones get a compensation plan up front.

Merge compensation is not merely a soothing gesture; much of the time it is the pricing of "the identity and rank a player accumulated on one server are being diluted." A slapdash compensation plan costs operations several times the effort in complaint handling; a clear plan often turns the merge into a fresh start in players' eyes.

Compensation issuance itself should also go through an idempotent asset pipeline: compensation paid out in bulk on merge day, if executed twice, costs far more than ordinary reward grants.

### Decommission and archiving

Decommissioning is another form of merge: not joining two live servers, but letting one server exit with dignity. The key to decommissioning is separating "compute decommission" from "data decommission":

- Compute decommission: recycle processes, remove routing, hide from the list server; the cost is released immediately.
- Data archiving: move player data into cold storage while keeping a query path, retrievable for win-back and audit.

The retention period and retrieval method for archived data usually need to be settled before decommission. Deleting low-activity server data outright is the operation most likely to trigger irrecoverable player complaints -- low activity does not mean no players; even a server of only a few hundred people holds the entire history of those few hundred.

### Common pitfalls

- Treating a merge as data moving, planning only the storage migration and not ID remapping or reference rewriting.
- Mapping relations carried by a script's runtime variables, never persisted into a mapping table.
- Drills only verifying "it runs to completion," without row-count or reference sampling checks, so missed rewrites stay in the dark.
- Rollback scripts never genuinely run, so at migration failure the backup-restore flow turns out to be equally rusty.
- Conflict rules decided on the spot, with players learning from a forum before the announcement what their name was changed to.
- Deleting data along with the server at decommission, saving storage worth far less than the later cost of getting the data back.

The essence of migration and merging is a stress test of the system's data model: identity ambiguity, loose references, and unclear ownership that runtime logic papered over in normal times all surface together in these events. Conversely, every merge done carefully is also a chance to re-clarify the data model.

### Practical case: triaging ID-collision missed rewrites at "three weeks after the merge, mail sent to someone who does not exist"

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes this page's "ID collisions: the most typical hidden conflict," "Referential integrity determines migration quality," and "Execution discipline: freeze writes, dry run, verify" into deep water: everything normal on merge day, missed rewrites surfacing over the following weeks -- this is the triage of a hidden conflict with delayed exposure, and also a full unfolding of "why a full scan is the only means that catches missed rewrites."

**Background and symptoms**: two servers merged, with the source server's IDs offset wholesale by **10 million**. Row-count verification was fully correct on merge day; from day **3** scattered complaints appeared one after another -- strangers in friend lists, mail returned with "player does not exist," leaderboard snapshot names mismatching -- **87** cases in three weeks, each pointing at the same batch of old IDs.

### Step 1: symptoms and caliber -- first confirm which class of reference hides the missed rewrite

Conflict caliber: visible conflicts (name clashes, guild name clashes) had been handled with suffixes and renames; the problem was the hidden collision -- an old ID was never offset-rewritten somewhere and still pointed at "someone else."

Missed-rewrite caliber: the investigation found an abandoned event snapshot table still referencing old IDs -- a leftover copy from two revisions ago, in nobody's memory of the table list; the migration script enumerated **42** tables from memory and missed this one.

Verification caliber: the drill only verified "it runs to completion," with no row-count or sampling comparison -- the snapshot table was not in the verification checklist, so the missed rewrite stayed in the dark.

### Step 2: layered attribution -- compare against this page's causes of missed rewrites

```text
ID-collision missed-rewrite attribution  share
  A data copy nobody knew of, no full scan    57%
  Drill verified no row counts or reference sampling              26%
  Mapping table nearly cleaned as temporary data              17%
```

Item-by-item comparison: the root cause of a missed rewrite is almost always "a data copy nobody knows about exists" -- this page's own words, the highest hit rate; the drill only verified it runs to completion -- hitting "missed rewrites stay in the dark"; the mapping table entered the cleanup candidates as "temporary data" after the merge -- hitting the hard lesson of having no way to start on historical disputes.

### Step 3: root cause -- the table list was enumerated from memory and the full scan was skipped

Remapping is surgery touching every data table; relying on "remembering all the tables" to guarantee integrity is doomed: data copies breed continuously as versions evolve, and the coverage of memory-based enumeration always lags reality. Integrity is guaranteed not by care but by mechanism -- all data access funneled through a unified identifier layer, with migration rewriting by full scan.

### Step 4: remediation and backfill -- replace memory with mechanism

1. Full-scan rewriting: the migration script now scans the whole information_schema, identifies every column holding old IDs, and the dry run prints the rewrite list.
2. Verification pass gate: the row-count relation plus reference sampling comparison, with any sampled hit on an old ID aborting the server opening; high-risk bulk rewrites get a two-person review.
3. Mapping table kept permanently: entered into the asset inventory, explicitly retained until end of product life, taking no part in business reads and writes but always queryable.
4. Dry-run-first made routine: every migration first produces the "will rewrite, will merge, will delete" list for human confirmation before the real run.

Recheck ledger: complaints **87** -> **0** at the next merge; the full-scan dry run identified **3** more referencing tables than memory-based enumeration; sampling comparison caught **1** view still holding old IDs during the drill window.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Unified identifier layer | Data access funneled through the identifier layer; migration changes only that layer and the underlying data | Referential integrity determines migration quality |
| Full scan | The migration script scans all tables for old-ID columns, not enumerated from memory | Referential integrity determines migration quality |
| Verification pass | Row-count relation plus sampling comparison; any mismatch aborts the server opening | Execution discipline: freeze writes, dry run, verify |
| Mapping table made permanent | The mapping table enters the asset inventory, retained until end of product life | Why the mapping table is worth keeping permanently |

### Three lessons from the case

1. **Hidden conflicts do not detonate on schedule.** Everything correct on merge day, with missed rewrites surfacing over the following weeks as "mail sent to someone who does not exist" and "a stranger appeared in my friend list."
2. **Memory-based enumeration always misses; only a full scan catches everything.** Data copies nobody knows about always exist; coverage must come from mechanism, not care.
3. **The mapping table is the right to interpret historical data.** Clean it up once as temporary data, and years later there is no way to start on a dispute.
