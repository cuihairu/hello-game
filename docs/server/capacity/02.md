# Scale Out, Scale In, and Dynamic Server Addition

## Category

server / capacity subtree. Node positioning: the hard part of scaling is the state layer, not the resource layer -- sessions live in memory, progression lives in processes, partitions live in data; dynamic server addition is relatively safe, scaling in is harder than scaling out, and global components need coordinated re-checking.

## Definition


Scaling sounds like a resource operation: add machines, remove machines, adjust quotas. But for game services, the hard part is never the resource layer; it is the state layer -- player sessions live in memory, progression lives in processes, partition boundaries are drawn in data. Stateless services can scale almost at will; every scale change of a stateful service must answer the same question: what happens to the state. An elasticity scheme that cannot answer this question will correct your understanding with dropped connections on day one of launch.

Dynamic server addition is the most common and safest form of scale-out in the game industry, because a new server touches no old data. Once you understand why adding servers is easy, you can work backwards to why scaling in and merging are hard: the former only adds without modifying, the latter must touch the ownership and boundaries of existing state.

## Problem

Stateless services can scale almost at will; every scale change of a stateful service must answer the same question: what happens to the state. An elasticity scheme that cannot answer this question will correct your understanding with dropped connections on day one of launch -- scaling in is harder than scaling out precisely because it has to move state.


### First separate which components can actually be elastic

Within one game backend, the elasticity headroom of components differs enormously; talking about "auto scaling" in blanket terms is meaningless:

- Access and proxy layer: stateless or with transferable sessions, usually free to scale horizontally at any time.
- Matchmaking, chat, announcement type public services: process on request, release on completion, the biggest elasticity payoff.
- Room servers: state is born and dies with the match; the process can be recycled after the match ends, which is semi-elastic.
- Main city and character logic servers: player sessions and data are bound to the process and cannot be freely added or removed at runtime.
- Storage layer: scaling involves data distribution, usually must be planned ahead, cannot be scaled on the fly.

Elasticity schemes should be designed component by component, not given one uniform strategy across the whole backend. The layered practice commonly seen is: the stateless layer goes to generic elasticity infrastructure, the room layer is scheduled by match lifecycle, and the character logic layer relies on dedicated processes such as server opening and migration.

### Preconditions for horizontal scaling

The precondition for horizontal scaling is not having machines, but the system itself possessing the structural conditions to be scaled:

- Shardable: the load can be cut into non-interfering units, for example by game server, by room, by scene.
- Routable: requests can be correctly delivered to the corresponding shard, and routing information can be updated dynamically.
- Clear single-writer boundary: the same data is owned by only one instance at any moment, so scaling produces no dual writes.
- New instances can become ready: a new instance can obtain the configuration, data, and registration it needs at startup, without manual intervention.
- Scaling is reversible: the scale-out operation itself can be undone; when the direction is found to be wrong, it can retreat to the original state instead of pressing on with the mistake.

Missing any one of these conditions, scaling will get stuck at the corresponding spot: without a sharding design, adding machines only adds empty shells; without routing updates, players still connect to old instances; without the single-writer constraint, data races appear the instant you scale out. These structural conditions must be prepared in normal times; there is no time to patch them up mid-scale-out-event.

### Why dynamic server addition is relatively safe

Opening new servers is the main means of game scale-out, and its safety comes from one simple fact: a new server is pure addition, modifying no existing data. Even so, server addition still has a set of engineering requirements worth following:

- Automated server opening flow: create the database, load base data, initialize configuration, register into the list server and gateway routing -- the whole flow scripted, done within minutes.
- Pre-built resource pools: images, templates, and database accounts prepared in advance; building resources on the fly at peak is a common cause of server-opening delays.
- Launch surge included in capacity: the influx at the moment a new server opens is often several times the norm; capacity is provisioned for the surge, not the average.
- Global component re-check: every server opened changes the capacity assumptions of global services such as matchmaking, cross-server, and chat, requiring coordinated re-verification.

The real risk of server addition lies not in the new server itself but in its cumulative pressure on global components. A single server is negligible; after twenty servers opened in a row, the load assumptions for cross-server gameplay may have been quietly broken.

### Why scaling in is harder than scaling out

Scaling out adds things; scaling in takes away things that are in use. The directions are opposite and the difficulty is asymmetric:

- You cannot scale in while players are online: sessions live in memory; forcibly reclaiming them means dropped connections and lost state.
- Empty-server detection needs debouncing: a brief online trough does not mean nobody is really there; scaling in wrongly costs you the win-back.
- Data cannot be deleted casually: the data of a low-activity server is a player asset; only the compute layer is scaled in, storage is usually kept in place.

The common practice is to turn scaling in into an operations decision with explicit thresholds, not an automatic action: continuously watch a server's activity level, move it to a watchlist after it falls below the threshold, and only after the trend is confirmed execute a dedicated process such as merge or decommission. Automatic scale-in is reserved for the layer that is truly stateless and holds no assets.

### The applicability boundary of elastic scaling

Elastic scaling has a polarized reputation in game backends, usually because the applicability boundary was never drawn. Scenarios with obvious payoff often share these traits:

- Load units are small and many: rooms, matches, battle instances; a single unit is cheap and can be created and destroyed at high frequency.
- Lifecycle is driven by business events: created when a match starts, destroyed when it ends; no human judgment of timing needed.
- State can be snapshotted or discarded: the cost of interruption is bounded, or no long-lived state exists at all.

Conversely, components with large load units, thick state, and long lifecycles (character logic servers being typical) get mostly incidents rather than payoffs when the same elasticity model is applied. To judge whether a component suits elasticity, first ask whether its state can be safely transferred or rebuilt within a few seconds; if the answer is no, do not force it.

### Capacity re-checking of global components

The number of game servers is a hidden variable in the capacity of many global components, yet server addition decisions often only account for the new server itself. The re-check must at least cover:

- Cross-server gameplay: the more servers participating, the larger the battlefield convergence and the matchmaking pool; verify against whole-region online, not single-server.
- Global chat and social: broadcast scale grows with total online, unrelated to single-server online.
- Matchmaking and leaderboard services: data volume and update frequency rise linearly with the number of servers.
- Shared storage: the pressure on region-wide shared data such as accounts, lists, and orders rises in step.

An actionable discipline: every time a batch of new servers exceeds a certain scale, recalculate the capacity assumptions of the global components. Global components are unsung in normal times, but when they fail the blast radius is the whole region.

### Server addition cadence and the operations calendar

Adding servers is not just a technical action; it meshes with the operational rhythm, and the timing of server openings is itself part of the operations strategy:

- Concentrated opening days (Friday evenings, before holidays) mean stacked surges; capacity must be provisioned for the worst-case stacking.
- Over-dense opening intervals dilute the population of each new server while raising the standing pressure on global components.
- Opening servers right before a major version update is usually unwise; new-server players' first encounter would be an not-yet-stable version.
- The opening time slot also matters: placing it in a window when players have ample free time smooths the influx better than placing it mid-peak.

The technical side and the operations side sharing one server-opening calendar is a low-cost, high-return form of collaboration. Capacity contingencies rolled forward along the calendar are far calmer than event-driven last-minute preparation, and leave time for drills and resource reservation.

### Scale-out plans and drills

The value of a scale-out plan depends on whether it is maintained as a living document. A plan only dug out during incident retrospectives has usually drifted from reality. Habits worth keeping include:

- The plan states trigger conditions, execution steps, owners, and verification methods, not a single line of "just scale out."
- Regular drills: actually scale out one round per the plan, verifying process duration and the usability of every step.
- Dynamic resource reservation: how many machines to reserve and where follows the operations calendar, stocking up before major versions and holidays.
- Pre-defined post-scale-out observation items: which metrics show the scale-out worked, which metrics show the bottleneck is elsewhere.

Process breakpoints found in drills -- permissions not granted, stale images, template fields with no owner -- take minutes to fix in normal times, and half an hour minimum to fix on the incident scene. A plan without drills is capacity on paper only.

### Common pitfalls

- Understanding scaling out as adding machines, ignoring the structural preconditions of routing, sharding, and single-writer.
- Applying stateless auto-scaling policy to stateful components, trading dropped connections for the lesson.
- Server addition only accounts for the new server, and the capacity assumptions of global components are quietly broken after twenty servers opened in a row.
- Handing scale-in to an automatic policy that reclaims, during a trough, servers that were just warming back up.
- Plans written as documents, never drilled, so on the day of the incident every step runs for the first time on the scene.

The maturity of scaling capability ultimately shows in whether response speed and safety hold at the same time: scaling out fast without incidents depends not on on-the-spot improvisation but on structural conditions prepared long before and plans long since rehearsed. Most of the value of capacity work is delivered when there is no capacity event.

### Practical case: triaging an elasticity-boundary failure at "evening peak arrives, three servers drop at once"

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes this page's "First separate which components can actually be elastic," "Why scaling in is harder than scaling out," and "Capacity re-checking of global components" into deep water: the elasticity policy copied the generic practice, and dropped connections corrected the understanding -- this is the triage of the wrong elasticity applied to stateful components, and also a full unfolding of "scale-in thresholds and global re-checking."

**Background and symptoms**: a web-game backend onboarded an auto-scaling platform and applied the policy of "reclaim when CPU stays under **30**% for **10** minutes" uniformly to all services. As the Sunday **19**:00 evening peak was rising, three character logic servers were judged idle and reclaimed, over **6,000** online players dropped simultaneously, the sessions had nowhere to be restored from memory, and the game rolled back **15** minutes.

### Step 1: symptoms and caliber -- first separate which layer was scaled in

Scale-in caliber: the judgment used CPU, not online player count -- the scale-in triggered by the afternoon trough queued until the evening peak to execute; the three reclaimed servers had their online rate climbing that night, a textbook case of "a brief trough does not mean nobody is really there."

State caliber: you cannot scale in while players are online: sessions live in memory, and forcibly reclaiming them means dropped connections and lost state -- the sessions and progression of character logic servers all live in the process.

Global caliber: twenty servers were opened that month, doubling the matchmaking pool and global chat scale, but the server addition decision only accounted for the new servers themselves; nobody recalculated the capacity assumptions of global components.

### Step 2: layered attribution -- compare against this page's elasticity boundary

```text
Dropped-connection incident attribution  share
  Stateful component under stateless auto-scaling       52%
  Scale-in without debounce threshold, trough judgment executed late    29%
  Server addition only accounted for new servers, global components not re-checked      19%
```

Item-by-item comparison: character logic servers are components with large load units, thick state, and long lifecycles -- hitting "applying the same elasticity model mostly yields incidents rather than payoffs"; the scale-in had no watchlist and no debounce -- hitting "scaling in wrongly costs you the win-back"; cross-server matchmaking latency rose with the number of servers, and "server addition only accounts for the new server while the capacity assumptions of global components are quietly broken by twenty servers opened in a row" hits this exactly.

### Step 3: root cause -- one uniform elasticity policy was applied to the entire backend

The elasticity scheme was not designed component by component: the access layer and the room layer being elastic does not mean the character logic servers are elastic. To judge whether a component suits elasticity, first ask whether its state can be safely transferred or rebuilt within a few seconds -- for character logic servers the answer is "no," yet they hung under the same automatic policy.

### Step 4: remediation and backfill -- elasticity by layer, scale-in turned into a decision

1. Character logic servers exit auto-scaling: scale-in becomes a watchlist plus a manual merge process; a server enters the watchlist only after its activity level stays below the threshold for two consecutive weeks.
2. The stateless layer keeps elasticity: access proxies, matchmaking, and announcements continue auto-scaling; automatic scale-in is reserved only for the layer that is truly stateless and holds no assets.
3. Server addition triggers a global recalculation: every batch of more than **5** new servers recalculates the capacity assumptions of matchmaking, chat, and shared storage.
4. Scale-out plan drills: actually scale out one round per the plan, verifying the usability of every step -- images, permissions, templates.

Recheck ledger: dropped-connection incidents **1** -> **0**; the global matchmaking pool, verified against whole-region online, had **0** overloads after scaling; drills caught two breakpoints early -- stale images and missing permissions -- and the on-scene fix cost during incidents went to zero.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Component elasticity tiers | Access/room semi-elastic and automated, character logic servers on dedicated processes | First separate which components can actually be elastic |
| Scale-in debounce | Watchlist, two-week trend confirmation, manual merge, no automatic scale-in | Why scaling in is harder than scaling out |
| State-transfer criterion | Whether state can be safely transferred within seconds; if not, do not force elasticity | The applicability boundary of elastic scaling |
| Global re-check | Any server addition batch over 5 triggers recalculation of global component capacity assumptions | Capacity re-checking of global components |

### Three lessons from the case

1. **Elasticity is a per-component property, not a platform switch.** Applying auto-scaling to thick-state components trades dropped connections for the lesson.
2. **Scaling in is harder than scaling out because it takes away things in use.** Trough judgments need debouncing, and scaling in wrongly costs you the win-back.
3. **The server addition ledger must be accounted to the global level.** A single server is negligible; after twenty servers opened in a row, the load assumptions of cross-server components may already have been quietly broken.
