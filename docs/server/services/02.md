# Core Service Roles

## Category

server / services subtree. Node positioning: service role division is discussed on its own — what each role actually solves, the shapes of boundary contamination, and that a stable boundary matters more than having many roles.

## Definition


Once a system starts to split, the most common problem is rarely "not enough services" — it is many names with badly tangled responsibilities. Everyone talks about room server, scene server, event server, account server, but once it reaches implementation, the room server casually writes assets, the event server casually advances in-match state, the gateway casually runs half a business orchestration, and at the end the service names are separated while the state boundaries are still mixed.

So the point is the responsibility boundaries and state ownership behind these roles, not listing the common names.

## Problem

"Not enough services" is not the problem; "many names, badly tangled responsibilities" is: the room server casually writes assets, the event server casually advances in-match state, the gateway casually runs half an orchestration — the names are separated while the state boundaries are still mixed, which is the same as not having split at all.


### Why role division must be discussed on its own

The previous section solved "why split" and "what to draw the boundary around first"; this section solves "after splitting, which roles are easiest to stabilize, and which are easiest to pollute".

In real projects, most systems ultimately organize around a few typical classes of roles:

- Roles facing connections and sessions
- Roles facing runtime instances
- Roles facing long-lived assets and peripheral capabilities
- Roles facing scheduling and governance

If these roles are not clearly separated, the system usually ends up in one of two states:

- Some service accepts everything and finally becomes a new big monolith
- The names are split apart, but the state and responsibilities still cross each other

### What each common service role actually solves

### 1. Gateway / access service

The most core value of this class of service is maintaining the connection and session entry point. It typically owns:

- Connection establishment, disconnection, heartbeat, and rate limiting
- Session binding after authentication
- Basic protocol conversion and entry routing
- Kick, ban, and basic access governance

It should typically not own:

- Heavy business logic
- High-cost database transactions
- Advancing room, scene, or world state

The gateway is often done badly because it looks "closest to the player", so every piece of temporary logic gets stuffed into it. The result is that the connection layer and the business layer contaminate each other, and both failures and performance problems become harder to locate.

### 2. Account / character service

This class of service is closer to long-lived identity and character baseline governance. It typically owns:

- Account information and character profiles
- Login entry and character selection
- Basic character state reads
- The out-of-match asset entry, or the master asset index

It is not suited to carrying high-frequency in-match state, and it should not become a universal entry where "you can look up anything here". If the account service keeps getting stuffed with gameplay runtime state, it will easily become the hardest-to-split core coupling point later.

### 3. Matchmaking / scheduling service

A matchmaking service is not just about assembling players into a table. It often carries:

- Matchmaking buckets and rule computation
- Team formation and pre-match validation
- Room creation requests
- Node selection and instance allocation
- State coordination before match start

From an engineering perspective, the matchmaking layer is actually the first gateway through which many session-based games enter the scheduling system.

### 4. Room / dungeon / combat instance service

The core feature of this class of service is strong instance state, a relatively short lifecycle, and a boundary bound directly to a match or a dungeon. They typically own:

- High-frequency runtime state advancement
- Player input handling and broadcast
- Maintaining the authoritative state of the match
- Reconnection context and hosting context
- The final runtime result before settlement

What this class of service most fears is being stuffed with long-lived asset writes, global rule interpretation, and peripheral query logic, because its goal should be to keep the in-match primary path as simple, stable, and low-latency as possible.

### 5. Scene / world service

The room service emphasizes short-lived instances, while the scene or world service emphasizes a shared space that exists long term. Their usual distinction is:

- Whether state persists long term
- Whether there is multi-person coexistence and a public space
- Whether there is region switching and world migration
- Whether it carries continuous online maintenance of world rules

In MMO, large-open-map, and survival-sandbox projects, this class of service is often the system's backbone. Its difficulty is not just synchronization — it also includes region management, hotspot governance, and control handoff.

### 6. Peripheral business services such as events / quests / shop

This class of service is better organized around long-lived rules, config interpretation, and progress governance. Common responsibilities include:

- Event rule interpretation
- Maintaining quest or event progress
- Reward grant requests
- Shop state, purchase constraints, and redemption records

Their biggest problem is usually not "too many features" but that the boundary is easy to lose control of. If one event service simultaneously carries config, progress, granting, reports, and cross-server orchestration, every subsequent change becomes a system-wide chain reaction.

### 7. Shared capability services such as leaderboard / mail / social / chat

These capabilities are usually reused across gameplay modes and across scenes, so whether the boundary is clear is very important.

- A leaderboard is more like a read, aggregation, and display capability, and should not intrude back into the combat primary path
- Mail and compensation are more like long-lived asset peripheral delivery paths
- Chat and social have their own connection, broadcast, and relationship models, and do not fit well being mixed with in-match synchronization

They are easily underestimated because they are usually not in the main combat loop, but once the boundary is unclear they create hidden coupling across the whole system.

### 8. Payment / order / risk control service

This class of service is usually not on the gameplay main loop, but its boundary is often more stable than the gameplay services. Common responsibilities include:

- The order state machine
- Callback confirmation and fulfillment triggering
- Handling abnormal orders
- The audit, risk control, and accountability chain

What this class of service most fears is "doing it while at it". Because once the asset and order path breaks, the repair cost is far higher than for ordinary gameplay problems.

### 9. Coordination layer / control plane related services

Many projects do not formally count these as service roles early on, but they will definitely add them later. They typically own:

- Node registration, grouping, and health governance
- Region routing and instance allocation
- Migration, draining, and traffic cutover
- Scaling orchestration
- Global config distribution and version gating

They do not advance business state themselves, yet they determine whether the whole system can be stably scheduled and recovered.

### The most common boundary contamination of these roles

### Long-lived assets and instance state mixed together

For example, the room server directly writes long-lived assets, the account server directly advances dungeon state, the event server directly holds high-frequency in-match state. It looks convenient early on, but later it simultaneously raises coupling, recovery cost, and the blast radius of failures.

### Rule interpretation and state maintenance mixed together

This appears especially easily in systems like events, quests, and the shop. If config interpretation, progress maintenance, reward granting, and statistical reports all grow inside one service, every small change can affect the whole path.

### Turning the gateway into a business bus

Once the gateway starts carrying too many business decisions, it is no longer just the access layer — it becomes a hidden bus that is hardest to split, hardest to test, and hardest to troubleshoot.

### More roles is not better; a steadier boundary is better

Listing so many roles does not mean every project should split all of them out from the start. What should really be asked is:

- Are these responsibilities already stable enough
- Would splitting them out reduce cross-service jitter
- Is it worth having independent scaling and governance
- Is there an independent failure domain and independent operational value

Early on, it is not uncommon for one service to hold several roles at once. The problem is not whether they are merged, but whether the logical boundary was clarified first. With a clear boundary, they can be smoothly extracted later; without a clear boundary, merged or split, it is messy either way.

### A more practical observation framework

When building intuition, you can first look at these roles as four layers:

- Connection and session layer: gateway, access, session binding
- Runtime state layer: matchmaking, room, dungeon, scene, world
- Long-lived asset and shared capability layer: account, events, payment, mail, leaderboard, social, risk control
- System governance layer: coordination layer, control plane, routing, orchestration, monitoring

This is not a fixed deployment diagram, but it helps the team avoid the mess of "everything is called the business server".

### Common pitfalls

The most common error is treating a service name as a boundary, assuming that once you name something "room server", "event server", or "account server", the responsibilities automatically become clear. The second is letting one service carry three kinds of responsibility at once — connection, instance state, and long-lived assets. The third is ignoring the independent role of the coordination layer and control plane, so the business logic runs but the system cannot be stably scheduled, migrated, and recovered.

### Practical case: a business-bus investigation where "the gateway kept growing fatter, and one change made the whole server jitter"

> The case is a demonstration example (not drawn from a real project); the numbers are rounded for simplicity. It drives this page's "1. Gateway / access service", "Turning the gateway into a business bus", and "More roles is not better; a steadier boundary is better" into deep water: what changed was rate limiting, what jittered was the whole server — this is an investigation into separated service names with mixed state boundaries, and the full expansion of "how to make the boundary steady rather than the role count high".

**Background and symptoms**: A gateway service in an MMO that grew from a pure connection access layer into **80,000** lines of code with **30**-plus embedded business logic points. A small release that changed only the rate limiting strategy triggered **20** minutes of server-wide login anomalies — the blast radius expanded from a single module to every accessing player.

### Step 1: Symptoms and caliber — first measure how large the failure blast radius is

Blast radius caliber: every gateway release affects all accessing players, so a single gateway failure is counted as a server-wide blast radius; releases of business services in the same period affected only their own gameplay mode.

Change caliber: **30**-plus business logic points (order validation, event state query, part of settlement triggering) all grew inside the gateway, so any change anywhere required a full regression of the entire access path.

Localization caliber: inside the gateway the connection layer and the business layer contaminated each other, and the average localization time for the same class of failure was **4** hours — during troubleshooting you could not say whether it was an access problem or a business problem.

### Step 2: Layered attribution — investigating against this page's boundary contamination list

```text
故障影响面扩散归因  占比
  网关承担重业务逻辑与半套业务编排    57%
  房间服顺手写长期资产                25%
  活动服持有局内高频状态              18%
```

Compared item by item: the gateway was stuffed with business orchestration (this page says the gateway is "closest to the player, so every piece of temporary logic gets stuffed in"); the room server casually wrote long-lived assets; the event server held high-frequency in-match state. All three kinds of contamination were present, and the gateway one had the largest blast radius.

### Step 3: Root cause — treating the service name as the boundary

Once the name "gateway" was given, the team assumed the responsibilities were automatically clear, when in fact connection, instance state, and business logic were mixed inside the same process. Once the gateway carries too many business decisions, it is no longer just the access layer — it becomes a hidden bus that is hardest to split, hardest to test, and hardest to troubleshoot.

### Step 4: Disposition and backfill — redrawing boundaries by role

1. Slim down the gateway: keep only connection establishment and disconnection, heartbeat, rate limiting, session binding after authentication, basic protocol conversion, and entry routing; move all business decisions out to business services.
2. Separate long-lived assets from instance state: the room server no longer writes long-lived assets, and all asset changes go through the account / asset service; the event server no longer holds high-frequency in-match state.
3. Write boundaries into the role definition review: each service states two columns, "responsible for" and "not responsible for", and the review checks them item by item.

Recheck ledger: gateway code **80,000** lines → **21,000** lines; the failure blast radius contracted from the whole server to a single module; the average localization time for the same class of failure went from **4** hours → **40** minutes; the release regression scope for rate limiting changes shrank to the gateway itself.

**Backfill checklist**:

| Backfill item | Action | Backfilled at |
|-----|------|--------|
| Gateway responsibility boundary | The gateway keeps only connection, session, authentication, and routing; business decisions move out to business services | 1. Gateway / access service |
| Separate long-lived assets from instance state | The room server does not write long-lived assets, the account service does not advance dungeon state, and asset changes go through the asset service | Long-lived assets and instance state mixed together |
| Separate rule interpretation from state maintenance | The event service's config interpretation, progress maintenance, granting, and reports are split apart and not crammed into one service | Rule interpretation and state maintenance mixed together |
| Role boundary review | Each service writes two columns, "responsible for / not responsible for", with boundary stability prioritized over role count | More roles is not better; a steadier boundary is better |

### Three lessons from the case

1. **A service name is not a boundary.** Naming something "gateway" does not mean the responsibilities are clear; when connection, instance state, and business logic are mixed in one process, the failure blast radius is counted by the largest of them.
2. **The service closest to the player is the most likely to grow into a hidden bus.** Once the gateway starts carrying too many business decisions, it becomes the link that is hardest to split, hardest to test, and hardest to troubleshoot.
3. **A steady boundary matters more than role count.** Whether to split is a later matter; first make each service's "responsible for / not responsible for" clear, and only then is smooth extraction worth talking about.
