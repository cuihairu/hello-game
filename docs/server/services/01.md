# Service Splitting Methodology

## Category

server / services subtree. Node positioning: splitting answers four hard questions — state binding, failure isolation, independent scaling, and team boundaries; draw boundaries around state first, not around menus. General outline of the services subtree.

## Definition


Service splitting is not cutting one big process into a few small processes, and it is not translating project management's "module" directly into "service". Splitting that is genuinely valuable answers four harder questions: which state must advance together, which failures should be confined locally, which paths are worth scaling independently, and which teams need boundaries that support them rather than boundaries that lock them against each other.

If these questions are not thought through first, the finer you split the system, the more you will have to pay back later: service discovery, routing binding, idempotency, compensation, migration, reconnection, governance, audit — all of it comes crashing up behind you.

## Problem

Treating splitting as "cut processes" or as a translation of project management's "module" yields fourteen services and triple the latency: splitting that is genuinely valuable is driven by four questions — state advancement, failure domains, scaling, and team collaboration; menu-style splitting adds more than it buys, and the cost rises first while the benefit arrives later.


### Why a project reaches the point of splitting

Rarely does a project need a complex distributed architecture on day one. Most are pushed to this point bit by bit by the reality of production:

- Some gameplay modes have extremely high traffic spikes at match start, while other systems are long-term low-frequency but must stay stable
- Runtime state such as rooms, dungeons, and scenes begins to show clearly different load shapes
- Peripheral capabilities such as events, payment, social, and leaderboards need to decouple from the core gameplay
- Players start flowing across gameplay modes, across nodes, and across regions
- The organization grows, and different teams must release and govern independently
- The blast radius of a single point of failure is too large, and "one module breaks and the whole site rides along for the ride" is no longer acceptable

What really pushes splitting is not the abstract "high concurrency", but that state boundaries, failure domains, and operational needs have begun to diverge noticeably.

### Draw boundaries around state first, not around menus

Many teams start by splitting along the function menu:

- One service for login
- One service for mail
- One service for events
- One service for the shop

This way of cutting can work sometimes, but it is not naturally correct. A more reliable starting point for splitting is usually state:

- Which state must collaborate at high frequency within the same process
- Which state can tolerate asynchronous flow
- Which state is short-lived instance state
- Which state is long-lived asset state
- Which state, once wrong, is extremely costly and must be governed on its own

For example, combat state inside a room usually requires high-frequency, low-latency, same-domain advancement, and is not a good candidate for being cut into several remote calls; payment orders, reward grants, and mail delivery look more like long-lived asset paths and are better governed separately; event rules and event progress, though both called "events", do not necessarily belong on the same runtime path.

What a boundary should really be drawn around is the way state is updated and the semantics of failure, not what the front-end menu looks like.

### Answer four questions before splitting

### 1. Where do you most want a failure to be isolated

If a room node is saturated, you want only the current room affected, not login, payment, and social jittering along with it; if the event path fails, you do not want it dragging down the combat primary path in reverse. Judgments of this kind — "where do I want the break, and where do I not want it to spread" — are essentially failure domain partitioning, and they are the most genuine splitting signal.

### 2. Which paths are worth scaling independently

Different services often have completely different traffic curves:

- Matchmaking and rooms rise and fall with match-start peaks
- Events and the in-game shop are driven by operational timing
- Chat, push, and social have their own independent rhythm
- Payment and order paths need peak headroom but should not sit at high load permanently

If these entirely different loads stay bound in a single deployment unit for a long time, scaling actions become increasingly crude, and both wasted resources and risk go up.

### 3. Which state must never jitter across services at high frequency

It is fine for a path to make an occasional single cross-service request, but if high-frequency state such as skill casts, object synchronization, position updates, and collision settlement has to keep crossing services, the system will be dragged down by network latency, timeouts, and retries very quickly. The point of splitting is not "divide as much as possible", but avoiding forcibly cutting apart state that ought to advance within the same domain.

### 4. Which boundaries need to support independent evolution

Events, payment, login, matchmaking, rooms, and world operations are, in reality, often maintained by different teams. If these boundaries fundamentally do not support independent release, independent scaling, and independent problem localization, the engineering cost keeps amplifying once the organization grows.

### What each common splitting approach fits

### Split by gameplay instance

Typical examples are the matchmaking server, room server, dungeon server, and battle server. This approach suits projects with clear session boundaries and a well-defined in-match lifecycle. Its advantages are an intuitive runtime model and instances that can be created, destroyed, and scaled independently; its downside is that it tends to put all attention inside the match and neglect long-term state outside the match and cross-gameplay migration.

### Split by world or scene

This approach is common in MMOs, large open maps, survival sandboxes, or persistent online worlds. It is closer to spatial boundaries and long-lived world state, but the price is that migration, cross-scene collaboration, hotspot governance, and handoff of control all become noticeably heavier.

### Split by domain capability

Accounts, payment, social, mail, leaderboards, events, and risk control all belong to this class. It suits governing long-lived assets and shared capabilities; its advantages are relatively stable boundaries that are easy to govern independently, and its downside is that if the join to instance-state boundaries is not done well, it easily creates large amounts of cross-service coupling on the primary path.

In real projects the most common pattern is not a three-way choice but a hybrid: instance state organized by gameplay or scene, long-lived assets and peripheral capabilities organized by domain.

### What cost does service splitting actually add

Splitting is not elastic for free. What you gain is failure isolation, independent scaling, and team decoupling; what you pay is the following set of continuing costs:

- Service discovery and node governance
- Routing, binding, migration, and reconnection
- Cross-service timeouts, retries, idempotency, and compensation
- Tracing, log correlation, and problem localization
- Config distribution, gray release, version compatibility, and deployment orchestration
- Control plane, health checks, draining, and recovery mechanisms

If the team is not ready to absorb these infrastructure costs, splitting too early usually just moves the problem out of the code and onto the system boundary.

### A more practical decision criterion

To judge whether a service should be split, looking at the following is usually enough:

- Whether long-term stable state boundaries already exist inside the monolith
- Whether a subsystem is worth scaling independently
- Whether a class of failure must be isolated locally
- Whether a team must release and govern independently
- Whether the high-frequency paths and consistency cost can still be tolerated after splitting

As long as these questions cannot be answered clearly, so-called splitting is very likely just renaming complexity.

### A safer order of splitting

A more reliable order is usually:

1. Draw boundaries by state and responsibility first.
2. Then correct the boundaries against failure domains and scaling needs.
3. Only then decide what deployment form, process count, and node topology those boundaries correspond to.

The benefit of doing it this way is that the system is organized around real problems first, rather than around the fashionability of deployment first.

### Common pitfalls

The most common error is understanding service splitting as an "organizational upgrade" or a "technology upgrade", rather than as state boundary design. The second is splitting services while simultaneously letting high-frequency strongly-consistent state jitter back and forth across them. The third is splitting only the business nodes without adding service discovery, routing, monitoring, recovery, and a control plane — the result being that monolithic complexity has merely been swapped for distributed chaos.

### Practical case: an over-splitting investigation where "fourteen services were split out, and skills got three times slower"

> The case is a demonstration example (not drawn from a real project); the numbers are rounded for simplicity. It drives this page's "Draw boundaries around state first, not around menus", "Answer four questions before splitting", "What cost does service splitting actually add", and "Common pitfalls" into deep water: splitting answers a state boundary question, not a technology fashion question — this is a boundary investigation of service splitting, and the full expansion of "so-called splitting is very likely just renaming complexity".

**Background and symptoms**: A competitive project with real-time battlefields; a **25**-person team split out **14** services along a microservices template — login, matchmaking, room, input, combat calculation, state broadcast, settlement, mail, shop, leaderboard, chat, events, payment, GM — each with its own repository and its own deployment. After launch, the end-to-end P99 of the PVP skill path was **130** milliseconds, while the same path under load testing in the monolithic period took only **45** milliseconds, close to **3** times; the complaint "a skill cast takes half a second to respond" was steady at **260** tickets per day. More confusing was that the service governance dashboard was all green: the finer the split, the better a single-service view looked, and the fewer people who looked at the path view.

### Step 1: Symptoms and caliber — first turn "three times slower" into a comparable latency ledger

Caliber aligned: skill path latency = client sends skill request → server settlement response back, excluding client presentation. The comparison ledger runs two versions on the same load test model in the same data center:

- **Monolith version**: P99 **45** milliseconds
- **Split version**: P99 **130** milliseconds, increment **85** milliseconds

The increment is not evenly distributed: packet capture compared skill requests one by one, and the latency concentrated in the interval of "requests queuing between services" — network transport itself accounted for almost nothing. Rule out the physical layer first, then count the hops.

### Step 2: Layered attribution — the increment ledger from network to hops

```text
物理网络   机房内 RTT 0.3ms、跨可用区 0 次——排除网络质量
序列化     单次 payload 约 2KB、编解码 0.6ms/次——不是包大小与编解码
跳数账     一次技能释放串行 3 跳：输入服务 → 战斗计算服务 → 状态广播服务
           每跳排队+调度+序列化 ≈ 28ms，3 跳叠加 ≈ 84ms——增量几乎全在跳数上
状态账     战斗状态被三个服务来回读写：输入队列、判定状态、广播快照分属三处，
           同一帧的数据跨进程走两圈
```

The increment ledger closes to a single sentence: of the **85** milliseconds, about **84** milliseconds came from three serial hops — the queuing, scheduling, and serialization of each hop is precisely this page's "cross-service timeouts, retries, idempotency, and compensation" cost accruing interest hop by hop along the path.

### Step 3: Root cause — high-frequency strongly-consistent state was cut across a service boundary

Checked against this page's "Answer four questions before splitting", none of the four questions was answered in this split: failure domains were never imagined (nobody discussed "where do I want the break, and where do I not want it to spread"); scaling was a gut call (the load curves of input, combat, and broadcast were entirely of the same source, with no independent value in scaling them separately); most fatal was the third question — **high-frequency state such as skill casts, object synchronization, position updates, and collision settlement had to keep crossing services**, which is exactly the counter-example this page names in its own words; and independent evolution did not hold either (the three services were the same team on the same version cadence). The motive for splitting was "upgrade to a microservices architecture" — the first of this page's common pitfalls, "understanding service splitting as an organizational upgrade or a technology upgrade", came true verbatim; and the cut was along the function menu rather than along state boundaries — combat state for skills should have "collaborated at high frequency within the same process", yet was cut into three remote calls.

### Step 4: Disposition and backfill — pull the combat path back into one domain, keep the domain split

The fix: input, combat calculation, and state broadcast were merged back into a **single-process room instance** (returning to this page's "split by gameplay instance" track), with in-room state advancing in one domain; long-lived asset paths such as mail, shop, leaderboard, events, and payment kept their domain split. Recheck: skill path P99 **130** → **48** milliseconds, complaints **260** → **30** per day; service count **14** → **9** (**5** instance-state services merged), and service discovery entries and path hop counts fell back in step — the operational surface did not get heavier, it got lighter.

**Backfill checklist**:

| Landing point | Action | Backfilled at |
|-----|------|--------|
| Splitting review | A new service must answer the "four questions" at proposal: failure domain, scaling, high-frequency state, independent evolution | Answer four questions before splitting |
| State boundary first | Draw state boundaries before deciding deployment form; forbid cutting services along menus or along the org chart | Draw boundaries around state first |
| High-frequency paths in one domain | Register frame-level paths as "advancing in one domain"; cross-service calls require an architecture review waiver | Which state must never jitter across services at high frequency |
| Splitting cost ledger | At proposal, assign the six cost items (discovery / routing / compensation / tracing / config / control plane) to an owner | What cost does service splitting actually add |

### Three lessons from the case

1. **Splitting answers a state boundary question, not an organizational slogan** — "going microservices" is not the goal; failure domains, scaling, and independent evolution are.
2. **High-frequency strongly-consistent state is a hard boundary for splitting** — every extra hop pays the tax of queuing and serialization one more time.
3. **The decision criterion comes before the splitting action** — when the four questions cannot be answered, so-called splitting is very likely just renaming complexity.
