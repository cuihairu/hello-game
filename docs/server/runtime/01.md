# Single-threaded, Multi-threaded, and Actor

## Category

server / runtime subtree. Node positioning: an execution model is first and foremost a question of state -- single-threaded, multi-threaded, and Actor are three different state-organization philosophies, and real systems are hybrids rather than a pick-of-three.

## Definition


Single-threaded, multi-threaded, and Actor look on the surface like three parallel technical options, but in reality they correspond to three completely different state-organization philosophies. What has ever really been worth comparing is never "who is faster," but:

- Who holds the state.
- What the unit of scheduling is.
- How concurrency conflicts are avoided.
- Which model is easier to reason about under peaks and failures.

Many game systems are unstable in production not because the algorithms are poor, but because the execution model and the state boundaries never lined up from the start.

## Problem

Comparing execution models by asking "who is faster" is the wrong question: the three models correspond to completely different state organization and reasoning styles, with single-threaded winning on inferrability, multi-threaded winning on true parallelism, and Actor winning on isolation. Real systems are almost all hybrids, and the selection target is the common shape of game servers rather than theoretical superiority.


### Why an execution model is first and foremost a question of state

When discussing concurrency models, the most common pitfall is staring only at thread count and CPU utilization. The questions that actually matter are usually:

- Can the same state be modified by multiple parties at once.
- Is the execution order of a business path stable.
- Who takes over the result after an async task comes back.
- Will one module slowing down drag down the whole system.

All of these questions are essentially about state ownership, not about "how many threads were used."

### Why single-threaded has had staying power for so long

A lot of game logic -- especially core paths like rooms, scenes, combat, matchmaking, and state machines -- still prefers single-threaded or single-writer models. Not because the technology is behind, but because single-threaded naturally solves many of the hardest problems:

- Execution order is stable.
- There is no lock contention.
- State-change timing is easy to infer.
- Replay, re-enactment, and debugging are cheap.

Single-threaded is really suited to:

- Logic whose state is tightly coupled and requires sequential execution.
- Workloads that are still within a manageable range for a single instance.
- Situations where the cost of failure fears inconsistency more than it fears leaving the CPU under-utilized.

Its cost is equally clear: single-instance throughput has a ceiling, and when hotspots concentrate you need to scale by partitioning, splitting instances, or outsourcing async work -- not by brute-forcing it with "just open a few more threads."

### What multi-threaded is really good at

Multi-threaded is not automatically a more advanced choice. What it is really good at is:

- Parallel heavy computation.
- Async I/O.
- Batch tasks.
- Parallelizable work that is loosely coupled from main logic.

For example:

- Batch pathfinding.
- Asset preprocessing.
- Log flushing.
- Peripheral statistics.
- Encoding and compression.

What multi-threaded is least suited to is core logic with very tight shared state, very strong ordering requirements, and results that must be strictly replayable. Because once that kind of logic flows freely across threads, lock contention and timing problems amplify quickly.

### What Actor actually solves

The most valuable thing about Actor is not "messages sound elegant," but that it rewrites the concurrency problem as:

- Each Actor holds its own enclosed state.
- External parties interact through messages rather than directly sharing memory.
- Within the same Actor things usually execute sequentially.

The payoff of this is very direct:

- State boundaries are clear.
- Concurrency conflicts are reduced.
- Dependencies between modules are more explicit.
- Containing the spread of failures is easier than with a fully shared-memory model.

Actor is especially suited to:

- Systems with a natural partition key or single-writer model.
- Rooms, scenes, player entities, matchmaking buckets, and sequential state machines.
- Teams that want to turn "thread concurrency" into "message cooperation."

But Actor is not a free lunch. You still have to solve:

- Message storms between Actors.
- Mailbox backlogs.
- Hotspot Actors becoming bottlenecks.
- Cross-Actor cooperation and consistency.

### What a more practical way of comparing should look at

### State isolation

- Single-threaded: strongest, everything is by default in the same context.
- Multi-threaded: weakest, unless you govern the state boundaries separately.
- Actor: strongest locally, on the premise that the state is really enclosed inside the Actor.

### Throughput scaling

- Single-threaded: scales by splitting instances, partitioning, and outsourcing heavy tasks.
- Multi-threaded: best in theory, but real gains depend heavily on task independence.
- Actor: scales by multiple Actors, partitioning, and schedulers, but hotspot Actors cap the ceiling.

### Ordering inferrability

- Single-threaded: best.
- Multi-threaded: worst.
- Actor: in between -- good within a single Actor, and requiring extra governance across Actors.

### Production recoverability

- Single-threaded: failures are most direct to locate, but hotspot pressure concentrates.
- Multi-threaded: problems hide most easily, especially intermittent timing bugs.
- Actor: local failures are easier to isolate, but message queues and hotspot distribution must be observed continuously.

### Real systems are usually hybrids, not a pick-of-three

Mature systems almost never choose just one model; what is more common is:

- Core state machines and combat rooms use single-threaded or single-writer Actor.
- Asset processing, compression, logging, and peripheral computation use multi-threaded.
- Async flows are picked up by coroutines or task queues.

The key is not "mixing" itself, but being clear about which parts must be sequential, which parts are worth parallelizing, and which parts can be made async without polluting core state in return.

### A more common landing point for game servers

A safer engineering landing point is usually:

- Gateway and I/O layers use event-driven or multi-threaded I/O.
- Room, scene, and player state use a single-writer thread or Actor partitioning.
- Heavy computation tasks are outsourced to a thread pool or batch system.
- Long-lived assets and peripheral systems are made async wherever possible.

This organization is not the only answer, but it honors one core principle: keep the state that most fears inconsistency inside the execution model that is easiest to reason about.

### Common pitfalls

- Parallelizing too early for performance, so shared state and lock contention amplify the problem.
- Treating Actor as a silver bullet that automatically solves every concurrency problem, while not governing hotspot Actors, mailbox backlogs, and cross-Actor consistency.
- Staring only at CPU utilization and ignoring ordering inferrability, recovery difficulty, and production triage cost.

What this page really needs to answer is not which model is hipper, but what kind of execution unit the core state should live in.

### Practical case: triaging a concurrency misjudgment where "multi-threading was adopted for performance, but the timing bugs could not be tracked down"

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes this page's "Why an execution model is first and foremost a question of state," "What multi-threaded is really good at," and "A more common landing point for game servers" into deep water: throughput did go up, but the timing failures could not be tracked down -- this is the triage of parallelizing too early for performance, and also a full unfolding of "how to keep the state that most fears inconsistency inside the execution model that is easiest to reason about."

**Background and symptoms**: one SLG battle server, **400** rooms per instance. To raise CPU utilization, the team changed room logic from single-threaded to **4** threads sharing the same world state. After launch, average TPS rose **22**%, but **5-8** timing-class failures appeared every week -- skill settlement occasionally duplicated or was lost, reproduction rate was low, and mean time to locate was **2.5** days.

### Step 1: symptoms and caliber -- record the gains and the costs separately

Gains ledger: average TPS rose from **12000** to **14640** (+**22**%), and CPU utilization climbed from **38**% to **71**%.

Costs ledger: timing-class failures of **5-8** per week, all concentrated on the path where multiple threads concurrently mutate the same world state; intermittent, with no fixed reproduction steps, mean time to locate **2.5** days.

Contrast caliber: read-only pathfinding batches and log flushing during the same period had no problems -- everything that broke involved reading and writing shared state.

### Step 2: layered attribution -- investigate along this page's state-isolation dimension

```text
时序故障归因  占比
  共享世界状态跨线程自由流动，锁外读改写    62%
  顺序敏感逻辑被并行打散                     26%
  偶发时序 Bug 本身难以复现、排障成本高      12%
```

Triage path: failures concentrate in three places -- room state, Buff settlement, and skill timing -- all logic that is "tightly coupled in state and requires sequential execution"; and these are precisely the targets this page says multi-threaded is least suited to -- tight shared state, strong ordering requirements, and results that must be replayable.

### Step 3: root cause -- parallelizing too early for performance, placing core state into the hardest model to reason about

The change only stared at CPU utilization and never first asked "can this state be modified by multiple parties at once" or "is the execution order of this business path still stable." The result was placing the core state that most fears inconsistency into the execution model with the worst ordering inferrability, amplifying lock contention and timing problems together.

### Step 4: remediation and backfill -- return core state to a single writer, outsource heavy computation

1. Change room and scene state back to a single-writer thread or Actor partitioning: one execution unit per room, sequential execution within the room, and state is no longer shared across threads.
2. Outsource heavy computation to a thread pool: loosely coupled work like batch pathfinding, log flushing, and peripheral statistics goes to the thread pool and never writes back to core state.
3. Make the sequential/parallel boundary explicit: which parts must be sequential, which are worth parallelizing, and which may be async but must not pollute core state in return -- write this into architecture review.

Verification ledger: timing-class failures **5-8** per week -> **0**; TPS holds at **+18**% (slightly below the multi-threaded peak after partitioning, but failures went to zero); mean time to locate similar problems **2.5** days -> **0.5** days.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| State isolation assessment | Before any parallelization change, assess whether the state may be modified by multiple parties at once and whether the execution order is still stable | Why an execution model is first and foremost a question of state |
| Multi-threaded only for loosely coupled parallelism | Parallelism is used only for loosely coupled work like heavy computation, async I/O, and batch tasks | What multi-threaded is really good at |
| Actor partitioning | Rooms, scenes, and player entities land on single-writer Actors by partition key, with sequential execution inside the room | What Actor actually solves |
| Hybrid landing point | Multi-threaded I/O at the gateway, single-writer core state, heavy tasks on a thread pool -- written into the architecture diagram | A more common landing point for game servers |

### Three lessons from the case

1. **Before parallelizing, ask the state questions first, not the CPU question**. A change that only stares at utilization hands shared state to multi-threading, and lock contention and timing problems will amplify together.
2. **Order-sensitive core logic is not worth parallelizing**. The value of room combat lies in inferrability and replayability; the throughput bought by true parallelism often cannot pay back the triage cost.
3. **In a hybrid the key is the boundary, not the mixing**. Only when it is clear which parts must be sequential and which are worth parallelizing can you claim to be "keeping the state that most fears inconsistency inside the execution model that is easiest to reason about."
