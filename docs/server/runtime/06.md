# Epoch-driven Actor / Channel Runtime

## Category

server / runtime subtree. Node positioning: a dedicated runtime built for determinism, sequential state advancement, low latency jitter, and re-enactment -- Epoch defines the unit of advancement, Channel governs timing, and ECS carries the data layout.

## Definition


If you keep pushing the execution model discussion from the earlier pages further down, you naturally arrive at a more concrete question: is there a runtime that is not designed for a general business framework, but specifically for problems like determinism, sequential state advancement, low latency jitter, and re-enactment?

Runtimes of the `Epoch` variety are a very typical answer. They are not a general distributed Actor platform, nor simply a message queue, but a runtime organization leaning toward games and highly time-sensitive systems. They bind `Epoch-driven`, `Actor`, `Channel`, and `ECS` explicitly together, with a clear goal: to make determinism, sequential execution, and low jitter formal design in a single-partition, single-writer authoritative logic scenario.

## Problem

General frameworks solve reuse, while this problem domain asks for re-enactment and controllable jitter: Epoch decides the granularity of advancement, Channel solves timing governance rather than communication, and ECS decides the data layout. It is not suited to general business, and if the boundary is not declared it will be misused as a universal runtime.


### Why this kind of runtime appears

Many general runtimes and general Actor frameworks are better at:

- Decoupling between services.
- General concurrency encapsulation.
- Throughput-oriented async tasks.

But they are not necessarily good at the stricter problems below:

- All logic advances around an explicit logical time.
- The same state allows only a single writer.
- Message timing must be stable and inferrable.
- Behavior needs to be reproducible, re-enactable, and replayable.
- Jitter matters more than average throughput.

In scenarios like game combat, frame sync, sequential matchmaking, and risk-control state machines, these requirements are often more important than "generality." That is why this runtime design, with its obvious stance, exists.

### What `Epoch` really means here

In this kind of design, `Epoch` is not just Tick with a new name; it makes logical time a first-class runtime concept. More concretely:

- A message is not executed the instant it arrives.
- Logic does not run for whoever grabs a thread first.
- State is not visible or writable at any moment.

Instead, the system organizes around explicit logical time intervals:

- Which messages are received within a given time interval.
- Which Actors execute within a given time interval.
- Which state is externally visible at the boundary of a given time interval.

The core value of doing this: time comes before scheduling, and order comes before concurrency.

### How the Actor here differs from a general Actor

The Actor here is closer to an "enclosed state unit on a fixed thread" than to an "infinitely flexible message object." It emphasizes:

- Enclosed state.
- Sequential execution.
- Visible boundaries.

This means:

- State updates inside the same Actor more easily keep a deterministic order.
- External parties do not directly share writes to state but send messages through a Channel.
- Scheduling policy is easier to organize around time slices and a single-writer model.

This kind of Actor is not necessarily the most general, but it suits systems with strong timing and strong inferrability.

### The Channel here does not solve "communication," it solves "timing governance"

Judging from this kind of design, the key point of a Channel is not "it can send messages," but:

- Messages enter a queue first.
- They do not trigger execution immediately.
- Epoch then decides when they are consumed.

This differs a lot from many general message mechanisms. General message systems often emphasize async decoupling and consuming as fast as possible; here the emphasis is:

- When a message takes effect for the system.
- In what logical order a message is processed.
- Whether a consumption boundary can be replayed and inferred.

This is also why it looks more like runtime infrastructure than an ordinary message bus.

### What role ECS plays here

This kind of runtime is not content with being "semantically correct"; it also wants:

- Hot path object updates to be batchable.
- Data layout closer to cache.
- CPU utilization pushed up while preserving sequential execution and a single writer.

In other words, ECS here is not a standalone architectural style but forms, together with Epoch + Actor:

- Time organization.
- Enclosed state.
- Hot path data layout.

Only these three together produce its performance and determinism characteristics.

### What this is best at taking on

The boundary where this kind of runtime fits is usually very clear:

- Single-partition or single-writer authoritative logic.
- Hard-real-time combat.
- Frame sync or near-frame-sync logic advancement.
- Sequential state-machine style systems.
- Scenarios highly sensitive to reproducibility, re-enactment, and low jitter.

To put it plainly, it suits systems that "cannot let state be written concurrently at will, and cannot let time semantics drift."

### What this is not suited to

This kind of design is usually not suited to:

- Arbitrary cross-node distributed cooperation.
- Globally strongly ordered large systems.
- Business systems that wait on many external slow dependencies everywhere and have many external side effects.
- Highly loosely coupled scenarios pursuing general middle-platform capability.

In other words, it is not a "stronger general framework" but a "narrower, harder, more opinionated runtime."

### The biggest difference from an ordinary Actor framework

The difference closer to engineering can be understood this way:

### A general Actor framework cares more about

- Concurrency abstraction.
- Decoupling inside a service.
- Possibilities for distributed cooperation.
- Usability and extensibility.

### An Epoch-driven Actor Runtime cares more about

- Time as a first-class citizen.
- Single-writer state and sequential execution.
- Reproducible behavior.
- Low latency jitter.
- When a message takes effect, not merely when it arrives.

Both kinds of systems can be called Actor, but their design goals are clearly different.

### What makes this runtime so attractive

From a game engineering perspective, this runtime has several especially strong points:

- Logical time is explicit, naturally suited to frame advancement and replay.
- Actor state is enclosed, naturally reducing shared writes and lock contention.
- Channels do not trigger execution immediately, making deterministic timing governance easier.
- Combined with ECS, it fits high-frequency hot path object updates better.

This is really turning many of the principles from Chapters 4 and 5 into one unified runtime:

- Tick / Epoch.
- Single writer.
- Sequential consumption.
- Batch updates.
- Low jitter.

### What is really hard about this runtime

Its difficulties are equally obvious, and they are not in the surface API but in the design boundary:

- Once the system crosses partitions and nodes, how is the single-writer model maintained.
- How to interact with non-deterministic external systems.
- How is Channel message backlog governed.
- How do Epoch boundaries and real-time I/O align.
- Which state may live inside the runtime and which must be outsourced.

In other words, this kind of runtime is very well suited to be a "core logic kernel," but not necessarily to swallow an entire site's business.

### A landing point closer to game servers

If placed in a game system, the more realistic use is usually not "use it for the whole project," but:

- Room combat core.
- Frame sync main loop.
- Combat Actor / entity scheduling.
- Sequential state-machine style gameplay instances.

And put these on the outside:

- Login and access.
- Payment and orders.
- Events and mail.
- Most peripheral async business.

This combination better matches its nature as a "strong runtime, weak general platform."

### Common pitfalls

- Treating this kind of runtime as a general distributed platform and trying to make it carry all business and all cross-node cooperation directly.
- Seeing only names like Actor and Channel, while ignoring that its real core premise is actually `Epoch-driven` logical time organization.
- Using it to solve a large number of external non-deterministic, cross-partition global coordination problems, and ending up thinking the framework is "not flexible" when it is really just a mismatch between the problem and the tool.

What this page really wants to show is not how cool some concrete implementation is, but why some game core logic chooses a runtime kernel that is time-first, order-first, and single-writer-first.

### Practical case: triaging a boundary misjudgment where "a dedicated runtime was treated as a general foundation, and frame advancement drifted more with every run"

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes this page's "`Epoch` really means here," "The Channel here does not solve 'communication,' it solves 'timing governance'," and "What this is not suited to" into deep water: the team wanted to save one framework, but ended up inviting peripheral business into the kernel -- this is the triage of a boundary that was never declared and got misused as a universal runtime, and also a full unfolding of "strong runtime, weak general platform."

**Background and symptoms**: one project treated the Epoch-driven Actor / Channel Runtime as the foundation for the whole site, with **4** classes of peripheral business -- login access, payment orders, events and mail, external reconciliation -- all entering the kernel. External payment callbacks averaged **1.8** s and blocked Epoch boundary alignment; frame advancement jitter P99 was **22** ms, and Channel peak backlog reached **60,000** entries.

### Step 1: symptoms and caliber -- first tell whether the kernel is jittery or the outside is waiting

Impact caliber: frame advancement jitter P99 **22** ms, and replay and matches drifted in a reproducible way; during backlog, the latency of new messages grew linearly with queue length.

Boundary caliber: the kernel housed both real-time combat and business with external slow dependencies; each of the **4** classes of peripheral business could wait on external I/O, and that wait crossed the Channel to hold the Epoch boundary.

### Step 2: layered attribution -- investigate along this page's kernel / outer landing points

```text
帧推进越跑越飘归因  占比
  外围业务混入内核、等待外部 I/O    51%
  外部慢依赖阻塞 Epoch 边界         30%
  Channel 积压无水位治理            19%
```

Item-by-item comparison: login, payment, events, and reconciliation -- four classes of business -- lived in the kernel, and this page spells out clearly what belongs on the outside: the outside holds "login and access," "payment and orders," "events and mail," and "most peripheral async business"; payment callbacks at **1.8** s crossed the Channel; backlog had no governed water level. All three are present, and the one mixed into the kernel carries the largest share.

### Step 3: root cause -- the boundary was never declared and it was misused as a universal runtime

This page's Problem says it directly: it is not suited to general business, and if the boundary is not declared it will be misused as a universal runtime. The team only saw names like Actor and Channel and ignored that the `Epoch-driven` logical time is the core premise -- time before scheduling, order before concurrency; once external slow dependencies moved into the kernel, that premise could not hold.

### Step 4: remediation and backfill -- re-draw the boundary "narrower and harder"

1. Converge the kernel: keep only the four classes of room combat core, frame sync main loop, combat Actor scheduling, and sequential state machines; migrate login access, payment orders, events and mail, and external reconciliation all the way out to the outer layer.
2. Govern Channel backlog: messages enter the queue first and are consumed by Epoch, with a backlog water level and a degradation order set, and all slow dependencies placed outside.
3. Put the not-applicable list into review: cross-partition cooperation, business with many external side effects, and globally strongly ordered large systems are excluded at project kickoff.

Verification ledger: frame advancement jitter P99 **22** ms -> **3** ms; peripheral business in the kernel **4** classes -> **0**; Channel peak backlog **60,000** entries -> **4,000**; payment callbacks became outer-layer async confirmation and no longer crossed the Epoch boundary.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Kernel boundary list | The kernel keeps only the four classes of room combat, frame loop, entity scheduling, and sequential state machines | A landing point closer to game servers |
| Epoch as a first-class concept | Messages are consumed by logical time interval, not executed the instant they arrive | What `Epoch` really means here |
| Channel timing governance | Enter the queue first, consume by Epoch, and set a backlog water level and degradation order | The Channel here does not solve "communication," it solves "timing governance" |
| Not-applicable boundary review | Cross-partition, external slow dependencies, and globally strongly ordered are all placed outside | What this is not suited to |

### Three lessons from the case

1. **If the boundary is not declared, it is treated as having no boundary**. If a dedicated runtime does not write out its not-applicable list, the first peripheral business that hooks in will push it toward being a universal foundation.
2. **A similar name does not mean similar goals**. Both are called Actor, but general frameworks care about concurrency abstraction and distributed cooperation, while this kind of runtime cares about when a message takes effect, not merely when it arrives.
3. **It is not a "stronger general framework," it is a "narrower, harder, more opinionated runtime"**. Do the core logic kernel well and keep peripheral business in the outer layer -- that is the correct use of this kind of runtime.
