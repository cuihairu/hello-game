# Epoch-driven Actor / Channel Runtime

## Category

server / runtime 子树。节点定位：为确定性、顺序状态推进、低延迟抖动、可重演而设的专用运行时——Epoch 定义推进单位、Channel 治理时序、ECS 承载数据布局。

## Definition


如果把前面几篇的执行模型讨论继续往下压，会自然走到一个更具体的问题：有没有一种运行时，不是为了通用业务框架，而是专门为了确定性、顺序状态推进、低延迟抖动和可重演这类问题而设计。

`Epoch` 这一类运行时，就是很典型的答案。它不是通用分布式 Actor 平台，也不是单纯消息队列，而是一种更偏游戏和高时序敏感系统的运行时组织方式。它把 `Epoch-driven`、`Actor`、`Channel` 和 `ECS` 明确绑在一起，目标很清楚，就是在单分区、单写权威逻辑场景里，把确定性、顺序执行和低抖动做成正式设计。

## Problem

通用框架解决复用，这个问题域要的是可重演与抖动可控：Epoch 决定推进粒度、Channel 解决时序治理而非通信、ECS 决定数据布局。它不适合通用业务，边界不声明会被误用成万能运行时。


### 为什么这种运行时会出现

很多通用运行时和通用 Actor 框架，更擅长的是：

- 服务间解耦。
- 通用并发封装。
- 吞吐型异步任务。

但它们未必擅长下面这些更苛刻的问题：

- 一切逻辑围绕明确逻辑时间推进。
- 同一状态只允许单写。
- 消息时序必须稳定且可推理。
- 行为需要可复现、可重演、可回放。
- 抖动比平均吞吐更重要。

在游戏战斗、帧同步、顺序撮合和风控状态机这类场景里，这些需求往往比“通用性”更重要。所以才会出现这种明显带立场的运行时设计。

### `Epoch` 在这里真正意味着什么

在这类设计里，`Epoch` 不是简单换个名字叫 Tick，而是把逻辑时间做成运行时一级概念。更具体地说：

- 消息不是来了就立即执行。
- 逻辑不是谁先抢到线程谁先跑。
- 状态也不是随时可见、随时可改。

相反，系统会围绕明确的逻辑时间区间来组织：

- 某个时间区间内收哪些消息。
- 某个时间区间内哪些 Actor 执行。
- 某个时间区间边界上哪些状态对外可见。

这样做的核心价值是：时间先于调度，顺序先于并发。

### 这里的 Actor 和通用 Actor 有什么不同

这里的 Actor 更接近“固定线程上的封闭状态单元”，而不是“无限灵活的消息对象”。它强调的是：

- 状态封闭。
- 顺序执行。
- 边界可见。

这意味着：

- 同一个 Actor 内部的状态更新更容易保持确定顺序。
- 外部不直接共享写状态，而是通过 Channel 发送消息。
- 调度策略更容易围绕时间片和单写者模型组织。

这类 Actor 不一定最通用，但很适合强时序、强可推理性的系统。

### 这里的 Channel 解决的不是“通信”，而是“时序治理”

从这类设计的描述看，Channel 的关键点不是“能发消息”，而是：

- 消息先入队。
- 不立即触发执行。
- 再结合 Epoch 决定何时消费。

这和很多通用消息机制差异很大。通用消息系统往往强调异步解耦和尽快消费；这里更强调：

- 消息何时对系统生效。
- 消息以什么逻辑顺序被处理。
- 消费边界能否被重放和推理。

这也是它为什么更像运行时基础设施，而不是普通消息总线。

### ECS 在这里扮演什么角色

这类运行时并不满足于“语义正确”，它还希望：

- 热路径对象更新可以批处理。
- 数据布局更贴近 cache。
- 在保持顺序执行和单写者前提下，把 CPU 利用率做上去。

也就是说，ECS 在这里不是单独的架构风格，而是和 Epoch + Actor 一起构成：

- 时间组织。
- 状态封闭。
- 热路径数据布局。

这三者合在一起，才形成它的性能和确定性特征。

### 它最适合承接什么问题

这类运行时最适合的边界通常非常明确：

- 单分区或单写权威逻辑。
- 强实时战斗。
- 帧同步或接近帧同步的逻辑推进。
- 顺序状态机类系统。
- 对可复现、可重演、低抖动非常敏感的场景。

用更直白的话说，它最适合那些“不能让状态随意并发写、也不能让时间语义飘掉”的系统。

### 它不适合什么问题

这类设计通常不适合：

- 任意跨节点分布式协作。
- 全局共享强序大系统。
- 到处要等外部慢依赖、外部副作用很多的业务系统。
- 高度松耦合、追求通用中台能力的场景。

也就是说，它不是“更强通用框架”，而是“更窄、更硬、更有立场的运行时”。

### 和普通 Actor 框架最大的区别

更贴近工程的区别可以这样理解：

### 通用 Actor 框架更关注

- 并发抽象。
- 服务内解耦。
- 分布式协作可能性。
- 易用性和扩展性。

### Epoch-driven Actor Runtime 更关注

- 时间为第一公民。
- 单写状态与顺序执行。
- 行为可复现。
- 低延迟抖动。
- 消息何时生效，而不是仅仅何时到达。

这两类系统都可以叫 Actor，但设计目标明显不同。

### 这类运行时最吸引人的地方

从游戏工程角度看，这类运行时有几个特别强的点：

- 逻辑时间明确，天然适合帧推进和回放。
- Actor 状态封闭，天然减少共享写和锁争用。
- Channel 不立即触发执行，更容易做确定性时序治理。
- 配合 ECS，更适合高频热路径对象更新。

这其实是在把第 4 章和第 5 章的很多原则做成一个统一 runtime：

- Tick / Epoch。
- 单写者。
- 顺序消费。
- 批处理更新。
- 低抖动。

### 这类运行时真正难的地方

它的难点也同样明显，不在表面 API，而在设计边界：

- 一旦系统跨分区、跨节点，单写模型如何维持。
- 和外部非确定性系统如何交互。
- Channel 消息积压如何治理。
- Epoch 边界和实时 I/O 如何对齐。
- 哪些状态可以留在 runtime 内，哪些必须外包。

也就是说，这类 runtime 非常适合做“核心逻辑内核”，但不一定适合独吞整站业务。

### 一个更贴近游戏服务器的落点

如果放在游戏系统里，更现实的用法通常不是“整个项目都用它”，而是：

- 房间战斗核心。
- 帧同步主循环。
- 战斗 Actor / 实体调度。
- 顺序状态机式玩法实例。

而把下面这些东西放在外层：

- 登录和接入。
- 支付和订单。
- 活动与邮件。
- 大部分外围异步业务。

这种组合更符合它“强运行时、弱通用平台”的性质。

### 常见误区

- 把这类 runtime 当成通用分布式平台，试图让它直接承载所有业务和所有跨节点协作。
- 只看到 Actor 和 Channel 这些名词，却忽略它真正的核心前提其实是 `Epoch-driven` 的逻辑时间组织。
- 拿它去解决大量外部非确定性、跨分区全局协调问题，最后觉得框架“不灵活”，实际上只是问题和工具不匹配。

这一页真正要说明的，不是某个具体实现多酷，而是为什么某些游戏核心逻辑会选择时间优先、顺序优先、单写优先的运行时内核。

### 实战案例：一次「把专用运行时当通用底座，帧推进越跑越飘」的边界误判排查

> 案例为教学示例（非摘自真实项目），数字经过取整简化。它把本页「`Epoch` 在这里真正意味着什么」「这里的 Channel 解决的不是“通信”，而是“时序治理”」「它不适合什么问题」用到深水区：本想省一套框架，却把外围业务请进了内核——这是边界不声明被误用成万能运行时的排查，也是「强运行时、弱通用平台」的完整展开。

**背景与现象**：某项目把 Epoch-driven Actor / Channel Runtime 当全站底座，登录接入、支付订单、活动邮件、外部对账 **4** 类外围业务全部进内核。外部支付回调平均 **1.8** 秒，阻塞 Epoch 边界对齐；帧推进抖动 P99 **22** 毫秒，Channel 峰值积压 **6** 万条。

### 第一步：现象与口径——先看是内核在抖还是外层在等

影响面口径：帧推进抖动 P99 **22** 毫秒，回放与对局可复现地漂移；积压期间新消息延迟随队列长度线性放大。

边界口径：内核里同时住着实时战斗与外部慢依赖业务，**4** 类外围业务每一类都可能等待外部 I/O，等待就会穿过 Channel 拖住 Epoch 边界。

### 第二步：分层归因——按本页内核 / 外层落点排查

```text
帧推进越跑越飘归因  占比
  外围业务混入内核、等待外部 I/O    51%
  外部慢依赖阻塞 Epoch 边界         30%
  Channel 积压无水位治理            19%
```

逐项比对：登录、支付、活动、对账四类业务住在内核，本页把该放外层的写得很清楚——外层要放「登录和接入」「支付和订单」「活动与邮件」「大部分外围异步业务」；支付回调 1.8 秒穿过 Channel；积压没有治理水位。三类都在，混入内核那条占比最大。

### 第三步：根因——边界没声明，被误用成万能运行时

本页 Problem 写得直接：它不适合通用业务，边界不声明会被误用成万能运行时。团队只看到 Actor 和 Channel 这些名词，忽略了 `Epoch-driven` 的逻辑时间才是核心前提——时间先于调度，顺序先于并发；一旦外部慢依赖住进内核，这个前提就守不住。

### 第四步：处置与回填——按「更窄更硬」重新划边界

1. 内核收口：只留房间战斗核心、帧同步主循环、战斗 Actor 调度、顺序状态机 **4** 类；登录接入、支付订单、活动邮件、外部对账全部迁到外层。
2. Channel 积压治理：消息先入队、按 Epoch 消费，设积压水位与降级顺序，慢依赖一律外置。
3. 不适用清单进评审：跨分区协作、外部副作用多的业务、全局强序大系统，立项时直接排除。

复核账：帧推进抖动 P99 **22** 毫秒 → **3** 毫秒；外围业务 **4** 类 → **0** 类留在内核；Channel 峰值积压 **6** 万条 → **4000** 条；支付回调改为外层异步确认，不再穿过 Epoch 边界。

**回填清单**：

| 回填项 | 动作 | 回填处 |
|-----|------|--------|
| 内核边界清单 | 内核只留房间战斗、帧循环、实体调度、顺序状态机四类 | 一个更贴近游戏服务器的落点 |
| Epoch 一级概念 | 消息按逻辑时间区间消费，不来了就立即执行 | `Epoch` 在这里真正意味着什么 |
| Channel 时序治理 | 先入队、按 Epoch 消费、设积压水位与降级顺序 | 这里的 Channel 解决的不是“通信”，而是“时序治理” |
| 不适用边界评审 | 跨分区、外部慢依赖、全局强序一律外置 | 它不适合什么问题 |

### 案例的三个教训

1. **边界不声明就会被当成没有边界**。专用运行时不写清不适用清单，第一个接入的外围业务就会把它往万能底座推。
2. **名字像不等于目标像**。都叫 Actor，通用框架关心并发抽象与分布式协作，这类 runtime 关心消息何时生效，而不是仅仅何时到达。
3. **它不是“更强通用框架”，而是“更窄、更硬、更有立场的运行时”**。核心逻辑内核做好，外围业务留在外层，才是这类 runtime 的正确用法。
