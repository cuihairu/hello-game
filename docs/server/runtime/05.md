# Lock Contention and Performance Cost

## Category

server / runtime subtree. Node positioning: locks drag inferrable sequential execution into unpredictable jitter -- hotspot locks, granularity is not always the answer, and a single writer is usually worth more.

## Definition


What makes lock contention scary is not simply "locks are slow," but that it often drags a system from inferrable sequential execution into an unpredictable jittering system. Many teams look only at average throughput before launch and assume that adding threads makes everything faster; after launch, what blows up first is usually tail latency, intermittent timeouts, hotspot object jitter, and extremely hard-to-reproduce timing bugs.

## Problem

Before launch, average throughput with added threads looked faster; after launch, what exploded first was tail latency, intermittent timeouts, and hard-to-reproduce timing bugs. A lock problem that manifests as "occasional" is basically untraceable -- a single writer (serial handling) is usually cheaper than fine-grained locks and easier to infer.


### Why lock problems are more dangerous in game systems

Many core paths of game systems are very sensitive to timing and jitter:

- Room main loop.
- Scene object updates.
- Combat event handling.
- Skill and Buff timing.
- Broadcast and input consumption.

These paths do not merely require being "fast on average," they require "never being especially slow once in a while." What lock contention is best at destroying is exactly this kind of stability.

### What costs locks really bring

The common costs are not just lock and unlock themselves, but include:

- Thread waiting.
- Context switches.
- Cache invalidation and cache line jitter.
- Priority inversion.
- Longer long-tail requests.
- Deadlock and livelock risk.

So "this lock looks like only a few lines of code" does not mean it has a low runtime cost.

### Where hotspot locks most easily form

In game servers and runtimes, common hotspots include:

- The global player table.
- Room or scene indexes.
- Broadcast connection lists.
- Timer containers.
- Shared object pools.
- Cross-thread logging or statistics aggregators.

Once these are accessed repeatedly on a high-frequency path, they easily go from "convenient to share" to "global hotspot."

### Why "make the lock granularity finer" is not always the answer

When lock contention appears, many people's first reaction is to split the lock granularity finer. That direction sometimes works, but it has clear limits:

- Finer locks mean more complex management.
- Ordering is harder to infer.
- Deadlock and lock-order problems are harder to control.
- The shared state itself has not disappeared.

In other words, lock granularity optimization treats the symptom and does not necessarily fix the structural problem. The more solid approach is usually to ask first: does this state need to be shared at all.

### What is usually worth more than a lock is "single writer"

Many high-performance, low-jitter runtimes eventually converge not on "making the lock stronger" but on minimizing shared writes. Common techniques include:

- A single-threaded main loop.
- Actor-enclosed state.
- Sharding by partition key.
- Async message delivery instead of direct shared writes.

The core of these approaches is not anti-concurrency, but turning the concurrency problem into a boundary problem that is easier to govern.

### When a lock is still reasonable

Locks should not all disappear. Locks are usually still reasonable in:

- Low-frequency config updates.
- Background admin interfaces.
- Protection of small-scope shared resources.
- Startup-time or maintenance-time operations.

The key is not to let locks appear on high-frequency hot paths, and especially not on the core runtime paths that should advance sequentially.

### Why lock problems often end up looking "occasional"

The worst thing about lock contention is that it is not consistently slow; it often manifests as:

- Fine normally, suddenly jittery at peak.
- Under the same pressure, occasionally a few rooms are especially slow.
- The same logic does not reproduce locally, but breaks in production co-location.

This is because lock contention depends heavily on:

- Thread scheduling.
- Access timing.
- Hotspot object distribution.
- CPU cache and NUMA behavior.

So lock problems are often harder to reproduce than a purely algorithmic slowness.

### A more practical governance order

When lock contention appears, a safer governance order is usually:

1. First locate which shared state on the hot path is being contended.
2. Judge whether this state really must be shared.
3. Consider single-writer, partitioning, replication, or async aggregation first.
4. Only when the structure cannot change, optimize lock granularity, read-write locks, or lock-free structures.

If you dive straight into swapping lock types, you usually only treat the symptom.

### Lock problems are connected to the execution model

This chapter and the earlier pages are actually the same line:

- Single-threaded and Actor have had lasting appeal largely because they structurally route around a lot of locks.
- Coroutines whose underlying layer still shares global writes will hit lock problems just the same.
- A Tick-driven system that contends for locks repeatedly within a frame will directly amplify frame jitter.
- Backpressure and flow control that depend on a shared hotspot queue will also be bitten back by lock contention.

In other words, lock problems are not an isolated performance point, but a result of how the runtime is organized.

### Common pitfalls

- Parallelizing too early for performance, so shared state and lock contention amplify the problem.
- Treating finer lock granularity as the only optimization lever, without reflecting on why the state must be shared.
- Looking only at average throughput and ignoring tail latency and hotspot contention, so the system appears faster on the surface while actually running more jittery.

What this page really wants to stress is not "which lock is faster," but how to avoid putting high-frequency core state into a situation where it must contend for locks.

### Practical case: triaging lock contention in a "added a global lock, the battle server got more jittery instead" incident

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes this page's "What costs locks really bring," "Where hotspot locks most easily form," "Why 'make the lock granularity finer' is not always the answer," "What is usually worth more than a lock is 'single writer'," and "A more practical governance order" into deep water: average throughput did not drop, but tail latency collapsed first -- this is the triage of lock contention on a battle server's hot path, and also a full unfolding of "how to avoid putting high-frequency core state into a situation where it must contend for locks."

**Background and symptoms**: one MMO battle server, **8** rooms per process and **200** players per room. To support cross-room assistance, development changed player state from room-private to a globally shared table, guarded by one global lock. The pre-launch stress test showed average TPS dropping from **12000** to **11640** (**3**% lower), and the team judged it "acceptable"; after launch, P99 frame cost jittered from **12** ms to **38** ms, timeout rate went **0.2**% -> **1.8**%, and it only appeared during peak hours -- exactly the "fine normally, suddenly jittery at peak" this page describes.

### Step 1: symptoms and caliber -- turn "occasional" into measurable tail latency

Tail latency caliber: P99 frame cost **38** ms and P999 **61** ms, while average frame cost rose from only **4** ms to **4.3** ms -- the average barely moved, but the tail collapsed first.

Timeout caliber: combat event timeout rate **1.8**%, concentrated during the **16,000** concurrent-online peak window; the same stress test at low peak had a timeout rate of **0.2**%.

Reproduction caliber: local single-process stress tests failed to reproduce it in **3** rounds, but production co-location (**4** processes sharing cores) reproduced it on day **2** -- lock contention depends on thread scheduling and NUMA behavior, and a clean local environment cannot surface it by nature.

### Step 2: layered attribution -- check this page's cost checklist item by item

```text
帧耗时抖动 38ms  归因
  全局玩家表锁等待（热路径争用）    71%  →  27ms
  上下文切换与 cache line 抖动       19%  →   7ms
  长尾请求变长（锁排队）             10%  →   4ms
```

- Waiting layer: **71**% of the jitter came from the global player table lock -- combat event handling iterates over assistance targets every frame, all queued on the same lock.
- Switching layer: **19**% came from context switches and cache line jitter -- **8** room threads fought over one lock, and cache lines bounced back and forth between cores.
- Long-tail layer: **10**% came from lock queueing -- an occasional long frame backed up every following frame behind the lock, appearing as "a few rooms especially slow."

### Step 3: root cause -- a lock appeared on the core runtime path that should advance sequentially

There is only one root cause: the global player table was put onto the combat hot path. This page says "do not let locks appear on high-frequency hot paths, and especially not on the core runtime paths that should advance sequentially" -- combat event handling accessed the global table **200** times per frame, **8** room threads contended for the lock at the same time, and lock wait was amplified into frame jitter.

"Make the lock granularity finer" does not hold: this page says "lock granularity optimization treats the symptom and does not necessarily fix the structural problem" -- after splitting by room shard, cross-room assistance still has to access across shards, lock-order problems are harder to control, and the shared state itself has not disappeared.

### Step 4: remediation and backfill -- ask first "does this state need to be shared"

1. Return player state to room-private: change cross-room assistance to async message delivery, with assistance requests going through a message queue instead of direct shared writes.
2. Make the global index read-only: assistance target lookups go through a read-only snapshot built each frame, built single-threaded and consumed lock-free.
3. Fix the governance order: locate shared state -> judge whether it must be shared -> single-writer/partition/async aggregation -> lock granularity optimization, written into the performance review checklist.

Verification ledger: P99 frame cost **38** ms -> **14** ms; timeout rate **1.8**% -> **0.1**%; triage time for similar jitter **2** days -> **0** days after fixing the governance order (caught at review).

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Hot path lock check | Global state accessed per frame by combat event handling is registered as a hot path, and each lock is walked through at review | Where hotspot locks most easily form |
| State privatization | Player state returns to room-private, cross-room cooperation becomes async message delivery | What is usually worth more than a lock is "single writer" |
| Read-only snapshot | The global index is built as a single-threaded read-only snapshot each frame, consumed lock-free | A more practical governance order |
| Governance order | Locate -> judge -> single-writer/partition/async -> lock granularity, four steps written into the performance review checklist | Lock problems are connected to the execution model |

### Three lessons from the case

1. **Average throughput not dropping does not mean the system is not worse**. When a **3**% TPS drop is deemed acceptable, P99 is already **3** times jittier -- tail latency and hotspot contention must be read separately; average metrics are nearly blind to lock problems.
2. **Finer lock granularity treats the symptom, not the root**. After splitting the lock, the shared state is still there and lock ordering is harder to control; ask "does this state need to be shared" first, then talk about how to add locks.
3. **Lock problems must be triaged in governance order**. Locate which shared state on the hot path is contended, then judge whether it must be shared, and only then come to lock granularity -- get the order backwards and you can only treat the symptom.
