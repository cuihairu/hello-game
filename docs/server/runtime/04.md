# Flow Control, Backpressure, and Stability Mechanisms

## Category

server / runtime subtree. Node positioning: flow control, backpressure, and stability mechanisms solve "what happens when the system cannot speed up" -- queues blow up first at peak, the backpressure propagation path, explicitly designed capacity limits, and backpressure designed together with business priority.

## Definition


Flow control, backpressure, and stability mechanisms are not about "is the system fast," but "what happens when the system cannot go fast." This is especially critical for game runtimes, because many failures do not come from a total crash but from slowly accumulating backlog:

- Messages pile up more and more.
- Queues grow longer and longer.
- Slow consumers drag down fast producers.
- A node is still alive, but its latency gets more and more absurd.

Without flow control and backpressure, a system usually does not degrade gracefully; it suddenly avalanches after a while.

## Problem

Gradually accumulating failures are more common and harder to trace than crashes: "take it in first and handle it slowly later" is usually a bad strategy, and the order in which experience degrades when a queue is full should be determined by priority rather than happen randomly. Capacity limits must be designed explicitly, and backpressure must be designed together with business priority.


### Why queues are what actually blows up first at peak

The places most prone to backlogs in game systems are usually not CPU, but queues:

- Gateway write buffers.
- Actor mailboxes.
- Async task queues.
- Persistence write queues.
- Pending broadcast lists.

When peak arrives, if the system only knows how to "keep accepting, keep stuffing, keep waiting," then every slow path ultimately passes its pressure to the queues. The point of flow control and backpressure is to express that pressure explicitly before the queues run out of control.

### What flow control, backpressure, and stability mechanisms each do

### Flow control

Flow control concerns how many requests, messages, and tasks the system allows onto a given path. It leans more toward entry governance.

### Backpressure

Backpressure concerns how, once a downstream becomes slow, the upstream senses it and slows down, drops, degrades, or refuses. It leans more toward propagation along the path.

### Stability mechanisms

Stability mechanisms concern how a system stays recoverable, explicable, and degradable when load is abnormal. They usually include flow control and backpressure, but are not limited to them.

### Why "take it in first and handle it slowly later" is usually not a good strategy

This is the most common intuitive error. Many systems, when peak arrives, choose:

- If we can receive it, receive it first.
- Put the task in a queue first.
- Consume it slowly later.

This strategy may work for short small peaks, but under sustained high pressure or a slow-downstream failure it is usually very dangerous. Because:

- Queue growth brings greater tail latency.
- Greater tail latency causes more timeouts and retries.
- More retries further amplify entry traffic.

In the end the system did not "hold the line," it just used backlog to postpone the failure for a while.

### The most common backpressure propagation paths

### Connection-layer backpressure

The gateway or connection layer cannot send, and the write buffer starts to pile up. If the business layer is unaware and keeps pushing, it will eventually drag down the connection or the whole event loop.

### Actor / queue backpressure

Some Actor, room, or consumer cannot keep up, and its mailbox or queue piles up. If the upstream keeps producing at normal speed, the hotspot module becomes a global stability risk.

### Storage-layer backpressure

The database, cache, or logging system slows down, and upstream tasks wait in large numbers for write-back. Without isolation, core logic gets dragged down too.

### What a stable system usually prepares

A safer system usually does not prepare just one lever; it combines several:

- Entry rate limiting.
- Queue capacity limits.
- Priority isolation.
- Timeout and drop policies.
- Degradation paths.
- Circuit breaking and fail-fast.

For example:

- At a login surge, peripheral notifications can be deferred and core authentication takes priority.
- When room broadcasts back up, non-critical state can be rate-limited or overwritten with newer values.
- At event peak, event tracking and reports can be degraded asynchronously while the reward issuance path is protected first.

The key is not "never lose a message," but "keep the critical path alive first."

### Capacity limits must be designed explicitly

Mature systems usually give key buffers and queues explicit limits:

- Per-connection write buffer limit.
- Per-room broadcast backlog limit.
- Per-Actor mailbox limit.
- Per-node async task queue limit.

Once a limit is exceeded, there must be an explicit policy:

- Refuse.
- Degrade.
- Drop stale messages.
- Transfer to proxy.
- Stop accepting work.

A queue with no limit essentially only postpones the exposure of the failure.

### Backpressure must be designed together with business priority

Backpressure is never a purely technical act; it must be designed together with business priority. Otherwise the system falls into absurd situations like:

- Announcements, red dots, and chat slow down combat broadcasts.
- Event tracking and log write-back slow down the settlement path.
- Peripheral event tasks hold up the login peak.

So a more practical question is: if the system can only handle half the traffic right now, which half must survive, and which half can be late, degraded, or dropped.

### A degradation order closer to practice

A safer system often degrades in layers:

1. First drop low-priority and expirable messages.
2. Then degrade peripheral async paths.
3. Then limit new traffic from entering.
4. Only last consider affecting the core primary path.

Without this degradation order, at peak the whole system can only jitter together.

### Why these mechanisms must be done in advance

Many teams like to wait until after a stress test to add flow control and backpressure. That order is usually too late. Because:

- Without capacity boundaries, a stress test can hardly show the real shape of the failure.
- Without priority isolation, a stress test can only prove the system dies together.
- Without degradation paths, a peak rehearsal has no engineering handle.

Flow control, backpressure, and stability mechanisms should not be "optimization items" but one of the starting points of the architecture.

### Common pitfalls

- Treating a queue as an infinite buffer, thinking "taking it in first is never wrong."
- Having no priority isolation, so peripheral traffic drags down the core path.
- Looking only at average throughput and ignoring tail latency, backlog length, and over-limit behavior, so the system appears not to have died while the experience is already unusable.

A truly mature system is not one without peaks, but one that still knows what to protect first and what to give up when a peak arrives.

### Practical case: triaging backpressure and priority in a "announcements drag down combat broadcasts" incident

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes this page's "Why queues are what actually blows up first at peak," "Capacity limits must be designed explicitly," and "Backpressure must be designed together with business priority" into deep water: the system did not crash, but broadcasts went **50** times slower -- this is the triage of gradually accumulating failures, and also a full unfolding of "how to keep the critical path alive first at peak."

**Background and symptoms**: one MMO, after a server-wide on-the-hour event started, room broadcast latency rose from **60** ms to **3.5** s; combat feel degraded wholesale with no service crashing and metrics reading "all normal." The gateway write buffer peaked at **28,000** entries and took **5** minutes to drain.

### Step 1: symptoms and caliber -- record "not crashed" and "unusable" separately

Latency caliber: room broadcast P99 **60** ms -> **3.5** s, a **58**-fold degradation; CPU utilization was only **45**% -- not a compute shortage, but messages not being able to line up.

Backlog caliber: the gateway write buffer peaked at **28,000** entries, of which server-wide announcements, red dot refreshes, and chat messages made up **83**% -- peripheral messages squeezed combat broadcasts to the back.

Timeout caliber: combat operation timeout rate **0.2**% -> **2.1**%, and player retries further amplified entry traffic.

### Step 2: layered attribution -- investigate against this page's three propagation paths

```text
广播延迟劣化归因  占比
  无优先级隔离，外围消息与战斗广播同队列      61%
  无容量上限，队列无界增长                    24%
  无降级与丢弃策略，超限只能硬扛             15%
```

Triage path: two of the three propagation paths hit -- connection-layer backpressure (write buffer pile-up) and queue backpressure (pending broadcast list pile-up). The storage layer was fine. The root was the **61**% item: all messages shared one queue and one priority, so as soon as announcements flushed, combat broadcasts had to wait in line.

### Step 3: root cause -- backpressure was not designed together with business priority

The queue could hold every message, but it never answered "if only half the traffic can be handled, which half must survive." Announcements, red dots, chat, and combat broadcasts shared one priority and one queue, so when peak arrived the peripheral traffic slowed the core path -- exactly the "appears not to have died, but the experience is already unusable" this page describes.

### Step 4: remediation and backfill -- separate priority first, then set limits, and finally fix the degradation order

1. Priority isolation: combat broadcasts and settlement confirmations go to a high-priority queue; announcements, red dots, and chat go to a low-priority queue, and the per-connection write buffer is quotaed by priority.
2. Explicit capacity limits: per-connection write buffer, per-room broadcast backlog, and per-node task queue each get a limit; over-limit combat broadcasts drop superseded stale state, and over-limit announcements are deferred directly.
3. Four-layer degradation order: first drop low-priority expirable messages, then degrade peripheral async paths, then limit new traffic from entering, and only last touch the core primary path.
4. Broadcast backlog governance: non-critical state is rate-limited or overwritten with newer values, with no per-entry resend.

Verification ledger: broadcast P99 latency **3.5** s -> **80** ms; write buffer peak **28,000** entries -> **4,000** entries; combat operation timeout rate **2.1**% -> **0.1**%; the next server-wide event retested on the same caliber showed no degradation of the core path.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Priority isolation | Combat broadcasts and peripheral messages in separate queues, write buffer quotaed by priority | Why queues are what actually blows up first at peak |
| Explicit capacity limits | Write buffer, broadcast backlog, and task queue each get a limit, with an explicit over-limit policy | Capacity limits must be designed explicitly |
| Degradation order | Drop low priority -> degrade peripheral -> limit entry -> touch core, four layers written into the runbook | A degradation order closer to practice |
| Backpressure and priority designed together | "Which half must survive" is answered by business priority, not by arrival order | Backpressure must be designed together with business priority |

### Three lessons from the case

1. **"Take it in first and handle it slowly later" postpones the failure, it does not hold the line**. Unbounded queue growth only moves the avalanche a few minutes later, and it hits harder.
2. **Without priority isolation, peak means peripheral traffic drags down the core**. Announcements flush and combat stutters -- which half must survive has to be answered in advance, not figured out on site at peak.
3. **Metrics reading "not crashed" does not mean the experience is usable**. A system at **45**% CPU utilization can still slow broadcasts **58** times -- look at tail latency, backlog length, and over-limit behavior, not just average throughput.
