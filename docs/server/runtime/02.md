# Coroutines, State Machines, and Task Queues

## Category

server / runtime subtree. Node positioning: coroutines, state machines, and task queues answer three different questions -- async orchestration, explicit sequencing, and queueing plus governance; their division of labor has to be read together with the execution model.

## Definition


Coroutines, state machines, and task queues look like three different "ways of writing code," but in reality each answers a different question:

- Coroutines: how to write an async flow naturally.
- State machines: how to express flow stages clearly.
- Task queues: how work units are queued, rate-limited, and consumed.

Many systems blur these three into one, and the result is either async flows written like a callback maze, or queues that burst full with nobody knowing what to drop and what to stop.

## Problem

The three are easiest to confuse: coroutines bring an async feel, state machines maintain explicit branching, and queues handle queueing governance. Mixing them writes inferrable sequencing into implicit entanglement. Fix the division of labor first, and only then is there a basis for judging "when does one take precedence over the others."


### What coroutines are really good at

The greatest value of coroutines is not the slogan "lightweight threads," but that they let you write async flows close to sequential code. Suitable scenarios usually include:

- Connection and session flows.
- Asset loading and async waits.
- Multi-step business flows whose state is not complex.
- Paths that must wait for an external I/O result.

Its advantages are direct:

- Natural to write.
- Logic context stays continuous.
- Error handling is relatively concentrated.

But coroutines are not automatically safe. The problems they most easily mask are:

- After a coroutine suspends, is its state still valid when it resumes.
- Whether the number of coroutines grows without bound.
- Coroutine execution points are scattered, making the real scheduling order hard to see.

So coroutines are better for expressing flow than for replacing state governance.

### Why explicit state machines still matter

Many teams, once they use coroutines, are unwilling to write state machines anymore. That instinct is understandable in simple flows, but it is often dangerous in complex interactions. The greatest value of an explicit state machine is:

- The state set is visible.
- The transition conditions are visible.
- Illegal state transitions are easy to check.
- Recovery and replay are easier to implement.

Typical scenarios well suited to state machines include:

- Room lifecycle.
- Matchmaking state flow.
- Skill casting phases.
- Payment order state.
- Player reconnection and proxy takeover switching.

Coroutines can write the flow smoothly; state machines can write the stages clearly. The two are not mutually exclusive.

### What task queues solve is not asynchrony but queueing and governance

Task queues are most easily misused as "anything async goes into a queue." In reality, what task queues are really good at is:

- Queueing work units.
- Peak shaving and valley filling.
- Priority isolation.
- Rate limiting, retry, and failure transfer.

This is especially important in game systems, because you repeatedly encounter:

- Login peaks.
- Event peaks.
- Massive reward issuance.
- Massive async persistence.
- Bulk logging and event tracking.

The essence of a task queue is a stability tool, not a way-of-writing tool.

### Where these three are most easily confused

### A coroutine written as an implicit state machine where nobody knows where the state is

The flow looks smooth, but the moment it interrupts, retries, replays, or recovers, it is hard to say where the current stage is.

### A state machine written as an if-else stack

It is called a state machine by name, but is actually just a pile of branches and boolean flags, with no real state set or transition semantics.

### A queue that is only a pile-up

Messages and tasks can all enter the queue, but there is no capacity limit, no priority, and no timeout or drop policy. Such a queue becomes a failure amplifier instead of a buffer layer.

### A more practical division of labor

A safer approach is usually:

- Coroutines express waits and async steps.
- State machines describe finite stages and state transitions.
- Task queues carry work units that can be queued, deferred, and governed.

For example:

- A player login flow can be strung together with coroutines.
- Player session state switching should be constrained by a state machine.
- Post-login log flushing, peripheral notifications, and some async write-backs can go to a task queue.

Once the division of labor is like that, the runtime semantics of the system become much clearer.

### When should each one take precedence

### Coroutines first

When the flow is linear, wait points are clear, the number of states is limited, and the main complexity comes from async waiting, coroutines are usually the most comfortable fit.

### State machines first

When the flow has clear stages, interrupts and recovers frequently, or needs visual debugging or strong validation, state machines are usually more solid.

### Queues first

When the real problem is peak shaving, rate limiting, async consumption, and failure governance rather than flow expression, the task queue is the protagonist.

### They must be read together with the execution model

These three do not exist independently of the thread model; together with the execution model they determine system behavior:

- Coroutines running in a single-threaded main loop can keep strong ordering inferrability.
- Managing lifecycle with state machines inside an Actor is often more stable than scattered callbacks.
- In a multi-threaded environment task queues must be designed together with backpressure, capacity, and priority.

In other words, they are local tools of runtime organization, not replacements for the overall execution model.

### Common pitfalls

- Treating coroutines as an async silver bullet, so the system ends up full of invisible state and hanging flows.
- Using state machines in name only, while actually still piling logic with boolean variables and branches.
- Treating a task queue only as a cache pool, with no capacity, priority, timeout, or drop policy, so under peak the queue becomes a failure amplifier.

What this page really wants to stress is not which of the three styles is more elegant, but that async flows, finite state, and queueing governance should each be owned by a different mechanism.

### Practical case: triaging implicit state and queue pile-up in a "order state garbled after reconnection" incident

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes this page's "Why explicit state machines still matter," "What task queues solve is not asynchrony but queueing and governance," and "A more practical division of labor" into deep water: the flow was written smoothly, but nobody could state where the state was -- this is the triage of coroutines, state machines, and queues being blurred into one thing, and also a full unfolding of "how to return async flows, finite state, and queueing governance each to their place."

**Background and symptoms**: one mobile game wired its entire payment and order flow with coroutines. After launch, two classes of problem appeared: order state garbled after reconnection, **60** cases per day; and during peak events, "reward issuance delayed by **20** minutes." The common ground of the two -- there is nothing at the breaking point that could state "which state we are in right now."

### Step 1: symptoms and caliber -- first tell whether it is a state problem or a queueing problem

State caliber: order state was scattered across coroutine local variables, boolean flags, and callback closures, so after reconnection or timeout retry the current stage could not be rebuilt, and customer support could only guess from logs.

Queue caliber: the reward issuance task queue had no capacity limit and no priority, piling up to **42,000** entries at peak with **20** minutes of tail latency; low-priority event notifications and high-priority paid rewards sat in the same queue.

### Step 2: layered attribution -- compare against this page's three confusion points

```text
故障归因  占比
  协程写成隐式状态机，中断后状态无法重建      55%
  名义状态机实为布尔标记堆叠，非法转换无校验    25%
  任务队列只当缓存池，无容量/优先级/超时       20%
```

Item-by-item comparison: the order flow "looked smooth," but the moment it interrupted, retried, or reconnected the stage could not be stated -- hitting this page's first confusion point; order state was stitched together from a few boolean flags with no validation of illegal transitions -- hitting the second; the reward queue only had enqueueing and no governance -- hitting the third, so a queue becomes a failure amplifier instead of a buffer layer.

### Step 3: root cause -- three things were merged into one

Flow expression (coroutines), stage governance (state machines), and queueing governance (queues) had no division of labor: the coroutine acted as both flow and state container, the state machine was just stacked branches, and the queue was just a pile-up. The responsibilities of the three mechanisms were never separated, so the runtime semantics of the system naturally turned to mud.

### Step 4: remediation and backfill -- separate the three things and return each to its place

1. Extract order state into an explicit state machine: write out the state set, transition conditions, and illegal-transition checks, and rebuild by current state after reconnection instead of relying on coroutine local variables.
2. Let coroutines express only wait steps: keep async steps like "waiting for the payment callback" and "waiting for the fulfillment result" in coroutines, and hand stage judgment to the state machine.
3. Add the four-piece governance set to the reward queue: capacity limit, priority isolation (paid rewards ahead of event notifications), timeout drop, and failure transfer; when the queue is full, low-priority tasks are degraded and deferred.

Verification ledger: order state garbling **60** per day -> **0**; reward issuance tail latency **20** minutes -> **90** seconds; queue peak **42,000** entries -> **6,000** entries.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Explicit state machine | Write out the state set and transition conditions, check illegal transitions, and rebuild by state after reconnection | Why explicit state machines still matter |
| Coroutine responsibility boundary | Coroutines express only waits and async steps, and do not take on state governance | What coroutines are really good at |
| Four-piece queue governance | Land capacity limit, priority isolation, timeout drop, and failure transfer one by one | What task queues solve is not asynchrony but queueing and governance |
| Division of labor | Coroutines own flow, state machines own stages, queues own queueing -- written into the design standard | A more practical division of labor |

### Three lessons from the case

1. **A smooth flow does not mean a clear state**. Coroutines are good at expressing waits, not at carrying state; when interruption, retry, or reconnection arrives, the implicit state shows its true face.
2. **A nominal state machine must really have a state set and transition semantics**. A "state machine" piled up from a few boolean flags cannot block illegal transitions and cannot support recovery and replay.
3. **A queue without governance is a failure amplifier**. Miss one of capacity, priority, timeout, and failure transfer, and a peak-time queue goes from buffer layer to amplifier.
