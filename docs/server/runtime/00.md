# Concurrency Stance Overview: From Seven Concurrency Models in Seven Weeks to Game Runtimes

## Category

server / runtime subtree. Node positioning: lay out the concurrency stances first in full (shared memory, immutability, identity/state separation, Actor, CSP, data parallelism, data tiering) before judging -- game engineering cannot just copy the book. Entry point of the runtime subtree.

## Definition


If Chapter 5 only talked about a few words like "single-threaded, multi-threaded, Actor, coroutines," its scope is actually incomplete. Because a concurrency problem never has just one way of being decomposed; behind it lies at least an entire set of different stances: shared-memory concurrency, immutable data and pure functions, identity/state separation, Actor, CSP, data parallelism, and a data-tiering line of thinking that separates the real-time layer from the batch layer.

What material like *Seven Concurrency Models in Seven Weeks* is really worth is not that it gives you a "scripture architecture" to copy, but that it hands you a coordinate chart of concurrency models. What game engineering needs is not mechanical reproduction, but knowing which models suit a game's primary runtime, which only suit local tooling, and which are better for peripheral data systems.

## Problem

Talking only about a few words like "single-threaded, multi-threaded, Actor, coroutines" is an incomplete scope: behind concurrency problems lies an entire contest of stances. If the stances are not laid out in full, selection devolves into a war of faith -- each side argues from the stance they are familiar with, and whoever holds the higher job title wins.


### First, lay out the common concurrency stances

Following that classic line of descent, the seven most common models can be summarized as:

1. Threads and locks.
2. Functional programming.
3. Identity and state separation, for example the STM / Refs / Agents line of thinking.
4. Actor.
5. CSP, that is, Communicating Sequential Processes.
6. Data parallelism.
7. Lambda architecture.

These seven models are not mutually exclusive technology stacks; they are seven different concurrency stances. The focus of each one is completely different:

- Some address how to manage shared memory.
- Some address how to keep state from being casually rewritten.
- Some address how a flow is coordinated by several sequential units.
- Some address how large-batch computation is parallelized.
- Some address how online and offline work are tiered.

### Why game engineering cannot just copy the book

A game is not a pure backend business, not a pure scientific computation, and certainly not a pure offline data platform. It usually has to handle all of the following at once:

- Hard-real-time paths.
- Single-writer authoritative state.
- High-frequency object updates.
- Weak networks, disconnects, and reconnection.
- Long-cycle assets and peripheral services.

So a game runtime often ends up a hybrid:

- The combat primary path looks like single-threaded, Actor, or Tick-driven state machines.
- Engine hot paths look like data parallelism and a Job System.
- Sessions and access look more like coroutines, state machines, and Channels.
- BI, audit, and recommendation look more like event streams and data-tiering architecture.

In other words, what a game project really does is usually not "choose one model," but place different models in different positions.

### A more useful overview table

| Model | Core idea | Strongest value | Main cost | What it suits best in games |
| --- | --- | --- | --- | --- |
| Threads and locks | Multithreaded shared memory, locks for protection | Direct, general-purpose, compatible with legacy systems | Lock contention, jitter, hard-to-infer ordering | Toolchains, background tasks, parts of service infrastructure |
| Functional programming | Immutable data, pure functions, few side effects | Easy to test, easy to reason about, favors parallelism | Copy and state-transition expression cost on hot paths | Numerical computation, rule evaluation, replay derivation |
| STM / identity-state separation | Govern shared state through transactions or references | Reduces shared-write chaos | High cost on heavily contended hot paths | Config backends, low-frequency coordination logic, tool systems |
| Actor | Encapsulated state, message-driven, sequential within a single Actor | Clear boundaries, friendly to a single writer | Hotspot Actors, message storms, cross-Actor consistency | Rooms, scenes, player aggregates, combat authority |
| CSP / Channel | Sequential processes + Channel cooperation | Clear flow decomposition, strong composability | A badly designed Channel becomes an implicit blocking web | Gateway, sessions, pipelines, internal coordination paths |
| Data parallelism | Batch-parallel processing of homogeneous data | Squeezes out CPU / SIMD / Job System | Not good at complex shared-state flows | ECS, animation, batch pathfinding, collision, pre-render processing |
| Lambda / data tiering | Division of labor between a real-time layer and a batch layer | Serves both real-time approximation and offline exact computation | High governance cost of dual paths | BI, audit, recommendation, risk control, profiling systems |

The most important thing in this table is not memorizing the terms, but seeing clearly: all of these are called "concurrency," yet some models govern shared state, some govern flows, some govern batch computation, and some govern data tiering.

### Which models are closer to a game's primary runtime

Looking only at the core game runtime, rather than every system in the whole project, the ones that genuinely enter the primary path are usually:

- Single-threaded / single-writer thinking.
- Actor.
- CSP / Channel combined with state machines.
- Data parallelism used for hot-path batching.

Conversely, these below are more common at the local or peripheral layer:

- Functional thinking, used for rule evaluation, replay, and config processing.
- STM / identity-state separation, used for tools, backends, and low-frequency shared state.
- Lambda / data tiering, used for BI, risk control, and offline analysis.

This distinction matters, because many teams' problem is not that they do not know the models, but that they place models suited to peripheral systems onto the highly time-sensitive core path.

### A judging method closer to game projects

When discussing concurrency models, do not first ask "which one is more advanced." First ask the following questions:

- Is this state allowed to be written by multiple parties at the same time.
- Must this path preserve inferrable ordering.
- Is the main pressure here shared-state conflict, complex async flow, or batch computation throughput.
- Is the worst feared failure inconsistency, jitter, or insufficient throughput.

Once these questions are answered clearly, most model choices will converge on their own.

### Common pitfalls

- Treating concurrency models as a question of language or framework taste, rather than a question of how state is governed.
- Trying to make one model cover the entire game system, so that in the end neither the primary path nor the peripheral path fits.
- Looking only at theoretical parallel capability, and ignoring ordering inferrability, recovery difficulty, and production triage cost.

What this page really wants to establish is not which model is best, but a coordinate system for judging which layer a concurrency problem belongs in.

### Practical case: triaging a concurrency-stance mismatch where "one model rules everything, and the whole server gets more jittery with every fix"

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes this page's "First, lay out the common concurrency stances," "A more useful overview table," and "A judging method closer to game projects" into deep water: what was chosen was the "most advanced," and what got jittery was the primary path -- this is the triage of stances not laid out in full and models placed in the wrong position, and also a full unfolding of "ask the questions before choosing the model."

**Background and symptoms**: one team used a single Actor framework to cover **4** classes of paths across the whole server (combat primary path, engine hot paths, session access, BI audit), on the grounds that "Actor is the most advanced." During the combat peak, a hotspot scene Actor queued **35** ms within a single frame, and frame P99 rose to **48** ms against a budget of **16** ms; the same set of BI daily-update jobs and match settlement crowded onto one online path, and settlement lagged by **6** hours.

### Step 1: symptoms and caliber -- first tell which path is jittery

Impact caliber: frame P99 of **48** ms is three times over budget, and dropped-frame complaints are concentrated in the combat peak; settlement and daily updates share the same Actor scheduler and squeeze each other during the evening peak.

Selection caliber: the selection meeting minutes contain only arguments over "which is more advanced," with not a single judgment about state, ordering, pressure, and failure -- none of the four questions was answered.

All three are present, and the misplacement one carries the largest share.

### Step 3: root cause -- stances not laid out in full, selection devolved into a war of faith

Talking only about a few words like "single-threaded, multi-threaded, Actor, coroutines" leaves the stances incomplete, and selection devolves into a war of faith -- each side argues from the stance they know, and whoever holds the higher job title wins. The four judging questions -- whether this state may be written by multiple parties at once, whether this path must preserve inferrable ordering, whether the main pressure is shared-state conflict or async flow or batch throughput, and whether the worst feared failure is inconsistency or jitter or throughput -- were all unanswered, so the model choice had no basis on which to converge.

### Step 4: remediation and backfill -- re-place things according to the coordinate system

1. Lay out the stances in full: bring the seven concurrency stances and the overview table into the selection meeting, and map each candidate model against the three columns "strongest value / main cost / what it suits best."
2. Converge the primary path: keep only single-writer, Actor, state machines, and data parallelism on the combat primary path; migrate BI, audit, and recommendation onto a Lambda / data-tiering path.
3. Put the four questions first: any concurrency selection must answer the four judging questions first; if it cannot, it does not enter review.

Verification ledger: frame P99 **48** ms -> **16** ms; hotspot Actor single-frame queueing **35** ms -> **4** ms; settlement latency **6** hours -> **40** minutes; all **4** classes of paths passed four-question review.

### Three lessons from the case

1. **Advanced does not equal fit**. Concurrency models are a contest over how state is governed, not a question of language or framework taste; any selection that cannot answer the four questions is a war of faith.
2. **Placing something in the wrong position is more common than choosing the wrong model**. Putting a model suited to peripheral systems onto the highly time-sensitive primary path makes jitter a foregone conclusion.
3. **Hybrids are the norm**. What a game project really does is not choose one model, but place different models in different positions, so the primary path and the peripheral path each return to their place.
