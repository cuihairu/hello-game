# 行为风控与治理体系

## Category

server / security 子树。节点定位：风控本质是业务治理不是抓作弊——识别、判定、处置、申诉的长期闭环与跨系统联动。

## Definition


风控如果只被理解成“抓作弊”，那它最多只是一个检测模块。真正的治理体系要回答的是：当系统里持续出现异常行为、恶意利用、社区破坏和业务滥用时，团队能不能建立一套长期稳定的识别、判定、处置和申诉机制。

## Problem

只被理解成抓作弊的风控最多是检测模块：持续的恶意利用、社区破坏、业务滥用需要长期稳定的识别→判定→处置→申诉机制；不和其他系统联动，处置落不了地、申诉没有依据，风控系统最后都不工作。


### 为什么行为风控本质上是业务治理

游戏里的高风险行为，很多都不属于传统意义上的入侵攻击，而是“利用系统允许的表面行为达成不被允许的结果”。例如：

- 高频注册和批量养号
- 异常交易和资源转移
- 刷活动、刷邀请、刷广告、刷回流奖励
- 恶意聊天、辱骂、诈骗、公会渗透
- 故意掉分、演员、代练、排位操控

这些行为往往并不总是违反接口层规则，却会持续破坏经济、公平、社区和经营数据。因此风控天然属于业务治理，而不只是安全团队的附属品。

### 风控闭环至少要有哪几层

一个真正可用的风控体系，通常至少需要以下环节：

- 信号采集：登录、设备、支付、资产、社交、匹配、聊天、举报
- 判定策略：显式规则、统计阈值、画像对比、模型评分
- 处置策略：禁言、冻结、限流、隔离匹配池、限制交易、封禁
- 人工复核：高价值账号、误伤争议、批量事件升级处理
- 申诉与恢复：解释依据、解除限制、补偿和回滚

缺任何一个环节，治理都会变形。只有检测没有处置，风险只会持续累积；只有处置没有申诉，误伤会迅速制造舆情和客服压力。

### 为什么很多风控系统最后不工作

因为它们只解决了“能不能打分”，没有解决“这分数接下来怎么办”。典型问题包括：

- 命中规则太多，但没有人知道哪些真的值得处置
- 处罚动作过于激进，误伤正常用户
- 处罚动作过于保守，黑产把规则当可接受成本
- 申诉时拿不出证据，只能机械回复

这说明风控真正难的部分不在模型，而在治理策略和组织协同。

### 更有用的设计方式

### 把风控对象分层

不是所有风险都应该用同一种方式处理。通常至少可以分成：

- 资产类风险：盗刷、套利、洗号、异常交易
- 公平类风险：外挂、代练、排位操控、脚本对战
- 社区类风险：辱骂、诈骗、引流、骚扰、恶意组织行为
- 经营类风险：刷新增、刷召回、刷广告、刷活动参与

分层的价值在于，不同风险关注的证据、容忍度和处罚策略都不一样。

### 把处罚动作分梯度

成熟系统一般不会只有“封”或“不封”两种结果，而是会根据风险等级设计梯度：

- 提示或警告
- 限制某项能力
- 冻结部分资产或交易能力
- 隔离到特殊池子
- 临时封禁
- 永久封禁

这样做的好处是，可以在不确定时先控风险，在证据充分后再升级处罚。

### 风控和其他系统为什么必须联动

行为风控很难单独完成闭环，它必须和这些能力协作：

- 和审计协作，保存证据链和操作记录
- 和客服协作，处理申诉、沟通和恢复
- 和经济系统协作，识别异常流向和追缴资产
- 和运营分析协作，避免黑产污染经营判断

如果这些系统割裂，风控就会陷入两个极端：要么命中很多但没人执行，要么执行了很多但团队解释不清。

### 常见错误

- 只关注外挂，不关注交易、社交和运营奖励滥用
- 风控信号很多，但没有分层策略和处罚梯度
- 误伤后没有复核、申诉和恢复流程
- 风控数据与客服、审计、经济分析系统彼此断开

行为风控真正成熟的标志，不是模型多复杂，而是团队是否能把异常行为持续压制在可接受范围内，同时把误伤和治理成本控制住。

### 实战案例：一次「刷活动奖励刷了三百万，封了又放」的风控闭环排查

> 案例为教学示例（非摘自真实项目），数字经过取整简化。它把本页「风控闭环至少要有哪几层」「为什么很多风控系统最后不工作」「把处罚动作分梯度」用到深水区：分数打出来了，处置和申诉都没跟上——这是只有检测没有治理的排查，也是「怎样让识别→判定→处置→申诉闭环转起来」的完整展开。

**背景与现象**：某游戏新活动上线，黑产批量养号刷邀请奖励，**3** 天刷出 **300** 万游戏币；风控命中 **12** 万条规则却处置 **0** 条；玩家申诉 **800** 起，客服拿不出证据只能机械回复，其中 **200** 起是误伤，一周内演变成舆情。

### 第一步：现象与口径——先数闭环断在哪一环

处置口径：命中 **12** 万条，处置 **0** 条——信号采集和判定策略都在工作，处置策略没落地，风险只会持续累积。

申诉口径：申诉 **800** 起，客服拿不出命中依据和操作记录，只能机械回复；误伤 **200** 起没有复核流程，直接变成舆情。

分层口径：风险不分层，处罚只有「封」或「不封」两种结果，黑产把规则当成可接受成本。

### 第二步：分层归因——按本页闭环断点比对

```text
风控失效归因  占比
  只有检测没有处置，风险持续累积     47%
  申诉拿不出证据，误伤变舆情         33%
  风险不分层，处罚无梯度             20%
```

逐项比对：命中 **12** 万条处置 **0** 条——命中「只有检测没有处置，风险只会持续累积；只有处置没有申诉，误伤会迅速制造舆情和客服压力」；申诉无证据——命中「申诉时拿不出证据，只能机械回复」；处罚只有封与不封——命中「处罚动作过于激进，误伤正常用户」与「过于保守，黑产把规则当可接受成本」两个极端。

### 第三步：根因——风控被当成了检测模块

团队只解决了「能不能打分」，没解决「这分数接下来怎么办」：处置策略没接进业务系统，申诉没有证据链，风险对象没有分层。风控本质是业务治理，缺了处置、复核、申诉任何一环，治理都会变形。

### 第四步：处置与回填——把闭环的每一环接上

1. 处置策略落地：按风险等级接禁言、冻结、限流、隔离匹配池、限制交易、封禁，处置动作进业务系统而不是停在报表里。
2. 人工复核：高价值账号、误伤争议、批量事件升级处理，**200** 起误伤全部走复核。
3. 申诉证据链：命中规则、操作记录、判定依据随申诉单流转，客服按证据回复。
4. 系统联动：风控与审计协作保存证据链，与客服协作处理申诉，与经济系统协作识别异常流向和追缴资产。

复核账：刷出 **300** 万游戏币，当周回收 **270** 万；误伤 **200** 起复核后确认 **12** 起；申诉响应 **3** 天 → **4** 小时；同类活动刷量下降 **92**%。

**回填清单**：

| 回填项 | 动作 | 回填处 |
|-----|------|--------|
| 处置策略落地 | 处置动作接进业务系统，命中即按梯度执行 | 风控闭环至少要有哪几层 |
| 申诉证据链 | 命中规则与操作记录随申诉单流转 | 为什么很多风控系统最后不工作 |
| 风险分层 | 资产/公平/社区/经营四类风险分别定证据与处罚 | 把风控对象分层 |
| 处罚梯度 | 警告到永久封禁六档，不确定时先控风险 | 把处罚动作分梯度 |

### 案例的三个教训

1. **只有检测没有处置，风险只会持续累积**。命中 12 万条处置 0 条，黑产 3 天刷走 300 万。
2. **申诉拿不出证据，误伤就变舆情**。200 起误伤没有复核流程，一周内上了论坛。
3. **处罚要有梯度**。只有封与不封，要么误伤正常用户，要么把规则送给黑产当成本。
