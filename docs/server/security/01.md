# Security and anti-cheat

## Category

server / security subtree. Node positioning: the client sits in the player's hands and its yields can be monetized -- always untrusted but also cannot be entirely abandoned; authoritative judgment must be placed in the right spot; anti-cheat is more than cheat detection. Master outline of the security subtree.

## Definition


Game security problems are both similar to and different from traditional Web systems. Similar in that they also face account theft, interface abuse, permission overreach, data leaks, and supply chain risk; different in that games inherently have a stronger adversarial surface, because the client is in the player's hands and many yields can be directly converted into rankings, virtual assets, and even real-world profit.

## Problem

Client-side detection alone cannot stop it, and putting everything on the server alone ruins the experience -- the core is putting authoritative judgment in the right spot: settlement-level adjudication must be decided by the server. A "client-decides" single-session token farmed 76.8 million in four days -- that is the cost of misplacing authority.


### Why game security cannot do without anti-cheat

Many internet products can keep damage low even without perfect client trust, relying on server-side permissions and transaction constraints. Games are different. As long as any of the following holds, cheating directly breaks the product's core value:

- Match fairness affects wins/losses, rank, and retention
- Resource production affects the economic loop and paid conversion
- Rankings, social, and guild honor affect public sentiment and the ecosystem
- High-value accounts and virtual items can be directly monetized

This means "security" and "anti-cheat" cannot be separated. Security is not a generic protective shell, and anti-cheat is not a detection script bolted on after launch. Both must be designed around the business primary path.

### The client is never trustworthy, but the client cannot be entirely abandoned

A mature team usually accepts this premise: the client can be tampered with, debugged, injected, packet-captured, replayed, accelerated, simulated, and mass-controlled. Therefore critical adjudication must be placed on the server as much as possible. But this does not mean client-side protection has no value.

Client-side protection still has two roles:

- Raise the attack threshold so that low-cost scripts and bulk studios cannot scale
- Provide more environment signals for server-side risk control, such as debug state, device fingerprints, and integrity check results

The real question is not "whether to do client-side protection" but not placing final security on client-side protection. Relying only on a shell, encryption, and anti-debugging usually only blocks the most superficial attacks.

### More importantly, putting authoritative judgment in the right spot

In a game, what needs the most protection is usually not all data but a few key states:

- Battle results and settlement results
- Currency, items, gacha, and transaction assets
- Matchmaking eligibility, rank, leaderboards, and season rewards
- Payment orders, delivery state, and refund state

If these states are decided by the client, or the server only does superficial validation, they will be exploited quickly. A more robust approach is usually:

- The server holds final settlement and key state change authority
- For inputs from the client, only accept "intent" or "candidate actions" rather than directly accept results
- Establish idempotency, rate limiting, and anomalous behavior validation for high-value operations

This adds some implementation complexity, but it determines the floor of the system.

### Anti-cheat is not only cheat detection

When people mention anti-cheat, the first things they think of are wallhacks, speed hacks, auto-clicking, and memory modification. In reality, cheating and abuse in games go far beyond these:

- Scripted bulk account creation and studio account farming
- Proxy top-up, refund arbitrage, and black-card payments
- Exploiting config vulnerabilities, compensation vulnerabilities, and event rule vulnerabilities to farm resources
- Mass-controlled devices farming activity, farming referrals, farming ad revenue
- Account sharing, boosting, and unauthorized trading destroying the matchmaking and economic environment

So the anti-cheat system usually needs at least several layers:

- Client integrity and environment counters
- Server-side rule validation and anomalous behavior detection
- Economic and transaction anomaly identification
- Social propagation chain and account association identification
- Punishment, appeal, and rollback handling

Only when the last layer is in place does anti-cheat truly form a governance capability.

### Common construction approaches and their costs

### Relying on a third-party security shell or anti-cheat SDK

Fast to integrate, can block some low-level attacks, and is convenient for meeting the minimum requirements of a channel or platform. But it cannot possibly understand your gameplay rules, economic logic, and asset risk, so it can only serve as a baseline threshold and cannot replace core validation.

### In-business rule detection

Many projects write large numbers of rules inside core modules such as combat, payment, events, and trading. The advantage is that it aligns with business; the drawbacks are that rules are scattered, hard to audit, and iterate slowly, easily turning into "whoever hits a problem adds an if."

### A standalone risk control and cheating governance platform

A more mature approach is to turn high-frequency signals, punishment strategies, the audit chain, and the manual review platform into unified capabilities. But such a platform is only truly cost-effective when there are enough projects and governance rules are relatively stable; otherwise the platform ends up heavy and the business cannot keep up.

### Common mistakes

- Believing that integrating a security product means security construction is complete
- Only doing cheat detection, not protecting assets, transactions, and event rules
- Key states still client-led, with the server only doing superficial validation
- After hitting an anomaly, having no punishment, appeal, or rollback plan

The real mark of a mature game security system is not "whether you have a cheat SDK" but, when attacks and cheating appear, whether the system can hold steady the most expensive, most critical path that most affects fairness and assets.

### Practical case: triaging a "single-session token client-decides, farmed 76.8 million in 4 days" settlement authority breakdown

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes the page's "Why game security cannot do without anti-cheat," "The client is never trustworthy, but the client cannot be entirely abandoned," "More importantly, putting authoritative judgment in the right spot," "Anti-cheat is not only cheat detection," "Common construction approaches and their costs," and "Common mistakes" into deep water: a token farming incident during a spring leaderboard push event, exposing at once the cost of separating security from anti-cheat, misplacement of authority, and the absence of a handling layer.

**Background and symptoms**: A long-cycle project ran a **7**-day spring leaderboard push event, where event tokens could be redeemed for gacha tickets (**240** tokens for **1** ticket), and the top **100** on the leaderboard also received a season-limited title. The config set a single-session token cap of **120**, but this cap only took effect on the client; the server only validated the reported score for "integer, non-negative, type-legal" format. From day **2** of the event, **80** same-origin accounts entered (occupying **80** of the top **100** spots, online in the same time window, same device model cluster, identical movement trajectories); the script reported a single-session score of **1200** (**10**x the cap), averaging **200** sessions per day, per-account daily production of **240,000** -- **24**x the roughly **10,000** daily production of top real players. By day **5**, operations had finally circled the **80** accounts through manual comparison. **80** accounts x **240,000** x **4** days, cumulatively farming **76.8 million** tokens, redeemed for **320,000** gacha tickets, of which **290,000** had already been opened, and **1,200** limited cosmetics were partially listed on the trading post. The team had previously integrated an anti-cheat SDK to satisfy channel compliance, with **1** security item checked in launch acceptance; after the incident the only handling was account bans **1** type, appeal channels **0**, rollback plans **0**.

### Step 1: symptoms and caliber -- first distinguish "how fake the production is" from "how hard the stock is to collect"

Unify caliber: use the server-recomputable "single-session production x sessions x running accounts" as the production ledger baseline, then record two items:

- **Production**: per-account daily production **240,000** = **200** sessions x **1200**/session -- the reported value is **10**x the cap of **120** and **24**x the top real players' **10,000**
- **Stock**: **80** accounts x **240,000** x **4** days = **76.8 million** tokens = **320,000** tickets, of which **290,000** already opened and **30,000** pending freeze

The production ledger balances because the reported value never went through any reasonableness validation; the stock ledger is hard to collect because from the moment of production there was no rollbackable record.

### Step 2: layered attribution -- from a farming incident to the five-layer anti-cheat ledger

```text
Shell ledger       Channel-compliance anti-cheat SDK integrated, acceptance checked 1 item -- it does not understand gameplay rules and only blocks superficial attacks
Authority ledger   Single-session token client-reported 1200 (cap 120), server only validates format -- key states client-led
Identification ledger   80 of the top 100 accounts behave from the same origin, only circled through manual comparison -- economic anomaly and association identification absent
Handling ledger    Punishment only 1 type (ban), 0 appeal channels, 0 rollback plans -- of 320k tickets only 30k frozen
```

Ledger convergence: the **76.8 million** stock is owed by the authority ledger, and the **290,000** already-opened tickets are owed by the handling ledger -- both ledgers point to the same thing: the five-layer anti-cheat system was only built to layer **1** and a half, while "only when the last layer is in place does anti-cheat truly form a governance capability."

### Step 3: root cause -- the shell was checked, authority was misplaced, handling had no follow-up

Cross-checking the page's "More importantly, putting authoritative judgment in the right spot": of the four types of key states, settlement results, currency and items, and leaderboard and season rewards -- all three -- were client-led; the three things the server should do -- "the server holds final settlement and key state change authority," "for inputs from the client, only accept 'intent' or 'candidate actions' rather than directly accept results," and "establish idempotency, rate limiting, and anomalous behavior validation for high-value operations" -- not a single one was done. Cross-checking "The client is never trustworthy, but the client cannot be entirely abandoned": the page's premise "the client can be tampered with, debugged, injected, packet-captured, replayed, accelerated, simulated, and mass-controlled" occurred verbatim, while the two roles of client-side protection -- "raise the attack threshold so that low-cost scripts and bulk studios cannot scale" and "provide more environment signals for server-side risk control" -- the shell was present but never put to use; the script did not even touch the shell and directly modified the reported value at the protocol layer, so "relying only on a shell, encryption, and anti-debugging usually only blocks the most superficial attacks" was borne out exactly. Cross-checking "Anti-cheat is not only cheat detection": among the abuse forms, "exploiting config vulnerabilities, compensation vulnerabilities, and event rule vulnerabilities to farm resources" and "mass-controlled devices farming activity, farming referrals, farming ad revenue" -- two hit; in the five-layer system, client integrity and environment counters had a shell, server-side rule validation only did format, and economic and transaction anomaly identification, social propagation chain and account association identification, and punishment appeal rollback handling -- all three layers were empty. Cross-checking "Common construction approaches and their costs": squarely hitting the positioning of "relying on a third-party security shell" -- "it cannot possibly understand your gameplay rules, economic logic, and asset risk," "can only serve as a baseline threshold and cannot replace core validation"; not a single business-aligned rule detection was written, and the standalone risk control platform's high-frequency signals, punishment strategies, and audit chain were all absent. "Common mistakes" -- all four hit: integrating a security product counted as building it, only doing cheat detection while ignoring assets and event rules, key states client-led with the server only superficially validating, and after hitting an anomaly having no punishment, appeal, or rollback plan.

### Step 4: handling and backfill -- first take authority back, then complete the five layers

The fix comes in two stages. Emergency: **T+0** settlement authority reclaimed -- single-session tokens recomputed by the server from session time and behavior sequence, any single report of **1200** settled at the cap of **120** (shrunk **10**x), and script-account yields were cut off on the spot; **T+1** stock handling -- **30,000** unopened tickets frozen, of the **290,000** already opened **110,000** unconsumed were reclaimed and **180,000** consumed were logged as event loss, of the **1,200** limited cosmetics **950** unbound were reclaimed and **250** deeply bound were exempted by announcement; all **80** same-origin accounts banned, and **600** same-cluster suspected accounts moved to marked observation (of which **37** were later confirmed and banned), no longer a blanket ban. Institutional, three steps: first, authority reclaimed -- settlement, tokens, and leaderboard, three types of key states, all pulled to the server, with the client only reporting "intent"; per-account daily production given a **20,000** rate control cap (**2**x the top real players' **10,000**), exceeding this enters a queue for manual review. Second, identification layer -- key production connected to anomaly detection, per-account daily production exceeding **10**x the real average automatically flagged; device fingerprint plus social propagation chain clustering, so same-origin accounts went from manually circling **80** to auto-circling **74** (the remaining **6** filled in by review). Third, handling layer -- punishment split into **4** tiers: rate limit, disqualification, ban, reclaim; **1** appeal channel (**72**-hour response); the three asset types -- tokens, tickets, cosmetics -- rollbackable by snapshot, aligning with the direction of "turning high-frequency signals, punishment strategies, the audit chain, and the manual review platform into unified capabilities." Review: the following month's event stress-test drill had **20** simulated accounts all report **1200**, rate control and anomaly validation blocked **20**/**20** that day, none entered settlement, the end-to-end drill ran **40** minutes with **20**/**20** handling traces, and **5** drill appeals were answered **5**/**5** within **72** hours.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Authority reclaimed | Settlement, tokens, and leaderboard -- three types of key states -- pulled to the server, client only reports intent | More importantly, putting authoritative judgment in the right spot |
| Security shell repositioned | The shell keeps only the two roles of raising the threshold and providing environment signals, no longer an acceptance completion item | The client is never trustworthy, but the client cannot be entirely abandoned |
| Identification layer filled | Production anomaly detection and device, social chain clustering auto-circle accounts | Anti-cheat is not only cheat detection |
| Handling closed loop | Punishment in four tiers, appeals answered in 72 hours, three asset types rollbackable by snapshot | Common construction approaches and their costs |

### Three lessons from the case

1. **Checking the acceptance box does not mean security is built** -- after the anti-cheat SDK was checked **1** item, **1200** was accepted as-is: a security product is a threshold, not a solution.
2. **The closer key states are to the client, the bigger the bill** -- every day the server only validates format is a withdrawal window for **80** accounts producing **24**x, and **4** days farmed **76.8 million**.
3. **Anti-cheat without a handling layer is just an alarm** -- of **320,000** tickets only **30,000** were frozen; the mark of mature game security is "whether the system can hold steady the most expensive, most critical path that most affects fairness and assets."
