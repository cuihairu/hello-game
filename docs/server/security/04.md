# Compliance, game license (ISBN), and platform constraints

## Category

server / security subtree. Node positioning: compliance and platform constraints continuously reverse-shape architecture, feature boundaries, and version cadence -- they cannot be deferred, because they change technical freedom.

## Definition


Many technical teams are used to treating compliance as "check the list one more time before launch," but for a game project, compliance and platform constraints continuously reverse-shape architecture, feature boundaries, and version cadence. If you wait until review submission, store listing, channel integration, or cross-region publishing to patch it, the cost is usually already very high.

## Problem

Treating compliance as a final checklist before review submission pays a big price: game license (ISBN) and platform rules change feature boundaries and version cadence, and cross-region publishing stacks another layer on top. Patching it after the fact usually costs far more than including it during design -- it is a set of continuously active constraints, not a one-time check.


### Why compliance directly changes the implementation approach

Games are not ordinary content products; they are subject to multiple constraints at once:

- Content review and subject-matter restrictions
- Real-name and minor protection requirements
- Constraints on payment, probability, disclosure, and virtual trading
- Requirements on chat, social, reporting, and content governance
- Platform rules on SDK, login, payment, ads, and permission use

These requirements are not just legal documents -- they ultimately all land in technical implementation. For example:

- Minor restrictions affect login state, online duration, spending power, and cross-day settlement logic
- Probability disclosure and gacha records affect backend display, data retention, and customer support query capability
- Channel payment and login constraints affect the account system, version cadence, and hot update headroom
- Content review requirements affect chat, UGC, announcements, and asset update workflows

### Why the game license (ISBN) and platform rules cannot be deferred

In domestic publishing scenarios, the game license (ISBN), real-name authentication, anti-addiction, and content compliance usually need to be included during the design phase. The reason is that many requirements cannot be solved by adding a UI notice, but go straight into core flows:

- Whether certain feature entries must be gated by age, real-name status, or region
- Whether chat, social, event copy, and assets need a review chain
- Whether probability and payment information must be long-term retrievable
- Whether version content may be delivered separately via hot update

If all of these are only patched before launch, the project often can only finish by hard-cutting features and taking temporary bypasses.

### Platform constraints change your technical freedom

When integrating different platforms, channels, and regions, teams often find that capabilities they took for granted do not necessarily hold:

- Not all platforms allow the same hot update strategy
- Not all platforms allow the same account interoperability and payment interoperability
- Not all SDKs can stably provide the same fields and callback semantics
- Not all channels allow consistent ads, push, and social capabilities

This means technology selection cannot only chase "most unified" -- it must leave room for differences and fallbacks. Otherwise, once a platform strategy changes, the entire integration path must be redone.

### A more realistic approach

Most teams are better off splitting compliance and platform constraints into three layers:

- Bottom-layer hard constraints: real-name, anti-addiction, payment, content review, data handling
- Adaptation-layer differences: different platforms' login, payment, ads, push, and review rules
- Operations and version strategy: which features open by region, by platform, by review stage

The benefit is that bottom-layer hard constraints are more stable, the adaptation layer can change locally, and the operations strategy can be adjusted according to publishing progress.

### Common mistakes

- Believing compliance is only a legal responsibility and does not enter R&D design
- Only sorting out platform differences until just before review submission or channel integration
- Assuming all regions, platforms, and versions can share the same strategy
- Not leaving a system entry for content review, minor restrictions, and probability retrieval

The truly mature state of compliance, game license (ISBN), and platform constraints is not how many regulations you know, but whether the project can still run stably with clear technical boundaries under different publishing constraints, rather than scrambling for big changes before every launch.

### Practical case: triaging a "one week before review, the login flow had to be redone entirely" compliance-deferral breakdown

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes the page's "Why compliance directly changes the implementation approach," "Why the game license (ISBN) and platform rules cannot be deferred," and "A more realistic approach" into deep water: only one week before review was anti-addiction found to be missing -- this is the triage of compliance treated as a review checklist, and also a complete unfolding of "how to push hard constraints forward into the design phase."

**Background and symptoms**: A product only sorted out compliance one week before review submission and found anti-addiction, real-name, and probability disclosure were all missing: login state, online duration, spending power, and cross-day settlement logic all needed changes; **3** features could only be hard-cut, and the version was delayed **6** weeks.

### Step 1: symptoms and caliber -- first distinguish which are hard constraints

Implementation caliber: minor restrictions go straight into login state, online duration, spending power, and cross-day settlement logic -- not something solvable by adding a UI notice, but core flow rework.

Cadence caliber: version content may not be delivered separately via hot update, channel payment and login constraints affect the account system and version cadence, and hot update headroom was compressed to almost nothing.

Difference caliber: three publishing regions were supposed to share the same strategy, but in reality real-name requirements, probability disclosure, and content review rules all differed.

### Step 2: layered attribution -- account by deferral cost

  Compliance treated as a pre-review checklist, not included in design phase     55%

Item-by-item comparison: the login flow had to be redone entirely -- hitting "if all of these are only patched before launch, the project often can only finish by hard-cutting features and taking temporary bypasses"; one strategy for three regions -- hitting "assuming all regions, platforms, and versions can share the same strategy"; probability disclosure and gacha records with no retrieval entry -- hitting "not leaving a system entry for content review, minor restrictions, and probability retrieval."

### Step 3: root cause -- compliance was seen as a final checklist before review submission

Compliance and platform constraints continuously reverse-shape architecture, feature boundaries, and version cadence; it is a set of continuously active constraints, not a one-time check. Waiting until review to patch it means the cost is already very high -- feature boundaries and version cadence are both forced to be rearranged in the most conservative way.

### Step 4: handling and backfill -- three-layer split, hard constraints pushed forward

1. Bottom-layer hard constraints included in the design phase: real-name, anti-addiction, payment, content review, and data handling are mandatory items during architecture review.
2. Three-layer split management: bottom-layer hard constraints stay stable, the adaptation layer (login, payment, ads, push, review rules) allows local changes, and the operations strategy is adjusted by publishing progress.
3. Probability disclosure and gacha records long-term retrievable: backend display, data retention, and customer support query capability are built in advance.
4. Content review chain leaves a system entry: chat, UGC, announcements, and asset update workflows have review hook points from the design phase.

Review ledger: second review submission hard-cut features **3** -> **0**; version delay **6** weeks -> **0** weeks; payment point retrieval entry coverage **0**% -> **100**%.

### Three lessons from the case

1. **Compliance changes the implementation approach, not just copy**. Anti-addiction enters login state and spending logic; patching it before review means redoing the whole thing.
2. **The cost of deferring is hard-cutting and delays**. **3** features hard-cut, **6** weeks delayed -- all avoidable with a week of design-phase work.
3. **Differences must be managed by tier**. Hard constraints stable, adaptation layer variable, operations strategy adjustable -- only then does the assumption of one strategy for three regions hold.
