# Audit, privacy, and data security

## Category

server / security subtree. Node positioning: audit, privacy, and data security share one core question -- who can touch which data, and after an incident can you say clearly who used it how; the point of audit is traceability, not recording.

## Definition


Many teams understand "data security" as database encryption, backups, and permission management, "audit" as backend operation logs, and "privacy" as adding a privacy policy before launch. In real projects, these three things actually share the same core question: who can touch which data, and when something goes wrong can you explain clearly who used the data in what way.

## Problem

Treating data security as encryption and backups, audit as backend logs, and privacy as a pre-launch policy addition -- all three become mere formalities: the core question they share is the explainability of data access and use -- if they are not looked at together, none of them can be governed.


### The point of audit is not recording, it is traceability

A text log saying "some admin performed some action at some time" usually does not truly help a team handle an incident. Because when an incident occurs, the more important questions are:

- Which objects were changed
- What they were before and after the change
- What the basis for the operation was, such as a work order, an approval ticket, or an event ticket
- Whether it was executed in batch, and how large the blast radius was
- Where it stopped when it failed, and whether it partially succeeded

This is also why high-risk backend operations must be made as structured as possible. Queries, resends, clawbacks, unbans, migrations, batch reward grants, config changes, hotfix tasks -- none of these can be traced by just "someone clicked a button."

### Privacy problems are not marginal in games

Games often handle much sensitive or regulated information:

- Account identifiers, phone numbers, real-name information
- Device information, login locations, payment information
- Chat content, report records, punishment records
- User behavior trajectories and profile tags

Once this information is connected to monetization, recommendation, risk control, and customer support systems, it is easily used widely inside the company. The risk comes not only from external leaks but also from internal over-access, over-retention, and out-of-scope use.

So privacy governance cannot be just legal copy -- it must land in concrete implementation:

- Is collecting this data actually necessary
- Has minimal storage and tiered access been applied
- Who can see plaintext in what scenario
- After the retention period, can it be deleted, desensitized, or frozen

### Where data security most easily goes wrong

### Backend query systems

Many teams consolidate customer support, operations, and R&D queries into one big backend, and it increasingly looks like a "super data entry point." As long as the permission model is not fine-grained and audit is incomplete, this kind of system is itself the largest leak surface.

### Logs and exports

Production logs, report exports, and temporary triage scripts often unintentionally carry out sensitive fields. Especially during troubleshooting and operations reviews, people habitually pass screenshots, CSVs, and SQL results around in group chats, which is usually harder to govern than formal database access.

### Third-party integrations

Analytics SDKs, ad SDKs, login SDKs, payment SDKs, customer support tools, and marketing platforms all touch some user data. As long as integration boundaries are unclear, internally desensitized data can be reassembled into a complete profile when externally integrated.

### A more realistic governance approach

For most teams, data security should start from a few minimal practices rather than aim for comprehensive coverage from the outset:

- Tier user data and backend operations, first identifying the most sensitive parts
- Queries, exports, and batch operations must leave an audit and approval chain
- Make customer support, operations, and R&D see data views at different granularities
- Establish a desensitization habit and tooling for logs, reports, and temporary scripts
- For third-party SDKs and outsourced tools, clarify field boundaries, transmission boundaries, and retention boundaries

### Why audit, privacy, and data security must be looked at together

Because all three answer the same question: when sensitive data is accessed, modified, propagated, or abused, does the team have a way to detect, block, trace, and remediate? Missing any link makes the system fail:

- Permissions only, no audit: when something happens you do not know who touched what
- Audit only, no least privilege: it is the same as assuming everyone can see everything
- Privacy copy only, no actual technical boundaries: it still cannot land in the end

### Common mistakes

- Believing that "internal systems" do not need fine-grained permissions and audit
- Logs, reports, and export paths are not desensitized, so sensitive data spreads everywhere
- Privacy governance stays at the agreement-copy level and never enters R&D and operations processes
- Treating high-sensitivity data such as real-name, payment, customer support, and chat the same as ordinary business data

The truly mature state of audit, privacy, and data security is not having written a few policies, but, when someone queries, exports, modifies, or leaks sensitive data, the system knows what happened, who was affected, and how to stop the loss.

### Practical case: triaging a "customer support screenshot circulated around in the group, all phone numbers in it" audit desensitization breakdown

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes the page's "The point of audit is not recording, it is traceability," "Backend query systems," and "A more realistic governance approach" into deep water: the leak happened in a group chat, and you cannot say who exported it -- this is the triage of a super data entry point plus no audit, and also a complete unfolding of "how to make sensitive data detectable and traceable."

**Background and symptoms**: A game's customer support backend consolidated all capabilities for queries, resends, clawbacks, and unbans. During one troubleshooting session, a customer support agent sent a CSV containing plaintext phone numbers directly into the project group; over **3** days it circulated in **4** groups, involving **12,000** players; afterwards, trying to trace who exported it, the backend queries had no operation records at all.

### Step 1: symptoms and caliber -- first count the leak surface and explainability

Leak caliber: the CSV contained **12,000** plaintext phone numbers, visible in **4** groups, harder to govern than formal database access -- passing screenshots, CSVs, and SQL results around in groups is the norm.

Audit caliber: backend queries have no operation records, so you cannot say who used the data in what way; when something happens you do not know who touched it, and traceability is out of the question.

Tiering caliber: risk does not come only from external leaks but also from internal over-access, over-retention, and out-of-scope use -- treating high-sensitivity data such as real-name, payment, customer support, and chat the same as ordinary business data, with customer support able to see plaintext by default.

### Step 2: layered attribution -- compare against the page's easy-to-miss points

```text
Data leak attribution  share
  Backend queries with no fine-grained permissions and audit       52%
  Log exports with no desensitization tooling or habit         31%
  High-sensitivity data not tiered, plaintext visible by default      17%
```

Item-by-item comparison: customer support, operations, and R&D queries consolidated into one big backend, increasingly like a "super data entry point" -- hitting "as long as the permission model is not fine-grained and audit is incomplete, this kind of system is itself the largest leak surface"; during troubleshooting, CSVs are habitually passed around -- hitting log exports unintentionally carrying out sensitive fields; high-sensitivity data not tiered -- hitting treating high-sensitivity data the same as ordinary business data.

### Step 3: root cause -- audit was treated as a backend operation log

What the team understood audit to be was a text record of "someone clicked a button," but what truly needs answering when an incident occurs is which objects were changed, what they were before and after, what the basis was, and how large the blast radius was -- none of these existed. The point of audit is not recording, it is traceability; if the record is not traceable, it is just a log.

### Step 4: handling and backfill -- make sensitive data detectable and traceable

1. Backend splits data views by role: customer support, operations, and R&D see data at different granularities, with high-sensitivity fields desensitized by default.
2. Queries, exports, and batch operations leave an audit plus approval chain: exports require a work order number, and operation records include the object, before/after values, and blast radius.
3. Tooling for log, report, and temporary script desensitization: exports automatically desensitize phone numbers and payment information, with tooling blocking rather than relying on habit.
4. Third-party SDKs clarify field boundaries, transmission boundaries, and retention boundaries, so internally desensitized data is not reassembled into a complete profile when externally integrated.

Review ledger: same-type group leaks **1** -> **0**; export approval chain coverage **0**% -> **100**%; desensitization tooling blocked **3** test exports during the drill.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Traceable audit | Operation records include object, before/after values, basis, blast radius, with high-risk operations structured | The point of audit is not recording, it is traceability |
| Backend view splitting | Customer support / operations / R&D at different granularities, high-sensitivity fields desensitized by default | Backend query systems |
| Desensitization tooling | Logs, reports, and exports auto-desensitize, with tooling blocking rather than relying on habit | Logs and exports |
| Minimization and tiering | First identify the most sensitive data, minimize storage, tier access, and make it deletable and desensitizable on expiry | A more realistic governance approach |

### Three lessons from the case

1. **The largest leak surface is an internal super entry point**. A big backend with a coarse permission model and incomplete audit is itself the largest leak surface.
2. **The value of audit lies in traceability, not recording**. If you cannot say who used it in what way, the log is just a log.
3. **Desensitization relies on tooling, not habit**. Passing screenshots and CSVs around in groups is the norm; only tooling blocking can catch it.
