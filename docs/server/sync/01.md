# Tick and Time Advancement

## Category

server / sync subtree. Node positioning: time is more foundational than the protocol -- four kinds of time are separated, fixed Tick remains mainstream, multi-clock layering, and which time is shared between client and server. Master outline of the sync subtree.

## Definition


In real-time combat, the most underestimated thing is never the protocol or the bandwidth, but time itself. The moment multiple clients and the server participate in the same logical session, a few foundational questions must be answered first: what pace does the system advance at, who defines "this is frame N," how do rendering and logic decouple, and how do network jitter and dropped frames not drag the whole session's tempo apart. Many so-called "sync problems" actually have their root cause in a time model that went wrong first.

## Problem

The root cause of "sync problems" is often a time model gone wrong first: who defines which frame it is, how to decouple rendering from logic, how not to scatter the session's tempo when network jitter or dropped frames occur. If time is not fixed first, no matter how you design the protocol, it will be reworked again and again.


### Why time is more foundational than the protocol

Player inputs happen continuously, but machine execution always lands on discrete steps. The instant you press a skill key, to the player it is one continuous point in time; to the system, it must be mapped to a logical frame, an input window, a skill startup point, and a server adjudication moment. If this mapping is inconsistent across the client, the server, and the replay chain, then no matter whether what follows is an input, state, or event, it will drift step by step.

Almost every key object in a combat system depends on time:

- Skill startup, hit point, and recovery.
- Buff duration, periodic Tick, and dispel window.
- Projectile flight, collision detection, and delayed detonation.
- Animation events, effect triggers, and camera shake.
- Proxy takeover, disconnect recovery, and settlement timeouts.

So time advancement is not a runtime detail but a shared foundation for the combat system and the sync system.

### First, separate the four kinds of time

Many teams, when they say "this frame," actually conflate several different kinds of time. A safer approach is to distinguish them from the start:

- Wall-clock time: real-world time, from the system clock.
- Render time: the screen refresh and animation playback pace, possibly 30 FPS, 60 FPS, 120 FPS, or fluctuating.
- Logical time: the step by which the combat simulation advances, usually expressed as a fixed Tick.
- Network time: link times such as message send, receive, queueing, resend, and frame catch-up windows.

These four should not substitute for one another. Rendering dropping to 40 FPS does not mean logic must follow along; a network hiccup does not mean a skill's duration should stretch along with it. Mature systems usually keep logical time as stable as possible and constrain rendering and network fluctuations in the peripheral layers.

### Why fixed Tick is still mainstream

The most common choice in combat simulation is still a fixed Tick. The reasons are straightforward: a fixed Tick makes order easiest to define, replay easiest to record, state hashing easiest, and cross-endpoint consistency easiest to handle. As long as the input and state boundaries of each step are clear, many problems can be reduced to "what happened on frame N."

The direct benefits of a fixed Tick include:

- Skill, Buff, and projectile timing can all land on discrete frame numbers.
- Client and server more easily share a debugging language, e.g. "an anomalous hit on frame 2136."
- Replay, spectating, and state validation are easier to land.
- Frame sync, lockstep, and partial prediction are easier to build on the same logical base.

Its costs are equally clear:

- When a frame exceeds its budget, you need frame patching, frame catch-up, or a degraded mode.
- The higher the Tick frequency, the greater the CPU pressure, and the tighter the network input window.
- If peripheral systems are not layered, the entire project gets dragged down by high-frequency logical advancement.

So the common practice is not "run everything on a fixed Tick," but to put the core logic that actually affects adjudication on a fixed step, and keep presentation and peripheral systems on a looser pace.

### Why variable timestep often breaks combat adjudication

A variable timestep looks flexible but is actually dangerous for multiplayer combat. Once the time step fluctuates with frame cost, collisions, interpolation, random triggers, skill durations, and physics approximations all start to deform. On a single machine this is sometimes tolerable; in a multiplayer sync or replay system, this drift quickly becomes structural cost.

The most common problem is not "occasionally inaccurate," but:

- The same input on different machines evolves into different results.
- Certain skill hit windows get amplified or shrunk by low frame rates.
- Replay re-enactment does not match live gameplay.
- When the client and server share part of the logic, they gradually diverge.

Therefore, even if the rendering and animation layers use a variable timestep, the combat adjudication layer usually tries to stay on a fixed Tick.

### What real projects commonly have is multi-clock layering

A design closer to engineering reality is not a single clock but multiple clock layers:

- Combat logic clock: fixed Tick, determines adjudication and skill timing.
- Render interpolation clock: patches interpolation based on screen refresh, does not directly affect authoritative state.
- Network send clock: organizes messages by packet frequency, packet batching strategy, or input window.
- UI and peripheral system clock: button cooldown display, countdown display, notification animations, etc.

The key to this layering is not complexity but clarity about who can change what and who cannot. A UI countdown can be off by tens of milliseconds, but a combat adjudication frame must not be scrambled; a rendering hitch can skip a few frames of drawing, but the logical frame should not be dropped along with it; a network send a beat late can patch the packet, but it must not let every module reinvent its own notion of time.

### Which time do client and server actually share

In multiplayer combat, the most important thing is to share a single attributable logical time. This typically manifests as:

- The server maintains an authoritative combat clock or authoritative frame number.
- The client maintains a local logical clock but continuously converges toward the authoritative frame.
- All key events can be pinned to an explicit frame number or Tick sequence number.

Even if you adopt server-authoritative state sync rather than pure lockstep, combat events should still carry a clear logical time identifier. Otherwise, when it comes to reconnection, frame catch-up, report review, and state correction, the system simply cannot say whether something is stale state, current state, or a future predicted state.

### Frame patching, frame catch-up, and frame budgets must be designed up front

The real engineering difficulty of a fixed Tick is not writing `tick = 33ms`, but what to do when the system cannot keep up. There are three common cases:

- Local rendering is slow, but the logic thread can still keep up.
- Local logic is also slow and starts to back up.
- After network recovery, the client needs to catch up to the server's frame number.

So the Tick system must design frame patching and catch-up strategies up front, rather than defaulting to "if it's slow, it's slow." Common measures include:

- The maximum number of logic steps to patch in a single frame, to avoid entering a death spiral.
- Disabling some presentation or degrading effects during frame catch-up.
- Switching to snapshot recovery when falling behind too far, rather than endlessly chasing frame by frame.
- Making clear which systems are allowed to skip presentation and which must never skip adjudication.

Without a unified combat clock, pause is just the UI freezing; without a catch-up budget, reconnection easily becomes permanent loading.

### Tick is not just how many times per second it runs

Mature teams usually do not treat Tick as only a frequency constant but care about more concrete runtime facts:

- How long is the input collection window for a frame.
- Is the logical update order stable.
- How do skill hit points and animation events bind to logical frames.
- Is a Buff's periodic Tick by frame count or by time slice.
- Are cross-thread messages consumed in this frame or the next.

Without unified rules for these, a so-called Tick system is just the name of a global timer.

### Observability should start from time

If a Tick system cannot be observed, every sync problem eventually becomes guessing. At minimum you should continuously monitor:

- The current logical frame's cost.
- The number of frame patches over a recent window.
- The maximum number of steps caught up in a single frame.
- The frame-difference distribution between clients and server within a room.
- The number of times default input was used due to timeout.
- The catch-up duration and success rate after reconnection.

These metrics can turn "players say it lags," "skills feel half a beat late," and "reconnection keeps spinning" into quantifiable links, rather than relying on eyeballing a recording to guess.

### Common pitfalls

- Letting different systems each maintain their own "feel of time," so skills, effects, compensation, and adjudication end up misaligned.
- Treating render frame rate as logical time, so when the machine drops frames the combat tempo changes along with it.
- Only looking at Tick during normal operation, and never verifying time consistency during frame patching, catch-up, background suspension, and reconnection recovery.

Once the time system becomes loose, the downstream sync model, pause recovery, skill timing, and replay system all distort together.

### Practical case: triaging a "low-end device skills always half a beat late" mismatch between render time and logical time

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes the page's "First, separate the four kinds of time," "What real projects commonly have is multi-clock layering," and "Frame patching, frame catch-up, and frame budgets must be designed up front" into deep water: high-end devices are fine, low-end devices are a half beat behind overall -- this is the triage of render frame rate being treated as logical time, and also a full unfolding of "how to keep logical time stable and constrain render fluctuation in the peripheral layers."

**Background and symptoms**: a MOBA mobile game, **300,000** DAU, low-end devices (**30** FPS tier) accounting for **22**%. Two weeks after launch, low-end device players complained "skills half a beat late" and "I pressed it but nothing happened," **420** tickets per day, while high-end devices (**60** FPS tier) had almost none. Meanwhile hit rate, win rate, and other business metrics were all green -- another time problem invisible to business metrics.

### Step 1: symptoms and caliber -- first split the ledger by device tier

Device tier caliber: low-end device skill presentation lagged the server-authoritative hit by **3-5** frames, high-end no more than **1** frame; complaint volume was strongly correlated with device tier.

Frame number caliber: the difference between the client-reported local logical frame and the server authoritative frame was stable at **1-2** frames on high-end devices and reached **12** frames on low-end -- the difference moved with render frame rate, indicating logical advancement was running along with rendering.

Business caliber: hit rate and damage statistics were all normal -- because adjudication is on the server, and the server was not slow; what was slow was the client's presentation and local logic.

### Step 2: layered attribution -- decompose layer by layer along the page's four kinds of time

```text
低端机帧差 12 帧  归因
  渲染帧率被当逻辑时间，逻辑按渲染帧推进      68%  →  8.2 帧
  插值时钟与逻辑时钟未分层                    22%  →  2.6 帧
  无补帧预算，掉帧后不回补                    10%  →  1.2 帧
```

Triage path: first check the network (low-end and high-end devices in the same city on the same carrier, link differences ruled out); then check the server (server frame number stable, ruled out); finally check the client loop -- logical updates were hung on the render callback, so when rendering dropped to **30** FPS, logical advancement dropped with it from **60** Hz to **30** Hz, stretching timing such as skill startup and hit points that are measured in frame counts.

### Step 3: root cause -- render frame rate and logical step were not decoupled

Logical updates and rendering shared one loop, with no independent fixed Tick and no independent render interpolation clock. Render dropped frames directly slowed logical advancement -- exactly the page's "treating render frame rate as logical time, so when the machine drops frames the combat tempo changes along with it." The interpolation clock was also not layered, so on low-end devices presentation interpolation added another layer of lag.

### Step 4: remediation and backfill -- three changes to decouple logic from rendering

1. Split the logic layer onto a fixed Tick: logic advances at a fixed **33** ms step, decoupled from render frame rate; when rendering drops to **30** FPS, logic still advances at a fixed step, running two logic steps within a single render frame if necessary.
2. Independent interpolation clock for the render layer: presentation patches interpolation according to screen refresh, and degrades effects and particles on low-end devices, but does not change the logical step.
3. Frame patching budget: a single render loop patches at most **4** logic steps, switching to snapshot recovery when over budget, to avoid low-end devices entering a death spiral.

Verification ledger: low-end frame difference **12** frames -> **2** frames; "skills half a beat late" complaints **420** per day -> **30** per day; the hit presentation difference between low-end and high-end converged to within **1** frame.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Four-time separation | Define wall-clock, render, logical, and network time separately; explain during review which cannot substitute for which | First, separate the four kinds of time |
| Render interpolation clock | Render patches interpolation by screen refresh, logic advances by fixed Tick, neither changes the other's step | What real projects commonly have is multi-clock layering |
| Frame patching budget | At most 4 logic steps patched per frame, over budget switches to snapshot, avoiding a death spiral | Frame patching, frame catch-up, and frame budgets must be designed up front |
| Frame-difference observability | Continuously monitor the client-to-server frame-difference distribution within a room, grouped by device tier | Observability should start from time |

### Three lessons from the case

1. **All-green business metrics does not mean the time model is right**. Adjudication is on the server, metrics are on the server, what was slow was client time advancement -- time problems must be looked at by frame number, not just by business results.
2. **Render frame rate must never be used as logical time**. Sharing one loop for logic and render means a low-end device's dropped frames become an overall tempo slowdown; fixed Tick plus an independent interpolation clock is the dividing line.
3. **The frame patching budget must be set in advance, otherwise dropped frames become a death spiral**. How many steps to patch per frame and when to switch to snapshot must be decided to survive low-end devices.
