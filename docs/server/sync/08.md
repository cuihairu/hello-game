# Skill System Design

## Category

server / sync subtree. Node positioning: the skill system is an architecture problem -- description/instantiation/execution/sync/debugging/extension designed as one, the timeline/state machine split of duties, an independent effect pipeline, and Buffs as first-class citizens.

## Definition


The skill system is not as simple as "write one script per skill." It is essentially answering a set of harder questions: how skills are described, instantiated, executed, synced, debugged, and continuously extended by the content team. If these are not designed uniformly, early on the project may only have uglier code, but mid-to-late stage it evolves into new skills getting slower, online problems getting harder to chase, and balance adjustments getting easier to accidentally hurt old logic.

## Problem

"Write one script per skill" is only ugly code early on; mid-to-late stage it becomes new skills getting slower, online problems harder to chase, and balance adjustments hurting old logic. The skill system and the sync boundary must be fixed together -- if skill timing changes, the sync model has to move with it.


### Why the skill system sooner or later becomes an architecture problem

Designers see gameplay, feel, combos, and class differences in skills; clients see input feedback, animation, effects, and camera; the server sees adjudication, hits, cooldowns, resources, and anti-cheat; AI and levels see reusable behavior capabilities; the toolchain sees configuration, validation, logs, and replay.

A "charge and launch" skill often simultaneously involves:

- Movement and collision.
- Target filtering.
- Damage and control.
- Buffs and passive triggers.
- Presentation broadcasting and replay recording.

The skill system is hard not because a single skill is complex but because it naturally crosses too many boundaries.

### What the skill system truly needs to design

What the skill system truly needs to design is not "what the skill table looks like" but how the following layers divide duties:

- Skill definition: statically describing what behavior a skill has.
- Cast request: what a player or AI wants to cast this time, on whom, at what position.
- Skill instance: the object that actually enters the runtime for this cast, carrying stages, timers, a target snapshot, and context.
- Target selection: who becomes a candidate target, and how to filter, sort, truncate, and lock.
- Effect settlement: how damage, healing, Buffs, movement, summons, interrupts, and so on are executed uniformly.
- Presentation events: how animation, effects, sound, screen shake, floating text, and camera subscribe to authoritative results.
- Sync adjudication: which results can be predicted and which must wait for server confirmation.
- Debugging and replay: why it didn't hit, why it was interrupted, why it triggered one extra time -- can the system say clearly.

If these layers are not separated, the project usually degrades into a "skill ID + if/else + fire events everywhere" shape.

### A more robust runtime skeleton

If a skill system is to be maintainable long-term, it usually needs at minimum the following runtime objects:

- `SkillDefinition`: the static skill definition, describing tags, cast method, cost, cooldown, stage timeline, target rules, and the effect list.
- `CastRequest`: a cast request, containing the caster, skill ID, input direction, target point, target object, and initiation time.
- `CastContext`: one cast context, containing the current Tick, a caster snapshot, a random seed, the map environment, and the link source.
- `SkillInstance`: a running skill instance, containing the current stage, remaining time, locked targets, and triggered effects.
- `TargetResolver`: a target selector, uniformly responsible for finding the final hit set from the candidate set.
- `EffectProcessor`: an effect processor, uniformly executing damage, healing, Buffs, movement, summons, and dispels.
- `BuffInstance`: a state effect instance, responsible for duration, stacking, periodic Tick, and disappearance conditions.
- `CombatEvent`: a standard combat event, recording cast start, hits, dodges, interrupts, Buff additions, shield absorption, and deaths as a unified event stream.

The core idea of this skeleton is simple: the skill organizes the casting flow and does not directly monopolize all business logic; effects are responsible for specifically changing state; Buffs are responsible for persistence; the presentation layer subscribes to events rather than changing adjudication in reverse.

### How should a single cast be broken into a flow

A mature skill system usually breaks a cast into the following chain:

1. Input or AI issues a `CastRequest`.
2. Enter pre-validation, checking cooldown, cost, death state, control state, and global CD.
3. Create a `SkillInstance` and record the cast context.
4. Enter the casting stage, advancing startup, hit points, the duration segment, and recovery by timeline or state machine.
5. Execute target selection at a given node, getting the hit set or area of effect.
6. Send the effect list into the unified effect pipeline, executing damage, healing, Buffs, movement, etc. one by one.
7. Produce authoritative combat events, driving client presentation, logs, replay, and subsequent trigger chains.
8. The skill ends, is cancelled, or is interrupted, clearing runtime state and entering cooldown or recovery state.

Breaking the flow this way, the biggest benefit is not pretty architecture but that any problem in any link can be located to a clear responsibility layer.

### How should the timeline and state machine divide duties

For most regular action skills, RPG skills, and monster skills, the most common and stable pattern is timeline-driven. The skill definition does not write one complete script but defines:

- `startup`: the windup, deciding whether it is interruptible, whether orientation locks, and whether the animation starts playing.
- `active`: the hit segment, which can be a single point or multiple fragments.
- `recovery`: the follow-through, deciding when the character resumes movement or chains into another skill.

Under this model, many seemingly different skills can be unified into "trigger some effects at some points in time."

When a skill has obvious conditional branching, interrupt recovery, channeling sustain, and stage switches, a state machine is more stable than a pure timeline. Typical examples include:

- Channeling skills: `casting -> channeling -> complete / interrupt`
- Charged skills: `hold -> charged_lv1 -> charged_lv2 -> release`
- Combo skills: `stage1 -> combo_window -> stage2`

The safer practice is usually: regular skills use the timeline, complex sustained or conditional-branch skills use a state machine, and the two share the same effect and event pipeline.

### Why the effect pipeline must be separated out

The most easily broken place in a skill system is writing every skill as a "compute everything itself" block of logic. A safer approach is to separate skills from effects:

- The skill defines "which effects to trigger when."
- The effect processor defines "how a given effect type is settled uniformly."

Common effect types include:

- Damage.
- Healing.
- Add Buff / remove Buff.
- Movement, pull, knockback, launch.
- Resource changes.
- Summons.
- Shields.
- Interrupt, silence, stun, control immunity.

Designing this way gives several direct benefits:

- Adding a new skill is mostly combining existing capabilities rather than writing another new script.
- Adding a new effect type only requires extending one effect processor rather than changing every skill.
- Damage bonuses, resistances, shield absorption, crits, and tag corrections can all hang off the same settlement pipeline.

### Buffs must be treated as first-class citizens

Many projects early on treat Buffs as "a little bit of state attached to a skill," and problems almost certainly follow. Buffs actually carry far too much persistent logic:

- Sustained damage and sustained healing.
- Control and control immunity.
- Attribute corrections and stacking.
- Auras, domains, marks, and triggers.

Safer designs are usually:

- Skills are responsible for applying or removing Buffs.
- Buffs themselves are responsible for duration, stacking, periodic Tick, triggers, and disappearance conditions.
- The attribute system and Buff system are linked, with no ad-hoc modification of base attributes inside skills.

If Buffs are not modeled as independent objects, the further along you get, the harder it is to handle overwrite, refresh, dispel, immunity, and log tracking.

### The skill system and the sync boundary must be fixed together

The skill system cannot be designed in isolation from the sync system. At minimum, these must be clarified first:

- Which stages allow client pre-play, e.g. startup motions and local effects.
- Which results must wait for authoritative confirmation, e.g. hits, damage, death, and key control.
- Which states of a skill instance need to enter replay and reconnection recovery.
- Whether target selection and effect settlement depend on strict logical frames.

If these boundaries are not fixed first, the skill system ends up repeatedly patching between the client playing ahead, the server correcting, and replay being unable to explain.

### What long-term extension capability mainly depends on

Whether a skill system can survive long-term is not about "whether a few ultimates can be written at the start" but about whether the following capabilities exist:

- Whether new skills can be completed mainly by combining existing capabilities.
- Whether new effect types can be extended locally rather than affecting the global.
- Whether skills, Buffs, passives, and summons can reuse a unified event stream.
- Whether online problems can be located to a specific cast instance, specific target selection, and specific effect settlement.

Without these capabilities, once the number of skills grows, the system quickly enters a "every content addition is like defusing a bomb" state.

### Common pitfalls

- Understanding the skill system as "write one script per skill," and the more you build the harder it is to maintain.
- Letting target selection, damage calculation, Buff logic, and presentation broadcasting all live inside skill scripts, ending up with no boundaries at all.
- Designing the skill system alone, then patching sync, replay, and reconnection afterward, so every adjudication problem ends up unexplainable.

What skill system design truly needs to do is not write skills but organize three things together: how skills grow long-term, how they are adjudicated, and how they are explained.

### Practical case: triaging a "skills get slower as they're added, every balance change hurts something" script-stacking problem

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes the page's "A more robust runtime skeleton," "Why the effect pipeline must be separated out," and "The skill system and the sync boundary must be fixed together" into deep water: one script per skill, the more stacked the harder to separate -- this is the triage of a skill system without unified design, and also a full unfolding of "the skill organizes the flow, effects handle settlement."

**Background and symptoms**: a project with **320** skill scripts each on their own, with target selection, damage calculation, Buff logic, and presentation broadcasting all written inside the scripts. New skill delivery grew from **4** days early on to **12** days; one balance adjustment caused **17** old skills to be accidentally affected, and "why didn't it hit" tickets averaged **4** hours and still could not be explained online.

### Step 1: symptoms and caliber -- first see which layer slowness and collateral damage arise in

Delivery caliber: a new skill requires copying and pasting the entire previous skill script, and **8** of the **12** delivery days go into aligning the old script's various implicit conventions.

Collateral damage caliber: damage bonuses, resistances, and shield absorption are scattered across skill scripts, so changing one base formula connectedly changed **17** skills referencing the old implementation.

Item-by-item comparison: the page says the skill system is hard "not because a single skill is complex but because it naturally crosses too many boundaries," and the scripts inlined all the boundaries; Buffs had no independent object, so overwrite, refresh, dispel, and immunity were managed by per-script conventions; the sync boundary was added later, so the client played ahead, the server corrected, and replay could not explain. All three are present, and the "script computes everything" one is the largest proportion.

### Step 3: root cause -- the skill system was understood as "write one script per skill"

The problem layers were not separated, so early on it was only ugly code, but mid-to-late stage it becomes new skills getting slower, online problems harder to chase, and balance adjustments hurting old logic -- the project degraded into a "skill ID + if/else + fire events everywhere" shape. This page's layers -- skill definition, cast request, skill instance, target selection, effect settlement, presentation events, sync adjudication, debugging and replay -- were compressed into one script, so any change in any layer required manually triaging every script.

### Step 4: remediation and backfill -- split the layers by the skeleton

1. Land the eight-piece runtime set: `SkillDefinition`, `CastRequest`, `CastContext`, `SkillInstance`, `TargetResolver`, `EffectProcessor`, `BuffInstance`, `CombatEvent`, each owning one segment, with scripts only organizing the casting flow and not directly monopolizing all business logic.
2. Timeline / state machine split of duties: regular skills use the timeline (`startup` / `active` / `recovery`), conditional branching and channeling/charging use a state machine, and the two share the same effect and event pipeline.
3. Independent effect pipeline + Buff as a first-class citizen: the effect processor settles uniformly, Buffs manage their own duration, stacking, periodic Tick, and disappearance conditions; the sync boundary fixed together, with hits, damage, and death requiring authoritative confirmation.

Verification ledger: new skill delivery **12** days -> **3** days; balance adjustment collateral damage **17** -> **0**; "why didn't it hit" ticket location **4** hours -> **15** minutes.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Eight-piece runtime set | Eight layers from `SkillDefinition` to `CombatEvent`, scripts only organizing the flow | A more robust runtime skeleton |
| Timeline / state machine split of duties | Regular skills use the timeline, conditional branching uses a state machine, sharing the effect pipeline | How should the timeline and state machine divide duties |
| Independent effect pipeline | The skill defines when to trigger, the effect processor settles uniformly | Why the effect pipeline must be separated out |
| Buff as a first-class citizen | Buffs manage their own duration, stacking, periodic Tick, and disappearance conditions | Buffs must be treated as first-class citizens |

### Three lessons from the case

1. **The skill system is an architecture problem, not a script count problem**. Without separating the layers, the more skills there are, the more every content addition feels like defusing a bomb.
2. **The skill organizes the casting flow and does not directly monopolize all business logic**. Effects change state, Buffs handle persistence, and the presentation layer subscribes to events rather than changing adjudication in reverse.
3. **The skill system and the sync boundary must be fixed together**. Adding the boundary later results in endlessly patching between the client playing ahead, the server correcting, and replay being unable to explain.
