# Pause, Resume, Frame Catch-up, and Reconnection

## Category

server / sync subtree. Node positioning: pause, resume, frame catch-up, and disconnect reconnection are four different things -- the scenarios that most easily expose architectural truth, and they must share one clock model.

## Definition


Pause and resume are not a UI detail but the scenario that most easily exposes architectural truth in a sync system. Many teams think "the client pressed pause, the combat clock stops stepping" counts as supporting pause, yet the moment it hits online combat, background suspension, disconnect recovery, a server that never stops, and reconnection, the system immediately shows its cracks.

## Problem

"Client pressed pause, combat clock stops stepping" is not supporting pause: online combat, background suspension, disconnect recovery, and a server that never stops are where truth shows. If the constraint that pause and resume share the same clock model is not fixed up front, the system falls apart the moment it enters online scenarios.


### First, separate four different things

In real engineering, many people call the following four situations "pause," but they are fundamentally not the same thing:

- Local UI pause: the player opens a menu, pausing rendering or pausing inputs, but room logic may keep running.
- Room-level combat pause: the authoritative logical time of the whole battle stops advancing, all participants stop at the same frame.
- Client suspension or freeze: the client locally stops advancing, but the server and other players may not have stopped at all.
- Disconnect reconnection and frame catch-up: the client left for a while and must catch back up to the authoritative frame upon returning.

If these four scenarios are not separated first, every subsequent design fights with the others.

### In online combat there is only one kind of "pause"

In online combat, the only definition of a real combat pause is: the authoritative combat clock stops advancing. That is, it is not just the client's picture freezing, but the server or room coordinator explicitly locking the logical frame on a given frame until a resume command takes effect.

If only some client locally stops stepping while the server keeps advancing:

- To the server, this is not a pause but a client falling behind or being suspended.
- To other players, this is not a pause but the room continuing normally.
- To the reconnected client, what it faces upon returning is a frame catch-up recovery problem, not a pause-resume problem.

This is exactly the root cause of many failure cases: the system thought it implemented pause, when in fact only one endpoint locally stopped.

### Who should control a room-level pause

If a project allows pausing online combat, the safer practice is usually:

- The authoritative server or room coordinator decides whether to enter the paused state.
- The paused state is bound to an explicit room state and current frame number.
- During the pause no new logical frames are generated and no future inputs are consumed.
- On resume, advancement continues from the same authoritative frame, not by each endpoint "continuing to run" on its own.

Pause permissions must also be clearly defined:

- Who can initiate a pause.
- Whether a pause requires everyone's consent.
- How long a pause may last at most.
- Whether a disconnected player triggers an automatic pause, a proxy, or the match continuing.

These rules are not product side-branches but part of the sync system.

### What are many failure cases fundamentally about

"Server didn't stop and kept running; after the client reconnected it kept catching up on frames and kept loading" -- this phenomenon is usually not a single bug but several design problems stacked:

- Mistaking client suspension for a combat pause.
- No room-level authoritative pause semantics, so the server naturally keeps advancing.
- No periodic combat checkpoints, so reconnection can only patch frame by frame from long ago.
- No catch-up upper bound, so the client forever tries to use CPU to finish patching history.
- The loading process and catch-up process are coupled, so resources are not ready and logic cannot catch up either.

At that point, what the client is "loading" is often not a single resource but doing several things at once that should not be forced together: pulling room state, restoring the object graph, patching historical frames, rebuilding skill and Buff timing, loading presentation resources, aligning with the current authoritative frame. If any one item cannot keep up, continuous loading appears.

### What should reconnection actually restore first

A more reasonable question is not "should reconnection catch up on frames," but "restore to which base point first, then how many frames to catch up." The safer answer is usually:

- Room basics: map, mode, current phase, player list, factions.
- The most recent authoritative checkpoint: character positions, orientation, health, resources, Buffs, cooldowns, projectiles, summons, and combat sub-states.
- A small amount of incremental frames after the checkpoint: the inputs or events from the checkpoint frame to the current authoritative frame.
- The current authoritative frame number and time base: telling the client where it needs to catch up to.
- The minimum necessary presentation resources: not replaying the whole presentation history, but ensuring the current state displays correctly.

There is only one key point: the goal of reconnection recovery is to return to the current authoritative state as fast as possible, not to faithfully replay every historical presentation detail from while disconnected.

### Why you cannot blindly catch up frame by frame

Frame-by-frame catch-up is only reasonable when the gap is small. Once far behind, it almost always breaks down:

- The client is catching up logic while also loading resources and rebuilding objects; the CPU easily gives out first.
- If rendering and logic are not thoroughly separated, the experience during catch-up is very poor.
- Once new frames keep arriving, the target keeps rolling forward and the client may never catch up.

Therefore mature systems usually set multiple recovery tiers:

- Slightly behind: fast frame catch-up directly.
- Moderately behind: load the most recent checkpoint, then patch a small segment of incremental frames.
- Far behind: state jump directly to the latest checkpoint, discarding some intermediate presentation if necessary.
- Beyond the recovery window: do not force recovery; switch to re-joining, proxy, or declaring defeat.

Without these tiers, reconnection recovery usually degenerates into "theoretically correct, unusable online."

### How should frame catch-up run so it does not crush the client

Frame catch-up is essentially a constrained fast simulation process. Common practices include:

- Degrading or disabling part of the presentation system during catch-up.
- Limiting the maximum number of logical frames caught up within a single render loop to prevent freezing.
- Splitting resource loading from logical catch-up to avoid blocking each other.
- Prioritizing recovery of key objects, deferring non-critical presentation.
- When the gap grows despite catching up, immediately switching to checkpoint recovery rather than continuing to push through.

Frame catch-up is not the normal combat loop on fast-forward but a specially designed recovery mode.

### Pause and disconnect recovery must share the same clock model

If the system has room-level pause, then both pause and resume must land on the authoritative combat clock. Otherwise several common disasters occur:

- The client thinks it stopped at frame 2000 while the server is actually at frame 2150.
- During the pause the client still locally advances animations or skill logic, and after resume the state is misaligned.
- On resume different clients continue from different local clocks and the session diverges immediately.

Better designs are usually:

- What stops or resumes is the authoritative frame advancer, not the UI.
- The paused state is part of the room state machine, not a local switch.
- On resume all clients align to the same authoritative frame and the same checkpoint.

### A set of metrics that must be continuously observed

If the system supports pause, resume, and reconnection, at minimum it should continuously monitor:

- The number of room pauses and average pause duration.
- Disconnect reconnection success rate.
- Average recovery time after reconnection.
- Snapshot recovery hit rate.
- Average and maximum number of frames caught up.
- The number of failures due to exceeding the recovery window.

Without these metrics, you cannot tell whether slow recovery is due to a slow network, snapshots too stale, resource loading blocking, or a problem with the logical catch-up strategy itself.

### Common pitfalls

- Treating the client locally stopping stepping as an online combat pause.
- Having no checkpoints, so reconnection can only patch frame by frame from the breakpoint.
- Frame catch-up and resource loading strongly coupled, so the more the client recovers the more behind it falls.
- No fallback for recovery failure, so the system would rather load forever than explicitly declare this recovery infeasible.

What this page really needs to solve is not "how to write pause," but how room clocks, reconnection recovery, and catch-up strategy unify into one set of deployable semantics.

### Practical case: triaging "reconnection keeps spinning on loading" frame catch-up and checkpoints

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes the page's "First, separate four different things," "What are many failure cases fundamentally about," and "How should frame catch-up run so it does not crush the client" into deep water: returning after a disconnect means endless loading, waiting longer and longer -- this is the triage of reconnection catch-up and missing checkpoints, and also a full unfolding of "how to make recovery return to the current authoritative state rather than replaying history."

**Background and symptoms**: an MMO raid, disconnect reconnection success rate **82**%, average recovery time **47** seconds, tail over **3** minutes; sessions far behind almost always stuck on the loading screen. Customer support's take: "once you disconnect you can't get back in," while network metrics were normal at the time.

### Step 1: symptoms and caliber -- first tier by frames behind

Recovery time caliber: average **47** seconds, P99 **190** seconds; sessions behind by **900** frames or fewer averaged **8** seconds, sessions behind by more than **900** frames almost all failed.

Failure shape caliber: clients stuck on loading were simultaneously pulling room state, patching historical frames, rebuilding skill and Buff timing, and loading presentation resources -- exactly the page's "doing several things at once that should not be forced together."

Clock caliber: during the disconnect the server never stopped, and by the time the client returned the authoritative frame was already more than **1200** frames ahead -- the server never stopped, yet the client returned with a "pause" mindset.

### Step 2: layered attribution -- triage item by item along the page's failure list

```text
重连失败 18%  归因
  无周期检查点，重连从断点逐帧补             48%
  追帧与资源加载耦合，越补越落后             31%
  无追帧上限与恢复档位，超窗口也不判失败      21%
```

Triage path: network link normal (ruled out); server frame number kept advancing (confirmed the server never stopped); the problem is in the recovery strategy -- without checkpoints it can only patch frame by frame from the breakpoint, and falling behind **900** frames or more can never catch up; catch-up and resource loading are coupled, so the CPU gives out first; no recovery tiers, so no failure is declared even past the window, preferring to load forever.

### Step 3: root cause -- client suspension treated as pause, recovery with no base point and no tiers

The team believed "client pressed pause, combat clock stops stepping" counts as supporting pause, but in online combat the only real pause is the authoritative combat clock pausing. The disconnected client, upon returning, faces a frame catch-up recovery problem, yet the system has neither periodic checkpoints as a recovery base point nor a catch-up bound and recovery tiers, so recovery naturally degenerates into permanent loading.

### Step 4: remediation and backfill -- give recovery a base point first, then tier it

1. Periodic checkpoints: generate a room checkpoint every **300** frames (character positions, health, Buffs, cooldowns, projectiles, summons, combat sub-states), and reconnection preferentially loads the most recent checkpoint.
2. Four recovery tiers: slightly behind, fast catch-up directly; moderately behind, load the checkpoint and patch a small segment of incremental frames; far behind, jump directly to the latest checkpoint; past the recovery window, switch to re-joining or proxy.
3. Decouple catch-up from resource loading: degrade or disable presentation systems during catch-up, key objects recover first, non-critical presentation deferred; a single render loop is limited to catching up at most **4** logical frames.
4. Pause semantics restored: room-level pause bound to the authoritative frame number, disconnect triggers proxy rather than making the whole session wait.

Verification ledger: reconnection success rate **82**% -> **98.6**%; average recovery time **47** seconds -> **6** seconds; P99 **190** seconds -> **18** seconds; permanent-loading-type tickets cleared to zero; snapshot recovery hit rate **91**%.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Four things separated | Local UI pause, room-level pause, client suspension, disconnect reconnection defined separately, not sharing one set of semantics | First, separate four different things |
| Authoritative pause semantics | Pause bound to the authoritative frame number and room state machine, disconnect triggers proxy rather than the whole session waiting | In online combat there is only one kind of "pause" |
| Recovery order and tiers | First restore room info and the most recent checkpoint, then patch a small amount of incremental frames; four tiers by how far behind | What should reconnection actually restore first |
| Catch-up without crushing the client | Degrade presentation during catch-up, decouple logic from resource loading, past the window switch to re-joining | How should frame catch-up run so it does not crush the client |

### Three lessons from the case

1. **In online combat the server never stops, so the "pause" mindset is simply wrong**. The disconnected client returns facing frame catch-up recovery, not pause-resume -- without separating the four things first, the recovery strategy is inevitably twisted.
2. **Without checkpoints, reconnection can only patch frame by frame from the breakpoint, and far behind it never catches up**. Checkpoints are the base point of recovery, and also the precondition for making long sessions stable.
3. **Frame catch-up needs a bound and tiers; rather than loading forever, explicitly declare failure**. The goal of recovery is to return to the current authoritative state as fast as possible, not to faithfully replay every historical presentation from while disconnected.
