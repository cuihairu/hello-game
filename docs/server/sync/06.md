# Determinism and Numerical Consistency

## Category

server / sync subtree. Node positioning: determinism and numerical consistency are first-class citizens -- divergence sources, floating point costs, randomness as a resource, order discipline, verification as everyday infrastructure.

## Definition


Many teams understand sync problems as "network problems" until they find packets all arrived and the order is not scrambled, yet the client and server still diverge further and further. The real cause is often not in the network but in determinism and numerical consistency not being treated as first-class citizens. As long as a system relies on frame sync, lockstep, input replay, or cross-endpoint shared logic, this problem will come knocking sooner or later.

## Problem

Packets all arrived, order not scrambled, and two machines still compute two results -- the sync problem is not in the network but in determinism. When relying on frame sync, lockstep, replay, and cross-endpoint sharing, determinism will come knocking sooner or later; treating verification tools as everyday infrastructure is what catches a divergence at the moment it appears.


### What does determinism mean

In this context, determinism can be crudely understood as one sentence: the same initial state, the same input sequence, and the same advancement order should yield the same result.

As long as this does not hold, all of the following capabilities are shaken:

- The consistency of frame sync.
- The reproducibility of input replay.
- The correctness of catching up by input after a disconnect.
- The post-hoc review of disputed sessions.
- The trustworthiness of logic shared between server and client.

So determinism is not mathematical pedantry but the engineering precondition for whether a sync system can land.

### What are the most common divergence sources

In real projects, divergences often come from very small details:

- Floating point errors differing across CPUs, platforms, and compilers.
- Unstable collection traversal order.
- A randomized source not unified, or different modules sharing the same random stream.
- Unfixed multithreaded update order.
- Physics engines or collision libraries behaving differently across platforms.
- Unstable interaction order between a script VM and its host.
- Time APIs, system clocks, and frame costs directly participating in logic decisions.

In short sessions these may not be obvious, but in long sessions, many objects, and high-frequency skill interactions they accumulate fast.

### Which systems most easily break determinism

Things that commonly go wrong are usually not pure numerical formulas but the following kinds of systems:

- Movement, collision, and pathfinding.
- Skill hit judgment and target selection.
- Buff periodic Tick and trigger chains.
- Projectile advancement and hits.
- Logic relying on order semantics like "nearest target" or "first unit hit."
- Places using script hot updates or cross-endpoint shared logic.

The common thread of these systems: order, boundaries, and numerics are all very sensitive.

### Floating point is not the original sin, but the cost must be known

Many engineering debates ultimately land on "whether to switch everything to fixed point." More realistically:

- Floating point is more convenient and develops faster.
- Perfectly consistent floating point across platforms is hard to guarantee.
- Not every system is worth paying a very high cost for full consistency.

So the more common practice is layering:

- The core adjudication layer tightens numerical behavior as much as possible.
- The presentation layer allows some error.
- Local systems truly depending on strong determinism consider stronger constraints, e.g. fixed point or a controlled math library.

The key is not religious rejection of floating point but not pretending floating point differences do not exist inside an architecture that depends on determinism.

### Randomness must be managed like a resource

Randomness is the most typical hidden divergence source. Safer practices typically include:

- Assign a clear random seed to a combat instance.
- Different subsystems use different random streams; do not share one global RNG.
- Fix the random consumption order for the same event.
- Be able to restore RNG state on replay and reconnection.

If a Buff triggers one extra time or a projectile randomizes its angle one extra time, the rest of the session can start to drift.

### Order matters more than many think

Much logic looks unrelated to numerics but actually depends heavily on order. For example:

- Update Buffs before movement, or vice versa.
- Traverse a target list by creation order, distance order, or ID order.
- When multiple hit targets exist, does damage lifesteal or kill-to-mana resolve first.
- When two control effects expire simultaneously, which is removed first.

As long as order is unstable, even with identical formulas the results will diverge. Stable order is often more important than "a more advanced data structure."

### Multithreading and async messages most easily quietly break consistency

As long as logic depends on execution order, multithreading naturally brings risk. Common problems include:

- Different threads writing back to shared state in an unfixed order.
- Async messages arriving at the logic thread at an unstable time.
- Scheduling differences across platforms leading to different concurrent race results.

Therefore the common conservative practice in the combat adjudication layer is:

- Core logic still advances single-threaded or in strict order.
- Async results entering the logic layer are uniformly wrapped to be consumed next frame.
- Multithreading is used more for peripheral work that can parallelize but does not affect adjudication order.

This is not rejecting multithreading but acknowledging that a sync system is very sensitive to order.

### Verification tools must be everyday infrastructure

Determinism problems fear nothing more than "only triaged after an incident." Safer teams usually prepare:

- Periodic state hashing.
- Key object snapshot comparison.
- Automatic replay comparison on two or more endpoints.
- Earliest divergence frame location tools.
- Logs of key systems' random streams and event sequences.

Without this infrastructure, once a determinism problem goes online, it degrades from an engineering problem into numerology.

### Not every system must pursue full determinism

A more realistic principle is layered determinism:

- Must be strongly deterministic: core adjudication, skill hits, key resource changes, and replay evidence.
- Try to be consistent: character movement, projectiles, Buff triggers, and important timing state.
- Can be relaxed: pure presentation effects, camera micro-adjustments, local interpolation, and sound effects.

This layering is not a compromise but a way to avoid dragging the entire project into high determinism costs.

### Common pitfalls

- Depending on determinism architecturally while continuing to use uncontrolled floating point, randomness, and order in engineering.
- No everyday verification, only starting to triage once players find out-of-sync.
- Wanting every system to reach the same strength of determinism, and eventually losing control of the cost.
- Conflating presentation-layer error with adjudication-layer error, so where it should be strict it is not, and where it should be loose it dares not be.

What determinism and numerical consistency really need to handle is not "is the math correct" but whether the set of engineering preconditions a sync system stands on can be continuously upheld.

### Practical case: triaging a determinism divergence where "the same replay, two machines compute two results"

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes the page's "What does determinism mean," "What are the most common divergence sources," "Order matters more than many think," "Randomness must be managed like a resource," and "Verification tools must be everyday infrastructure" into deep water: replay inconsistency is not a network problem but the determinism preconditions not being upheld in engineering -- this is the triage of frame sync and input replay systems, and also a full unfolding of "determinism is the engineering precondition of a sync system, not mathematical pedantry."

**Background and symptoms**: a frame sync + input replay competitive mobile game, **750,000** sessions per day, using replays for dispute review and adjudication. Test machines and online machines replaying the same input sequence produce results that do not match; players complain "the replay is not the same match." Replay comparison samples **200** sessions/day, **13** inconsistent -- inconsistency rate **6.5**%, while replay uses local files and input sequences are consistent frame by frame, so network factors were ruled out from the start.

### Step 1: symptoms and caliber -- first turn "doesn't match" into statable divergence frames

Inconsistency caliber: in replay comparison, the sessions where two machines advance from the same initial state and the same input sequence and the state hash first differs. Of **200** sampled sessions, **13** inconsistent, inconsistency rate **6.5**%.

Divergence location: frame-by-frame state hash comparison, the earliest divergence frame median in inconsistent sessions is frame **47** -- divergences are not randomly scattered but concentrated in skill interactions within the first two seconds.

Ticket caliber: **45** customer support tickets per day of "replay doesn't match the match," **0.006**% of daily sessions -- the proportion is extremely low, but every ticket is an arbitration risk.

### Step 2: layered attribution -- triage item by item along the page's divergence sources

```text
回放不一致 13 局  归属
  集合遍历顺序不稳定（目标选择 map 遍历）  62%  →  8 局
  随机数流共用（暴击与特效共用同一随机流）  23%  →  3 局
  浮点差异（不同 CPU 三角函数末位）        15%  →  2 局
```

- Input layer: two machines' input sequences are consistent frame by frame, initial state consistent -> inputs and initial state ruled out.
- Order layer: **62**% points to target selection -- skill hit judgment traverses a candidate target map to take the "nearest target," Go's map traversal order is random, so with the same inputs the target order differs, and the damage settlement order differs with it.
- Random layer: **23**% points to shared random streams -- the skill crit judgment and the effects module share one global RNG, so a crit consuming one extra random number shifts the entire session's subsequent random sequence.
- Numerical layer: **15**% points to floating point -- last-bit trig differences across CPUs, accumulating only at projectile boundaries, a long tail.

### Step 3: root cause -- unstable order is the primary root cause, shared random streams the secondary

Primary root cause: target selection depends on map traversal order. The page says "unstable collection traversal order" is one of the divergence sources; here it is a live example: **62**% of inconsistent sessions trace to the same code -- traversing a candidate target map to take the nearest target, traversal order differs every session, and hit judgment and settlement order diverge with it. Identical formulas, different order, different result.

Secondary root cause: shared random streams. The page says "the randomized source is not unified, or different modules share the same random stream" -- the crit judgment and effects module share one global RNG, and a crit drawing one extra time shifts the entire rest of the session.

Long tail: floating point differences. Last-bit trig differences across CPUs contribute **15**% of inconsistent sessions, not worth fixing alone, so layered determinism groups it under tightening the core adjudication layer.

### Step 4: remediation and backfill -- three changes to close order and randomness

1. Change target selection to stable sorting: candidate targets sorted by (distance, ID) before taking the nearest, map traversal changed to ordered structures, and settlement order written into the code review checklist.
2. Split random streams: combat instances get an independent random seed, crit and effects each use independent random streams, and the random consumption order is fixed and registered in the architecture specification.
3. State hashing as everyday verification: compute a state hash at the end of each session, bring online automatic two-endpoint replay comparison plus an earliest-divergence-frame location tool, turning post-hoc triage into everyday infrastructure.

Verification ledger: replay inconsistency **13** sessions -> **0** sessions (**200** all consistent); arbitration tickets **45** per day -> **5** per day; triage time for similar problems **3** days -> **0** days to discover after state hashing auto-alerting (divergence automatically located at frame **47**).

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Stable order specification | Target selection and settlement order sorted by stable keys such as (distance, ID), reliance on map/hash traversal order forbidden | Order matters more than many think |
| Random stream registration | Independent seeds per combat instance, independent random streams per subsystem, consumption order fixed and registered | Randomness must be managed like a resource |
| State hashing as everyday verification | Per-session state hash + automatic two-endpoint replay comparison + earliest divergence frame location, as everyday infrastructure | Verification tools must be everyday infrastructure |
| Layered determinism | Strong determinism for core adjudication, relaxed for the presentation layer, review checked against three layers | Not every system must pursue full determinism |

### Three lessons from the case

1. **Determinism is an engineering precondition, not mathematical pedantry**. Replay, adjudication, and disconnect catch-up all stand on "the same initial state, the same input sequence, the same advancement order, the same result"; if this does not hold, the sync system is a castle on sand.
2. **Stable order matters more than advanced data structures**. A "seems fine" detail like random map traversal order is the top source of determinism divergence; stable key sorting is the baseline, not an optimization.
3. **Verification must be everyday infrastructure**. Without state hashing and automatic replay comparison, online determinism triage is numerology; with infrastructure, a divergence can be automatically located at frame **47** rather than discovered only through player complaints.
