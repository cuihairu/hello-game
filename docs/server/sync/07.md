# Replay, Spectating, and Adjudication

## Category

server / sync subtree. Node positioning: replay is the most honest acceptance criterion of a sync system -- the recording method is fixed together with the sync model, the evidence chain, spectating is not forwarding, and arbitration and player replays are kept separate.

## Definition


Replay and spectating look like add-on features, but in fact they are the most honest acceptance criteria of a sync system. A system that cannot stably reconstruct key session processes can hardly prove its adjudication is trustworthy and can hardly support esports, report handling, support tickets, and online retrospectives. Many teams think these capabilities can be added later, and once the underlying layer leaves no reconstructable evidence, almost nothing can be patched up afterward.

## Problem

Unable to stably reconstruct a session process, you cannot prove adjudication is trustworthy, and esports, reports, support, and retrospectives all lack support; if the underlying layer leaves no reconstructable evidence, almost nothing can be patched up afterward. Replay is often treated as an add-on feature, when in fact it is the acceptance criterion.


### Why replay is not icing on the cake

Player complaints, match disputes, cheat reports, and settlement questions all ultimately ask the same thing: what actually happened. Saving only the final result is not enough, because disputes often arise in the process:

- Did a given skill actually hit.
- Was a given control purged.
- Did a given player disconnect at a key frame.
- Was a given piece of damage a normal crit or an anomalous trigger.

Without process evidence, teams ultimately can only guess with log fragments and blurry recordings.

### Why the replay recording method must be fixed with the sync model

Different sync models have different natural friendliness for replay:

- Frame sync or lockstep: input replay is more natural but depends extremely on determinism.
- Server-authoritative state sync: state and event replay is more common, but snapshot granularity must be designed well.
- Hybrid models: usually need inputs, events, and snapshots recorded jointly.

So replay capability cannot be ignored once the sync model is fixed. It is inherently part of the same design chain.

### Three common replay recording methods

### Input stream replay

Record the whole session's input sequence and then re-simulate the combat using the same set of logic.

The advantage is a small volume and natural fit with frame sync. The downside is an extremely high determinism requirement, and any divergence drags the whole replay off track.

### State snapshot replay

Periodically record key state and rebuild the process during replay from the snapshots.

The advantage is more intuitive and lower dependence on full determinism. The downside is higher storage cost and a stronger test of state trimming design.

### Input plus checkpoint hybrid

This is the safer choice for many real projects: periodically save checkpoints and record inputs or key events between them. This way it does not rely on full input replay for very long durations, nor does it blow up storage.

### What should a decent evidence chain cover at minimum

A safer replay or adjudication evidence chain typically includes at minimum:

- Room basics and version information.
- The initial state or the most recent checkpoint.
- Input sequences, key events, or state deltas.
- Key frame numbers and timestamps.
- Adjudication results, e.g. hits, damage, death, and resource changes.
- Link events such as disconnect, reconnection, proxy, and pause.

Without these, many disputes cannot be strictly explained.

### Spectating is not "sending the room data again"

Spectating has different goals from replay. Replay focuses on reproduction; spectating focuses on real-time-ness, bandwidth, fairness, and isolation. Common questions include:

- How much delay is reasonable for spectators.
- Whether to allow seeing fog of war, hidden information, and a player's viewpoint.
- Whether the spectating link can affect main session performance.
- Whether spectating data goes directly through the main room broadcast or has an independent forwarding layer.

If spectating is simply hung off the main room broadcast, room performance and bandwidth are usually both affected.

### Arbitration evidence and player replays are not the same thing

It is best to keep the following two things separate in engineering:

- Arbitration evidence: for support, risk control, R&D, and esports arbitration, emphasizing accuracy and attributability.
- Player replays: for content distribution and retrospective experience, emphasizing watchability and loading efficiency.

The former can be harder and more raw; the latter usually needs presentation reconstruction, UI cleanup, and viewing experience optimization. Doing them mixed together usually makes both turn out poorly.

### Replay, reconnection, and spectating should reuse the same set of underlying infrastructure

Although these capabilities have different uses, their underlying infrastructure is often reusable:

- State checkpoints.
- Input or event logs.
- Frame numbers and timing identifiers.
- Combat object serialization.
- State hashing and verification tools.

If this infrastructure was originally designed for reconnection recovery, then replay and spectating will usually also be much easier. Conversely, if reconnection cannot recover stably, replay and spectating are probably not stable either.

### Spectating delay and fairness cannot be avoided

In competitive products, spectating does not end once the technical implementation is done; it must also answer fairness questions:

- Must spectating be delayed by several seconds or several frames.
- Can spectators get complete room information.
- Whether to allow a player's friends to spectate in real time.
- Whether to isolate and audit the spectating link.

If these are not defined up front, spectating becomes a new cheating surface.

### Toolchains are usually more important than the replay player

Many teams make replay files but not the tools that actually help triage. Safer practices usually include:

- Being able to jump to a specified frame.
- Being able to view key object state at that frame.
- Being able to view the timing of skills, Buffs, damage, and control.
- Being able to view inputs, default inputs, proxy, and disconnect records.
- Being able to compare two endpoints' hashes or two replay differences.

What truly determines team efficiency is often not "can it be played" but "can it be figured out."

### Common pitfalls

- Treating replay as a content capability added after launch, when the underlying layer left no reconstructable evidence at all.
- Implementing spectating as a direct bypass of the main link, ending up affecting session performance and still not getting a stable viewing experience.
- Mixing arbitration evidence and player replays into one set, ending up neither accurate enough nor presentable enough.
- Having only replay data but no frame-level tools, so after a dispute it still can only be guessed.

What replay, spectating, and adjudication really need to design up front is not "how to play the recording" but how to leave behind process evidence for the sync system that is stable enough and verifiable enough.

### Practical case: triaging "when the dispute happens, the replay cannot be pulled up" post-hoc evidence chain

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes the page's "Why the replay recording method must be fixed with the sync model," "What should a decent evidence chain cover at minimum," and "Spectating is not 'sending the room data again'" into deep water: only when adjudication needs it is there no evidence -- this is the triage of replay being treated as an add-on feature, and also a full unfolding of "replay is the acceptance criterion."

**Background and symptoms**: after a version iteration of an esports server, **1200** historical sessions could not be reconstructed, the finals' skill hit dispute could only be guessed with log fragments, and a single dispute took **3** days to adjudicate; spectating hung directly off the main room broadcast, occupying **40**% of room bandwidth, and main session P99 rose along with it.

### Step 1: symptoms and caliber -- first see which link of evidence is missing

Dispute caliber: **1200** old sessions lack version and checkpoint information, input stream replay diverges after the upgrade, and the hit conclusion is not reproducible.

Spectating caliber: spectating and the session share the main room broadcast, **40**% of room bandwidth on esports days is occupied by spectating, and the main session's message queue lengthens accordingly.

### Step 2: layered attribution -- triage along the page's evidence chain list

Item-by-item comparison: input stream replay "any divergence drags the whole replay off track," and the version upgrade hit exactly that; the evidence chain lacks both "initial state or most recent checkpoint" and "disconnect, reconnection, proxy, and pause" types; spectating goes directly through the main room broadcast. All three are present, and the determinism divergence one is the largest proportion.

### Step 3: root cause -- replay was treated as a content capability to add after launch

This page's Problem says it directly: replay is often treated as an add-on feature, when in fact it is the acceptance criterion; if the underlying layer leaves no reconstructable evidence, almost nothing can be patched up afterward. When the sync model was finalized, the recording method was not looked back at, and the six evidence chain items were missing two; spectating was also not designed separately -- if spectating is simply hung off the main room broadcast, room performance and bandwidth are usually both affected. Adjudication, performance, and viewing all collapse at once.

### Step 4: remediation and backfill -- front-load the evidence chain into sync design

1. Fix the recording method with the sync model: switch to input-plus-checkpoint hybrid recording, periodically save checkpoints, and record inputs and key events between them.
2. Fill in the six evidence chain items: room version, checkpoints, inputs and events, frame numbers and timestamps, adjudication results, and disconnect/reconnection events each written to disk.
3. Independent spectating forwarding: spectating goes through an independent forwarding layer with forced delay, no longer hung off the main room broadcast; arbitration evidence and player replays produced as two separate sets.

Verification ledger: reconstructable sessions **0%** -> **100**%; single dispute adjudication **3** days -> **2** hours; spectating's share of room bandwidth **40%** -> **9**%; esports-day main session P99 restored within budget.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Recording method fixed together | When the sync model is fixed, fix the replay recording method together, with hybrid recording as the base | Why the replay recording method must be fixed with the sync model |
| Six evidence chain items | Version, checkpoints, inputs and events, frame numbers and timestamps, adjudication results, and link events each written to disk | What should a decent evidence chain cover at minimum |
| Independent spectating forwarding | Spectating goes through an independent forwarding layer and delay, not hung off the main room broadcast | Spectating is not "sending the room data again" |
| Arbitration and replay separated | Arbitration evidence seeks accuracy and attributability, player replays seek watchability | Arbitration evidence and player replays are not the same thing |

### Three lessons from the case

1. **Replay is the acceptance criterion, not a content feature**. If the underlying layer leaves no reconstructable evidence, almost nothing can be patched up afterward.
2. **The recording method must be fixed with the sync model**. Patching recording after the sync model is finalized means the version divergence in between is enough to drag the whole replay off track.
3. **Spectating is not "sending the room data again"**. Hanging it off the main link drags down room performance and leaves a new cheating surface for spectating.
