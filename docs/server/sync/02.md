# Sync Model

## Category

server / sync subtree. Node positioning: the essence of the sync model is adjudication authority -- authoritative state sync, input lockstep, and hybrid approaches are matched to the problem, not classified by "send inputs or send state."

## Definition


The sync model does not answer an abstract theoretical question, but rather how this battle converges into one result that all participants can accept and that the platform can hold accountable for. Whether you send inputs, state, events, or snapshots is only a surface difference; what truly carries weight is who holds adjudication authority, when consistency is established, how much the client can do ahead, and which complexities local and server each bear.

## Problem

If you start work without fixing the sync model and just go by intuition -- who holds adjudication authority, when consistency is established, how much the client can do ahead, how complexity is divided -- these four questions unanswered, sending inputs or sending state is only surface, and the team will repeatedly tear down and rebuild based on misjudgment.


### Why the sync model must be fixed first

The sync model is not an implementation detail that can be swapped out casually later. It affects almost every core system:

- Whether skills depend on strict frame numbers and determinism.
- Whether character movement allows local feed-forward and correction.
- Whether the Buff and attribute systems can be partially simulated on the client.
- Whether replay records inputs or records state.
- Whether reconnection pulls a snapshot or catches up frame by frame.
- Whether anti-cheat relies on authoritative adjudication or post-hoc auditing.

So the later the sync model is chosen, the larger the scope of rework.

### Do not classify only by "send inputs or send state"

A more useful way to understand sync models is to look at them across several harder dimensions at once:

- Authority attribution: the final result is decided by the client, the host, a coordinator server, or an authoritative server.
- Sharing granularity: what is synced is full state packets, key events, input sequences, or periodic snapshots.
- Consistency timing: achieved immediately on input, achieved after some delay in frames, or performed locally first and converged on the server later.
- Client responsibilities: only display the authoritative result, or participate in full simulation.
- Cheating surface: how much the client can forge, how much the server can verify.

After looking at it this way, you realize a so-called "sync model" is not three labels but a set of engineering trade-offs.

### Common model one: server-authoritative state sync

This is the most common mainstream approach today. The server holds the authoritative world state, clients send inputs or action requests, and after the server computes it broadcasts key results or state updates. Clients typically do limited prediction and interpolation but do not hold final adjudication authority.

Its advantages are clear:

- Anti-cheat and arbitration are easier to establish.
- Clients do not need strict determinism among themselves.
- Reconnection more easily goes through snapshot recovery.
- Content teams more easily accept the "the server decides" organization.

Its costs are equally direct:

- Local feel must be built up through prediction, compensation, and interpolation.
- Broadcast pressure and state compression costs are relatively high.
- The experience can be very poor when corrections are frequent.
- Server logic and network link pressure are relatively high.

A large number of ARPGs, MMOs, shooters, and most online projects emphasizing server authority fall closer to this category.

### Common model two: input lockstep / frame sync

The core idea of this class of models is not to sync state but to sync inputs. Each participant receives consistent inputs on frame N and then advances to frame N + 1 by the same logic. As long as inputs are consistent, order is consistent, and simulation is consistent, the final state should be consistent.

Its advantages are typically:

- Bandwidth is more controllable.
- Theoretically, consistency and replay are more natural.
- Key gameplay more easily revolves around the same frame number.
- Many disputes can be reduced to "are frame N's inputs and state consistent."

Its costs are also heavy:

- It demands extremely high determinism.
- Any participant falling behind can slow the entire session.
- Reconnection, frame catch-up, pause, default inputs, and proxy must be designed up front.
- Client problems more easily directly affect in-session consistency.

Frame sync is not "more advanced," but rather transfers complexity from state broadcasting to time organization and determinism control.

### Common model three: hybrid approach

In real projects, what is most common is neither pure state sync nor pure lockstep but a hybrid approach. Common mixes include:

- Core combat objects converge by frame or by event, peripheral objects go through state sync.
- Inputs are first fed forward locally, key results are then corrected by the server.
- Projectiles, skills, and hits are computed by authoritative logic, while movement and animation are performed locally first.
- Main combat inside the room goes frame sync, peripheral systems outside the room go through ordinary request-response.

The value of a hybrid approach is real: it acknowledges that different objects, gameplay, and links do not have the same fault-tolerance needs. Its risks are equally real: if the boundary is not drawn clearly, the system ends up bearing the downsides of both models at once.

### There is no "strongest model," only problem matching

Looking roughly at common project types, the sync model usually leans this way:

- Hard-real-time competitive, RTS, some fighting games, and a few room-based products are more drawn to frame sync or near-lockstep approaches.
- MMOs, ARPGs, shooters, and most multiplayer online projects more easily land on server-authoritative state sync.
- Complex hybrid projects often use different sync strategies inside/outside the session, across object levels, and across skill levels.

The deciding factors are usually not technical preference but the following harder facts:

- The tolerance boundary of players for immediate feel.
- Requirements for fairness and attributability.
- Whether the client cheating surface is acceptable.
- Whether the team has the ability to maintain determinism and debugging tools long-term.
- Whether supporting capabilities like reconnection, replay, spectating, and esports matter.

### A more useful comparison perspective

| Dimension | Server-authoritative state sync | Frame sync / input lockstep | Hybrid approach |
| --- | --- | --- | --- |
| Adjudication authority | Server centralized | Participants share or server coordinates | Layered per object |
| Bandwidth shape | More state or event broadcast | Input packets lighter | Mixed |
| Determinism requirement | Moderate | Very high | Locally very high |
| Local feel | Relies on prediction/compensation | Relies on leading frames or local feed-forward | Relies on boundary design |
| Reconnection recovery | Snapshot more natural | Needs snapshot, catch-up, default inputs | Depends on subsystem |
| Replay implementation | State and event replay more common | Input replay more natural | Usually both together |
| Cheating surface | Easier to control | Harder to control | Depends on authority boundary |

The meaning of this table is not to give standard answers, but to remind you: sync model differences manifest across the whole engineering chain, not only in what the network packets look like.

### Why many teams misjudge

The most easily misjudged reason for the sync model is that teams only see one local benefit:

- Seeing frame sync saves bandwidth but not seeing the determinism and reconnection costs.
- Seeing server authority makes anti-cheat easy but not seeing the experience cost of prediction and correction.
- Seeing a hybrid approach looks like it gets both but not seeing the boundary design and debugging cost.

If you do not include the skill system, disconnect recovery, replay, spectating, proxy, cheating, and the toolchain together in the evaluation, the final model judgment will usually be off.

### Common pitfalls

- Treating the sync model as an implementation detail that can be swapped out later.
- Understanding the sync model only through "send inputs or send state," ignoring adjudication authority, recovery semantics, and the cheating surface.
- Launching high-complexity approaches without logs, state hashing, snapshots, and visualization tools.

What the sync model really needs to fix first is not the name but the adjudication philosophy, recovery semantics, and where complexity lands.

### Practical case: triaging a sync-model misjudgment where "frame sync saved bandwidth but reconnection and disputes exploded"

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes the page's "Do not classify only by 'send inputs or send state'," "Common model three: hybrid approach," and "Why many teams misjudge" into deep water: broadcast traffic did drop, but reconnection and dispute costs went up -- this is a triage of a sync model seeing only local benefits, and also a full unfolding of "how to evaluate model selection across the whole engineering chain."

**Background and symptoms**: a room-based real-time competitive game (4v4, an RTS-and-fighting hybrid gameplay), the team chose frame sync to save bandwidth, and broadcast traffic dropped **64**% compared with the original state sync approach. One month after launch, the reconnection failure rate was **8**%, dispute tickets **600** per day, and state divergence **3** times per week -- the bandwidth cost saved was paid back many times over through three other holes.

### Step 1: symptoms and caliber -- record what was saved and what went up separately

Bandwidth caliber: broadcast traffic down **64**%, per-session bandwidth from **48** KB/s down to **17** KB/s; this benefit is real.

Reconnection caliber: reconnection failure rate **8**%, failed sessions concentrated in scenarios falling behind more than **900** frames; average recovery time for successful reconnections **41** seconds.

Dispute caliber: of **600** dispute tickets per day, **63**% were "results don't match" -- client and server state were inconsistent but both sides believed themselves normal.

### Step 2: layered attribution -- triage item by item along the page's cost list

```text
重连失败 8%  归因
  无默认输入与超时策略，整局等掉线玩家     55%  →  4.4 个百分点
  无周期检查点，重连只能逐帧补             30%  →  2.4 个百分点
  无状态哈希，分叉不自知只能重开           15%  →  1.2 个百分点
```

Item-by-item comparison: of the frame sync dependency list, the three items -- default inputs, checkpoints, and state hashing -- were all unbuilt. When a disconnected player does not submit inputs, the server does not fill in default inputs, the whole session stalls on waiting, and everyone else gets dragged along; reconnection clients patch from the breakpoint frame by frame, falling behind **900** frames or more simply cannot catch up; after a divergence there is no hash check, so the **3** divergences per week all had to be found by players' recordings.

### Step 3: root cause -- only seeing that frame sync saves bandwidth, not seeing the determinism and reconnection costs

At selection time only the bandwidth was tallied, without bringing the skill system, disconnect recovery, replay, and dispute handling together into the evaluation. Frame sync transfers complexity from state broadcasting to time organization and determinism control, and the team had no corresponding default inputs, checkpoints, or hash toolchain -- exactly the page's "seeing frame sync saves bandwidth but not seeing the determinism and reconnection costs."

### Step 4: remediation and backfill -- fill in the supporting pieces, then draw the hybrid boundary

1. Fill in default inputs and a timeout policy: when a player's frame N input times out, fill in a default input (no-op or hold direction), so the whole session no longer waits.
2. Periodic checkpoints + reconnection via snapshot: generate a checkpoint every **300** frames, reconnection preferentially loads the most recent checkpoint, then catches up on a small segment of incremental frames.
3. State hashing and divergence location: compute a key state hash every **60** frames and compare within the room, and after a divergence is found locate the earliest anomalous frame.
4. Draw the hybrid boundary: move peripheral systems such as chat, announcements, and event refresh out of the frame sync primary path to request-response, no longer occupying the frame packet.

Verification ledger: reconnection failure rate **8**% -> **0.6**%; dispute tickets **600** per day -> **80** per day; state divergence **3** times per week -> **0** times; bandwidth still holds a **60**% or greater drop -- only after the supporting pieces are filled in does frame sync's benefit truly land.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Four model questions | At selection, evaluate item by item across adjudication authority, consistency timing, client responsibilities, and cheating surface, not a single benefit | Do not classify only by "send inputs or send state" |
| Frame sync dependency list | Default inputs, input buffering, state hashing, checkpoints, and frame catch-up policy as pre-launch items verified item by item | Common model two: input lockstep / frame sync |
| Hybrid boundary | Core combat goes frame sync, peripheral systems go request-response, the boundary written into the architecture diagram | Common model three: hybrid approach |
| Misjudgment checklist | Selection review includes a two-column ledger of "what was saved, what went up," reconnection and dispute costs must be listed | Why many teams misjudge |

### Three lessons from the case

1. **Sync model selection must tally the whole chain, not just the bandwidth line**. Saving **64**% of broadcast traffic brought **8**% reconnection failure and **600** dispute tickets per day -- a local benefit is not a benefit.
2. **Complexity does not disappear, it only transfers**. Frame sync swaps the complexity of state broadcasting for the complexity of determinism and reconnection; without a corresponding toolchain, the transferred cost cannot be paid back.
3. **A model lacking supporting pieces has its benefit eaten by its own gaps**. After default inputs, checkpoints, and state hashing are filled in, frame sync's bandwidth benefit is retained -- the model and its supporting pieces are one body.
