# Prediction, Compensation, and Correction

## Category

server / sync subtree. Node positioning: bridging between "waiting for the server is sluggish" and "trusting the client loses control" -- the boundaries of prediction, compensation, and correction: which state can steal time, and correction is not only teleporting back.

## Definition


If you wait completely for server results before presenting, real-time games feel sluggish; if you completely trust the client, the local experience is smooth but adjudication and anti-cheat break. Prediction, compensation, and correction are the set of engineering mechanisms bridging between these two ends. The difficulty is not in the concept but in the boundaries: which state can steal time, which must wait for authority, and how to pull local feed-forward back into convergence after the server returns.

## Problem

The difficulty is not in the concept but in the boundaries: which state can steal time, which must wait for authority, and how to pull local feed-forward back into convergence when the server returns. With unclear boundaries, real-time feel and adjudication anti-cheat both collapse -- and prediction in frame sync is not the same thing as prediction in state sync.


### Why you must steal time

When humans operate, their perception of latency does not wait for the server's favor. As long as character movement, shooting, casting skills, reloading, melee hits, and camera feedback all wait a round trip to the server, the feel will definitely collapse.

So the sync system must answer three things at once:

- What does the client play ahead.
- How does the server compute the true result.
- How is the deviation corrected when the true result returns.

All three are indispensable.

### What prediction, compensation, and correction each do

- Prediction: the client advances some future presentation or logic based on local inputs and known state.
- Compensation: the system reduces the impact of network latency on experience and judgment through input windows, interpolation, server rewind, or other mechanisms.
- Correction: when the server's authoritative result returns, it pulls the state deviation between client and server back into convergence.

Many discussions collapse the three into "client prediction," which is not enough. Prediction solves playing ahead, compensation solves latency itself, and correction solves the deviation the first two necessarily bring.

### Not all state should be predicted

Safer practice usually layers state:

- Suitable for bold prediction: local movement, orientation, startup motions, some non-critical animation feedback.
- Suitable for limited prediction: skill startup, projectile launch, melee swing start, local hit effect pre-play.
- Better suited for authoritative confirmation: resource deduction, death, final landing point of knockback and launch, key control, settlement-related state.

The closer to win/loss adjudication, the more easily exploitable by cheating, and the more dependent on complex collision and multiplayer interaction, the less suitable a state is for being fully decided locally.

### Common prediction and compensation techniques

### Local input feed-forward

When a player presses a movement key, the local character immediately starts moving, and the server later gives the authoritative position. Most common for movement and feel-sensitive action feedback.

### Action and skill startup pre-play

After sending a cast request, the client first plays the startup motion and startup effects. If the server judges it failed, it then interrupts or rolls back.

### Remote object interpolation and extrapolation

For other players' characters, this is usually not predicting "what they're going to do" but interpolating between the two most recent authoritative states, with short-time extrapolation when necessary. This is not local input prediction but is also stealing time.

### Server rewind judgment

In shooting and some hit judgments, the server may look back at historical positions based on the fire time reported by the client to compensate for link latency. This is compensation, not client prediction, but it often appears together with prediction.

### Correction is not only "teleport back"

After the server result returns, correction has many levels:

- Hard correction: directly change the client state to the server state, simple and brutal but the experience easily breaks.
- Smooth correction: interpolate to converge to the authoritative state in a short time, visually more natural but more complex to implement.
- Categorized correction: different states use different methods, e.g. smooth position recovery, immediate authority for death, interrupting active skills by rule.
- Rollback replay: in heavier approaches, the client rolls back to a past authoritative point and then replays subsequent inputs.

None is always better; the key is not to treat all deviations as one kind of deviation.

### Prediction in frame sync and state sync is not the same

In server-authoritative state sync, prediction is usually to compensate for the RTT between client and server, focusing on local feel and server correction.

In frame sync systems, the system more often relies on leading frames, input buffering, and unified frame numbers to absorb part of the latency. Here the prediction space is usually smaller, but not nonexistent. Some projects still feed forward on action startup, camera feedback, and some local presentation.

So "doing frame sync means no prediction" is not accurate; the more accurate statement is that frame sync puts more latency handling into the input window and shared frame advancement, so the prediction boundary is usually more conservative than server state sync.

### What disputes does server compensation most easily provoke

If compensation is not designed clearly, it directly becomes "I clearly dodged but still got hit" in players' mouths. The most typical case:

- The server, to accommodate the shooter's experience, rewinds the target's past position.
- The client already locally sees itself having moved away.
- Both sides think they are right.

Therefore compensation strategy must match the gameplay. The more competitive, the more it must be defined up front:

- How long rewind is allowed at most.
- Which kinds of skills allow rewind judgment, which do not.
- How movement, dash, and invulnerability frames participate in judgment.
- Whether the logs can reconstruct the timing evidence at the time.

Compensation is not "the more the better," but rather one where both experience and attributability hold up.

### A more realistic state layering

In safer projects, state is commonly split into three layers:

- Local experience layer: prioritize speed, allow short-time deviation, e.g. action startup, camera, and some movement feed-forward.
- Authoritative adjudication layer: must be accurate, better slow than wrong, e.g. damage, death, and key control.
- Presentation convergence layer: responsible for smoothing the differences between the first two layers, e.g. position interpolation, effect cancellation, and delayed hit replay.

Once these three layers are not separated, the system easily conflates "present first" with "adjudicate first" into one thing.

### Prediction chains must have logs

Prediction problems fear nothing more than lacking evidence. At minimum you should record:

- The local time and logical frame when the client sends an input.
- The time and processing frame when the server receives the input.
- The client's local predicted result.
- The server's final authoritative result.
- The timing and magnitude of correction triggers.

Otherwise, when a player says "I clearly already dodged," engineers can only guess by eyeballing a recording.

### Common pitfalls

- Infinitely expanding the prediction scope, eventually even key adjudication being played locally first, with the server reduced to a formal confirmer.
- Forcing writes back the moment the server result returns, without smoothing or categorization, so the experience feels like the system is fighting the player for control.
- Only staring at local feel, not seeing the side effects compensation strategy brings to fairness and arbitration.
- No timing logs, so when the prediction chain breaks it can only be guessed.

What prediction, compensation, and correction really need to solve is not "how to hide latency" but how to steal some of the latency from the player's hands without giving up adjudication authority and attributability.

### Practical case: triaging a rewind-judgment dispute where "I clearly dodged but still got hit"

> This case is a demonstration example (not drawn from a real project), with numbers rounded and simplified. It pushes the page's "What disputes does server compensation most easily provoke," "Correction is not only teleporting back," "A more realistic state layering," and "Prediction chains must have logs" into deep water: the compensation window itself is not a bug, but the window and client-visible state not sharing the same caliber is -- this is the adjudication triage for real-time competitive, and also a full unfolding of "compensation is not the more the better, but one where both experience and attributability hold up."

**Background and symptoms**: a PVP shooter mobile game with dash/dash-in skills, **200,000** DAU and **600,000** sessions per day (an average of **12** shots per session). Server hit judgment uses **rewind judgment** based on the fire time reported by the client, with a rewind window of **200** milliseconds; dash skills carry **120** milliseconds of invulnerability frames. The first week after launch was flat across the board, until two new ranged skills with dashes were added, and customer support tickets of "I clearly dodged but still got hit" began climbing, stabilizing at **1800** per day, while the hit rate caliber **did not change at all** -- exactly the hardest kind of signal to chase: business metrics all green, player feel collapsing.

### Step 1: symptoms and caliber -- first turn "I clearly dodged" into a statable ticket tag

Dispute caliber: customer support tickets judged as "the client screen already shows a dodge, the server still records a hit." **1800** per day, accounting for **0.1**% of all daily hits -- the proportion looks low, but it is simultaneously an **arbitration risk**: once this kind of ticket is substantiated, adjudication authority becomes numerology in players' eyes.

Hit rate caliber: server rewind hits / shot requests = **25**% (**7.2 million** shots all day, **1.8 million** hits). Laying the two calibers side by side first is what shows the problem is not in whether hit judgment is "accurate" but in "on what basis it judged this way."

### Step 2: layered attribution -- decompose disputes along the three state layers

Checking each disputed ticket's attribution layer by layer along the page's state layering:

```text
争议工单 1800 单/日  归属
  回溯口径（无敌帧未排除）    88%  →  1584 单
  硬纠正瞬移（观感争议）        9%  →   162 单
  其他（表现/状态不同步）        3%  →    54 单
```

- Local experience layer: no anomaly. Startup motions, camera, and dash pre-play are all running as designed, and players truly **dodged locally** -- this confirms the disputed ticket caliber is fine.
- Authoritative adjudication layer: **88**% of disputes concentrate here, all pointing to the same rule: when rewinding to historical positions, **invulnerability frames are not in the exclusion set**. At the very moment the player pressed dash on the client, the server was looking back at the target's position **200** milliseconds ago.
- Presentation convergence layer: **9**% are appearance disputes caused by hard correction -- the server result returned and directly wrote back the position, so what the player saw was a teleport. This is not a misjudgment but turns an otherwise acceptable judgment into a complaint.

Timing comparison (the same shot, shooter P99 RTT **80** milliseconds):

```text
  客户端  t=0ms     按下射击，同时闪现进入无敌帧（120ms）
  服务端  t=80ms    收到请求，回看 200ms → 取 t=-120ms 的受击方位置
  判定    t=80ms    命中：t=-120ms 受击方在弹道上，无敌帧未进入排除集合
```

### Step 3: root cause -- the window is longer than the dodge lead time a player can see

There is only one root cause, but it has two interlocking parameters: rewind window **200** ms > invulnerability frames **120** ms + P99 RTT **80** ms. In other words, to accommodate the shooter's experience the server opened the judgment window to a segment the player **simply could not see in time**; and precisely in that segment, the client had already made a visible promise of "I dodged" using invulnerability frames. Neither side wrote the code wrong; it is that **the judgment caliber and the client-visible state were not aligned**.

The accompanying secondary problem is no basis to check: when a disputed ticket needs review, the team has neither the client-reported fire time and logical frame nor the server's processing frame and correction magnitude, arbitration accuracy is only **61**%, and the remaining **39**% can only be guessed by eyeballing a recording, finally tallied up as "players feel something is wrong."

### Step 4: remediation and backfill -- three changes, align the window to P99

1. Shrink the rewind window from **200** ms to **80** ms, aligned to P99 RTT: judgment only looks back at the segment the link already consumed, not at a future the player cannot see.
2. Include invulnerability frames in the rewind exclusion set, and write the participation of dash, teleport, and invulnerability frames in judgment per skill into the judgment rule table, no longer inherited by default from the rewind implementation.
3. Change hard correction to smooth correction: movement converges smoothly, death and key control remain immediately authoritative, layered per the three layers on this page.

Verification ledger: dispute tickets **1800** per day -> **180** per day, dispute rate **0.1**% -> **0.01**%; hit rate **25**% -> **24**% (after the window narrowed, rewind hits dropped slightly, and this drop is **deliberate**); arbitration ticket review accuracy **61**% -> **97**%, on the basis of filling in five kinds of timing logs so each disputed ticket can reconstruct the timing evidence item by item.

**Backfill checklist**:

| Backfill item | Action | Backfill location |
|-----|------|--------|
| Three-layer state split | The technical review template reviews the authoritative adjudication layer and the presentation convergence layer in separate columns, eliminating the conflation of "present first + adjudicate first" | A more realistic state layering |
| Compensation caliber matched to gameplay | Per-skill judgment rule table: rewind cap, whether rewind is allowed, and how dash/teleport/invulnerability frames participate in judgment | What disputes does server compensation most easily provoke |
| Correction level specification | Movement converges smoothly, death and key control immediately authoritative, written as a correction specification rather than ad-hoc judgment everywhere | Correction is not only "teleport back" |
| Five kinds of timing logs | Full retention of combat logs, **100**% of disputed tickets can reconstruct timing: the client's local time and logical frame when sending an input, the server's receive time and processing frame, the client's local predicted result, the server's final authoritative result, and the timing and magnitude of correction triggers | Prediction chains must have logs |

### Three lessons from the case

1. **The rewind window must not exceed the dodge lead time a player can see**. The window is set by P99 RTT, not by "feels better" guesswork; the page says "how long rewind is allowed at most" must be defined up front, and when defining it, set it by link metrics, not by wish.
2. **Authoritative judgment must share the same caliber as client-visible state**. If the client dares to make a promise to the player using invulnerability frames, the server must count them in the exclusion set; if promises and judgment do not share a caliber, adjudication authority becomes numerology.
3. **Dispute rate and hit rate must be watched together**. When hit rate **25**% stays put, fairness is already collapsing -- missing one of the "feel and fairness" metrics leaves monitoring with only half an eye.
