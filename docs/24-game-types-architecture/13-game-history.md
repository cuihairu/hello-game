# 游戏发展史与技术演进

了解游戏技术的发展历程，才能理解为什么今天的架构是这样设计的。本章从游戏诞生讲起，梳理玩法演进、技术变革和网络协议的发展脉络。

## 1. 游戏的诞生与早期发展（1950s-1970s）

### 1.1 电子游戏的黎明

| 年代 | 里程碑 | 技术 | 意义 |
|------|--------|------|------|
| 1958 | Tennis for Two | 模拟计算机 + 示波器 | 第一个交互式电子游戏 |
| 1962 | Spacewar! | PDP-1 小型计算机 | 第一个多人对战游戏 |
| 1971 | Computer Space | 硬连线逻辑 | 第一个商业街机 |
| 1972 | Pong | 雅达利 | 街机游戏黄金时代开始 |
| 1978 | 太空侵略者 | Z80 CPU | 日本游戏产业崛起 |

### 1.2 技术特点

```
早期游戏（1950s-1970s）：
- 硬件直接编程，没有操作系统
- 游戏逻辑固化在硬件中
- 单机为主，物理对战（街机并排）
- 无网络概念，无持久化
```

### 3.2 MUD：文字网络游戏的开端

MUD1（Multi-User Dungeon，1978）是第一个多人在线游戏，使用 **TCP Telnet** 协议：

```
> 你进入了一个黑暗的洞穴。
> 你看到一只哥布林！
> 攻击哥布林
> 你对哥布林造成了 15 点伤害！
> 哥布林攻击了你，你受到 8 点伤害。
> 哥布林被击败了！你获得了 50 经验值。
```

**MUD 的技术特点**：
- 纯文本交互
- 服务端权威（所有逻辑在服务端）
- TCP 长连接
- 支持多人同时在线
- 简单的房间系统

### 3.3 DOOM：局域网对战的开端

DOOM（1993）开创了 FPS 对战模式，使用 **IPX 协议**：

```
DOOM 网络架构：
- 服务器/客户端混合（Host Player）
- 对等传输（Peer-to-Peer）
- 客户端预测（减少延迟感）
- 只同步输入，不同步状态（帧同步雏形）
```

### 3.4 Quake：互联网对战的开端

Quake（1996）是第一个真正意义上的互联网 FPS：

```
Quake 网络架构：
- 独立服务器（Dedicated Server）
- UDP 传输（放弃 TCP 的可靠性）
- 客户端预测 + 服务端校验
- 位置插值（平滑其他玩家移动）
- 延迟补偿（公平性）
```

**为什么 Quake 选择 UDP？**

```
TCP 的问题：
- 重传机制导致延迟抖动
- 有序交付阻止乱序处理
- 拥塞控制不适合实时游戏

UDP 的优势：
- 无重传（丢包就丢了）
- 无序交付（先到先处理）
- 无拥塞控制（低延迟）
- 应用层自己控制可靠性
```

## 6. 网络协议详解

### 6.1 HTTP：请求-响应模型

```
客户端                服务器
  │                      │
  │──── GET /data ──────→│
  │                      │
  │←──── 200 OK ─────────│
  │                      │

特点：
- 无状态
- 请求-响应模式
- 适合：登录、商店、背包操作
- 不适合：实时游戏、聊天推送
```

**HTTP 在游戏中的使用场景**：
- 登录认证
- 商店/背包操作
- 活动/公告
- 资源下载
- 配置更新

### 6.2 WebSocket：全双工长连接

```
客户端                服务器
  │                      │
  │── HTTP Upgrade ────→│
  │←── 101 Switching ───│
  │                      │
  │←── 双向通信 ────────→│
  │                      │

特点：
- 全双工通信
- 低延迟
- 适合：实时游戏、聊天、推送
- 缺点：基于 TCP，延迟较高
```

**WebSocket 在游戏中的使用场景**：
- 实时聊天
- 房间管理
- 排行榜推送
- 活动通知
- 轻量级实时游戏

### 6.3 SSE（Server-Sent Events）：服务端单向推送

```
客户端                服务器
  │                      │
  │── GET /events ─────→│
  │                      │
  │←── data: event1 ────│
  │←── data: event2 ────│
  │←── data: event3 ────│
  │                      │

特点：
- 服务端单向推送
- 基于 HTTP，兼容性好
- 自动重连
- 适合：通知、日志流、实时数据
- 不适合：需要客户端发送消息的场景
```

### 6.4 MQTT：轻量级消息协议

```
发布/订阅模型：

发布者 ────→ Broker ────→ 订阅者1
              │
              └──────→ 订阅者2

特点：
- 极轻量（最小2字节头）
- 支持 QoS（0/1/2）
- 发布/订阅模式
- 适合：物联网、消息推送、低带宽场景
```

**MQTT 在游戏中的使用场景**：
- 公告/通知推送
- 跨服消息
- 物联网游戏（智能家居联动）
- 低带宽场景

### 6.5 TCP：可靠传输

```
客户端                服务器
  │                      │
  │── 三次握手 ────────→│
  │←── SYN-ACK ─────────│
  │── ACK ─────────────→│
  │                      │
  │── 数据包1 ─────────→│
  │── 数据包2 ─────────→│  ← 有序交付
  │←── ACK ─────────────│  ← 确认机制
  │                      │

特点：
- 可靠传输（重传、确认）
- 有序交付
- 流量控制
- 适合：登录、重要操作
- 缺点：延迟较高（重传等待）
```

**TCP 在游戏中的使用场景**：
- 登录/认证
- 重要操作（购买、交易）
- 配置更新
- 非实时游戏（棋牌、回合制）

### 6.6 UDP：低延迟传输

```
客户端                服务器
  │                      │
  │── 数据包1 ─────────→│
  │── 数据包2 ─────────→│  ← 无序
  │                      │  ← 不等待确认
  │── 数据包3 ─────────→│  ← 丢包就丢了
  │                      │

特点：
- 无连接
- 无重传
- 无序交付
- 低延迟
- 适合：实时游戏、语音
- 缺点：不可靠
```

**UDP 在游戏中的使用场景**：
- FPS/TPS（CS:GO、和平精英）
- MOBA（王者荣耀、LOL）
- 格斗游戏
- 竞速游戏

### 6.7 KCP：可靠 UDP

```
KCP = UDP + 可靠性 + 低延迟

特点：
- 基于 UDP 实现可靠传输
- 比 TCP 更低的延迟（牺牲带宽）
- 可调参数（RTO、重传策略）
- 适合：实时游戏、对延迟敏感的场景

KCP vs TCP 延迟对比：
TCP:  100-200ms（丢包重传等待）
KCP:  30-80ms（快速重传，不等ACK）
```

### 6.8 协议选择决策树

```
游戏需要什么？
│
├── 实时性要求高（< 50ms）
│   ├── 需要可靠性 → KCP
│   └── 不需要可靠性 → UDP
│
├── 实时性要求中等（50-200ms）
│   ├── 双向通信 → WebSocket
│   └── 服务端推送 → SSE
│
├── 实时性要求低（> 200ms）
│   ├── 请求-响应 → HTTP
│   └── 消息推送 → MQTT
│
└── 重要操作（不能丢）
    └── TCP
```
