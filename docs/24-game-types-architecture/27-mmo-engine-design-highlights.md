# Mainstream MMO Server Engines: Eight-Angle Design Analysis and Transferable Highlights

> Verified on 2026-10-19. This document compares BigWorld, KBEngine, Project Darkstar/RedDwarf, Pitaya (Go), Unreal dedicated server, and NetEase Pomelo. They are not the same class of product: Unreal is a game engine network layer, Pitaya/Pomelo are distributed server frameworks, RedDwarf is a transactional Java server platform; "the engine does not provide it" is not inferred into "the project cannot implement it".

## BigWorld

### The eight angles

1. **Failure recovery**: the old programming guide can be confirmed to treat player entity persistence and database disaster recovery as server responsibilities, and it also introduces secondary databases and snapshot/consolidation tooling; but that is not the same as a WAL, a transaction log, or per-input rollback. The exact recovery order, RPO/RTO and partition arbitration for a BigWorld 14.4.1 CellApp/BaseApp crash are all unverified. Sources: [Server Programming Guide §9][bw-db], [Server Operations Guide][bw-ops].
2. **Scale-out**: BigWorld's representative approach is one Space cut into multiple Cells, with CellApps hosting Cells; CellAppMgr moves BSP boundaries by load, offloads entities across boundaries, and uses ghosts to keep the data copies adjacent Cells need. The benefit is that one large space can scale horizontally by adding CellApps; the costs are boundary synchronization, migration and ghost traffic, and a hotspot that boundary movement cannot spread is still a bottleneck. This conclusion cites only the old mirror/guides and does not extrapolate to 14.4.1. Sources: [BigWorld BSP-related source files (2.0.1 mirror)][bw-bsp], [Cell/Space Guide][bw-cell].
3. **Hot update**: the archived programming guide has Python script reload APIs/flows; that is an update of behavior code, and does not mean that changing entity property types, network fields or DB schema can migrate safely without downtime. The costs and guarantees of the latter are unverified. Source: [BigWorld scripting guide][bw-reload].
4. **Debug observability**: the public old source has Watcher/Nub and ForwardingWatcher paths, allowing cross-component watcher query/set; it is a development/operations diagnostic interface, not Prometheus long-term time series, distributed tracing or auditing. The version-specific coverage of AOI visualization and recording capability is unverified. Sources: [WatcherNub][bw-watcher], [ForwardingWatcher][bw-forward].
5. **Programming model**: DataDescription/entity declarations coexist with Python entity scripts; methods are declared per execution context such as Base, Cell and Client, reducing the need for business scripts to re-implement cross-side forwarding. The corresponding cost is that the same entity behavior requires understanding multi-side copies, Mailbox/EntityCall and script lifecycles. Version boundaries in the [BigWorld guide][bw-guide].
6. **Network layering**: the BigWorld 2.x programming guide, when comparing secondary DB consolidation in its database chapter, explicitly states that inter-server-process communication uses UDP; the same guide/source mirror shows its message definitions and binary streams are engine-own formats. The exact TCP/UDP mix, reliable transport strategy and serialization compatibility rules of 14.4.1 toward clients are unverified locally. Sources: [database and communication chapter][bw-db], [2.0.1 property stream implementation][bw-property-stream].
7. **Permissions and anti-cheat**: server authority is the premise of its entity execution model; the archived guide specifically warns against trusting arbitrary Python parameters from clients and allows a custom physics validator. Game logic still has to validate speed, cooldowns and resource changes; a generic anti-cheat detection/ban loop is unverified. Sources: [Client method/security guidance][bw-client-method], [Physics validation][bw-physics].
8. **Billing and operations**: what is provable is server configuration, component runtime tools, database/secondary-database tooling. There is insufficient evidence for generic multi-zone merges, event editors and billing settlement; treat these as game-project/operations-platform responsibilities. Source: [Server Operations Guide][bw-ops].

### Transferable design highlights

| Highlight | What problem it solves | Implementation essentials (evidence) | When it is worth copying | When it does not apply |
|---|---|---|---|---|
| BSP spatial partitioning + ownership offload | One process hosting a whole map hits CPU/memory limits | BSP leaf nodes correspond to Cells, load drives the split boundaries, and entity control is handed over; [2.0.1 `internal_node.cpp`][bw-bsp], [Cell concept guide][bw-cell] | Very large continuous worlds, entity-movement-heavy MMOs that can accept spatial boundary management | Small rooms/instances suffice; cross-Cell sync costs are high, the map is extremely uneven and cannot migrate |
| Adjacent ghosts as boundary read replicas | Interactions between entities near a Cell boundary need cross-process state reads but not a sync RPC every time | Maintain ghosts only in the neighboring regions that need them, then let Witness/AOI pick client-visible state; [Ghost system][bw-ghost] | The map really spans multiple space workers and needs low-latency boundary awareness | Pure room servers, globally strongly consistent transactions, or when replication costs exceed interaction benefits |

## KBEngine

### The eight angles

1. **Failure recovery**: on the Cell side `backupCellData()` compares a digest of persistent properties and, when changed, backs Cell state up to Base via a message: `/home/cui/workspaces/kbengine/kbe/src/server/cellapp/entity.cpp:1129-1180`. The BaseApp game tick calls the Backuper, processing entities in batches by `backupPeriod`: `.../kbe/src/server/baseapp/baseapp.cpp:560-583`, `.../baseapp/backuper.cpp:25-93`. After a CellApp dies, Base creates a `RestoreEntityHandler` and progressively restores spaces/entities: `.../baseapp/baseapp.cpp:694-729`, `.../baseapp/restore_entity_handler.cpp:89-185`. This is an in-memory copy/periodic backup, not a WAL; the state guarantee when a BaseApp crashes, or both processes are lost at once, is unverified.
2. **Scale-out**: CellAppMgr's `findFreeCellapp()` skips processes not participating in balancing and, among active candidates, picks the host first by lower load and then by fewer entities: `.../kbe/src/server/cellappmgr/cellappmgr.cpp:230-263`; new Space creation goes through that election/load-balancing path: `.../cellappmgr/cellappmgr.cpp:328-392`. This proves added CellApps share new spaces, and does not prove a running Space is automatically cut into multiple Cells; that behavior is unverified. A single-Space hotspot can be limited by a single CellApp.
3. **Hot update**: `KBEngine.reloadScript(fullReload)` reaches `EntityApp::reloadScript()`, reloading EntityDef, running `onReloadScript` and the entry script `onInit(1)`: `.../baseapp/baseapp.cpp:5090-5127`, `.../lib/server/entity_app.h:1451-1469`. A normal reload and a full reload differ in their impact on definitions/property contracts; hot-loading code does not automatically fix cached old Python objects, and does not automatically do online DB schema migration. Runtime risks live at the script reference retention points; safe-migration guarantees are unverified.
4. **Debug observability**: built-in Watcher reads process variables by path, with Profile/Logger/WebConsole; SpaceViewer connects the WebConsole to a CellApp and periodically pulls the Space/Cell entity view: `.../kbe/tools/server/webconsole/WebConsole/views_spaceviewer.py:21-90,122-136`, and the underlying viewer pushes via a timer and stream: `.../kbe/src/server/cellapp/space_viewer.cpp:35-92,161-220`. The Watcher Python client sends requests by path and parses typed values: `.../kbe/tools/server/pycommon/Watcher.py:15-40,70-140`. A generic timeline replay/trace is unverified.
5. **Programming model**: the server embeds CPython in C++ processes/entity runtimes; business entity scripts participate through Base/Cell execution contexts and callbacks; the assignment entry types of `entity_macro.h` are handled and then `onDefDataChanged` is called back: `.../kbe/src/lib/entitydef/entity_macro.h:810-825`, and Cell-side handling of the persistent dirty flag/property broadcast is at `.../cellapp/entity.cpp:658-710`. The benefit is fast script iteration with a centralized contract; the costs are C++/Python object lifecycles, GIL/old-Python dependencies and reload reference management.
6. **Network layering**: `Channel` defaults to TCP but offers a KCP subtype; KCP init uses a UDP peer and KCP parameters: `.../kbe/src/lib/network/channel.h:76-82,225-250`, `.../network/channel.cpp:233-260,338-370`. The WebSocket handshake switches to the WebSocket packet reader/filter: `.../network/channel.cpp:1060-1093`. Logical messages are framed by `Bundle::newMessage()` from the message tables and written into its own `MemoryStream`/DataType; not a protobuf-default schema: `.../lib/network/bundle.h:70-103`, `.../lib/entitydef/property.cpp:82-108` (the DataType serialization chain).
7. **Permissions and anti-cheat**: client method execution must match the contract and check parameters, and the receiving side additionally validates that the entity is alive, whether it is real, whether it has a Witness/client, and whether the target entity is in view: `.../kbe/src/server/cellapp/client_entity_method.cpp:53-113`. These are runtime boundary checks, not an anti-cheat system; speed, damage, drops and payment semantics still must be validated server-side. Client input should be treated as a request, not trusted state.
8. **Billing and operations**: WebConsole, Watcher, centralized logs, component management and DB write tooling are the operations base the engine provides; the `Baseapp` exposes a `charge` Python interface, registration visible at `.../kbe/src/server/baseapp/baseapp.cpp:440-453`, but business settlement, idempotent ledgers and payment callback validation are not automatically guaranteed by that interface. Multi-zone merges/event configuration are unverified as generic engine capabilities.

### Transferable design highlights

| Highlight | What problem it solves | Implementation essentials (evidence) | When it is worth copying | When it does not apply |
|---|---|---|---|---|
| Cell authoritative state consolidated back to Base first, then written to the DB uniformly | Avoids persisting only a stale Base mirror and losing spatial state | Cell `backupCellData()` encodes and compares digests, then sends to Base; on `writeToDB()` the Cell runs `onWriteToDB/backupCellData` first, and after Base consolidates it goes to Dbmgr: `.../cellapp/entity.cpp:1129-1180`, `.../baseapp/entity.cpp:1141-1227`, `.../dbmgr/dbmgr.cpp:1044-1066` | Entities spanning multiple subsystems that still need one clear persistence consolidation point | High-frequency full state, cross-entity atomic transactions, or when data loss within the in-memory backup period is unacceptable |
| Batched periodic backup + dirty digest | Reduces tick spikes and cross-process traffic from full syncs/repeated serialization | Process a budgeted share per tick by `backupPeriod`; the Cell-side SHA1 digest decides whether anything changed before sending to Base: `.../baseapp/backuper.cpp:25-74`, `.../cellapp/entity.cpp:1150-1180` | Entity services with a clear state RPO, a primary/replica process boundary, and acceptable periodic recovery points | Economy/transaction chains needing per-operation strong persistence or unable to accept falling back to the last backup on failure |
| Dual-metric scheduling by space load and entity count | New space allocation must not depend only on connection count or a random process pick | `Cellappmgr::findFreeCellapp()` looks at process load first, breaks ties by entity count, and reserves a no-balancing flag: `.../cellappmgr/cellappmgr.cpp:230-263` | A central manager doing limited-candidate placement with observable load metrics | Many workers across regions, or when the scheduler becomes a single-point bottleneck; layered scheduling/leases and overload rejection are needed |
| Production tooling facing spatial state directly | AOI/partition faults are hard to diagnose from logs alone | SpaceViewer periodically pulls Cell/Space/entity summaries and the WebConsole renders them over WebSocket: `.../cellapp/space_viewer.cpp:35-92,161-220`, `.../WebConsole/views_spaceviewer.py:72-115` | When spatial state has a clear topology and on-site operations tooling is needed | High-frequency visualization of millions of entities; sampling/aggregation should be used instead of unlimited detail refresh |

## OpenDarkstar / Mirrors (verifiable alternative evidence: RedDwarf Server)

### The eight angles

1. **Failure recovery**: precise OpenDarkstar/Mirrors materials are insufficient. The verifiable RedDwarf is the archived Project Darkstar successor, whose `TransactionScheduler` puts tasks into transactional execution; `TransactionImpl` provides participant prepare/commit/abort, and `WatchdogServerImpl` tracks failed nodes and marks them recovering. Whether there is a WAL/disk snapshot depends on the concrete DataStore configuration; the transaction interface must not be equated with a WAL. Sources: [RedDwarf README][rd-readme], [TransactionScheduler][rd-scheduler], [TransactionImpl][rd-txn], [Watchdog][rd-watchdog].
2. **Scale-out**: `NodeMappingService` maps identities to available nodes, and identity/service state allows coordinating cross-node resource ownership; ClientSessionService has a session relocation flow. What it scales is identity/session hosting, not automatic AOI spatial Cell splitting. Sources: [NodeMappingService][rd-nodemap], [ClientSessionService][rd-session].
3. **Hot update**: no safe mechanism for hot-swapping service logic/ManagedObject contracts was found; the semantics of deploying new applications/nodes versus migrating existing objects online have insufficient materials, so no hot-update claim is made.
4. **Debug observability**: the Profile Listener can output snapshots of thread counts, successful/total task counts and more to a server socket at a fixed period; code comments explicitly note the limited scope — not a full profiler. JMX/service statistics are also available. Source: [SnapshotProfileListener][rd-profile].
5. **Programming model**: Java `KernelRunnable` tasks are executed in transactions by the scheduler, and `DataService`/ManagedObject manages persistent object references. Application logic is not a generic Python/Lua entity-callback model. Sources: [Task Scheduler][rd-scheduler], [DataService][rd-data].
6. **Network layering**: the public SimpleSgs protocol uses opcodes, string/byte arrays and `ByteBuffer/MessageBuffer` to encode application messages; ClientSession goes through Java NIO channels; this repo's protocol is not protobuf by default. Source: [SimpleSgsProtocolImpl][rd-protocol].
7. **Permissions and anti-cheat**: the platform has Identity/Authenticator and session login/reconnect tokens; it provides no MMO movement/economy anti-cheat rules. Client submissions should still be treated as untrusted requests and validated by the application inside transactional tasks.
8. **Billing and operations**: the service platform has node, service and session management, with node migration/reconnection; there is no evidence for multi-zone merges, event configuration or commercial billing — insufficient materials.

### Transferable design highlights

| Highlight | What problem it solves | Implementation essentials (evidence) | When it is worth copying | When it does not apply |
|---|---|---|---|---|
| Transactional tasks as the business write-state entry point | When concurrent handlers mutate shared persistent objects, avoids half-writes, races and scattered retry logic | The scheduler creates a transaction per transactional task; participants do unified prepare/commit/abort, and failed tasks can retry per policy: [Scheduler][rd-scheduler], [TransactionImpl][rd-txn] | Low-frequency but atomically consistent business data such as character assets, market, rewards and mail | Per-frame movement/AOI hot path; transaction-conflict retries cause latency and throughput problems |
| Identity-to-node mapping and session relocation | Login/session hosting and node failure recovery need not stay pinned to the initially attached node | `NodeMappingService` maintains identity→node; the session service has a relocation key/state: [NodeMappingService][rd-nodemap], [ClientSessionServiceImpl][rd-session] | Multi-node session services that want to migrate user connections or route tasks to the same identity's node | Hard real-time spatial entities that must be split/switched wholesale and cannot handle connection redirection or state migration |

## Pitaya (modern Go option)

### The eight angles

1. **Failure recovery**: etcd service discovery can maintain the list of available server instances and NATS/gRPC provides RPC; these are not a player-data WAL/character snapshot. How business state recovers on failure must be designed by the game/database layer. Sources: [Pitaya README][pitaya-readme], [Features][pitaya-features].
2. **Scale-out**: separates the frontend that takes connections from the backend that only receives RPC, adding/removing instances per service type; by default it picks an instance by target type, and routing functions can also be defined. What scales is service processes; it does not automatically split the authoritative state of one oversized room. Sources: [Frontend and backend servers][pitaya-frontend], [Message forwarding][pitaya-forward].
3. **Hot update**: the official public features do not describe replacing business handlers in flight or migrating schemas; Go code usually switches by deploying versions, and a built-in no-downtime migration in Pitaya is unverified.
4. **Debug observability**: provides metrics grouped by route/status/server type, pluggable to StatsD/Prometheus; Tracing can integrate Jaeger, but whether every RPC is automatically instrumented depends on configuration. Sources: [Monitoring][pitaya-monitoring], [Pitaya README resources][pitaya-readme].
5. **Programming model**: Go handler routing, frontend/backend server types, RPC and service lifecycle hooks. Client SDKs are available; there are no built-in entity classes or AOI/space models. Sources: [Pitaya README][pitaya-readme], [Overview][pitaya-overview].
6. **Network layering**: TCP/WebSocket acceptors can be replaced/wrapped; JSON is the default serialization with Protobuf natively optional; internal RPC defaults to NATS and can also use gRPC. The client wire, server RPC and service-discovery layers can be split apart. Sources: [Acceptors][pitaya-acceptors], [Serializers][pitaya-serializers], [RPCs][pitaya-rpcs].
7. **Permissions and anti-cheat**: has generic components such as rate limiting and session bind/user id, but authentication and authorization, position/speed validation, transaction idempotency and anti-bot abuse are application responsibilities; property values submitted by clients must not be trusted. Sources: [Rate limiting][pitaya-ratelimit], [Sessions][pitaya-sessions].
8. **Billing and operations**: the framework supports service discovery, management metrics and routing extensions; there is no built-in MMO multi-zone merge, event delivery, character migration or billing settlement product — insufficient materials / outside the product boundary.

### Transferable design highlights

| Highlight | What problem it solves | Implementation essentials (evidence) | When it is worth copying | When it does not apply |
|---|---|---|---|---|
| Frontend access and backend business decoupled by server type | Scaling connection capacity and scaling room/business CPU need not be bound into one class of process | frontends hold listeners/sessions and forward by route; backends only handle RPC; etcd service discovery, NATS/gRPC: [Pitaya Features][pitaya-frontend], [RPCs][pitaya-rpcs] | When service types differ clearly, load curves differ and you want independent scaling | A small monolithic server; or when the critical-path RPC hop/service-discovery complexity outweighs the benefit |
| Pluggable transport acceptors, wrappers and serializers | Supports TCP/WS, JSON/Protobuf and different clients without hard-coding protocol policy in business handlers | acceptors own connections, wrappers process data before forwarding, serializers are set by the application: [Acceptors][pitaya-acceptors], [Serializers][pitaya-serializers] | Multi-client, multi-protocol services, or those needing gray-release wire schema upgrades | Fixed protocols with extreme latency sensitivity, where the config-matrix/compat-test cost of the abstraction layer is unacceptable |

## Unreal dedicated server

### The eight angles

1. **Failure recovery**: a dedicated server is an authoritative game instance without a local player for rendering, not a persistent world database. Character state WAL/snapshot/rollback and node failover are implemented by the game, storage and orchestration layers; the engine itself has no generic MMO transactional persistence. Source: [Dedicated Server setup][ue-dedicated].
2. **Scale-out**: multiple dedicated server processes can be deployed to host matches/instances; Replication Graph/Iris reduce per-connection actor replication cost, but they are replication filtering and network-layer extensions, not an automatic world partition / player handoff cluster. Sources: [Replication Graph][ue-repgraph], [Networking overview][ue-network].
3. **Hot update**: Live Coding/Hot Reload are development-stage C++ iteration tools and do not constitute a plan for migrating code and entity contracts on a running dedicated server. How game data hot-loads is project-implemented, and online compatibility guarantees are unverified.
4. **Debug observability**: the network profiler, Unreal Insights and network simulation/Replay tools can locate replication and latency problems; they do not provide a cross-region zone-server operations, merge or character recovery console. Source: [Networking overview][ue-network].
5. **Programming model**: C++/Blueprint Actor/Component, Actor RPCs, property replication, authority roles; GameMode/server logic is project-defined, and server validation must not rest on the client copy.
6. **Network layering**: UE's NetDriver defaults to UDP transport with its own replication bunch/bitstream encoding, exposing RPC/`NetSerialize` extension points; one cannot assume protobuf by default. Reliable and unreliable semantics come from replication/RPC channel settings. Overview source: [Networking overview][ue-network]; the concrete underlying NetDriver configuration varies per project/version.
7. **Permissions and anti-cheat**: server authority decides the authoritative copy; but server RPCs also need to validate the owner, call rate and business parameters. A dedicated server does not automatically provide game-rule anti-cheat. Actor replication documentation describes authoritative server-assigned network identity: [Replicate Actor Properties][ue-properties].
8. **Billing and operations**: the engine has the dedicated server target/build/cook/run base; multi-zone servers, merges, event configuration, account/payment and character migration belong to the game's online services and operations backend, not to what a dedicated server target ships. Source: [Dedicated Server setup][ue-dedicated].

### Transferable design highlights

| Highlight | What problem it solves | Implementation essentials (evidence) | When it is worth copying | When it does not apply |
|---|---|---|---|---|
| Per-connection replication dependency graph | As actor counts grow, scanning every Actor×connection per update costs too much | Replication Graph filters candidate Actors per connection using reusable spatial/classification nodes: [Replication Graph][ue-repgraph] | Multiplayer games with high actor counts, stable interest ranges and per-instance server isolation | When cross-process consistent world ownership is needed; small-scale games where maintaining graph nodes is more complex than scanning |
| Server authority + explicit RPC/property replication boundary | Local client predictions must not directly become authoritative asset/combat state | The server writes authoritative state and replicates to clients by owner/condition; clients send RPC/input requests validated by the server: [Networking overview][ue-network], [Replicate Actor Properties][ue-properties] | Games where competitive play, combat and asset state need a trust boundary | Cannot be copied as "the engine validates the game rules for you"; business validation, rate limiting and anti-cheat still must be built yourself |

## NetEase Pomelo (domestic vendor public framework)

### The eight angles

1. **Failure recovery**: the Pomelo README declares a master high availability plugin; generic character state persistence, transaction recovery/WAL and world state rollback are not among its core guarantees. Player state recovery on failure depends on business storage. Source: [Pomelo README][pomelo-readme].
2. **Scale-out**: the distributed multi-process architecture separates connection-taking servers from business backends, managing heterogeneous processes by route/server type; parallelizing an existing single room or a single hot worker still needs business sharding. Sources: [README][pomelo-readme], [Pomelo overview (Chinese)][pomelo-cn-overview].
3. **Hot update**: the README does not promise no-downtime updates of online business code/message contracts; Node.js modularity is not runtime-replacement safety, and deployment and session migration strategies are unverified.
4. **Debug observability**: the README lists command-line, admin, performance-test and AI tools; the actual monitoring metrics, sampling and production maintenance boundaries depend on plugins/versions. Sources: [Pomelo README][pomelo-readme], [Admin/Architecture wiki][pomelo-admin].
5. **Programming model**: Node.js handler/route, request-response/broadcast, Master/Monitor and multi-process server types, avoiding shared-state locks inside one process via the event loop; cross-process still cooperates via RPC/messages. Sources: [Pomelo README][pomelo-readme], [Pomelo architecture docs (Chinese)][pomelo-cn-architecture].
6. **Network layering**: pomelo-protocol organizes message frames/types, with TCP and WebSocket connectors for access; protobuf is supported by the separate `pomelo-protobuf` component and must not be read as enabled by default in every project. The dependency tree includes `pomelo-protocol` and `ws`: [package.json][pomelo-package].
7. **Permissions and anti-cheat**: the framework's connections/routing and sessions do not prove business identity validity; client fields must be validated by handlers. Generic anti-cheat, payment security and economic validation are not declared in the README.
8. **Billing and operations**: pomelo-admin has a service management base and the README lists plugins, AI/bots and stress-test tools; multi-zone merges, event configuration, billing ledgers and data migration remain game/operations-system duties, with no complete engine-built-in solution seen.

### Transferable design highlights

| Highlight | What problem it solves | Implementation essentials (evidence) | When it is worth copying | When it does not apply |
|---|---|---|---|---|
| convention-over-configuration server types/routes | Adding a service role reduces hand-written forwarding, deployment coupling and routing boilerplate | Master/Monitor manage service types and instances, and the framework forwards requests to the target server type by route; the docs emphasize multi-process distribution: [Pomelo README][pomelo-readme], [architecture (Chinese)][pomelo-cn-architecture] | Many RPC endpoints, business services scaling horizontally by load, and teams wanting to split services quickly | When every call needs strong consistency or strong runtime schema validation; convention is not an authorization/idempotency guarantee |
| Admin, stress-test client and framework plugins as separate modules | Operations/stress-test capability need not be stuffed into business logic and a single core package | The framework provides extensible components and admin/performance-test tools, with extra capability composed per module: [Pomelo README][pomelo-readme] | Wanting to add/remove management capability per project lifecycle and reuse one control plane | When plugins have no version governance/permission isolation; or the legacy plugin stack is unmaintained or incompatible with the current Node.js |

## Cross-engine common problems

1. **Crash consistency and experience continuity cannot be solved by the network engine alone.** BigWorld/KBEngine provide recovery points through archiving/backups or DB consolidation; RedDwarf writes part of the tasks into transactions; Pitaya/Pomelo/Unreal leave state guarantees to the application and storage. Periodic snapshots have a clear RPO, transactions have throughput/conflict costs, and event logs need replay version compatibility. No mechanism gets high throughput, strong consistency and fast recovery for free.
2. **Horizontal scale-out and a single hot state are not the same problem.** BigWorld can migrate spatial boundaries but pays for ghosts, boundary events and handoff complexity; KBEngine mainly places new spaces on emptier CellApps, and single-space horizontal slicing is unproven; service frameworks can add frontend/backends but do not automatically split one hot room; Unreal's Replication Graph only reduces replication work and does not change authoritative state ownership.
3. **The hardest part of hot update is state and contracts, not reloading code files.** KBEngine's fullReload already touches EntityDef, and Python still holds old class/callback references; the other frameworks mostly leave version switching/data migration to the project; Unreal's dev hot-compile tools are not online migration. Explicit compatibility windows, version fields, rollback strategy, connection drain and old-data upgrades are needed.
4. **Observability often stops at current metrics, lacking a causal chain from player input to persisted results.** Watcher, pomelo admin, Pitaya metrics, Unreal Insights and RedDwarf profile each cover a different layer; cross-process tracing, unified entity/request correlation IDs, replay and online security auditing do not close the loop automatically.
5. **Transport reliability is not business reliability.** TCP/KCP/RPC success only proves delivery at that layer; a retry after timeout may double-charge or double-reward, and a disconnect can leave the server result inconsistent with the client's understanding. Request ids, idempotency keys, persistence confirmation semantics and owner generation/epoch are mandatory.
6. **Authoritative execution still needs application rule validation.** The engine can restrict who may call an RPC, which classes of properties replicate, and what message parameter types are; whether rules for speed/cooldowns/drops/currency/payment are legal can only be judged in business-domain context. The client should provide intent, not authoritative results.
7. **Commercial operations capability is often mistaken for "MMO engine capability".** Multi-zone routing, server merges, event configuration, payment reconciliation, offline character migration and data repair usually belong to separate operations/platform systems; public framework materials are generally insufficient to prove generic safe semantics.

## Highlights Mistlane can borrow directly (by priority)

Mistlane's current goals divide `gateway/login/coordinator/gameServer/crossServer/data` and make clear that player/scene, persistence write ownership and cross-region ownership still have unimplemented parts (see [`architecture.md`](26-mmo-engine-survey.md) and [`process-roles.md`](26-mmo-engine-survey.md)). The following are design suggestions, not implemented features:

1. **P0: an authoritative consolidation point and confirmation contract for persistence writes** (borrow KBEngine's boundary where Base consolidates Cell authoritative state, but do not copy its in-memory-only periodic backup). Define a unique writer/generation per character; save requests carry an idempotency key, a database transaction boundary, a defined meaning of success confirmation and a query/retry path after timeout; forbid double writes when returning cross-region to home data. Applies to character assets/rewards/payments; not to per-tick position snapshots.
2. **P0: process transfer uses an explicit prepare → snapshot → destination-ack → route-switch → source-release state machine** (borrow RedDwarf's identity-to-node routing and BigWorld's owner handoff). Define crash recovery, duplicate messages and a fencing epoch for each step; load routing or heartbeats alone are not enough to grant a second writer. Mistlane's current transfer handshake is explicitly unimplemented, and it is fitting to write the protocol/fault-injection tests first.
3. **P1: placement by load and entity capacity, but with scheduling and admission kept separate** (borrow KBEngine CellappMgr's dual load/entity-count metrics). Compute effective capacity and overload rejection for online workers instead of assigning randomly; identify large rooms as hotspots separately, and do not assume adding processes auto-scales one room.
4. **P1: pluggable transport, serialization and explicit message contracts** (borrow Pitaya acceptor/serializer and Pomelo's protocol modularity). Mistlane has already separated the TCP/WS adapter and the internal payload boundary; keep versioning the external protocol, internal request ids, deadlines, error codes and schema compatibility rules — "it parses" is not a substitute for compatibility.
5. **P1: dev/operations live tooling layered by entity and space** (borrow KBEngine Watcher/SpaceViewer and BigWorld Watcher). First add read-only diagnostics for active sessions/character owners/scene distribution, replication/migration stages and persistence task state; isolate authentication on internal interfaces, bound the output, and keep full entity dumps out of the main tick.
6. **P2: script reload replaces behavior only; state/contract migration is versioned separately** (borrow KBEngine's reload/fullReload distinction while avoiding the stale-reference problem). Mistlane's Lua VM replacement should pair with request drain/old VM stop, new VM init and keeping the old VM on failure; character data upgrades use explicit migration instead of expecting the reload to rewrite player state.
7. **P2: stress tests and fault drills as prerequisite evidence for scale/recovery claims** (borrow Pomelo/Pitaya's standalone bot/test tools). Make repeatable tests for gateway disconnects, service partitions, DB timeouts, worker crashes, duplicate payment callbacks and hot rooms, and record RPO/RTO, P99, backlog and overload rejections; passing tests does not automatically equal a production capacity commitment.
