### 2. KBEngine — material completeness: partial (A–E and G have code evidence; F partial) {#2-kbengine--资料完整度部分a–e-g-有代码证据f-部分}

**A Contract**: `entity_defs/*.def` declares each property's `<Type>`, `<Flags>`, `<Persistent>`, default value and Base/Cell/Client methods; `entities.xml` decides whether an entity has Base, Cell, Client. The entity-definition initialization code builds the flags mapping, and property descriptions record flags/persistent/type. The example format is in this repo's existing KBEngine definition docs and the local template files; the current template `Account.def` is an empty-property example and cannot be used to prove a field set. [K1][K2]

**B Sync**: `Proxy::initClientBasePropertys()` sends Base client data to the client for the first time; `Witness::update()` builds a batched update bundle for view entities when a player client exists, sending a property/position snapshot when an entity enters view; the `Entity::` property update path sends to Witness according to visibility flags and view/detail level, with data encoded as property UID/alias + serialized value. The own-client versus other-clients scope is distinguished by flags, and Cell's `Witness`/View is the AOI filtering entry. The evidence supports "initial snapshot + subsequent incremental/per-property change", and does not mean arbitrary fields are fully sent every frame. [K3][K4]

**C Persistence**: `EntityTableMysql::initialize()` selects fields from `getPersistentPropertyDescriptions()` and builds mapping items per entity type; `EntityTables::load()` iterates entity script modules to initialize EntityTables, and `syncToDB()` syncs table structure; `DBTaskWriteEntity` hands serialized data to EntityTables for writing and passes back the result. What can be proven is property-set-driven single-entity-type table/field sync; atomic transactions across multiple tables for cross-entity, property split-table rules and reliable scheduled auto-save cannot be asserted from this code. `ENTITYCALL` persistence is disabled. [K5][K6]

**D Topology**: the local source has independent server modules `loginapp`, `baseappmgr`, `baseapp`, `cellappmgr`, `cellapp`, `dbmgr`, etc.; BaseApp listens on an external client interface and CellApp goes through an internal interface; Dbmgr initializes EntityDef and global/base/cell data. Components use the engine Network/Bundle, message interfaces and internal addresses, rather than a single monolithic server loop. [K7][K8]

**E Map**: `SpaceMemory` manages entities, spatial coordinate nodes and world enter/leave; CellApp has Space/coordinate structures and Witness updates. Existing evidence is insufficient to reduce "space/ghost replication across multiple CellApps" to seamless player migration across chunks, and it is insufficient to give a generic answer on chunk-switch latency / whether the client loads. [K4][K9]

**F Cross-server**: the source shows that server components/EntityCall/migration APIs can orchestrate entity and client control, but this round did not fully trace the cross-server battlefield / cross-server matchmaking / player server-migration business chains and persistent data ownership in the public repo. So it cannot be claimed to be a built-in cross-server solution; overall **partial / unverified**. [K7][K10]

**G Player and NPC**: the same EntityDef mechanism defines game entities, with Proxy for types that carry client connection semantics; Base and Cell each hold entity-side state and are linked via client/witness. `giveClientTo()` can rebind client control to another Proxy (the source only proves this API path; it cannot be used to infer automatic reconnect on disconnect or complete cross-process migration). [K1][K3][K10]

## Cross-cutting observations

### Observable consensus

1. **The authoritative end of real-time simulation and data-saving responsibility must be kept apart**: KBEngine decouples Base/Cell from DBMgr; UE Dedicated Server's server-authoritative semantics do not ship a business DB either; Nakama explicitly separates match state logic from the Storage API. The point to borrow is defining state owners, save triggers and ACKs, not copying component names. [K7][K6][U1][N1][N2]
2. **Network sync needs interest/recipient filtering**: KBEngine Witness/View + flags, UE relevancy/Replication Graph, and Nakama match handler relevant-peer broadcast each solve subscription at different granularity. Full broadcast is usually not the default strategy for large scenes; specific AOI structures are not a universal standard. [K3][K4][U2][U3][N1]
3. **"Map chunking" has several meanings**: asset/Actor streaming, gameplay Scene/Match room separation, and server simulation-authority sharding are different problems. UE World Partition evidence supports the former and Nakama Match supports room-style play; neither can be called BigWorld-style server-side seamless spatial migration without additional implementation. [U5][N1]
4. **A declarative entity model helps generate sync/serialization metadata, but brings schema constraints**: KBEngine's `.def` describes types, sync flags and persistent fields at once; UE reflection/replication leans toward a network object model; Nakama Match uses code-defined state. The more automated, the more version migration and compatibility management is needed.

### Major school differences and trade-offs

| School | Representatives | Benefits | Cost / boundary |
|---|---|---|---|
| **Engine-level entity runtime + multi-role processes** | KBEngine; BigWorld cannot be used as a factual comparison this round due to missing materials | Entity schema, replication, space and saving can form unified conventions; scale out by process per responsibility | Cross-component RPC/migration/failure recovery is complex and the schema is deeply bound to the framework; BigWorld's specific trade-offs are unverified |
| **Transaction/object-style server middleware** | Darkstar/Reddwarf | Object lifecycle and transaction/persistence APIs have middleware-level abstractions | Not equal to an off-the-shelf MMO AOI, seamless map or cross-server entity engine; the maintenance state of historical source and applicability to today's production need separate evaluation |
| **Authoritative match / game backend platform** | Nakama | Suited to rooms, matchmaking, real-time play, and account and metadata backends; business logic entry points are clear | Game state structure and entity sync are mostly defined by business code; not the same layer as persistent world sharding |
| **Game-engine built-in networking** | Unreal Dedicated Server | Game objects, replication and content tooling are integrated, suited to instance servers / project-defined backends | Dedicated Server itself does not solve operational MMO data ownership, cross-server, online migration or character DB; World Partition cannot replace server sharding |
| **In-house by commercial vendors (sparse public materials)** | Tencent public course sample | Concrete project engineering experience can be learned from public talks | Complete code and boundaries cannot be audited from outside; when public materials are insufficient, only "unverified" can be recorded — architecture must not be derived from a product or company name |

## Implications for Mistlane

Mistlane's current docs assign `gameServer / crossServer / data / coordinator` as service responsibilities rather than an implemented MMO runtime; current code mainly has generic network forwarding, Lua execution, routing and admission, and the complete Avatar/Scene/save chain is still unimplemented. [M1][M2]

### Directly borrowable (as design constraints, not immediate implementation)

1. **Define authority and data ownership first, then implement migration**: make explicit that each Avatar has only one writable owner at a time; define read/write boundaries between home data and temporary cross-region simulation servers, migration snapshots, generation/ACK, and failure compensation. This direction matches Mistlane's existing single-writer/ownership goals. [M1][M2]
2. **Split property declarations into independent orthogonal policies**: at least separate network sync audience/AOI, persistence, client-writable, and update rate/precision. Do not auto-derive "persistable" or "client-modifiable" from "client-visible". KBEngine's flags+Persistent is a referenceable model, but its flags enum need not be copied as-is. [K1][K3][K5]
3. **Take different paths for incremental sync and enter-view snapshots**: on AOI entry, first give a stable entity initialization snapshot, then encode changes; give broadcasts an explicit recipient set, throttling and a byte budget. Validate at small scale only after Mistlane's entity/scene contract matures, and do not start with arbitrary world sharding. [K3][K4][M2]
4. **Make persistence schema/write-back auditable**: separately define a persistent field whitelist, serialization version, dirty tracking, async batched writes, idempotent keys, error/timeout callbacks and durability confirmation. Entity state persistence must not be merged with strongly consistent transaction records such as transactions/emails into one automatic ORM. [K5][K6][N2]
5. **Land cross-server by instance/battlefield matchmaking first**: Nakama-style ticket/match is close to Mistlane's existing crossServer room ownership / over-capacity rejection model; it can validate matchmaking, capacity and entry boundaries, but a successful match does not mean the player entity migration has completed. [N3][M2]
6. **Keep an interface boundary for external adapters**: use the UE ecosystem as a possible client/instance service, but do not treat Unreal Actor network replication as Mistlane's server property/DB contract; map asset loading also does not replace server-side simulation owner handoff. [U2][U5]
