# 14 研发组织与项目管理

> 本章目标：掌握游戏研发团队的组织协作方法——角色分工、需求与文档流程、敏捷实践、版本里程碑、变更管理、跨职能协作、外包管理、技能培养与项目交接。技术之外，这些"软实力"往往同样决定项目成败。
>
> 参考书籍：《网络游戏核心技术与实战》（中嶋谦互）、《凤凰项目》的流程视角。

游戏开发不仅是技术问题，更是组织协作问题。团队协作效率、代码质量管控、项目交接规范——这些"软实力"往往决定了项目的成败。《百万在线》中指出：很多技术优秀的团队最终失败，不是因为技术不行，而是因为管理混乱。

游戏研发的管理挑战在于它的**特殊性**：需求频繁变化（玩家反馈驱动）、功能高度耦合（体验完整性）、品质要求极高（玩家容忍度低）、内容与技术双流水线并行（策划出案、美术出资源、程序出功能，缺一不可）。传统的软件项目管理方法不能直接套用，需要针对游戏开发的特点进行适配。

本章聚焦组织协作本身。技术侧的配套流程（发布管理、故障应急）见第 13 章，配置表管线见第 17 章。

## 1. 游戏研发团队的角色构成

### 1.1 四大职能

一个典型的游戏研发团队由四大职能构成：

| 职能 | 核心产出 | 与后端技术的关系 |
|------|---------|----------------|
| 策划 | 设计文档、数值表、关卡配置 | 需求方 + 配置生产者 |
| 程序 | 客户端/服务端代码、工具 | 系统实现者 |
| 美术 | 原画、模型、动画、特效、UI | 资源生产者（进资源管线） |
| QA | 测试用例、缺陷报告、验收 | 质量守门人 |

后端工程师最容易产生认知偏差的是：**策划和美术不是"提需求的甲方"，而是内容生产线的同事**。一个新玩法从立项到上线，通常需要策划出方案与数值、程序实现逻辑、美术产出表现资源、QA 验证、配置入表——五段流水线任何一段延迟，整体就延迟。理解这条流水线，后端工程师才能正确回答"这个功能为什么排三周"这类问题：瓶颈可能不在代码量，而在等美术资源或数值验证。

### 1.2 策划岗位细分

策划是连接创意与实现的桥梁。典型的策划团队结构：

| 岗位 | 核心职责 | 技能要求 | 产出物 |
|------|---------|---------|--------|
| 主策划 | 玩法框架、团队协调 | 全局视野、决策力 | 系统框架文档 |
| 系统策划 | 功能设计、流程设计 | 逻辑思维、文档能力 | 功能设计文档 |
| 数值策划 | 数值平衡、经济系统 | 数学能力、数据分析 | 数值表格、公式 |
| 关卡策划 | 关卡设计、难度曲线 | 创意能力、玩家心理 | 关卡配置、地图 |
| 活动策划 | 活动设计、运营支持 | 创意能力、数据分析 | 活动配置、规则 |
| 剧情策划 | 故事设计、世界观 | 文学功底 | 剧本文档、对话 |

每个岗位对应五个能力维度：创意、数值、系统、技术理解、数据。现实中大多数策划只擅长其中 1-2 个维度，团队管理的关键是**让不同专长的人互补协作**——数值强的配系统强的，互相评审对方的产出。

### 1.3 程序团队细分

程序侧的常见分工及其协作边界：

| 岗位 | 核心职责 | 关键协作点 |
|------|---------|-----------|
| 服务端程序 | 逻辑、存储、网络 | 与客户端定协议、与策划定数值验证 |
| 客户端程序 | 表现、交互、优化 | 与服务端定协议、与美术接资源 |
| 引擎/平台程序 | 引擎改造、工具链、SDK | 支撑两个业务团队 |
| 工具/运维程序 | 编辑器、GM 工具、CI/CD | 服务策划和运维效率 |

一个常被忽视的岗位是**工具程序**：策划需要关卡编辑器、数值模拟器，QA 需要自动化测试工具，运营需要 GM 后台。工具投入不足的团队，所有效率损失都会转嫁到业务程序头上（程序替策划手工配数据、QA 全人肉测试）。中大型团队标配 10%-20% 的工具人力。

## 2. 需求与设计文档

### 2.1 功能设计文档规范

功能设计文档是策划和开发之间的"合同"。一份可开发的设计文档应包含：

```
功能设计文档结构：
├── 概述：功能目标、目标用户、成功指标
├── 玩法设计：流程图、规则说明、边界情况
├── 数值设计：数值表、公式、与现有系统的关系
├── 界面/表现：原型图、表现需求（供美术）
├── 异常处理：掉线、并发、边界值的行为定义
├── 数据需求：埋点事件、指标定义（供分析，见第 12 章）
└── 验收标准：QA 可执行的验收用例
```

其中"**异常处理**"是最常缺失的一节，也是后端工程师最需要的一节——玩家在功能进行中断线怎么办？奖励发放到一半失败怎么办？两个玩家同时触发同一个限量活动怎么办？策划没写、程序没问的部分，上线后都会变成故障。评审设计文档时，后端的常规动作就是逐条追问异常分支。

**关键原则**：设计文档不是"写完就扔"的文档，而是需要在开发过程中持续维护的"活文档"。开发中发现设计不合理时，及时更新文档而不是口头沟通完事——否则三个月后"代码为什么这么写"就没人能回答了。

> **陷阱**：最常见的协作事故是"需求不清就开始开发"——口头说了几句就写代码，结果与策划预期不一致。建议坚持"先文档，后开发"；紧急需求可以文档从简，但异常处理和验收标准两节不可省略。

### 2.2 数值表的协作流程

策划的数值产出最终要变成游戏内生效的配置，这条链路的协作质量直接决定迭代速度：

1. **策划在表格中维护数值**（Excel / 在线表格），表格结构按配置管线的 schema 约定（字段名、类型、枚举值固定）
2. **校验规则内置于表格**：非法值（负数价格、超出枚举）在表格里就标红，而不是等程序加载时报错
3. **导出管线自动转换**：表格 → 导出工具 → 运行时格式（JSON/二进制），人工不经手中间格式
4. **测试环境先行**：数值改动先进测试服验证，再进生产（第 17 章配置管线的灰度与回滚）

这条链路的常见故障是"策划直接改生产配置没留痕"（第 13 章把它列为配置事故的排查难题）。组织上的解法是权限与流程：生产配置的修改走审批 + 自动记录变更人和变更原因。

### 2.3 技术评审机制

重大功能在开工前应有技术评审，评审的输入输出要明确：

- **输入**：设计文档、相关模块的现状说明、备选方案
- **评审问题清单**：对现有架构的影响？性能瓶颈在哪（容量推演见第 13 章）？数据结构是否可扩展？失败如何降级？埋点是否覆盖？
- **输出**：方案结论、风险清单、任务拆分建议

评审的价值不只在"把关"，更在**知识共享**——参与评审的人对系统的理解同步了，后面接手和维护的人才不会抓瞎。评审记录（方案、理由、被否掉的备选）应该归档，它们是第 9 节"项目交接"里最值钱的文档。

## 3. 敏捷开发实践

### 3.1 Scrum 的游戏化适配

游戏开发与传统软件开发的差异决定了 Scrum 需要适配：

| 维度 | 传统软件 | 游戏开发 |
|------|---------|---------|
| 需求稳定性 | 相对明确 | 频繁变化（玩家反馈驱动） |
| 交付单元 | 功能可独立交付 | 功能高度耦合（体验完整性） |
| 验收标准 | 需求满足即可 | "能跑"不等于"好玩" |
| 质量要求 | 可用性 | 手感、节奏等主观品质 |

**适配策略**：缩短 Sprint 周期（1-2 周）、增加评审频率、建立体验评审机制、技术债务优先级提升（游戏的耦合度高，债务的利息也高）。

### 3.2 Sprint 规划实践

Sprint 规划会议的核心是**确定目标和拆分任务**：

1. Sprint 目标确认（15 分钟）：回顾产品愿景，确认 Sprint 目标
2. 用户故事评审（45 分钟）：逐条评审用户故事，确认故事点估算
3. 任务拆分（45 分钟）：故事拆任务、估工时、定负责人
4. 计划确认（15 分钟）：确认 Sprint Backlog 与风险点

**用户故事模板**：

```markdown
## 用户故事 #1234
作为 **一名玩家**，
我想要 **查看自己的战绩统计**，
以便 **了解自己的游戏表现**。

### 验收标准
- [ ] 能够查看最近 100 场战斗记录
- [ ] 能够查看胜率、击杀数等统计
- [ ] 数据实时更新（延迟 < 5 秒）

### 涉及方
- 策划：@系统策划（验收体验）
- 服务端：战绩数据接口 + 存储方案
- 客户端：战绩界面 + 表现
- 美术：界面资源（排期中）

### 故事点估算：5
```

模板里的"涉及方"一栏是游戏项目特有的：一个用户故事横跨策划、程序、美术多个职能，规划时就把四方对齐，比联调阶段才发现美术资源没排期要省得多。

### 3.3 每日站会与体验评审

每日站会控制在 15 分钟内，聚焦三个问题：昨天完成了什么、今天计划做什么、有什么阻塞。

**游戏开发特有的站会环节是体验评审**（约 3 分钟）：展示新完成的功能，收集团队反馈，记录改进点。这是游戏与传统软件开发的重要区别——代码能跑不等于功能好玩，团队自己先玩起来是最低成本的品质保障。

### 3.4 Sprint 回顾与改进

Sprint 回顾是持续改进的核心机制。每次回顾应该产出 2-3 个具体的改进措施，并在下个 Sprint 中执行、再下个 Sprint 中检查：

```
Sprint 回顾改进项跟踪：
├── 问题1：代码评审延迟
│   ├── 改进措施：建立评审 SLA（24 小时内完成）
│   └── 检查时间：Sprint 13 回顾
├── 问题2：测试环境不稳定
│   ├── 改进措施：增加测试环境监控（第 13 章监控体系）
│   └── 检查时间：Sprint 13 回顾
└── 问题3：需求变更频繁
    ├── 改进措施：建立需求冻结期（Sprint 中段后不接受新需求）
    └── 检查时间：Sprint 14 回顾
```

> **陷阱**：敏捷最常见的错误是"只有形式没有灵魂"——站会变成流水账汇报，回顾变成吐槽大会。敏捷的核心是"持续改进"，而不是"走流程"；改进项没有跟踪和复查，回顾就只是情绪宣泄。

## 4. 版本里程碑与阶段门管理

Sprint 是周级别的节拍，Sprint 之上还有月级别的节拍：**版本里程碑**。游戏研发的典型阶段门（Stage-Gate）：

| 阶段 | 门禁产出 | 服务端工作重心 | 常见延迟/终止原因 |
|------|---------|--------------|-----------------|
| 预研（Prototype） | 核心玩法可玩 demo | 验证技术可行性：帧同步确定性、同步模型选型（选型依据见第 1 章游戏类型与后端差异） | "好玩"验证不通过——预研期终止项目是正常结果，不是失败 |
| 垂直切片（Vertical Slice） | 一段达到量产品质的完整内容 | 定架构骨架、协议框架、存储方案 | 品质标准未对齐（demo 的精致度 ≠ 量产标准） |
| 量产（Production） | 全量内容铺开 | 系统开发、容量推演（第 13 章）、工具链 | 内容产能不足、系统间耦合失控 |
| 删档测试（CBT） | 若干轮限量测试 | 删档数据清理脚本、压测、放量扩容 | 服务器容量、崩溃率、留存不达标 |
| 公测/上线 | 正式运营 | 值班体系、开服扩容、热更管线 | 兼容性、支付对账、平台审核 |

阶段门的意义在于：**在沉没成本变大之前给出停止的选项**。预研期砍掉一个项目是省钱，公测前夜砍掉是灾难。服务端工程师需要理解两条配套纪律：

- **预研与量产的代码标准不同**。预研代码允许"验证后丢弃"（快速堆出可玩性验证），量产代码才要求可维护性。但预研期验证过的技术结论（确定性测试结果、容量上限实测）是量产的正式输入，要留文档——丢代码不丢结论
- **删档测试有独有的组织配套**。删档意味着玩家投入清零，所以要提前准备：数据快照留存（客服与纠纷回溯需要）、补偿承诺的处理（承诺过"删档补偿正式服发放"就必须兑现，或提前说明）、放量节奏（少量邀请 → 逐步扩大，容量按放量节奏提前扩，而不是一次全量）

### 4.1 里程碑估期的现实

"这个版本什么时候能上"是所有角色都要回答的问题。服务端的估期经验：

- **联调与测试占功能工期的 1/3 以上**。只按写代码的时间估期，必然延期——协议联调、异常分支测试、多端兼容，都是真实成本
- **估期给区间和前提**，不给单点："两周，前提是数值表在第 3 天前锁定、美术资源不返工"。前提不满足时提前暴露，比到期解释好得多
- **预留集成缓冲**。多系统并行开发，最后合起来的时间总是比各部分之和长；经验做法是按功能估期总和的 20%-30% 预留集成期

## 5. 需求变更管理

游戏研发的需求变更频率高于一般软件（玩家反馈、竞品动作、数据表现都在驱动变更），管理目标不是"消灭变更"，而是**变更成本的可见化与分级**：

| 变更级别 | 例子 | 处理方式 |
|---------|------|---------|
| 文案级 | UI 文案、提示语、公告 | 直接改，走常规提测 |
| 数值级 | 掉率、成长曲线、商店价格 | 改配置表走配置管线（第 17 章），数值策划回归验证 |
| 系统级 | 掉落系统结构、匹配规则、结算流程 | 完整流程：影响评估 → 技术评审 → 排期 |

变更管理的核心动作是**量化成本**。策划说"把这个奖励改成邮件发放"时，程序最有价值的回答不是"行"或"不行"，而是："奖励发放路径已有邮件通道，改配置半天；但领取表要加字段，涉及合服兼容，一共两天，建议下个版本。"**成本量化之后，变更就从"程序嫌麻烦"变成了产品决策**——策划拿着真实的代价去权衡，才是健康的协作。

冻结期纪律与分级配套：Sprint 中段后不接受系统级变更（文案、数值级不受限，保持迭代灵活）；版本发布前 2-3 周系统级冻结（发布期纪律，与第 17 章版本冻结对应）。两个冻结期冻的都是系统级——一刀切全冻的团队，通常会被迫私下解锁，纪律反而失效。

> **陷阱**：变更管理的两个退化极端——"来一个做一个"（团队被变更驱赶，Sprint 目标永远完不成，士气崩坏）和"全部走重流程"（改个错别字要一周审批，策划开始绕过流程私下找程序改，流程名存实亡）。**分级的意义就是让大多数变更走轻量路径，把重流程留给系统级变更**。

## 6. 跨职能协作

### 6.1 前后端协作流程

前后端协作是游戏开发中最频繁的跨职能协作。标准流程：

1. **需求评审**：策划介绍需求，客户端评估 UI 实现，服务端评估接口与数据设计
2. **协议设计**：服务端输出协议文档（消息定义、字段语义、错误码——格式与兼容规则见第 4 章），客户端确认
3. **并行开发**：服务端优先实现接口，客户端用 Mock 数据开发表现
4. **联调**：真机联调，修复协议理解偏差
5. **测试**：功能测试、性能测试、兼容性测试

其中"**Mock 数据先行**"值得强调：协议定义好之后客户端就不再被服务端进度阻塞，两边并行能把整体工期压缩 30% 以上。这要求协议文档先于代码——先写代码后补文档的团队永远享受不到并行红利。

> **陷阱**：跨团队协作最常见的问题是"接口文档不更新"——服务端改了协议没同步文档，客户端按旧文档开发，联调时才发现。解法是**文档即代码**：协议用 Protobuf 等 IDL 定义（第 4 章），文档由 IDL 自动生成，改协议必然改 IDL，文档不可能过期。

### 6.2 策划与程序的协作

策划-程序协作的关键是**双向翻译**：

- **策划 → 程序**：设计文档要说清"异常分支"，数值要给公式而不是只给结果表（程序需要知道"等级 10 时血量为什么是 8500"才能验证）
- **程序 → 策划**：把技术约束翻译成策划能决策的语言——不说"AOI 的复杂度是 O(N×M)"，说"同屏 500 人时服务器每帧的开销是 100 人的 25 倍，同屏人数上限建议 200"

冲突高发的场景是"策划要的效果技术上代价很大"。健康的处理路径：程序给出量化的代价（性能数字、工期数字、风险描述）→ 策划拿着代价重新权衡 → 主策划拍板。危险的路径是程序直接说"做不了"（关闭了权衡空间）或默默照做（埋下性能雷）。

### 6.3 技术方案冲突的解决

技术方案冲突的解决流程：

1. **问题识别**：记录冲突点和各方观点（写下来，避免"你说得不对"式的口舌之争）
2. **方案对比**：各方陈述方案优缺点，尽量落到可比较的维度（性能数据、工期、可维护性）
3. **决策机制**：技术负责人决策，必要时升级。**决策后统一执行**——可以保留不同意见，但不阻塞执行
4. **复盘**：验证决策效果，沉淀为团队的技术决策记录（ADR）

"谁嗓门大听谁的"和"争不出就都做"是两个常见退化。决策权明确（架构师/技术负责人）+ 决策记录留痕，是冲突不内耗的底线保障。

## 7. 外包与混合团队管理

美术外包是行业常态（原画、建模、动作、特效大量依赖外部产能），组织上要把外包当作**流水线上的外部节点**来管理，而不是"钱付出去就等收货"：

- **规格先行**：验收标准写成文档——面数、贴图规格、命名规范、动作帧数、交格式。规格不清的外包必然返工；规格文档由内部美术或技术美术（TA）维护，并随引擎/管线升级同步更新
- **样品确认后再批量**：先交 1-2 个样品确认风格与规格，再批量生产。跳过样品直接生产 100 个不合规格的资源，是最贵的外包事故
- **管线自动校验**：外包交付 → 脚本自动检查规格（命名、尺寸、面数）→ 入库。靠人工检查规格的团队，在量产期会被交付量淹没
- **权限边界**：外包人员不接触生产环境、玩家数据和核心代码仓库；内部工具给外包开独立账号、最小权限、操作留痕（与第 18 章数据安全要求一致）

服务端相关的特例是**外包开发 GM 工具或运营后台**。部分团队会把这类"非核心"系统外包，必须坚守的边界：外包开发的工具，部署与账号权限体系由内部掌控（不允许外包自带后门账号），代码验收包含安全评审（第 18 章审计要求）。工具可以外包，**对玩家数据的访问权不能外包**。

> **陷阱**：外包管理最常见的坑是"最低价中标 + 规格文档缺失"的组合——返工成本远超省下的差价，而返工期恰好在量产关键路径上。外包省的是人力成本；管不好外包，省下的钱会以内部协调时间的形式加倍还回去。

## 8. 技能培养与团队建设

### 8.1 技能矩阵

团队技能矩阵帮助识别能力短板和培养方向：

| 成员 | Go | SQL | Redis | 网络 | 架构 | 沟通 |
|------|-----|-----|-------|------|------|------|
| 组长 | 4 | 4 | 4 | 5 | 5 | 4 |
| 成员 A | 5 | 4 | 4 | 4 | 3 | 3 |
| 成员 B | 3 | 5 | 3 | 3 | 3 | 4 |
| 成员 C | 3 | 3 | 3 | 2 | 2 | 3 |
| 新人 | 2 | 2 | 2 | 1 | 1 | 2 |

技能等级：1-初学者、2-初级、3-中级、4-高级、5-专家。矩阵的用法：横着看（谁的短板在哪）、竖着看（哪项能力只有一个人撑着——**单点风险**，这个人离职或请假，这块工作就停摆）。矩阵显示"网络 5 分只有组长一人"时，正确的动作不是让组长更忙，而是指定第二人深耕，把单点变双点。

### 8.2 成长路径与个人发展计划

服务端程序员的典型成长阶梯：

| 阶段 | 能力标志 | 典型任务 |
|------|---------|---------|
| 初级 | 能按文档完整实现一个功能模块 | 背包、邮件、签到 |
| 中级 | 能设计一个子系统的方案并处理边界 | 活动框架、排行榜、公会 |
| 高级 | 能主导跨系统设计、处理性能与一致性 | 战斗结算、交易系统、跨服架构 |
| 资深 | 能做架构决策、带人、跨团队推动 | 服务化拆分、技术选型、容量规划 |

个人发展计划的关键：不是"读 10 本书"，而是"主导一个模块的架构设计"。实践是主要的学习方式，理论学习只是辅助——每次培训后安排一个小型实践任务，让知识落到手上。

### 8.3 知识分享与 Code Review

**技术分享会**是团队知识沉淀的核心机制。建议每周一次、每次 1 小时、成员轮流分享。分享主题贴近实战：Redis 数据结构应用、分布式锁的陷阱（第 5 章）、性能优化实践、一次线上故障的复盘。分享的材料归档——它们和评审记录一起，构成新人培养的教材库。

**Code Review 规范**：评审检查项包括逻辑正确性、潜在 bug、性能、安全、可读性。规则上明确：评审是评审代码不是评审人，作者对代码负责、评审人对把关负责；核心模块（支付、战斗结算、经济）需要两人以上评审。

> **陷阱**：技能培养最常见的错误是"只培训不实践"——课上完就完了。培训的价值要靠后续的项目任务兑现；另一个隐性错误是"能者多劳"——强者永远做核心任务，没有培养替代者，技能矩阵上的单点风险越滚越大。

## 9. 项目交接与文档管理

### 9.1 项目交接流程

项目交接是团队管理中最容易被忽视的环节。交接不清会导致：新人上手慢、历史问题反复出现、关键知识丢失。

**交接清单**：

1. **代码交接**：仓库权限、代码结构说明、核心模块文档
2. **文档交接**：架构设计、协议文档、数据库设计、运维手册（第 13 章）
3. **环境交接**：开发/测试/生产环境的配置与访问方式
4. **知识交接**：业务逻辑说明、技术难点、历史问题记录（含历次故障复盘报告——它们是"哪里有坑"最诚实的地图）
5. **人员交接**：协作方介绍、外部依赖的对接人清单

交接期安排：至少 1-2 周的交接重叠期，新人先"跟班"（旁观日常操作、读文档、做小任务），再"接管"（原负责人旁观）。交接结束后保留一段咨询期（原负责人可被随时询问，1-3 个月）。

### 9.2 文档管理规范

文档集中管理、统一目录结构和命名规范：

```
project-docs/
├── README.md                    # 项目概述与文档索引
├── architecture/                # 架构文档与技术决策记录
├── development/                 # 开发规范、协议文档、环境说明
├── operations/                  # 运维手册、应急预案、值班制度
├── postmortems/                 # 故障复盘报告
└── templates/                   # 文档模板（设计文档、复盘报告）
```

比目录结构更重要的两条纪律：

- **文档有 owner**：每份文档写明负责人，负责人负责保持更新。没有 owner 的文档等于没有文档——没人敢信它还是新的
- **过期文档下架**：定期清理，过时文档打"已废弃"标记或删除。文档库里最危险的不是缺文档，而是过时文档——读者按旧方案操作造成的损失比没文档更大

### 9.3 研发效能度量

研发效能度量帮助团队识别改进方向：

| 维度 | 指标 | 说明 |
|------|------|------|
| 交付效率 | 需求交付周期 | 从需求提出到上线的时间 |
| 代码质量 | 缺陷密度、线上故障数 | 每千行缺陷数、每版本 P0/P1 数 |
| 团队效率 | Sprint 完成率 | 计划任务的完成比例 |
| 产品价值 | 功能使用率 | 新功能的实际使用情况 |

度量的两个红线：**不把效能指标用于个人考核**（一旦用于考核，指标就会被优化而不是工作被优化——交付周期会被拆分注水、缺陷会被瞒报）；**看趋势不看绝对值**（团队之间的绝对值不可比，自己和自己比才有意义）。

## 10. 故障的组织管理：无责复盘

第 13 章讲了故障应急的**流程**（止损、定位、修复），本节讲组织侧的**机制**——流程靠制度执行，制度靠文化存活。

### 10.1 无责复盘文化

复盘的核心原则是**对事不对人（blameless）**：追问"系统为什么允许这个错误发生"，而不是"谁犯了这个错"。原因很实际——一旦复盘变成追责会，下次故障的第一个动作就是隐瞒和甩锅，信息不流动的组织学不到任何东西。

无责复盘的操作要点：

- **描述事实链而非行为评价**：写"操作者执行了删除命令且命令没有二次确认机制"，不写"XX 手滑删库"
- **追问系统性原因**：每条人为失误都值得问一句"什么样的机制能让这个失误不发生或被拦截"（权限分级、二次确认、灰度、备份）
- **表扬上报**：第一时间上报自己闯的祸，应该被明确肯定而不是被追罚——信息早到一分钟，止损就早一分钟

### 10.2 复盘报告与改进跟踪

复盘报告的标准结构：时间线（何时发现、何时止损、何时恢复）、影响（多少玩家、多少资产、多长时间）、根因（技术根因 + 流程根因，各至少一条）、改进措施（每条有负责人和期限）。

改进措施的跟踪决定复盘的成败。常见做法是把改进项当作正式任务进 Sprint（不是"有空再做"），在下一次回顾中检查完成情况（与 3.4 节的改进跟踪是同一机制）。同类故障出现第二次时，先查上次的改进项为什么没落地——通常不是技术问题，是跟踪机制问题。

### 10.3 从故障中沉淀文档

每次 P0/P1 复盘的产出应该回填到知识库：应急预案更新（这次的止损路径写进 playbook）、监控补盲（这次靠玩家投诉才发现的，配一条告警）、文档勘误（过时的运维手册修正）。故障是最贵的老师，学费交了就要把笔记留下来。

## 11. 设计决策指南

**何时采用 Scrum vs 看板**

- **Scrum**：需求变化快、需要固定节奏迭代、团队规模 5-9 人
- **看板**：运维导向（GM 工具、活动配置类）、持续交付、工作量波动大

**何时需要完整的设计文档**

- 核心系统（战斗、交易、经济）
- 跨团队协作的接口（协议文档）
- 涉及资产安全的功能
- 预计会反复修改、长期维护的功能

**何时引入 Code Review 的强制门槛**

- 团队超过 3 人
- 有新人加入
- 项目进入维护期（改动者不再是原作者）
- 涉及支付、经济、战斗结算等资产敏感代码

**何时需要专职工具人力**

- 策划频繁手工操作数据（配表、查线上）
- QA 全人肉测试、回归成本高
- 运营/GM 操作没有审批与留痕（第 17 章的配置管线依赖工具支撑）

**何时收紧冻结期**

- 版本发布前 2-3 周（系统级冻结，与第 17 章版本冻结对应）
- 删档测试的放量期（改动会导致数据口径前后不一致，测试结论失真）
- 大版本刚上线的观察期（热修复优先，新需求排队）

**何时必须设阶段门**

- 立项决策没有数据支撑、靠热情推进的项目（预研门是止损阀）
- 团队第一次做该品类（技术可行性与品质标准都没验证过）
- 项目规模大到半途终止的损失不可承受（切片门、CBT 门的价值最大）

## 12. 常见陷阱总结

| 陷阱 | 表现 | 根本原因 | 解决方案 |
|------|------|---------|---------|
| 需求不清就开发 | 开发结果与预期不符 | 缺设计文档 | 先文档后开发，异常处理与验收标准不可省 |
| 串行等待 | 等美术、等服务端，工期翻倍 | 没有并行机制 | 协议先行 + Mock 数据并行开发 |
| 技术约束失译 | "做不了"或默默硬做 | 没有量化翻译 | 程序给数字，策划做权衡，负责人拍板 |
| 敏捷走形式 | 站会变流水账 | 只走流程不改进 | 聚焦阻塞与改进项，跟踪到复查 |
| 技能单点 | 核心模块只有一人会 | 能者多劳无备份 | 技能矩阵识别单点，指定第二深耕人 |
| 接口文档过期 | 联调才发现不一致 | 手工维护文档 | 协议 IDL 化，文档自动生成 |
| 交接不充分 | 新人上手慢、坑反复踩 | 交接期太短 | 1-2 周重叠期 + 复盘报告作知识交接 |
| 复盘变追责 | 隐瞒甩锅，学不到东西 | 无责文化缺失 | 对事不对人 + 表扬上报 |
| 效能指标考核 | 指标被优化、数据失真 | 度量误用 | 指标只看团队趋势，不进个人考核 |
| 阶段门形同虚设 | 项目带病推进、越陷越深 | 沉没成本绑架决策 | 门禁产出量化明确；砍项目在预研期最便宜 |
| 变更一刀切 | 要么被变更驱赶，要么流程名存实亡 | 没有变更分级 | 文案/数值走轻量路径，系统级走完整流程 |
| 外包规格不清 | 批量返工、交付压在关键路径上 | 验收标准没文档化 | 规格先行 + 样品确认 + 管线自动校验 |

## 本章小结

| 问题 | 简答 |
|------|------|
| 游戏研发与普通软件最大的组织差异？ | 内容与技术双流水线（策划/美术/程序/QA 四职能），一个功能横跨四方 |
| 设计文档哪节最不能省？ | 异常处理（掉线/并发/边界）与验收标准——缺失部分上线后都会变成故障 |
| 前后端并行的前提？ | 协议文档先行（IDL 化），客户端用 Mock 开发，整体工期可压缩三成 |
| 程序表达技术约束的正确方式？ | 量化代价（性能数字、工期、风险），把权衡空间留给策划和决策者 |
| 技能矩阵最重要的用法？ | 识别单点风险——只有一人掌握的能力是团队的组织级风险 |
| 无责复盘为什么重要？ | 追责文化让信息隐瞒，组织失去学习能力；对事不对人 + 表扬上报 |
| 复盘改进项怎么落地？ | 当正式任务进 Sprint，下次回顾检查；同类故障再现先查改进项为何未落地 |
| Sprint 之上还有什么节拍？ | 版本里程碑（预研 → 切片 → 量产 → 删档测试 → 上线），阶段门在沉没成本变大前给停止选项 |
| 需求变更怎么管？ | 分级（文案/数值/系统），成本量化后交给产品决策；冻结期只冻系统级 |
| 外包管理的底线？ | 规格先行 + 样品确认 + 自动校验；工具可以外包，玩家数据的访问权不能外包 |
