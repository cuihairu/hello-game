# 03 前端引擎与客户端

> 本章目标：让服务端开发者理解各引擎客户端的约束、网络层工作方式和资源体系，从而做出与客户端匹配的服务端设计——协议选型、超时与重连策略、多端账号身份、响应体积、资源版本接口。不需要会写客户端代码，但需要知道**客户端的约束会反向决定服务端的设计空间**。
>
> **参考书籍**：引擎特性部分参考各引擎官方文档与《百万在线》中的多端适配实践；前后端边界的分析方法参考知识库主线"前后端边界与网络层"一篇。

## 1. 为什么服务端要了解前端引擎

很多服务端开发者觉得"前端是客户端的事，跟我无关"。但现实是：**你的 API 设计、协议格式、消息推送策略，都需要考虑客户端引擎的限制和特性**。

比如，微信小游戏的主包只有 4MB，如果你的协议定义文件太大，客户端根本装不下。再比如，Unity 的 WebSocket 实现在 iOS 后台会被系统挂起，如果你不知道这一点，就会在设计断线重连机制时犯错——把"后台切回前台"误判成"网络异常"，触发不必要的重新登录。

理解前端引擎不是要你去写客户端代码，而是要理解三件事：**客户端的约束条件是什么？客户端的网络层是怎么工作的？客户端的资源管理有什么限制？**

### 1.1 最重要的边界：三类逻辑的划分

前后端协作中大部分长期扯皮，根源是"这块逻辑谁做"没有清晰标准。比较稳妥的划分是把逻辑分成三类：

| 逻辑类别 | 内容 | 归属 | 服务端要点 |
|---------|------|------|----------|
| 表现逻辑 | 特效、动画、镜头、UI 过渡、本地提示 | 客户端 | 无需服务端参与 |
| 交互逻辑 | 输入响应、页面状态、本地校验、局部预测 | 客户端（带边界） | 服务端保留最终裁决 |
| 权威逻辑 | 资源变更、战斗裁决、匹配结果、房间状态、支付结果 | **服务端** | 客户端展示服务端结果 |

前两类留在客户端换取流畅体验；第三类必须由服务端决定。最容易出问题的是边界模糊地带：客户端做了"乐观扣款"（先扣本地钻石再发请求），服务端却没有对账逻辑——一旦请求失败，本地已经扣掉的钻石就成了账目黑洞。**判断标准：任何影响数值、资产、胜负的操作，客户端只能"预期"，不能"决定"。**

### 1.2 引擎选型对服务端的影响

| 引擎 | 语言 | 平台 | 网络方案 | 对服务端的影响 |
|------|------|------|---------|--------------|
| **Unity** | C# | 全平台 | WebSocket/Mirror | 需要连接管理器、心跳机制 |
| **UE5** | C++/蓝图 | PC/主机 | 内置网络框架/UDP | 可能需要自定义 UDP 可靠层 |
| **Cocos Creator** | TypeScript | 小游戏/Web | WebSocket/HTTP | 小游戏包体限制、HTTP 为主 |
| **Godot** | GDScript/C# | 全平台 | MultiplayerAPI | ENet/UDP 可靠层 |
| **LayaAir** | TypeScript/AS3 | 小游戏/Web | WebSocket/HTTP | 类似 Cocos Creator；3D 小游戏常见 |

引擎选型决策树（客户端视角）：

```text
选择什么引擎？
│
├── 微信/抖音小游戏
│   ├── Cocos Creator（生态最好）
│   └── LayaAir（3.0 性能优化好）
│
├── 手游（iOS/Android）
│   ├── Unity（人才最多，生态成熟）
│   └── Cocos Creator（小游戏+手游一体化）
│
├── PC/主机 3A
│   ├── Unreal Engine 5（画面顶级）
│   └── Unity（中等品质，效率高）
│
└── 独立游戏
    ├── Godot（开源免费，MIT 协议）
    ├── Unity
    └── Unreal Engine
```

从服务端视角看这棵决策树：**前两类（小游戏、手游）基本都是 WebSocket + Protobuf 的组合**，服务端只需要一套接入协议；UE5 项目则需要考虑 UDP 自定义协议；如果产品同时覆盖小游戏和 App（很常见的发行策略），服务端需要**同一套逻辑服务两种接入形态**——协议层统一，接入层按平台分流。

### 1.3 多端发行的服务端深水区：一个人的多个 ID

"同一套逻辑服务两种接入形态"落到账号体系上，就是多端发行最典型的难题：**同一个真实玩家，在不同平台是不同的平台身份**。

| 平台侧身份 | 获取方式 | 可信范围 | 备注 |
|-----------|---------|---------|------|
| openid（微信） | code2session | 仅当前 appid 内唯一 | 同一主体下不同小程序/App 的 openid 不同 |
| unionid（微信） | 绑定微信开放平台后随登录返回 | 同一开放平台主体下跨端唯一 | **App 不绑开放平台就拿不到** |
| 手机号 | 运营商一键登录 / 短信验证码 | 跨一切平台稳定 | 最可靠的跨端锚点，但有成本与覆盖率问题 |
| 游客 ID | 设备标识 / 客户端生成 UUID | 仅本设备 | 卸载、换机即丢失，必须支持后续升级绑定 |

服务端需要一张独立的身份绑定表，以游戏内 UID 为中心挂载多条平台身份：

```sql
CREATE TABLE user_identity (
  id_type    TINYINT  NOT NULL,     -- 1=wechat_openid 2=unionid 3=phone 4=guest
  id_value   VARCHAR(128) NOT NULL,
  uid        BIGINT   NOT NULL,     -- 游戏内唯一 ID
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id_type, id_value),
  KEY idx_uid (uid)
);
```

登录时的判定逻辑很直接：按 `(id_type, id_value)` 查 `uid`，命中就登录；未命中就创建新玩家并写入绑定。麻烦全部出在**合并冲突**：玩家以游客身份玩了一周（uid=1001，充值过），某天用微信登录——而这个微信身份此前已在另一台设备建过 uid=2002。两个 uid 都有真实资产，不能悄悄丢掉任何一个。常见的裁决方式：

- **让玩家自己选**（保留哪个进度），而不是后台自动合并——背包、充值记录、排行榜名次的合并规则没有让所有人信服的普适答案，自动合并几乎必然产生客诉
- 若产品决定自动合并，被合并账号进入一段"可申诉冻结期"，期间允许客服按记录回滚
- 身份锚点分可信级：unionid、手机号是高可信锚点；openid 只在 appid 内可信；**不要用"昵称相同"之类弱信号做合并依据**

> **陷阱**：很多团队小游戏 + App 双端上线后才发现账号不互通，根因是 App 侧没有走微信开放平台的绑定流程——拿不到 unionid，openid 又天然不互通，此时只能靠手机号补绑，错过的是整整一个运营周期。**双端立项时就要确认身份锚点方案**，这是服务端在立项评审里该主动问的问题。

## 2. Unity：手游市场的中坚

### 2.1 Unity 客户端网络层的典型结构

Unity 客户端的网络层通常分为四层：**传输层**（WebSocket/TCP/KCP）→ **协议层**（Protobuf/JSON）→ **消息分发器**（Dispatcher）→ **游戏逻辑层**。

对服务端有意义的是两点。其一，Unity 的 WebSocket 在不同平台行为有差异：iOS 在后台会挂起连接，Android 省电模式下限制网络活动。这要求服务端的超时判定足够宽容——**"暂时沉默"不等于"掉线"**。其二，Unity 项目通常用 async/await 处理网络 I/O，客户端对几十毫秒的响应延迟不敏感，但这不是忽视性能的理由——高延迟在战斗、抽卡等关键交互上会被玩家直接感知。

心跳超时阈值可以按一个简单的推导来定：

```text
超时阈值 ≥ 客户端最长合法静默时长 + 网络最大抖动 + 服务端处理余量
```

问题在于"最长合法静默时长"在移动端没有一个稳定值：iOS 切后台典型几分钟、用户回来连接自动恢复；部分 Android 厂商的省电策略下静默可达 10 分钟以上。若心跳间隔 10 秒、阈值 30 秒（容忍丢 2 个心跳），切后台玩家会被批量误判掉线——而他们几分钟后回来，不该承受重新登录和状态丢失。

所以移动端长连接普遍采用**显式挂起**代替猜测：客户端切后台时发 `suspend` 包，切回前台发 `resume` 包。服务端收到 suspend 就冻结该会话的心跳计时，按"宽限期"（分钟到半小时量级，按产品形态定）管理，宽限期内资源不释放、消息继续入队；resume 则恢复计时并补发离线期间的消息。宽限期超时才真正断开、走完整的重连流程。**判定"掉线"的依据从"没收到心跳"变成"客户端说挂起后宽限期已过"**，误判率会下降一个量级。没有 suspend/resume 时，退而求其次的做法是把心跳阈值放宽到分钟级，代价是真正的死链要几分钟后才能回收。

### 2.2 协议对接的三件套

Unity 团队通常使用 Protobuf + WebSocket。服务端需要提供：

1. **Protobuf 定义文件**（.proto）：客户端和服务端共享同一份协议定义，由它生成两端的编解码代码（见第 4 章协议治理）
2. **消息 ID 编码规则**：模块(8bit) + 动作(16bit) + 类型(8bit)，两端用同一张 ID 常量表
3. **错误码体系**：统一格式，客户端按错误类型决定是弹窗、toast 还是静默重试

### 2.3 常见问题与服务端应对

| 问题 | 原因 | 服务端应对策略 |
|------|------|--------------|
| 消息粘包 | TCP 流式传输 | 消息头包含长度字段（见第 4 章拆包器） |
| 断线后状态丢失 | 客户端缓存过期 | 提供状态快照接口 |
| 大消息包拆分 | 协议限制 | 支持分包发送 + 消息重组 |
| SSL 证书问题 | 平台差异 | 证书链完整、兼容系统证书库 |
| 后台连接被杀 | iOS/Android 限制 | 断线重连机制 + 状态恢复 |

其中"断线重连 + 状态恢复"值得展开，因为它是设计出来的而不是补出来的。服务端需要一组配套接口：**会话保持**（连接断了会话 token 还在，重连携带 token 免重新登录）、**增量恢复**（客户端上报自己最后收到的序列号，服务端只补发缺口，而不是全量重推）、**快照兜底**（缺口太大时直接发全量快照，比补几百条消息更便宜）。补发窗口可以用环形缓冲实现：

```go
// 会话：连接断开后并不销毁，而是进入"待重连"状态
type Session struct {
    UID       int64
    Token     string        // 会话凭证；重连校验通过即复用，无需重新走登录
    SendSeq   uint64        // 本会话已下发的最后一条消息序号
    Pending   *RingBuffer   // 未确认消息的环形缓冲（容量 = 补发窗口）
    Snapshot  func() []byte // 全量快照生成器（业务层注册，兜底用）
}

// 重连处理：客户端携带 token 和它最后收到的 seq
func (s *Session) OnReconnect(conn Conn, lastAck uint64) error {
    gap := s.SendSeq - lastAck
    if gap == 0 {
        return nil // 没有缺口，直接恢复收发
    }
    if gap <= uint64(s.Pending.Cap()) {
        // 缺口在补发窗口内：按序重放，客户端按序号去重
        return s.Pending.Replay(conn, lastAck+1)
    }
    // 缺口太大（窗口外的消息已不在内存）：快照兜底更便宜
    conn.Send(&Msg{Type: MsgSnapshot, Body: s.Snapshot()})
    return nil
}
```

三个设计点值得注意。**补发窗口的大小是内存与快照成本的权衡**：窗口越大，能覆盖的断线场景越多，但每个待重连会话占的内存越多——万人在线、每人窗口 1000 条消息，就是千万元素级常驻内存。**快照生成器由业务层注册**，因为"什么算完整状态"只有业务知道；这也是为什么快照兜底通常按模块拆（背包快照、房间快照），而不是一个大而全的状态序列化。**SendSeq 是会话级的**，重连不重置——客户端的"我收到哪了"以序号为准，不以连接为准。这套机制与第 4 章广播设计、知识库主线"一致性、恢复与重连"一篇是同一套东西的客户端视角。

## 3. Cocos Creator 与小游戏平台

Cocos Creator 是微信小游戏、抖音小游戏的主流引擎。它的技术特性和平台限制直接影响服务端设计。

### 3.1 小游戏平台的硬性约束

微信小游戏有一系列硬性约束，这些约束不是"建议"而是"限制"：

- **包体大小**：主包 4MB + 分包 20MB（总包上限随版本调整，以平台文档为准）。协议定义文件、首屏配置都要算进首包预算
- **内存限制**：iOS/Android 有上限（机型相关），客户端不能缓存太多数据——服务端下发的列表类接口要支持分页，客户端可能随时丢弃非当前页数据
- **域名白名单**：只能连接备案过的白名单域名，上线前必须配置——包括 WebSocket 域名和 CDN 域名，漏一个就是线上事故
- **开放数据域隔离**：好友排行榜等社交数据运行在独立的数据域，与主域不能直接通信，只能通过特定接口交换——服务端设计排行榜时要知道"平台好友关系"走平台开放数据，"游戏内好友"才走自己的服务

这些约束的汇总含义：**API 响应体积要小**。用同一个排行榜数据实际量一下两种编码的差距：

```go
type PlayerBrief struct {
    UID    int64  // varint，小数值实际 1-2 字节
    Name   string // UTF-8，长度前缀 + 内容
    Level  int32
    Score  int64
    Avatar string // URL，通常是最大头
}

// 100 人排行榜，同一份数据的序列化体积对比：
func compareSizes(players []PlayerBrief, pbPlayers *pb.RankList) (int, int) {
    jsonBytes, _ := json.Marshal(players)     // ≈ 14 KB —— 字段名每人重复一遍是大头
    protoBytes, _ := proto.Marshal(pbPlayers) // ≈ 3 KB  —— 字段号编码，字段名只在 .proto 里出现一次
    return len(jsonBytes), len(protoBytes)
}
```

差距的来源有两个：JSON 每条记录都重复传输字段名（`"uid":10001,"name":"..."`），Protobuf 只传字段号和值；整数值在 Protobuf 里走 varint 变长编码，等级 35 这样的数只要 1 字节。对小游戏来说这不只是流量——还是弱网下的加载等待时间和客户端内存占用。**列表类接口的验收标准里应该写上响应体积上限**（常见做法是 5KB 以内），而不是等客户端抱怨加载慢再回头裁字段。裁字段的优先级：先裁"客户端当前页用不到的"，再考虑列表接口不返回大字段（头像 URL 换成头像 ID，由客户端拼 CDN 地址）。

### 3.2 网络层特点：一切自己造

Cocos 的 WebSocket 实现接近浏览器原生 API：没有内置重连机制、没有内置消息队列（连接断开时发送即丢失）、心跳要自己实现。这意味着小游戏的客户端网络层质量**高度依赖团队自建**，服务端要按"客户端不可靠"来设计：消息带序列号便于客户端去重、关键接口幂等（同一个请求重发不产生副作用）、断线期间的推送允许客户端回来后拉取（推送 + 拉取兜底的双通道设计）。

### 3.3 小游戏的登录链路

小游戏登录有一个平台特有的时序，服务端必须实现对应接口：

```text
1. 客户端调用 wx.login() 获得 code（临时凭证，5分钟有效）
2. 客户端把 code 发给你的服务端
3. 服务端拿 code + appid + secret 调微信 code2session 接口
   → 换得 openid（用户唯一标识）+ session_key
4. 服务端绑定 openid ↔ 游戏账号，签发自己的会话 token
5. 之后所有请求带游戏会话 token，不再依赖微信会话
```

要点：**secret 只能放在服务端**；session_key 用于解密平台敏感数据，不要下发给客户端；会话过期与微信态解耦——玩家可能微信在线但你的会话已过期，也可能反过来，两条过期路径都要处理。

服务端 handler 的骨架大致是：

```go
func (h *LoginHandler) WxLogin(ctx context.Context, code string) (*LoginResult, error) {
    if code == "" {
        return nil, ErrEmptyCode
    }
    // code 是一次性的：同一个 code 第二次调 code2session 会被微信拒绝。
    // 本地先做一次性标记，把重放请求挡在自己这一层，也避免无效请求打到微信侧限流
    if !h.codeSeen.MarkOnce(code, 5*time.Minute) {
        return nil, ErrCodeReplay
    }
    resp, err := h.wx.Code2Session(ctx, h.appID, h.appSecret, code)
    if err != nil {
        return nil, fmt.Errorf("code2session: %w", err)
    }
    // openid 仅在当前 appid 内唯一；unionid 只有绑定了开放平台才可能有值（见 1.3）
    uid, err := h.identities.ResolveOrCreate(ctx,
        IdentityWechatOpenID, resp.OpenID,
        IdentityUnionID, resp.UnionID) // 可能为空，空则跳过该锚点
    if err != nil {
        return nil, err
    }
    // session_key 只在需要解密手机号等敏感数据时使用：留在服务端、短 TTL、用完即弃
    // 会话 token 是自家签发的，有效期、续期、踢人均与微信态无关
    token, err := h.sessions.Issue(uid, 7*24*time.Hour)
    if err != nil {
        return nil, err
    }
    return &LoginResult{UID: uid, Token: token}, nil
}
```

两个容易遗漏的细节。**code2session 是外部调用，要有超时与降级**：微信侧偶发超时会让玩家卡在登录页，超时设置通常在 2-3 秒量级，连续失败时返回明确的"登录服务繁忙"而不是无限转圈。**ResolveOrCreate 是并发热点**：同一玩家双击登录、断线重连竞态都可能并发到达，`(id_type, id_value)` 的唯一键 + 插入冲突时回查是标准处理方式（依赖数据库唯一约束做幂等，与第 8 章落库策略同理）。

### 3.4 小游戏的服务端适配清单

```text
小游戏服务端适配检查清单：

□ 1. API 响应体积控制在 5KB 以内，列表接口分页
□ 2. 使用 Protobuf 而非 JSON（体积减少 60-80%）
□ 3. 实现断线重连机制（小游戏切前后台极频繁）
□ 4. suspend/resume 挂起协议 + 宽限期（区分"切后台"与"真掉线"）
□ 5. 状态快照 + 增量恢复接口（重连后恢复状态）
□ 6. 域名白名单配置（WebSocket 域名 + CDN 域名）
□ 7. 分包资源的 CDN 地址管理
□ 8. 微信登录链路（code2session + code 防重放）与支付异步通知
□ 9. 身份锚点方案确认（unionid 可用性 / 手机号补绑路径，双端发行前置）
□ 10. 防刷机制（小游戏环境更容易被脚本批量访问）
□ 11. 推送 + 拉取双通道（断线期间的推送可回补）
```

## 4. Unreal Engine 5：3A 品质的代价

UE5 是 3A 游戏的首选引擎，网络框架非常成熟，也非常复杂。服务端开发者需要理解 UE5 的网络模型，才能正确对接。

### 4.1 权威服务器模型

UE5 使用**权威服务器（Dedicated Server）**模型：服务端是游戏世界的权威，客户端是"观察者"和"输入者"。客户端可以做预测（Prediction），但最终结果由服务端校验（Validation）。这与本书反复强调的"服务端权威"原则完全一致——UE5 把这套理念做成了引擎内置设施。

核心网络机制：

- **属性同步（Replication）**：服务端自动将 Actor 属性同步到客户端，支持条件同步（只有变化时、只对相关玩家）
- **RPC**：客户端/服务端远程过程调用，区分可靠/不可靠
- **Actor 复制**：整个 Actor 在服务端和客户端之间同步，配合相关性（Relevancy）控制同步范围

### 4.2 与自定义服务端的协作

很多项目用 UE5 做客户端，但用 Go/Java 做自定义服务端（而不是 UE5 Dedicated Server）——因为大世界的账号、社交、经济、跨服逻辑用通用后端技术栈更高效。这种混合模式下：

- UE5 内实现一个 NetworkComponent，处理与自定义服务端的连接管理、消息收发、心跳
- 战斗/物理等强引擎相关的部分留在 UE5 Dedicated Server，账号/交易/社交走自定义服务端
- 两类服务端之间需要一个内部协议桥接（通常是 gRPC 或内部 TCP 协议）

### 4.3 特殊挑战

| 挑战 | 原因 | 解决方案 |
|------|------|---------|
| UDP 可靠性 | UE5 默认用 UDP | 引擎自带可靠性层；对接自定义服务端时用 KCP/QUIC |
| 大规模同步 | MMO 场景 | 分组同步 + AOI（兴趣区域管理） |
| 属性同步冲突 | 多端同时修改 | 服务端权威 + 客户端预测 + 服务器回滚纠正 |
| 跨平台差异 | PC/主机/移动端 | 分平台适配网络参数和同步频率 |

### 4.4 预测与纠偏的服务端配合

"服务端权威 + 客户端预测 + 回滚纠正"（reconciliation）这行表格里的机制，服务端侧的配合决定了纠偏的体验。流程是：客户端对本地输入做**预测**（立即表现移动结果），每条输入带输入序号发给服务端；服务端按权威逻辑**裁决**，把结果连同"已裁决的输入序号"广播下发；客户端发现某条输入的权威结果与自己的预测不一致，从那条输入起**本地重演**后续输入。

服务端要注意三件事：

- **逐输入即时回，不要攒批**。为省带宽把多条输入的裁决攒在一个包里下发，客户端的重演就要滞后——纠正延迟越大，回滚幅度越猛，玩家看到的是画面"突刺"。带宽优化的正确位置是压缩编码与合并不可靠更新（第 4 章），不是延迟纠正包
- **纠正包必须带被裁决的输入序号**。缺了它客户端无法定位从哪条开始重演，只能整体重同步（画面回跳），体验比不纠正还差
- **预测偏差率是风控信号**。正常客户端的预测偏差应该在很小的百分比内波动；偏差率持续异常（服务端总是否决同一步移动）往往意味着客户端被篡改，可接入第 18 章的风控指标体系

## 5. Godot：开源引擎与独立游戏的取舍

Godot 是商业引擎之外存在感持续上升的一支：MIT 协议完全开源，零授权费、无分成条款，引擎源码随项目分发、可读可改。4.x 重写渲染器后，2D 工作流与运行时补齐了长板（2D 与 3D 共用一套场景树，2D 不是 3D 的降维投影），买断制独立游戏里已经有一批公认作品用它交付——Brotato、Dome Keeper、Buckshot Roulette。对服务端的定位一句话：这些项目多以小团队、P2P 或轻后端形态起步，但一旦接自定义权威服务端，Godot 就是一个普通网络客户端，8.3 节的标准客户端网络层原样适用。

### 5.1 客户端网络层的典型结构

Godot 的高层多人能力是 **MultiplayerAPI**：传输由 **MultiplayerPeer** 的实现提供，内置 ENet（UDP 加可靠层）、WebSocket、WebRTC 三种实现，也可用 StreamPeer 自接；逻辑侧用 `@rpc` 注解声明远程调用（区分可靠/不可靠、any_peer/authority），配合 MultiplayerSpawner 与 MultiplayerSynchronizer 做节点生成和属性同步。它的默认心智是**房间对等架构**：peer 1 是主机，既可以当专用服务器，也可以由某个玩家的客户端充当，其余 peer 连向它——一局一服的房间模型，天然匹配合作/竞技小局与 P2P 托管，也是 1.1 节「权威归服务端」边界经常失守的架构：

```text
房间对等（MultiplayerAPI 默认）         自定义权威（自研服务端）
peer 1 = 主机（玩家客户端或 Godot 专服）  Go/Java 权威服务端（普通 WS/TCP 入口）
peer 2/3/4 连向主机，流量可 P2P 直连      各客户端连服务端，绕开 MultiplayerAPI
RPC 帧与 peer 握手 = Godot 私有格式       协议帧 = Protobuf/JSON，两端各自编解码
```

对接自定义权威服务端时结论明确：**绕开 MultiplayerAPI，按普通 WebSocket/TCP 客户端对接**。原因有二：其一，高层多人协议（peer 握手、RPC 帧）是 Godot 私有格式，Go/Java 侧没有对等实现；其二，ENet 的可靠 UDP 层同样是私有协议，与自研 KCP 网关不互通——让服务端讲 ENet 是反向适配，正确方向是服务端入口收敛 WebSocket/TCP（强实时另配 KCP，第 4 章）。绕开之后，8.3 节的四层结构（传输 → 协议 → 分发 → 逻辑）自己搭一遍即可；平台后台策略对连接的影响也回到 2.1 节的老问题——suspend/resume 显式挂起与引擎无关，Godot 项目同样适用。

### 5.2 协议对接

默认路径是 HTTP/REST + JSON 起步（内置 HTTPRequest/HTTPClient），长连接用 WebSocketPeer 自组帧。序列化的坑在二进制：Godot 内置的 Variant 序列化（`var_to_bytes`/`bytes_to_var`）是引擎私有格式、大版本间有变动，而且 `bytes_to_var` 能还原任意 Variant——跨语言服务端既难解析，也不该信任客户端发来的 Variant 字节（反序列化面即攻击面）。跨端协议回到通用格式：Protobuf 或 JSON（第 4 章序列化选型口径）。Godot 没有官方自带的 Protobuf 插件，社区生成器覆盖参差，选型时把「同一份 .proto 能同时产出 GDScript 与 C# 两侧代码」当验收条件；用 C#（.NET）版的项目可直接复用官方 C# Protobuf 生态，与 Unity 项目共享同一套生成产物。三件套不因引擎而变：.proto 单一来源、消息 ID 常量表、统一错误码体系（2.2 节）——语言换了，清单照旧。

### 5.3 常见问题与服务端应对

| 问题 | 原因 | 服务端应对策略 |
|------|------|--------------|
| 高层 RPC 连不上自研服务端 | MultiplayerAPI 默认 peer 架构，peer 1 即服务器 | 客户端绕开高层 API，按普通 WebSocket/TCP 对接（8.3 节标准结构） |
| 服务端被迫实现 ENet | ENet 可靠层是私有协议，Go 侧无成熟实现 | 服务端入口收敛 WebSocket/TCP（强实时另配 KCP），不做反向适配 |
| `bytes_to_var` 解析失败或被注入 | Variant 序列化是引擎私有格式且可嵌对象 | 跨端协议用 Protobuf/JSON；Variant 字节不出引擎边界 |
| 大版本升级协议错位 | Godot 4.x 大版本间 GDScript 与序列化有破坏性变更 | 协议自带版本字段 + 最低可玩版本拦截（8.6 节） |
| Web 导出线上白屏 | CDN/网关剥掉 COOP/COEP 响应头 | 两个响应头配置进 CDN 与网关并纳入巡检（5.5 节） |

### 5.4 与 Unity 的取舍

两者的比较集中在三处。授权结构：MIT 零授权费、无分成条款对买断制小团队是真实成本差；Unity 按席位订阅，且 2023 年运行时收费方案提出又撤回，条款确定性经历过一轮信任重建。生态与管线：Unity 的素材商店、广告/归因/支付 SDK 链路与人才池更大，手游商业化开箱即用；Godot 的对应环节多要自封装或依赖社区插件。技术边界：两者都能覆盖 2D 买断制与常规手游，UE5 级别的重度 3A 画面不在 Godot 的常规射程。对服务端，这场争论几乎无感——协议、超时、重连都由团队自定，服务端不感知引擎；需要提前写进立项评审的只有两条：目标平台含小游戏时 Godot 链路缺位（3.1 节），Web 端用 Godot 4 时 COOP/COEP 是硬前提（5.5 节）。

### 5.5 多端发行注意

- **PC/Steam 主场**：GodotSteam（社区扩展）让 Steamworks 的成就、云存档、大厅、网络中转、票证等接口全部可用，独立项目的发行链路围绕它搭建。服务端两点：Steam 票证要在服务端校验（防伪票与重放）；启用 Steam 网络中转时玩家流量可能不经过你的服务器，服务端的「在线」口径要与平台状态对账
- **移动端**：iOS/Android 导出链路可用，但推送、支付、广告等平台 SDK 官方多只提供 Unity/Cocos 版本，Godot 项目靠自封装插件——登录凭证与支付回调的格式要在两端提前对齐，别让客户端在联调期现场发明
- **主机**：主机平台层因平台方 NDA 不在开源仓库内，导出能力经平台授权与第三方移植合作获得；立项排期要把这段外部依赖周期算进去
- **小游戏**：官方没有微信/抖音小游戏导出链路，社区适配方案属实验性质——小游戏立项直接回到 3.1 节硬约束选型，不要把 Godot 塞进小游戏排期
- **Web**：Godot 4 的 Web 导出依赖 SharedArrayBuffer，站点必须携带 COOP/COEP 两个响应头，且 CDN 与网关不得剥掉它们——缓存层剥头是线上白屏的常见根因（8.5 节），这是引擎需求反向写进服务端/运维配置的典型

## 6. LayaAir（Layabox）：小游戏生态的另一支主力

LayaAir 是 Layabox 团队的小游戏/H5 引擎，与 Cocos Creator 同属小游戏生态的主力选型：1.x/2.x 提供 ActionScript3 与 TypeScript 双语言，3.x 收敛为纯 TypeScript 并重写了架构。引擎库轻量，在小游戏首包预算里占位小；3D 能力自 2.x 起就在小游戏场景里打磨，3D 类小游戏立项时常与 Cocos Creator 同台比较。对服务端的定位一句话：网络链路与 Cocos 完全同构（3.2 节），按 3.4 节清单适配一遍即可同时覆盖两个引擎；增量认知在「三代引擎并存」的版本碎片上。

### 6.1 客户端网络层的典型结构

LayaAir 的网络层与 Cocos 同构：引擎只提供基础件——Socket 封装（WebSocket 连接管理、事件回调）与 Byte 二进制读写（大小端、类型化字段），没有内置的多人框架或状态同步，8.3 节的四层结构（传输 → 协议 → 分发 → 逻辑）同样由项目自建。两个值得服务端知道的细节：其一，Byte 类自带大小端与类型化读写，客户端习惯用它自组二进制帧——AS3 时代（ByteArray）的存量项目尤其常见自定义二进制协议而非 Protobuf，7.1 节 Cocos2d-x 的提示在这里同样成立；其二，小游戏容器里的 WebSocket 由平台代理，切前后台与心跳行为回到 3.1 节的平台约束，2.1 节的 suspend/resume + 宽限期骨架照用。

### 6.2 协议对接

默认组合与 Cocos 一致：WebSocket + Protobuf/JSON（第 4 章序列化选型口径），TypeScript 侧直接用 protobuf.js；AS3 存量项目多用 ByteArray 自组二进制协议或 AS3 生态的 Protobuf 移植库。三件套照旧：.proto 单一来源、消息 ID 常量表、统一错误码体系（2.2 节）。服务端要注意的 LayaAir 特有项是**代际碎片**：1.x/2.x（AS3 + TS）与 3.x（纯 TS、架构重写）互不兼容，同一产品跨代际升级时服务端面对的是两套客户端编解码实现并存——协议兼容窗口要按引擎代际算（8.6 节），而不是按版本号线性算。

### 6.3 小游戏平台约束与服务端应对

包体、内存、白名单、开放数据域四条硬约束与登录链路对 LayaAir 同样成立（3.1 节、3.3 节），差异只在触发概率和长尾：

| 问题 | 原因 | 服务端应对策略 |
|------|------|--------------|
| 首包超限提审被拒 | 引擎库 + 首场景资源挤占 4MB 主包红线（3.1 节） | 引擎库瘦身 + 分包下发配合，资源走 CDN（8.5 节） |
| 请求域名漏配白名单 | 小游戏容器只放行白名单域名，3D 小游戏资源域名更多 | 域名清单纳入上线 checklist 并演练（3.4 节清单第 6 条） |
| AS3 存量客户端协议长尾 | 1.x/2.x AS3 项目仍在运营，代际不互通 | 协议层按代际兼容 + 最低可玩版本拦截（8.6 节） |
| 3D 资源加载拖垮弱网体验 | 3D 小游戏资源体量大于 2D，弱网等待被放大 | 响应体积上限 + 列表分页（3.1 节）+ CDN 预热（8.5 节） |

### 6.4 与 Cocos Creator 的取舍

两者的比较集中在三处。生态：Cocos 的社区规模、文档教程与招人面更宽，LayaAir 生态集中在小游戏尤其是 3D 小游戏场景。技术栈：3.x 两侧同为 TypeScript；LayaAir 1.x/2.x 的 AS3 存量是真实的迁移包袱。3D 时间线：LayaAir 自 2.x 起就主打小游戏 3D，Cocos Creator 到 3.0 才合并 3D 能力——这是不少 3D 小游戏选 LayaAir 的历史原因。对服务端，这场取舍同样几乎无感：WebSocket + Protobuf + code2session 登录链路是两引擎共用的同一套（3.3 节），按 3.4 节清单做一次适配即可两端通吃；立项评审真正要有人认领的还是那两件事——白名单域名清单与包体/内存红线。

### 7.1 Cocos2d-x（Lua）

## 8. 前后端协作的核心要点

### 8.1 协议格式的选择

| 格式 | 体积 | 编解码速度 | 强类型 | 代码生成 | 适用场景 |
|------|------|-----------|--------|---------|---------|
| **Protobuf** | ★★★★★ | ★★★★ | ✓ | ✓ | 大型游戏（主流选择） |
| **FlatBuffers** | ★★★★★ | ★★★★★ | ✓ | ✓ | 高性能热路径 |
| **MessagePack** | ★★★★ | ★★★ | ✓ | ✓ | 中型游戏 |
| **JSON** | ★★ | ★★ | ✗ | ✗ | 管理接口/原型 |

大型游戏用 Protobuf，极致性能场景用 FlatBuffers，管理后台和原型用 JSON——**按链路选格式，不搞一刀切**（详细对比与兼容性纪律见第 4 章）。

### 8.2 客户端-服务端交互模式

```text
模式1：请求-响应（最常用）
客户端 ──请求──→ 服务端 ──响应──→ 客户端
适用：登录、商店、背包、排行榜

模式2：服务端推送
服务端 ──推送──→ 客户端
适用：公告、活动通知、排行榜更新

模式3：实时同步（状态同步）
客户端 ──输入──→ 服务端 ──状态广播──→ 所有客户端
适用：MMO、实时对战

模式4：帧同步
客户端 ──输入──→ 服务端收集 ──帧广播──→ 所有客户端计算
适用：MOBA、RTS
```

四种模式的协议诉求不同：模式 1/2 走可靠通道，带请求 ID 和错误码；模式 3/4 带序列号和时间戳，允许丢旧保新（第 4 章）。**在协议设计期就标注每条消息属于哪种模式**，比上线后再区分容易得多。

### 8.3 客户端网络层的标准结构

服务端要对接的其实是一个"标准形态"的客户端网络层，了解它有助于服务端提供正确的配套：

```text
┌─────────────────────────────────────────┐
│              游戏逻辑层                   │
│   发起请求（带回调）/ 接收推送更新状态      │
├─────────────────────────────────────────┤
│           消息分发器 Dispatcher           │
│   按 MsgID 路由到注册的处理函数             │
├─────────────────────────────────────────┤
│              请求管理器                   │
│   请求队列 + 超时重试 + 序列号 + 去重       │
├─────────────────────────────────────────┤
│        传输层（WebSocket/TCP/KCP）        │
│   连接管理、心跳、断线重连、编解码           │
└─────────────────────────────────────────┘
```

服务端与之对应的配套责任：请求 ID 原样返回（客户端超时重试后按 ID 丢弃重复响应）、消息序列号（客户端断线回来报出最后序列号，服务端增量补发）、心跳应答（服务端要回 pong，客户端据此测 RTT）、关键接口幂等（重试不产生副作用）。

### 8.4 联调期的工程配套

前后端联调的效率不取决于沟通态度，取决于工程配套：

- **接口文档自动生成**：从 .proto / IDL 直接生成文档，禁止手工维护 Word——手写文档与代码的漂移是联调扯皮第一来源
- **Mock 服务**：协议定义完成后、服务端实现前，客户端可以先对接 mock 数据联调 UI；服务端也可以用 mock 客户端做压测
- **环境分层**：开发/测试/预发布/生产四级环境，协议版本和配置版本逐级验证；联调环境的服务端要能一键重置数据
- **联调期常见问题**与约定：

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 消息丢失 | 网络抖动 | 重试机制 + 消息 ID 去重 |
| 消息乱序 | UDP / 并发处理 | 序列号 + 接收缓冲区重排 |
| 版本不兼容 | 前后端不同步发布 | 协议版本号 + 兼容窗口（见第 4 章） |
| 状态不一致 | 客户端预测偏差 | 服务端权威 + 校验纠正包 |
| 性能瓶颈 | 消息过多过碎 | 消息合并 + 优先级（见第 4 章） |

### 8.5 CDN 与资源分发

CDN（内容分发网络）是游戏客户端资源分发的核心基础设施。对服务端开发者来说，理解 CDN 是为了设计资源更新策略和排查资源加载问题。

**CDN 在游戏中的三大用途**：

| 用途 | 说明 | 典型场景 |
|------|------|---------|
| **热更新资源** | 客户端代码、Lua/JS 脚本、配置表 | 版本更新、Bug 修复、活动配置 |
| **静态资源** | 图片、音频、视频、预制体 | 美术资源、UI 素材、过场动画 |
| **配置下发** | 活动配置、公告、版本信息 | 运营活动、紧急公告 |

**工作原理**：客户端请求资源 → DNS 解析到就近 CDN 节点 → 节点缓存命中直接返回（最快）；未命中则回源到源站，缓存后返回。对游戏热更来说，通常的流程是：

```text
1. 服务端生成版本号 + 资源清单（manifest）
2. 客户端启动时请求版本号
3. 对比本地版本，计算差异资源
4. 从 CDN 下载差异资源
5. 客户端加载新资源，完成热更新
```

**CDN 选型考虑**：节点覆盖（国内/海外、城市层级）、回源带宽成本、缓存策略（静态资源长缓存、配置短缓存）、HTTPS 支持、防盗链、预热功能（新版本上线前把资源推到各节点）。

**服务端与 CDN 的协作**：

- **版本管理**：服务端维护版本号和资源清单，客户端通过 CDN 下载资源
- **灰度发布**：按渠道/区域/比例下发不同版本的清单
- **回滚机制**：服务端切换版本号指针，客户端下载旧版本资源（资源文件按版本保留，不覆盖）
- **监控告警**：CDN 下载失败率、回源率、延迟监控

> **实战经验**：CDN 的缓存刷新不是实时的。新版本上线时，要确保资源文件名带版本号或内容哈希（如 `bundle_a3f9c2.bundle`），而不是依赖 CDN 缓存刷新。这样即使 CDN 缓存未更新，客户端也能通过新文件名获取最新资源——**内容寻址代替缓存失效**，是所有 CDN 场景的第一原则。

### 8.6 资源版本管线的服务端视角

资源系统连接着内容生产、版本发布、运行时内存和线上修复能力，服务端在其中承担的接口职责：

- **版本检查接口**（checkversion）：客户端上报平台、渠道、当前版本，服务端返回最新版本号、清单地址、是否强制更新
- **清单接口**：资源清单本身走 CDN，但清单的**索引**由服务端下发——这样切换版本、灰度、回滚都只是服务端改指针
- **强制更语义**：兼容性破坏的版本必须能强制升级（返回"最低可玩版本"，低于它的客户端拦截进入更新页）
- **下载兜底**：CDN 大面积故障时的备用源（源站限流直下）是最后手段，平时不用但要演练

版本检查接口的核心逻辑不长，值得完整看一遍：

```go
// 版本比较必须按数值逐段比，不能按字符串比：
// 字符串序里 "9.9.10" < "9.9.9"，会把最新版误判为旧版
func compareVersion(a, b string) int {
    as, bs := strings.Split(a, "."), strings.Split(b, ".")
    for i := 0; i < len(as) || i < len(bs); i++ {
        av, bv := 0, 0
        if i < len(as) {
            av, _ = strconv.Atoi(as[i])
        }
        if i < len(bs) {
            bv, _ = strconv.Atoi(bs[i])
        }
        switch {
        case av < bv:
            return -1
        case av > bv:
            return 1
        }
    }
    return 0
}

func (h *VersionHandler) CheckVersion(platform, channel, cur string) *VersionInfo {
    // 不同渠道可以处在不同版本（渠道审核节奏不同是常态）
    latest := h.rules.Latest(platform, channel)
    info := &VersionInfo{
        Latest:   latest.String(),
        Manifest: h.manifestURL(latest), // 清单地址指向 CDN；切版本/回滚只改这里
    }
    if compareVersion(cur, h.rules.MinPlayable(platform, channel)) < 0 {
        info.ForceUpdate = true // 低于最低可玩版本：客户端拦截进更新页
    }
    return info
}
```

**灰度也命中在这个接口上**：按渠道、UID 尾号、设备白名单等维度决定不同玩家拿到哪个 `latest`，实现上只是 `h.rules.Latest` 内部多一层分流规则——灰度策略与兼容窗口的完整设计见第 17 章。

资源打包策略（首包/分包/热更划分、依赖治理）属于客户端工程，但其产物——版本清单的结构——需要前后端一起定义。更完整的版本与发布体系见第 17 章。

## 9. 代码示例：切后台、重连与补发的会话骨架

本章 2.1 与 2.3 节给出的是要点式片段，这一节把「显式挂起 + 宽限期」与「有限补发窗口 + 快照兜底」两个设计组装成一个可读的最小骨架。示例是本章设计决策的最小 Go 演示实现（非摘自真实项目），小节内代码块合并后可通过 `go vet` 与 `go build` 编译，并受全库代码块回归测试约束。

### 显式挂起：判定掉线的依据从心跳改为宽限期

```go
type sessState uint8

const (
    sessActive    sessState = iota // 在线：正常收发，期待心跳
    sessSuspended                  // 客户端上报切后台：心跳计时冻结
    sessClosed
)

// 宽限期：分钟到半小时量级，按产品形态定。
// iOS 切后台典型几分钟、部分 Android 省电策略下静默可达 10 分钟以上
const gracePeriod = 15 * time.Minute

// Conn：一个会话的运行态。切后台不等于掉线——
// 判定依据从「没收到心跳」改成「挂起后宽限期已过」（2.1 节）
type Conn struct {
    UID       int64
    state     sessState
    suspendAt time.Time // 进入宽限期的时刻；active 态恒为零值
}

// Suspend：客户端切后台时发 suspend 包触发。
// 资源不释放、消息继续入队，宽限期内随时可无损回来
func (c *Conn) Suspend(now time.Time) {
    if c.state == sessActive {
        c.state = sessSuspended
        c.suspendAt = now // 重复 suspend 不刷新计时：防异常客户端无限续期
    }
}

// Resume：切回前台发 resume 包，恢复心跳计时并补发离线期间的消息
func (c *Conn) Resume() {
    c.state = sessActive
    c.suspendAt = time.Time{} // 计时归零：误判率在这里下降一个量级
}

// Sweep：后台定时任务逐会话调用。返回 true 才真正断开、走完整重连流程
func (c *Conn) Sweep(now time.Time) bool {
    return c.state == sessSuspended && now.Sub(c.suspendAt) >= gracePeriod
}
```

`Suspend`/`Resume` 由客户端的前后台切换事件触发，服务端只是忠实记录状态转换——这正是 2.1 节说的「显式挂起代替猜测」。注意三个细节：`Suspend` 只在 active 态生效，重复 suspend 不刷新计时，异常客户端无法用它无限续期；`Resume` 把 `suspendAt` 归零而不是删除字段，状态机转换显式、可回放；`Sweep` 是唯一能关闭会话的路径，判定条件是「挂起后宽限期届满」——iOS 切后台几分钟的玩家在这里不会被误杀，真正死链的回收延迟由宽限期长度显式定价。

### 有限补发窗口：环形缓冲与快照兜底的分界线

```go
// Msg：下发的业务消息。Seq 是会话级序号，重连不重置（2.3 节）
type Msg struct {
    Seq  uint64
    Body []byte
}

// Writer：客户端连接的最小抽象（真实项目是 WebSocket/TCP 连接的封装）
type Writer interface {
    Write(m Msg) error
}

// Replay：补发窗口的环形缓冲实现。容量创建时定死，
// 写满后覆盖最老消息——窗口外的内容不再可补，这是快照兜底的触发条件
type Replay struct {
    buf  []Msg
    head int // 下一个写入位置；写满一圈后它同时指向最老的消息
    full bool
}

func NewReplay(capacity int) *Replay {
    return &Replay{buf: make([]Msg, capacity)}
}

// Push：每条下发消息在发送前先入窗（发送失败无需特殊处理：
// 序号在缓冲里，重连后按序号补发）
func (r *Replay) Push(m Msg) {
    r.buf[r.head] = m
    r.head++
    if r.head == len(r.buf) {
        r.head = 0
        r.full = true
    }
}

// oldest：窗口内最老的序号。窗口未满时从 1 起全部可得
func (r *Replay) oldest() uint64 {
    if !r.full {
        return 1
    }
    return r.buf[r.head].Seq
}

// ReplayTo：把 lastAck 之后的消息按序写给重连的客户端。
// 返回 false 表示缺口起点已滚出窗口：调用方转快照兜底，不再尝试重放
func (r *Replay) ReplayTo(w Writer, lastAck uint64) bool {
    if lastAck+1 < r.oldest() {
        return false
    }
    for i := 0; i < len(r.buf); i++ {
        m := r.buf[(r.head+i)%len(r.buf)] // 从最老到最新遍历
        if m.Seq > lastAck {
            _ = w.Write(m) // 写失败交由传输层重试；序号还在窗口里
        }
    }
    return true
}
```

`Replay` 就是 2.3 节 `Pending` 字段的自包含实现。窗口容量在创建时定死：万人在线、每人 1000 条，就是千万元素级常驻内存——这笔账要在设计期算（本章常见陷阱表「补发窗口设成无限大」一行）。`ReplayTo` 的返回值是两种恢复策略的分界线：缺口还在窗口内就按序重放，客户端按序号去重；起点已滚出窗口就返回 false，让调用方转快照兜底——「补几百条消息」和「重发一份全量」哪个更便宜，由这个布尔值决定，而不是由重连处理代码临场判断。

把两块拼起来就是 2.3 节 `OnReconnect` 的完整底座：重连请求先过会话校验，`gap == 0` 直接恢复收发；缺口在窗口内走 `ReplayTo` 重放；窗口外注册业务层的快照生成器兜底。会话保持、增量恢复、快照兜底三件事各自独立成型，组合关系只在重连入口出现一次——这套机制与第 4 章广播设计、知识库主线「一致性、恢复与重连」是同一套东西的客户端视角。

## 11. 实战建议

### 11.1 服务端开发者必知

1. **了解客户端限制**：小游戏包体与内存上限、移动端后台挂起行为、Web 平台浏览器限制
2. **划清三类逻辑边界**：表现归客户端、交互客户端带边界、权威归服务端——用这条标准评审每一个"这块谁来算"的问题
3. **多端发行先定身份锚点**：确认 unionid 可用性与手机号补绑路径，身份绑定表与合并规则在写第一行登录代码前定下来
4. **选择合适的协议**：WebSocket 最通用，UDP/KCP 用于强实时；按链路选序列化格式
5. **设计可扩展的协议**：消息 ID 分模块、预留扩展字段、版本兼容设计（第 4 章）
6. **提供完善的工程配套**：文档自动生成、mock 服务、错误码说明——联调效率是设计出来的

### 11.2 性能优化检查清单

```text
□ 协议优化：Protobuf 优先、消息压缩、一帧内消息合并
□ 连接优化：心跳间隔匹配平台行为、断线重连 + 增量恢复
□ 体积优化：列表分页、字段裁剪、按接收者定制粒度
□ 资源优化：内容寻址的文件名、版本清单指针化、CDN 预热
□ 监控优化：接口延迟分平台统计、CDN 命中率、重连率
```

## 12. 常见陷阱总结

本章的陷阱大多不在"不会写"，而在"不知道客户端那边会发生什么"：

| 陷阱 | 后果 | 正确做法 |
|------|------|---------|
| 把切后台当掉线，按心跳超时踢下线 | 玩家回来面对重新登录和状态丢失，体验断裂 | suspend/resume 显式挂起 + 宽限期（2.1 节） |
| code2session 不防重放 | 同一 code 二次调用被微信拒绝，无效请求打到微信侧触发限流 | 本地一次性标记（MarkOnce），重放直接拒绝（3.3 节） |
| 双端发行没提前确认身份锚点 | 上线后账号不互通，只能手机号补绑，错过一个运营周期 | 立项时确认 unionid 可用性与补绑路径（1.3 节） |
| 自动合并多端账号 | 资产冲突客诉，回滚困难 | 让玩家选择，或合并后留申诉冻结期（1.3 节） |
| 版本号按字符串比较 | `"9.9.10" < "9.9.9"`，最新版被误判为旧版触发错误强更 | 数值逐段比较（8.6 节） |
| 白名单漏配 CDN 域名 | 提审通过后线上资源加载全挂 | 域名清单纳入上线 checklist 并演练（3.1 节） |
| 纠正包攒批发送 | 客户端重演滞后，画面突刺 | 逐输入即时回，带宽优化去别处找（4.4 节） |
| 补发窗口设成无限大 | 待重连会话吃光内存 | 有限窗口 + 快照兜底的组合（2.3 节） |
| 客户端乐观扣款无服务端对账 | 请求失败后账目黑洞 | 权威逻辑只认服务端结果，客户端仅"预期"（1.1 节） |
| 让服务端实现 ENet 去对接 Godot | 反向适配：Go 侧没有成熟 ENet 实现，可靠层重复造轮子 | 服务端收敛 WebSocket/TCP 入口，客户端绕开 MultiplayerAPI（5.1 节） |

## 13. 小结

| 关键问题 | 答案 |
|---------|------|
| 服务端为什么要懂客户端？ | API、协议、超时、重连设计的空间由客户端的平台约束反向决定 |
| 前后端逻辑怎么划分？ | 表现归客户端、交互客户端带边界、权威归服务端；影响数值资产的只能服务端决定 |
| 多端发行账号怎么办？ | 身份绑定表挂多条平台身份；unionid/手机号是高可信锚点；合并让玩家选，不自动合 |
| 小游戏平台最需要注意什么？ | 包体/内存/白名单三大硬约束 + code2session 登录链路 + 极频繁的前后台切换 |
| Unity 项目的服务端要点？ | suspend/resume 区分切后台与掉线；断线重连 = 会话保持 + 增量恢复 + 快照兜底 |
| UE5 混合架构是什么？ | 引擎内战斗 + 自定义服务端管账号经济社交，中间内部协议桥接；纠正包逐输入即时回 |
| Godot 项目的服务端要点？ | 房间对等是默认心智，接权威服务端按普通 WebSocket/TCP 客户端对接；Web 导出必须 COOP/COEP |
| 版本检查接口的要点？ | 数值逐段比较版本、清单地址指针化、最低可玩版本拦截强更、灰度命中在此接口 |
| CDN 使用的第一原则？ | 内容寻址（文件名带哈希）代替缓存刷新，版本切换只是服务端改指针 |
| 客户端网络层长什么样？ | 传输层 → 请求管理器（序列号/重试/去重）→ 分发器 → 逻辑层，服务端按此提供配套 |
| 联调效率靠什么？ | 文档自动生成 + mock 服务 + 环境分层，不靠沟通态度 |

## 14. 实战案例：一次「切个微信就要重新登录」的切后台误判掉线排查

> 案例为教学示例（非摘自真实项目），数字经过取整简化，聚焦排查思路与回填逻辑。

**背景与现象**

移动端上线后的第二个版本周，客诉集中在同一句话：「切出去回个微信，回来就要重新登录，刚才的界面全没了」。客诉 **486** 份；网关日志抽样 **3000** 次重连，其中 **2210** 次的断开原因是「心跳超时」，且断开时刻与客户端切后台时刻吻合——误判率 **74**%。更糟的是晚间高峰：重连请求形成尖峰，把没切后台的玩家也挤得掉线。

### 第一步：现象与口径

按 2.1 节的超时推导公式对口径，公式的 **3** 项里逐项找答案：

- **服务端侧**：心跳间隔 **10** 秒、超时阈值 **30** 秒——容忍丢 **2** 个心跳，链路本身没有丢包异常；
- **平台侧**：iOS 切后台会挂起连接，典型静默几分钟；部分 Android 省电策略下静默可达 **10** 分钟以上——都是**合法静默**；
- **口径差**：阈值 **30** 秒只按 PC 端习惯取值，比移动端合法静默（按 **600** 秒计）短 **20** 倍。

判定口径先立住：被踢下线的不是「死链」，是「合法静默的活链」——这是两个完全不同的分母。

### 第二步：分层归因

```text
传输层   心跳 10 秒一次，30 秒阈值内无丢包——链路本身无罪
平台层   iOS 切后台挂起连接、Android 省电限网——静默分钟级是平台行为，不是异常
会话层   判定掉线即销毁会话：token 作废、待补发队列清空——玩家回来只能重新登录 + 全量重拉
观测层   只有「在线数」下跌被当成正常波动，「误判掉线率」从未被度量
```

**账本收敛**：日活 **5** 万，人均每天切后台 **6** 次，其中静默超 **30** 秒的占 **40**%——每天被误判掉线 50000 × 6 × 40% = **12** 万人次；每次误判的代价是重新登录加全量重拉 **18** 个接口。晚高峰切回瞬时 **800** 人/分钟 × **18** 接口 = **1.44** 万 QPS 打在登录与查询服务上——切回来的人把没切的人也挤掉线，风暴有了二级伤害。

### 第三步：根因

1. **直接原因**：超时阈值的「最长合法静默时长」一项直接沿用 PC 端习惯值——推导公式的 3 项里取错了 1 项，**30** 秒阈值对移动端平台行为失明。
2. **机制原因**：判定掉线后的动作是「销毁会话」，而 2.1 节给出的替代方案——suspend/resume 显式挂起 + 宽限期——一行都没实现；3.4 节适配清单 **11** 条里的第 **4** 条「suspend/resume 挂起协议 + 宽限期」就是为本案写的，清单躺在文档里没人对账。
3. **深层原因**：第 12 节陷阱表 **10** 行里的第 **1** 行「把切后台当掉线，按心跳超时踢下线」与本案逐字对应——现象、后果、正确做法三列俱全，但它没进任何评审 checklist；「掉线」被当成纯网络问题，没人对照平台行为定参数。

### 第四步：处置与回填

1. **显式挂起**：上线 suspend/resume——客户端切后台发 suspend、回前台发 resume；宽限期定 **15** 分钟（分钟到半小时量级的取值中段），iOS 几分钟与 Android 省电 **10** 分钟的合法静默全部落在宽限期内；重复 suspend 不刷新计时，异常客户端无法用它无限续期。
2. **判定换轨**：掉线判定从「**30** 秒没心跳」改为「挂起后宽限期已过」——Sweep 扫描是唯一关闭会话的路径，真死链的回收延迟由宽限期显式定价（最长 **15** 分钟）。
3. **会话不销毁**：宽限期内会话保持、消息照常入队；补发窗口定 **1000** 条，重连按序号增量补发，缺口滚出窗口转快照兜底——重连代价从「重新登录 + 18 个接口」降为「一条 resume + 几条补发」。
4. **观测补位**：「误判掉线率」与重连率进面板，按平台分列——移动端的掉线监控从此有了正确的分母。

**复核**：上线一周，误判掉线 **12** 万次/天 → **0** 次；客诉 **486** 份 → **9** 份（下降 **98**%）；晚高峰重连尖峰从 **1.44** 万 QPS → **0.1** 万（回落 **93**%，残余为真断线）；真死链平均 **15** 分钟内回收——「切个微信」从此只是切个微信。

**回填清单**：

| 回填项 | 落点 | 回链 |
|--------|------|------|
| suspend/resume + 宽限期 15 分钟 | 会话网关 | 第 03 讲 2.1 节 / 第 9 节骨架 |
| 补发窗口 1000 条 + 快照兜底 | 会话网关 | 第 03 讲 2.3 节 / 第 9 节骨架 |
| 误判掉线率 + 重连率按平台分列进面板 | 监控告警 | 第 03 讲 11.2 节 / 第 13 讲 |
| 平台静默行为表进超时参数评审 | 接入配置 | 第 03 讲 2.1 节推导公式 / 3.4 节清单 |

### 案例的三个教训

1. **掉线是平台行为的函数，不是心跳的函数**——超时推导公式三项里的「最长合法静默时长」取错平台，后面两项算得再准也是错（2.1 节推导公式）。
2. **会话生命周期要为「会回来的人」留一态**——销毁与挂起是两种成本结构：销毁省内存、把代价转嫁给回归玩家；挂起花一点内存、把重连变成一条 resume（2.1/2.3 节）。
3. **风暴的账要连二级伤害一起算**——误判掉线本身是体验问题，切回高峰形成的重连尖峰会把登录服务打满、误伤没切后台的玩家；容量账要按风暴口径算，不按日常口径算（账本收敛）。
