# 03 前端引擎与客户端

> 本章目标：让服务端开发者理解各引擎客户端的约束、网络层工作方式和资源体系，从而做出与客户端匹配的服务端设计——协议选型、超时与重连策略、响应体积、资源版本接口。不需要会写客户端代码，但需要知道**客户端的约束会反向决定服务端的设计空间**。
>
> **参考书籍**：引擎特性部分参考各引擎官方文档与《百万在线》中的多端适配实践；前后端边界的分析方法参考知识库主线"前后端边界与网络层"一篇。

---

## 1. 为什么服务端要了解前端引擎

很多服务端开发者觉得"前端是客户端的事，跟我无关"。但现实是：**你的 API 设计、协议格式、消息推送策略，都需要考虑客户端引擎的限制和特性**。

比如，微信小游戏的主包只有 4MB，如果你的协议定义文件太大，客户端根本装不下。再比如，Unity 的 WebSocket 实现在 iOS 后台会被系统挂起，如果你不知道这一点，就会在设计断线重连机制时犯错——把"后台切回前台"误判成"网络异常"，触发不必要的重新登录。

理解前端引擎不是要你去写客户端代码，而是要理解三件事：**客户端的约束条件是什么？客户端的网络层是怎么工作的？客户端的资源管理有什么限制？**

### 1.1 最重要的边界：三类逻辑的划分

前后端协作中大部分长期扯皮，根源是"这块逻辑谁做"没有清晰标准。比较稳妥的划分是把逻辑分成三类：

| 逻辑类别 | 内容 | 归属 | 服务端要点 |
|---------|------|------|----------|
| 表现逻辑 | 特效、动画、镜头、UI 过渡、本地提示 | 客户端 | 无需服务端参与 |
| 交互逻辑 | 输入响应、页面状态、本地校验、局部预测 | 客户端（带边界） | 服务端保留最终裁决 |
| 权威逻辑 | 资源变更、战斗裁决、匹配结果、房间状态、支付结果 | **服务端** | 客户端展示服务端结果 |

前两类留在客户端换取流畅体验；第三类必须由服务端决定。最容易出问题的是边界模糊地带：客户端做了"乐观扣款"（先扣本地钻石再发请求），服务端却没有对账逻辑——一旦请求失败，本地已经扣掉的钻石就成了账目黑洞。**判断标准：任何影响数值、资产、胜负的操作，客户端只能"预期"，不能"决定"。**

### 1.2 引擎选型对服务端的影响

| 引擎 | 语言 | 平台 | 网络方案 | 对服务端的影响 |
|------|------|------|---------|--------------|
| **Unity** | C# | 全平台 | WebSocket/Mirror | 需要连接管理器、心跳机制 |
| **UE5** | C++/蓝图 | PC/主机 | 内置网络框架/UDP | 可能需要自定义 UDP 可靠层 |
| **Cocos Creator** | TypeScript | 小游戏/Web | WebSocket/HTTP | 小游戏包体限制、HTTP 为主 |
| **Godot** | GDScript/C# | 全平台 | MultiplayerAPI | ENet/UDP 可靠层 |
| **LayaAir** | TypeScript | 小游戏/Web | WebSocket/HTTP | 类似 Cocos Creator |

引擎选型决策树（客户端视角）：

```
选择什么引擎？
│
├── 微信/抖音小游戏
│   ├── Cocos Creator（生态最好）
│   └── LayaAir（3.0 性能优化好）
│
├── 手游（iOS/Android）
│   ├── Unity（人才最多，生态成熟）
│   └── Cocos Creator（小游戏+手游一体化）
│
├── PC/主机 3A
│   ├── Unreal Engine 5（画面顶级）
│   └── Unity（中等品质，效率高）
│
└── 独立游戏
    ├── Godot（开源免费，MIT 协议）
    ├── Unity
    └── Unreal Engine
```

从服务端视角看这棵决策树：**前两类（小游戏、手游）基本都是 WebSocket + Protobuf 的组合**，服务端只需要一套接入协议；UE5 项目则需要考虑 UDP 自定义协议；如果产品同时覆盖小游戏和 App（很常见的发行策略），服务端需要**同一套逻辑服务两种接入形态**——协议层统一，接入层按平台分流。

## 2. Unity：手游市场的中坚

### 2.1 Unity 客户端网络层的典型结构

Unity 客户端的网络层通常分为四层：**传输层**（WebSocket/TCP/KCP）→ **协议层**（Protobuf/JSON）→ **消息分发器**（Dispatcher）→ **游戏逻辑层**。

对服务端有意义的是两点。其一，Unity 的 WebSocket 在不同平台行为有差异：iOS 在后台会挂起连接，Android 省电模式下限制网络活动。这要求服务端的超时判定足够宽容——**"暂时沉默"不等于"掉线"**，心跳超时阈值要大于典型的切后台时长（分钟级），或者客户端在切前台时主动发一个 resume 包。其二，Unity 项目通常用 async/await 处理网络 I/O，客户端对几十毫秒的响应延迟不敏感，但这不是忽视性能的理由——高延迟在战斗、抽卡等关键交互上会被玩家直接感知。

### 2.2 协议对接的三件套

Unity 团队通常使用 Protobuf + WebSocket。服务端需要提供：

1. **Protobuf 定义文件**（.proto）：客户端和服务端共享同一份协议定义，由它生成两端的编解码代码（见第 4 章协议治理）
2. **消息 ID 编码规则**：模块(8bit) + 动作(16bit) + 类型(8bit)，两端用同一张 ID 常量表
3. **错误码体系**：统一格式，客户端按错误类型决定是弹窗、toast 还是静默重试

### 2.3 常见问题与服务端应对

| 问题 | 原因 | 服务端应对策略 |
|------|------|--------------|
| 消息粘包 | TCP 流式传输 | 消息头包含长度字段（见第 4 章拆包器） |
| 断线后状态丢失 | 客户端缓存过期 | 提供状态快照接口 |
| 大消息包拆分 | 协议限制 | 支持分包发送 + 消息重组 |
| SSL 证书问题 | 平台差异 | 证书链完整、兼容系统证书库 |
| 后台连接被杀 | iOS/Android 限制 | 断线重连机制 + 状态恢复 |

其中"断线重连 + 状态恢复"值得展开，因为它是设计出来的而不是补出来的。服务端需要一组配套接口：**会话保持**（连接断了会话token还在，重连携带 token 免重新登录）、**增量恢复**（客户端上报自己最后收到的序列号，服务端只补发缺口，而不是全量重推）、**快照兜底**（缺口太大时直接发全量快照，比补几百条消息更便宜）。这套机制与第 4 章广播设计、知识库主线"一致性、恢复与重连"是同一套东西的客户端视角。

## 3. Cocos Creator 与小游戏平台

Cocos Creator 是微信小游戏、抖音小游戏的主流引擎。它的技术特性和平台限制直接影响服务端设计。

### 3.1 小游戏平台的硬性约束

微信小游戏有一系列硬性约束，这些约束不是"建议"而是"限制"：

- **包体大小**：主包 4MB + 分包 20MB（总包上限随版本调整，以平台文档为准）。协议定义文件、首屏配置都要算进首包预算
- **内存限制**：iOS/Android 有上限（机型相关），客户端不能缓存太多数据——服务端下发的列表类接口要支持分页，客户端可能随时丢弃非当前页数据
- **域名白名单**：只能连接备案过的白名单域名，上线前必须配置——包括 WebSocket 域名和 CDN 域名，漏一个就是线上事故
- **开放数据域隔离**：好友排行榜等社交数据运行在独立的数据域，与主域不能直接通信，只能通过特定接口交换——服务端设计排行榜时要知道"平台好友关系"走平台开放数据，"游戏内好友"才走自己的服务

这些约束的汇总含义：**API 响应体积要小**。一个 100 玩家的列表，每人 20 个字段，JSON 可能超过 10KB；Protobuf 可以压到 2-3KB。对小游戏来说这不只是流量，还是加载等待时间和内存占用。

### 3.2 网络层特点：一切自己造

Cocos 的 WebSocket 实现接近浏览器原生 API：没有内置重连机制、没有内置消息队列（连接断开时发送即丢失）、心跳要自己实现。这意味着小游戏的客户端网络层质量**高度依赖团队自建**，服务端要按"客户端不可靠"来设计：消息带序列号便于客户端去重、关键接口幂等（同一个请求重发不产生副作用）、断线期间的推送允许客户端回来后拉取（推送 + 拉取兜底的双通道设计）。

### 3.3 小游戏的登录链路

小游戏登录有一个平台特有的时序，服务端必须实现对应接口：

```
1. 客户端调用 wx.login() 获得 code（临时凭证，5分钟有效）
2. 客户端把 code 发给你的服务端
3. 服务端拿 code + appid + secret 调微信 code2session 接口
   → 换得 openid（用户唯一标识）+ session_key
4. 服务端绑定 openid ↔ 游戏账号，签发自己的会话 token
5. 之后所有请求带游戏会话 token，不再依赖微信会话
```

要点：**secret 只能放在服务端**；session_key 用于解密平台敏感数据，不要下发给客户端；会话过期与微信态解耦——玩家可能微信在线但你的会话已过期，也可能反过来，两条过期路径都要处理。

### 3.4 小游戏的服务端适配清单

```
小游戏服务端适配检查清单：

□ 1. API 响应体积控制在 5KB 以内，列表接口分页
□ 2. 使用 Protobuf 而非 JSON（体积减少 60-80%）
□ 3. 实现断线重连机制（小游戏切前后台极频繁）
□ 4. 状态快照 + 增量恢复接口（重连后恢复状态）
□ 5. 域名白名单配置（WebSocket 域名 + CDN 域名）
□ 6. 分包资源的 CDN 地址管理
□ 7. 微信登录链路（code2session）与支付异步通知
□ 8. 防刷机制（小游戏环境更容易被脚本批量访问）
□ 9. 推送 + 拉取双通道（断线期间的推送可回补）
```

## 4. Unreal Engine 5：3A 品质的代价

UE5 是 3A 游戏的首选引擎，网络框架非常成熟，也非常复杂。服务端开发者需要理解 UE5 的网络模型，才能正确对接。

### 4.1 权威服务器模型

UE5 使用**权威服务器（Dedicated Server）**模型：服务端是游戏世界的权威，客户端是"观察者"和"输入者"。客户端可以做预测（Prediction），但最终结果由服务端校验（Validation）。这与本书反复强调的"服务端权威"原则完全一致——UE5 把这套理念做成了引擎内置设施。

核心网络机制：

- **属性同步（Replication）**：服务端自动将 Actor 属性同步到客户端，支持条件同步（只有变化时、只对相关玩家）
- **RPC**：客户端/服务端远程过程调用，区分可靠/不可靠
- **Actor 复制**：整个 Actor 在服务端和客户端之间同步，配合相关性（Relevancy）控制同步范围

### 4.2 与自定义服务端的协作

很多项目用 UE5 做客户端，但用 Go/Java 做自定义服务端（而不是 UE5 Dedicated Server）——因为大世界的账号、社交、经济、跨服逻辑用通用后端技术栈更高效。这种混合模式下：

- UE5 内实现一个 NetworkComponent，处理与自定义服务端的连接管理、消息收发、心跳
- 战斗/物理等强引擎相关的部分留在 UE5 Dedicated Server，账号/交易/社交走自定义服务端
- 两类服务端之间需要一个内部协议桥接（通常是 gRPC 或内部 TCP 协议）

### 4.3 特殊挑战

| 挑战 | 原因 | 解决方案 |
|------|------|---------|
| UDP 可靠性 | UE5 默认用 UDP | 引擎自带可靠性层；对接自定义服务端时用 KCP/QUIC |
| 大规模同步 | MMO 场景 | 分组同步 + AOI（兴趣区域管理） |
| 属性同步冲突 | 多端同时修改 | 服务端权威 + 客户端预测 + 服务器回滚纠正 |
| 跨平台差异 | PC/主机/移动端 | 分平台适配网络参数和同步频率 |

## 5. 其他引擎速览

### 5.1 Cocos2d-x（Lua）

"老而弥坚"的引擎，大量历史项目仍在使用。核心优势是 **Lua 热更新**——改 Lua 脚本即可热更，不需要重新发版。对服务端的影响：这类项目通常使用自定义 TCP 协议和二进制编码（而非 Protobuf），服务端需要支持这种历史协议；Lua 热更依赖 CDN 资源分发（见 6.5 节）。

### 5.2 LayaAir

LayaAir 3.0 性能显著提升，适合微信/抖音小游戏。网络层与 Cocos Creator 类似，基于 WebSocket，服务端适配策略相同。

### 5.3 Godot

完全开源免费（MIT 协议），MultiplayerAPI 内置 ENet（UDP 可靠层）、WebSocket 和 TCP 支持。独立游戏的常见选择。对服务端的提示：Godot 的多人 API 默认假设"引擎 P2P 架构"，接自定义权威服务端时按普通 TCP/UDP 客户端对接即可。

## 6. 前后端协作的核心要点

### 6.1 协议格式的选择

| 格式 | 体积 | 编解码速度 | 强类型 | 代码生成 | 适用场景 |
|------|------|-----------|--------|---------|---------|
| **Protobuf** | ★★★★★ | ★★★★ | ✓ | ✓ | 大型游戏（主流选择） |
| **FlatBuffers** | ★★★★★ | ★★★★★ | ✓ | ✓ | 高性能热路径 |
| **MessagePack** | ★★★★ | ★★★ | ✓ | ✓ | 中型游戏 |
| **JSON** | ★★ | ★★ | ✗ | ✗ | 管理接口/原型 |

大型游戏用 Protobuf，极致性能场景用 FlatBuffers，管理后台和原型用 JSON——**按链路选格式，不搞一刀切**（详细对比与兼容性纪律见第 4 章）。

### 6.2 客户端-服务端交互模式

```
模式1：请求-响应（最常用）
客户端 ──请求──→ 服务端 ──响应──→ 客户端
适用：登录、商店、背包、排行榜

模式2：服务端推送
服务端 ──推送──→ 客户端
适用：公告、活动通知、排行榜更新

模式3：实时同步（状态同步）
客户端 ──输入──→ 服务端 ──状态广播──→ 所有客户端
适用：MMO、实时对战

模式4：帧同步
客户端 ──输入──→ 服务端收集 ──帧广播──→ 所有客户端计算
适用：MOBA、RTS
```

四种模式的协议诉求不同：模式 1/2 走可靠通道，带请求 ID 和错误码；模式 3/4 带序列号和时间戳，允许丢旧保新（第 4 章）。**在协议设计期就标注每条消息属于哪种模式**，比上线后再区分容易得多。

### 6.3 客户端网络层的标准结构

服务端要对接的其实是一个"标准形态"的客户端网络层，了解它有助于服务端提供正确的配套：

```
┌─────────────────────────────────────────┐
│              游戏逻辑层                   │
│   发起请求（带回调）/ 接收推送更新状态      │
├─────────────────────────────────────────┤
│           消息分发器 Dispatcher           │
│   按 MsgID 路由到注册的处理函数             │
├─────────────────────────────────────────┤
│              请求管理器                   │
│   请求队列 + 超时重试 + 序列号 + 去重       │
├─────────────────────────────────────────┤
│        传输层（WebSocket/TCP/KCP）        │
│   连接管理、心跳、断线重连、编解码           │
└─────────────────────────────────────────┘
```

服务端与之对应的配套责任：请求 ID 原样返回（客户端超时重试后按 ID 丢弃重复响应）、消息序列号（客户端断线回来报出最后序列号，服务端增量补发）、心跳应答（服务端要回 pong，客户端据此测 RTT）、关键接口幂等（重试不产生副作用）。

### 6.4 联调期的工程配套

前后端联调的效率不取决于沟通态度，取决于工程配套：

- **接口文档自动生成**：从 .proto / IDL 直接生成文档，禁止手工维护 Word——手写文档与代码的漂移是联调扯皮第一来源
- **Mock 服务**：协议定义完成后、服务端实现前，客户端可以先对接 mock 数据联调 UI；服务端也可以用 mock 客户端做压测
- **环境分层**：开发/测试/预发布/生产四级环境，协议版本和配置版本逐级验证；联调环境的服务端要能一键重置数据
- **联调期常见问题**与约定：

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 消息丢失 | 网络抖动 | 重试机制 + 消息 ID 去重 |
| 消息乱序 | UDP / 并发处理 | 序列号 + 接收缓冲区重排 |
| 版本不兼容 | 前后端不同步发布 | 协议版本号 + 兼容窗口（见第 4 章） |
| 状态不一致 | 客户端预测偏差 | 服务端权威 + 校验纠正包 |
| 性能瓶颈 | 消息过多过碎 | 消息合并 + 优先级（见第 4 章） |

### 6.5 CDN 与资源分发

CDN（内容分发网络）是游戏客户端资源分发的核心基础设施。对服务端开发者来说，理解 CDN 是为了设计资源更新策略和排查资源加载问题。

**CDN 在游戏中的三大用途**：

| 用途 | 说明 | 典型场景 |
|------|------|---------|
| **热更新资源** | 客户端代码、Lua/JS 脚本、配置表 | 版本更新、Bug 修复、活动配置 |
| **静态资源** | 图片、音频、视频、预制体 | 美术资源、UI 素材、过场动画 |
| **配置下发** | 活动配置、公告、版本信息 | 运营活动、紧急公告 |

**工作原理**：客户端请求资源 → DNS 解析到就近 CDN 节点 → 节点缓存命中直接返回（最快）；未命中则回源到源站，缓存后返回。对游戏热更来说，通常的流程是：

```
1. 服务端生成版本号 + 资源清单（manifest）
2. 客户端启动时请求版本号
3. 对比本地版本，计算差异资源
4. 从 CDN 下载差异资源
5. 客户端加载新资源，完成热更新
```

**CDN 选型考虑**：节点覆盖（国内/海外、城市层级）、回源带宽成本、缓存策略（静态资源长缓存、配置短缓存）、HTTPS 支持、防盗链、预热功能（新版本上线前把资源推到各节点）。

**服务端与 CDN 的协作**：

- **版本管理**：服务端维护版本号和资源清单，客户端通过 CDN 下载资源
- **灰度发布**：按渠道/区域/比例下发不同版本的清单
- **回滚机制**：服务端切换版本号指针，客户端下载旧版本资源（资源文件按版本保留，不覆盖）
- **监控告警**：CDN 下载失败率、回源率、延迟监控

> **实战经验**：CDN 的缓存刷新不是实时的。新版本上线时，要确保资源文件名带版本号或内容哈希（如 `bundle_a3f9c2.bundle`），而不是依赖 CDN 缓存刷新。这样即使 CDN 缓存未更新，客户端也能通过新文件名获取最新资源——**内容寻址代替缓存失效**，是所有 CDN 场景的第一原则。

### 6.6 资源版本管线的服务端视角

资源系统连接着内容生产、版本发布、运行时内存和线上修复能力，服务端在其中承担的接口职责：

- **版本检查接口**（checkversion）：客户端上报平台、渠道、当前版本，服务端返回最新版本号、清单地址、是否强制更新
- **清单接口**：资源清单本身走 CDN，但清单的**索引**由服务端下发——这样切换版本、灰度、回滚都只是服务端改指针
- **强制更语义**：兼容性破坏的版本必须能强制升级（返回"最低可玩版本"，低于它的客户端拦截进入更新页）
- **下载兜底**：CDN 大面积故障时的备用源（源站限流直下）是最后手段，平时不用但要演练

资源打包策略（首包/分包/热更划分、依赖治理）属于客户端工程，但其产物——版本清单的结构——需要前后端一起定义。更完整的版本与发布体系见第 17 章。

## 7. 引擎选择对服务端的影响总结

| 引擎选择 | 协议类型 | 连接方式 | 消息格式 | 特殊要求 |
|---------|---------|---------|---------|---------|
| Unity + WebSocket | TCP | 长连接 | Protobuf/JSON | 心跳宽容后台挂起 |
| UE5 + 自定义服务端 | UDP | 长连接 | 自定义/KCP | 可靠 UDP 层 + 内部桥接 |
| Cocos Creator | WebSocket | 长连接 | Protobuf/JSON | 小游戏适配 + 登录链路 |
| Cocos2d-x（Lua） | TCP | 长连接 | 自定义二进制 | Lua 热更 + 历史协议 |
| Web 游戏 | HTTP/WS | 短连接+长连接 | JSON | RESTful API |
| 多端发行 | 统一逻辑层 | 按平台分流 | 统一协议层 | 接入层适配，逻辑复用 |

## 8. 实战建议

### 8.1 服务端开发者必知

1. **了解客户端限制**：小游戏包体与内存上限、移动端后台挂起行为、Web 平台浏览器限制
2. **划清三类逻辑边界**：表现归客户端、交互客户端带边界、权威归服务端——用这条标准评审每一个"这块谁来算"的问题
3. **选择合适的协议**：WebSocket 最通用，UDP/KCP 用于强实时；按链路选序列化格式
4. **设计可扩展的协议**：消息 ID 分模块、预留扩展字段、版本兼容设计（第 4 章）
5. **提供完善的工程配套**：文档自动生成、mock 服务、错误码说明——联调效率是设计出来的

### 8.2 性能优化检查清单

```
□ 协议优化：Protobuf 优先、消息压缩、一帧内消息合并
□ 连接优化：心跳间隔匹配平台行为、断线重连 + 增量恢复
□ 体积优化：列表分页、字段裁剪、按接收者定制粒度
□ 资源优化：内容寻址的文件名、版本清单指针化、CDN 预热
□ 监控优化：接口延迟分平台统计、CDN 命中率、重连率
```

## 9. 小结

| 关键问题 | 答案 |
|---------|------|
| 服务端为什么要懂客户端？ | API、协议、超时、重连设计的空间由客户端的平台约束反向决定 |
| 前后端逻辑怎么划分？ | 表现归客户端、交互客户端带边界、权威归服务端；影响数值资产的只能服务端决定 |
| 小游戏平台最需要注意什么？ | 包体/内存/白名单三大硬约束 + code2session 登录链路 + 极频繁的前后台切换 |
| Unity 项目的服务端要点？ | 心跳阈值宽容 iOS 后台挂起；断线重连 = 会话保持 + 增量恢复 + 快照兜底 |
| UE5 混合架构是什么？ | 引擎内战斗 + 自定义服务端管账号经济社交，中间内部协议桥接 |
| CDN 使用的第一原则？ | 内容寻址（文件名带哈希）代替缓存刷新，版本切换只是服务端改指针 |
| 客户端网络层长什么样？ | 传输层 → 请求管理器（序列号/重试/去重）→ 分发器 → 逻辑层，服务端按此提供配套 |
| 联调效率靠什么？ | 文档自动生成 + mock 服务 + 环境分层，不靠沟通态度 |
