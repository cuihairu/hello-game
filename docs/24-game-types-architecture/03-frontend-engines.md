# 03 前端引擎与客户端

> 本章目标：让服务端开发者理解各引擎客户端的约束、网络层工作方式和资源体系，从而做出与客户端匹配的服务端设计——协议选型、超时与重连策略、多端账号身份、响应体积、资源版本接口。不需要会写客户端代码，但需要知道**客户端的约束会反向决定服务端的设计空间**。
>
> **参考书籍**：引擎特性部分参考各引擎官方文档与《百万在线》中的多端适配实践；前后端边界的分析方法参考知识库主线"前后端边界与网络层"一篇。

## 1. 为什么服务端要了解前端引擎

很多服务端开发者觉得"前端是客户端的事，跟我无关"。但现实是：**你的 API 设计、协议格式、消息推送策略，都需要考虑客户端引擎的限制和特性**。

比如，微信小游戏的主包只有 4MB，如果你的协议定义文件太大，客户端根本装不下。再比如，Unity 的 WebSocket 实现在 iOS 后台会被系统挂起，如果你不知道这一点，就会在设计断线重连机制时犯错——把"后台切回前台"误判成"网络异常"，触发不必要的重新登录。

理解前端引擎不是要你去写客户端代码，而是要理解三件事：**客户端的约束条件是什么？客户端的网络层是怎么工作的？客户端的资源管理有什么限制？**

### 1.1 最重要的边界：三类逻辑的划分

前后端协作中大部分长期扯皮，根源是"这块逻辑谁做"没有清晰标准。比较稳妥的划分是把逻辑分成三类：

| 逻辑类别 | 内容 | 归属 | 服务端要点 |
|---------|------|------|----------|
| 表现逻辑 | 特效、动画、镜头、UI 过渡、本地提示 | 客户端 | 无需服务端参与 |
| 交互逻辑 | 输入响应、页面状态、本地校验、局部预测 | 客户端（带边界） | 服务端保留最终裁决 |
| 权威逻辑 | 资源变更、战斗裁决、匹配结果、房间状态、支付结果 | **服务端** | 客户端展示服务端结果 |

前两类留在客户端换取流畅体验；第三类必须由服务端决定。最容易出问题的是边界模糊地带：客户端做了"乐观扣款"（先扣本地钻石再发请求），服务端却没有对账逻辑——一旦请求失败，本地已经扣掉的钻石就成了账目黑洞。**判断标准：任何影响数值、资产、胜负的操作，客户端只能"预期"，不能"决定"。**

### 1.2 引擎选型对服务端的影响

| 引擎 | 语言 | 平台 | 网络方案 | 对服务端的影响 |
|------|------|------|---------|--------------|
| **Unity** | C# | 全平台 | WebSocket/Mirror | 需要连接管理器、心跳机制 |
| **UE5** | C++/蓝图 | PC/主机 | 内置网络框架/UDP | 可能需要自定义 UDP 可靠层 |
| **Cocos Creator** | TypeScript | 小游戏/Web | WebSocket/HTTP | 小游戏包体限制、HTTP 为主 |
| **Godot** | GDScript/C# | 全平台 | MultiplayerAPI | ENet/UDP 可靠层 |
| **LayaAir** | TypeScript | 小游戏/Web | WebSocket/HTTP | 类似 Cocos Creator |

引擎选型决策树（客户端视角）：

```text
选择什么引擎？
│
├── 微信/抖音小游戏
│   ├── Cocos Creator（生态最好）
│   └── LayaAir（3.0 性能优化好）
│
├── 手游（iOS/Android）
│   ├── Unity（人才最多，生态成熟）
│   └── Cocos Creator（小游戏+手游一体化）
│
├── PC/主机 3A
│   ├── Unreal Engine 5（画面顶级）
│   └── Unity（中等品质，效率高）
│
└── 独立游戏
    ├── Godot（开源免费，MIT 协议）
    ├── Unity
    └── Unreal Engine
```

从服务端视角看这棵决策树：**前两类（小游戏、手游）基本都是 WebSocket + Protobuf 的组合**，服务端只需要一套接入协议；UE5 项目则需要考虑 UDP 自定义协议；如果产品同时覆盖小游戏和 App（很常见的发行策略），服务端需要**同一套逻辑服务两种接入形态**——协议层统一，接入层按平台分流。

### 1.3 多端发行的服务端深水区：一个人的多个 ID

"同一套逻辑服务两种接入形态"落到账号体系上，就是多端发行最典型的难题：**同一个真实玩家，在不同平台是不同的平台身份**。

| 平台侧身份 | 获取方式 | 可信范围 | 备注 |
|-----------|---------|---------|------|
| openid（微信） | code2session | 仅当前 appid 内唯一 | 同一主体下不同小程序/App 的 openid 不同 |
| unionid（微信） | 绑定微信开放平台后随登录返回 | 同一开放平台主体下跨端唯一 | **App 不绑开放平台就拿不到** |
| 手机号 | 运营商一键登录 / 短信验证码 | 跨一切平台稳定 | 最可靠的跨端锚点，但有成本与覆盖率问题 |
| 游客 ID | 设备标识 / 客户端生成 UUID | 仅本设备 | 卸载、换机即丢失，必须支持后续升级绑定 |

服务端需要一张独立的身份绑定表，以游戏内 UID 为中心挂载多条平台身份：

```sql
CREATE TABLE user_identity (
  id_type    TINYINT  NOT NULL,     -- 1=wechat_openid 2=unionid 3=phone 4=guest
  id_value   VARCHAR(128) NOT NULL,
  uid        BIGINT   NOT NULL,     -- 游戏内唯一 ID
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id_type, id_value),
  KEY idx_uid (uid)
);
```

登录时的判定逻辑很直接：按 `(id_type, id_value)` 查 `uid`，命中就登录；未命中就创建新玩家并写入绑定。麻烦全部出在**合并冲突**：玩家以游客身份玩了一周（uid=1001，充值过），某天用微信登录——而这个微信身份此前已在另一台设备建过 uid=2002。两个 uid 都有真实资产，不能悄悄丢掉任何一个。常见的裁决方式：

- **让玩家自己选**（保留哪个进度），而不是后台自动合并——背包、充值记录、排行榜名次的合并规则没有让所有人信服的普适答案，自动合并几乎必然产生客诉
- 若产品决定自动合并，被合并账号进入一段"可申诉冻结期"，期间允许客服按记录回滚
- 身份锚点分可信级：unionid、手机号是高可信锚点；openid 只在 appid 内可信；**不要用"昵称相同"之类弱信号做合并依据**

> **陷阱**：很多团队小游戏 + App 双端上线后才发现账号不互通，根因是 App 侧没有走微信开放平台的绑定流程——拿不到 unionid，openid 又天然不互通，此时只能靠手机号补绑，错过的是整整一个运营周期。**双端立项时就要确认身份锚点方案**，这是服务端在立项评审里该主动问的问题。

## 2. Unity：手游市场的中坚

### 2.1 Unity 客户端网络层的典型结构

Unity 客户端的网络层通常分为四层：**传输层**（WebSocket/TCP/KCP）→ **协议层**（Protobuf/JSON）→ **消息分发器**（Dispatcher）→ **游戏逻辑层**。

对服务端有意义的是两点。其一，Unity 的 WebSocket 在不同平台行为有差异：iOS 在后台会挂起连接，Android 省电模式下限制网络活动。这要求服务端的超时判定足够宽容——**"暂时沉默"不等于"掉线"**。其二，Unity 项目通常用 async/await 处理网络 I/O，客户端对几十毫秒的响应延迟不敏感，但这不是忽视性能的理由——高延迟在战斗、抽卡等关键交互上会被玩家直接感知。

心跳超时阈值可以按一个简单的推导来定：

```text
超时阈值 ≥ 客户端最长合法静默时长 + 网络最大抖动 + 服务端处理余量
```

问题在于"最长合法静默时长"在移动端没有一个稳定值：iOS 切后台典型几分钟、用户回来连接自动恢复；部分 Android 厂商的省电策略下静默可达 10 分钟以上。若心跳间隔 10 秒、阈值 30 秒（容忍丢 2 个心跳），切后台玩家会被批量误判掉线——而他们几分钟后回来，不该承受重新登录和状态丢失。

所以移动端长连接普遍采用**显式挂起**代替猜测：客户端切后台时发 `suspend` 包，切回前台发 `resume` 包。服务端收到 suspend 就冻结该会话的心跳计时，按"宽限期"（分钟到半小时量级，按产品形态定）管理，宽限期内资源不释放、消息继续入队；resume 则恢复计时并补发离线期间的消息。宽限期超时才真正断开、走完整的重连流程。**判定"掉线"的依据从"没收到心跳"变成"客户端说挂起后宽限期已过"**，误判率会下降一个量级。没有 suspend/resume 时，退而求其次的做法是把心跳阈值放宽到分钟级，代价是真正的死链要几分钟后才能回收。

### 2.2 协议对接的三件套

Unity 团队通常使用 Protobuf + WebSocket。服务端需要提供：

1. **Protobuf 定义文件**（.proto）：客户端和服务端共享同一份协议定义，由它生成两端的编解码代码（见第 4 章协议治理）
2. **消息 ID 编码规则**：模块(8bit) + 动作(16bit) + 类型(8bit)，两端用同一张 ID 常量表
3. **错误码体系**：统一格式，客户端按错误类型决定是弹窗、toast 还是静默重试

### 2.3 常见问题与服务端应对

| 问题 | 原因 | 服务端应对策略 |
|------|------|--------------|
| 消息粘包 | TCP 流式传输 | 消息头包含长度字段（见第 4 章拆包器） |
| 断线后状态丢失 | 客户端缓存过期 | 提供状态快照接口 |
| 大消息包拆分 | 协议限制 | 支持分包发送 + 消息重组 |
| SSL 证书问题 | 平台差异 | 证书链完整、兼容系统证书库 |
| 后台连接被杀 | iOS/Android 限制 | 断线重连机制 + 状态恢复 |

其中"断线重连 + 状态恢复"值得展开，因为它是设计出来的而不是补出来的。服务端需要一组配套接口：**会话保持**（连接断了会话 token 还在，重连携带 token 免重新登录）、**增量恢复**（客户端上报自己最后收到的序列号，服务端只补发缺口，而不是全量重推）、**快照兜底**（缺口太大时直接发全量快照，比补几百条消息更便宜）。补发窗口可以用环形缓冲实现：

```go
// 会话：连接断开后并不销毁，而是进入"待重连"状态
type Session struct {
    UID       int64
    Token     string        // 会话凭证；重连校验通过即复用，无需重新走登录
    SendSeq   uint64        // 本会话已下发的最后一条消息序号
    Pending   *RingBuffer   // 未确认消息的环形缓冲（容量 = 补发窗口）
    Snapshot  func() []byte // 全量快照生成器（业务层注册，兜底用）
}

// 重连处理：客户端携带 token 和它最后收到的 seq
func (s *Session) OnReconnect(conn Conn, lastAck uint64) error {
    gap := s.SendSeq - lastAck
    if gap == 0 {
        return nil // 没有缺口，直接恢复收发
    }
    if gap <= uint64(s.Pending.Cap()) {
        // 缺口在补发窗口内：按序重放，客户端按序号去重
        return s.Pending.Replay(conn, lastAck+1)
    }
    // 缺口太大（窗口外的消息已不在内存）：快照兜底更便宜
    conn.Send(&Msg{Type: MsgSnapshot, Body: s.Snapshot()})
    return nil
}
```

三个设计点值得注意。**补发窗口的大小是内存与快照成本的权衡**：窗口越大，能覆盖的断线场景越多，但每个待重连会话占的内存越多——万人在线、每人窗口 1000 条消息，就是千万元素级常驻内存。**快照生成器由业务层注册**，因为"什么算完整状态"只有业务知道；这也是为什么快照兜底通常按模块拆（背包快照、房间快照），而不是一个大而全的状态序列化。**SendSeq 是会话级的**，重连不重置——客户端的"我收到哪了"以序号为准，不以连接为准。这套机制与第 4 章广播设计、知识库主线"一致性、恢复与重连"是同一套东西的客户端视角。

## 3. Cocos Creator 与小游戏平台

Cocos Creator 是微信小游戏、抖音小游戏的主流引擎。它的技术特性和平台限制直接影响服务端设计。

### 3.1 小游戏平台的硬性约束

微信小游戏有一系列硬性约束，这些约束不是"建议"而是"限制"：

- **包体大小**：主包 4MB + 分包 20MB（总包上限随版本调整，以平台文档为准）。协议定义文件、首屏配置都要算进首包预算
- **内存限制**：iOS/Android 有上限（机型相关），客户端不能缓存太多数据——服务端下发的列表类接口要支持分页，客户端可能随时丢弃非当前页数据
- **域名白名单**：只能连接备案过的白名单域名，上线前必须配置——包括 WebSocket 域名和 CDN 域名，漏一个就是线上事故
- **开放数据域隔离**：好友排行榜等社交数据运行在独立的数据域，与主域不能直接通信，只能通过特定接口交换——服务端设计排行榜时要知道"平台好友关系"走平台开放数据，"游戏内好友"才走自己的服务

这些约束的汇总含义：**API 响应体积要小**。用同一个排行榜数据实际量一下两种编码的差距：

```go
type PlayerBrief struct {
    UID    int64  // varint，小数值实际 1-2 字节
    Name   string // UTF-8，长度前缀 + 内容
    Level  int32
    Score  int64
    Avatar string // URL，通常是最大头
}

// 100 人排行榜，同一份数据：
json.Marshal(players)      // ≈ 14 KB —— 字段名每人重复一遍是大头
proto.Marshal(pbPlayers)   // ≈ 3 KB  —— 字段号编码，字段名只在 .proto 里出现一次
```

差距的来源有两个：JSON 每条记录都重复传输字段名（`"uid":10001,"name":"..."`），Protobuf 只传字段号和值；整数值在 Protobuf 里走 varint 变长编码，等级 35 这样的数只要 1 字节。对小游戏来说这不只是流量——还是弱网下的加载等待时间和客户端内存占用。**列表类接口的验收标准里应该写上响应体积上限**（常见做法是 5KB 以内），而不是等客户端抱怨加载慢再回头裁字段。裁字段的优先级：先裁"客户端当前页用不到的"，再考虑列表接口不返回大字段（头像 URL 换成头像 ID，由客户端拼 CDN 地址）。

### 3.2 网络层特点：一切自己造

Cocos 的 WebSocket 实现接近浏览器原生 API：没有内置重连机制、没有内置消息队列（连接断开时发送即丢失）、心跳要自己实现。这意味着小游戏的客户端网络层质量**高度依赖团队自建**，服务端要按"客户端不可靠"来设计：消息带序列号便于客户端去重、关键接口幂等（同一个请求重发不产生副作用）、断线期间的推送允许客户端回来后拉取（推送 + 拉取兜底的双通道设计）。

### 3.3 小游戏的登录链路

小游戏登录有一个平台特有的时序，服务端必须实现对应接口：

```text
1. 客户端调用 wx.login() 获得 code（临时凭证，5分钟有效）
2. 客户端把 code 发给你的服务端
3. 服务端拿 code + appid + secret 调微信 code2session 接口
   → 换得 openid（用户唯一标识）+ session_key
4. 服务端绑定 openid ↔ 游戏账号，签发自己的会话 token
5. 之后所有请求带游戏会话 token，不再依赖微信会话
```

要点：**secret 只能放在服务端**；session_key 用于解密平台敏感数据，不要下发给客户端；会话过期与微信态解耦——玩家可能微信在线但你的会话已过期，也可能反过来，两条过期路径都要处理。

服务端 handler 的骨架大致是：

```go
func (h *LoginHandler) WxLogin(ctx context.Context, code string) (*LoginResult, error) {
    if code == "" {
        return nil, ErrEmptyCode
    }
    // code 是一次性的：同一个 code 第二次调 code2session 会被微信拒绝。
    // 本地先做一次性标记，把重放请求挡在自己这一层，也避免无效请求打到微信侧限流
    if !h.codeSeen.MarkOnce(code, 5*time.Minute) {
        return nil, ErrCodeReplay
    }
    resp, err := h.wx.Code2Session(ctx, h.appID, h.appSecret, code)
    if err != nil {
        return nil, fmt.Errorf("code2session: %w", err)
    }
    // openid 仅在当前 appid 内唯一；unionid 只有绑定了开放平台才可能有值（见 1.3）
    uid, err := h.identities.ResolveOrCreate(ctx,
        IdentityWechatOpenID, resp.OpenID,
        IdentityUnionID, resp.UnionID) // 可能为空，空则跳过该锚点
    if err != nil {
        return nil, err
    }
    // session_key 只在需要解密手机号等敏感数据时使用：留在服务端、短 TTL、用完即弃
    // 会话 token 是自家签发的，有效期、续期、踢人均与微信态无关
    token, err := h.sessions.Issue(uid, 7*24*time.Hour)
    if err != nil {
        return nil, err
    }
    return &LoginResult{UID: uid, Token: token}, nil
}
```

两个容易遗漏的细节。**code2session 是外部调用，要有超时与降级**：微信侧偶发超时会让玩家卡在登录页，超时设置通常在 2-3 秒量级，连续失败时返回明确的"登录服务繁忙"而不是无限转圈。**ResolveOrCreate 是并发热点**：同一玩家双击登录、断线重连竞态都可能并发到达，`(id_type, id_value)` 的唯一键 + 插入冲突时回查是标准处理方式（依赖数据库唯一约束做幂等，与第 8 章落库策略同理）。

### 3.4 小游戏的服务端适配清单

```text
小游戏服务端适配检查清单：

□ 1. API 响应体积控制在 5KB 以内，列表接口分页
□ 2. 使用 Protobuf 而非 JSON（体积减少 60-80%）
□ 3. 实现断线重连机制（小游戏切前后台极频繁）
□ 4. suspend/resume 挂起协议 + 宽限期（区分"切后台"与"真掉线"）
□ 5. 状态快照 + 增量恢复接口（重连后恢复状态）
□ 6. 域名白名单配置（WebSocket 域名 + CDN 域名）
□ 7. 分包资源的 CDN 地址管理
□ 8. 微信登录链路（code2session + code 防重放）与支付异步通知
□ 9. 身份锚点方案确认（unionid 可用性 / 手机号补绑路径，双端发行前置）
□ 10. 防刷机制（小游戏环境更容易被脚本批量访问）
□ 11. 推送 + 拉取双通道（断线期间的推送可回补）
```

## 4. Unreal Engine 5：3A 品质的代价

UE5 是 3A 游戏的首选引擎，网络框架非常成熟，也非常复杂。服务端开发者需要理解 UE5 的网络模型，才能正确对接。

### 4.1 权威服务器模型

UE5 使用**权威服务器（Dedicated Server）**模型：服务端是游戏世界的权威，客户端是"观察者"和"输入者"。客户端可以做预测（Prediction），但最终结果由服务端校验（Validation）。这与本书反复强调的"服务端权威"原则完全一致——UE5 把这套理念做成了引擎内置设施。

核心网络机制：

- **属性同步（Replication）**：服务端自动将 Actor 属性同步到客户端，支持条件同步（只有变化时、只对相关玩家）
- **RPC**：客户端/服务端远程过程调用，区分可靠/不可靠
- **Actor 复制**：整个 Actor 在服务端和客户端之间同步，配合相关性（Relevancy）控制同步范围

### 4.2 与自定义服务端的协作

很多项目用 UE5 做客户端，但用 Go/Java 做自定义服务端（而不是 UE5 Dedicated Server）——因为大世界的账号、社交、经济、跨服逻辑用通用后端技术栈更高效。这种混合模式下：

- UE5 内实现一个 NetworkComponent，处理与自定义服务端的连接管理、消息收发、心跳
- 战斗/物理等强引擎相关的部分留在 UE5 Dedicated Server，账号/交易/社交走自定义服务端
- 两类服务端之间需要一个内部协议桥接（通常是 gRPC 或内部 TCP 协议）

### 4.3 特殊挑战

| 挑战 | 原因 | 解决方案 |
|------|------|---------|
| UDP 可靠性 | UE5 默认用 UDP | 引擎自带可靠性层；对接自定义服务端时用 KCP/QUIC |
| 大规模同步 | MMO 场景 | 分组同步 + AOI（兴趣区域管理） |
| 属性同步冲突 | 多端同时修改 | 服务端权威 + 客户端预测 + 服务器回滚纠正 |
| 跨平台差异 | PC/主机/移动端 | 分平台适配网络参数和同步频率 |

### 4.4 预测与纠偏的服务端配合

"服务端权威 + 客户端预测 + 回滚纠正"（reconciliation）这行表格里的机制，服务端侧的配合决定了纠偏的体验。流程是：客户端对本地输入做**预测**（立即表现移动结果），每条输入带输入序号发给服务端；服务端按权威逻辑**裁决**，把结果连同"已裁决的输入序号"广播下发；客户端发现某条输入的权威结果与自己的预测不一致，从那条输入起**本地重演**后续输入。

服务端要注意三件事：

- **逐输入即时回，不要攒批**。为省带宽把多条输入的裁决攒在一个包里下发，客户端的重演就要滞后——纠正延迟越大，回滚幅度越猛，玩家看到的是画面"突刺"。带宽优化的正确位置是压缩编码与合并不可靠更新（第 4 章），不是延迟纠正包
- **纠正包必须带被裁决的输入序号**。缺了它客户端无法定位从哪条开始重演，只能整体重同步（画面回跳），体验比不纠正还差
- **预测偏差率是风控信号**。正常客户端的预测偏差应该在很小的百分比内波动；偏差率持续异常（服务端总是否决同一步移动）往往意味着客户端被篡改，可接入第 18 章的风控指标体系

## 5. 其他引擎速览

### 5.1 Cocos2d-x（Lua）

"老而弥坚"的引擎，大量历史项目仍在使用。核心优势是 **Lua 热更新**——改 Lua 脚本即可热更，不需要重新发版。对服务端的影响：这类项目通常使用自定义 TCP 协议和二进制编码（而非 Protobuf），服务端需要支持这种历史协议；Lua 热更依赖 CDN 资源分发（见 6.5 节）。

### 5.2 LayaAir

LayaAir 3.0 性能显著提升，适合微信/抖音小游戏。网络层与 Cocos Creator 类似，基于 WebSocket，服务端适配策略相同。

### 5.3 Godot

完全开源免费（MIT 协议），MultiplayerAPI 内置 ENet（UDP 可靠层）、WebSocket 和 TCP 支持。独立游戏的常见选择。对服务端的提示：Godot 的多人 API 默认假设"引擎 P2P 架构"，接自定义权威服务端时按普通 TCP/UDP 客户端对接即可。

## 6. 前后端协作的核心要点

### 6.1 协议格式的选择

| 格式 | 体积 | 编解码速度 | 强类型 | 代码生成 | 适用场景 |
|------|------|-----------|--------|---------|---------|
| **Protobuf** | ★★★★★ | ★★★★ | ✓ | ✓ | 大型游戏（主流选择） |
| **FlatBuffers** | ★★★★★ | ★★★★★ | ✓ | ✓ | 高性能热路径 |
| **MessagePack** | ★★★★ | ★★★ | ✓ | ✓ | 中型游戏 |
| **JSON** | ★★ | ★★ | ✗ | ✗ | 管理接口/原型 |

大型游戏用 Protobuf，极致性能场景用 FlatBuffers，管理后台和原型用 JSON——**按链路选格式，不搞一刀切**（详细对比与兼容性纪律见第 4 章）。

### 6.2 客户端-服务端交互模式

```text
模式1：请求-响应（最常用）
客户端 ──请求──→ 服务端 ──响应──→ 客户端
适用：登录、商店、背包、排行榜

模式2：服务端推送
服务端 ──推送──→ 客户端
适用：公告、活动通知、排行榜更新

模式3：实时同步（状态同步）
客户端 ──输入──→ 服务端 ──状态广播──→ 所有客户端
适用：MMO、实时对战

模式4：帧同步
客户端 ──输入──→ 服务端收集 ──帧广播──→ 所有客户端计算
适用：MOBA、RTS
```

四种模式的协议诉求不同：模式 1/2 走可靠通道，带请求 ID 和错误码；模式 3/4 带序列号和时间戳，允许丢旧保新（第 4 章）。**在协议设计期就标注每条消息属于哪种模式**，比上线后再区分容易得多。

### 6.3 客户端网络层的标准结构

服务端要对接的其实是一个"标准形态"的客户端网络层，了解它有助于服务端提供正确的配套：

```text
┌─────────────────────────────────────────┐
│              游戏逻辑层                   │
│   发起请求（带回调）/ 接收推送更新状态      │
├─────────────────────────────────────────┤
│           消息分发器 Dispatcher           │
│   按 MsgID 路由到注册的处理函数             │
├─────────────────────────────────────────┤
│              请求管理器                   │
│   请求队列 + 超时重试 + 序列号 + 去重       │
├─────────────────────────────────────────┤
│        传输层（WebSocket/TCP/KCP）        │
│   连接管理、心跳、断线重连、编解码           │
└─────────────────────────────────────────┘
```

服务端与之对应的配套责任：请求 ID 原样返回（客户端超时重试后按 ID 丢弃重复响应）、消息序列号（客户端断线回来报出最后序列号，服务端增量补发）、心跳应答（服务端要回 pong，客户端据此测 RTT）、关键接口幂等（重试不产生副作用）。

### 6.4 联调期的工程配套

前后端联调的效率不取决于沟通态度，取决于工程配套：

- **接口文档自动生成**：从 .proto / IDL 直接生成文档，禁止手工维护 Word——手写文档与代码的漂移是联调扯皮第一来源
- **Mock 服务**：协议定义完成后、服务端实现前，客户端可以先对接 mock 数据联调 UI；服务端也可以用 mock 客户端做压测
- **环境分层**：开发/测试/预发布/生产四级环境，协议版本和配置版本逐级验证；联调环境的服务端要能一键重置数据
- **联调期常见问题**与约定：

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 消息丢失 | 网络抖动 | 重试机制 + 消息 ID 去重 |
| 消息乱序 | UDP / 并发处理 | 序列号 + 接收缓冲区重排 |
| 版本不兼容 | 前后端不同步发布 | 协议版本号 + 兼容窗口（见第 4 章） |
| 状态不一致 | 客户端预测偏差 | 服务端权威 + 校验纠正包 |
| 性能瓶颈 | 消息过多过碎 | 消息合并 + 优先级（见第 4 章） |

### 6.5 CDN 与资源分发

CDN（内容分发网络）是游戏客户端资源分发的核心基础设施。对服务端开发者来说，理解 CDN 是为了设计资源更新策略和排查资源加载问题。

**CDN 在游戏中的三大用途**：

| 用途 | 说明 | 典型场景 |
|------|------|---------|
| **热更新资源** | 客户端代码、Lua/JS 脚本、配置表 | 版本更新、Bug 修复、活动配置 |
| **静态资源** | 图片、音频、视频、预制体 | 美术资源、UI 素材、过场动画 |
| **配置下发** | 活动配置、公告、版本信息 | 运营活动、紧急公告 |

**工作原理**：客户端请求资源 → DNS 解析到就近 CDN 节点 → 节点缓存命中直接返回（最快）；未命中则回源到源站，缓存后返回。对游戏热更来说，通常的流程是：

```text
1. 服务端生成版本号 + 资源清单（manifest）
2. 客户端启动时请求版本号
3. 对比本地版本，计算差异资源
4. 从 CDN 下载差异资源
5. 客户端加载新资源，完成热更新
```

**CDN 选型考虑**：节点覆盖（国内/海外、城市层级）、回源带宽成本、缓存策略（静态资源长缓存、配置短缓存）、HTTPS 支持、防盗链、预热功能（新版本上线前把资源推到各节点）。

**服务端与 CDN 的协作**：

- **版本管理**：服务端维护版本号和资源清单，客户端通过 CDN 下载资源
- **灰度发布**：按渠道/区域/比例下发不同版本的清单
- **回滚机制**：服务端切换版本号指针，客户端下载旧版本资源（资源文件按版本保留，不覆盖）
- **监控告警**：CDN 下载失败率、回源率、延迟监控

> **实战经验**：CDN 的缓存刷新不是实时的。新版本上线时，要确保资源文件名带版本号或内容哈希（如 `bundle_a3f9c2.bundle`），而不是依赖 CDN 缓存刷新。这样即使 CDN 缓存未更新，客户端也能通过新文件名获取最新资源——**内容寻址代替缓存失效**，是所有 CDN 场景的第一原则。

### 6.6 资源版本管线的服务端视角

资源系统连接着内容生产、版本发布、运行时内存和线上修复能力，服务端在其中承担的接口职责：

- **版本检查接口**（checkversion）：客户端上报平台、渠道、当前版本，服务端返回最新版本号、清单地址、是否强制更新
- **清单接口**：资源清单本身走 CDN，但清单的**索引**由服务端下发——这样切换版本、灰度、回滚都只是服务端改指针
- **强制更语义**：兼容性破坏的版本必须能强制升级（返回"最低可玩版本"，低于它的客户端拦截进入更新页）
- **下载兜底**：CDN 大面积故障时的备用源（源站限流直下）是最后手段，平时不用但要演练

版本检查接口的核心逻辑不长，值得完整看一遍：

```go
// 版本比较必须按数值逐段比，不能按字符串比：
// 字符串序里 "9.9.10" < "9.9.9"，会把最新版误判为旧版
func compareVersion(a, b string) int {
    as, bs := strings.Split(a, "."), strings.Split(b, ".")
    for i := 0; i < len(as) || i < len(bs); i++ {
        av, bv := 0, 0
        if i < len(as) {
            av, _ = strconv.Atoi(as[i])
        }
        if i < len(bs) {
            bv, _ = strconv.Atoi(bs[i])
        }
        switch {
        case av < bv:
            return -1
        case av > bv:
            return 1
        }
    }
    return 0
}

func (h *VersionHandler) CheckVersion(platform, channel, cur string) *VersionInfo {
    // 不同渠道可以处在不同版本（渠道审核节奏不同是常态）
    latest := h.rules.Latest(platform, channel)
    info := &VersionInfo{
        Latest:   latest.String(),
        Manifest: h.manifestURL(latest), // 清单地址指向 CDN；切版本/回滚只改这里
    }
    if compareVersion(cur, h.rules.MinPlayable(platform, channel)) < 0 {
        info.ForceUpdate = true // 低于最低可玩版本：客户端拦截进更新页
    }
    return info
}
```

**灰度也命中在这个接口上**：按渠道、UID 尾号、设备白名单等维度决定不同玩家拿到哪个 `latest`，实现上只是 `h.rules.Latest` 内部多一层分流规则——灰度策略与兼容窗口的完整设计见第 17 章。

资源打包策略（首包/分包/热更划分、依赖治理）属于客户端工程，但其产物——版本清单的结构——需要前后端一起定义。更完整的版本与发布体系见第 17 章。

## 8. 实战建议

### 8.1 服务端开发者必知

1. **了解客户端限制**：小游戏包体与内存上限、移动端后台挂起行为、Web 平台浏览器限制
2. **划清三类逻辑边界**：表现归客户端、交互客户端带边界、权威归服务端——用这条标准评审每一个"这块谁来算"的问题
3. **多端发行先定身份锚点**：确认 unionid 可用性与手机号补绑路径，身份绑定表与合并规则在写第一行登录代码前定下来
4. **选择合适的协议**：WebSocket 最通用，UDP/KCP 用于强实时；按链路选序列化格式
5. **设计可扩展的协议**：消息 ID 分模块、预留扩展字段、版本兼容设计（第 4 章）
6. **提供完善的工程配套**：文档自动生成、mock 服务、错误码说明——联调效率是设计出来的

### 8.2 性能优化检查清单

```text
□ 协议优化：Protobuf 优先、消息压缩、一帧内消息合并
□ 连接优化：心跳间隔匹配平台行为、断线重连 + 增量恢复
□ 体积优化：列表分页、字段裁剪、按接收者定制粒度
□ 资源优化：内容寻址的文件名、版本清单指针化、CDN 预热
□ 监控优化：接口延迟分平台统计、CDN 命中率、重连率
```

## 9. 常见陷阱总结

本章的陷阱大多不在"不会写"，而在"不知道客户端那边会发生什么"：

| 陷阱 | 后果 | 正确做法 |
|------|------|---------|
| 把切后台当掉线，按心跳超时踢下线 | 玩家回来面对重新登录和状态丢失，体验断裂 | suspend/resume 显式挂起 + 宽限期（2.1 节） |
| code2session 不防重放 | 同一 code 二次调用被微信拒绝，无效请求打到微信侧触发限流 | 本地一次性标记（MarkOnce），重放直接拒绝（3.3 节） |
| 双端发行没提前确认身份锚点 | 上线后账号不互通，只能手机号补绑，错过一个运营周期 | 立项时确认 unionid 可用性与补绑路径（1.3 节） |
| 自动合并多端账号 | 资产冲突客诉，回滚困难 | 让玩家选择，或合并后留申诉冻结期（1.3 节） |
| 版本号按字符串比较 | `"9.9.10" < "9.9.9"`，最新版被误判为旧版触发错误强更 | 数值逐段比较（6.6 节） |
| 白名单漏配 CDN 域名 | 提审通过后线上资源加载全挂 | 域名清单纳入上线 checklist 并演练（3.1 节） |
| 纠正包攒批发送 | 客户端重演滞后，画面突刺 | 逐输入即时回，带宽优化去别处找（4.4 节） |
| 补发窗口设成无限大 | 待重连会话吃光内存 | 有限窗口 + 快照兜底的组合（2.3 节） |
| 客户端乐观扣款无服务端对账 | 请求失败后账目黑洞 | 权威逻辑只认服务端结果，客户端仅"预期"（1.1 节） |
