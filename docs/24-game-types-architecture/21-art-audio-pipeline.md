# 21 音频与美术管线协作

> 本章目标：讲清资源从美术/音频工具走到玩家设备上的那条管线，以及服务端工程师在这条管线里的真实角色——**管契约、管版本、管审计，不管创作**。扩展讲次的前两章讲的是客户端的钱花在哪（第 19 讲）与质量怎么变成门禁（第 20 讲），本章补上最后一块：那些钱买回来的资源，是怎么被生产、验收和送达的。跨职能协作的混乱大多不是沟通态度问题，而是**接口没定义**——本章的目标就是把接口定义出来。
>
> **参考书籍**：资源管线与 DCC 工具链的工程实践参考各引擎官方 Art Pipeline 文档（Unity Asset Workflow、Unreal Asset Guidelines）；音频部分参考《游戏音频设计与制作》类实践指南与平台音频规范。

## 1. 资源管线全景：从 DCC 工具到玩家设备

资源管线的全程是一条转换链：**DCC 工具**（Photoshop/Blender/Spine/DCC 音频编辑器）产出源文件 → **导出**成中间格式 → **引擎导入**转换为引擎资产（重压缩、重编码、生成元数据）→ **打包**进包体或资源补丁 → 经 CDN 到达设备（第 17 讲多构件版本、第 19 讲分包）。

后端工程师需要建立的第一判断：**这条链上每一环都是有损且不可逆的**。PSD 转 PNG 丢图层、PNG 进引擎再压缩丢色彩、高码率音频降档丢动态——所以源文件（DCC 工程文件）必须留档，且版本与导出物对应。资源问题排障时"只有导出物没有源文件"的项目，等于服务端只有日志没有代码。

管线的第二判断：**管线是契约，不是流程图**。规格（尺寸/面数/格式）、命名（目录与文件名约定）、版本（资源与包的对应关系）三件事写下来并自动化检查的，才是契约；只存在于口头和 wiki 里的，装饰品。第 20 讲讲过"性能门槛写进 wiki 会被绕过"，资源契约同理。

## 2. 美术管线：规格、命名、版本、审计

### 2.1 资源规格：预算表的前置

第 19 讲的**资源预算表**（单屏 DC、面数、贴图内存）在美术侧的前身就是**资源规格**：角色多少面、贴图多大、几套换色、特效粒子预算。规格由性能预算倒推，而不是美术先做完再测——顺序反了的项目，最后都在"砍美术保帧率"，砍掉的全是前期投入。

规格要区分**源规格**与**运行时规格**：源文件可以 4K、可以高模，运行时按档导出（第 19 讲 LOD 与贴图分档）。审计检查的是运行时规格，创作约束的是源规格，两件事混着谈会变成鸡同鸭讲。

### 2.2 命名与目录：可检索性就是协作效率

命名约定解决三个问题：**是什么**（类型前缀：`tex_`/`mdl_`/`fx_`）、**属于谁**（模块路径：`ui/bag/`、`scene/forest/`）、**哪一版**（变体后缀与避免 `_new`/`_final`——没有日期与语义的版本后缀必然失控）。约定本身不重要，**可被工具校验**才重要：命名不合规的资源在 CI 直接进不了包，比评审时人眼把关可靠一个数量级。

### 2.3 资源版本：与代码版本的两套节奏

资源是二进制大文件，Git 的 diff/merge 对它无效，这是资源版本管理的根本困难。工程上的成熟做法：

- **源文件进版本库或 LFS**，导出物不进（由管线从源生成，保证可重建）。
- **资源与包版本解耦**：资源走自己的版本号与补丁链（第 17 讲的多构件版本），客户端按"包版本 + 资源版本"两个坐标判定可用性——服务端做版本检查接口时要把这两个坐标都纳入判定输入。
- **兼容窗口**：资源改了引用关系（删贴图、改骨骼）时，老包客户端还在跑——资源下线的策略与协议字段下线同构：先停新增引用、再观察依赖、最后移除（第 17 讲版本可判定性）。

### 2.4 工具链与资源审计：把规格变成门禁

导入导出的重复劳动（格式转换、压缩参数、平台分档）应该被**工具链自动化**——美术只导出中间格式，平台产物由管线生成。审计（audit）是管线的门禁层，检查四类规则：

1. **规格规则**：贴图超尺寸、面数超预算、音频超时长——超限资源直接拒绝进包（第 20 讲"门槛进 CI 不进 wiki"同款纪律）。
2. **命名规则**：2.2 节的约定校验。
3. **引用规则**：悬空引用（引用了不存在的资源）、孤儿资源（没人引用却被打进包——包体超标的常见肥肉）。
4. **重复规则**：内容相同的不同名文件（同一张图标存了五个副本）。

## 3. 音频管线：资源体系与触发模型

### 3.1 音频资源分类与格式档位

音频资源四类：**BGM**（长、循环、需无缝衔接）、**SFX 音效**（短、量大、并发多）、**语音**（角色台词，包体大头）、**环境音**（循环、随场景）。格式按平台分档（第 03 讲平台约束）：iOS/Android/小游戏容器支持的编解码与采样率各有差异，音频的兼容性事故（无声、爆音）多出在格式档位没按平台出包——归到第 20 讲兼容性归属判定的**资源层**。

### 3.2 触发模型：谁决定什么时候响

音频触发的判定口径：**本地事件的音效客户端自治，跟随全局状态的音频服务端驱动**。

- **客户端自治**：按钮点击、技能命中、UI 反馈——本地事件本地响，零网络依赖（第 19 讲三态交互的原则：本地即时反馈不进网络）。
- **服务端驱动**：活动开始/结束的主题曲切换、战斗阶段 BGM（Boss 阶段切换）、全服事件警报——这些的**时刻权威在服务端**（第 04 讲状态同步），客户端只是收到状态后查表播放。

服务端驱动音频的工程要点：**下发的是状态与事件，不是音频指令**。服务端说"活动开始了"（事件推送，第 11 讲的推送体系），客户端自己决定播什么——音频表现与网络解耦，弱网下宁可晚切歌也不能让 BGM 状态机和服务端状态机失配重置。边界案例：节奏类玩法的判定音频（音游判定音）表面是表现，实际参与玩法判定，走第 19 讲"动画帧事件不承载逻辑"的同款纪律——判定在逻辑层，音频只是表现的回声。

### 3.3 混音分组与玩家设置

混音按通道分组（BGM/音效/语音/环境），玩家设置落在通道音量上——这件事服务端的关联点是**设置同步**：音量偏好属于玩家数据（第 08 讲游戏数据模型），跨设备跟随账号走。房间语音（开黑通话）是独立的传输课题（实时语音转发、混流、成本），服务端向，与本章的"音频资源管线"是两条线，不要混为一谈。

## 4. 跨职能协作的成本接口

### 4.1 变更的代价不对称

规格变更（贴图上限从 1024 降到 512、音频从 mp3 换 opus）的成本分布极不对称：**提需求的一方改一行文档，执行的一方重导全部受影响资源、重跑审计、重出资源补丁**。所以规格变更要走与 API 变更同级的评审：影响面清单（哪些资源受影响）+ 过渡策略（老资源兼容到哪个版本）+ 时间表。判定口径：**改规格是接口变更，不是建议**。

### 4.2 资源出问题时的排障路径

资源问题的三层归属（第 20 讲兼容性归属判定的延伸）：

| 层 | 症状 | 定位手段 |
|----|------|---------|
| 资源本体 | 单个资源显示异常（贴图花屏、音频无声） | 检查导出物规格与源文件，用审计工具复核 |
| 管线层 | 一批资源同时异常（全部偏色、全部丢通道） | 检查导入参数与转换配置的最近变更——管线配置也要进版本管理 |
| 引用层 | 资源在但没生效（皮肤不生效、BGM 不切） | 查引用链与触发条件——常见是服务端状态没到，回到协议与状态排查 |

第三层是后端工程师最常接手的一层：**「资源没生效」有相当比例最后定位在服务端状态与判定**（活动状态没推送、权限字段没下发），归因时先确认服务端数据的正确性，再让客户端查表现层。

### 4.3 冻结点与验收节奏

版本冻结（第 20 讲出包关卡）之前要有**资源冻结点**：资源补丁截止、审计全绿、机型矩阵抽查通过。资源冻结晚于代码冻结是普遍现象，但要**显式管理**而不是默认发生——冻结点后进来的资源走下一班资源补丁，不拦版本。音频验收要真机听（压缩伪影与延迟在桌面端听不出来），进机型矩阵的抽查清单。

## 5. 代码示例

以下代码块是本章资源审计门禁的最小演示实现（非摘自真实项目）：规格/命名/孤儿三类规则的检查骨架。小节内代码块合并后可通过 `go vet` 与 `go build` 编译，并受全库代码块回归测试约束。

**资源审计规则检查**——第 2.4 节门禁层的最小骨架（真实实现接引擎导出清单与引用图）：

```go
// Asset 资源清单里的一条（导出管线产出，含运行时规格与引用）
type Asset struct {
    Name     string   // 如 tex_ui_bag_coin
    Kind     string   // tex / mdl / audio
    MaxDim   int      // 贴图最大边（运行时规格）
    RefCount int      // 被引用次数（0 = 孤儿）
}

// Audit 单条资源的审计结果
type Audit struct {
    Asset string
    Pass  bool
    Reason string
}

// CheckAsset 按门禁规则检查：命名规范 + 尺寸预算 + 孤儿判定
// 任一规则不过 = 拒绝进包（第 2.4 节：门禁在 CI，不在 wiki）
func CheckAsset(a Asset) Audit {
    audit := Audit{Asset: a.Name, Pass: true}
    if !strings.HasPrefix(a.Name, a.Kind+"_") {
        audit.Pass, audit.Reason = false, "命名不符: 缺类型前缀 " + a.Kind + "_"
        return audit
    }
    if a.MaxDim > 2048 {
        audit.Pass, audit.Reason = false, "超预算: 贴图最大边超 2048"
        return audit
    }
    if a.RefCount == 0 {
        audit.Pass, audit.Reason = false, "孤儿资源: 无引用却进包"
    }
    return audit
}
```

## 6. 实战建议

按角色给行动清单：

- **服务端开发**：做版本检查/资源补丁接口时，把"包版本 + 资源版本"当两个独立坐标处理（第 17 讲多构件版本）；排查"资源没生效"时先验证服务端状态数据（第 4.2 节引用层）。
- **接入资源管线时**：审计四类规则（规格/命名/引用/重复）做成 CI 门禁，超限资源拒绝进包；管线配置本身进版本管理——"这批资源为什么全偏色"的答案常在导入参数的最近变更里。
- **参与规格评审时**：把规格变更当 API 变更对待——要影响面清单、过渡策略与时间表；反过来，服务端字段下线时也用资源下线的同款三步（停新增、观察依赖、再移除）。
- **排期沟通时**：资源冻结点显式写进版本计划，晚到的资源走下一班补丁，不拦版本。

## 7. 常见陷阱总结

| 陷阱 | 说明 | 缓解 |
|------|------|------|
| 只留导出物不留源文件 | 资源不可重建，排障无据 | 源文件进 LFS，导出物由管线生成 |
| 版本后缀 `_new`/`_final` | 命名失控，检索瘫痪 | 类型前缀+模块路径，工具校验 |
| 规格先做后测 | 最后砍美术保帧率 | 预算表倒推规格，审计前置 |
| 审计只进 wiki | 超限资源照进不误 | 规则进 CI，拒绝进包 |
| 孤儿资源不清 | 包体悄悄膨胀 | 引用规则审计，无引用不进包 |
| 服务端下发音频指令 | 表现与网络耦合，弱网失配 | 下发状态与事件，客户端查表播放 |
| 规格变更当建议 | 执行方重导全量资源 | 规格变更走 API 级评审 |
| 资源冻结默认发生 | 冻结后资源混进版本 | 显式冻结点，晚到走补丁 |

## 8. 小结

本章把资源管线讲成一份三方契约：美术/音频按规格与命名生产，管线按规则审计与转换，服务端管版本坐标、状态权威与下线策略。跨职能协作的质量不取决于沟通频率，取决于**接口是否被定义并自动校验**——规格是性能契约（第 19 讲预算表的前置），审计是质量门禁（第 20 讲门禁纪律的资源版），版本坐标是发布契约（第 17 讲多构件版本的资源一翼）。

至此「扩展」三讲收束：第 19 讲讲客户端的成本模型，第 20 讲讲质量的生产线，第 21 讲讲资源的供给线——加上既有 18 讲，教程从后端主场延伸出一条完整的前端与协作路线。规划与后续方向见「章节扩展规划」页。
