# 06 常见框架：从最轻到最重

> 本章目标：帮助读者理解不同游戏服务器框架的设计哲学、适用场景和演进路径，避免"一上来就选最重框架"的常见错误。参考《游戏编程模式》中的"增量式设计"思想——从最简单的方案开始，在真正需要时才引入更复杂的框架。

---

## 为什么需要了解框架光谱？

很多团队在立项时就面临一个选择：用什么框架？这个问题看似简单，实际上隐藏着一个巨大的陷阱——**过度工程化**。一个卡牌游戏用 KBEngine，就像用航母去钓鱼。一个 MMO 用原生 HTTP Server，就像用自行车去跑高速。

游戏服务器框架的本质是**并发模型的选择**。不同的框架提供了不同的方式来回答一个问题：当 5000 个玩家同时在线时，如何让他们的操作互不干扰、高效处理？

理解框架光谱的关键不是背诵每个框架的 API，而是理解**每个框架解决了什么问题，又引入了什么新问题**。正如《游戏服务器架构与优化》所强调的：没有最好的框架，只有最适合当前阶段的框架。

### 框架选型的第一性原理

在选框架之前，先回答三个问题：

1. **你的游戏是什么交互模式？** 卡牌回合制（请求-响应即可）还是实时对战（需要长连接和状态同步）？
2. **你的团队技术栈是什么？** 会 Go 就别硬上 C++，会 Lua 就别逼着转 Java。
3. **你的项目阶段是什么？** 原型验证期需要快速出活，上线期需要稳定可靠。

### 框架光谱：从轻到重

```
轻 ◀──────────────────────────────────────────────────▶ 重

HTTP Server → Netty → Skynet → Pitaya → Photon → KBEngine → BigWorld
(通用)      (网络库)  (Actor)  (Go框架)  (商业)   (Python)   (商业)
```

| 重量级 | 框架 | 语言 | 核心模型 | 学习曲线 | 生产力 |
|-------|------|------|---------|---------|-------|
| 🪶 轻 | HTTP Server | 任意 | 请求-响应 | ⭐ | ⭐⭐ |
| 📦 中轻 | Netty | Java | Reactor | ⭐⭐ | ⭐⭐⭐ |
| 🎯 中 | Skynet | C + Lua | Actor | ⭐⭐⭐ | ⭐⭐⭐ |
| 🚀 中 | Pitaya | Go | Actor + Cluster | ⭐⭐ | ⭐⭐⭐⭐ |
| 💼 中重 | Photon Server | C# | Actor + 状态机 | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| 🏗️ 重 | KBEngine | C++ + Python | Entity + Cell | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 🏔️ 最重 | BigWorld | C++ + Python | Entity + Space | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

> **《百万在线》启示**：选择框架时要关注的不是"它能做什么"，而是"它在什么规模下开始出问题"。小框架在低并发时简单高效，但到了万级在线就会遇到瓶颈；大框架在万级以上游刃有余，但启动一个最小可用系统就需要大量配置。

## 1. HTTP Server：最简单的起点

### 为什么 HTTP 能做游戏服务器？

这听起来像开玩笑，但 HTTP Server 是**每一个游戏项目的起点**。原因很简单：登录验证、支付回调、活动接口、后台管理——这些系统天然就是请求-响应模式，不需要长连接，不需要实时推送。

《网络游戏核心技术与实战》指出，很多看似"需要实时"的系统，其实只需要"准实时"。挂机游戏的离线收益计算、卡牌游戏的抽卡结果、策略游戏的建筑升级——这些操作完全可以走 HTTP 接口。只有实时对战、场景内聊天、AOI 同步才真正需要长连接。

**适用场景**：

- 卡牌/回合制游戏的全部服务端逻辑
- 任何游戏的登录服、支付回调、活动接口
- SLG（策略游戏）的大部分逻辑
- 挂机游戏的离线收益计算
- 后台管理系统、GM 工具

**局限性**（必须清楚）：

- 无状态管理：每次请求都是独立的，需要自己维护玩家会话
- 无实时推送：客户端必须轮询或用 WebSocket 补充
- 无房间概念：多人对战需要额外实现房间系统
- 连接模型：HTTP 的短连接特性不适合高频交互

### 核心代码示例：一个能用的登录服

```go
// 最小可用的游戏登录服（约20行核心逻辑）
func loginHandler(w http.ResponseWriter, r *http.Request) {
    var req LoginRequest
    json.NewDecoder(r.Body).Decode(&req)

    // 查数据库验证用户
    var player Player
    if err := db.Where("username = ?", req.Username).First(&player).Error; err != nil {
        http.Error(w, "用户不存在", 401)
        return
    }

    // 生成 token
    token := jwt.NewWithClaims(jwt.SigningMethodHS256, jwt.MapClaims{
        "player_id": player.ID,
        "exp":       time.Now().Add(24 * time.Hour).Unix(),
    })
    tokenStr, _ := token.SignedString([]byte(secretKey))

    json.NewEncoder(w).Encode(map[string]string{"token": tokenStr})
}
```

> **坑：不要用 HTTP 做实时对战**。HTTP 的请求-响应模型意味着服务器无法主动推送消息。即使你用 WebSocket 补充了推送能力，HTTP 框架的设计哲学（无状态、短连接）也会让你在处理房间管理、AOI 同步时事倍功半。

### HTTP Server 局限性分析

| 维度 | HTTP Server | 游戏专用框架 |
|------|------------|------------|
| 连接模型 | 短连接/长连接 | 长连接/UDP |
| 实时推送 | 需要轮询/SSE/WebSocket | 原生支持 |
| 状态管理 | 需自己实现 | 内置 |
| 并发模型 | 线程/协程 | Actor/Entity |
| 房间管理 | 无 | 内置 |
| 热更新 | 不支持 | 部分支持 |

### 什么时候该从 HTTP 迁移？

当你发现以下情况时，说明 HTTP Server 已经不够用了：

1. **你需要实时同步**：玩家移动后，其他 50 人需要立刻看到——HTTP 轮询延迟太高
2. **你需要房间管理**：5v5 对战需要匹配、组房、状态同步——HTTP 无法自然表达
3. **你需要状态持久化**：玩家掉线后需要恢复现场——HTTP 无状态模型处理起来很痛苦
4. **你的代码开始变得复杂**：用 HTTP 模拟房间状态、用全局变量管理在线玩家——说明该换框架了

## 2. Netty：Java 游戏服务器的基石

### Netty 不是游戏框架，但它是 Java 游戏的起点

Netty 本身是一个高性能网络框架，不是游戏服务器框架。但几乎所有 Java 游戏服务器都建立在 Netty 之上，就像几乎所有 C++ 游戏都用 libevent 或 libuv 一样。

理解 Netty 的关键在于理解 **Reactor 模型**：一个线程负责接受连接，一组线程负责处理 I/O 事件。这种模型天然适合"大量连接、少量活跃"的游戏场景——10000 个玩家同时在线，但同一时刻只有几百人在操作。

《百万在线》中提到，Java 游戏服务器的最大优势是**生态成熟**：Spring 做业务层、Redis 做缓存、MySQL 做持久化、Kafka 做消息队列——所有组件都有成熟的 Java 客户端。最大劣势是 **GC 停顿**：当在线人数超过 5000 时，Full GC 的几秒停顿可能导致大面积掉线。

### Netty Pipeline：数据如何流经你的代码

```
┌─────────────────────────────────────┐
│           Netty Pipeline            │
│  ┌──────┐ ┌──────┐ ┌────────────┐  │
│  │Decode│→│Logic │→│   Encode   │  │
│  └──────┘ └──────┘ └────────────┘  │
│       ↑                  ↓          │
│  ByteBuf in          ByteBuf out   │
└─────────────────────────────────────┘
```

**核心特性**：

- Reactor 线程模型，基于 epoll/kqueue 的高并发
- 零拷贝、内存池——减少 GC 压力
- Channel Pipeline 编解码链——像流水线一样处理数据
- 心跳检测、断线重连——游戏必备

**Java 游戏服务器的典型架构**：

```
Netty (网络层) + Spring (业务层) + Redis (缓存) + MySQL (持久化)
```

### 核心代码示例：Netty 游戏服务器骨架

```java
// 启动 Netty 服务器（约15行关键配置）
ServerBootstrap bootstrap = new ServerBootstrap();
bootstrap.group(bossGroup, workerGroup)
    .channel(NioServerSocketChannel.class)
    .option(ChannelOption.SO_BACKLOG, 1024)
    .childOption(ChannelOption.TCP_NODELAY, true)
    .childHandler(new ChannelInitializer<SocketChannel>() {
        protected void initChannel(SocketChannel ch) {
            ChannelPipeline p = ch.pipeline();
            p.addLast("idle", new IdleStateHandler(30, 0, 0));
            p.addLast("decoder", new LengthFieldBasedFrameDecoder(65535, 0, 4, 0, 4));
            p.addLast("encoder", new LengthFieldPrepender(4));
            p.addLast("handler", new GameMessageHandler());
        }
    });
```

### 坑：GC 停顿是 Java 游戏服务器的阿喀琉斯之踵

当你的游戏在线人数达到 3000+ 时，GC 停顿会成为噩梦。一个 2GB 堆的 Full GC 可能耗时 2-5 秒，期间所有玩家操作都会卡住。常见的缓解手段包括：G1/ZGC 调优、对象池复用、减少短生命周期对象创建。但这些都只是"缓解"，无法"消除"。

> **决策建议**：如果你的团队是 Java 技术栈、游戏类型是 MMO 或策略游戏、在线规模在 5000 以内，Netty + Spring 是非常好的选择。如果需要万级以上在线或极低延迟的实时对战，考虑 Go（Pitaya）或 C++（Skynet）。

## 3. Skynet：轻量级 Actor 框架的代表

### 为什么 Skynet 在中文游戏圈如此流行？

Skynet 由云风开源，核心设计哲学是**用最少的资源做最多的事**。一个 Skynet 实例可以用不到 100MB 内存支撑 5000 个在线玩家——这在内存敏感的场景（如手游服务端、嵌入式设备）中是巨大优势。

Skynet 的 Actor 模型解决了一个核心问题：**如何在单进程内高效处理大量并发任务？** 每个服务是一个独立的 Actor，通过消息队列通信。Lua 协程让你用同步的写法写异步的代码——这比直接处理回调地狱优雅得多。

《游戏编程模式》中的"组件模式"在 Skynet 中体现得淋漓尽致：每个服务是一个独立组件，可以独立开发、测试、热更新。你可以把聊天服务、战斗服务、背包服务拆分成不同的 Actor，它们之间通过消息解耦。

### Skynet 的架构特点

```
┌──────────────────────────────────────────┐
│               Skynet                     │
│  ┌────────┐ ┌────────┐ ┌────────┐       │
│  │Service1│ │Service2│ │Service3│  ...   │
│  │ (Lua)  │ │ (Lua)  │ │ (C)   │       │
│  └───┬────┘ └───┬────┘ └───┬────┘       │
│      └────┬─────┘──────────┘            │
│           ↓                              │
│     消息队列 (全局单队列)                 │
│  ┌──────────────────────────────────┐   │
│  │    Timer   │   Network   │  IO   │   │
│  └──────────────────────────────────┘   │
│        多个工作线程消费队列               │
└──────────────────────────────────────────┘
```

**架构要点**：

- 一个 Skynet 实例 = 一组 C 线程 + 一组 Lua 服务
- 每个服务是独立 Actor，通过消息通信——天然避免锁竞争
- Lua 协程实现异步 I/O 的同步写法——代码可读性极佳
- 全局消息队列，工作线程竞争消费——负载自动均衡

### 核心代码示例：Skynet 服务间通信

```lua
-- Skynet 服务间通信的核心模式（约15行）
local skynet = require "skynet"

-- 服务A 发送消息给服务B
function send_to_player_service(fd, msg)
    skynet.send("player_service", "lua", "on_message", fd, msg)
end

-- 服务B 接收并处理消息
function CMD.on_message(fd, msg)
    local cmd = string.sub(msg, 1, 4)
    if cmd == "MOVE" then
        handle_move(fd, string.sub(msg, 5))
    end
end
```

### 坑：Skynet 的全局单队列是双刃剑

所有服务共享一个消息队列意味着：**一个慢服务会拖慢整个系统**。如果聊天服务的敏感词过滤逻辑很慢（比如用正则匹配大量敏感词），它会阻塞队列，导致战斗服务的消息延迟。

**应对策略**：把耗时操作（如复杂计算、I/O 操作）放到独立的 C 服务中，避免阻塞 Lua 服务的消息处理。

### 什么时候不该用 Skynet？

- **团队不会 Lua**：学习 C + Lua 的成本比想象中高
- **需要强类型**：Lua 的动态类型在大型项目中容易出 bug
- **需要内置集群**：Skynet 不提供集群支持，需要自己实现
- **内存不是瓶颈**：Go 的 Pitaya 开发效率更高，除非内存极度敏感

## 4. Pitaya：Go 生态的现代游戏服务器框架

### 为什么 Go 正在成为游戏服务器的主流选择？

Go 语言的 goroutine 天然适合游戏服务器的并发模型。每个玩家连接一个 goroutine，百万个 goroutine 只占几百 MB 内存——这比 Java 的线程模型轻量得多。更重要的是，Go 的 CSP（通信顺序进程）模型与游戏服务器的"消息驱动"架构高度吻合。

Pitaya 在 Go 游戏框架中的定位是**开箱即用的 Actor + 集群框架**。它解决了 Skynet 的最大痛点——内置集群支持。通过 etcd 做服务发现、NATS 做消息总线，Pitaya 可以轻松实现跨服通信、负载均衡。

《游戏服务器架构与优化》指出，Go 游戏服务器的另一个优势是**部署轻量**：一个静态编译的二进制文件，几 MB 大小，启动时间不到 1 秒。这在容器化部署（Docker/K8s）场景中非常有价值。

### Pitaya 的架构设计

```
┌─────────────────────────────────────────┐
│              Pitaya 架构                 │
│  ┌──────────┐  ┌──────────┐  ┌───────┐ │
│  │ Frontend │  │ Backend  │  │ Agent │ │
│  │ (网关)   │→│ (逻辑)   │→│(玩家) │ │
│  └──────────┘  └──────────┘  └───────┘ │
│       │             │            │       │
│       └───────── NATS ──────────┘       │
│              (消息总线)                   │
└─────────────────────────────────────────┘
```

**核心优势**：

- **内置集群**：etcd 服务发现 + NATS 消息总线，开箱即用
- **Protobuf 序列化**：高效、跨语言、版本兼容
- **Actor 模型**：每个玩家一个 Agent，天然避免并发问题
- **Go 生态**：Redis、MySQL、Kafka 的 Go 客户端都很成熟

### 核心代码示例：Pitaya 玩家移动

```go
// Pitaya 的核心是"组件 + 方法"的模式（约15行）
func (p *Player) Move(ctx context.Context, msg *MoveRequest) (*MoveResponse, error) {
    p.X = msg.X
    p.Y = msg.Y

    // 广播给同场景的其他玩家
    p.GetServer().BroadcastToScene(p.Scene, "PlayerMoved", map[string]interface{}{
        "id": p.ID, "x": p.X, "y": p.Y,
    })

    return &MoveResponse{Success: true, X: p.X, Y: p.Y}, nil
}
```

### Pitaya vs Skynet 对比

| 维度 | Pitaya | Skynet |
|------|--------|--------|
| **语言** | Go | C + Lua |
| **并发模型** | goroutine (CSP) | Actor + 协程 |
| **集群支持** | 内置 (etcd/NATS) | 需自建 |
| **内存效率** | 中等 (GC) | 极高 (无GC) |
| **开发效率** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| **性能** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **适合场景** | 中型 MMO、多人在线 | 中小型、嵌入式 |

### 坑：Go 的 GC 虽然比 Java 好，但不是没有

Go 的 GC 停顿通常在 1-10ms，比 Java 的 100ms+ 好很多。但在高频操作场景（如每秒处理 10 万次移动广播）中，GC 仍然可能导致偶尔的延迟毛刺。Pitaya 的解决方案是**对象池复用**和**批量发送**，减少内存分配压力。

## 5. Photon Server：商业级多人游戏引擎

### 商业框架的价值：用钱买时间

Photon 是 Exit Games 公司的商业产品，广泛用于手游和独立游戏。它的核心价值不是"比开源框架更好"，而是**开箱即用**。房间管理、匹配系统、状态同步、帧同步——这些功能如果自研需要 3-6 个月，Photon 几天就能搞定。

**适用场景**：

- 手游快速上线（1-2 个月开发周期）
- 独立游戏团队（没有专职服务端工程师）
- 需要帧同步的 MOBA/RTS（Photon Quantum）
- 需要状态同步的射击游戏（Photon Fusion）

**不适合场景**：

- 需要完全掌控底层逻辑的大型 MMO
- 预算有限的长期项目（按 CCU 收费）
- 需要深度定制的特殊玩法

### Photon 家族产品对比

| 产品 | 定位 | 同步方式 | 价格 | 适用场景 |
|------|------|---------|------|---------|
| Photon Server | 本地部署 | 自定义 | 付费 | 大型项目，完全控制 |
| Photon Cloud | 云托管 | 自定义 | 按CCU | 快速上线，全球部署 |
| PUN (Unity) | Unity 插件 | 状态同步 | 按CCU | Unity 手游 |
| Quantum | 帧同步框架 | 帧同步 | 付费 | MOBA、RTS |
| Fusion | 状态同步框架 | 状态同步 | 免费/付费 | 射击、动作 |

### 坑：Photon 的按 CCU 收费可能很贵

假设你的游戏有 10 万日活，其中 1 万同时在线。Photon Cloud 的月费可能在几千到几万美元之间。如果你的游戏生命周期超过 2 年，自研框架的总成本可能更低。**决策关键**：你是要"快速验证"还是"长期运营"？

> **《百万在线》建议**：如果预算允许且时间紧迫，Photon 是非常好的选择。但要提前评估长期成本——当你的 CCU 超过 5 万时，Photon 的费用会急剧上升。

## 6. KBEngine：开源 MMO 引擎

### KBEngine 的定位：大型 MMO 的开源解决方案

KBEngine 源自蜗牛游戏，用 Python（CellApp）+ C++（底层引擎）实现了一套完整的 MMO 服务端架构。它的核心概念是 **Entity + Cell**：每个在线玩家是一个 Entity，场景被分割成多个 Cell，Entity 在 Cell 之间迁移。

**为什么选择 KBEngine？**

- **完整**：登录、匹配、战斗、背包、公会——全都有
- **开源**：免费使用，可以深度定制
- **文档丰富**：中文社区活跃，大量实战案例
- **性能优秀**：C++ 底层保证了关键路径的性能

**KBEngine 的架构**

```
┌──────────────────────────────────────────┐
│            KBEngine 架构                  │
│                                          │
```

### 核心代码示例：KBEngine 玩家实体

```python
# KBEngine 的核心是 Entity（约20行核心逻辑）
class Player(KBEngine.Entity):
    def __init__(self):
        KBEngine.Entity.__init__(self)
        self.hp = 100
        self.level = 1

    def onDie(self, killerId=None):
        self.hp = 0
        self.client.onDied()
        # 5秒后复活
        self.addTimer(5, 0, self.onRespawnTimer)

    def onRespawnTimer(self, timerHandle):
        self.hp = 100
        self.client.onRespawned(0, 0, 0)
```

### 坑：KBEngine 的 Python 层性能瓶颈

KBEngine 的底层是 C++，但业务逻辑用 Python 编写。当单个 CellApp 的 Entity 数量超过 5000 时，Python 的 GIL 和解释器开销会成为瓶颈。**常见解决方案**：把热点逻辑下沉到 C++ 层，或者用多 CellApp 分担负载。

### 什么时候该考虑 KBEngine？

- 你的游戏是 MMO（需要大世界、AOI、Entity 迁移）
- 团队有 Python 经验
- 预算有限，无法购买商业引擎
- 需要在大型 MMO 基础上做深度定制

## 7. BigWorld：重量级商业解决方案

BigWorld 是最老牌的 MMO 服务端引擎，被《坦克世界》等大作采用。它的核心优势是**完整性和稳定性**：自动空间分割、兴趣管理（AOI）、Cell 分布式处理——这些都是大型 MMO 的刚需。

但 BigWorld 的问题也很明显：**商业授权昂贵**（通常数十万美元起）、**学习曲线陡峭**、**社区相对封闭**。对于中小团队来说，KBEngine 或自研是更实际的选择。

### KBEngine vs BigWorld 对比

| 维度 | KBEngine | BigWorld |
|------|----------|----------|
| **开源状态** | 开源 | 商业闭源 |
| **架构** | Entity + Cell | Entity + Space + Cell |
| **AOI** | 需插件 | 内置 |
| **成本** | 免费 | 昂贵 |
| **适合** | 中大型 MMO | 超大型 MMO |

## 按项目阶段选型

### 阶段一：原型验证（1-3 人，1-2 周）

**推荐**：HTTP Server + 简单 WebSocket

**原因**：最快出活，验证玩法是否可行。不要在这个阶段引入任何复杂框架——你的首要任务是验证"这个游戏好不好玩"，不是"架构是否优雅"。

**预期支撑**：100-500 在线

### 阶段二：小规模上线（3-10 人，1-3 个月）

**推荐**：Skynet 或 Pitaya

**原因**：足够支撑 1K-10K 在线，有成熟的 Actor 模型。选择依据：团队会 Lua 选 Skynet，会 Go 选 Pitaya。

### 阶段三：中型项目（10-30 人，3-6 个月）

**推荐**：Pitaya + Redis + 集群

**原因**：Go 生态、水平扩展、维护成本低。当你的在线人数超过 1 万时，单机架构会遇到瓶颈，需要集群支持。

### 阶段四：大型 MMO（30+ 人，6-12 个月）

**推荐**：自研 或 KBEngine 魔改

**原因**：需要完全控制 Entity 模型、AOI、状态同步。这个阶段的决策应该基于具体需求，而不是框架的名气。

### 阶段五：手游快速上线（1-3 个月）

**推荐**：Photon (PUN/Quantum/Fusion)

**原因**：客户端 SDK 完善，匹配/房间开箱即用。对于手游来说，"快速上线"比"极致性能"更重要。

## 框架迁移指南

### 迁移的核心原则

迁移不是"推倒重来"，而是"渐进式替换"。保留能用的部分，逐步替换有问题的部分。每次迁移只解决一个核心问题，不要试图一步到位。

### 从 HTTP Server 迁移到 Skynet/Pitaya

```
迁移步骤：
1. 保留 HTTP 层做登录/支付等辅助服务
2. 新增 Skynet/Pitaya 实例处理实时游戏逻辑
3. HTTP 层与游戏服务器通过内部 RPC 通信
4. 逐步将有状态逻辑迁移到游戏服务器
5. 下线 HTTP 层的有状态逻辑
```

**关键**：不要试图一次性迁移所有逻辑。先把"实时性要求最高"的逻辑（如移动同步、战斗）迁移过去，验证稳定后再迁移其他逻辑。

### 从 Photon 迁移到自研

```
迁移步骤：
1. 分析 Photon 的游戏逻辑层
2. 提取核心游戏逻辑，去除 Photon 依赖
3. 实现自己的网络层（可以用 Netty/Pitaya）
4. 实现房间管理和匹配系统
5. 逐步替换 Photon SDK
```

**坑**：Photon 的很多功能是隐式实现的（如状态同步的插值、预测）。迁移时很容易遗漏这些"看不见的功能"，导致游戏体验下降。

## 常见陷阱与避坑指南

### 陷阱一：过度选型

> "我们要做一个卡牌游戏，但考虑到未来可能做 MMO，所以我们选 KBEngine……"

这是最常见的错误。**不要为未来的假设需求选择当前不需要的框架**。卡牌游戏用 HTTP Server 足够了。等真的要做 MMO 时再换框架，成本远低于一开始就背着重框架开发。

### 陷阱二：忽略团队技术栈

框架再好，团队不会用就等于零。一个只会 Python 的团队硬上 Go 框架，开发效率可能还不如用 Python 框架。

### 陷阱三：只看性能指标，不看开发体验

Skynet 的内存效率比 Pitaya 高，但 Pitaya 的开发效率比 Skynet 高。如果你的团队有 5 个 Go 工程师，选 Pitaya 的总产出可能远高于选 Skynet。

### 陷阱四：忽视运维成本

开源框架意味着你要自己处理部署、监控、日志、告警。商业框架（如 Photon Cloud）帮你处理了这些，但要为此付费。**选框架时一定要算"总拥有成本"，不只是"授权费用"**。

## 小结

| 关键问题 | 答案 |
|---------|------|
| 最简单的起步方式？ | HTTP Server + WebSocket，半小时出原型 |
| 做 MMO 选什么？ | Go (Pitaya) 或 C++/Python (KBEngine) |
| 手游最快上线？ | Photon Cloud，客户端 SDK 买现成的 |
| 为什么 Go 游戏服务器越来越多？ | goroutine 并发简单、CSP 模型天然适合多服务解耦、部署轻量 |
| Skynet 适合什么？ | 中小型项目、Lua 开发者团队、追求极致内存效率 |
| 需要帧同步？ | Photon Quantum 或自研 |
| 团队小怎么办？ | 从 HTTP Server 开始，逐步演进 |
| 预算有限？ | KBEngine 或 Pitaya，免费且功能完整 |

### 框架选型决策树

```
你的游戏是什么类型？
├── 卡牌/回合制 → HTTP Server 足够
├── SLG（策略） → HTTP Server + 定时任务
├── 射击/动作（小规模） → Photon Fusion
├── MOBA/RTS（帧同步） → Photon Quantum 或自研
├── MMO（中型） → Pitaya + 集群
├── MMO（大型） → KBEngine 或自研
└── 不确定 → HTTP Server 先验证玩法
```

> **最终建议**：《游戏编程模式》告诉我们，最好的架构是"刚好够用的架构"。选择框架时，从最简单的方案开始，在真正遇到瓶颈时再引入更复杂的解决方案。记住：**框架是工具，不是信仰**。
