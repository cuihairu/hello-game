# 13 运维与基础设施实战

> 本章目标：掌握游戏后端的容量规划、监控告警、发布与回滚、开服保障、故障应急的完整工程方法——重点是游戏运维区别于普通互联网服务的那些特殊性。
>
> 参考书籍：《网络游戏核心技术与实战》（中嶋谦互）的运维框架、《SRE：Google 运维解密》的可靠性思想。

游戏上线只是开始，真正的考验在于持续运营。服务器崩溃、流量突增、数据丢失——每一个运维失误都可能导致玩家流失和收入损失。《百万在线》中指出：游戏运维不是"修服务器"，而是一个需要持续优化、不断改进的系统工程。

很多团队把运维当作"技术活"来对待，忽视了它的"管理属性"。事实上，运维的核心挑战不只是技术问题，更是**流程问题**：如何预判风险、如何快速响应、如何从故障中学习。一个有完善流程的团队，即使技术能力一般，也往往比一个技术强但流程混乱的团队更稳定。

游戏运维还有两个区别于普通互联网服务的特殊性，本章会反复出现：

- **有状态**：玩家会话、内存态数据让"随手重启实例"的云端常规操作变得危险，发布和扩容都要考虑状态迁移
- **峰谷悬殊**：负载按晚间峰值规划、凌晨大量空转，弹性与成本优化的空间和动机都比 web 服务大

## 1. 基础设施成本估算

### 1.1 成本构成全景

网络游戏的基础设施成本远不止服务器采购。完整的成本模型包括五个维度：硬件成本、软件成本、机房成本、运维成本、灾备成本。很多团队只算了硬件成本，忽略了带宽、人力等隐性成本，导致预算严重不足。

```text
┌──────────────────────────────────────────┐
│              基础设施成本结构               │
├──────────────────────────────────────────┤
│  硬件成本 ─── 服务器、存储、网络设备       │
│  软件成本 ─── 操作系统、数据库许可、CDN    │
│  机房成本 ─── 机柜租金、电力、带宽         │
│  运维成本 ─── 人力、监控工具、7x24 值班    │
│  灾备成本 ─── 异地备份、容灾切换           │
└──────────────────────────────────────────┘
```

除了五个常规维度，游戏还有一类容易被漏算的**全局组件成本**：跨服战场、匹配服务、网关、聊天、排行榜这些"全服共享"的组件不随区服数量线性增长，但也不是免费的——它们要按全区在线峰值规划，且任何一个区服扩容都可能推高它们的容量需求。算区服成本时漏掉全局组件，是预算超支的常见原因。

### 1.2 带宽估算示例

带宽是最常被低估的成本。估算方法是把"每玩家带宽 × 在线峰值"再乘以冗余系数：

```text
假设：5 万人同时在线的 MMO
├── 每玩家平均带宽：50 Kbps（下行，状态同步场景）
├── 峰值总带宽：50,000 × 50 Kbps = 2.5 Gbps
├── 冗余系数：× 1.5（突发广播、活动高峰）≈ 3.75 Gbps
└── 按 ¥200/Mbps/月 包月计：约 ¥750,000/月
```

三个降带宽的工程手段，优先级从高到低：

1. **AOI 与分频广播**（第 6 章框架）：只把状态发给"看得见的人"，一条广播从 5 万人缩到视野内数百人
2. **Delta 同步与合并**（第 4 章协议）：只发变化字段，多次变化合并成一包
3. **频率分级**：远处玩家低频率同步、近处高频率，闲时数据（排行榜、聊天离线拉取）不走实时通道

带宽估算要先做这个逐层优化再报价——"5 万人 × 50Kbps"是未优化协议的粗估，实际成本可能只有它的几分之一。

### 1.3 云服务 vs 自建机房

| 维度 | 云服务 | 自建机房 |
|------|--------|---------|
| 初始投入 | 低（按月付费） | 高（数百万起） |
| 扩容速度 | 分钟级 | 周/月级 |
| 运维人力 | 1-2 人 | 5-10 人 |
| 长期成本 | 较高 | 较低 |
| 灾备能力 | 内置（跨可用区） | 需额外建设 |

**建议**：中小团队用云服务，头部大厂自建。云服务的弹性和免运维对中小团队远比长期单价重要——尤其是游戏这种"成功项目一年百倍增长"的行业，自建机房的采购周期经常追不上业务增长。

### 1.4 成本优化策略

成本优化不是"省钱"，而是"把钱花在刀刃上"。核心策略：

1. **弹性伸缩**：基于历史曲线预测性扩容，低峰期自动缩容（对无状态的匹配、网关、聊天类服务收益最大）
2. **预留实例**：基础负载用预留/包年实例（折扣 30-50%），弹性峰值用按量实例
3. **资源复用**：开发测试环境错峰、用完即毁，减少空闲资源
4. **存储分层**：热数据 SSD、温数据 HDD、冷数据对象存储（日志与归档的常规做法，见第 3.3 节）

> **陷阱**：成本优化最常见的错误是"过度优化"——为了省几万块的服务器成本导致容量不足，玩家体验下降，损失的收入远超节省的成本。优化前提是不动玩家可感知的体验；另一个隐蔽错误是"砍掉了灾备"，平时省下备份的钱，第一次数据事故全部还回去。

## 2. 负载曲线与容量规划

### 2.1 游戏负载的峰谷特征

网络游戏的负载曲线呈现明显的**峰谷特征**：午间小高峰（12:00-14:00）、晚间大高峰（20:00-23:00）、凌晨低谷（2:00-8:00）。周末峰值约为工作日的 1.5-2 倍，节假日更高。

这意味着：服务器需要按峰值配置，但大部分时间在空转——弹性伸缩的价值空间很大，但受本章开头说的"有状态"限制：真正能随意伸缩的是无状态组件（网关、匹配、HTTP 服务），玩家所在的游戏服/房间服不能在玩家在线时缩容。

| 游戏类型 | 峰谷比 | 峰值时段 | 扩容策略 |
|---------|--------|---------|---------|
| MMORPG | 3:1 | 20:00-23:00 | 按区服独立扩缩，玩家分流 |
| MOBA | 5:1 | 19:00-24:00 | 房间服弹性伸缩（对局结束即释放） |
| 休闲手游 | 2:1 | 12:00-14:00, 20:00-22:00 | 全局弹性伸缩 |
| SLG 策略 | 1.5:1 | 全天较均匀 | 基础预留 + 少量弹性 |

**MOBA 的峰谷比最大**（5:1），但它的房间服天然无状态化程度高（对局结束房间即销毁、状态可快照），弹性伸缩收益也最高——凌晨释放大部分房间服务器是可行的。

### 2.2 容量推演：从单机压测到开服机器数

容量规划的核心是**一条推演链**：单机压测数据 → 组件容量上限 → 按峰值反推机器数。跳过推演直接"拍脑袋开 20 台"是容量事故的常见起点：

```text
推演链示例（开服 MMO，目标首日峰值 30,000 人在线）：

1. 单机游戏服压测：稳定承载 3,000 人（CPU <70%、P95 <100ms）
2. 会话网关：单机 20,000 长连接
3. 推演：
   ├── 游戏服：30,000 ÷ 3,000 = 10 台 → 留 50% 余量 = 15 台
   ├── 网关：30,000 ÷ 20,000 = 2 台 → 开服洪峰系数 ×3 = 6 台
   ├── 数据库：按每玩家每秒 0.2 次写 × 30,000 = 6,000 写/秒
   │          → 主从架构 + 连接池验证
   └── Redis：每玩家会话 ~2KB × 30,000 ≈ 60MB → 单实例绰绰有余，
              但要按"命令 QPS"而不是内存选型
4. 全局组件按全区峰值校验一遍（跨服、匹配、聊天）
```

两条推演纪律：

- **余量是给故障的，不是给增长的**。留 50% 余量的第一目的是"坏掉一台机器流量接得住"，增长需求靠弹性扩容满足，两者不要混为一谈。
- **内存按"每玩家常驻 × 峰值在线"估算并实测校准**。每玩家内存占用（会话、背包缓存、AOI 列表）是容量规划的基本参数，应该来自压测实测而不是拍脑袋；它也是"单机在线上限"的第一约束——很多游戏服先撞内存墙再撞 CPU 墙。

### 2.3 压测模型设计

负载测试不能只看峰值，需要模拟真实场景。推荐**阶梯式加压**：逐步增加负载，观察系统在不同压力下的表现，找出瓶颈点和"拐点"（延迟开始非线性上升的位置）。拐点位置决定安全水位——生产负载应控制在拐点的 60-70% 以内。

**压测核心指标**：

| 指标 | 目标值 | 告警阈值 | 说明 |
|------|--------|---------|------|
| 平均响应时间 | < 50ms | > 100ms | 请求处理速度 |
| P95 响应时间 | < 100ms | > 200ms | 95% 请求的延迟 |
| 错误率 | < 0.1% | > 1% | 请求失败比例 |
| 单机承载人数 | 达到设计目标 | 低于目标 80% | 容量推演的输入 |
| CPU 使用率 | < 70% | > 80% | 峰值 CPU |
| GC 暂停 | < 10ms | > 50ms | 垃圾回收影响 |

| 游戏类型 | 压测重点 | 特殊考虑 |
|---------|---------|---------|
| MMO | 在线人数、AOI 广播 | 大规模状态同步、数据库写入 |
| FPS/TPS | 延迟、丢包、同步精度 | UDP 性能、帧同步计算 |
| MOBA | 匹配速度、团战性能 | 房间创建销毁频率、5v5 实时同步 |
| 卡牌 | 并发登录、抽卡瞬时峰值 | 活动开启瞬间的洪峰（零点抽卡） |
| 挂机 | 定时任务批量处理 | 离线收益批量结算、整点重置 |

压测有两个容易失真的细节：

- **机器人行为要真实**。压测机器人只发登录和心跳，测出来的上限会比真实场景（移动 + 战斗 + 聊天 + 交易混合）高数倍。机器人脚本按真实玩家行为分布建模（在线时长、操作频率分布来自上一款产品或行业数据）。
- **数据要有量**。空库压测和亿行库压测的数据库表现完全不同。压测前灌入接近生产规模的数据量，尤其覆盖最慢的查询路径。

> **陷阱**：压测最常见的错误是"测试环境与生产环境差异太大"——更好的硬件、没有模拟真实网络延迟、没有真实数据量。压测结果很好，上线却扛不住。建议在与生产同规格的环境压测，至少对"存疑的部分"做生产环境的影子流量验证。

## 3. 监控与日志体系

### 3.1 三层监控架构

监控是运维的"眼睛"。推荐三层监控架构：

```text
┌─────────────────────────────────────────────┐
│  第一层：基础设施监控                          │
│  CPU │ 内存 │ 磁盘 │ 网络 │ 进程 │ 端口       │
│                    ↓ 告警                    │
│  第二层：应用性能监控 (APM)                    │
│  QPS │ 延迟 │ 错误率 │ 在线人数 │ 连接数       │
│                    ↓ 告警                    │
│  第三层：业务指标监控                          │
│  登录成功率 │ 充值成功率 │ 掉线率 │ 活动参与    │
└─────────────────────────────────────────────┘
```

三层的价值分工：第一层告诉你"机器是否正常"，第二层告诉你"服务是否正常"，第三层告诉你"玩家是否正常"。**很多故障是第三层先发现的**——充值成功率突然下降、某区服在线人数异常下滑，可能比 CPU 告警早几分钟暴露数据库连接池耗尽。反过来，只看第一层会有大量"机器正常但玩家已经玩不了"的盲区。

游戏业务监控里最值得做的三条告警：

- **在线人数突降**（5 分钟内跌幅超阈值）：宕机、网络故障、版本事故的第一信号，比任何技术告警都早
- **登录成功率**（< 99% 告警）：登录链路覆盖网关、账号服务、会话服务，任何一环故障都体现在这里
- **充值成功率**（< 基线告警）：直接影响收入，且往往在技术指标恶化前先动

### 3.2 工具选型

| 层级 | 工具 | 用途 | 部署成本 |
|------|------|------|---------|
| 指标采集 | Prometheus + Exporter | 系统/应用指标 | 低 |
| 可视化 | Grafana | 监控看板 | 低 |
| 日志收集 | Filebeat / Vector | 日志采集 | 中 |
| 日志存储 | Elasticsearch / Loki | 日志检索 | 高 / 中 |
| 链路追踪 | Jaeger / SkyWalking | 分布式追踪 | 中 |
| 告警通知 | Alertmanager | 告警路由与静默 | 低 |

选型上注意：日志系统的成本弹性很大，ES 全量索引的机器成本可能超过游戏服本身——先用 Loki 这类"索引少、存量大"的方案起步，检索需求真的长起来再升级；链路追踪在微服务化的后端（网关→账号→游戏服→跨服）里价值显著，单体架构可以先不做。

### 3.3 日志规范

结构化日志是高效运维的基础。一条规范的业务日志包含：时间戳、级别、服务名、**追踪 ID**、玩家 ID、事件名、关键数据。追踪 ID 与第 4 章协议层的请求 ID 一脉相承：客户端请求 → 网关 → 逻辑服 → 下游服务全程携带，一个请求在几十万行日志里就能被串成一条线——跨服务排障时这省下的是小时级的时间。

**日志级别使用规范**：

| 级别 | 用途 | 保留策略 |
|------|------|---------|
| DEBUG | 开发调试信息 | 仅测试环境 |
| INFO | 正常业务流程 | 30 天 |
| WARN | 潜在问题（重试、降级触发） | 90 天 |
| ERROR | 错误但可恢复 | 180 天 |
| FATAL | 严重错误（进程级故障） | 永久保留 |

**日志量估算**（10 万在线）：每玩家每分钟约 50 条、每条 500 字节，每日约 3.6TB。分层存储：热数据 7 天 SSD、温数据 30 天 HDD、冷数据 90 天以上进对象存储。日志量本身应该被监控——日志增速的异常跳变经常是异常行为（外挂扫描、bug 循环）的第一信号。

> **陷阱**：日志最常见的问题是"日志风暴"——某个异常循环大量打印日志，磁盘写满拖垮整个进程（日志写入阻塞业务线程）。防御手段：日志速率限制（单进程每秒上限、超限丢弃并计数）、ERROR 日志带去重（同一错误一分钟内只记一条 + 次数累加）、日志盘与数据盘分离。

### 3.4 告警治理

监控建起来之后，新的问题会出现：**告警太多，没人看了**。告警治理的原则：

- **每条告警必须可行动**——收到告警的人知道该做什么。做不到的告警（"CPU 突增又自己恢复了"）降级为看板曲线，不进通知
- **分级路由**：P0 走电话/值班强提醒，P1 走即时消息，P2/P3 进工单。所有告警一个音量，等于没有告警
- **抑制与聚合**：主机宕机时自动抑制它上面的几十条衍生告警（Alertmanager 的 inhibition 规则）；同类告警窗口内聚合为一条
- **值班制度**：on-call 轮值、交接文档、升级路径（15 分钟未响应自动升级到上级）。没有值班制度的告警系统只是历史记录仪

一个健康的指标：**每周 P0/P1 告警量稳定且每条都有处理记录**。告警量持续膨胀说明阈值失效或系统在退化，需要专项治理而不是加人盯屏。

## 4. 部署与发布管理

### 4.1 灰度发布策略

灰度发布通过逐步放量控制风险：

```text
阶段1：内部测试（员工+白名单）→ 验证基本功能
    ↓ 无问题
阶段2：小规模灰度（1 个区服 / 5% 流量）→ 种子用户验证
    ↓ 无问题
阶段3：扩大灰度（20-50% 区服）→ 观察一个晚高峰
    ↓ 无问题
阶段4：全量发布（100%）
```

每个阶段盯三组指标：错误率与延迟（技术面）、崩溃率与掉线率（客户端面）、关键业务指标（充值、登录）。任一异常先暂停放量——灰度的意义就在"随时可以停在中间状态"。

游戏版本的灰度有个 web 服务没有的约束：**客户端版本与服务端版本的兼容窗口**。老版本客户端在应用商店里的存续期长达数周，服务端必须同时兼容多个客户端版本（协议演进的兼容纪律见第 4 章）。所以游戏服务端的"灰度"经常是双轨的：服务端先发兼容版本（所有老客户端可用），客户端再按渠道灰度，最后服务端下线旧协议支持。

### 4.2 有状态服务发布的特殊性

游戏服务端发布和 web 服务最大的差异在这里：**不能随手重启**。

- **Web 服务**：无状态，滚动重启，流量切换，玩家无感知
- **游戏服务**：玩家会话在内存里，硬重启 = 全部掉线 + 内存态丢失

常见应对方式，按对玩家的影响从低到高：

1. **自然下线滚动**：发布脚本标记"停止新玩家进入"，等待在线玩家自然下线（挂机游戏可等，重度游戏等待时间不可控）
2. **公告 + 定点维护**：提前公告停服窗口，玩家预期内。大版本的标准做法
3. **快速踢出 + 快速恢复**：状态先落盘（快照），踢人、重启、恢复连接，全程 1-2 分钟。配合客户端断线重连，玩家感知为一次短暂卡顿。竞技对局中的玩家需要先等对局结束或转移对局
4. **进程内热更**（脚本/配置层，见 4.3）：不停服修复逻辑 bug，体验最好但能力边界受限

发布窗口的选择也是博弈：凌晨发布对玩家影响小，但运维值班最薄弱；晚高峰前发布赶得上晚间高峰但风险窗口正好撞上峰值。常见约定是"下午发布、晚高峰前完成验证"，把黄金时间留给观察而不是操作。

### 4.3 热更新与回滚

热更新能力分级：

| 类型 | 影响范围 | 停服要求 | 典型场景 |
|------|---------|---------|---------|
| 配置热更 | 无 | 不需要 | 数值调整、活动配置、开关切换 |
| 脚本热更 | 单进程 | 不需要 | 逻辑修复、平衡调整 |
| 协议热更 | 客户端+服务器 | 需要 | 协议变更、新功能 |
| 全量更新 | 全服 | 需要 | 大版本更新、引擎升级 |

配置热更的核心是**配置与逻辑分离**（第 10 章活动系统的实践），脚本热更的机制与边界见第 16 章。这里强调运维视角的一条：**配置变更是"发布"，要按发布管理**——灰度（先改一个区服观察）、可回滚（旧版本配置保留一键回切）、有变更记录（谁、何时、改了什么、为什么）。"策划直接改了线上数值没留痕"是数值事故里最难排查的一类。

回滚机制的原则：**回滚不是"可选的"，而是"需要的"**。发布前回滚方案就要准备好并演练过：二进制回滚（保留 N 个历史版本制品）、配置回滚（版本化存储）、数据库变更回滚（schema 变更要设计成向前兼容，新代码先兼容旧表结构，回滚时不需要回滚表结构——这条纪律能避免"代码好回滚、数据回不去"的死局）。

> **陷阱**：发布最常见的错误是"发布后不验证"——发布完成没人盯指标，玩家投诉了才发现问题。建议发布后立即跑一轮自动化冒烟测试（登录、进服、核心玩法请求、支付下单），并安排人盯关键指标 15 分钟以上。

## 5. 游戏开服实战

### 5.1 开服前准备清单

开服是游戏生命周期中最关键的时刻，需要周密的准备：

```text
□ 基础设施：服务器已部署、数据库已初始化、CDN 已配置、DNS 已生效
□ 客户端准备：已过渠道审核、资源包已上传 CDN、首日补丁已演练
□ 运营准备：活动配置已上传并核对、礼包已配置、公告与客服话术已准备
□ 监控准备：看板已配置、告警规则已设置、值班表已排定
□ 压力测试：单机压测已通过、集群压测已通过、容量推演已评审
□ 应急预案：回滚方案已验证、扩容预案已就绪、降级开关已测试
```

最后一项"降级开关已测试"值得展开：降级不是故障时临时找代码加 if，而是**提前埋好的开关**。开服前应把降级清单写成配置并实际演练：

| 可降级项 | 降级动作 | 玩家感知 |
|---------|---------|---------|
| 排行榜 | 切换为小时级刷新 | 数据延迟 |
| 好友在线状态 | 关闭实时推送，轮询替代 | 状态更新慢 |
| 世界聊天 | 频率限制/临时关闭 | 打字受限 |
| 跨服玩法 | 延期开启公告 | 功能延后 |
| 客户端资源校验 | 跳过校验直通 | 安全性临时降低 |

### 5.2 开服流量洪峰应对

开服瞬间的流量洪峰是最大的挑战——预约玩家集中在开放时刻涌入，峰值可能是稳态的 5-10 倍。核心策略是"限流 + 排队 + 降级 + 扩容"：

- **排队系统**：超过容量时让玩家在排队界面等待，而不是直接拒绝。"排队"比"失败"的体验好得多——玩家愿意等 5 分钟进服，但"连接失败"三次之后就卸载了。排队系统实现要点：排号令牌持久化（进程重启队列不丢）、进度条显示预计等待、防刷（同一设备重复排队去重）
- **限流**：登录接口令牌桶限流（第 4 章的 TokenBucket），超限返回"服务器繁忙请稍后"，而不是让请求堆积把服务打挂
- **降级**：按 5.1 的开关清单关闭非核心功能，把资源留给登录和核心玩法
- **扩容**：按 CPU/连接数自动扩容网关和无状态服务；游戏服按预案的"预备区服"逐个开启

> **陷阱**：排队系统自己被打挂是开服事故的黑色幽默——所有进不来的玩家都在刷排队状态接口，排队服务的压力反而最大。排队状态的查询要用缓存/静态化（每 5 秒更新一次全局进度），不能用玩家各自的实时查询。

### 5.3 开服后监控重点

开服后的前 24 小时是最关键的监控期，重点盯：

- 在线人数趋势（vs 预期曲线）
- 登录成功率（目标 > 99%）
- 排队人数与预计等待时间
- 新增注册数、充值金额（vs 预期）
- 错误日志数量与 Top 错误类型
- 服务器资源使用率与容量水位

> **陷阱**：开服最常见的错误是"准备不足就上线"——没压测、监控没配好、回滚没验证。建议至少提前一周完成所有准备，开服前一天做一次全流程演练（含扩容和回滚演练）。

## 6. 故障应急处理

### 6.1 故障分级与响应

| 级别 | 定义 | 影响范围 | 响应时间 | 处理时限 |
|------|------|---------|---------|---------|
| P0 | 服务器宕机/全服不可用 | 全服玩家 | 5 分钟 | 30 分钟 |
| P1 | 核心功能不可用 | 大范围玩家 | 15 分钟 | 2 小时 |
| P2 | 功能异常但可用 | 部分玩家 | 30 分钟 | 8 小时 |
| P3 | 体验问题 | 少量玩家 | 2 小时 | 24 小时 |

### 6.2 应急处理流程

```text
故障发现（监控告警/玩家反馈）
    ↓
故障确认（5 分钟内）── 确认级别、影响范围、拉起应急群、指定指挥
    ↓
止损优先（15 分钟内）── 快速恢复优先于根因定位：回滚、重启、切流、降级
    ↓
问题定位（恢复后）── 收集日志、分析根因、制定修复方案
    ↓
修复实施 ── 执行修复、验证效果、监控稳定
    ↓
事后复盘（48 小时内）── 编写报告、总结教训、制定改进措施并跟进行
```

流程里最重要的一条原则：**止损优先于定位**。线上事故的前 15 分钟，目标不是"搞明白为什么"，而是"让玩家先能玩"。回滚一个 10 分钟前刚发的版本，比读 40 分钟日志定位根因更划算——哪怕最后发现不是版本的锅，回滚的代价也远小于持续宕机。反过来，"先定位再动手"的执念是 P0 事故恶化的最大人为因素。

另一条常被忽略的：**应急期间保持信息同步**。指定一人只负责沟通（对外公告、对内播报进展），处理的人专注处理。"玩家在论坛已经吵翻、公司内部还在排查"的信息真空期，比故障本身更伤口碑。

### 6.3 常见故障速查

几个高频故障的典型特征与第一反应：

| 现象 | 常见根因 | 第一反应 |
|------|---------|---------|
| 在线人数断崖下跌 | 网关宕机/运营商故障/版本事故 | 分层确认：网关进程→机房网络→最近变更 |
| 全服卡顿但没宕机 | 慢查询/日志风暴/GC 恶化 | 先看数据库慢查询和磁盘 IO，再查最近变更 |
| 充值成功率下降 | 支付回调积压/渠道故障 | 先查回调队列积压，联系渠道确认 |
| 登录失败集中爆发 | 会话服务故障/数据库连接池耗尽 | 看连接池水位，重启会话服务 |
| 局部区服异常 | 单服数据问题/该服最近配置变更 | 对比正常服与异常服的变更差异 |

### 6.4 故障复盘的价值

故障复盘不是"追责"，而是"学习"。复盘的三个标准问题：根本原因是什么？为什么没有提前发现？如何防止再次发生？

改进措施要有**归属和期限**（"XX 在 X 月 X 日前给数据库加上慢查询告警"），否则复盘纪要就是另一个没人看的历史文档。跨故障看趋势：同类故障出现两次以上，说明上一次的改进措施没有落地——这是流程问题，不是技术问题。

> **陷阱**：故障处理最常见的错误是"急于修复，忽视根因"——服务器挂了就重启，数据库慢了就加索引。止血操作是必要的，但不定位根因，同样的问题会反复发生。正确姿势是：先止血（恢复服务），再定位（找到根因），后修复（根治问题），全程记录。

## 7. 运维自动化

### 7.1 自动化体系

自动化让运维从"人肉消防员"变成"流程保障者"。核心组件：

- **配置管理**（Ansible 等）：服务器配置统一管理、批量变更
- **持续集成**（CI）：代码自动构建、测试、制品化
- **容器编排**（Kubernetes）：无状态服务自动扩缩容、故障转移
- **日志与监控**（第 3 节体系）：自动告警与看板
- **运维工单/审批**：高危操作（合服、删数据、改配置）走审批流留痕

需要说明游戏运维的边界：Kubernetes 对无状态组件（网关、匹配、HTTP 服务）收益显著；但**玩家所在的游戏服/房间服是有状态进程**，直接套 K8s 的"随时重启漂移"模型会出事故。有状态服务的编排需要自定义的迁移流程（状态落盘→通知→切换→恢复），很多团队的做法是"K8s 管无状态层 + 专有的房间调度器管游戏服"，不要为了统一技术栈把有状态服务硬塞进标准模型。

### 7.2 自动化部署流程

自动化部署的核心是**可重复、可回滚**：

1. 代码合并到 release 分支
2. 触发 CI 流水线：构建 + 自动化测试 + 制品归档
3. 灰度发布（4.1 节的阶段化放量）
4. 自动化冒烟验证 + 指标观察
5. 全量发布或自动回滚

每一步有明确的成功标准和回滚条件——"冒烟测试不过自动停止""错误率超阈值自动回滚"这类守门规则，比任何人工把关都可靠。

> **陷阱**：自动化最常见的错误是"自动化了错误的流程"——手动部署本身就有问题，自动化只会让问题更快扩散。建议先手动跑通并稳定执行一段时间，把流程中的坑填完，再自动化固化。

## 8. 设计决策指南

**何时选择云服务 vs 自建机房**

- **云服务**：中小团队、快速迭代、流量波动大、多地区运营
- **自建机房**：流量稳定的大 DAU 产品、长期成本敏感、有专职运维团队

**何时需要完整的监控体系**

- 在线玩家超过 1 万
- 有付费系统上线
- 多服务器/多区服部署
- 有 SLA 承诺或渠道考核

**何时引入值班制度（on-call）**

- 产品进入公测/上线阶段，需要非工作时段响应
- P0 故障的分钟级响应有明确业务要求
- 自动化告警已经建立，需要人来消费告警

**发布方式的选择**

- 配置/脚本可热更的改动：热更发布，零感知
- 服务端二进制改动：自然下线滚动或定点维护（4.2 节）
- 客户端改动：渠道分批灰度，服务端保持兼容窗口

## 9. 常见陷阱总结

| 陷阱 | 表现 | 根本原因 | 解决方案 |
|------|------|---------|---------|
| 成本低估 | 预算超支 | 只算硬件，漏带宽和全局组件 | 完整成本模型 + 带宽逐层优化估算 |
| 压测失真 | 上线后扛不住 | 环境差异、机器人不真实、空库 | 同规格环境 + 真实行为分布 + 灌数据 |
| 容量拍脑袋 | 开服洪峰打挂 | 没有单机数据到机器数的推演链 | 2.2 节推演链 + 余量评审 |
| 监控盲区 | 故障发现晚 | 只监控基础设施不监控业务 | 三层监控 + 在线人数/登录率/充值率告警 |
| 告警疲劳 | 告警没人看 | 不可行动的告警太多 | 分级路由 + 抑制聚合 + 定期治理 |
| 发布事故 | 上线后崩溃 | 无灰度、无回滚、发布后不验证 | 阶段化灰度 + 预案化回滚 + 冒烟验证 |
| 随手重启 | 全服掉线状态丢失 | 把无状态运维习惯带进有状态服务 | 4.2 节的有状态发布流程 |
| 排队系统崩溃 | 开服排队接口被打挂 | 排队状态被高频实时查询 | 状态静态化/缓存化 |
| 故障反复 | 同样问题反复出现 | 只止血不复盘，或复盘无落地 | 根因定位 + 改进措施带归属和期限 |

## 本章小结

| 问题 | 简答 |
|------|------|
| 容量规划的核心方法？ | 推演链：单机压测 → 组件上限 → 按峰值反推机器数；余量给故障、弹性给增长 |
| 游戏服务发布和 web 最大的区别？ | 有状态——不能随手重启，需要自然下线/定点维护/快照快速重启等专门流程 |
| 哪条业务告警最值得配？ | 在线人数突降——它是宕机、网络、版本事故的最早综合信号 |
| 日志体系的两个关键设计？ | 追踪 ID 全链路贯穿 + 速率限制防日志风暴 |
| P0 故障前 15 分钟的目标？ | 止损不是定位——回滚、重启、切流、降级，让玩家先能玩 |
| 数据库 schema 变更的回滚纪律？ | 向前兼容：新代码兼容旧表结构，代码可回滚、表结构不回滚 |
| 开服洪峰四件套？ | 限流 + 排队 + 降级 + 扩容，排队状态必须静态化防打挂 |
| 自动化的前置条件？ | 先手动跑通并稳定，再自动化固化——不要自动化一个坏流程 |
