# Project Analysis and Retrospective Index

This knowledge base is positioned to explain judgment, cost, and pitfalls, so it is naturally suited as an analysis tool rather than a feature checklist. The three most common uses are project reviews, older-project inventories, and incident retrospectives. All three share the same set of actions: translate the player's path into state and chains, then check for capability gaps against each chapter.

## The Basic Actions of Project Analysis

- First draw the player's core behavior path: from login to one complete gameplay loop, marking which systems each step passes through.
- Along that path, list the state involved, distinguishing runtime state, long-term assets, and derived data.
- Partition the main chain from peripheral chains, marking each segment's latency, consistency, and recovery requirements.
- For each segment, ask the cost of failure: what does an error affect, how long does recovery take, and can it be audited and compensated?
- Compare these questions against the main-line chapters to find which layer has no corresponding capability to take it up.

The output of these actions is not an architecture diagram but a state list annotated with failure costs. For most projects, once the first list is done, the main problem usually surfaces on its own.

## Which Chapters Each Action Maps To

- Drawing the player path: mainly compare against the problem model to confirm where the main behavior and main cost land.
- Listing the state list: compare against the runtime-state, long-term-asset, and derived-data classification in data modeling.
- Partitioning chains: compare against the method of partitioning main chains and peripheral chains.
- Asking failure cost: compare against the judgments about recovery and rollback in observability and version release.
- Finding capability gaps: compare against the applicability conditions in the chapters on service splitting, cache and middleware, and shared services.

## Several Judgment Questions to Bring Into the Analysis

- Who is authoritative for this state, and whose word wins in a dispute?
- If this chain goes down, what do players see and what do operators see?
- How is this change rolled back, and how long does it take to take effect?
- How long does this failure take to recover from, and can it be automated?
- Where do the current evidences for this class of problem live?

Most of these questions can be unfolded in their corresponding chapters. Citing them during analysis aligns the team more easily than inventing criteria on the spot.

## How to Use This at the Project-Review Stage

The most valuable step at the project-review stage is forcing out the problem model: where does this product's main chain land, which state directly harms business outcomes once wrong, and which constraints come from platforms and channels. Common related content at project review includes the general introduction, the problem model, and two or three articles directly relevant to the project's constraints.

## How to Use This for an Older-Project Inventory

The point of an older-project inventory is not to find "where it is not advanced" but to find structural gaps: is authoritative state clear, do config changes have validation and gray release, does a control plane exist, does observability cover the main chain, do operational actions have audit and rollback. Each of these checks has a corresponding chapter on the main line; going through them item by item often lands on concrete actions more readily than a generic architecture review.

## How to Use This in an Incident Retrospective

Retrospective is the reverse use: start from symptoms and ask layer by layer which layer should have intercepted this phenomenon. Is the time model not unified, are state boundaries confused, is observation lacking evidence, or is the process lacking approval? A retrospective conclusion that lands on "which layer's which capability to add" is far more useful than "be more careful next time," and easier to put on a schedule.

## Common Orders of Analysis Entry

Both entry orders are common. Entering from the most painful incident gives strong motivation and fast results, but easily fixes only the pain points; pushing forward from the main chain gives full coverage and good structure, but easily stalls on paper. The common practice is to combine them: push forward to get the main chain and state list first, then use the recent months of incidents to calibrate priorities, so the list has both structure and a sense of pain.

## What Analysis Results Should Look Like

- One page of main-chain description: the player path, the state list, and the failure cost of each segment.
- One gap list: each item noting which chapter's problem domain it belongs to and what currently holds the line.
- One set of judgments to be verified: which conclusions are only conjecture and what data is needed to confirm them.

Only in this form can analysis results be scheduled and tracked rather than staying in meeting minutes.

## Division of Labor When the Team Uses It Together

Analysis is best done together by two or three people from different tracks: someone familiar with the gameplay path, someone familiar with server-side state, someone familiar with production operation. The knowledge base provides shared language so that disagreements like "which segment is the lag you're talking about" and "who decides for this state" can be made concrete instead of each person throwing around adjectives.

## How Analysis Conclusions Stay Valid

Project analysis is not one-shot. Major version changes, new gameplay, entering the operations phase, and changes in platform rules all shift where the main chain and failure costs land. Treating analysis results as documentation maintained alongside versions, rather than a one-time deliverable, is what gives them long-term value; the moment they are archived is usually the moment they start going stale.

## Common Pitfalls

- Turning project analysis into a per-chapter scorecard, producing "which chapter wasn't done well" instead of a problem list.
- Inventorying only the tech stack and not state and chains, so conclusions land on no architectural action.
- Retrospective that chases only the direct cause without checking the missing capability layer, so the same class of incident returns in a new skin.
- Analyzing once and archiving, without updating with versions and operations stages, so the list goes stale quickly.
