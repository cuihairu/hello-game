# Content Structure and Problem Index

The main line of this knowledge base is organized by judgment dependencies, not spread out by discipline: later chapters rely on the vocabulary and prerequisites defined earlier. The dependency relationships between topics are preserved here so that relevant records can be located when working on project questions, reviews, and retrospectives.

## Dependency Relationships Between Topics

The general introduction and problem model sit at the front, data/version/operations in the middle, and practice/retrospective at the end; this reflects the dependencies between chapters. The cost judgments given by the problem model are the discussion premises for the network, sync, and execution model chapters; conversely, if you read about service splitting first and the problem model later, you will likely retain only the form of the split while missing the motivation for it. These dependencies also explain why adjacent topics share prerequisites; when reading a single topic in isolation, you can follow the links back to the relevant background.

## Main-Line Topic Index

- General Introduction: establishes the analysis order of "first look at what players repeatedly do, then look at how state is shared"; the book's problem-translation rules start here.
- Problem Model: translates gameplay types into the cost landing points of the main chain; every conclusion in the chapters that follow carries this premise.
- Network Access: breaks apart the chains of login, in-session interaction, push, and download, establishing judgments about access-layer responsibilities and protocol stability.
- Sync and Combat: discusses the time model, authority ownership, prediction and correction; the technical backbone of real-time gameplay.
- Execution Model: answers what unit logic advances in, how state is organized, and how peaks are absorbed.
- Service Splitting and Control Plane: handles state boundaries, failure domains, and node governance; the judgment chain for entering the distributed phase.
- Messages and IPC: draws the lines between synchronous calls, asynchronous events, and queues, preserving the explainability of the main chain.
- Client Architecture: treats the client as a long-running system, filling in the engineering surfaces of resources, scripts, and platform access.
- Scripts and Hot Update: discusses the trade-offs among iteration speed, fix windows, and the radius of incidents.
- Version Release: treats multi-platform coexistence, gray release, and compatibility windows as governance capabilities, not just an operational workflow.
- Data Modeling: distinguishes runtime state, long-term assets, and derived data, deciding whether the system can evolve long-term.
- Cache and Middleware: explains how infrastructure turns from a helper into a hidden risk.
- Shared Services: the construction order and costs of public capabilities such as accounts, payments, mail, and leaderboards.
- Operations and Monetization: turns operational actions into system chains that are controllable, auditable, and reviewable.
- Observability and Stability: builds an evidence chain around the main chain so that troubleshooting no longer relies on guessing.
- Security and Risk Control: discusses attack/defense, business governance, and compliance separately.
- Platforms and SDKs: explains how platform rules shape the technical form in reverse.
- Practice and Retrospective: condenses the earlier judgments into a method of selection and a mechanism of correction.

## Two Threading Lines

Though there are many chapters, two lines actually thread through them. One is the state line: how state is shared, who holds authority, how it is stored and recovered; it strings together the problem model, sync and combat, service splitting, and data modeling. The other is the chain line: how traffic comes in, how it is routed, how it is observed; it strings together network access, messages and IPC, cache and middleware, and observability. Locating the state line or chain line helps judge whether a given conclusion applies to the current project.

## Cross-Topic Problem Combinations

A single article usually covers only part of a complete feature. Several cross-topic problems and their related records are listed below:

- Building reconnection: session recovery in network access, frame catch-up in sync and combat, and reconnection behavior in client architecture — all three must be read together.
- Building an event system: operations and monetization, version release, plus the config pipeline appendix; the focus is gray release, approval, and rollback.
- Building cross-server gameplay: service splitting and control plane, messages and IPC, data modeling; the focus is state ownership and consistency cost.
- Building anti-cheat: authority ownership in sync and combat, security and risk control; first distinguish pre-arbitration from post-hoc audit.

These problems involve cross-article dependencies; before implementing, compare against the relevant records to verify state ownership, recovery semantics, and consistency cost.

## Numbered Topics and Topic Entry Points

There are dependencies between numbered topics, but reading them strictly in order is not required. The general introduction, problem model, and execution model form a commonly used judgment chain; other topics can be consulted crosswise according to the project stage and role focus.

## Role and Topic Index

- Server-side track: complete the general introduction, problem model, network access, sync and combat, and execution model first, then read service splitting and messages and IPC.
- Client track: start with client architecture, then go back and fill in prediction and correction in sync and combat, and finally read scripts and hot update and version release.
- Operations and monetization engineering: operations and monetization, data modeling, plus the config pipeline appendix; focus on measurement criteria, approval, and rollback.
- Infrastructure and stability track: execution model, service splitting, messages and IPC, cache and middleware, observability; finally fill in the capacity scaling appendix.
- Producer and lead designer: general introduction, problem model, operations and monetization, practice and retrospective — used to build a shared language with the technical team.

## Cross-Comparison and Topic Appendices

The game-type topics and problem-domain index provide cross-comparison, commonly used for project selection, design reviews, and retrospective location; they complement the main-line topics.

## Prerequisite Dependencies and Backlinks

If a design appears to fit the project but you cannot explain its premises for holding, you usually need to go back to the game types and problem model; if the argument centers on state ownership or recovery semantics, you can follow the relevant links back to sync and the execution model.

## Topics Related to Incident Investigation

For incident investigation, start from the topic corresponding to the symptom, then go back to game types and the problem model to judge which layer of capability is missing. Fixing only the current symptom may let a similar problem reappear through another chain.

## Judgment Questions Covered by the Main Line

The main line centers on several kinds of project judgments: where the main chain lands, which state errors directly affect business outcomes, and which failures cannot be recovered. The corresponding content is distributed across the problem model, sync, data modeling, and stability articles.

## Boundaries Easy to Overlook When Using the Content

- Treating the numbered order as a mandatory process and ignoring the current problem and premises of the project.
- Skipping the problem model and applying technical conclusions directly, ignoring the constraints introduced by gameplay type.
- Confusing main-line reasoning with appendix checklists, overlooking the difference in responsibility between the two.
- Checking only records within one's own role and missing the interfaces and collaboration conditions that cross boundaries.

The connections between these topics are essentially the prerequisite management of project judgment.
