# 13. 通用游戏服务

游戏项目早期最容易把精力都压在战斗、玩法和主链路上，等到版本进入上线准备或进入长线运营，团队才发现真正把项目拖慢的往往不是核心玩法代码，而是那些看起来“不够性感”的公共能力：账号、角色、活动、排行、匹配、社交、支付、风控、客服和 GM。

这些能力有几个共同特点。第一，它们跨系统、跨团队、跨生命周期，几乎不会只服务一个玩法。第二，它们和资产安全、用户关系、运营效率直接相关，一旦出错，影响通常比某个局内技能 bug 更大。第三，它们很容易被“先做一个能跑的版本”拖成历史包袱，最后每个项目都维护一套近似但不兼容的实现。

因此，这一章真正讨论的不是“要不要做这些功能”，而是三个更难的问题：

- 哪些能力应该平台化，哪些能力必须保留项目定制
- 哪些操作必须可审计、可回放、可追责
- 业务效率、运营灵活性和资产安全之间应该怎么取舍

阅读这一章时，建议始终带着下面几个判断框架：

- 先分清楚账号、角色、订单、社交关系、处罚记录分别是谁的权威状态
- 再看这些状态的读写路径里，哪些属于主链路，哪些属于外围治理链路
- 最后再决定复用方式，是统一服务、统一 SDK、统一控制台，还是只统一协议和数据口径
