# Accounts, Characters and Base Systems

## Category

system / general services subtree. Node position: accounts and characters are separated first — base systems are not "just make a form", implementation approaches and their costs compared, and a few of the most easily overlooked design points.

## Definition


Account systems and character systems are often mistaken for "the base that gets thrown together casually during project initialization", but they actually determine whether many later designs can converge. Login, real-name verification, guest conversion, character creation, server affiliation, bans, rebinding, recovery, server-merge migration: once the boundaries of these flows are unclear, every system added afterwards keeps stacking more debt.

## Problem

Most account and character system incidents come from designing the two mixed together first: the account is the identity and security boundary, the character is the gameplay data carrier, and once they are mixed, merging, recovery and bans all become hard. The real complexity of base systems is not in the forms but in the boundaries — registration channels, binding and unbinding, recovery and bans, these paths are the actual source of incidents.


### Why the problem happens

Accounts and characters naturally cross multiple boundaries:

- For platforms and channels, the account is first an identity entry point, solving login, authorization, real-name and payment entity
- For game business, the character is the object that actually carries assets, progress, social relationships and behavior records
- For operations and support, accounts, characters, servers, devices, orders and punishment records need to be linkable

The trouble is that these three viewpoints are related but cannot be merged into one object. Many incidents come from "merging them first to save effort". For example, using the channel uid directly as the internal primary key saves a mapping table in the short term, but as soon as you add a second channel, support guest conversion, do cross-device interoperability or account recovery, the whole identity system is forced to be redone.

### Separate accounts from characters first

A long-running online project usually needs at least the following layers of objects made explicit:

- Login identity: who completed authentication on an external platform, usually corresponding to a channel account, phone number, email or self-built account
- Game account: the unified identity inside the project, used to bind multiple login methods and carry real-name status, payment entity, ban status and similar information
- Character: the game entity in a given server or world, carrying inventory, quests, growth, social and combat state
- Human-service object: the aggregated view that support and risk control see in the backend, able to string together multiple characters, multiple orders and multiple punishments

These layers do not all have to be split into independent services, but their semantics must be separated first. Otherwise you will immediately hit problems in very concrete scenarios:

- After a player switches servers, do assets follow the account or the character
- Can the same account create multiple characters, and is the limit global or at the server level
- Does the character id change after a server merge, and how are historical logs traced back
- Is a ban on the character, the account, the device, or on payment capability

### Why base systems are not "just make a form"

So-called base systems usually include nickname, avatar, currency display, mail, announcements, check-in, inventory entry, settings, terms confirmation and other seemingly ordinary modules. The difficulty is not in the pages, but that these modules all sit at the intersection of assets, audit and user reach.

Take the mail system as an example; it often carries several different responsibilities at once:

- As a reward delivery entry point, re-issuing event rewards, compensating items, support re-fulfillment
- As an operations reach tool, sending announcements, recall notifications, version hints
- As an audit-assist path, leaving a trace for every fulfillment and compensation

If mail is treated as nothing but a client UI feature, you will quickly run into these problems:

- Rewards claimed twice, or unclaimable after timeout cleanup
- Bulk sends without an idempotent key, so rerunning a script fulfills twice
- Unable to distinguish "issued automatically by the system" from "issued from the operations console" from "re-issued manually by support"

### Common implementation approaches and costs

### Monolithic implementation inside the project

The most common approach in small teams is to put login, characters, mail and announcements all together inside the game server or gateway. The benefit is fast development, simple calls, and problems are easy to locate in one codebase. The cost is that every later project copies it once more, and identity rules, audit caliber and backend interfaces are hard to unify.

This approach suits:

- Products with small scale and short lifecycle
- Single-channel or few-channel access
- No need for complex account recovery, cross-device interoperability or large-scale support operations

It does not suit:

- Multiple projects in the same company sharing an account system
- Needing unified real-name, anti-addiction, bans and payment risk control
- A clear expectation of platformized operations later on

### Platform account center plus project character service

A more common mid-size approach is to build login identity, account binding, real-name, anti-addiction and unified bans as platform-layer capabilities, while character and server data stay the responsibility of project services. This both unifies governance and preserves the project's control over the character model.

The cost is that interface design becomes harder:

- A successful login does not mean the character can enter the game; in between there are still checks such as server selection, character list and gray-release eligibility
- Platform account state changes must be pushed to the project in time, for example real-name status refresh, punishment escalation, recovery appeal handling
- The support backend needs to see through both platform and project data, otherwise tickets cannot be closed

### Full platformization of accounts and characters

The heavier approach makes even the base character services a unified platform, such as a unified character primary key, unified mail, unified announcements, unified character bans and migration interfaces. The benefit is extremely strong consistency across the operations console and audit caliber, and low cost of sharing across projects. The drawback is that project customization gets compressed, and character model evolution is held back by the platform version.

This kind of approach only pays off when all of the following hold at the same time:

- Product types within the company are relatively concentrated
- There is a clear platform team and governance mechanism in the organization
- Business teams are willing to accept unified standards and integration cost

### The design points most easily overlooked

### Primary key strategy

Do not let external channel identifiers pollute the internal primary key. Internally there must at least be your own stable account id and character id, otherwise once the channel changes, compliance rules change, or cross-platform interoperability is needed, data migration will be extremely painful.

### Server and world model

"Server" is not a simple display field, but a composite object of permissions, routing, capacity, social boundaries and event boundaries. Decide early:

- Whether the same server equals the same world
- In cross-server gameplay, which side asset ownership and leaderboard ownership count as
- After a server merge, how historical battle records, mail and guild relationships are mapped

### Safety boundary for manual operations

Support re-fulfillment, character renaming, banning and unbanning, asset rollback: these operations must have strict permissions, ticket numbers, approval chains and audit logs. Many teams only do "the console can edit it" before launch, and only when something real goes wrong do they discover there is no replay, no reason field, and no before/after snapshots.

### Common mistakes

- Using one id for account, character, device and channel user, making later extension impossible
- Designing only the successful login flow, not recovery, rebinding, bans, appeals and migration flows
- Client base features and backend governance capabilities completely disconnected, so operations and support can only firefight with database scripts
- Making the character service a shared database that "every system can write to directly", so there is no real authoritative boundary in the end

A truly mature account and character system is not how pretty the login page is, but that when you connect a new channel, do cross-device interoperability, handle an asset dispute, or enforce a compliance policy, the system still knows who is who, where things are, who changed what, and why it was changed.
