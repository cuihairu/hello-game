# Config-Driven vs Script-Driven

## Category

system / scripting and hot-update subtree. Node positioning: the boundary between config-driven and script-driven — config drifting into something that behaves like script, and script turning into a universal patch, are two common boundary breaches; the boundary judgment has to come first, and the config system itself also has to be engineered.

## Definition


When a project needs more flexibility, many teams reach for two levers at the same time: put more behavior into config, or put more logic into script. Both can raise iteration speed, but they do not solve the same kind of problem. Config is better at expressing rule parameters and static combinations; script is better at expressing flow, branching and runtime behavior. Blending the two into one usually produces an intermediate state that is hard both to maintain and to validate.

So what really needs answering here is not "which of config and script is more advanced," but "what change is suited to be turned into data, and what change must stay as executable logic."

## Problem

Config drifts into something that behaves more and more like script because business complexity has leaked down from the scripting layer; script becomes a "universal config patch" because no admission judgment was established. Both breaches let change cost run away — the boundary must be an explicit judgment, not a habit.


### Where Config-Driven Design Actually Earns Its Value

What is most valuable about config-driven design is extracting change out of the code release chain, so rule parameters, content combinations and some static structures can be adjusted faster. It is especially well suited to:

- Numerical values and rule parameters
- Drops, quests and campaign conditions
- UI layout or page composition relationships
- Text, localization and resource mapping
- Static branches under a finite state

The advantage of config is not only that it "changes fast" — it is also much easier to review, validate, diff and roll back.

### What Script-Driven Is Better Suited to Solve

Script is better suited to problems that already go beyond "expressing parameters," for example:

- Complex flow orchestration
- Dynamic conditional branching
- Behavior that requires runtime state judgment
- Logic that changes at high frequency but is not worth a full release

In other words, script is suited to expressing "how to do it," while config is better suited to expressing "what inputs and constraints exist."

### Why Many Projects Let Config Grow Until It Resembles Script

This is a very common path to loss of control. Early in a project, config carries only parameters; later, to avoid editing code, teams keep adding more and more into config:

- Conditional expressions
- Nested rules
- Event callback names
- Execution-order descriptions
- Small DSLs

In the end, config still looks like data on the surface, but in reality it has become a scripting language with no debugger and no type system. Systems like these look flexible up front and are the most likely to cause online incidents later.

### Conversely, Script Should Not Become a "Universal Config Patch" Either

If every data problem, presentation problem and flow problem is eventually fixed ad hoc in script, the common result is:

- The scripting layer looks more and more like a dumping ground for business garbage
- The responsibilities of config and script get blurrier and blurrier
- The same rule ends up half in config and half in script
- Triage makes it hard to tell which layer is actually at fault

So what really matters is not "who can do it" but "who should do it by default."

### A Steadier Boundary Judgment

You can start by asking a few of the following questions:

- Is this change a parameter change, or a behavior change
- Can the error be caught early through static validation
- Does it require complex runtime context
- Does it require debugging, breakpoints and execution tracing

If the answers lean toward parameters and static combination, config is the better fit; if they lean toward flow, conditions and runtime judgment, script is the better fit.

### Why the Config System Itself Must Also Be Engineered

Many teams think too lightly about the config system, assuming that being able to edit tables and export files is enough. In real projects the config system is often a high-frequency entry point for incidents, because it connects designers, client, server and the release chain. A mature config system typically needs:

- Type validation
- Reference validation
- Diff review
- Gray release
- History tracking and rollback

In other words, config-driven is not "hand the development work over to spreadsheets," but bring rule change under formal engineering governance.

### Common Pitfalls

The most common error is expanding the config system indefinitely into a hidden scripting language. The second error is pushing all high-change logic onto the scripting layer, letting config degrade into a loose data dump. The third error is looking only at the editing experience and failing to add type validation, auditing and rollback capability, so both config and script become high-risk entry points.
