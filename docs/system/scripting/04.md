# The Hot-Update System

## Category

system / scripting and hot-update subtree. Node positioning: the hot-update system — what problem it solves, the capability checklist beyond a single download chain, compatibility being the most dangerous problem, the priority of rollback and gray release, and the relationship to testing.

## Definition


The most appealing thing about hot updates is that they appear to be able to compress the time from "problem found" to "fix in effect." For long-running live-ops projects this capability is genuinely very important, because many problems simply cannot wait for a full release and platform review. But this is also where hot updates are truly dangerous: what they shorten is the fix window, not the testing responsibility, and certainly not the design responsibility.

Without version compatibility, signature verification, gray release and fast rollback, hot updates do not make the system safer — they only get errors to more players faster.

## Problem

Hot updates are most easily treated as "download succeeded, job done," when in fact the most dangerous part is compatibility: all-green verification still cannot stop a gray bucket from collapsing. Rollback capability must be top priority, and gray release is not a nice-to-have optimization but an incident isolation mechanism — a hot update without rollback is a car without brakes.


### What Problem Hot Updates Actually Solve

What hot updates are best suited to solving is these real pressures:

- Platform release cycles are long
- Operations campaigns switch over frequently
- Online problems need fast containment of damage
- Some script, config and asset changes are not worth a full-package release

Their essence is not "make everything mutable," but to give the system a controlled fix chain that is faster than a full-package release.

### A Hot-Update System Is Usually More Than One Download Chain

A mature hot-update system typically includes at least these layers of capability:

- Patch content organization
- Version and dependency management
- Download, verification and signature validation
- Gray release and phased ramp-up
- Rollback and invalidation strategy
- Compatibility judgment against the host version

If these capabilities are not built together, so-called hot updates are usually just "remote file replacement," not a genuinely operable system.

### The Most Dangerous Problem Is Compatibility, Not Download Failure

When building hot updates, many teams first fix their eyes on patch size and download success rate, but what actually tends to cause major incidents is compatibility:

- A new script depends on an interface the old host does not have
- Fields a new config requires are unrecognized by old code
- A new asset references a dependency that was never delivered
- Patches have ordering dependencies between them that are not correctly expressed

These problems are dangerous because the patch may have downloaded and verified successfully, and only start crashing at runtime.

### Why Rollback Capability Must Be Top Priority

A hot update without rollback is essentially treating production as a test field. A genuinely usable hot-update system must be able to answer:

- If a patch goes wrong, can it be disabled quickly
- Can the client fall back to the previous stable version
- How are state and caches handled after a rollback
- Does the server know the patch level each client is currently at

If these are not designed up front, when an incident happens the team can often only ship a second patch to fix the first one, and risk keeps stacking.

### Gray Release Is Not a Nice-to-Have Optimization, It Is an Incident Isolation Mechanism

The reason hot updates need gray release is not that "it is more professional," but that any patch may have real-world compatibility differences. Device models, network conditions, historical versions and cache state all affect the outcome. The value of gray release lies in:

- Shrinking the blast radius first
- Observing error rates and compatibility first
- Verifying first whether the patch chain is actually recoverable

Without gray release, the incident radius of a hot update is usually far larger than that of a full-package release.

### What Is the Relationship Between Hot Updates and Testing

Hot updates can shorten the fix path, but they can never replace testing. More precisely, hot updates make you need layered testing even more:

- Testing the patch content itself
- Compatibility testing against the current host version
- Regression testing against the historical patch chain
- Testing the rollback path and the invalidation path

If a team treats hot updates as "fix it in production, that is the test," they will end up as a source of ever more combinations of online state.

### A Steadier, Systematic Approach

A steadier hot-update system usually manages to:

- Keep patch content with clear boundaries, knowing what can be hot-updated and what must be a full package
- Maintain an explicit compatibility matrix between patches and host versions
- Build signature, gray release, observability and rollback into the release chain itself
- Let the server know the patch version and capability level each client is at

What truly matters about this system is not making changes faster, but keeping fast changes still inside a controllable range.

### Common Pitfalls

The most common error is treating hot updates as a testing substitute, assuming problems can be fixed live in production. The second error is building only download and replacement capability, without building compatibility, gray release and rollback. The third error is not defining the hot-update boundary first, so script, config, assets and host interfaces all drift across versions together, and the patch chain itself ends up as the source of incidents.

### Practical Case: A "Verification All Green, Gray Bucket Crashed Fourfold" Hot-Update Compatibility Investigation

> The case is an illustrative example (not drawn from a real project), with figures rounded for simplicity. It pushes this page's "a hot-update system is usually more than one download chain," "the most dangerous problem is compatibility, not download failure," "why rollback capability must be top priority," "gray release is not a nice-to-have optimization, it is an incident isolation mechanism," and "common pitfalls" into deep water: the last acceptance gate of a hot update is not download verification but the compatibility matrix and patch levels — this is a complete investigation of a compatibility gap being stopped by the gray bucket.

**Background and symptoms**: a long-running live-ops project, with host major versions **2.4**～**2.7** in circulation at the same time (the oldest supported being **2.4**). To fix a reward-granting error in a campaign settlement script, a script hot-update patch was released. Download, verification and signature were all green; gray release bucketed by device at **5%**; **40** minutes later the gray bucket alarmed: crash rate **0.3**% → **1.2**% (**4x**), while the remaining **95%** of users had not yet been exposed.

### Step One: Symptoms and Metrics — Bucket the "Fourfold Crash" by Host

Unify the metrics: take the crash rate as the crash platform's session crash share metric, and compare in buckets by host major version. Record one entry before and after the patch:

- **Before the patch**: full-population baseline **0.3**%
- **Gray bucket**: **1.2**%, an increment of **0.9** percentage points (**4x**)

The increment is not distributed uniformly: **100%** of the crash stacks fall on the new script's call stack, and the host distribution is concentrated on **2.4**/**2.5** — bucket first, then do the compatibility accounting.

### Step Two: Layered Attribution — The Patch-Chain Ledger From Download Verification to Runtime

```text
传输账   补丁下载成功率 99.8%、签名校验 100% 通过——传输层无责
版本账   灰度桶宿主分布：2.6+ 占 60%（崩溃率 0.2%），2.4/2.5 占 40%（崩溃率 2.7%）
合成账   60%×0.2% + 40%×2.7% = 1.20%——与桶内实测 1.2% 对上，崩溃集中在老宿主
接口账   崩溃栈顶是活动配置门面接口——它在宿主 2.6 才暴露，2.4/2.5 一调用就抛
止损账   告警到停用下发通道 22 分钟；原计划 T+2 小时全量，灰度桶拦下 95% 暴露面
```

The ledgers close: the transport chain is all green (download **99.8%**, signature **100%**), and every crash comes from a runtime compatibility gap — the façade interface the new script calls exists only on host **2.6**+, so the **40%** of the bucket running **2.4**/**2.5** throws the moment they enter the campaign. This page's line "a patch may download and verify successfully, but only starts crashing at runtime" comes true verbatim.

### Step Three: Root Cause — The Compatibility Matrix Was Missing the Row "Minimum Host Version for the Script API"

Checked against the six layers of capability from this page's "a hot-update system is usually more than one download chain": content organization, download/verification/signature, and gray ramp-up were all in place. What was missing was that the "compatibility judgment against the host version" was never carried down to interface granularity — the compatibility matrix only recorded "patch ↔ host major version: installable or not," not "the minimum host version for each façade interface the script calls," so an old host like **2.4** slipped into the gray bucket. Against the four rollback questions it looks even worse: "does the server know the patch level each client is currently at" could not be answered at the time — the server knew only "installed or not," not "installed to which level," so disabling the channel could only block new loads, and already-loaded clients had to fall back through a local last-resort path via restart. This page's line "without gray release, the incident radius of a hot update is usually far larger than that of a full-package release" holds in reverse: what stopped this incident was precisely the **5%** bucket; and the third common pitfall, "script, config, assets and host interfaces all drift across versions together, and the patch chain itself becomes the source of incidents," is exactly the shape that nearly came true here.

### Step Four: Response and Backfill — Closing the Channel Stops the Bleeding; Rolling Back to the Patch Level Is the Recovery

The fix came in two stages. Three emergency steps: disable the patch delivery channel (**22** minutes after the alarm); guide already-loaded clients to restart and fall back to the previous stable patch level — campaign caches are versioned by patch level, so the fall back leaves no dirty state; cut a compatibility-only patch for **2.4**/**2.5** (interface-existence guards plus a degraded path) and replay it through the same bucketed gray release. Verification: **30** minutes after disabling, the crash rate returned to the **0.3%** baseline; the compatibility patch replayed flat within the same bucket, then ramped up. Three institutional steps: write the minimum host version for each script API into the compatibility matrix and have the release pipeline enforce it (no registration, no release); make rollback drills granular down to patch level, with the server recording the level each client is at; add "compatibility testing against the current host version" to the layered test checklist, with smoke runs mandatory on the two oldest major versions in the matrix.

**Backfill Checklist**:

| Landing point | Action | Backfill target |
|-----|------|--------|
| Compatibility gate | Minimum host version for each script API goes into the compatibility matrix; the pipeline blocks releases according to the matrix | The most dangerous problem is compatibility, not download failure |
| Level rollback | Rollback drills go down to patch-level granularity; the server records the patch level each client is at | Why rollback capability must be top priority |
| Gray isolation | The gray bucket for compatibility-type patches must always include the oldest supported host; during the observation window, watch crashes bucketed by host | Gray release is not a nice-to-have optimization, it is an incident isolation mechanism |
| Compatibility testing | "Compatibility with historical host versions" enters the layered test checklist; smoke runs mandatory on the two oldest major versions | What is the relationship between hot updates and testing |

### Three Lessons From the Case

1. **All-green verification only proves the patch arrived intact, not that it can run on every host** — the compatibility matrix has to be granular down to interface level; it is the last acceptance gate of a hot update.
2. **Gray release is an incident isolation mechanism, not a procedural ritual** — the **5%** bucket held an interface gap away from the other **95%** of users.
3. **Disabling the channel only stops the bleeding; rolling back to the patch level is the recovery** — if the server cannot answer "which level is each client installed to," containment is always missing half.
