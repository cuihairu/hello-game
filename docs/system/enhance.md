# 装备强化与升星

## Category

system / 玩法系统（成长闸门）。节点定位：强化与升星把「消耗资源 → 换属性提升」做成**可预期、可失败、可保底**的定向成长动作。它与随机产出的分工：掉落（[掉落与概率设计](/numerical/05)）决定「你拿到什么」，强化决定「拿到之后怎么变强」。消耗走[结算](./settlement.md)凭证，强化事件的成就与任务接入走[成就与图鉴](./achievement.md)。

## Definition

强化（Enhancement/Refinement）是对既有时装/装备对象的确定性或概率性升级：消耗材料与货币，提升基础属性或追加词条。升星（Star Upgrade/Ascension）是品质阶梯：消耗同名或专属材料，把对象推到下一档，档间是离散的属性乘数或解锁位。两者的共同结构：**一张等级/星级表 + 一个失败策略 + 一条保底规则**。强化有失败与回退问题，升星通常是确定性兑换，失败策略为零。

## Problem

强化的坑按出现顺序：

- **概率公示与实际不符**：客户端显示的成功率与服务端判定不一致，或运营暗调概率——合规红线，不是体验问题。
- **失败无止损**：失败只扣材料不给补偿，玩家挫败感全部由概率承担；连败没有保底，极端体验不可控。
- **材料多来源对不上账**：材料来自掉落、商店、活动回收多个入口，强化扣材料失败后回补的路径与消耗凭证不一致。
- **装备替换的传承断档**：换一把武器，旧武器的强化等级作废——前期投入瞬间贬值，玩家不敢强化。
- **强化等级绑死装备实例**：服务端把强化状态存在装备实例内还是独立表没想清，迁移与传承实现不了。

## Algorithm

### 强化表：等级、消耗、成功率与属性

```text
enhance_def:                      # 静态表，按装备品质分档
  quality:     purple
  level:       3 → 4
  cost:        { gold: 8000, stone: 12 }
  success_rate: 0.75
  bonus:       { atk: +40 }
  fail_policy: keep            # keep / downgrade / break
  pity_band:   5               # 连败 5 次内必成

equip_enhance_state:              # 运行态，每件装备一行
  equip_uid:   e-77123
  player:      u1001
  level:       3
  fail_streak: 2               # 当前保底计数
```

- 判定在服务端：随机数、成功判定、保底计数全部服务端完成，客户端只展示——口径与[服务器权威](/client/05)一致
- 失败策略三档：

| 策略 | 失败后果 | 体验 | 适用 |
|------|---------|------|------|
| keep（不降级） | 只扣材料 | 温和 | 手游主流，强化材料本身是消耗 |
| downgrade（降一级） | 等级回退 | 强烈的风险感 | PC/端游传统强化（如武器强化类玩法） |
| break（碎裂） | 装备消失 | 极端 | 仅限高危装备位，需前置止损设计 |

### 保底：连败计数与同构 pity

- 每件装备每档位维护 `fail_streak`，连败达到 `pity_band` 内必成——与抽卡 pity（[掉落与概率设计](/numerical/05)）同构：都是「概率表面下的硬性下限」
- 保底计数**只在失败时增加、成功时清零**，不随时间衰减；换装备不转移保底（除非做传承，见下）
- 公示口径：概率与保底规则在客户端展示处写明——国内随机抽取类玩法的概率公示是监管要求，强化若含随机同样适用

### 升星：确定性阶梯

```text
star_def:
  quality:     purple
  star:        2 → 3
  cost:        { shard: 60 }          # 同名碎片或通用升星材料
  multiplier:  { hp: 1.15, atk: 1.15 }  # 全属性乘数

star_progress:
  equip_or_hero_uid: h-2201
  star:        2
  shards:      42 / 60
```

- 升星是确定性兑换：材料齐即成，无失败策略——风险感由「材料获取难」承担，不由随机承担
- 属性用乘数而非加值：星级是品质档，跨品质不可比，乘数让表可按品质独立维护
- 碎片来源（掉落、商店、活动）只决定材料入账，消耗统一走凭证——与强化共用结算路径

### 强化传承：等级转移与折损

装备被替换时，旧强化投入的出路三选一：

| 方案 | 口径 | 代价 |
|------|------|------|
| 全额继承 | 新装备直接获得旧等级 | 后期养成无摩擦，前期投入不贬值 |
| 折损继承 | 按比例降级继承（如 -1 级或 80%） | 保留替换动机，投入仍受保护 |
| 材料返还 | 拆解返还部分强化材料 | 玩家重新操作一遍，返还率是数值敏感点 |

- 存储上强化状态必须是**独立于装备基础属性的记录**（`equip_enhance_state` 以 `equip_uid` 关联），传承才有实现空间——这是「强化等级绑死装备实例」问题的解法
- 传承动作本身走凭证：旧记录销毁与新记录生成在同一事务，防复制

## Used By

- **原神**（商业手游）：武器突破与圣遗物强化为**确定性消耗**（无失败），圣遗物词条强化有档位随机——「强化无失败 + 词条有随机」的混合形态参照。
- **Diablo 系列**（商业 ARPG，暴雪公开设计资料）：装备随机词缀与洗练消耗，是「随机强化 + 定向重随」的参照。
- **阴阳师**（商业手游）：御魂强化，词条随机提升、档位节点保底——随机强化带节点的参照。
- **梦幻西游**（商业端游，网易公开资料）：宝石镶嵌与合成，确定性阶梯 + 材料合成的参照。
- **TrinityCore**（开源 MMORPG 服务端套件，公开仓库与 wiki）：附魔、宝石插槽、装备升级均为数据表定义加服务端判定，本页「强化表 + 服务端判定」的直接参照；具体表结构以项目公开文档为准。

可参考分析：TrinityCore 附魔/宝石表=可参考（强化表结构直接落本页 enhance_def）；原神无失败强化=可借鉴（keep 策略与确定性升星落失败策略表）；阴阳师御魂=可借鉴（随机词条与档位节点落保底一节）；Diablo 洗练=可借鉴（重随机制，本页未展开，落点 design 树养成设计）；梦幻西游合成=可参考（确定性阶梯落升星一节）。

## Related

关系链：强化表 → 服务端判定 → 保底 → 升星 → 传承。逐段回答「为什么需要下一个」：

- 表定了才谈判定——成功率与消耗是静态数据，判定是它们的运行态。
- 判定在服务端才谈保底——客户端判定的概率没有公信力，保底必须服务端计数。
- 保底兜住了才敢做升星——确定性阶梯是失败策略为零的特例，共用同一套消耗凭证。
- 消耗闭环了才谈传承——传承是强化状态的迁移问题，状态独立存储才有迁移可言。
