# 玩法品类与功能组件覆盖对照

## Category

system / 玩法系统。节点定位：把市场常见的 21 个玩法品类拉成一张网，逐品类列出最先要求的功能组件，再把 46 个组件一一对到本仓现有篇目上，给出「已覆盖 / 部分 / 缺口」三档判定。判定只认独立篇与专节，正文里出现过一次词不算覆盖。

## Definition

品类是玩家和发行沟通用的标签，功能组件是服务端真要建出来的件。两者不是一对一：排行榜这一个组件，棋牌、派对、MOBA、卡牌十几个品类都要；SLG 这一个品类要的件，横跨账号、持续世界、社交、运营四组。所以本页用两张表回答两个不同的问题：品类表回答「做这个品类，第一批要建什么」，组件表回答「这个件本仓有没有、在第几层」。

## Problem

本仓玩法篇的选取标准是「做起来最难」：撮合、排行、技能、结算、同步这类件，做错了会出事故，所以先写。市场常见场景的标准是「每款都要」：任务、成就、签到、邮件这类件，难点不在算法，在数量、配置量与运营节奏。两套标准的交集不是全集，按最难选出来的篇目，必然漏掉最常用的一批。

漏掉的后果在做品类分析时才显形：架构层面讲得通，系统清单却凑不齐，立项时的服务端工作量估算偏低。本页做一次拉网，顺序是先定对照基准，再枚举品类，再把品类反复要求的件归并成清单，最后只把「既没有独立篇、也没有专节」的算作缺口。

## 判定口径

三档判定，判定对象是本仓 `docs/` 下的 md：

- **已覆盖**：有以该组件为主题的独立篇，文件主标题就是这个系统。
- **部分**：没有独立篇，但在知识库某篇有专节或成段展开，或在教程《玩法系统设计》《辅助系统设计》两讲有专节。
- **缺口**：知识库与教程都没有专节，全库只剩零星词，甚至一个词都检索不到。

检索方式是全库关键词 grep 加同义写法复核，检索日期 2026-10-08。全页计数以表格为准：品类 21 个，组件 46 项，其中已覆盖 40、部分 6、缺口 0（原 11 个缺口由 2026-10-09 玩法系统丰富批补齐）。

## 缺口清单（11 项，已全部补齐）

**结论：11 个缺口全部属于「不做就上不了线」型，没有一个属于「做错会出事故」型；按品类需求密度排，任务与成就最先，走马灯与签到其次。2026-10-09 玩法系统丰富批十篇全部补齐，逐项落点见各条末行，下文保留补齐前的分析作对照。**

1. **任务系统**。接取条件、进度推进、链式前置、奖励发放四件事，MMORPG 与卡牌的内容量全压在它上面。TrinityCore 的做法是把任务定义、达成条件、奖励各自放数据表，服务端只按事件推进进度，加任务不改引擎代码。本仓只有教程 09 讲一句字节码举例，奖励发放侧反而已经有 [结算](/system/settlement) 的凭证口径可接，缺的是中间那层进度模型。落点：[任务系统](/system/quest)。

2. **成就系统**。与任务同构，差别在进度只增不减、按事件订阅、一次性发奖。TrinityCore 把成就与达成条件同样做成数据表加判定条件。本仓用它举例观察者模式，说明事件订阅的动机已经在，缺的是成就自己的口径：进度幂等、跨玩法事件源、发奖与对账怎么接流水。落点：[成就与图鉴](/system/achievement)。

3. **装备强化与升星**。资源消耗、失败保护、材料回收、属性迁移四件事，是养成线里最烧资源也最容易出事故的地方。成熟开源件里少见独立的强化模块，属项目自建。本仓数值侧有 [成长曲线模型](/numerical/03)，账务侧有 [交易、支付与经济系统](/system/services/03) 的流水要求，缺的是把两者连起来的机制篇。落点：[装备强化与升星](/system/enhance)。

4. **走马灯、喇叭与游戏内公告**。全服下行通道，难点在频控、分片广播、屏蔽与重要消息的保序。Colyseus 的房间广播是框架给的现成下行口，频控与屏蔽仍在业务层。本仓 [房间广播、弱网与国内网络环境](/networking/07) 讲到网络层，[触达体系与外部能力接入](/operation/bi/05) 讲站外推送，游戏内这一段两头都不占。落点：[走马灯与公告](/system/marquee)。

5. **签到、福利与兑换码**。领取幂等、断档补领、兑换码的批次与一码一用、防刷，全是小额高频的账务动作。Nakama、Colyseus、KBEngine 的内置模块清单里没有这一项，属自建件。本仓邮件附件领取的凭证口径可以直接复用，缺的是签到日历与码池管理这两块。落点：[签到、福利与兑换码](/system/checkin)。

6. **赛季通行证（战令）**。免费轨与付费轨的进度、任务驱动的赛季活跃、结算时的补发。Nakama 内置的是 tournaments 与 leagues，管报名、时间窗、奖池与赛季串联，战令的进度轨仍要自建。本仓 [商业化数值示例模型](/numerical/06) 已经把战令放进付费梯度，机制侧缺一节。落点：[战令与赛季轨](/system/battle-pass)。

7. **图鉴与收藏**。收集进度、解锁条件、收集度加成，卡牌与开放世界的长线留存主要靠它。成熟开源件里同样少见对应模块。本仓缺的是「只增不减的事件集合」这个存储口径，以及解锁事件怎么与奖励发放对接。落点：[成就与图鉴](/system/achievement) 图鉴节。

8. **体力与次数门控**。体力恢复、按服务器日重置的副本次数、扫荡与补领，是休闲与卡牌品类的节奏闸门。本仓 [经济循环与产出消耗](/numerical/04) 把体力当回收口、[关卡难度与新手节奏](/numerical/07) 把体力当重试成本，都只到数值口径，时区与重置幂等没有落点。落点：[体力与次数门控](/system/stamina)。

9. **外观、皮肤与装扮**。库存归属、穿脱的权威、局内可见的同步，是 MOBA 与二次元的主力付费件。本仓数值侧已经把外观当回收口与定价项，状态侧的库存与同步没有专节，正好夹在 [技能系统](/system/skill) 之外的实体表现与 [同步模型](/server/sync/02) 之间。落点：[外观、皮肤与装扮](/system/cosmetics)。

10. **家园、领地与建造权限**。生存建造、模拟经营、SLG 三个品类的主循环都压在这上面：空间归谁、谁能改、破坏怎么算。BigWorld 与 KBEngine 给的是引擎侧的空间与触发器这类件，领地规则属玩法层自建。本仓 [AOI：兴趣区域](/server/aoi) 与 [开源服务器地图](/server/map) 提供空间底座，权限与规则没有落点。落点：[家园、领地与建造权限](/system/territory)。

11. **语音（队伍与房间内）**。派对、FPS 开黑、MMO 副本的标配，常见做法是接第三方 SDK，服务端只负责房间语音位的分配与鉴权。本仓 [登录、支付、社交与广告 SDK](/industry/platforms/03) 覆盖了另外四类 SDK 的接入边界，语音不在其中，[队伍匹配（组队）](/system/party-matchmaking) 也只在撮合形态里提了一句。落点：[游戏内语音](/system/voice)。

补齐顺序按品类需求密度排：任务与成就最先，因为 14 个基准主题里它们就占了两个，且 MMORPG、卡牌、放置三个大品类同时依赖；走马灯与签到其次，运营一开活动就会要。（该顺序已按批次执行完毕：2026-10-09 十篇全部入库，见各条末行落点。）

## 可参考分析

对照基准与缺口条目里引用过的外部做法，逐条给出参考结论、理由与落点；判定只针对「要不要按它的方式补本仓的篇」，不评价原项目本身。

- **TrinityCore 的任务数据表化（任务定义、达成条件、奖励各自成表，服务端只按事件推进进度）——可参考。** 理由：它把「加任务不改引擎代码」做成了机制，正好是本仓缺的那层进度模型，且与全库配置驱动的既有口径同构。落点：任务系统篇的机制骨架按「定义表 / 条件表 / 奖励表 + 事件推进」展开，奖励发放接[结算](/system/settlement)的凭证口径，配置面引[配置表与数据驱动管线](/production/05)。
- **TrinityCore 的成就判定条件表——可参考。** 理由：进度只增、按事件订阅、一次性发奖三个口径都能落进条件表，避免成就写成散落在业务代码里的 if。落点：成就与图鉴篇的判定口径，事件源按战斗、经济、社交三类归并成订阅表，图鉴作为「只增不减的事件集合」变体同篇展开。
- **Nakama 的 tournaments 与 leagues（报名、时间窗、奖池与赛季串联）——可借鉴。** 理由：赛季时间窗与赛季串联的口径现成；但它是锦标赛与段位件，战令的免费轨与付费轨进度不在其内，照搬会漏掉进度轨。落点：赛季通行证篇的赛季侧借它的口径，进度轨自建方案单独成节，赛季榜实现回指[排行榜](/system/leaderboard)。
- **Colyseus 的房间广播（框架级下行口）——可借鉴。** 理由：全服公告可以视作「向全体房间各广播一份」，下行通道语义现成；但频控、屏蔽、重要消息保序都在业务层，框架不管。落点：走马灯与公告篇承接[房间广播、弱网与国内网络环境](/networking/07)的网络层，补业务层频控与保序；站外触达那段仍归[触达体系与外部能力接入](/operation/bi/05)。
- **BigWorld 与 KBEngine 的空间与触发器件——可借鉴。** 理由：空间底座（谁在附近、进出触发）引擎件给现成，但领地归属、建造权限、破坏判定属玩法层，引擎不管。落点：家园领地篇以[AOI：兴趣区域](/server/aoi)与[开源服务器地图](/server/map)为空间底座，权限与规则作为成篇主体。
- **Agones 与 Orleans 的调度与 actor 承载——不适用（对这 11 个缺口）。** 理由：两者解决的是「件跑在哪」的承载与编排问题，不提供任务、签到、战令这类运营件，放进缺口篇会变成背景噪音。落点：仅在相关篇的承载取舍一句带过，不展开；承载层本身已有[协调层、跨服与控制平面](/server/services/03)。
- **市场品类分类口径（平台标签体系）——可参考。** 理由：本页品类表的基础，「题材不入表、只留会改变组件需求的维度」的剔除口径已经过一轮验证。落点：维持本页口径不变；品类到问题模型的映射继续由[常见玩法类型概览](/industry/models/00)承担，本页不重复。
