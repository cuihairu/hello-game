# Event Tracking, BI, and Analysis Systems

## Category

operation / bi subtree. Node positioning: the failure mode of a data system is "everyone has a chart, no one dares to trust it" — the factual collection discipline of event tracking, definition governance, BI reuse, and chain failure points.

## Definition


The most common failure of a data system is not a lack of data, but that everyone can produce a chart and no one dares to guarantee the numbers in it actually represent business reality. Event tracking, BI, and analysis systems without unified definitions only escalate the argument from "what happened" to "which report should we believe".

## Problem

Without unified definitions, analysis only escalates the argument from "what happened" to "which report should we believe"; if any link in the collection → transmission → warehousing → reporting chain silently drops data, every downstream conclusion distorts. Event tracking first answers "what are the facts"; charts are merely projections of the facts.


### Event tracking is first and foremost factual collection, not "log whatever comes to mind"

Many teams' early event tracking practice is: whoever wants numbers — product, operations, analysts — just has the client or server "casually log it". This is fast short-term, but keeps manufacturing problems afterward:

- The same behavior is redefined on different ends
- Event names are similar but field meanings differ
- Old instrumentation is never cleaned up, new instrumentation is never accepted
- Client events and server facts contradict each other

A more solid approach is to tier the events first:

- Behavioral events: frontend interactions such as click, enter, exit, browse
- Business events: key facts such as match completed, reward claimed, payment completed, character created
- System events: load failures, network errors, lag, crashes, service exceptions

Among these, the key metrics that genuinely affect operating judgment should be built preferentially on server-side verifiable facts. Client behavioral data is important, but is better suited to explaining paths and experience, and is not fit to single-handedly bear settlement, revenue, or asset conclusions.

### Why metric definitions always matter more than charts

Daily reports, weekly reports, and campaign dashboards are all just presentation layers. What truly determines analysis quality is the definition itself, for example:

- Is "new user" counted by first login, first character creation, or first completion of the newbie tutorial
- Is "active user" counted by login, or by producing valid behavior
- Is "paying user" counted by successful payment, or by successful delivery
- Is "churn" X days without logging in, or X days without core behavior

As long as these definitions are unstable, the more reports there are, the more severe the misdirection. Many classic disputes are not algorithm problems but definition problems:

- The marketing side says spend drove high new-user growth, the product side says newbie churn is abnormal — in fact one counts by registration and one counts by character creation
- Operations says a campaign lifted retention, the analyst says there was no significant change — it turns out one looked at next-day login and the other at seven-day core behavior
- The payment dashboard shows revenue growth, but finance reconciliation finds it includes orders that were never finally confirmed

So any important metric should have a clear definition document, an owner, and a change record.

### The value of a BI system is not "can query" but "what you query can be reused"

If a data system only lets analysts write SQL and then screenshot results to send to the group chat, that does not count as real BI capability. A more mature BI platform usually needs to solve at least three things:

- Let different roles see metrics under the same definitions
- Template high-frequency analysis rather than rewriting SQL every time
- Connect reports to action chains such as campaigns, experiments, segmentation, and alerts

In other words, BI is not just about reading data; it must also become the organization's shared fact layer. Without this shared fact layer, retrospectives turn into everyone talking past everyone.

### Where does the data chain usually break

### Collection side

- Client packet loss, retries, and offline caching scramble event ordering
- Server event definitions are inconsistent with database facts
- Multiple ends share one instrumentation name but with inconsistent field semantics

### Processing side

- ETL logic changes are not synced with historical recomputation
- Dimension table definitions change, e.g. channel, region, and user level mappings are not synced
- Timezone, calendar day, and operations day definitions are not unified

### Consumption side

- Different departments copy a report and process it again, forming "folk definitions"
- Campaign retrospectives use ad-hoc reports directly, without fixed samples and time windows
- Key metrics have no anomaly alerts, and errors go undiscovered for many days

### A more practical construction order

For most teams, a more realistic construction order for a data system is:

1. First stabilize the key business fact events and core metric definitions
2. Then build unified subject domains, e.g. new users, retention, paying, campaigns, economy
3. Only then build more flexible self-service analysis, tag segmentation, and experiment analysis

Many teams do the reverse: they deploy a powerful query platform first, then discover the underlying data is untrustworthy — the stronger the platform, the faster it spreads errors.

### Common Mistakes

- Instrumentation without naming conventions or an acceptance process, so no one knows which of it is still trustworthy
- Over-relying on client instrumentation to judge asset, payment, and settlement facts
- BI platforms that serve only analysts, not the joint decisions of operations, product, and R&D
- Lots of reports but no metric owner, no definition document, no anomaly validation

A truly mature data analysis system is not about how many charts you can draw, but whether at a critical moment the team can quickly obtain the same trustworthy facts and then make decisions on top of them.
