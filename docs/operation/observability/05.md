# Load Testing, Capacity Planning and Scaling

## Category

operation / observability subtree. Node positioning: load testing → capacity model → scaling is one chain of reasoning — the tipping point is more useful than the limit value, the shadow-traffic trade-off, and the constraints stateful services put on elasticity.

## Definition


The easiest way load testing turns out is running a script before launch, getting a throughput number, and writing it into the report. The questions it really should answer are far more specific: under what distribution of player behaviour does the system choke first and where, how does it behave after choking, and whether adding machines can solve the bottleneck. Load testing, capacity planning and scaling are in fact one chain of reasoning, and doing any one link detached from the model makes the output lose value quickly.

## Problem

Running a script before launch to get a throughput number is not capacity work: load testing detached from player behaviour distribution is distorted, and "add machines" cannot solve an architectural bottleneck. What the capacity model has to answer is: under what behaviour distribution, where does it choke first, how does it behave after, and can adding machines solve it — and stateful services make elastic scaling far more expensive than stateless ones.


### Load testing goals come from the capacity model, not from the script

The capacity model answers "what the system is going to face": expected online scale, player behaviour distribution (online duration, action frequency, gameplay composition, payment and settlement rhythm), and the shape of load each component therefore endures. Load testing goals are derived from that model — how many players in the same scenario a single machine must carry stably, how many logins per second at peak, how many writes per second the database must endure, how large a room the broadcast path must hold up.

Skipping the model and going straight to load testing yields numbers with no yardstick: whether 8,000 is a lot or a little depends on the target that has to be supported. Producing a number and validating capacity are two different things; the output of the former cannot enter capacity decisions and cannot answer "how much more is needed".

### The basic shape of the capacity projection chain

The common projection path is: load-test a single machine or single component to find its limit, back out the number of components from peak load, then leave headroom. Headroom allocation has two principles that are easily confused:

- Headroom is for faults: when a machine dies or a component jitters, traffic still has to be absorbed.
- Elasticity is for growth: load beyond expectation is digested by scaling out and dynamically opening servers.

Mixing the two either pads capacity to a wasteful high or leaves no buffer during faults. The large peak-to-valley gap of game load further magnifies the weight of capacity decisions: planning for the evening peak and idling most of the time is the norm. The wider the peak-to-valley ratio of a category, the more carefully the cost-benefit of elastic scaling should be calculated, and the idling cost of the valley period really is part of the capacity model.

### Why load testing results get distorted

The credibility of load test numbers depends on simulation quality. Common sources of distortion fall into a few categories:

- Unrealistic bot behaviour: bots that only send logins and heartbeats can measure limits several times higher than a real mixed load.
- Insufficient data volume: the database behaves completely differently on an empty database versus a billion-row one, and the slowest query paths often surface only after the data volume is there.
- Environment differences: higher specs, simpler network topology, missing real third-party dependencies — all of these make the results systematically optimistic.
- Evenly applied pressure: real pressure is local spikes — a few rooms filling up, the flood at the moment an event opens, on-the-hour batch settlement. Evenly ramping cannot produce that shape.

These distortions share the property of skewing in the optimistic direction, which is exactly the most dangerous direction: the sense of security a load test gives has to be paid back in faults after launch. Bot behaviour distributions are usually modelled after comparable products or historical data, and data volume is loaded to production scale; both of these cost far less than the incidents they prevent.

### Choosing the key scenarios determines the value of load testing

Choosing load test scenarios is essentially answering "which pressure is most likely to take the system down first". Common candidate scenarios:

- Server open and returning-player flood: the login path hit hard over a short window, often an order of magnitude apart from steady-state load.
- Event open and on-the-hour resets: large numbers of players triggering the same piece of logic at once, with instantaneous writes bursting.
- Team fights and large same-screen counts: broadcast volume, object scale and sync frequency all hitting their limits together.
- Cross-server and whole-server gameplay: aggregating region-level load onto global components, exposing global capacity.

Scenario selection usually fails in two shapes: only testing the familiar login path, turning load testing into a login test; or evenly loading every interface and finding no bottleneck at all. The valuable approach is to start from the capacity model, pick out the three or five scenarios most likely to be the weak point, and concentrate resources on them.

### Load test environment and data preparation

The goal of environment preparation is to make the conclusions transferable: specs as close to production as possible, topology reproduced as far as possible, and at least caution about the parts in doubt. The goal of data preparation is to expose slow paths: load data to production scale, especially the heaviest query tables, so missing indexes and full table scans show up during the load test rather than after launch. On the bot side, model the real behaviour distribution — the distributions of online duration, action frequency and gameplay composition reflect real load better than simply piling up connection counts.

The shared property of these three preparations is that their cost occurs before the load test and their benefit occurs after launch. Omitting them saves a few days; what gets paid is usually the night of the server open.

### The tipping point is more useful than the limit value

Under pressure a system usually does not degrade linearly but has a tipping point: past it, latency starts to rise non-linearly, error rates begin to lift, and queues start to back up. The limit throughput number is instantaneous and not runnable; the water level at the tipping point is what can run continuously. Production load is usually kept at a level clearly below the tipping point, with the buffer reserved for absorbing fluctuations and local spikes.

A load test report that only records "the highest throughput reached" and does not record the position of the tipping point contributes almost nothing to capacity decisions. Ramping the load in steps and watching latency and error rate step by step exists to find that tipping point, not to chase a good-looking peak.

### The trade-off of shadow traffic and production load testing

Importing load test traffic into the real production environment is the most direct way to eliminate environment differences. Its value lies in real data shapes, real dependencies and real topology; the risks are equally concrete:

- Write requests pollute production data: fake orders, fake payments and fake mail, once written to the database, are very expensive to clean up.
- They may trigger real downstream actions: settlement, item delivery, push, callbacks to third parties.
- What gets crushed is a shared dependency real users are using right now.

So production load testing usually has to be preconditioned by a whole set of protections: traffic carries a tag and is isolated at the storage layer, write paths are bypassed or simulated, shared dependencies are assessed in advance, a one-click circuit breaker is available at any time, and it runs in a business trough. Starting a load test before the protections are complete turns the load test itself into an incident rehearsal nobody wanted. Also because the protection cost is not low, production load testing is usually reserved for key paths and major versions rather than run casually as routine.

### When scaling helps and when it does not

Adding machines only works for load that can be spread. Typical cases where horizontal scaling works: stateless access and logic services, and rooms that can be sharded automatically. Typical cases where scaling is useless or barely helps:

- Single-match hotspots: the object scale limit of one room or one map, with the bottleneck inside a single process.
- Global locks and centralized state: all requests squeezed through the same node.
- A single slow query: however many machines are added on the application side, the database is still the same bottleneck.
- Downstream dependencies: a third-party interface's rate-limit quota does not go up because you added machines.

Seeing a bottleneck and adding machines first is the most common and most expensive misjudgment in capacity problems. Before scaling, answer the type of bottleneck first; the answer usually decides whether what should scale is the machines, an architectural split, or the gameplay design itself.

### How statefulness constrains elastic scaling

The particularity of game servers is that state lives in memory: player sessions and room state cannot be migrated or destroyed at will. This limits the scope elasticity can act on — what can really be scaled freely is stateless components, while the rooms and scene servers where players sit have to be started and stopped per runbook, and scaling in requires waiting for drain or completing a migration. Bringing the web-service operations habit of "restart anytime, drift anytime" straight into game servers is a frequent source of incidents. Distinguishing these two kinds of services when designing the scaling scheme is far cheaper than remediating afterwards.

### The scaling runbook is the execution face of the capacity model

Conclusions from the capacity model only truly take effect once they become an executable runbook. A runbook usually has to answer: at what capacity water level scaling is triggered, who executes it, what the steps are for bringing machines up and opening a server, and whether data initialization and access configuration for a new server are automated. Scaling without a runbook degrades, when the flood arrives, into temporarily requesting machines, initializing by hand, and coordinating verbally, with no guarantee of either speed or correctness.

Runbooks also need to be rehearsed. Problems exposed by scaling rehearsals are very typical: a config missing from the image, a new server unable to reach a dependency, an open-server script assuming an old number of regions. These problems take minutes to expose in a rehearsal and become part of the incident when they surface in a real flood.

### The capacity model has to evolve with versions

The shape of load changes with gameplay: object scales of new gameplays, new broadcast patterns, changes to event rules — all of these make the conclusions of the last load test expire. A common practice is to hook capacity review into the version flow — retest key scenarios before and after major versions, continuously observe the gap between actual production load and the model, and update the model when the gap keeps widening. Capacity governance is continuous work that comes out of repeated corrections, not a one-off ceremony before launch; the first signal of an expired model is often that production water level and the predicted curve start to diverge systematically.

### The cost view inside capacity decisions

Capacity has never been only technical numbers. Machines sized for the peak idle most of the time, the idling cost of the valley, the benefit boundary of elastic scaling, the ratio of reserved to on-demand — all of these are part of the capacity model. The technical side has to explain water levels and tipping points clearly before the cost side's trade-offs have a basis; discussing capacity detached from cost lets the plan keep inflating, and conversely discussing saving money detached from water level means the money saved will sooner or later be paid back in faults.

### Common pitfalls

- Load testing goals with no source, taking the produced number as the conclusion and unable to support capacity decisions.
- Distorted bot behaviour and insufficient data volume, yielding limits that are systematically optimistic.
- Recording only the limit value and never finding the tipping point, so the report looks good but the corresponding water level is not runnable.
- Production load testing with no isolation and circuit breaker protection, so the load test itself becomes an incident.
- Adding machines before the type of bottleneck is known, so cost rises while experience does not change.
- Load testing once, after which the capacity model stays expired as gameplay iterates.

Seen together, load testing, capacity and scaling share one clear property: they are all reasoning about "what the system is going to face", not measurement of "what score the system can hit". The closer the inputs to that reasoning come to real behaviour distribution, the closer the output comes to being usable.
