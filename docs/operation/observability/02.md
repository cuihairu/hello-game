# 专项可观测与 Tick 指标

通用监控回答的是“机器和服务是否正常”，游戏可观测的核心问题却是“玩家这一局体验是否正常”。这两层经常不一致：监控面板一片绿，玩家社区已经在抱怨卡顿和掉线。出现这种错位时，缺的往往不是更多机器指标，而是围绕游戏主链路专门设计的观测信号。

## 通用指标的世界观与游戏的错位

通用指标体系建立在资源与请求的世界观上：CPU、内存、磁盘、网络描述资源，QPS、延迟、错误率描述请求。这套世界观对以请求为单位的 web 服务足够有效，但游戏主链路的核心既不是资源也不是请求，而是节奏——逻辑帧按固定步长推进、广播按帧分发、匹配按队列演进。节奏类的问题，资源指标和请求指标都探测不到。

## 为什么 CPU 正常玩家仍然会卡

监控正常而玩家受影响的场景，常见的成因有这几类：

- 尖峰被均值抹平：平均 CPU 只有四成，但某几帧冲到几百毫秒，玩家的感知恰好来自最差的那几帧。
- 等待被算进空闲：逻辑线程大部分时间在等锁、等落盘、等广播队列消费，资源占用不高，推进却很慢。
- 问题出在链路下游：服务端一切正常，客户端渲染积压或帧同步滞后，服务端监控永远看不到。
- 感知来自分布而不是均值：一个房间卡和全服平均卡是两回事，聚合到全服的指标把局部问题稀释掉了。

玩家对流畅度的判断接近“最差的时刻好不好”，而通用监控天然擅长描述平均状态。这个感知差异，就是专项可观测存在的理由。

## 游戏主链路自己的生命体征

围绕主链路的专项指标，常见的覆盖面包括：

- 节奏类：逻辑帧耗时分布、超预算帧的比例、补帧次数、单帧最大追赶步数、因超时使用默认输入的次数。
- 同步类：客户端与服务端的帧差分布、广播队列积压深度、消息端到端延迟。
- 房间类：活跃房间数、房间人数分布、房间创建与销毁速率、房间平均生命周期。
- 匹配类：匹配等待时长分布、匹配成功率、玩家取消匹配的比例。
- 恢复类：掉线率、重连成功率、重连后追帧耗时、快照恢复的耗时与成功率。

这些指标的共同特点是直接对应一种玩家可描述的体验问题。帧耗时分布对应“卡”，帧差分布对应“不同步”，重连追帧耗时对应“转圈转很久”。专项可观测的建设过程，本质上是把玩家语言翻译成指标语言，并且提前把翻译表建好，而不是等投诉之后再逐条发明。

## 帧级指标为什么值得单独强调

Tick 体系的指标有一个特殊性：它是几乎所有同步类问题的公共证据源。重连慢、技能慢半拍、回放对不上、举报争议，追到最后经常落在“某一帧超预算了”“追帧时跳了太多步”“帧差在这个区间扩大”这类帧级事实上。所以成熟团队通常把帧级指标当成主链路观测的地基，而不是锦上添花：逻辑帧耗时看分布和分位数，超预算看比例和集中时段，补帧和追赶看次数与步数。没有这一层，所有同步问题最后都会退化成肉眼看录像猜测。

## 匹配与房间指标的设计要点

匹配和房间是两个容易埋错的观测点。匹配的难点在于等待时长是一个“截断分布”：放弃匹配的玩家没有等待结束时间，只统计成功匹配的耗时，会把最不满意的那批玩家从数据里删掉。所以匹配等待的观测通常要同时看成功耗时分布、取消率和超时率三个面，才能还原真实体验。

房间指标的难点在于“平均”几乎没有意义。房间人数、房间时长、广播量的分布往往高度偏斜，均值会被少数极端房间拉走。更常用的做法是看分位数和分段计数：多少比例的房间超过设计人数、多长的房间占比在上升、哪个玩法区间的广播量异常。房间数的趋势本身也是一个容量信号，它的拐点经常早于资源告警出现。

## 用对照时段验证指标

专项指标的另一个常见用途是排除噪声。玩家投诉“晚上卡”，是全天如此还是只在特定时段？活动期间掉线率上升，是活动玩法本身重，还是恰好叠加了晚高峰？单看异常时段的曲线很难回答，把异常时段与历史同期、与正常时段并排对比，问题通常自己显形。

这也是专项指标应该覆盖日常的原因：没有日常基线，异常时段的数据就没有对照物，只能靠感觉判断“这算不算异常”。

## 玩法层指标与业务数据的互相印证

玩法层指标和运营侧的业务数据经常能互相印证：帧差严重的房间，玩家的局内流失和举报往往同步上升；匹配等待恶化，匹配完成后的留存通常跟着波动。把技术侧的专项指标和业务侧的行为数据放在一起看，一方面能让技术问题的影响量化成业务语言，另一方面也能从业务异常反推技术侧应该补哪类观测。两条数据链各自独立采集、结论互相对得上，可信度都更高。

专项指标通常分成三层：系统层描述进程与资源，服务层描述接口与队列，玩法层描述帧、房间、匹配这些游戏语义。告警的位置值得斟酌——只在系统层挂告警，会出现机器全绿而玩家已经炸锅的盲区；只在玩法层挂告警，又会缺少归因线索，告警响了不知道往哪查。

常见的折中是把“玩家可感知”的信号做成一级告警，例如掉线率突增、匹配等待显著恶化、帧差超阈值房间占比上升；系统层和服务层指标作为下钻入口保留在看板上。这样告警响起来时，既代表真实的玩家影响，又有现成的排查路径。

## 指标基数的陷阱

专项指标有一个通用的技术风险：基数爆炸。按房间聚合、按玩家聚合、按技能聚合，维度组合很快超过指标系统的承受能力。常见的处理方式包括：

- 维度收敛：指标只保留玩法类型、区服分组这类低基数维度，个体细节进日志。
- 抽样上报：帧耗时这类高频信号按比例采样，靠样本量维持分布估计的稳定。
- TopN 记录：异常个体只保留最差的若干条，例如积压最深的房间、耗时最长的帧。

基数问题最好在指标系统选型和埋点设计时就考虑进去，事后治理的成本远高于事前收敛。

## 专项埋点的治理成本

专项指标的生命周期管理和业务代码一样需要维护。每个指标有口径定义、采集位置和负责人；版本迭代时，埋点会随代码重构悄悄失真——字段没人填了、采样点被删了、语义变了名字没变。缺少指标字典和上线验收的团队，往往在一年之后发现一堆“没人说得清怎么算出来的”指标，最后只能整批废弃重建。

所以专项可观测的成本不在第一次埋点，而在持续治理。常见的做法是把黄金路径的指标清单模板化，新玩法上线按模板补齐，老玩法下线时同步清理指标，让指标集合始终和实际玩法对得上。

## 什么时候开始建设

经验上，专项指标越早建设越便宜。上线之后出了体验问题再补，往往只来得及加日志，而日志不擅长回答分布类问题；在早期就把黄金路径的指标立起来，后续每次新玩法只需要按惯例扩展。越是长线项目越依赖这一层：随着玩法不断叠加，通用监控的盲区只会越来越大，而玩家对体验问题的容忍度会越来越低。

新玩法接入专项观测的时机也有讲究：上线前埋好，首发几天的高峰数据就是最宝贵的一批样本；上线后再补，要么错过高峰，要么带着事故的紧迫赶工出错。把它放进新玩法的上线检查单，是成本最低的约束方式。

## 掉线与重连的细分观测

掉线率和重连是玩家投诉的高发区，但笼统的掉线率几乎无法指导排查，通常要做几层细分：

- 按口径分：主动退出、网络断开、被踢下线，混在一起的数字没有含义。
- 按维度分：区服、网关实例、运营商、客户端版本，异常往往集中在某一维。
- 重连要看完整链路：重连请求成功率、鉴权耗时、状态恢复耗时、追帧耗时，玩家感知的是总时长而不是某一段。

细分之后，掉线数据才能定位问题；粗粒度的掉线率只能确认出了事，说明不了哪里出了事。重连链路尤其值得按阶段拆开计时，因为“转圈转很久”的成因可能落在四个完全不同的环节。

## 每个指标背后要有下钻路径

指标告警只是起点，每个核心指标背后最好预设下钻路径：掉线率上升，先看区服和网关维度；匹配等待恶化，先看队列长度和在线结构变化；帧耗时超标，先看是否集中在特定玩法或时段。没有预设路径时，告警到排查之间会多出一段自由发挥的时间，而故障时刻最缺的恰恰是时间。把下钻入口写进告警附带的处理提示或值班手册，专项指标体系才算形成闭环。

## 常见误区

- 把专项指标当成补充装饰，出了体验问题才临时加日志，错过第一批现场。
- 只看均值不看分布，尖峰类问题在面板上长期不可见。
- 指标堆积却不分层，告警泛滥之后没人知道哪些真正影响玩家。
- 高基数维度直接进指标系统，观测系统先于业务被压垮。
- 埋点没有字典和验收，随版本迭代悄悄失真，等要用时才发现数据不可信。

通用监控解决的是服务活不活着，专项可观测解决的是游戏玩起来对不对。两者在指标来源、聚合方式和告警策略上都不相同，用同一套思路去覆盖，往往两头都做不好。
