# Game Data Classification and Modeling

## Category

database / data modeling. Node position: answer "which category of state is this" before talking about tables — the boundaries between runtime ephemeral state, long-term assets, derived query data, and audit/archival data are the master outline for the rest of this tree.

## Definition


The genuinely hard part of database design is not how to build tables, but how to partition state. "Data" in a game all looks like it has to be stored, but their natures differ enormously: some is high-frequency ephemeral state, some is long-term assets, some is a derived replica kept for retrieval convenience, and some is operation records retained for audit and recovery. Stuffing these completely different kinds of data into the same model long-term will quickly drain the system's elasticity.

So when discussing data modeling, the first step is never building tables — it is first answering "which category of state is this".

## Problem

"Can be stored" day to day does not mean the model is sound. Modeling quality only reveals itself at moments of migration, compensation, rollback and archival. The two most expensive kinds of wrong ledger: runtime ephemeral state mixed with long-term assets — the real-time path is dragged down by assets, and assets are polluted by high-frequency writes; and derived replicas reverse into the source of truth — a leaderboard replica treated as the ground truth of combat power, report aggregates used for online arbitration. Classify state and fix the authoritative source first, then talk about table structure.


### The common data types in a game are not all the same

A fairly common way of classifying usually includes at least:

- Runtime ephemeral state
- Long-term asset state
- Derived query data
- Audit and operation logs
- Analytics and archival data

The reason these have to be distinguished is not for conceptual completeness, but because their requirements for consistency, query patterns, retention periods and recoverability are completely different.

### Why runtime ephemeral state cannot be mixed with long-term assets

Data such as room state, scene objects, combat processes and matchmaking contexts changes fast, has a short lifecycle, and demands high real-time behavior. What they care about is whether the present moment can keep moving forward quickly, not whether they survive complex queries and long retention.

Long-term states such as character assets, inventories, orders, quest progress and currency balances are different. What they care about is:

- Whether it is ultimately correct
- Whether it can be audited
- Whether it can be rolled back and compensated
- Whether it is explainable when migrating across versions and across server groups

Tying the two together long-term usually yields the worst possible middle state: the real-time path is dragged down by long-term assets, and long-term assets are polluted by the real-time path's high-frequency writes and ephemeral structures.

### Derived data and source data must be kept apart

The single easiest point to botch in many systems is that, for the sake of convenient querying, derived data slowly reverses into the source of truth. For example:

- A leaderboard replica is treated as the player's ultimate ground truth of combat power
- A mail display replica is treated as the authoritative reward state
- Report aggregate results are used for online arbitration

A more solid approach is to distinguish explicitly:

- Who is the authoritative source data
- Who is the derived replica generated for performance and query efficiency
- When the replica updates, and how to rebuild it when it goes stale

As long as this boundary is unclear, later troubleshooting, data backfill and migration will all become progressively more painful.

### What questions should data modeling start from

### Who owns this state

Which system ultimately owns this data, and whether it is the single source of truth, decides the update path and recovery approach that follow.

### How is it read

Is it read by player primary key, queried over time ranges, or does it need complex aggregation? This directly affects whether the storage structure is reasonable.

### How long does it need to be retained

Some state is only valuable within a single match, some has to accompany a player for their entire lifecycle, and some only needs to be kept for audit and archival.

### How large is the cost if it goes wrong

Asset errors, wrong payment orders, duplicated rewards and short query latency — the costs are entirely different. If modeling does not look at failure cost first, the cost will inevitably be misallocated later.

### Why so many problems only surface during migration and recovery

A system that runs fine day to day is not necessarily soundly modeled. What genuinely exposes modeling quality is often these moments:

- Server merges and cross-region migration
- Asset compensation and data repair
- Rollback and audit-based accountability
- Hot/cold tiering and archival rebuilds

If the moment these scenarios arrive the team discovers that state provenance is unclear, field semantics are muddled, and the derivation chain cannot be rebuilt, then the problem was never in the database product to begin with — it was in the modeling itself.

### Common pitfalls

The most common error is treating "can be stored" as "modeling complete", without distinguishing runtime state, long-term assets and derived data. The second is building tables however is convenient for querying, with no clearly designated authoritative data source over the long run. The third is modeling only for current features, without reserving structure for migration, recovery, audit and archival — so the system begins to lose control as soon as it reaches the long-term operations stage.

## Used By

Data review for any project with a server side: new systems fix data classification and authoritative source (the four questions — who owns it, how it is read, how long it stays, and the cost if it goes wrong); long-running projects do a modeling health check before merges, compensation and rollback. Acceptance method: take one real asset-dispute ticket and check whether the provenance and recovery path of all four data types can be answered.
