# Data Synchronization, Hot/Cold Tiering and Archival

## Category

database / data lifecycle. Node position: hot/cold tiering, synchronization semantics, archival and recovery — treat the entire data lifecycle as a first-class design object, not "only think about archival once the table gets too big".

## Definition


Many systems early on only care about "getting the data stored", and it is only after running for years that the real problems surface all at once: online tables grow heavier and heavier, historical data gets harder and harder to query, recovery relies on people stitching logs by hand, merges and migrations grow more and more dangerous, and when you try to audit or replay you discover that the right data was never retained in the first place. Data synchronization, hot/cold tiering and archival exist precisely to solve these long-term problems.

They sound like storage-optimization topics, but they actually affect directly:

- Query and write cost
- Recovery and compensation capability
- Support for spectator viewing, replay and anti-cheat
- Merging, migration and historical audit capability

So what is discussed here is not "where to move old data", but how the entire data lifecycle is governed systematically.

## Problem

Early on the only concern is "store it"; years later the problems surface all at once: online tables grow heavier, recovery depends on people stitching logs by hand, merging gets more dangerous, and trying to audit finds that the right data was never kept. What is hard about synchronization is not copying but semantics — which copy is authoritative, which is allowed to lag, how to rebuild it when it goes stale; the value of archival lies in the recovery rate, not in having stored anything. These only reveal themselves in acceptance scenarios: tracing an asset dispute, rebuilding a leaderboard, pre-merge verification.


### Why "hot data" and "cold data" cannot keep living mixed together

Hot data usually has these characteristics:

- High-frequency online read and write
- Directly affects the current player experience
- Latency-sensitive
- Relatively short lifecycle but dense changes

Cold data is usually:

- Historical records
- Audit logs
- Long-term archive
- Low-frequency queries but retained for a long time

If the two keep living mixed together, the common consequences are:

- Online tables grow bloated
- Queries and indexes grow heavier
- Backup and recovery windows keep stretching
- Even an ordinary business change touches a large amount of historical baggage

The essence of hot/cold tiering is letting data of different lifecycles live under different cost models.

### What is truly hard about data synchronization is not copying, but semantics

Many systems have multiple copies of data:

- Online primary database
- Cache and read replicas
- Search or leaderboard replicas
- Offline analytics database
- Archive storage

The question is not whether synchronization exists, but:

- Which one is authoritative
- Which one is allowed to lag
- How to rebuild a replica after it goes stale
- How does the system alert and compensate when synchronization fails

If you only "copy the data over" but never write these semantics down, then as replicas multiply the whole system gradually loses its single source of truth.

### Why archival is not a small problem at the tail end of storage

The real value of archival usually shows up in these scenarios:

- Historical behavior tracing
- Compliance and audit
- Asset dispute handling
- Basis for data repair and compensation
- Pre-verification for major version migration and merges

If a system only thinks about archival once the tables get too big, that usually means it never treated the data lifecycle as a first-class design object.

### A more solid perspective on the data lifecycle

A fairly solid approach is usually to split data into several tiers:

- Online authoritative data
- Online derived replicas
- Medium-term queryable history
- Long-term archival and audit data

Then define separately:

- Retention duration
- Query method
- Recovery method
- Whether it participates in the online path

The key to this approach is that the system knows from the start which data must always stay "alive" and which data exists only so that it can still be explained on some future day.

### The most honest acceptance scenarios for synchronization and archival

This kind of design shows no good or bad under normal conditions; what truly exposes quality is often these moments:

- A player asset dispute needs tracing
- A leaderboard entry or battle record needs rebuilding
- Pre-merge, cross-server data consistency must be checked
- A historical bug requires batch data repair
- A very large table must be migrated or split

If every time these scenarios arrive you find data provenance unclear, the path cannot be replayed, and historical records incomplete, that means the system never established formal data lifecycle governance.

### Common pitfalls

The most common error is understanding synchronization as "store more copies to be safer", without defining the authoritative source and replica semantics. The second is only doing hot/cold tiering and archival ad hoc once the table gets too big or the cost too high. The third is archiving only to save storage, not to serve recovery, audit and migration — so the historical data is moved away but still unusable when it is truly needed.

### Practical case: tracing an asset dispute where "only 8 of the transactions from 90 days ago could be recovered"

> The case is a demonstration example (not drawn from a real project); the numbers are rounded for simplicity. It drives this page's "Why 'hot data' and 'cold data' cannot keep living mixed together", "What is truly hard about data synchronization is not copying, but semantics", "Why archival is not a small problem at the tail end of storage", "A more solid perspective on the data lifecycle", "The most honest acceptance scenarios for synchronization and archival" and "Common pitfalls" into deep water: a single asset dispute exposed the semantic gaps of all four replicas at once.

**Background and symptoms**: A project two years into operation; a player complains of account theft: about three months earlier (the dispute window is T-92 to T-85 days) 3 pieces of equipment and 450,000 gold in the account were transferred out in 12 transactions. Support checked by process — the online transaction table only retains 30 days, so 0 transactions in the window are queryable; the read replica, whose cleanup policy is not synchronized with the primary, has 4 residual transactions, each differing from the player's bill screenshot by 5%, and the initial judgment was "amounts do not match, evidence insufficient". The player appealed a second time and it was escalated; by the time the dedicated team took it over, **2** days had already passed since the first ticket.

### Step 1: Symptoms and calibration — first fix "which one is authoritative", then talk about recovery

Calibration aligned: tracing uses "the settled transaction record" as the authoritative caliber (listing price and displayed amount do not serve as the asset basis), and assets are accounted separately for equipment and gold. First record the ticket ledger:

- **Ticket request**: **3** pieces of equipment + **450,000** gold, **12** transfers in total
- **Initially recoverable**: **0** transactions in the online table, **4** in the read replica (on the listing-price caliber, each carrying an extra **5**% fee)

The evidence chain broke at the very first link — take stock of the data sources first, then talk about recovery.

### Step 2: Layered attribution — the data-source ledger from online table to archive files

```text
口径账   争议窗口 T-92～T-85 天，涉 3 件装备、45 万金币：3 笔装备交易 + 9 笔金币转移 = 12 笔
在线账   在线交易表保留 30 天：窗口内可查 0 笔，90 天前流水已滚动清理
归档账   月度归档找回 8 笔；T-3 月文件止于当月 15 日——导出当日失败无重试，缺 4 笔
分析账   离线分析库按天同步权威流水：补回 4 笔，成交口径与归档 8 笔完全一致
对账账   12 笔全找回、45 万金币对平、3 件装备流向闭环——两个来源无一笔冲突
```

The ledger closes: **8** + **4** = **12** transactions all recovered. The 4 transactions whose amounts "did not match" in the initial check were exactly the caliber gap between the read replica recording the listing price and the transaction record writing the settled price — when this page's "which one is authoritative" has no answer, every replica is a dead end. The 4 transactions missing from the archive stalled at this page's "how does the system alert and compensate when synchronization fails": the export task failed that day, with no alert and no retry, so the gap existed silently for three months.

### Step 3: Root cause — archival served storage, not recovery

Compared against this page's list of five replicas in "What is truly hard about data synchronization is not copying, but semantics" (online primary database, cache and read replicas, leaderboard replicas, analytics database, archive storage): "which one is authoritative" was never registered, and support's query entry point read straight into a replica; the archive files had no index and no schema version, so recovering the 8 transactions relied on a human flipping through files by date. This page's "if a system only thinks about archival once the tables get too big" is exactly the source of it — archival was a stopgap action when tables grew, nobody reconciled export completeness, the task failed silently for three months, and it was only on the day of the dispute that "data provenance unclear, path not replayable, historical records incomplete" was discovered. The first of the common pitfalls — "understanding synchronization as 'store more copies to be safer', without defining the authoritative source and replica semantics" — came true word for word.

### Step 4: Disposition and backfill — close the ticket first, then make "unrecoverable" impossible

The fix came in two parts. Emergency response: issue a tracing report on the settled-transaction caliber — **2** pieces of equipment were still in the buyer's pack and were recovered, **1** had already been decomposed and was compensated at **120,000** gold per the settled price in the archive, and the full 450,000 gold was returned to the account, closing the case; initial check **2** days + dedicated handling **3** days, **5** days total. Institutional, four steps: register the "authoritative / derived" identity of the four replica classes, and let support's query entry point take only the authoritative source; add failure alerting plus retry to the archive task, and reconcile export completeness monthly (checking both counts and amounts); write the retention matrix (online table **30** days, analytics database **90** days, archive **2** years) into the lifecycle ledger; each quarter pull real tickets to rehearse a "90-days-ago tracing" drill, cutting the drill duration from **5** days down to **40** minutes. Recheck: a rehearsal drew a real dispute from T-4 month, closed end to end in **40** minutes.

**Backfill checklist**:

### Three lessons from the case

1. **The more replicas a system has, the more urgently it must answer "which one is authoritative"** — when the answer is absent, every replica is a dead end, and the 5% amount gap in the initial check was exactly the price of that dead end.
2. **The value of archival lies in the recovery rate, not in having stored anything** — an export failure with no retry means the very 4 transactions most needed on the day of the dispute are the ones missing.
3. **The quality of synchronization and archival only reveals itself in acceptance scenarios** — rehearse "90-days-ago tracing" by quarter; do not wait for players to put you to the test.
