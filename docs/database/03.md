# Transactions, Consistency and Sharding

## Category

database / transactions and scaling. Node position: split transactions (local correctness), consistency (convergence across the path) and sharding (scale extension) into three separate layers of problem and decide each on its own terms — tier by value, and reach for extension means only last.

## Definition


These terms are often talked about together, but they solve problems at different layers. Transactions discuss how a single state change keeps local correctness; consistency discusses how cross-path and cross-system state eventually converges; sharding discusses how to keep extending without dragging the system down once data volume and load rise. Blurring these three into one sentence like "just shard later and it will be fine" or "adding transactions makes it safe" usually only makes the problem more vague.

What really should be asked first is: which kinds of state must be strongly guaranteed, which kinds are allowed to converge late, and whether those costs are worth bearing for the current business.

## Problem

Blurring the three into one line — "transactions make it safe", "just shard later" — will always produce a miscalculated ledger: transactions only keep local correctness inside a single database boundary; once state crosses that boundary, what carries the load is the authoritative boundary, idempotency and compensation, not a bigger transaction; sharding is an extension means for when scale bottlenecks arrive, not a performance panacea — sharding too early turns a simple problem of indexes and query models into a complex problem of routing, migration and audit.


### Where transactions are genuinely valuable

The value of transactions has never been "advanced" — it is making a set of changes that should succeed or fail together controllable inside a local boundary. For these scenarios it is usually very important:

- Currency deduction and item issuance
- Order confirmation and shipping records
- Inventory changes and log writes
- Transaction state transitions

Once problems in this class go wrong, the later compensation and accountability cost is extremely high, so local transaction boundaries are often worth designing carefully.

### Why you cannot count on transactions to solve all consistency problems

Once state crosses out of a single database, a single service or a single storage boundary, transaction cost rises fast. Many real paths become:

- The asset write here succeeded, but the leaderboard update over there timed out
- The order was confirmed, but the notification and log have not landed yet
- Service A committed, but service B, which should have reacted, did not follow

What the system genuinely needs at this point is often not a bigger transaction, but a clearer authoritative boundary, idempotency, compensation and recoverable design.

### Consistency strength should be tiered by value

A more realistic approach is usually to look at consistency in tiers:

- High-value assets and the order chain — prioritize eventual correctness and auditability
- Derived data around the main flow — accept delayed convergence
- Reports, statistics and low-value replicas — allow looser eventual consistency

This is not compromise; it is avoiding designing every path at maximum strength, ending with both cost and latency out of control.

### Why sharding gets discussed too early so often

Many teams start talking enthusiastically about sharding before data volume has truly become a bottleneck. The problem is that sharding is not a performance panacea — it immediately brings these new costs:

- Primary keys and routing rules become complex
- Cross-shard queries and transactions get heavy
- Data migration and scaling become harder
- Troubleshooting and operations complexity rise

If the current problem is actually poor index design, hot and cold data mixed together, or an unreasonable query pattern, sharding early is just turning a simple problem into a complex one.

### When it actually becomes a real problem

Sharding truly enters the main agenda usually at these moments:

- A single table or single database is already near a real bottleneck
- Hot data and long-tail data differ enormously
- Single-machine resources and maintenance windows can no longer bear it
- Merging, cross-region and multi-region deployment bring a clear scaling requirement

At that point the focus of discussing sharding should not be "how to split the table name", but data routing, scaling strategy and migration cost.

### A more solid ordering of work

A fairly solid order is usually:

1. First fix the authoritative data boundary and the transaction boundary.
2. Then determine consistency requirements by tiering value.
3. Only then introduce sharding and more complex extension strategies, when genuinely needed.

The point of this order is not to let extension strategy take the lead over business boundaries.

### Common pitfalls

The most common error is treating transactions as the universal solution to all consistency problems. The second is rushing to shard before straightening out the authoritative boundary and the query model. The third is that after sharding, only the throughput gain is watched, not the cost of cross-shard queries, migration, audit and recovery — so the system is more distributed but harder to govern.
