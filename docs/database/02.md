# Relational and Non-relational Databases

## Category

database / storage selection. Node position: do not ask "relational or NoSQL" — tier the data and assign storage by failure cost and access pattern. Hybrid is the norm; the hard part is being able to state each tier's job clearly.

## Definition


When discussing database selection, the easiest error is to ask "relational or NoSQL, which one". The question itself is too coarse. A more practical way to ask: what consistency does this data need, how is it queried, how is it migrated and recovered, and can we accept the cost of schema evolution. Only once these are answered clearly do relational and non-relational carry engineering meaning.

In reality, most mature projects do not use a single storage. What actually has to be done is acknowledging that different data has different requirements, rather than chasing one storage model to rule the whole field.

## Problem

The question "relational or NoSQL" is too coarse — so coarse that selection turns into a product-religion debate. What really must be answered first: what is the cost of writing this data wrong once, what consistency is required, how is it queried, and will it need migrating in the future. Different answers, different storage — most mature projects end up on hybrid storage; the hard part is not picking one, but being able to state clearly who is source data, who is replica, and who is responsible for rebuilding.


### What relational databases are genuinely good at

Where relational databases are most valuable is usually:

- Strong transaction and constraint capability
- Clear data structures, with more stable semantics
- Friendlier to long-term assets and audit chains
- More mature expression of complex queries and multi-table relationships

So states that need clear boundaries and relatively strong consistency — character assets, orders, transactions, quest progress, reward-issuance records — are often better carried by relational databases.

### What non-relational storage is genuinely good at

Non-relational is not "a more advanced database", it is simply better suited to certain access patterns:

- Primary-key direct fetch and high-throughput KV access
- Schema-flexible data structures
- Large-scale log and document storage
- Easier horizontal scaling in specific scenarios

It is more like optimizing for a class of problem, not an automatic replacement for the relational database. If the business truly depends on strict transactions, strong constraints and long-term auditability, "more flexible" alone is usually not enough.

### Why many projects end up using a mix

Because a single game system usually has all of these requirements at once:

- The asset chain demands strong consistency and traceable accountability
- The online path demands low latency and high throughput
- The query side demands aggregation and multi-dimensional retrieval
- The historical side demands low-cost archival and offline analytics

Relational, KV, cache, search and data warehouse each excel at different parts. What truly matters is not whether they are mixed, but whether each tier's job has been stated clearly.

### The most important thing to look at first in selection is not the product, but failure cost

A more practical way to judge is usually:

- What is the cost of writing this data wrong once
- How much read latency is tolerable
- Are complex queries or transaction constraints needed
- Will it definitely need migration, merging or archival in the future

For example, a leaderboard cache lagging briefly and a player asset error have entirely different costs. The former can accept derived replicas and eventual consistency; the latter must usually be designed around authoritative storage.

### Schema flexibility does not mean low evolution cost

Many teams favor non-relational because early on the schema looks more flexible and iteration faster. But once it truly enters long-term operations, an unconstrained schema brings its own new costs:

- Field semantics drift
- Inconsistent historical data structures
- Backfill and migration scripts grow ever more complex
- Query logic accumulates patch after patch

So schema flexibility can help you run faster, but without extra governance it will also make later consolidation harder.

### A more solid approach to selection

A fairly solid approach is usually:

- Put long-term assets and high-value state first on the more strongly constrained, more easily auditable storage
- Put high-throughput, low-value, single-access-pattern data into lighter-weight models
- Treat query-optimization structures like search, leaderboards and reports explicitly as derived replicas
- Plan ahead for future migration and schema evolution, rather than looking only at current development speed

The key to this line of thinking is not conservatism — it is acknowledging that storage selection is essentially choosing which maintenance cost to bear in the future.

### Common pitfalls

The most common error is turning database selection into a product-religion debate instead of judging by data nature and failure cost. The second is prioritizing early flexibility and stuffing long-term assets into a storage model that lacks constraints. The third is mixing several storages without clearly stating who is source data, who is replica, and who is responsible for rebuilding, until the whole system loses explainability.
