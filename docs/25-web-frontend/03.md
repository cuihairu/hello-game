# 游戏引擎与 Cocos Creator

引擎解决的是「把渲染、场景、资源、适配这些共性设施组装起来」的工程问题。Web 游戏侧最主流的路线之一是 Cocos Creator：TypeScript 技术栈、对小游戏平台的构建链完善、2D 与轻量 3D 通吃。本页以它为载体讲清引擎的工作方式——这些概念（节点、组件、预制体、适配）在绝大多数引擎里都有对应物。

## 引擎替你解决什么

对照[第 8 章《客户端架构与引擎体系》](/10-client-engine-runtime/01)的结论：引擎是地基与公共设施，不是项目架构。Cocos Creator 这类引擎替你解决渲染器（2D/3D 双管线）、场景与节点管理、资源管线（导入、打包、释放）、UI 系统、屏幕适配、多平台构建；它不替你解决模块边界、网络层设计、状态管理与性能预算——那些仍是项目层的事。

## 节点、组件与场景

引擎把游戏世界组织成场景树：节点（Node）挂树，组件（Component）提供行为。一个节点可以有渲染组件（精灵、模型）、物理组件、以及任意多个自定义脚本组件。脚本组件有明确的生命周期：

```ts
import { _decorator, Component } from 'cc'
const { ccclass, property } = _decorator

@ccclass('Spin')
export class Spin extends Component {
  @property
  speed = 90 // 度/秒，可在编辑器面板调整

  update(deltaTime: number) {
    this.node.angle += this.speed * deltaTime // 2D 旋转
  }
}
```

把脚本挂到节点上即生效。`update` 每帧调用、`onLoad`/`start` 在初始化阶段调用一次。要点与误区同源：`update` 是热路径，每帧做节点查找（`getChildByName`、`getComponent`）是新手最贵的习惯——查找结果应在 `onLoad`/`start` 里缓存成成员。

## 预制体与对象池

预制体（Prefab）是「配置好的节点子树」的序列化模板：把做好的子弹、敌人、UI 条目存成预制体，运行时实例化。它是资源组织的原子单位，也是对象池的前提——频繁生成销毁的对象（子弹、飘字、列表项）应从池里取、用完还池，避免反复实例化带来的分配与初始化抖动。判断一个预制体设计好不好，看两件事：它是否只依赖自己的配置（而不是场景里的全局查找），以及实例化后是否还需要大量手工补配置（需要，说明模板切分不对）。

## 屏幕适配

Web 与小游戏平台共同的问题是：你不知道玩家用什么屏幕。适配的三层工具：设计分辨率（按一个基准尺寸做界面，引擎按策略缩放）、适配策略（`fitWidth`/`fitHeight`/`fitWidthAndHeight`，决定裁哪边、留哪边）、Widget 与锚点（把元素钉在父容器的边、角或中心，配合安全区处理刘海屏）。适配的验收标准很硬：最宽与最高的目标设备各过一遍，界面元素不裁切、不重叠、可点击区域不出安全区。

## 构建到小游戏平台

Cocos Creator 的构建链可以直接产出各小游戏平台工程与 Web 页面。构建阶段发生的事值得了解：资源按规则压缩与分包、脚本编译打包、生成平台适配层。构建产物超包体上限是最常见的发布阻塞，源头通常在未压缩音频与未分组纹理——资源分组（哪些进主包、哪些进远程包）要在项目早期定，而不是发布前补（对照[第 8 章 03 页资源系统](/10-client-engine-runtime/03)）。

## 常见误区

- **把引擎当架构**：所有逻辑堆在几个大组件里，节点树长成意大利面——引擎只给你承载点，分层仍要自己做（见本章 06 页）
- **`update` 里做查找与分配**：热路径三忌——查找、新建、日志
- **适配只测一种屏幕**：开发机屏幕就是全部测试集，上线才发现刘海屏按钮被吃掉
- **预制体互相依赖场景全局**：预制体离开原场景就不能用，说明依赖没收敛到配置与自身子树
- **用引擎不懂数值**：动画、缓动、物理参数全是数值工作，引擎把这些旋钮全暴露出来了——不懂就直接拍脑袋
