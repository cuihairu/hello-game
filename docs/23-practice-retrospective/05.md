# 个人查漏补缺清单

个人能力盘点比团队盘点更难，难点在于人天然会高估自己熟悉的东西。读过一篇讲网关设计的文章，和亲手扛过一次接入层雪崩，主观感觉上可能都是“懂网络”，差距要到独自面对故障的那一晚才显现。一份好用的自检清单，目标不是罗列知识点，而是用“能做成什么事”来度量每个维度，让薄弱处自己浮出来。

## 自检的难点在于高估熟悉度

能力错觉通常出现在两个位置：

- 读过但没做过：看懂了别人的推演，误以为自己具备同样的判断力。
- 做过但没想透：照着现成方案实现过一次，换一个约束条件就不会推了。

所以自检的标准动作不是问“这个我学过吗”，而是问三个更硬的问题：这个领域能不能独立设计方案，能不能独立排障，能不能把取舍讲给团队听。三问都过才算有底气，只过一问的位置往往就是薄弱点本身。

## 用能做什么来分级而不是学过什么

给每个维度打分时，常见的四级划分比“了解、熟悉、掌握”这类词更难自欺：

- 能讲清概念和常见取舍，但没有完整实践。
- 在别人设计的框架里能完成开发和排查。
- 能独立设计一个模块或子系统，处理边界和异常。
- 能主导跨系统方案，为容量、一致性和团队分工做取舍。

打分时值得诚实面对的一个事实是：级差拉开的维度通常比级别高的维度更值得投入，因为项目里最先出事的往往是没人真正负责的那一块。

## 主链路侧的维度

主链路是玩家每一次操作都会经过的路径，这里的短板最容易直接变成事故：

- 网络接入：长连接管理、弱网行为、心跳与重连、消息可靠性与顺序的处理思路。
- 同步与时间：帧推进、输入与状态收敛、预测与和解、断线追帧的取舍。
- 并发与运行时：进程内怎么组织逻辑推进，线程与任务怎么切分，锁竞争和背压怎么识别。

这一侧的自检可以很具体：拿当前项目里任意一条玩家操作路径，能否从客户端按键一直讲到状态落库，中间每一环谁权威、谁异步、坏了会怎样。讲不完整的段落，通常就对应一个薄弱维度。

## 状态与数据侧的维度

这一侧决定系统能不能长期活着，短板往往延迟兑现但代价巨大：

- 状态划分：临时状态、长期资产、派生数据能不能分清，各自的一致性要求是什么。
- 权威归属：每一类数据谁是事实来源，双写和派生反客为主的风险怎么防。
- 存储与迁移：合服、扩容、归档时数据结构撑不撑得住，补偿和对账怎么做。

自检的参考问题是：项目里任何一份数据，能否说出它的权威在哪、失效了怎么重建、出错后如何修复。答不出的那份数据，往往也是将来出资产事故最贵的那份。

## 运行与交付侧的维度

上线之后的生活质量，很大程度由这一侧决定：

- 可观测：日志、指标、追踪三者怎么配合定位问题，关键链路有没有 trace 串起来。
- 容量：从业务指标到机器数的推演会不会做，压测结论敢不敢直接信。
- 发布与回滚：灰度怎么做，回滚步骤是否可执行，配置和代码的发布顺序谁保证。
- 安全与风控：哪些输入天然不可信，风控和封禁的边界怎么处理。

这一侧的常见状态是“跟着做过”，跟随本身不产生判断力。自检时可以问：如果值班时告警响起，第一分钟看什么、第二分钟看什么，回答不出来就说明定位方法论还没建立。

## 协作与表达侧的维度

技术之外，这一侧往往决定同样的能力能发挥出几成：

- 需求翻译：能不能把技术约束翻译成产品同事可权衡的代价数字。
- 方案表达：能不能在评审里讲清取舍，而不是只讲结论。
- 复盘贡献：能不能从事故里提取流程改进，而不是停在修代码。
- 知识沉淀：自己的决策和踩坑有没有留下别人能读的记录。

这一侧容易被当作软技能忽略，但团队里最常被抱怨的两种人——说不清自己方案的人、说不清自己系统的人——问题都出在这里。

## 用项目经历校验而不是凭感觉

维度打分之后，值得用一段校验动作把分数落实：

- 每个自评较高的维度，找出一个自己完整处理过的实例，讲得出细节的才算数。
- 每个自评较低的维度，回想有没有其实接触过但当时没意识到的场景。
- 找不到任何实例的高分维度，自动降一级，因为那多半是阅读带来的错觉。

这个校验偶尔会产生反直觉的结果：有些人项目经验不少，但每个维度都讲不出独立设计的实例，说明一直在执行别人的框架；这本身就是重要的自检发现，指向的是争取设计机会，而不是再读十篇文章。

## 补短板的常见路径

发现短板后，不同类型的缺口有不同的补法：

- 概念型缺口：读文档和他人复盘，快速建立词汇和取舍地图，成本最低。
- 实践型缺口：找一个小场景完整做一遍，比如给现有系统补一条监控链路或做一次容量推演。
- 判断型缺口：只能靠参与真实评审和故障复盘积累，重点听别人怎么问问题、怎么权衡。

比较高效的长期习惯，是把自检和日常事件绑定：每次故障复盘后检查相关维度，每次接手新模块前先对照清单找盲区。跟随项目节奏的自检往往比年度盘点更诚实，因为记忆是新鲜的。

## 常见误区

- 用“学过”“了解过”给自己打分，分数普遍虚高，盲区全部漏检。
- 清单越列越长，变成知识点背诵表，和实际工作脱节。
- 只在跳槽或晋升前才盘点，平时从不与项目事件对照。
- 发现短板后用大量阅读回应实践型缺口，读完依然做不了设计。
- 只盯技术维度，协作与表达侧的短板长期无人认领。
- 自检结果从不转化为具体行动，第二年盘出同样的结论。

查漏补缺清单的真正用途，不是给自己一个能力评分，而是把“下一步学什么、做什么”这个模糊的问题变成明确的动作。清单诚实，方向就不会错得离谱；清单自欺，再努力也可能一直在最强的地方打转。
