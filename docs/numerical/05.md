# Drops and Probability Design

## Category

Numerical tree. Node positioning: drops and probability design — expectation is the only objective value-for-money convention, hard/soft pity, the variance knob, and disclosure and compliance as design inputs.

## Definition


Drops and gacha put randomness into a player's return curve: expectation (the mean) determines value-for-money, variance (volatility) determines emotion. Sections 4/5 of [Feature Note 02](/24-game-types-architecture/02-game-design) cover the implementation (random source, pity state machine, weighted roulette, pool splitting); this page covers the design side — how to compute expectation, how to set the pity ceiling, how to tune variance, all numbers recomputable.

## Problem

Once randomness is in the return curve, expectation determines value-for-money and variance determines emotion: a wrongly set pity means either a broken expectation (players can out-calculate it) or runaway variance (surprise turns to anger). Disclosure and compliance placed after the fact are a patch; placed into design inputs they are constraints.


### Expectation: The Only Objective Value-for-Money Convention

Expected drop = Σ(each outcome × its probability). Example: 2% per single pull for the target item, with no pity the expected pull count = 1/0.02 = **50 pulls** — this is the bill players and reviewers will both compute, and no "value-for-money" claim can escape it. Multi-layer randomness (deciding rarity first, then the entry) must be unfolded layer by layer into a joint probability before computing expectation, avoiding "each layer looks not-a-loss, but together you lose half".

### Hard Pity: Truncate the Tail, Pull Expectation Forward

A hard pity (guaranteed on the Nth pull) changes the probability distribution, not the per-pull probability. Work a recomputable bill: per-pull probability p=2%, hard pity at 50 pulls. Let q=0.98; the probability of 49 empty pulls in a row is q^49 ≈ **37.2%**; expected pulls = Σ(weighted hits within the first 49 pulls) + 50×37.2% ≈ 13.0 + 18.6 = **about 31.6 pulls**. Compared with 50 pulls without pity: pity cuts off the long tail, moving expectation from 50 down to 31.6 — **the shorter the pity, the closer expectation lands toward the pity number rather than the no-pity expectation**. When designing pity, compute expectation first, then set the number: the farther the pity number is from the no-pity expectation, the larger the expectation subsidy actually given.

### Soft Pity: The Smooth Version of Rising Probability

A soft pity (probability rises gradually after consecutive misses, e.g. +2% per pull starting from pull 30) is smoother than a hard pity — no wasteful feel of "49 empty pulls, then the 50th is a giveaway" — but its expectation is a series of cumulative probabilities with no closed-form shortcut, so acceptance uses a simulation script (sample ten thousand times and take the mean, keeping error controllable). Combining soft and hard is a common shape: soft pity governs feel (the more you pull, the closer), hard pity governs the cap (guaranteeing the worst case has a floor). **The state-machine implementation of both pity types is in Section 4.3 of Feature Note 02.**

### Variance: The Knob Between Surprise and Fairness

The same expectation can have completely different distribution shapes; choose by gameplay goal:

- **Low variance** (short pity, strong probability increment): pursues "predictable return", suited to progression resource distribution
- **High variance** (small probability, big reward): pursues "legendary moments", suited to gacha and rare drops — but the worst case must be floored by pity
- **Pseudo-random distribution** (probability rises on consecutive misses, resets after a hit, Dota-style): flattens the extreme experience of "missing in a row", the feel optimizer for competitive gameplay (implementation and seed management in Sections 3.3/4.2 of Feature Note 02)

Drop pool design has one more discipline: **split pools to prevent dilution** (Section 5.3 of Feature Note 02) — putting items of different value into one big pool is equivalent to diluting the probability of the rare rewards; set pools by value tier, with each tier's expectation disclosed separately.

### Disclosure and Compliance Are Design Inputs, Not After-the-Fact Patches

Probability disclosure (publicizing probabilities and pity rules of gacha gameplay) is already a mandatory requirement on most platforms (compliance red lines overview in [Chapter 17](/server/security/)). The design-side implication: **the disclosed probability is the probability players will use for decisions** — the disclosed convention must strictly match the implementation (see the audit and legal requirements in Sections 4.4/4.5 of Feature Note 02), "disclosed 2%, actual 1.5%" is not just a compliance breach but self-destruction at the trust level. Pity rules, total expectation, pool composition — all should be written at the "will be published" standard from the design-document stage onward.

### Common Pitfalls

- **Computing only the per-pull probability, not total expectation**: players compute "how much money / how many pulls to get it", and the design must use the same convention
- **Pity number pulled out of thin air**: set "50-pull pity" first and back-solve probability, expectation subsidy runs out of control — the order should be reversed
- **High variance with no floor**: with no floor on the worst case, public backlash will detonate on some "zero-spend unlucky player"
- **Pools ever merged bigger**: a big pool dilutes the value feel of core rewards, and players feel "what I pull is worth less and less"
- **Two books between disclosure convention and implementation convention**: audit catching it is an incident, players calculating it is a trust crisis
