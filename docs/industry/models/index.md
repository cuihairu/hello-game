# 2. 游戏类型与问题模型

游戏项目不能只按玩家熟悉的品类名词来理解，也不能一上来就跳到抽象技术术语。更稳妥的做法是承认两层事实同时存在：第一层是玩家、市场、团队日常沟通中的玩法类型；第二层是这些玩法背后真正主导架构的技术问题模型。

这一章的目标，就是把这两层关系讲清楚。因为真正决定网络、同步、服务组织、数据治理和运营成本的，通常不是“它叫不叫 RPG、FPS、SLG”，而是下面这些问题：

- 玩家是否共享同一份实时状态。
- 几十到几百毫秒的时差会不会直接改变结果。
- 关键状态是一局内闭合，还是要长期积累几个月。
- 最贵的故障是体验故障、资产故障，还是平台协作故障。
- 压力首先爆在服务端、客户端，还是支付与渠道链路。

如果这些问题没有先分清，团队就很容易两边都做错。一种错法是只按品类名词讨论技术，最后把所有“RPG”都做成一个样；另一种错法是只讲抽象模型，不给项目一个能落回现实玩法的入口。

本章的结构就是为了解决这个断层：

- 先用常见玩法类型建立直观入口。
- 再用可落地的分类方法把项目映射到问题模型。
- 然后分别展开几类最常见、最能主导架构的问题模型。
- 最后说明真实项目为什么往往是组合型，而不是单一标签。
