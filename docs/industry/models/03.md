# Hard-Real-Time Competitive Game Problem Model

## Category

industry / models subtree. Node positioning: hard-real-time competitive problem model—input timing differences directly decide the outcome, synchronization becomes a first-class problem, and feel and fairness are inseparable.

## Definition


The key to hard-real-time competitive games is not "has PvP," but `the timing difference between players' inputs is enough to directly change the outcome`. MOBA, FPS, fighting, RTS, racing, and high-tempo action combat are all closer to this class. As long as a difference of tens of milliseconds to one or two hundred milliseconds is enough to affect hitscan, positioning, reaction, first/second strike, and final win/loss, this model will overwhelm a large number of other technical topics.

Its biggest difference from an ordinary room contest is not whether it is multiplayer, but rather that `timing precision itself is part of the gameplay`. This means synchronization, prediction, adjudication, replay, and anti-cheat are no longer supporting facilities, but part of the core experience.

## Problem

When a tens-of-milliseconds input difference is enough to rewrite the outcome, synchronization, lag compensation, and anti-cheat rise from implementation details to decisive design. Handing "feel" to the client and "fairness" to the server as separate concerns will collapse on both ends.


### Why these projects push the problem onto the synchronization system

Hard-real-time competitive projects naturally have a conflict:

- Players want input to have feedback immediately, otherwise the feel collapses.
- The system must also guarantee that results are trustworthy, otherwise fairness and anti-cheat collapse.

These two requirements naturally pull against each other. As long as the project has the following things, the problem quickly escalates:

- Hit windows are very short
- Positioning and body position affect the outcome
- Skill timing decides win/loss
- Multiple players in the same arena strongly influence each other
- Players are extremely sensitive to disputes like "I clearly dodged but it was judged a hit"

This is why the most core problem of hard-real-time projects is usually not "how many features," but rather "how time, input, and adjudication together establish a trustworthy world."

### What the technical primary path usually is

The primary path of this kind of project is usually no longer "match into a room and that's it," but rather:

1. Input capture and local feedback
2. Network transport and time alignment
3. Synchronization model organizes in-session state
4. Server or shared logic performs authoritative adjudication
5. Client prediction, compensation, and correction
6. Replay, spectating, reporting, and anti-cheat provide post-hoc evidence

In other words, the primary path of a hard-real-time project is a path of "co-constructing experience and trustworthiness." Optimizing only one segment means other places immediately push back.

### What do these projects fear first

The most expensive live failures of hard-real-time projects are usually not missing features, but the following experience and fairness incidents:

- Obvious input latency, sluggish feel
- Multi-endpoint state desync
- A large number of hitscan and dodge disputes
- Players are naturally disadvantaged under certain network conditions
- Client tampering, hacks, accelerators, or script cheating amplified
- Replay and logs cannot reconstruct the dispute process

The cost of incidents for this kind of project is usually very high, because they directly destroy players' trust in "this game's win/loss is trustworthy."

### Common synchronization solutions, and why they become first-class here

Hard-real-time projects are forced to answer the synchronization model question early. The common paths are roughly three classes:

### Server-authoritative state sync

The server holds the final state; clients send input or requests and do limited local prediction.  
The benefit is that anti-cheat and arbitration converge more easily; the cost is that a lot of effort must be invested in fixing local feel, interpolation, and correction.

### Input lockstep / frame sync

Multiple endpoints advance logic around shared input and a shared frame number.  
The benefit is that theoretically consistency and replay are more natural; the cost is that requirements for determinism, timeouts, default input, reconnection, and frame catch-up are extremely high.

### Hybrid solution

Local objects or local state are organized by frame, and other parts use authoritative state sync; or local feed-forward plus server adjudication are used together.  
The benefit is more realistic; the cost is that when boundaries are not drawn clearly, you are most likely to bear the complexity of both stacks at the same time.

There is no naturally strongest solution here, only whether it matches the project's problem model.

### Client and server responsibilities must be fixed early

In hard-real-time projects, one of the most dangerous things is "making it work first" in the early phase and leaving responsibility boundaries for later. More reliable projects usually make clear very early:

- To what extent the client is allowed to pre-render
- Whether the server does complete authoritative adjudication at all
- Who decides hitscan, displacement, resource deduction, and death
- Which data chain disconnects, reconnection, replay, and spectating depend on
- Whether cheat auditing is real-time blocking or post-hoc audit

Once these questions are deferred, rework is not just one layer, but combat, network, skills, logs, and operations all going back to the oven together.

### Why "feel" and "fairness" cannot be discussed separately

Many discussions like to split these two things, but in hard-real-time projects they are fundamentally inseparable. Because:

- Good-feeling local feed-forward may widen the cheat surface.
- Extremely strict authoritative adjudication may make input feedback very slow.
- Compensation strategies can accommodate players with poor networks, but may also make players with good networks feel the adjudication is unfair.

So what should really be discussed is not "feel first or fairness first," but rather:  
`which things must guarantee fairness first, and which things can trade presentation techniques to buy back the feel.`

This is why later in this book you must continue looking at synchronization models, frame sync, prediction/correction, and replay adjudication, and cannot stop at gameplay tags.

### The toolchain is not a bonus in this kind of project

Hard-real-time projects without a toolchain are almost flying blind. At minimum you need:

- Tick and frame cost metrics
- Input and authoritative result logs
- State hash and divergence location tools
- Replay and frame-level jump tools
- Reconnection and frame catch-up metrics
- Anti-cheat and abnormal behavior evidence chains

Without these, all live disputes will eventually return to "I feel there is a problem here," rather than engineering evidence.

### When does this model dominate progression and monetization

Many projects have progression systems, season systems, in-game shops, and events, but as long as the core gameplay is hard-real-time combat, technical priority usually still has to yield to in-session timing and adjudication. The reason is simple:

- If an event is done poorly, the version can be tuned slowly.
- If monetization has a problem, you can compensate first.
- But once in-session synchronization, hitscan, and adjudication become untrustworthy, players will directly feel "this game cannot be played."

This is why once the hard-real-time model is established, many peripheral systems must make way around it.

### What typical misjudgments look like

### Misjudging "has PvP" as hard-real-time

Many projects do have combat, but the outcome is not highly dependent on millisecond-level operations. For example, many card contests, turn-based contests, and asynchronous attack records do not need to design synchronization and adjudication to the standard of MOBA or FPS.

### Choosing a solution only from theoretical fairness

Some solutions look very fair on paper, but the team has no ability to maintain determinism, hash verification, replay, and reconnection tools long-term, and ends up building a theoretically correct, live-unmaintainable system.

### Over-relying on client judgment

To pursue feel, hitscan, resources, control, and death are largely moved forward to the client. It feels great locally, but the cheat surface and dispute handling cost rise sharply.

### Conclusions closer to best practice

The more reliable approach for hard-real-time competitive projects is usually not pursuing a "most advanced solution," but first writing the main contradiction clearly:

- Where is the tolerance boundary for operation latency.
- Who exactly holds adjudication.
- Which states allow prediction, and which must be authoritatively confirmed.
- Which evidence chain do disconnect recovery, replay, reporting, and anti-cheat depend on.
- Does the team truly have the ability to maintain the long-term cost of the chosen synchronization model.

As long as these questions are not fixed first, the later skill, combat, network, and data design will all drift.

### Common pitfalls

The most common pitfall is choosing a synchronization model only from "theoretically fairest," ignoring whether the project team can actually make determinism, numerical consistency, and debugging tools solid. Another pitfall is over-relying on client-side local judgment to pursue feel, pushing up the cheat surface and dispute handling cost. The third pitfall is treating replay, reporting, and spectating as bolt-on features, leaving the underlying evidence chain never laid down.
