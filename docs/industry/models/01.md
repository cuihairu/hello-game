# Methods for Classifying Game Types

## Category

industry / models subtree. Node positioning: six questions classify the project—do they share real-time state? does timing precision decide the outcome? does state close? what is the most expensive failure? is the platform part of the primary path? which side breaks first?

## Definition


If game types only serve market communication, they are not enough to support technical design. A classification method that is truly useful technically must help the team answer three things: where the primary path is, where the most expensive failure is, and what the first phase of architecture should pay for first.

So this does not intend to repeat the encyclopedia definitions of "RPG, FPS, SLG, card, MMO," but directly gives a classification framework better suited to project initiation, review, and technical selection.

## Problem

Classifying by subject matter cannot support technical design; a useful classification must answer where the primary path is, where the most expensive failure is, and who the first phase pays for. The six questions translate genre language into engineering language and are the common entry point to the six problem models that follow.


### Do not classify by subject matter; classify by failure mode

From an engineering point of view, whether a classification method is valuable depends on whether it can directly expose the places where the system is most likely to fail. For example:

- A project that most fears input latency, desync, adjudication disputes, and hacks is closer to a hard-real-time problem.
- A project that most fears failed game starts, being unable to return after disconnect, wrong settlement, and dirty room state is closer to a room problem.
- A project that most fears wrong issuance, missed issuance, event incidents, data contamination, and compensation running out of control is closer to a long-cycle progression problem.
- A project that most fears lost orders, duplicate fulfillment, reconciliation mismatches, and failed risk control is closer to a platform and economy problem.
- A project that most fears dropped frames, memory blowups, loading avalanches, and broadcast overload is closer to a high-frequency object and heavy presentation problem.

If a classification method can only tell you "this looks like some kind of game" but not "where the system is most likely to die," then its help to architecture is limited.

### Classify the project with six questions

When you take on a new project, you can ask the following six questions in a row.

### 1. Do players share the same real-time state

This is the first question, because it is the fastest way to sort a project from "mainly a data and configuration problem" into "must handle synchronization and shared state problems."

- If one player's action must change the world another player is currently seeing within a few hundred milliseconds, the project has already entered the room-based, hard-real-time, or persistent online world regime.
- If players mainly influence each other through leaderboards, battle reports, trading, gifting, alliances, and asynchronous progress, the project is more likely close to long-cycle progression or platform type.

The point of this question is to first distinguish "a shared real-time world" from "shared long-term results," because their architecture costs are entirely different.

### 2. Is the outcome decided by timing precision

Not all multiplayer combat is hard-real-time. The most direct way to judge is: `does a 50-to-150-millisecond input difference suffice to significantly change the outcome.`

- If it does, then synchronization model, prediction, adjudication, replay, and anti-cheat must enter core design early.
- If it does not, then it may just be a room session, a turn-based contest, or a progression system with a competitive outer shell, and need not directly adopt the most expensive real-time architecture.

This question blocks many "if there is PvP then build it like MOBA" misjudgments.

### 3. Does the core state close within a session, or does it accumulate long-term

This question decides whether the system is more like a session-based system or more like a long-term asset system.

- After a game ends, most runtime state can be destroyed, leaving only scores, records, and rewards—this usually is closer to room-based or hard-real-time.
- A single wrong issuance, misconfiguration, or wrong settlement affects players for weeks or even months—this usually is closer to long-cycle progression.
- The world state itself exists long-term, with players and scenes, organizations, and ecosystems persisting—this usually is closer to persistent online world.

When judging, do not just ask "is there nurturing," but ask "is the player's most expensive state in-session or out-of-session."

### 4. Is the most expensive failure an experience failure or an asset failure

This step helps the team decide whether the system prioritizes optimizing "low latency" or "strong audit."

- When experience failure takes priority, the project fears stutter, drift, being unable to return after disconnect, desync, and failed migration.
- When asset failure takes priority, the project fears lost orders, wrong issuance, quest chaos, inventory contamination, event incidents, and rollback boundaries running out of control.

Many discussions are confused because these two classes of failure are compared on the same layer. They are both important, but they dominate system design in entirely different ways.

### 5. Is an external platform part of the primary path

The question is simple: without channels, payment, advertising, social platforms, creator ecosystems, or external moderation, can this product still stand as a whole?

- If yes, the platform is more peripheral support.
- If no, platform and economy capabilities have already entered the mainline.

This means accounts, orders, callbacks, risk control, reconciliation, moderation, and adaptation layers are no longer integration work bolted on before launch, but system capabilities that need to be formally modeled.

### 6. Does pressure break through on the server side or the client side first

This is the question a pure server-side perspective most easily ignores. The way to judge: if the number of online players stays the same but the number of on-screen objects, skill effects, asset sizes, and script volume are doubled, does the project die first?

- If yes, then high-frequency object and heavy presentation problems are already one of the dominant constraints.
- If no, the main contradiction may still be in synchronization, data, or the platform path.

This step avoids misjudging client-side throughput and resource organization problems as pure server-side scaling problems.

### A practical-enough classification table

| Project is more like this | Dominant model | What to design first in phase one | Most feared live incident |
| --- | --- | --- | --- |
| Multiplayer games form quickly; after settlement most in-session state is cleared | Room-based session | Matchmaking, room formation, lifecycle, reconnection, settlement | Cannot start games, cannot return, wrong settlement |
| Input timing differences directly change the outcome | Hard-real-time competitive | Tick, synchronization model, prediction/correction, adjudication, replay | Desync, misadjudication, hacks, disputes with no evidence |
| World and player relationships persist long-term | Persistent online world | Zone sharding, migration, scene organization, recovery, control plane | Scene hangs, migration loses state, merge/cross-server incidents |
| Long-term assets and events drive retention | Long-cycle progression and async interaction | Asset model, config pipeline, reward path, compensation/repair | Wrong/missed issuance, event incidents, data contamination |
| Growth and revenue depend on platforms and external ecosystems | Economy/platform | Accounts, order state machine, callback compensation, reconciliation, risk control | Lost orders, duplicate fulfillment, risk control failure |
| On-screen objects and presentation density are extremely high | High-frequency object and heavy presentation | Object lifecycle, asset budgets, network pruning, performance budgets | Dropped frames, memory blowups, loading avalanches, broadcast overload |

If a project hits multiple rows, that does not mean the classification failed; on the contrary, it means the project is closer to reality. The key is to keep judging priority and secondary, rather than trying to find a single label that covers everything.

### A directly usable judgment flow

When actually doing a design review, you can triage in the following order:

1. List the three core high-frequency behaviors of players.
2. Judge whether these behaviors depend on real-time shared state, long-term assets, or external platforms.
3. Find the failure path that is "most expensive and hardest to roll back."
4. Judge whether this path fears latency, misadjudication, lost state, wrong asset issuance, or external dependency failure.
5. Determine a dominant model for the project, then mark one or two secondary models.
6. In phase one, pay the highest cost only around the dominant model; for secondary models, first lay down boundaries and extension reserves.

### Common misjudgments

- Equating "has PvP" directly with hard-real-time, and over-investing in unnecessary synchronization complexity.
- Treating a progression product as ordinary CRUD, ignoring the long-term cost of audit, compensation, and configuration incidents.
- Treating platform and economy problems as end-of-launch cleanup, so account, order, and reconciliation systems stay out of control long-term.
- Treating heavy-presentation projects as late-stage optimization problems, setting no budgets early and then only being able to fight local fires later.

The real value of a classification method is not to make the project sound better, but to let the team know early which layer should absorb money, time, and complexity first in phase one.
