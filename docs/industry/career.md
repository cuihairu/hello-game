# 职业地图

## Category

industry / 横向节点 / 职业地图。一句话：把「行业里有哪些岗位、按什么分工、如何成长流动」铺成一张可对照的图——个人盘点与团队招聘用同一张图。

## Definition

industry 树回答「项目是什么」，本节点回答「项目由哪些人做、能力如何组合成岗位、岗位如何随项目类型迁移」。地图按四族组织——策划、程序、美术与音频、运营发行——每族对应项目三大输入（玩法类型、平台、商业形态，见 [树根总览](./index.md)）的一角。它与 [retro/05 的四维度自检](/production/retro/05) 互为镜像：retro/05 是个人侧的能力盘点，本页是行业侧的结构口径——自检的每一项短板，都要落回这张图上的某个岗位要求才有意义。

## Problem

- **按职衔理解职业**：同一职衔在不同项目类型下职责差异巨大——房间制小团队的「服务端」一人扛全部，MMO 大团队的服务端按域拆成五六个岗位。没有项目类型做坐标，职衔对照表就是误导。
- **成长只剩纵向一条路**：行业实际存在大量族间迁移（程序转 TA、策划转制作人、客户端转引擎），地图上没有流动方向，个人规划就退化成「跳槽升职级」单行道。
- **个人盘点没有行业锚点**：闭门自检出的「短板」可能根本不在这个岗位的要求清单里，也可能漏掉了岗位真正吃重的能力——对照错了，补短板就补在没用的地方。
- **团队组建照抄 JD**：不看项目类型的主导矛盾就招人配岗，招来的能力结构与项目的真实需求错位，复盘时才发现「人很优秀，配置不对」。

## Algorithm

### 岗位四族 × 项目输入

| 族 | 核心产出 | 对应项目输入 | 与相邻族的边界 |
|----|---------|-------------|---------------|
| 策划族 | 玩法定义、数值、系统、关卡 | 玩法类型（主导矛盾） | 定义玩法但不定实现口径（程序族的裁决边界见 [前后端边界](/industry/methodology/05)） |
| 程序族 | 客户端、服务端、引擎、工具 | 平台（技术边界） | 族内按 client/server 树的问题域分工，不按职衔分工 |
| 美术与音频族 | 原画、3D、动画、特效、TA、音频 | 表现与性能预算 | TA 是族间翻译层：美术语言的性能预算翻译成程序语言的实现约束 |
| 运营发行族 | 版本节奏、渠道、商业化、用户 | 商业形态（版本与运营节奏） | 版本节奏反过来约束技术树的发布与热更设计（[production](/production/) 的输入） |

### 成长与流动的三个口径

- **纵向**：族内职级序列（初级 → 资深 → 专家/管理），能力的判据是「能独立定义并交付多大范围的问题」，不是年限。
- **横向迁移**：族间流动的真实成本 = 相邻族的口径差。程序转 TA 贵在美术语言，策划转制作人贵在商业与组织——迁移方向要在地图上先看清楚再投时间。
- **项目类型迁移**：换项目类型比换岗位更贵——主导矛盾变了（[问题模型](/industry/models/) 六型各不相同），四族内部的配置与吃重能力都要重排。

### 与个人自检的接口

[retro/05 四维度自检](/production/retro/05) → 对照本页四族的岗位要求 → 短板落位 → 按补短板路径学习：程序族的技术面在 client、server、database 各树，策划族的口径面在 design、numerical 树——学习资源按族归位，不做全站漫游。

## Used By

招聘与团队组建（按项目类型反推四族配置）；个人成长规划（自检的行业锚点与学习资源归位）；晋升与职级评审（能力判据的横向对齐）；转岗与转行决策（迁移成本与口径差评估）；外包边界约定（[engines/03 的外包判断](/client/engines/03) 落到岗位族上）。

## Related

关系链：岗位四族 → 项目输入映射 → 成长与流动 → 自检接口 → 团队组建口径。逐段回答「为什么需要下一个」：

- 先有族再有输入映射：族的划分本身就该由项目输入决定，不是由招聘市场的话术决定。
- 输入映射定了才谈成长：纵向、横向、类型迁移三条路的成本都从族与输入的关系里算出来。
- 成长口径要接自检：个人盘点不落回岗位要求，就是没有坐标的练习。
- 自检过了才到组建：同一张图反过用，就是团队配置的依据。
