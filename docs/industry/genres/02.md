# Hard-Real-Time Competitive

## Category

industry / genres subtree. Node positioning: hard-real-time competitive topic — a genre quick overview of how time difference decides fairness and game feel.

## Definition


The keyword for hard-real-time competitive games is not "PVP" but that the time difference between player inputs is small enough that latency, jitter, packet loss, and cheating directly affect fairness and game feel. MOBA, FPS, fighting games, racing, and sports competition may all fall into this range, just with different sync approaches.

## Problem

The keyword is not PVP but that the input time difference is small enough: latency, jitter, packet loss, and cheating directly decide fairness. MOBA / FPS / fighting / racing differ in where they land and how they sync, but "sync is a first-class problem" is the same.


### Where These Games Are Actually Hard

The hardest part of these products is not writing out the rules, but making every player see a world that is "consistent enough, timely enough, and not easily exploitable by cheating." The core conflict here is very hard:

- Players want local feedback to happen immediately
- The system needs server authority to guarantee fairness
- Networks inherently have latency and packet loss

These three cannot all be perfectly satisfied at once, so hard-real-time projects are always an art of tradeoffs, not a single technology selection question.

### Where Architecture Focus Usually Goes

- The sync model is the first decision: lockstep, state sync, frame sync, server-authoritative simulation — each affects the engine, combat design, and debugging tools.
- The network link is part of the main gameplay: weak-network strategy, interpolation, prediction, rollback, packet filling — these are not peripheral optimizations but core experience.
- Anti-cheat must come first: the heavier the client, the later the settlement, the weaker the authority, the larger the cheating space.
- Spectating, replay, and arbitration are often not accessory features: they determine whether you can locate production problems and handle disputes.

### Common Approaches and Tradeoffs

Server-authoritative simulation is the safer mainstream route, because it handles fairness and cheating problems more easily, but the cost is higher server expense, and combat logic, toolchain, and replay systems all become heavier.

If you adopt frame sync or something closer to lockstep, the advantages are relatively controllable bandwidth and higher client presentation consistency; the downside is very demanding requirements on client determinism, version consistency, and weak-network tolerance. As soon as one link is unstable, production will show drift, divergence, and hard-to-reproduce bugs.

### Common Pitfalls

- Only watching average latency, ignoring jitter and the long tail. When players complain that "game feel is bad," it is usually not because the average is high, but because it is unstable.
- Getting combat out first, then adding sync and anti-cheat. Usually it cannot be added; you can only start over.
- Treating weak-network optimization as a client detail. In fact it affects skill design, collision strategy, hit detection, and even numerical balance.
