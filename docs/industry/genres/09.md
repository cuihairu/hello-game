# Roguelike and Roguelite: Definition, Berlin Interpretation, and Design Patterns

## Category

industry / genres subtree. Node positioning: the Roguelike deep-dive — what makes a game a roguelike, the Berlin Interpretation's canonical features, the roguelite split, and the design patterns that make run-based games work.

## Definition

The term **Roguelike** was coined for games that share mechanical DNA with *Rogue* (1980). The canonical definition is the **Berlin Interpretation** (2008), drafted at the International Roguelike Development Conference. It lists both "high-value" factors (required, by the interpretation's own framing) and "low-value" factors (commonly present but not defining).

The high-value factors, per the Berlin Interpretation:

1. **Random environment generation** — the game world is randomly generated to increase replayability; item appearance and placement are random, monster appearance is fixed but placement random.
2. **Permadeath** — you are not expected to win with your first character; you start over from level one on death (saves may exist but the save file is deleted on load).
3. **Turn-based** — each command corresponds to one action/movement; the game is not sensitive to time, you can deliberate.
4. **Grid-based** — the world is a uniform grid of tiles; monsters and player occupy one tile regardless of size.
5. **Non-modal** — movement, battle, and other actions take place in the same mode; every action is available at any point.
6. **Complexity** — enough complexity to allow several solutions to common goals.
7. **Player vs. world** — no monster-vs-monster relations; player is the only actor.
8. **Symmetry** — rules that apply to the player apply to monsters: they have inventories, use items, cast spells.
9. **ASCII display** — the traditional display represents the tiled world with ASCII characters.

The low-value factors (commonly present, not required): health points, level progression, item identification, hunger/consumption, etc.

## Roguelite: The Split

Modern usage distinguishes:

| | Roguelike (Berlin) | Roguelite |
| --- | --- | --- |
| Permadeath | Full run reset | Full run reset |
| Meta-progression | None (or minimal) | **Persistent unlocks between runs** |
| Run structure | One run = the whole game | One run = one attempt; unlocks accumulate |
| Examples | Rogue, NetHack, Angband, Brogue | Dead Cells, Hades, Slay the Spire, Spelunky |

The roguelite split adds an **out-of-run progression layer** (unlocks, codex, meta-currencies) while keeping the in-run permadeath. This is the single most commercially significant adaptation — it preserves the tension of permadeath while giving players a non-frustrating sense of progress across failures.

Cloudfall Studios' analysis reframes the two irreducible traits as **Procedural Content** (each run randomly generated) and **Permachoice** (outcomes cannot be undone, including death). "Permachoice" rather than "Permadeath" deliberately allows meta-progression so long as those decisions too cannot be undone — a cleaner frame for modern roguelites.

## Why Permadeath Works

Permadeath redefines the failure state. Instead of "play through and retry failures," the player is expected to complete the run without dying. Death is not a temporary setback but **part of the cycle of play**: the vast majority of attempts end in death, so "You Lose" reads as "Try Again" with what you learned.

The design benefits:

- **Visceral stakes** — without reload or lives, every decision carries critical meaning; precarious positions are heart-pounding.
- **Repetition is the design** — the game is built for attempts, so restarting is less onerous than in a checkpoint game.
- **Learning through failure** — each run teaches something that makes the next run deeper, not merely repeated.

The countervailing risk: if the game punishes the player for the *game's* mistakes (an unfairly generated unwinnable map) rather than the player's, permadeath reads as cruelty. The best roguelikes make the player feel punished when they misplay, not when the generator fails them.

## Procedural Generation as the Engine of Replayability

Procedural generation means the level design is not hardcoded — it is generated from a template with randomization each run. The player cannot memorize the level, so each playthrough is an exploration of new space; the general *form* is stable (e.g., a dungeon is always rooms and corridors) while the *specific arrangement* varies.

Two design benefits:

1. **Replayability** — the field of play is different every time; the player adapts to the underlying pattern rather than memorizing a specific layout.
2. **Blind exploration** — no memorizing "what's behind the next door," but you develop a sense of what *might* be behind it.

The danger: too much randomness makes difficulty vary wildly, producing unwinnable or trivial runs. Calibrating the generator so all maps are fun and completable is a real engineering effort — this is the architectural crux of a roguelike (see the Design Patterns section).

## The Architecture-Side View: What a Roguelike Demands

From the genre-coverage cross-reference, the Roguelike genre asks first for these feature components:

- **Random seeds and reproducibility** — deterministic RNG so runs can be replayed, seeded, and audited.
- **In-run / out-of-run state split** — the run state (resets on death) vs. the meta state (persists).
- **Unlocks and codex** — the meta-progression layer.

The dominant problem model is a combination of **room-based session** (each run is a session) and **long-cycle progression** (the meta layer).

For a server, the roguelike architecture questions are:

- **Where does the RNG live?** Deterministic, seeded, and reproducible is the requirement — the same seed must produce the same run, which means the seed is part of the run record.
- **What resets and what persists?** The in-run state (inventory, HP, map) resets; the out-of-run state (unlocks, codex, currencies) persists. The boundary must be explicit.
- **Is the run authoritative?** For single-player runs the client can hold state, but for any competitive or shared element (daily runs, leaderboards, seeded runs), the server must be authoritative and the seed must be server-issued.
- **Anti-cheat on runs** — if runs are ranked, the seed + result must be verifiable server-side.

## Design Patterns That Make Run-Based Games Work

These are the patterns that recur across commercially successful roguelikes/roguelites:

| Pattern | What it does | Example |
| --- | --- | --- |
| Seeded RNG | Deterministic, auditable randomness | Every Berlin roguelike |
| Pity / streak breaker | Guarantee rare drops after N failures | Modern loot-driven runs |
| Meta-unlock economy | Currency/items that persist across deaths | Hades, Dead Cells |
| Build diversity | Multiple viable builds per run | Slay the Spire, Binding of Isaac |
| Fair-but-unknown information | Show enough to decide, hide enough to surprise | Fog of war, item ID |
| Run-length design | Session-length runs with a natural end | 20-40 min runs, not infinite |
| Grace systems | Mechanics that soften unlucky death (revive, mercy) | Many modern roguelites |
| Daily/seeded challenge | Fixed seed for all players, leaderboard | Slay the Spire dailies |

The tension to engineer around: **difficulty variance**. A run-based game lives or dies on whether death is the player's fault or the generator's. Pity, grace, and fair-information systems all push toward the former.
