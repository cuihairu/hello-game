# An Analysis Method from Gameplay to Architecture

## Category

industry / methodology subtree. Node positioning: a five-step analysis method — player behavior → state ownership → path timeliness → deployment and organization → failure recovery — pushing from the gameplay loop to the technical implementation, not reverse-deriving from components.

## Definition


The easiest mistake in game architecture analysis is reverse-deriving requirements from technical components: first discussing whether to use microservices, whether to use ECS, whether to use Actor, whether to use Redis, and then looking for scenarios that fit these solutions. The safer order is the opposite: start from the gameplay loop and push layer by layer to state, paths, boundaries, and technical implementation.

## Problem

Reverse-deriving requirements from technical components (first debating whether to use microservices/ECS/Redis, then looking for scenarios) is the most common analysis illness: solution first, problem mismatch. Analysis must start from what players do repeatedly and push layer by layer to state ownership, path timeliness, the way things are organized, and recovery design.


### Step one: look first at what players do repeatedly

What architecture serves is not a "feature list" but high-frequency behavior. When analyzing, grab the core loop first:

- the player repeatedly starts a match, settles it, and starts another within a short time
- or stays inside the same world for a long time, moving, interacting, and growing continuously
- or mainly revolves around progression, collection, management, campaigns, and asynchronous social play

The core loop decides where the busiest path of the system is, and also decides where failures are least tolerable. For a room game, entering a room, starting a match, syncing, and settlement are the life-and-death links; for a progression product, login, character loading, configuration refresh, reward distribution, and campaign settlement matter more.

### Step two: identify state ownership

The next question is not "which database it goes into" but "who holds the final say over this state." Common states roughly fall into:

- transient interaction state: in-match position, skills, bullets, collisions, countdowns
- session state: room membership, matchmaking progress, temporary Buffs, in-match disconnect information
- long-term persistent state: character attributes, inventory, quests, payment records, leaderboard points
- platform and governance state: real-name verification, addiction prevention, risk control tags, punishment records, customer support audit

Once state ownership is defined clearly, many technical questions settle into place by themselves. In-match combat state is suited to being advanced by an authoritative battle node; long-term character assets belong in an auditable data store; platform governance state usually must not be scattered across business services to be modified at will.

### Step three: identify path timeliness

Not every request is worth running through the same expensive architecture. It helps to distinguish:

- paths that must give feedback at millisecond level
- paths that can be handled at hundreds of milliseconds to seconds
- paths that can land asynchronously and be reconciled later

Once the timeliness is mixed together, the system either over-designs or misses the bar on the critical experience. Squeezing payment backfill orders, event tracking cleaning, and combat sync into the same real-time execution path usually means all three end up done poorly.

### Step four: derive deployment and organization

Only when the gameplay loop, state ownership, and path timeliness are all clear does the architecture shape come into view:

- whether a room needs an exclusive execution context
- whether a world should be split by map, zone, shard, or logical domain
- whether capabilities like matchmaking, battle, chat, backpack, and campaigns merge or split
- which services must be strongly isolated and which are better on a shared base

The key here is not "the finer the split, the more advanced." It is keeping the primary path simple and controllable while letting the peripheral paths evolve independently.

### Step five: design failure recovery along with everything else

A game system cannot be designed for the happy path only. Every architecture analysis must also answer:

- how a player comes back after disconnecting
- how state is recovered after a node restarts
- which paths must be refused when versions disagree, and which paths can stay compatible
- how to retry, compensate, and audit when a platform interface fails

If the recovery strategy is bolted on afterward, it usually means the earlier state and boundary definitions were not solid enough.

### Common Mistakes

- reusing the previous project's architecture directly without re-analyzing the current gameplay loop
- looking only at features and not at state, treating "backpack, in-game shop, mail" as independent modules
- designing only the normal flow, without designing disconnect, retry, rollback, and compensation
- believing in some engineering style too early, such as "everything microservices" or "everything single process"

The meaning of pushing from gameplay to architecture is not to make the analysis more academic, but to give every technical decision a clear origin. Architecture should be traceable back to player behavior and system constraints, not back to the tools the team happened to know in the past.
