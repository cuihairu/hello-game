# Game Development Knowledge Map

## Category

industry / methodology subtree. Node positioning: the knowledge map is organized by problem domain rather than by discipline — draw the problem domains first, then decide which technology to use. Overarching statement for the methodology subtree.

## Definition


Game development is easy to split into disciplines — client, server, engine, operations, platform integration, database, security — but the problems a project actually meets do not show up by discipline. A single player path of "log in, finish a match, then claim the reward" crosses access, matchmaking, rooms, combat, settlement, configuration, event tracking, payment, and risk control at the same time. The job of the knowledge map is to draw the problem domains first, and only then decide what technology to use to solve each one.

## Problem

A project's problems never appear by discipline: one "log in, finish a match, then claim the reward" run crosses access, matchmaking, rooms, settlement, configuration, event tracking, payment, and risk control at once. Organizing knowledge by discipline means assembling on the spot whenever a real problem shows up; the map's role is to draw the problem domain first, with technology merely the answer.


### Why the knowledge map has to be drawn first

Without a knowledge map, the most common way teams work is to slice problems by role. The client talks about presentation, the server about interfaces, operations about campaigns, the platform about SDK integration; in the end everyone believes they have fulfilled their remit, but the system as a whole has never formed a closed loop. The problems that surface only after launch are usually cross-boundary ones:

- login succeeded, but character state recovery failed
- the room logic is correct, but the reconnection experience is unacceptable
- the campaign configuration can be published, but it clashes with the release window
- the payment path is wired through, but risk control and audit information cannot be retained completely

So a knowledge map is not a "learning sequence diagram"; it is a problem topology. It helps a team recognize which problems are the main trunk, which are supporting, which must be decided first, and which can wait.

### What this map usually contains

From an engineering view, a complete game system usually contains at least the following layers of problem:

- problem model: is this game a room-based session, a hard-real-time competitive product, a persistent online world, or a long-cycle progression driver.
- networking and sync: how state is transferred, how often, and who holds final adjudication
- runtime and services: how the logic executes, organized by thread, coroutine, Actor, or room process
- data and versions: which data must be persisted, which can be cached, which needs cross-version compatibility
- platform and monetization: how login, payment, ads, channels, review, and the game license (ISBN) constrain the implementation
- operations and governance: how campaigns, event tracking, risk control, customer support, GM, capacity, and security enter the primary path

These layers are not parallel topics; they press on one another. If you decide to do hard-real-time competitive play, networking and sync immediately become the main problem, and then runtime, replay, spectating, and weak-network recovery all tighten behind it; if you are building a long-cycle numerical progression product, data consistency, config-driven design, the operations cadence, and risk control cost are often more important than millisecond-level latency.

### The core use of the map

The most important use of a knowledge map is not "comprehensive coverage" but helping you rank things. Any project has limited resources, and the key is to answer three things first:

- what is the player's most frequent core action
- which state, once wrong, directly damages the experience or the business result
- which failures cannot be recovered, or cost far more to recover than to prevent

Once those three are answered, the main problem is usually clear. For a room-based battle project, the main problems mostly concentrate on matchmaking, room state, sync, and disconnect recovery; for a heavily operated progression project, the main problems turn toward configuration safety, numerical output, data correctness, campaign orchestration, and payment risk control.

### Common Mistakes

- treating a "tech stack" as a knowledge map, listing Unity, Go, Redis, and Kafka and assuming the analysis is done
- treating a "feature list" as a knowledge map, seeing only backpack, guild, mail, and in-game shop, and missing the shared state boundaries these systems have
- looking only at development-phase problems, not at post-launch operations, release, audit, recovery, and compliance
- chasing a unified big architecture too early, without first separating the primary path from the peripheral paths

The value of the knowledge map lies in exposing the system's contradictions first. It is not meant to look pretty; it is meant to let the team know which judgments, once wrong, drag the whole downstream chain into rework.
