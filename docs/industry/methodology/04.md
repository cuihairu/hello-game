# Core Trade-offs in Game Backend Design

## Category

industry / methodology subtree. Node positioning: five sets of tension — authority vs responsiveness, monolith vs distributed, real-time vs background, consistency vs recoverability, general vs specialized; design ability is knowing which side must win.

## Definition


The hardest part of game backend design is not getting the services running, but accepting that many goals cannot be maximized at the same time. Authority, real-time behavior, scalability, development efficiency, operations cost, version compatibility, and anti-cheat ability are constantly pulling against each other. What is called design ability is often just knowing which side has to win and which side can give ground.

## Problem

Authority, real-time behavior, scalability, development efficiency, operations cost, version compatibility, and anti-cheat cannot all be maximized at once. Without stating the trade-offs in advance, the team re-argues them on every single requirement; once the trade-offs are written down, the solution becomes reviewable and the retrospective becomes possible.


### Authority versus responsiveness

Who has the final say is the first dividing line in backend design.

- a strongly authoritative server is safer and better suited to adjudicating assets and combat results, but costs more in development and networking
- a client carrying more logic responds more directly and is more flexible during development, but carries greater cheating, divergence, and consistency risk

Most online projects do not end up as a pure either/or; they handle it in layers: core assets and critical combat results stay server-authoritative, while presentation details, predictive feedback, and some weak-consistency content are left to the client to carry the experience.

### Monolith efficiency versus distributed complexity

Splitting services lowers coupling and improves independent scaling, but it brings in registration and discovery, distributed tracing, timeout and retry, idempotency handling, data consistency, and cross-service troubleshooting cost. For many small and mid-sized projects, splitting too early costs far more complexity than it returns.

But refusing to split at all has its own obvious price:

- one failing module drags the whole process down
- the capacity models of different paths are mixed together, so the scaling granularity is too coarse
- different teams developing and releasing in parallel hold each other back

The key is not which of "monolith or microservices" is more advanced, but whether the execution unit and release unit of the primary path are clear.

### Real-time paths versus background paths

What is most worth separating explicitly in a game backend is the real-time interaction path and the background processing path. The former pursues stable latency and predictable execution time; the latter emphasizes throughput, compensation, batching, and auditability. When the two are mixed, the common consequences are:

- in-match logic slowed down by slow SQL, remote dependencies, or batch tasks
- campaign settlement and reward backfill cannot be fully audited
- during troubleshooting it is impossible to tell whether the problem occurred in the real-time execution layer or the asynchronous data layer

As a result, many systems end up as a "real-time execution core plus asynchronous peripheral systems" structure — not necessarily complex, but the boundary must hold.

### Consistency versus recoverability

A game backend rarely aims for strong consistency in every scenario. The more realistic approach is to distinguish:

- which state must be strongly consistent, such as top-up credits arriving, asset increments and decrements, and settlement adjudication
- which state may lag briefly, such as leaderboard display, recommendation results, and operations dashboards
- which state only needs eventual consistency, such as log archival, event tracking cleaning, and notification delivery

Different consistency levels mean different recovery means. Strong-consistency paths focus on transactions, idempotency, and audit; eventual-consistency paths focus on message replay, compensation tasks, and reconciliation tooling.

### General capability versus project specialization

Backend teams always want to build a general base, but game projects depend heavily on concrete gameplay. Too thin a base means lots of duplicate construction; too thick a base produces the reverse effect where "every business line has to be designed around the platform." A healthier approach is usually:

- platforming stable capabilities such as accounts, characters, payment, logs, monitoring, configuration, and audit
- leaving battle rules, room rules, campaign orchestration, and economy details inside the project domain

If the fastest-changing gameplay logic is also forced onto the platform, the platform itself becomes the new coupling center.

### Common Mistakes

- pushing all logic to the server "for safety," until development efficiency and cost get out of hand
- pushing adjudication authority too far down to the client "for speed," then patching in anti-cheat and audit later
- mixing the real-time battle path and the background batch path into one execution model
- applying an internet microservices template straight to a game project, without first identifying the specialness of in-match execution and room state

The core of backend design is not searching for one correct answer, but first separating which costs must be paid, which risks must be suppressed, and which complexity is only self-pleasing.
