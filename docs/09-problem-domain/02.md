# 强实时对战型架构

这一页从问题域角度归纳强实时对战型项目，同样是对应主线篇目的横向速查版。它不展开同步模型的完整推导，而是把这类项目区别于其他类型的关键判断集中在一页：谁说了算、状态怎么同步、卡了怎么追、作弊怎么防。

一句话画像：状态强耦合、时间毫秒级敏感、对抗结果要能被解释和复核。MOBA、FPS、格斗、竞速、实时动作竞技都落在这个画像里。它和单局房间型共享短会话边界，但时间与一致性要求陡增一个量级，架构形态随之完全不同。

## 这个问题域的特征

- 玩家对手感延迟极度敏感，几十毫秒的差异往往直接影响胜负。
- 状态耦合度高，一次命中判定牵动血量、技能、Buff、经济和 UI 多条链路。
- 对抗公平是产品生命线，任何一方获得时间或信息优势都会被放大成舆情。
- 局内操作密度高，带宽与消息频率天然偏高。
- 出错代价集中：重连、回滚、判负都发生在对抗最激烈的时刻。

## 核心取舍：确定性还是要权威裁决

这类项目绕不开的第一个判断，是服务端以什么方式说了算。常见的是两条路线，各有明确代价。

- 帧同步路线：服务端只转发输入，各端按相同顺序推进同一套确定性逻辑。带宽极省、回放天然免费，代价是要求逻辑完全确定，浮点、随机源、遍历顺序都要收敛，且客户端握有全部逻辑，反作弊面明显更大。
- 状态同步路线：服务端权威推进状态，客户端发送意图、接收结果，配合预测与回退。反作弊面小、逻辑可在服务端热修，代价是带宽高、服务端算力重、手感依赖预测质量。
- 实际项目往往是混合形态：核心裁决走权威，表现层走预测与插值，部分弱对抗信息用帧同步思路分发。

判断依据通常是产品形态而非技术偏好：小规模强对抗、逻辑封闭的项目往往偏帧同步；大规模开放对抗、需要服务端运营干预的项目往往偏权威状态同步。

## 追帧与纠偏的取舍

强实时对战的第二组约束来自网络抖动。无论哪条路线，客户端和服务端都会出现节奏不一致，提前设计追帧策略通常是硬要求。

- 预测要有边界，通常只预测己方行为，不预测他人和随机事件。
- 回退要可感知，纠偏幅度大时往往配合视觉平滑，避免角色瞬移。
- 追帧要有预算，单帧最多追多少步要有上限，否则容易进入越追越慢的死亡螺旋。
- 落后过多时常见做法是转向快照恢复，放弃逐帧硬追。
- 哪些系统允许跳表现、哪些裁决不允许跳过，要在分层里定清楚。

没有追帧预算的项目，重连往往变成永远在加载；没有纠偏策略的项目，玩家会先于系统发现状态错位。

## 反作弊面的差异

两条路线的反作弊面差别很大，这也是取舍的重要一环。

- 帧同步下客户端掌握全部逻辑，透视、改帧、加速类作弊难以从协议层根除，通常依赖行为检测、录像回查和服务端交叉验证。
- 权威状态同步下客户端只见局部信息，作弊面集中在协议伪造和输入异常，服务端校验往往更直接有效。
- 两条路线都需要把关键事件落到可追责的逻辑时间上，否则举报复盘和争议仲裁都没有证据。

## 常见方案形态

对局服务通常按局组织进程，一局一个或一组实体，局内推进固定 Tick，裁决事件带帧号或序号。

- 接入层维护连接与路由，负责弱网感知和重连定位。
- 对局服务维护权威时钟或权威帧号，客户端本地时钟持续向它收敛。
- 录像与回放通常从同步体系直接派生，帧同步存输入序列，状态同步存关键快照加事件流。
- 观战与托管复用同一条事件流，避免另起一套转发链路。

工程上常见的一致性保障手段，是定期对账：服务端抽样校验客户端状态哈希，或同逻辑双端互相校验，把漂移发现在局中而不是局后。

## 该类型特有的坑

把确定性当成口号：逻辑里留着一个浮点或一次哈希遍历，测试环境一切正常，上线后某类机型分叉，且很难复现。

回放与实战不一致：回放用的是一套逻辑版本，线上跑的是另一套，争议局复盘时对不上，公信力反而受损。

预测没有边界：全量预测他人行为和随机结果，网络一抖整屏回退，手感比不预测更差。

追帧没有上限：落后时无限补帧，CPU 占满、延迟加剧，越追越落后。

反作弊只靠协议：客户端可信度完全交给加密和混淆，没有行为面检测，作弊工具迭代几轮后防线整体失效。

## 常见误区

- 用单机手感直接套在线对战，把时间模型、预测和纠偏当成上线前再补的细节。
- 把帧同步与状态同步当成信仰之争，而不是按对抗规模、逻辑封闭度和反作弊需求做取舍。
- 只验证正常运行时的同步，不在弱网、重连、追帧和后台切换下验证一致性。

这类项目的架构方向通常可以概括为：时间单一权威，预测有边界，追帧有预算，作弊面与裁决路线一起选。
