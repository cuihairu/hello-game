# Gray Release, Rollback, and Compatibility Windows

## Category

production / release safety. Node positioning: the three pillars of gray release, rollback, and compatibility windows — the release system assumes by default that unknown problems will surface online, and the goal is to discover, contain, and roll back under control.

## Definition


A stable release does not mean "this time is definitely fine." It means that once there is a problem, the system can discover it, contain it, and roll it back within a controllable scope. Gray release, rollback, and the compatibility window are exactly the three pillars built around that goal. Missing any one of them, and the release system is hard to call mature.

Many teams understand gray release as percentage rollout, rollback as shipping an old package again, and the compatibility window as "let's just be compatible for these last few days." All three understandings are too shallow. What they actually solve is the isolation and recovery of unknown problems online.

## Problem

A stable release does not mean "this time is fine," but that when a problem appears it can be contained within a controllable scope. Without gray release, problems erupt at full volume; without rollback (and what rolls back is a stable combination, not old code), problems can only be fixed; a compatibility window decided off the top of your head (too short and it blows up the existing base, too long and you carry double maintenance) means problems concentrate and pay out at version boundaries.


### Why the release system must assume by default that unknown problems will surface online

No matter how carefully testing is done, the online environment always contains variables that cannot be exhausted beforehand:

- combinations of device models and system versions
- differences between historical packages and patch chains
- platform SDK or channel environment differences
- users' real paths and extreme operations
- combinations of old caches, new assets, and new config

So the release system cannot be built on the assumption that "testing has covered every case," but on the assumption that "unknown problems will definitely keep coming."

### What gray release is really worth its salt for

Gray release is not as simple as "let 5% of users try it first"; it is more like a risk-slicing capability. A gray release that is genuinely valuable can usually slice along these dimensions:

- user groups
- channel and platform
- region and network environment
- client package version
- feature flags and asset batches

The significance of doing this is that once a problem occurs, the team can learn much faster where the blast radius is, instead of having to guess blindly between "all users might be affected" and "we have no idea who is affected."

### Rollback is not returning to old code, it is returning to the old stable combination

This is the point most easily underestimated by many teams. Online problems are often not a single component failing, but a combination of components that is incompatible. So a rollback that actually works must be able to answer:

- is what needs rolling back the client package, assets, config, scripts, or server-side logic
- is the rollback target still mutually compatible
- does the player's current state and cache need to be cleaned up or migrated
- does the server know which clients are still sitting on the old combination

If these questions were not designed for in advance, then so-called rollback is usually just "quickly ship it once more," not a real return to a stable state.

### Why the compatibility window is neither better short nor better long

The compatibility window is the time range during which old versions are still allowed to coexist with the new system. Too short, and you get these problems:

- channel review is not finished and the old client can no longer connect
- the player upgrade distribution has not converged yet, and a forced cutover to the new version causes mass failures
- the server does not have time to migrate protocol and data structures smoothly

Too long, and you get another set of problems:

- the server and config carry a two-way compatibility burden for a long time
- new capabilities cannot quickly clean up old logic
- the test matrix and troubleshooting complexity keep climbing

So the compatibility window is not decided off the top of someone's head; it must be set by combining review cycles, upgrade distribution, risk level, and operational capability.

### A more sound release-safety model

A more sound practice usually designs three things together:

- use gray release to control the exposure surface of new change
- use rollback to guarantee that once a problem appears you can return to a known stable combination
- use the compatibility window to guarantee the system still runs during gray release and rollback

All three must exist at the same time. Gray release without rollback means that even after finding the problem you cannot cut losses; rollback without a compatibility window means that after you go back the system may still not run stably; a compatibility window without gray release means the risk still gets exposed in full at once.

### Where things most easily go wrong

### Only a rollout switch, no state-recovery design

Many systems can do "stop shipping the new version" but cannot do "restore already-affected users to the correct state."

### Only rolling back code, not rolling back config and assets

This makes it look on the surface like the rollback succeeded, while online is still running an incompatible combination.

### Compatibility window decided entirely by experience and verbal agreement

A compatibility window with no upgrade distribution and no platform cycle behind it usually ends up either too short or too long, and long term it is just guesswork.

### Common Pitfalls

The most common mistake is understanding gray release as simple percentage rollout rather than as a risk-slicing tool. The second type of error is understanding rollback as re-releasing an old version rather than as restoring a set of compatible, stable version combinations. The third type of error is deciding the compatibility window purely on experience, looking at neither platform review cycles nor players' real upgrade distribution, and ultimately damaging both evolution and stability.
