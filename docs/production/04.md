# 前后端协同与平台约束

游戏发布从来不是研发单方面把代码推上去这么简单。客户端、服务端、策划、测试、运营、渠道、平台审核和外部 SDK 供应方，都会在同一条发布链路里留下硬约束。忽略这些约束，技术流程再漂亮，也很难真正稳定。

很多团队在这类问题上吃亏，不是因为技术不懂，而是因为默认“后端可控、客户端配合、平台最后再看”。真实世界通常正好相反：平台和渠道约束经常先决定哪些能力何时能上线，而前后端必须围绕这些现实重新组织版本节奏和回滚方案。

## 平台约束为什么会反向塑造技术方案

客户端包之所以比服务端更重，不仅因为它包含宿主能力，更因为它受这些现实约束影响：

- 商店和渠道审核周期
- 权限与隐私规则
- 支付、广告、登录等 SDK 接入要求
- 包体、资源下载和网络使用限制
- 特定平台的能力上线门槛

这意味着很多“后端今天就能改”的东西，实际上并不能今天就对所有玩家生效，因为客户端宿主能力和平台规则可能根本不允许。

## 前后端协同真正难在哪里

很多团队把前后端协同理解成接口联调，但发布阶段真正难的通常不是接口，而是这些问题：

- 某个改动到底依赖不依赖新客户端包
- 老客户端在兼容窗口内还能不能接住新服务端逻辑
- 平台审核未完成时，服务端和配置能开到什么程度
- 问题发生后，前后端各自怎么回滚才不会互相踩

换句话说，前后端协同真正讨论的是版本节奏、能力边界和事故恢复，不只是消息格式。

## 哪些改动最容易在这里出问题

最常见的是这些跨边界改动：

- 新协议字段需要客户端宿主识别
- 新 SDK 依赖新的权限申请或审核材料
- 新资源加载方式依赖新的包体结构
- 新功能开关看似由服务端控制，实际客户端宿主还没有能力接

这类改动如果只在服务端视角下被看作“可灰度”，上线后很容易演变成特定平台、特定渠道、特定历史包才触发的复杂事故。

## 多平台和多地区为什么会进一步放大问题

一旦进入多平台、联运、多地区或小游戏适配场景，约束会成倍增长：

- 不同平台审核时长不同
- 不同地区上线节奏不同
- 外部 SDK 版本分布不同
- 某些功能在部分平台根本不可用

如果发布体系没有把这些差异正式建模，团队很快就会回到“靠表格和经验记住哪些平台能开哪些开关”的原始状态。

## 一个更稳妥的协同方式

比较稳妥的做法通常是：

- 在需求和版本设计阶段就把平台约束前置
- 用适配层隔离平台差异，而不是把分支散落在业务代码里
- 明确哪些变化依赖新包，哪些可通过资源、配置或服务端独立推进
- 让前后端、测试和运营共享同一套版本窗口和风险判断口径

这样做的关键，不是让所有团队动作一致，而是让所有团队对同一组约束有一致理解。

## 常见误区

最常见的错误，是把平台因素视为上线末端问题，等到提审或联运联调时才发现包体、权限、支付或广告接口已经反向影响主流程。第二类错误，是把前后端协同简化成接口联调，忽略版本节奏、兼容窗口和回滚策略的联动。第三类错误，是平台差异没有工程化承接，长期靠人工记忆维护，结果每次多平台上线都在重复踩坑。
