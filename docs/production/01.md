# Version System Overview

## Category

production / version system. Node positioning: a version is not a single number, but a set of components that evolve at different rhythms — only by admitting this first can the release system even be designed right. Master outline of the production tree.

## Definition


In a game project a "version" has never been one standalone number, but a set of components that coexist, depend on each other, yet do not change at the same rhythm. Client packages, asset patches, the script layer, config tables, protocol definitions, server-side logic, and operational event data are usually all evolving independently. Only by admitting this first is it possible to design the release system right.

Many version incidents are hard to diagnose not because one component itself is wrong, but because two sets of components that were each legal on their own mismatch when combined. For example, an old client pulled a new config, a new protocol met an old asset, a hot-update script ran on unprepared host code. As long as the system keeps treating version as the single abstraction of "the current online version," problems like this will almost never be seen in advance.

## Problem

In long-running projects the version problem is a system problem: the client package is constrained by review, assets and config must iterate fast, and the protocol and server must keep a compatibility window — bind them all to one version number and every change travels the slowest path; the phrase "the current online version" hides the everyday reality of multiple versions coexisting, so when something breaks you cannot even answer "what is actually running online."


### Why the longer a project runs, the more the version problem looks like a system problem

Short-cycle projects can sometimes limp along on "everyone ships together, everyone switches together, everyone replaces together." But once a project enters long-term operation, the realities below turn the version problem from a release action into a system problem:

- multi-platform parallelism and multi-channel distribution
- assets, config, and events needing high-frequency iteration
- hot update and gray release becoming the norm
- platform review making client package updates naturally lag
- old players and new players running long-term on different component combinations

At that point, without a formal version model the team can only rely on experience to guess compatibility relationships, and incidents become harder and harder to control.

### What a version system really has to answer

A mature version system should at minimum be able to answer four questions:

- which set of components is a given player actually running
- whether that set of components is within official support
- which components must be upgraded together, and which can be upgraded independently
- when a problem occurs, can you quickly fall back to the previous stable combination

Note that what really matters here is not the form of the version number, but whether the system has "decidability." If the team cannot clearly judge whether a set of components is legal, then gray release, rollback, and compatibility downstream are all talk.

### Why the phrase "the current online version" is often harmful

It is harmful not because the term cannot be said, but because it hides the real structure. Online there is usually not one absolutely unique version state; at minimum the following coexist simultaneously:

- different client package versions
- different hot-update layers
- different asset manifest versions
- different config activation batches
- different server-side gray release groups

If the system still thinks only in terms of one unified version number, many mismatches and incident paths that actually exist get masked by the language itself.

### A more realistic view of versions

A more sound practice is to treat a version as a set of "component combinations + dependencies + timing of activation":

- component combinations say which variable parts the system is made of
- dependencies say which combinations are legal and which are not allowed
- timing of activation says when they actually take effect for a player

With this view, many questions that were originally vague become clear, such as "does some event require new assets and new config to exist at the same time," "can some old package still coexist with the current protocol," or "does the hot update cover the device models that are crashing right now."

### A version system is not a tool substitute

CI/CD, package management, hot-update platforms, and config platforms are all important, but they themselves are not version governance. Tools can execute a process automatically, but they cannot define for the team:

- what the version boundary is
- how long the compatibility window is
- which set of components is the rollback target
- which changes can be rolled out independently

If nobody makes these judgments explicitly, then no matter how automated the process, incidents will just happen automatically and faster.

### Common Pitfalls

The most common mistake is outsourcing the version problem to the pipeline and the release platform, assuming that having tools means having governance. The second type of error is that the system already contains multiple independent versions in fact, yet a single version number is still used to reason about compatibility and rollback. The third type of error is focusing only on "how to ship the new version" and not on "how the old version keeps living and when it goes offline," so the compatibility window stays out of control for a long time.
