# Client, Asset, Config, and Protocol Versions

## Category

production / version system. Node positioning: what the four kinds of versions (client package, asset/config, protocol, server-side logic) each represent, why they must be governed separately, and how to manage the newly added dependency relationships after they are split apart.

## Definition


Tying all change to the client package version looks like the cheapest option early on, and long term it will almost certainly fail. The reason is simple: these components were never built to serve the same release rhythm. The client package is constrained by review and channels, assets and config often need to iterate faster, and the protocol and server-side logic may even be forced to evolve out of sync in order to keep a compatibility window. Binding them together by force means every change must travel the slowest, heaviest path.

So splitting versions is not "complicating" things from a management standpoint — it is an admission of the different rhythms of change.

## Problem

Tying all change to the client package version is cheap early and doomed to fail long term: every change is forced down the slowest, heaviest release path. What really gets added after the split is not numbering, but dependencies — which combinations are legal, who is compatible with whom, how the staggered window is computed. With no ledger for these dependencies, multi-version coexistence is a troubleshooting hell.


### What the four kinds of versions each really represent

### Client package version

It usually represents the host binary's capability, including:

- native code and the engine runtime
- platform SDKs and system permissions
- local host interfaces
- baseline rendering and runtime capability

It is the heaviest and the hardest to replace frequently, so it is usually more suitable as the lower bound of host capability, rather than as the carrier of all business change.

### Asset version

The asset version corresponds to presentation assets and load manifests, for example:

- UI atlases
- scenes and effect assets
- audio and animation
- sub-packages and hot-update asset sets

What matters here is not the version number itself, but asset dependencies, manifest consistency, and the match against host capability.

### Config version

The config version corresponds to rule data and content parameters, for example:

- numerical parameters
- event rules
- drop and quest tables
- page and content layout

The config version needs independent governance because its change frequency is usually far higher than the client package's, and when it goes wrong the symptom is often not a crash but a subtler rule incident.

### Protocol version

The protocol version represents the communication contract and the state structure, including:

- message formats
- field semantics
- the range of feature-flag support
- whether frontend and backend can reach the same understanding of the same piece of state

The difficulty of the protocol version is not the upgrade itself, but how the server correctly catches both old and new clients inside the compatibility window.

### Why these versions must be governed separately

If you do not separate them, the most direct consequences are usually two:

- lightweight change is forced down the heaviest release path, and overall responsiveness gets slower and slower
- heavyweight change disguises itself as lightweight change, and compatibility and risk are systematically underestimated

For example, a small change that only wants to fix an event parameter will run away in iteration cost if it must go through client review again; conversely, if a change that depends on a new host interface is disguised as "just an asset and config update," a very dangerous compatibility incident appears online.

### After versions are split, what really gets added is not numbering but dependencies

Many teams swing to the other extreme here: since we are splitting, let's give every kind of component its own version number. The problem is that version numbers without dependency relationships and validation rules will only make the system messier.

What really needs to be expressed formally is:

- which package version a given asset version requires at minimum
- whether a given config batch depends on a given protocol field
- whether a given protocol version is still compatible with a set of historical clients
- whether a given hot-update patch can only run on top of a specific host capability

The number of versions is not the problem; losing decidability is.

### A more sound way to organize it

A more sound practice is usually:

- use the package version to define the host capability baseline
- use the asset version to define the set of loadable assets
- use the config version to define a snapshot of rule data
- use the protocol version to define the boundary of communication compatibility
- string them together with explicit dependency rules

The core of doing this is not breaking concepts into finer pieces, but letting the system know which changes can advance independently and which changes must advance in lockstep.

### The testing difficulty most easily overlooked

Once versions are split, the testing difficulty is no longer just "does the current version run," but:

- do all legal combinations run
- are all illegal combinations blocked
- can historical packages still connect stably within the compatibility window
- do gray groups and non-gray groups see the correct differences

So multi-version governance essentially also demands upgrades to testing and to the release platform, otherwise the team has just moved complexity from the development side onto the live side.

### Common Pitfalls

The most common mistake is continuing to bind all change to the client package version, making the release path heavier and heavier. The second type of error is that version numbers have been split, but there are no explicit dependency relationships and no validation of legal combinations. The third type of error is doing version splitting only, without adding a test matrix and release-decision capability, so online still ends up guessing compatibility by experience.
