# Validation, Export, and Code Generation

## Category

production / config subtree. Node positioning: error handling cost is determined by where the error is found—validation left-shift, structure definition first, reference validation, environment isolation, and the benefits and costs of code generation.

## Definition


In a config pipeline, the handling cost of an error is almost entirely determined by where it is found. The same wrong field type, flagged red in the editor, is a matter of seconds; reported when loaded in the test environment, it is half a day; manifesting as a rule anomaly in production, it can be a multi-day incident plus a round of compensation. So the core of the validation system is not "how strictly it checks", but "how early it checks". How well validation is done comes down to whether errors can be stopped at the moment closest to the mistake.

Export and code generation are the bridge between editing and running. When these two things go smoothly, the config pipeline has a very low profile—designers change things and they naturally take effect. When they are awkward, the pipeline becomes a black box that needs dedicated people tending it, and every release is a prayer.

## Problem

The same field type error: editor red flag is seconds, test-environment error is half a day, production anomaly is a multi-day incident plus compensation. The core of validation is not "how strict" but "how early"; environment isolation is the link most easily compromised (test tables reaching production); passing validation does not mean the content is correct—legal but absurd numbers need a semantic validation backstop.


### Why Validation Should Be Left-Shifted as Much as Possible

The difference in cost of finding the same error at different stages is worth calculating on its own:

- Edit time: flagged at the moment of mistyping, cost is nearly zero, and the person who made the change can fix it themselves.
- Commit time: incremental validation runs at commit, and the cost is a few minutes of waiting plus one re-commit.
- Release time: intercepted at export or approval, and the cost is one voided release plus a round of investigation.
- Load time: fails at server startup or hot update, and at best the version is reverted, at worst the process will not come up.
- Run time: the data is legal but semantically wrong, and it surfaces as player complaints or metric anomalies.

The common left-shift techniques are not complicated: the editing interface does immediate validation against the field definition, local tooling offers a one-click self-check, and commit hooks run incremental checks. Their shared goal is to push errors into the cheapest range as much as possible. Whether a pipeline is mature can be roughly guessed from its error distribution—if errors cluster at edit time the system is working; if they cluster at run time, validation is basically absent.

### Structure Definition Is the Prerequisite for All Validation

To catch errors at validation time, you first need a clear definition of "what counts as wrong." This usually lands in a structure description: which fields each table has, what type, what value range, whether required, and which enum values. Without this definition, validation can only rely on if-statements scattered through the code and on people's memory.

What truly makes a structure definition valuable is that it makes implicit knowledge explicit:

- "This field is a percentage, max 100" becomes a machine-checkable rule instead of a verbal agreement.
- "This enum can only take these values" makes mistyping found at entry time.
- Field purpose descriptions travel with the definition instead of being scattered through chat logs.
- Composite constraints between fields (A greater than B, the two cannot both be empty) also go into the definition, making business rules checkable too.

Maintaining the structure definition itself has cost, especially in projects with many tables and many fields. A common way of loosening up is to allow the table format to run ahead and the definition to be filled in later—short-term convenient, but the long-term cost is that the definition drifts out of sync with actual data and validation becomes a formality. Definition drift is itself worth monitoring: when validation rules and actual data stop matching for a long time, it is usually not the data that is wrong, but that the definition has aged.

### Reference Validation: The Most Common Break Point

The most frequent class of config error is broken references: this table fills in an ID, and the thing being referenced does not exist. A drop table references a nonexistent item, a UI references a nonexistent image, a quest chain references a nonexistent next step. Reference validation is therefore usually the highest-return investment in the validation system:

- Cross-table references need full checks: looking at a single row cannot judge whether a reference holds; only by laying out all tables together can you confirm.
- Deleting referenced content should be intercepted, or at least warned about, rather than passing silently.
- The reference relationship itself is worth visualizing or listing; "where is this ID used" is a high-frequency need for both designers and programmers.

The performance of reference validation is often underestimated. As tables and references multiply, full validation can balloon from a few seconds to a few minutes, and people start bypassing it, making validation a formality. So reference validation usually needs an incremental mechanism: day-to-day it only checks the references touched by changes, and full validation is reserved for the last gate before release.

### Semantic Validation: From Legal to Reasonable

A structurally legal, fully referenced config can still be wrong: drop rates that add up to more than 100 percent, economic output far exceeding sinks, two mutually exclusive activities scheduled at the same time. This layer is usually called semantic validation, and its essential difference from structural validation is that the rules come from the business rather than from the type system:

- Probability class: the sum of probabilities across tiers, the upper bound of expected output.
- Economy class: the ratio range of output versus sinks, the speed of currency settling.
- Time class: activity ranges do not overlap, prerequisite quests come before subsequent ones.
- Dependency class: systems a new feature depends on already exist in the target version.

Semantic rules are hard to write completely at once; the usual practice is to accumulate them as incidents happen: each time a rule incident occurs, ask "can this rule become a validation?", and if so, harden it into the validation library. After a few years, a project's validation library is often the reverse image of its incident history.

### What the Export Step Is Really Solving

Export is not just format conversion. It usually takes on several things at once: converting the editing format to the runtime format, distributing one source dataset to multiple targets, and folding a human-friendly wide table into a program-friendly structure. These conversions hide common incident points in the pipeline:

- When one source dataset is exported to multiple targets, the versions across targets have to line up, or client and server each end up with inconsistent data.
- Default values and type narrowing during conversion quietly swallow abnormal data; a successful export does not mean the content is lossless.
- Export artifacts are release artifacts and deserve to be versioned and archived like code artifacts, rather than generated on the fly for each release and discarded after use.

A judgment habit worth cultivating: problems that come out of the export step usually manifest as "the data is right, but the program reads it wrong." When you hit this kind of problem, suspect the conversion layer first, then the loading layer, and only last the person who filled the table.

The export layer also has a natural advantage that is easily overlooked: it is the unavoidable road for all target-side data, so doing a final pre-release check here is often cheaper than setting up defenses separately at each loading end.

### Why Environment Isolation Is Easy to Lose

The config pipeline connects multiple environments: the designer's self-test environment, the development environment, the test environment, pre-release, and production. The wall between environments is the one most easily torn down under schedule pressure. Typical forms of losing it include:

- Test data mixing into a production batch, and players see internal placeholder text or test rewards.
- Opening up environments temporarily to make one activity deadline, and never closing them again.
- Config sources inconsistent across environments, so a batch validated in the test environment loads different results in production.
- The environment list is hard-coded in tooling, so adding a new environment requires a code change, and the isolation strategy gradually drifts from reality.

A common approach to environment isolation is to make environment a first-class concept of the release target: explicitly choose the target environment at release time, do not share writable entry points between environments, and give cross-environment borrowing a time-boxed channel. For every unit of looseness in isolation, the mental load of every subsequent release gets heavier by one unit.

### The Benefits and Costs of Code Generation

Generating loading code and access interfaces from the structure definition is a choice many teams make. The benefits are usually direct: field access gains type safety, structure changes surface affected code at compile time, and manual parsing logic scattered everywhere disappears. The costs are easy to gloss over:

- Whether generated output is checked in, when it is regenerated, and who is responsible for regenerating it need clear agreement, or you will get the dead end of changing the definition and forgetting to regenerate, or of generated output being hand-edited.
- The generator itself becomes project infrastructure, and its upgrades and compatibility have to be maintained like a formal tool.
- Indirection in errors increases: at runtime you see generated code, and during investigation you have to go back to the definition and the generation rules.

Code generation suits scenarios where the structure is relatively stable and there are many readers. If the structure changes every day and there are only one or two readers, a lightly maintained manual approach is sometimes cheaper.

### Passing Validation Does Not Mean the Content Is Correct

No matter how complete the validation system, it can only cover the part of judgment that has been formalized into rules. Whether the numbers feel right, whether the activity rhythm is smooth, whether the copy is appropriate still have to be judged by people. So a mature pipeline usually keeps a human confirmation slot after automatic validation:

- Diff review before release: a person goes through what this batch actually changed.
- Gray release observation: take effect on a small scope first, see the real behavior, then scale up.
- Spot checks after effectiveness: walk through key content for real on a test server or an internal account.

Automatic validation handles the mistakes people do not make; human confirmation handles the mistakes only people make, and the two do not substitute for each other. Betting everything on either side will cost you at some point.

### Common Pitfalls

- Validation concentrated at load time, so the server startup error becomes the first scene for discovering config problems.
- Only structural validation with no reference or semantic validation, so format errors get caught but rule incidents do not.
- Treating export as a throwaway script, with artifacts not versioned, so when a problem occurs you cannot tell which batch of data it came from.
- Environments left connected long term, with test data flowing to production and no end in sight to the recovery.
- Generated code hand-edited, so changes are silently lost on regeneration.

The one shared goal of validation, export, and generation is: make every step from editing a config to its taking effect checkable, traceable, and reversible. Once that level is reached, the lower the pipeline's profile, the better it is doing its job.
