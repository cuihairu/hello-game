# 表结构设计与拆分

配置表怎么拆，看起来是数据建模问题，实际上首先是协作问题。表的结构决定了谁能改什么、一次改动的影响范围有多大、两个策划会不会在同一个文件里互相覆盖。很多团队在表拆分上的纠结，表面上是“字段该放哪张表”，底层往往是“这次改动该由谁负责、出了错该找谁”。把协作关系想清楚了，拆分方案通常会自己浮出来。

反过来，拆分方案长期不合理的项目，往往会在运营期积累出一批只可意会不可言传的编辑规则：哪个字段不能乱动、哪两张表要一起改、哪个格子其实是给另一个系统看的。这些规则没有落进结构里，全靠人的记忆维持，人员一流动就开始出事故。

## 拆表的真正依据是谁在改、何时改

按数据含义拆表是最直觉的思路，但实践中更有生命力的拆法，通常围绕变更单元来组织：

- 归属不同就分开：数值组和系统组各管各的表，改动的审查路径也不同。
- 节奏不同就分开：活动表每周都在调，基础数值表一个版本才动一次，混在一起会让低频表陪高频表走完整的发布流程。
- 风险不同就分开：影响经济和资产的表，与纯表现层的表，出错代价差着量级，校验和审批强度也应该不同。
- 生命周期不同就分开：赛季活动表随赛季生灭，常年存在的基础表不该被它们反复扰动。

判断一张表拆得合不合理，一个简单的问题是：这张表的一次典型改动，是否只牵动一批人、一条审批路径、一组风险等级。如果答案是牵动了三拨人，通常说明它该再拆。

## 拆得太粗的代价

大而全的单表在项目早期很诱人，所有内容都在一个地方，查起来方便。但随着内容增长，成本会逐项显形：

- 编辑互斥：一个文件同时只能被少数人编辑，排队改表成为日常。
- 连带重导：改一行数值也要触发全表导出和全量校验，任何一个无关错误都会阻塞这次发布。
- 影响面失控：任何改动理论上影响所有系统，灰度和回归都只能按最大范围做。
- 审查疲劳：diff 里混杂大量无关变化，真正危险的改动反而容易被扫过。
- 归属模糊：一张表里混着多个系统的内容，出问题时常常说不清该找谁。

这些代价平时表现为“效率低”，出事时表现为“影响面大”。大表的事故往往不是一个格子填错，而是一次本该局部的改动，借着共享结构扩散到了不该去的地方。

## 拆得太细的代价

另一头的极端是按功能、按系统、甚至按页面拆出一大堆小表。小表本身没有错，错的是粒度失控之后跟着来的东西：

- 表数量爆炸，新人找不到入口，老人也只熟悉自己那一片。
- 跨表引用激增，任何一次拆分都会把原本的表内一致性变成表间引用，断裂概率随之上升。
- 一次功能改动要同时动十几张表，协调和排期成本反而回来了。
- 全量校验要遍历所有表和引用关系，跑一次的时间越来越长。

拆分的粒度没有标准答案，通常的做法是先按变更单元拆，出现明显热点后再细分，而不是一开始就追求结构上的完美对称。表结构是长出来的，不是一次设计出来的。

## 引用关系是拆表的隐藏成本

两张表一旦分离，它们之间的联系就从“同一份数据内部的约定”变成了“需要显式维护的引用”。这是拆表决策里最容易被低估的部分：

- 每一个跨表引用都是一个潜在的断裂点：被引用的行被删除、改号，引用方往往不会立刻报错，而是在运行时表现为空引用或默认值。
- 引用的合法性通常只能在全量校验时确认，引用越多，校验链路越长。
- 循环引用和隐式依赖（靠命名约定或口头约定维持的联系）会让“改一张表影响谁”变得难以回答。
- 引用方向也会随时间腐化：本该单向的引用慢慢长成双向，拆分带来的解耦被逐渐吃掉。

比较稳妥的做法，是让引用关系尽量显式：引用用统一的键类型表达，被引用方有明确的删除保护，全量校验覆盖所有引用路径。引用关系显式之后，拆分才有底气，否则每次拆表都是在增加一批无人看管的接缝。

## 命名与约定

表多起来之后，命名就是检索成本的直接来源。命名混乱的项目里，常见的景象是同一个概念在三张表里有三个名字，谁也不敢合并。一些低成本的做法通常值得在早期就定下来：

- 表名表达内容和用途，而不是工具格式或作者习惯。
- 主键与外键命名统一，看到字段名就能推断它引用谁。
- 临时表、废弃表、调试表有明确的标记约定，不与正式表混放。
- 赛季号、批次号这类版本后缀统一放表名尾部，枚举和检索才有规律可循。

约定的价值不在严谨，而在一致。一套朴素但执行一致的命名，通常胜过一套精巧但各人各写的规范。

## 多人同时编辑的冲突

共享表格文件是很多项目配置系统的起点，它的局限也最有共识：整文件锁定导致排队，二进制格式让 diff 和合并基本不可用，修改历史无法追溯。行级或字段级的编辑平台之所以值得投入，正是因为它把冲突解决点从发布期挪到了编辑期：

- 两个人改同一张表的不同行，互不阻塞。
- 改同一行的冲突在保存时立刻暴露，而不是在导出或发布时才炸出来。
- 每次修改都有人和时间的记录，追责和回溯有据可依。

冲突在编辑期解决的成本，往往比在发布期解决低一个量级。前者是两个人对一下数值，后者可能是一次回滚加一轮排查。

共享文件时期还容易留下一个习惯性遗产：为了避免冲突，先把表复制一份改自己的副本，之后再靠人工对齐。这类变体副本是引用断裂和数据漂移的高发源头，平台化编辑落地之后，通常值得专门清理一轮。

## 表结构的演进

表结构和代码一样会演进：加字段、改语义、废弃旧列。区别在于配置表还要面对“历史发布的批次仍在被引用”这个现实。演进时常见的坑通常集中在这几处：

- 字段语义漂移：列名没变，含义悄悄变了，老批次数据和新解释对不上。
- 只加不减的堆积：废弃字段不敢删，几年后没人说得清哪些还在被读取。
- 跨版本兼容：新配置依赖新代码才认识的字段，老进程加载时要么忽略要么报错，行为需要明确设计。

比较稳妥的纪律是：语义变化用新字段表达，废弃字段先标记停止写入、观察一段时间再物理删除，删除前确认没有还在运行的历史批次引用它。这些动作单看都琐碎，累积起来决定了一张表几年后还能不能被安全地修改。

## 什么时候值得重构表结构

重构有成本，触发时机通常来自明确的信号而不是审美：

- 某张表成为编辑瓶颈，多人排队或频繁互相覆盖。
- 一次典型改动需要跨太多张表，协作开销肉眼可见。
- 校验时间或导出时间长到影响发布节奏。
- 新人上手周期明显变长，问得最多的问题是“这个去哪张表改”。

重构最好安排在内容增长的间隙做，并且配一次完整的数据迁移和回归校验。结构重构最大的风险不是设计不出更好的结构，而是迁移过程中悄悄丢数据、改语义，上线后才在玩家侧暴露。

## 常见误区

- 按数据含义而不是变更单元拆表，结果一张表横跨三条协作线，谁都不完整拥有它。
- 用复制表的方式规避冲突，派生出大量只在一处使用的变体表，一致性无人维护。
- 把跨表引用建立在命名约定和口头提醒上，断裂后表现为运行时的诡异默认值。
- 表结构从不演进也不敢演进，最后所有新需求都靠加一张新表解决。

拆分的判断标准说到底只有一条：让一次典型改动的影响面，和它的真实风险相称。影响面大于风险的拆分是浪费，小于风险的拆分是隐患。
