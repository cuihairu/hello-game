# Table Structure Design and Splitting

## Category

production / config subtree. Node positioning: splitting a table is first a collaboration problem—who is changing it and when determines the granularity of the split; reference relationships are a hidden cost, and evolution needs a path left open.

## Definition


How to split a config table looks like a data modeling problem, but it is actually first and foremost a collaboration problem. The structure of the table decides who can change what, how large the impact scope of a single change is, and whether two designers will overwrite each other in the same file. Much of the fuss teams have about table splitting is, on the surface, "which table should this field go in", but at the bottom it is often "who should own this change, and who do we call when something goes wrong." Once the collaboration relationship is thought through clearly, the splitting plan usually surfaces by itself.

Conversely, projects where the splitting plan has been unreasonable for a long time often accumulate, during operation, a set of editing rules that can only be grasped by intuition: which field cannot be touched, which two tables have to be changed together, which cell is actually for another system to read. These rules never make it into the structure; they are held together entirely by people's memory, and once personnel churn begins, incidents start.

## Problem

The table structure decides who can change what, how large the impact scope is, and whether two people will overwrite each other. Split too coarse: changing one field requires a whole-table review, with constant conflicts; split too fine: reference relationships explode, and loading and validation costs rise. The bottom of the fuss about "which table should this field go in" is often "who should own this change, and who do we call when something goes wrong."


### The Real Basis for Splitting Is Who Changes It and When

Splitting by data meaning is the most intuitive approach, but in practice the splits that have more staying power are usually organized around change units:

- Different ownership means separate: the numerical team and the systems team each manage their own tables, and the change review path is different too.
- Different cadence means separate: activity tables get tuned every week, while base numerical tables move once a version; mixing them makes low-frequency tables ride the full release flow along with high-frequency ones.
- Different risk means separate: tables affecting economy and assets versus pure presentation-layer tables differ by orders of magnitude in the cost of error, so validation and approval intensity should differ too.
- Different lifecycle means separate: season activity tables live and die with the season; evergreen base tables should not be repeatedly disturbed by them.

A simple question for judging whether a table is split reasonably: does one typical change to this table only involve one group of people, one approval path, one risk level? If the answer is three groups of people, it usually means the table should be split further.

### The Cost of Splitting Too Coarsely

A big, all-encompassing single table is tempting early in a project—everything is in one place, and it is easy to look things up. But as content grows, the costs show up one by one:

- Edit mutual exclusion: a single file can only be edited by a few people at once, and queuing to change a table becomes routine.
- Collateral re-export: changing one number triggers a full-table export and full validation, and any unrelated error blocks this release.
- Loss of control over impact scope: any change theoretically affects every system, so gray release and regression can only be done at the maximum scope.
- Review fatigue: the diff is mired in a mass of unrelated changes, and the genuinely dangerous changes are easily skimmed past.
- Fuzzy ownership: one table mixes content from multiple systems, and when something goes wrong it is often unclear who to call.

These costs look like "low efficiency" in normal times and like "large impact scope" when an incident strikes. Big-table incidents are often not one wrong cell; they are one change that should have stayed local, which spreads through a shared structure to places it should never have reached.

### The Cost of Splitting Too Finely

The other extreme is splitting into a large pile of small tables by feature, by system, or even by page. Small tables themselves are not wrong; what is wrong is what comes after the granularity loses control:

- Table count explodes, newcomers cannot find an entry point, and veterans only know their own patch of it.
- Cross-table references surge, and every split turns what used to be intra-table consistency into an inter-table reference, raising the probability of breakage.
- One feature change requires touching a dozen or more tables at once, and the coordination and scheduling costs come right back.
- Full validation has to walk every table and reference relationship, and each run takes longer and longer.

There is no standard answer for split granularity; the usual approach is to split by change unit first, then subdivide once clear hotspots appear, rather than pursuing structural perfect symmetry from the start. Table structure grows organically; it is not designed in one shot.

### Reference Relationships Are the Hidden Cost of Splitting

Once two tables are separated, the connection between them turns from "an agreement internal to one piece of data" into "a reference that needs explicit maintenance." This is the most underestimated part of a split decision:

- Every cross-table reference is a potential break point: if the referenced row is deleted or renumbered, the referencing side often does not report an error immediately, but instead manifests at runtime as a null reference or a default value.
- The legitimacy of a reference can usually only be confirmed during full validation, and the more references there are, the longer the validation chain.
- Circular references and implicit dependencies (connections held by naming convention or verbal agreement) make "changing one table affects who" hard to answer.
- Reference direction rots over time: what should be one-way slowly grows two-way, and the decoupling brought by splitting gets eaten away gradually.

A more robust practice is to keep reference relationships as explicit as possible: references expressed with a unified key type, the referenced side with clear delete protection, and full validation covering every reference path. Only once reference relationships are explicit does splitting have grounds; otherwise every split just adds a batch of unwatched seams.

### Naming and Conventions

Once tables multiply, naming is a direct source of search cost. In projects with confused naming, the common scene is the same concept having three names across three tables, and no one daring to merge. Some low-cost practices are worth settling early:

- Table names express content and purpose, not tool format or the author's habit.
- Primary key and foreign key naming are unified, so seeing a field name you can infer who it references.
- Temporary tables, deprecated tables, and debug tables have clear marking conventions and are not mixed with formal tables.
- Version suffixes like season number and batch number go uniformly at the end of the table name, so enumeration and search have a pattern to follow.

The value of conventions is not in rigor, but in consistency. A plain naming scheme that is executed consistently usually beats an elegant scheme where everyone writes their own.

### Conflicts When Multiple People Edit at Once

The shared table file is the starting point of the config system for many projects, and its limitations are also the most agreed-upon: whole-file locking leads to queuing, binary formats make diff and merge essentially unusable, and modification history cannot be traced. The reason row-level or field-level editing platforms are worth investing in is precisely that they move the conflict resolution point from the release stage to the editing stage:

- Two people editing different rows of the same table do not block each other.
- A conflict on the same row surfaces immediately on save, rather than exploding at export or release time.
- Every modification has a record of who and when, so accountability and retrospection have a basis.

The cost of resolving a conflict at the editing stage is often an order of magnitude lower than resolving it at the release stage. The former is two people confirming a number; the latter may be a rollback plus a round of investigation.

The shared-file era also tends to leave behind a habitual legacy: to avoid conflicts, people first copy a table and edit their own copy, then reconcile by hand afterward. These variant copies are a high-yield source of broken references and data drift; once platform-based editing lands, it is usually worth a dedicated cleanup round.

### Evolution of Table Structure

Table structure evolves just like code: add fields, change semantics, deprecate old columns. The difference is that config tables also face the reality that "previously released batches are still being referenced." The common pitfalls during evolution usually cluster in a few places:

- Field semantic drift: the column name did not change, but its meaning quietly did, so old batch data no longer matches the new interpretation.
- Add-only accumulation: deprecated fields are not dared to be deleted, and after a few years nobody can say which are still being read.
- Cross-version compatibility: new config depends on fields only new code recognizes, so old processes either ignore or error on load, and the behavior needs to be explicitly designed.

A more robust discipline is: express semantic changes with a new field; mark deprecated fields to stop writing first, observe for a while, then physically delete; before deleting, confirm no still-running historical batch references it. These actions look trivial in isolation, but accumulated they decide whether a table can still be safely modified years later.

### When It Is Worth Refactoring Table Structure

Refactoring has cost, so the trigger is usually a clear signal rather than aesthetics:

- A table becomes an editing bottleneck, with people queuing or frequently overwriting each other.
- One typical change has to cross too many tables, and the collaboration overhead is visible to the eye.
- Validation time or export time is long enough to affect the release rhythm.
- Newcomer onboarding time is clearly longer, and the most asked question is "which table do I change this in".

Refactoring is best scheduled in the gaps between content growth, and paired with a full data migration and regression validation. The biggest risk of a structural refactor is not failing to design a better structure, but quietly losing data or changing semantics during migration, and only surfacing on the player side after release.

### Common Pitfalls

- Splitting by data meaning rather than change unit, so one table spans three collaboration lines and no one fully owns it.
- Avoiding conflicts by copying tables, spawning a large number of variant tables used in only one place, with no one maintaining consistency.
- Building cross-table references on naming conventions and verbal reminders, so breakage manifests as strange default values at runtime.
- Table structure never evolving and being too afraid to evolve, so every new requirement gets solved by adding another table.

The judgment standard for splitting comes down to one thing: make the impact scope of one typical change commensurate with its real risk. A split whose impact scope exceeds the risk is waste; a split whose impact scope is smaller than the risk is a hazard.
