# Config Table Driven Development

## Category

production / config subtree. Node positioning: what config-driven changes is the cost structure of modifying system behavior—what goes into a table, what does not, and the global/server/player boundary. This is the charter of the config subtree.

## Definition


The value of config tables is often summarized as "designers can change numbers themselves." That is not wrong, but centering it on editing convenience underestimates the weight of the thing. What config-driven really changes is the cost structure of modifying system behavior: which changes can take effect within an hour, and which have to wait for a full release; which changes are decided directly by the people closest to the business, and which have to go through code review and a release window. Many projects do not fail because they cannot build the core technology; they fail because they hard-code into code what should belong to config, or, the other way around, stuff into tables what should belong to code, and in the end both sides pay a price.

So the first step in discussing config-driven is not picking a tool, and not designing a table format; it is answering a more fundamental question: what goes into a table, and what stays in code. Whether that boundary is drawn correctly often determines whether all the downstream validation, release, and collaboration design is smooth or awkward.

## Problem

Centering on "designers can change numbers" underestimates the weight of it: what should belong to config gets hard-coded (every numerical tweak needs a release), and what should belong to code gets stuffed into tables (the table grows an if-else forest), and both sides pay. Table-driven also brings new failure modes—broken references, type drift, test-environment tables ending up in production.


### What Problem Config Is Actually Solving

Whether a value is worth externalizing into config is usually not judged by whether it is "data", but by whether it meets a few conditions:

- Its change frequency is clearly higher than code: numbers, activity times, probabilities—the kind of thing that gets tuned almost every week.
- The decision power sits on the consumption side: how to tune it depends on operational data and player feedback; the programmer is not the person with the most say.
- The shape of the logic is stable: what changes is only the parameters, not the branching structure of the rule itself.
- Errors are observable and reversible: if it is changed wrongly, it can be discovered from metrics or feedback, and it can be rolled back to the previous version.

Changes that meet these conditions usually shrink the response cycle from "days" to "hours" once put into a table. Conversely, if a piece of logic requires changing its branching structure every time it is adjusted, then no matter how much it looks like data, it is fundamentally code; forcing it into a table only disguises the absence of code review as "just changing a table".

### What Usually Suits Going Into a Table

Common content that goes into tables falls roughly into these categories:

- Numerical parameters: damage coefficients, health values, growth curves, economic output and sinks.
- Mapping relationships: level to experience, item to icon, error code to message text.
- Static rules: activity open times, quest completion conditions, feature unlock thresholds.
- Content arrangement: drop pools, shop shelves, page sections, announcement copy.
- Switches and thresholds: gray release ratios, rate-limit thresholds, feature on/off.

The common feature of this content is "the value changes, while the shape of the rule stays stable." This is exactly the kind of change a table is good at carrying: once the structure is fixed, the remaining work is long-term value entry, validation, and release, on a stable and predictable rhythm.

### What Often Does Not Suit Going Into a Table

The most typical slippage in a config system starts from "storing parameters" and slowly grows condition expressions, nested rules, and dynamic branches, until it becomes a half-implementation of a programming language. Once it gets there, the config has lost its data character: no compiler, no debugger, no unit tests, no code review, yet it carries logic complexity at the scale of code.

The following content is usually better kept in code:

- Real control flow: logic whose branching structure itself changes with requirements.
- Cross-system sequencing: processes where multiple systems have ordering dependencies and transaction boundaries.
- Asset settlement: core paths involving currency, payment, and grants; these are usually preferred to go through code review and testing.
- One-off needs: building a generic config structure for some temporary activity is often more expensive than writing a bit of code that gets deleted quickly.

The judgment can be very plain: if changing something requires understanding context to avoid mistakes, it deserves the tooling of code; only when changing it is just swapping a value is it suited to going into a table.

### Global, Per-Server, and Player: Another Boundary

Beyond "does it go into a table or not", config also has the question of "which layer it goes on." Putting the same parameter at the global layer, the channel layer, or the per-server layer has completely different modification costs and impact scopes:

- Global parameters: consistent across all servers, a single change takes effect, and usually also the most strictly validated layer.
- Channel and platform customization: the same logic behaves differently across different distribution channels, often implemented via an override mechanism.
- Per-server customization: content operated per server, such as activity times and server-open schedules, is usually configured separately per server.
- Player-level state: data that follows a person, such as progress and claim records, is usually not considered config; mixing it into config tables is often the source of incidents.

Once there are many layers, override relationships get complex: when the same value appears at multiple layers, which layer wins needs a clear rule inside the system. When troubleshooting "why is this server different from the others", if the override relationships cannot be explained, debugging turns from checking data into archaeology.

### New Failure Modes Brought by Table-Driven

Config errors and code errors look very different. Code errors usually surface on the spot: compilation fails, tests fail, the process crashes. Config errors more often manifest as rule incidents:

- Numerical anomalies; player rewards swing high and low.
- Activities open or close at the wrong time.
- Drops and rewards do not match design expectations.
- Broken resource references; blank or wrong content appears in the UI.

These problems do not crash the process and do not necessarily show up immediately; they slowly surface from business metrics, player feedback, or support tickets, and by the time they are noticed they may have been going on for days. Config-driven raises the speed of change while also stretching out the exposure time of errors; these two things are two sides of the same coin.

### Config Release Should Be Treated as a Formal Release

Because config changes are frequent, act directly on production, and are slow to surface, config release usually needs the same infrastructure as a code release:

- Versioning: every release is a traceable batch, so you can say clearly what actually changed this time.
- Gray release: take effect first on a single server or a small ratio, then scale up after observation.
- Effectiveness confirmation: the server reports back the version it loaded, to avoid the platform showing "released" while some processes are still running old values.
- Rollback: one click back to the previous batch, rather than relying on re-editing by hand.

Treating config release as "just pushing a table" is the most common starting point for this class of incident. Put the other way, how seriously a project takes config release often predicts its operational incident rate better than how seriously it takes code release.

### The Boundary Is Not Drawn Once

Early in a project, one big table plus a bit of generic loading logic is often enough. Once operational density ramps up, this boundary gets repeatedly stressed; common signals include:

- The same field is repeatedly requested to go into and out of the table, which means the judgment about its nature of change keeps wavering.
- The config piles up a lot of special-case branches, with correctness maintained by comments and verbal agreement.
- Programmers are repeatedly forced to release because of "just changing a parameter" needs, which means what should be externalized was not.
- Production shows "the config was not changed wrongly but the behavior is wrong" disputes, which means the responsibilities on both sides of the boundary cannot be explained clearly.

When these signals appear, it is usually worth stopping specifically to redraw the boundary, rather than continuing to patch both sides. Adjusting the boundary itself has migration cost: table structure has to change, loading logic has to change, and already-released historical config has to be handled accordingly, so each adjustment is worth figuring out the bill clearly beforehand.

### How Agreements Harden Into Mechanisms

In a small team where designers and programmers sit together, verbal communication often covers most boundary ambiguity. Once the team splits up and the desks move far apart, verbal agreements start to fail, and the common approach then is to harden these agreements into mechanisms:

- Use field-level descriptions and comments instead of word-of-mouth explanations of purpose.
- Use validation rules instead of the verbal reminder "this value cannot exceed so much".
- Use an approval flow instead of the confirmation style of "shout when you are done".

These mechanisms look like process overhead, but in reality they move communication cost from people onto the system. The maturity of a config pipeline is often not reflected in how powerful its tools are, but in how many agreements that used to rely on people's memory have become system guarantees. Conversely, if a team frequently has "I thought you knew" config incidents, it usually means a lot of agreements are still hanging at the verbal level.

### Common Pitfalls

- Treating "free to edit" as the whole goal of a config system, with no validation, no gray release, and no rollback, so the faster you change, the faster you err.
- Building the config system into a half-implementation of a programming language, trading verifiability for expressiveness, and ending up with no one daring to touch it.
- The boundary wavering for a long time, sometimes stuffing logic into the table, sometimes releasing for small changes, so neither path accumulates trust.
- Remembering trace-keeping and audit only after an incident, so during troubleshooting you can only dig through chat logs and file modification times.

What config-driven is truly worth pursuing is to land each class of change on the release path with its lowest cost, rather than cramming all changes into the fastest path.
