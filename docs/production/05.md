# Config Tables and the Data-Driven Pipeline

## Category

production / configuration pipeline. Node positioning: config tables and the data-driven pipeline are the formal primary release path — the six-piece pipeline, lineage audit, and controlling the bloat of a "half a programming language."

## Definition


Many online incidents are not caused by wrong code, but by configuration arriving at the wrong time, in the wrong format, and flowing into the wrong environment. For a long-running operational project, config tables and the data-driven pipeline are themselves the formal primary release path, not a designer-tool detail. They reach the live environment more often than code does, and when they fail they are subtler.

What makes configuration problems dangerous is not that they "can change rules," but that one end connects to designer expression and the other end connects to client and server execution, passing in between through export, validation, release, gray release, activation, and rollback links. If any one of those links loses control, the end result is an online rule incident.

## Problem

Configuration incidents are subtler than code incidents: they touch the live environment more often and are harder to locate when they fail, and "a test table got shipped to production" is a high-frequency incident on long-running projects. The root tension is between "free to edit" and "safe and controllable" — without lineage and audit, you cannot assess the blast radius of one wrong config; once the config system bloats into half a programming language, it also loses the reviewability that was configuration's most valuable property in the first place.


### Why configuration incidents are often harder to handle than code incidents

When code fails, the team can usually still lean on the compiler, tests, and crash logs to localize relatively quickly. When config fails, the problem more often shows up as:

- abnormal numbers
- wrong event activation conditions
- drops and rewards that do not match expectations
- page content and asset mapping mismatches
- some environments activated, some environments did not

This kind of problem does not necessarily crash immediately, and does not necessarily surface immediately; it often leaks out slowly through business metrics, player feedback, or long-chain data, and the localization cost is high.

### What a complete configuration pipeline really contains

A mature configuration pipeline is not just "export tables to JSON." It usually includes at least:

- schema definition and field constraints
- editing and data-entry conventions
- type and reference validation
- dependency analysis and diff comparison
- export generation and environment isolation
- release approval, gray release, and rollback records

Only when all of these links are connected does configuration formally enter the scope of engineering governance.

### Why "free to edit" is not the most important goal of a configuration system

Many configuration tools emphasize ease of use and flexibility early on, and that is of course important, but what really determines system quality is usually not "how fast can it be changed," but:

- which fields are allowed to be adjusted at high frequency
- which fields must go through stricter review
- which changes depend on a new client or new server capability
- which changes can be gray released, and which must switch over as a whole

An excellent configuration pipeline does not let everything be changed freely; it explicitly tiers changes by risk level.

### Why configuration lineage and audit must exist

Once a configuration problem surfaces online, the team usually needs to answer:

- who changed this rule
- which validations the change passed
- in which environments and when it took effect
- whether it is coupled with other tables or assets

If the system cannot answer these questions, then downstream you can only rely on chat logs, shared-table history, and human memory to troubleshoot. Configuration lineage, diff audit, and activation records exist precisely to avoid this low-efficiency form of troubleshooting.

### Why configuration systems most easily grow quietly into "half a programming language"

In pursuit of generality, many teams keep adding to the config system:

- conditional expressions
- nested rules
- dynamic branches
- functional fragments

In the short term this looks like fewer code changes, but long term it strips configuration of its data properties, turning it into an intermediate species that has neither a programming toolchain nor a configuration governance toolchain. It is hard to validate statically and hard to operate stably.

### A more sound approach

A more sound direction is usually:

- let configuration carry parameters, mappings, and static rules
- let scripts or code carry real execution logic
- fill out the config system's schema, diff, approval, gray release, and rollback capabilities
- treat configuration release as a formal version activity, not "just casually pushing a table"

The core of doing this is to keep configuration as governable data, rather than letting it become invisible code that nobody dares to touch.

### Common Pitfalls

The most common error is building the configuration system as a bundle of export scripts and shared tables, and only investigating manually after an incident. The second type of error is making the configuration language half a programming system in pursuit of flexibility, ending up hard both to validate and to operate. The third type of error is that configuration release frequency has already far exceeded code release, yet there is still no version, audit, or rollback capability, ultimately exposing high-frequency change as high-frequency incidents.

### Case Study: A Configuration Pipeline Investigation of "A Test Table Shipped to Production, Output Jumped Tenfold"

> The case is a demonstration example (not drawn from a real project); numbers are rounded for simplicity. It puts this page's "Why configuration incidents are often harder to handle than code incidents," "What a complete configuration pipeline really contains," "Why configuration lineage and audit must exist," "A more sound approach," and "Common Pitfalls" into the deep end: configuration release is the formal primary release path — this is a full investigation of a test-only table getting mixed into a production release.

**Background and symptoms**: a long-running operational project whose configuration release frequency is far higher than code release (a dozen-plus times per day versus once a week). The performance group had maintained a load-test-only table on the dungeon drop table (drop multiplier 10, used to stress-test the drop chain), and the release page of the config platform had "target environment" defaulting to "all environments." At **10**:**00** that day, a one-click release merged all pending changes of the day and carried them into production, with the load-test table riding along with the event configuration. At **13**:**40**, the trading-post price index alarmed: core material dropped **35**% in **2** hours, and screenshots of players hoarding material began appearing in player channels; output monitoring converted, and gold daily output went from **1**M to **4.15**M. No crashes throughout, no errors, type validation all green.

### Step 1: Symptoms and Definitions — First Separate a "Numbers Incident" From a "Code Incident"

Unified definitions: gold daily output is measured on the all-server gameplay output caliber (faucet caliber, excluding top-up exchange), booked by gameplay channel. One entry recorded before the incident and one after:

- **Baseline**: daily output **1**M (daily play **0.55**M + dungeon **0.35**M + event **0.1**M)
- **Incident day**: converted **4.15**M, increment **3.15**M

The problem is not at the execution layer — the code did not change and validations all passed, so first break the output ledger apart by channel.

### Step 2: Layered Attribution — The Configuration Ledger From Output Caliber to Release Records

```text
Baseline ledger   Gold daily output 1M: daily play 0.55M + dungeon 0.35M + event 0.1M
Anomaly ledger    Incident day converted 4.15M: daily play 0.55M flat + dungeon 3.5M + event 0.1M flat, increment 3.15M all in dungeons
Multiplier ledger Dungeon 0.35M -> 3.5M is exactly 10x — the release diff holds a line "drop multiplier 10," from the load-test-only table
Rollback ledger   Hit the previous stable version, platform rollback took 10 minutes to take effect; the 5h20m incident window over-issued about 0.7M
```

Ledger close-out: the entire **3.15**M increment comes from the dungeon chain, dungeon output **0.35**M → **3.5**M is exactly **10**× — the release record's diff holds a line "drop multiplier **10**" from the performance group's load-test-only table. This page's "some environments activated, some did not" comes true in its most glaring form: not "some environments activated," but "the environment that should not have activated did activate."

### Step 3: Root Cause — Validation Answers "Is It Correct," Not "Should This Be Released"

Checked against this page's "What a complete configuration pipeline really contains" six-piece set — schema, data-entry conventions, type and reference validation, dependency diff, export-environment isolation, approval/gray/rollback — type validation was present (the load-test table itself was perfectly legal in format), but two things broke: the schema had no "environment-specific" field constraint, so the test table passed through the production release chain unimpeded; "target environment" defaulted to all environments, so release approval was swept along by "one-click merge." Against the lineage four questions: who changed it is traceable, which validations it passed is traceable, "is it coupled with other tables" cannot be answered — the coupling between the load-test table and the dungeon drop chain was never registered, so localization could only be done by flipping through diffs table by table, costing an extra hour beyond the rollback itself. This page says "treat configuration release as a formal version activity, not 'just casually pushing a table'" — this one was exactly a "casual push": the one-click release swept the entire pending list away without distinguishing it, exposing high-frequency change as a high-frequency incident.

### Step 4: Remediation and Write-Back — Rollback Relies on Version Records, Localization Starves for a Lineage Ledger

The fix has two stages. Emergency: hit the previous stable version in the config platform, rollback completed at **15**:**20** — rollback took **10** minutes to take effect, alarm to rollback effective was **100** minutes; clean up trading-post and backpack cache indexes per the downstream list; the incident window of **5** hours **20** minutes converted at the over-issue rate of **3.15**M/day over-issued about **0.7**M, offset by that week's recovery event (cosmetic sink plus trading-tax sink), with no negative clawback. Recheck: the next day output fell back to the **1**M baseline, and the material price index recovered within three days. Four institutional steps: add an "environment-specific" field constraint to the schema and have the production release pipeline intercept test-only tables; force a second approval when a release diff exceeds threshold (changes to multiplier-type fields beyond **2**×); register table → system coupling into the lineage ledger, and check downstream before rolling back; make the release page's target environment an explicit selection and forbid defaulting to all environments — keeping configuration as governable data.

**Backfill Checklist**:

### Three Lessons From the Case

1. **Validation passing only proves the format is legal, not that this is the right place to release** — environment is part of configuration, and a schema that cannot govern environment makes isolation an empty phrase.
2. **Configuration rollback is far cheaper than code rollback, on the premise that version and lineage are built first** — this stop-loss took only **10** minutes, because the platform had built version records early; lineage lacked coupling registration, and localization took an extra hour.
3. **The higher the release frequency, the lower the governance bar cannot go** — configuration releases a dozen-plus times a day, and any default checkbox gets amplified into a daily incident.
