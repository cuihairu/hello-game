# 客户端技术栈与引擎

讨论客户端技术栈时，最容易犯的错就是把“选什么引擎”当成核心问题。真正影响项目成败的，往往不是引擎名字，而是引擎能力、项目层框架和业务运行时之间的责任划分有没有清楚。

引擎能帮你解决渲染、场景、动画、资源加载、平台抽象和部分工具能力，但它不会自动给你一个适合当前项目的客户端系统。项目一旦进入多端适配、长期迭代、大量内容生产和频繁版本演进阶段，真正重要的是：哪些能力直接用引擎，哪些能力要在项目层自己建，哪些能力必须从第一天就按运行时系统来治理。

## 为什么客户端技术栈会成为主工程问题

客户端不是“把画面显示出来”这么简单。它通常同时承担：

- 输入采集与反馈
- UI 和交互状态管理
- 渲染和表现层调度
- 资源加载、缓存和释放
- 网络协议接入和局部预测
- 平台 SDK、支付、登录、推送等集成
- 性能调优、包体控制和兼容适配

这些能力一旦都挤在同一个进程里，架构问题就会非常集中。如果项目层没有主动把职责拆开，后面很容易演变成“引擎层、业务层、工具层互相穿透”的混乱局面。

## 引擎到底解决什么，不解决什么

成熟引擎通常擅长解决的是底层运行时共性：

- 渲染管线与资源格式支持
- 动画、粒子、音频和场景系统
- 平台适配与构建打包
- 编辑器和内容预览工具
- 基本脚本宿主和插件体系

但引擎通常不替你解决下面这些项目级问题：

- UI、玩法和模块之间的边界
- 页面切换和运行时状态管理
- 资源分包、热更和版本兼容策略
- 多团队协作下的工具链治理
- 线上性能与异常问题的定位闭环

所以引擎更像地基和公共设施，不等于整套项目架构。

## 为什么很多项目会卡在“引擎够用，但项目越来越难改”

这通常不是引擎不够强，而是项目层框架没有成型。常见表现包括：

- UI 页面和玩法逻辑直接互调
- 资源路径、特效、音频和配置散落在业务代码里
- 平台 SDK 回调直接侵入业务状态
- 性能问题出现时找不到明确责任层
- 每次版本升级都像拆炸弹

一旦客户端承担的职责越来越多，没有项目层框架去吸收复杂度，后面所有问题都会直接堆到“客户端技术栈”这个大筐里。

## 技术栈选型真正要看什么

### 项目是跨端优先，还是单端深挖

如果目标是多平台共享大部分逻辑，技术栈必须优先考虑平台抽象、资源管线统一和适配成本；如果目标是某个单端平台的极致表现，选择会完全不同。

### 内容生产方式是什么

重内容项目和重玩法项目对引擎和工具链的要求不一样。前者更依赖编辑器能力、资源流程和美术工作流，后者更看重运行时架构、性能稳定性和快速迭代能力。

### 版本节奏和热修复压力有多大

如果项目需要频繁发包、快速修复和灰度能力，那么脚本层、分包、热更和线上诊断能力都会直接影响技术栈判断。

### 团队真正能维护什么复杂度

自研框架和深度改造引擎不是不能做，而是必须问清楚团队未来几年是否真能长期维护。

## 更稳妥的做法通常是什么

比较稳妥的客户端技术栈，通常遵循这样的分层：

- 用引擎承载通用运行时能力
- 用项目层框架约束模块边界、页面组织和资源访问
- 用工具链和构建流程承接内容生产与版本管理
- 用脚本层、数据驱动或热修复能力应对迭代压力

这样做的关键，不是“层数多”，而是让复杂度有明确落点，而不是全部堆在引擎工程和业务代码之间。

## 常见误区

最常见的错误，是把客户端当成纯表现层，低估它本身的系统复杂度。第二类错误，是把引擎当成项目架构，结果所有业务边界都被默认交给引擎插件和脚本去兜。第三类错误，是为了灵活性把过多裁决和状态管理塞进客户端，后面在安全、同步和一致性上一起付出代价。
