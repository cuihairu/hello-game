# Hard-Real-Time Competitive Architecture

## Category

design / problem-domains subtree. Node position: crosswise quick reference for the hard-real-time competitive problem domain — who calls the shots, how state syncs, how you catch up when you stall, how you stop cheating.

## Definition


This page generalizes hard-real-time competitive projects from the problem-domain angle, and like the others it is the crosswise quick-reference edition of the corresponding main-line chapters. It does not expand the full derivation of the sync model; instead it puts the key judgments that distinguish this kind of project from other types onto one page: who calls the shots, how state syncs, how you catch up when you stall, how you stop cheating.

One-sentence portrait: state is tightly coupled, time is sensitive at the millisecond level, and adversarial outcomes must be explainable and re-checkable. MOBA, FPS, fighting, racing, and real-time action competitive all fall into this portrait. It shares a short session boundary with the room-based session type, but its time and consistency requirements jump up by an order of magnitude, and the architectural shape is correspondingly entirely different.

## Problem

The four key judgments for competitive projects (determinism versus authoritative adjudication, frame catch-up versus correction, the anti-cheat surface, the sync shape) are scattered through the main-line derivation, and review needs a one-page consolidation. Nearly every solution disagreement in this kind of project traces back to a combination of these four judgments.


### Characteristics of this problem domain

- Players are extremely sensitive to input latency; a difference of tens of milliseconds often decides the outcome directly.
- State coupling is high; a single hit judgment pulls at health, skills, buffs, economy, and UI across several chains.
- Adversarial fairness is the product's lifeline; whichever side gains a time or information advantage gets amplified into public reaction.
- In-session input density is high, so bandwidth and message rates are naturally high.
- The cost of errors is concentrated: reconnection, rollback, and ruling a loss all happen at the most intense moments of combat.

### Core trade-off: determinism or authoritative adjudication

The first judgment this kind of project cannot avoid is how the server calls the shots. There are two common routes, each with clear costs.

- Frame sync route: the server only relays input, and each end advances the same deterministic logic in the same order. Bandwidth is extremely cheap and replay comes free, at the cost of requiring fully deterministic logic — floating point, random sources, and traversal order all have to converge — and the client holds all the logic, so the anti-cheat surface is noticeably larger.
- State sync route: the server advances state authoritatively, the client sends intent and receives results, paired with prediction and rollback. The anti-cheat surface is smaller and logic can be hot-fixed on the server, at the cost of high bandwidth, heavy server compute, and feel that depends on prediction quality.
- Real projects are often a hybrid shape: core adjudication runs authoritative, the presentation layer runs prediction and interpolation, and some weak-adversarial information is distributed with frame-sync thinking.

The basis for the judgment is usually the product form rather than technical preference: small-scale, tightly contested, closed-logic projects tend toward frame sync; large-scale open-contest projects that need server-side operational intervention tend toward authoritative state sync.

### Trade-off between frame catch-up and correction

The second set of constraints in hard-real-time competitive comes from network jitter. On either route, the client and the server fall out of rhythm, so designing a frame catch-up strategy up front is usually a hard requirement.

- Prediction needs a boundary; usually only your own actions are predicted, not other people's or random events.
- Rollback needs to be perceivable; when the correction magnitude is large it is usually paired with visual smoothing to avoid characters teleporting.
- Frame catch-up needs a budget; the maximum number of steps a single frame can catch up must have an upper bound, otherwise you easily enter a death spiral where chasing makes things slower.
- When falling too far behind, the common practice is to switch to snapshot recovery and give up on chasing frame by frame.
- Which systems are allowed to skip presentation and which adjudications are not allowed to be skipped must be settled in the layering.

Projects without a catch-up budget often end up with reconnection that is forever loading; projects without a correction strategy have players notice the state mismatch before the system does.

### Differences in the anti-cheat surface

The two routes differ a lot in anti-cheat surface, which is an important part of the trade-off.

- Under frame sync the client holds all the logic; wallhacking, frame editing, and acceleration cheating are hard to root out at the protocol layer and usually rely on behavioral detection, recording review, and server-side cross-validation.
- Under authoritative state sync the client sees only partial information; the cheat surface concentrates on protocol forgery and input anomalies, and server-side validation is usually more direct and effective.
- Both routes need to land key events on an accountable logical timeline, or complaint review and dispute arbitration have no evidence.

### Common solution shapes

Match services usually organize processes per session: one session, one or a group of entities, in-session advancement on a fixed Tick, adjudication events carrying a frame number or sequence number.

- The access layer maintains connections and routing, handling weak-network awareness and reconnect localization.
- The match service maintains an authoritative clock or authoritative frame number, and the client's local clock continuously converges on it.
- Recording and replay usually derive directly from the sync system: frame sync stores the input sequence, state sync stores key snapshots plus an event stream.
- Spectating and trust mode reuse the same event stream, avoiding a separate relay chain.

A common engineering consistency measure is periodic reconciliation: the server samples and checks client state hashes, or the same logic is cross-checked between two ends, so drift is found mid-match rather than after it.

### Pitfalls specific to this type

Treating determinism as a slogan: a floating point or one hash traversal left in the logic, tests pass fine, then after launch some device class diverges, and it is hard to reproduce.

Replay and live play disagree: replay runs one logic version, production runs another, and replay of a disputed session does not line up, which actually damages credibility.

Prediction without a boundary: fully predicting other people's actions and random results, so one network hiccup rolls the whole screen back and feel is worse than no prediction.

Frame catch-up without an upper bound: infinitely filling frames when behind, CPU pegged and latency growing, so the more you chase the further behind you are.

Anti-cheat relying on protocol only: client trust handed entirely to encryption and obfuscation, with no behavioral detection, so after a few rounds of cheat-tool iteration the whole line of defense fails.

### Common pitfalls

- Applying single-player feel directly to online competitive play, treating the time model, prediction, and correction as details to be filled in before launch.
- Treating frame sync versus state sync as a matter of faith rather than a trade-off to be made on contest scale, logic closure, and anti-cheat needs.
- Verifying sync only under normal operation, not under weak network, reconnection, frame catch-up, and background switching.

The architectural direction of this kind of project is usually summarized as: a single authority on time, prediction with a boundary, frame catch-up with a budget, and the anti-cheat surface chosen together with the adjudication route.
