# Room-Based Session Architecture

## Category

design / problem-domains subtree. Node position: crosswise quick reference for the room-based session problem domain — characteristics, constraints, solution shapes, the pitfalls specific to this type, all in a one-page comparison.

## Definition


This page generalizes room-based session projects from the problem-domain angle. It is the crosswise quick-reference edition of the book's problem model chapters. It does not re-derive why this kind of project is hard; instead it compresses the problem-domain characteristics, the architectural constraints derived from them, the common solution shapes, and the pitfalls specific to this type onto a single page, suitable for quick comparison during solution review, project inventory, or when you are unsure which direction a given project should go.

One-sentence portrait: most critical state closes inside a single session, the room is the unit of state birth and death, and only trustworthy results are kept outside the session. Mahjong, Dou Dizhu, party games, pool, light shooting, and short-session auto battlers all fall into this portrait.

## Problem

What solution review needs is a quick reference, not a re-reading of the derivation: the judgments for room-based projects concentrate on three things — state closing within one session, organize-and-discard service arrangement, and the out-of-session chains (matchmaking / settlement / anti-side-betting) being underestimated. When you are unsure about a project's direction, a one-page comparison is faster than flipping through the whole chapter.


### Characteristics of this problem domain

- State lifetimes are measured in sessions: a session ends and most runtime state becomes void with it.
- Session boundaries are clear; entering, leaving, and reconnecting all have explicit time windows.
- Players inside a session are tightly coupled; any single person's anomaly can drag down the whole session's experience.
- Out-of-session assets are decoupled from in-session process; settlement results are the only interface between the two.
- Session starts, session ends, reconnects, and settlements happen at extremely high frequency, while the value of any single state is very low.

None of these characteristics is hard on its own; the difficulty is in their combination: state is short-lived and high-frequency, and errors land directly on the points players are most sensitive to.

### Boundaries with adjacent types

Crosswise, room-based session is most easily confused with three other kinds of project, and mistaking the type often sends the whole architectural direction off course.

- Compared with the persistent online world type, it has no world state requiring long-term maintenance; the unit of scaling is the room rather than the map, so capacity issues are easier to slice and reclaim at room granularity.
- Compared with the hard-real-time competitive type, its requirement for millisecond-level consistency is usually looser; card and party games commonly get by with state sync alone and usually do not need frame sync or lockstep.
- Compared with the long-cycle progression type, its in-session state does not require versioning or migration; what truly needs long-term governance is the out-of-session points, records, and reputation.

To judge which type a project belongs to, a common approach is to look at the dominant contradiction: if word-of-mouth depends mainly on "fast to start, stable in-session, accurate settlement," it is room-type led, even if it also hangs growth, event, and monetization systems off it.

### Architectural constraints derived from the characteristics

Short-lifespan state constrains state organization: in-session state either resides as a whole in a single process or can be snapshotted as a whole; it is rarely worth introducing cross-process shared storage for it.

High-frequency session start and end constrains the resource model: room creation and destruction should be cheap operations. The metrics teams usually watch are concurrent rooms per node, room cold-start latency, and the completeness of reclamation after destruction.

Room-granularity scaling constrains the scheduling approach: scaling up and down usually happens by migrating rooms or by draining nodes, rather than by player session, which means rooms and nodes need a rebuildable ownership relation.

Settlement consistency constrains the write-back chain: wins, rewards, points, and records usually land in out-of-session assets through a single idempotent, auditable, compensatable chain, rather than having multiple services each write on their own.

### Common solution shapes

Separating lobby from match is the most common shape: the lobby layer handles login, matchmaking, team formation, and out-of-session state; the match layer handles in-room advancement, broadcasting, and authoritative adjudication; the two layers interface through the settlement contract.

- A room state machine is nearly standard equipment, with explicit transition conditions for each of creation, ready, start, running, abnormal, settlement, and destruction; disconnect, trust mode, and timeout all map onto the state machine.
- Matchmaking and room formation are usually separate services, bucketing by rank, latency, and team relationships to assemble a session, with room instances assigned to a node only after the session is assembled.
- Disconnect reconnection is usually implemented as a recovery window plus room snapshot: inside the window it restores to the pre-disconnect state, outside the window it switches to trust mode or rules a loss.
- The switching point between trust mode and real-player input must be fixed in the state machine, or disputed sessions will often be unable to say what happened in the middle.

The common practice for the settlement chain is to funnel it centrally: at match end, an authoritative settlement sheet is produced, and the settlement service writes back assets, rankings, and records in one place, with failures retryable and no double payout.

### Quick-reference judgments on capacity and scaling

- Scale on the number of rooms a node hosts, not on the online count.
- For projects with pronounced peak-to-valley difference, scaling usually runs on queue depth and room creation rate, and contraction by draining.
- The heavier the in-room state, the larger the blast radius of a single node failure; the common practice is to cap rooms per node and keep match logs so settlement can be replayed.
- During a version update, the common strategy is to let matches on old nodes end naturally before reclaiming them; letting a match survive across versions is rare.

### Pitfalls specific to this type

The room server gets stuffed into a mini world: friends, events, inventory, and payment callbacks all move into the room process, binding the room lifecycle to out-of-session systems, which makes scaling, migration, and abnormal recovery heavier as a result.

Missing post-session governance: teams often care about matchmaking and session start but not about log archiving, settlement confirmation, and resource reclamation; over time nodes fill up with dirty instances and unreclaimed state.

Reconnection as merely "try your best": no recovery window, no snapshot, no trust-mode switching point, so when a player comes back they either cannot get in or see a wrong board state.

Settlement written on the fly: multiple services each change points and issue rewards; if one step in the middle fails you get dirty states such as "result recorded but reward not issued," which are hard to compensate afterward.

### Common pitfalls

- Treating "a session is short" as "the backend is light," so that high-frequency session starts, disconnect recovery, and settlement disputes amplify local problems into global failures.
- Using a world-type monolithic architecture for a room-based game, where the system is heavy and the payoff is low, dragging the development rhythm apart.
- Treating the crosswise quick-reference conclusion as a complete derivation, seeing the three words "room type" and applying the solution, without first confirming that the dominant contradiction really is session rather than world.

The architectural direction of this kind of project is usually summarized as: state is short and boundaries are clear, rooms are independent and can be born and die, and settlement is the only trustworthy exit.
