# What This Page Is For

## Category

design / problem-domains subtree. Node position: usage instructions for the problem-domain quick reference — when to look it up, which dimensions to compare, how it divides work with the main line and the type topics, and the order of typing.

## Definition


This page explains how to use this group of problem-domain appendices and how it divides work with other content. The previous pages each generalized the key judgments of one class of project; this one answers the more practical questions: when to flip to this group of appendices, how to compare once you are there, and where to go back to afterward.

One-sentence portrait: this group of appendices is a crosswise quick-reference table, not an architectural answer. It compresses the conclusions derived by the main line, by problem domain, into page-by-page comparisons, and is suitable for locating — as fast as possible, after you understand the causes — "where this kind of project's money and risk roughly sit."

## Problem

The only misuse is copying the quick-reference pages as architectural answers: they compress judgment conclusions, not derivation processes. The correct path is to type first (six questions), then compare against the quick reference, and finally return to the main-line chapters to read the derivation.


### What questions does this group of appendices answer

What answers are given by clustering on problem domain are a very specific class of question: several candidate directions are laid out side by side, and which one fits this project's dominant contradiction best.

- What it gives is the shared judgments of same-type projects: which stage this kind of project usually pushes complexity onto, and where its special risks usually grow out of.
- What it gives is the yardstick for comparison: how state is shared, how time advances, asset complexity, and operations intensity — with those four dimensions fixed, comparison no longer lets everyone talk past each other.
- What it gives is a list of common pitfalls: these pitfalls recur across same-type projects, and comparing item by item at review time often catches some of them in advance.
- What it gives is the language of typing: room type, competitive type, world type, progression type, platform type, so the team has shared words when discussing "which kind do we look like."
- What it gives is a starting point for questions: the summary sentence at the end of each page is prepared for use after comparison, pointing out which questions to take back to the main line.

It does not answer "why" — causal derivation is left to the main line; and it does not answer "how exactly to do it" — parameters and implementation details are left to the individual engineering chapters.

### Which dimensions to look at when comparing

Four comparison dimensions recur across the quick-reference content of each page; going through them one by one at review time is often more effective than open discussion.

- State sharing: where critical state closes, how many boundaries it crosses, and who holds final interpretive authority.
- How time advances: frame by frame, event by event, or transaction by transaction, and whether tolerance for time error is at the millisecond level or the day level.
- Asset complexity: the number of asset kinds, issuance entry points, and economic closed loops, which decide the audit and reconciliation burden.
- Operations intensity: the frequency of events, compensation, versions, and rollback, which decides how much change the config chain and the data chain have to absorb.

Once the dimensions are fixed, comparing two projects is on the same scale; otherwise discussion easily slides back into a dispute of feeling about "we are different."

### Division of work with the main-line chapters

The main line unfolds by cause and effect: one problem is derived from cause to solution and cost; this group of appendices unfolds by crosswise clustering, compressing the conclusions of different projects into quick-reference tables. The two organizational methods serve different moments.

- When learning a mechanism for the first time, or when designing a specific system, you usually go through the main line, because to use a solution correctly you first have to understand why it takes that shape.
- At solution review, project inventory, and technical sharing, you usually flip to this group of appendices, because those moments call for fast comparison rather than complete derivation.
- When reviewing a live incident, both sides are often used together: first use the appendix to locate "which kind of project's historical pitfall does this resemble," then return to the main line for the derivation and details of the corresponding mechanism.
- When project background is not yet complete, the appendix provides genre cross-reference while the main line keeps the derivation of "why it is hard." Combining the two lowers the gap of understanding in team communication.

Substituting the appendix for the main line leaves conclusions without explanatory power; substituting the main line for the appendix leaves discussion without efficiency. A common practice is to treat the appendix as an index into main-line conclusions rather than as a summary replacement for the main line.

The correspondence between the typing language and the main line's six problem models is also worth spelling out. Of the five problem domains, room type, competitive type, world type, and progression type each echo a same-named model in the main line, and platform type corresponds to the economy-and-platform model. The only one folded in is the main line's high-frequency-objects-and-heavy-presentation model: the object throughput and presentation density it cares about rarely drive architecture on their own in real projects, and usually attach to dense-object scenarios in the world type or large-scale same-screen scenarios in the competitive type; and its other half, hot-spot read and write pressure, is often governed together with trading safety in economy and platform, so at typing time it is merged into platform type without a separate type. Models allow overlap and are an analysis tool; problem domains are classification labels and are required to guide scheduling. When the two sides do not line up, the usual move is to take the model analysis as authoritative and re-type.

### Division of work with the game-type appendices

There is another set of sister appendices in the book, clustered by game type (Appendix A1, the game-type topics), and this group is a different lens: one group speaks by genre, one group speaks by problem domain, and they look at the same set of projects.

- The genre view is closer to a team's everyday communication, suitable for aligning with designers, producers, and publishers, and answers "what kind of game is this."
- The problem-domain view is closer to architectural judgment, suitable for use in technical solutions, and answers "which class does the dominant contradiction belong to, and where do the constraints come from."
- The two labels often disagree: a product that looks like a casual genre may, because of high-frequency trading between players, actually land in the economy/platform problem domain.
- The genre appendix is good at building intuition and organizing cross-functional discussion; the problem-domain appendix is good at setting the architectural tone and bounding the risk surface.
- A common practice is to organize discussion with genre labels first, then use the problem-domain judgment to fix the architectural direction; when the two disagree, the problem domain is authoritative.

The same set of projects yields two different quick-reference conclusions under the two lenses, and this is not a contradiction: genre conclusions answer players' and colleagues' questions, problem-domain conclusions answer architectural review's questions, and mixing the two conclusions is actually the most common source of misuse.

Genre is not an architectural conclusion, and neither is problem domain. What each provides is a set of priors; the real shape still has to be derived from the constraints of the specific project.

### How to type a project

Typing is the first step in using this group of appendices and the step most easily taken the wrong way. A common approach is to look at behavior and cost rather than at the type labels on the marketing page.

- Look at state: state born and died per session is room type; state accumulated per account is progression type; state resident per world is world type.
- Look at time: millisecond-level sensitivity is competitive type, minute and hour level is room type, day and year level is progression type.
- Look at the direction money flows: assets moving between players and the system is progression type; assets being transferred heavily between players is platform type.
- Look at operations intensity: when the frequency of events, compensation, and rollback exceeds gameplay iteration, the operations chain is the dominant contradiction.
- Look at incident shapes: where the few most painful incidents in history concentrated is often a more honest pointer to the dominant contradiction than any portrait.

The result of typing should be "what the dominant contradiction is" rather than "we are so-and-so game." The former can derive constraints; the latter can only derive expectations.

### Recommended order of use

For a project from first contact to decision, there are three fairly natural points where this group of appendices enters.

- At project kick-off inventory, first use the one-sentence portrait to type the project, confirming which class the dominant contradiction falls into, so you do not schedule a world-type project like a room type.
- At solution review, compare the constraints and pitfalls of same-type projects item by item against the current solution, paying attention to whether the solution under review has answers prepared for special risks.
- At project retrospective, use the appendix to ask back: which class's which pitfall did this project's big incidents land in, and where the original typing judgment went wrong.
- At team assembly and hiring, typing also points at team gaps — a progression type lacking data and audit experience, a platform type lacking risk-control and trading experience — both are common composition gaps.

Most projects are not a single type. One product can have room combat, long-term cultivation, and player trading at the same time; a common practice is to set the tone by the dominant contradiction and then compare block by block against secondary problem domains, rather than forcing it into one label.

What you compare is also not limited to complete projects. A guild system, a trading house, or an event orchestrator can all be pulled out and typed on its own, judged for which kind's which block it most resembles, and then checked against the constraints and pitfalls listed in the corresponding page.

### What this group of appendices is not good at

The cost of crosswise clustering is losing the derivation, and some questions this group of appendices deliberately does not answer.

- It does not explain why a mechanism is designed that way; skipping the main line and applying quick-reference conclusions directly usually leaves the solution shallow.
- It does not give parameters, quotas, or implementation details; these vary enormously with project scale and team, and a quick-reference table cannot supply them.
- It does not handle mixed judgments across types; the difficulty of a mixed project lies exactly at the type boundary, and a quick-reference table can only point out where that boundary is.
- It does not replace measurement of a specific project; conclusions about capacity, consistency, and cost ultimately come from this project's data, not from classification.
- It is not an acceptance standard; matching a quick-reference conclusion does not mean the design is right, only that the direction is not visibly off.

This group of appendices compresses mechanism derivation and is only suitable for crosswise comparison with questions in hand; when you need the full causal background, return to the relevant main-line chapters.

If you find yourself citing only the appendix's conclusions without being able to say why, that is usually a signal: it is time to go back to the main line and fill in the derivation.

### Common misuses

- Treating the appendix as a checklist to tick off, assuming that having compared means having designed, when in fact every conclusion needs re-verification inside the current project.
- Using the one-sentence portrait to label a project and then letting the label replace discussion, so the dominant contradiction is never confirmed and the solution direction runs off course wholesale.
- Using a genre label to override a problem-domain judgment, or the reverse, with the two lenses competing for supremacy and forgetting that they answer different questions.
- Only flipping to the appendix after something breaks, turning retrospective into matching to a case rather than moving the typing judgment up front to kick-off and review.
- Treating the five problem domains as mutually exclusive options and cutting real secondary contradictions to force typing, with a mixed project hard-trimmed into a single type.

This group of appendices is best at three things: fast typing, organizing comparison, and accumulating experience from same-type projects. The one thing it is least suited to is replacing derivation and measurement aimed at a specific project.
