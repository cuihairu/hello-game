# 匹配功能：开源项目选型调研

> 整理日期：2026-10-18
> 范围：匹配（matchmaking）相关的开源框架与后端，按侧重点分四类
> 结论先行：**四个项目解决的是匹配链路上四个不同环节，不是互斥竞品**，
> 选型时应先明确自己缺哪一段，再决定参考谁、引入谁。

本文侧重开源项目的能力边界与选型取舍。自建服务的职责划分、会话协调与房间分配设计见[玩家匹配：自建架构的职责与落位](/zh/24-game-types-architecture/23-matchmaking-architecture)；队伍撮合与 PVP 评分、匹配池机制分别见[队伍匹配](/zh/system/party-matchmaking)和[PVP 匹配](/zh/system/pvp-matchmaking)。这些页面是同一主题的不同角度。

## 0. 匹配链路拆解

一个完整匹配流程大致分四段，四个项目各占一段：

```text
组队          匹配          分配房间/实例       进服
 ↑             ↑              ↑                  ↑
 Nakama      Open Match      Colyseus          Agones
 （组队生命周期）（匹配算法层）  （房间发现与席位预留）（服务器实例）
```

把它们当作竞品来比是常见的误判——**它们在链路上的位置不同，重叠部分主要在「匹配」与「分配」的边界**。

---

## 1. Open Match

| 项 | 内容 |
|---|---|
| 许可 | Apache-2.0 |
| 语言 | Go |
| 定位 | 可扩展匹配框架（Google for Games 推动） |
| 核心机制 | Ticket、Match Function、Evaluator、Director、Assignment |

**它解决什么**：把匹配基础设施与游戏自己的匹配算法分离。游戏只写
Match Function（打分/分组逻辑），调度、票据、并发收敛交给框架。

**优点**：适合跨游戏、跨模式的自定义匹配策略；策略可独立演进。

**不足**：需要自己接入组队、服务器分配、游戏接入与生命周期管理——
它只管「怎么匹配」，不管「匹配完之后」。

**选型注意**：Open Match 2 目前仍标为 **public preview**，
正式采用前应单独评估稳定性与迁移成本。

**适合谁**：匹配策略复杂、需要多游戏共用一套匹配基础设施的项目。

---

## 2. Agones

| 项 | 内容 |
|---|---|
| 许可 | Apache-2.0 |
| 语言 | Go（运行于 Kubernetes） |
| 定位 | 服务器实例分配 |

**核心机制**：GameServer、Fleet、Allocation、自动扩缩容。

**它解决什么**：管理游戏服务器进程池，并从池中**原子分配**实例，
避免并发分配到同一个服务器。

**优点**：分配的原子性有保障；与 K8s 生态结合，扩缩容能力成熟。

**不足**：**不负责队友选择与游戏内房间逻辑**。

**选型注意**：适合容器化专用服务器。如果游戏服务器是传统机器上的
长驻进程（未容器化），Agones 要么用不上，要么需要自己做一层适配。

**适合谁**：服务器已容器化、需要弹性伸缩的多人对战游戏。

---

## 3. Nakama

| 项 | 内容 |
|---|---|
| 许可 | Apache-2.0 |
| 语言 | Go |
| 定位 | 游戏后端（含组队、匹配、社交、存储等） |

**核心机制**：Party、队长、组队匹配、Matchmaker、Match Join。

**它解决什么**：组队生命周期。能保证一个 Party 内的玩家**作为整体**
参与匹配，同时支持单人与多人队伍混合匹配。

**优点**：功能基线完整，组队与匹配的边界处理（队长权限、成员变更、
组队解散对匹配的影响）考虑得比较细。

**不足**：作为完整后端，与自建的游戏服务器、账号体系、存储层
存在较多平台能力重叠。

**选型注意**：如果不打算采用 Nakama 作为完整后端，
**建议重点参考其实现，而不是引入整套体系**。

**适合谁**：需要完整后端的小型项目；或只想抄组队逻辑的大型项目。

---

## 4. Colyseus

| 项 | 内容 |
|---|---|
| 许可 | MIT |
| 语言 | TypeScript / Node.js |
| 定位 | 实时多人房间框架 |

**核心机制**：`joinOrCreate`、`joinById`、`reserveSeatFor` 等 Matchmaker API。

**它解决什么**：发现合适房间、创建房间、**预留席位**、返回连接信息。
席位预留是其中最容易被低估的部分——它解决了「看见房间但挤不进去」
的竞态问题。

**优点**：API 设计简洁，房间分配的语义清晰，非常值得学习。

**不足**：机制与自身游戏运行时（Node.js）结合较紧。

**选型注意**：如果希望多个服务端（不同语言/引擎）共用同一个调度平台，
**应抽象它的协议思想，而不是直接依赖其内部 Room 实现**。

**适合谁**：Node.js 技术栈的实时游戏；或需要参考房间分配协议设计的项目。

## 5. 选型建议

| 你缺什么 | 优先参考 | 是否直接引入 |
|---|---|---|
| 匹配算法与调度基础设施 | **Open Match** | 策略复杂时引入；简单匹配自建成本更低 |
| 服务器实例池与原子分配 | **Agones** | 已容器化才考虑；传统长驻进程先自建分配器 |
| 组队生命周期与整体匹配 | **Nakama** | 一般只参考实现，不引入整套后端 |
| 房间发现与席位预留 | **Colyseus** | 抽象其协议；运行时不同则不直接依赖 |

### 三条实践建议

1. **先拆链路再选型**。多数「选型困难」的根因是把四个不同环节的
   项目放在同一张对比表里。先确认自己缺的是组队、匹配、分配还是进服。

2. **席位预留容易被忽略**。Colyseus 的 `reserveSeatFor` 对应的竞态问题
   （发现房间 → 连接 → 房间已满）在自研方案里经常漏掉，
   值得单独设计。

3. **预览版不进生产关键路径**。Open Match 2 的 preview 状态意味着
   API 可能变动，若采用需锁定版本并准备迁移方案。
