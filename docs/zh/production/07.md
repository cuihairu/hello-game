# 工作室分工与质量门禁

## Category

production 树新增节点。节点定位：把「单人或小团队怎样借用成熟工作室的组织结构」收成一份可裁剪的参考——角色怎么分层、交接处由谁按什么词表裁决、「完成」用什么证据定义。素材是对开源工程模板 Claude-Code-Game-Studios 的结构调研（49 个角色定义、74 个工作流技能、28 道评审门禁），本页抽取其中可迁移的分工与门禁骨架。上游：研发协作与发布工作流（06）把工作流讲成责任界面设计，本页给出一份现成的界面样本。

## Definition

一套工作室方法由三件事组成：**角色分层**——总监定方向、主管守部门、专员做执行，每个角色是一份显式契约：职责、输出格式、「不做什么」清单、升级路径；**阶段门禁**——交接点上由指定角色按固定词表裁决，过不去就不进入下一阶段；**质量证据**——「完成」不是「我说做完了」，而是可查验的产物：通过的测试、留档的截图、真实的签核。单人加 AI 的开发可以一人分饰多角，但不能省掉角色之间的界面：写的人不能同时是验收的人。

## Problem

小团队的质量问题多数不是技术问题，而是没人把关：设计没人挑战，代码没人复审，视觉没人验收，发布没人拦。照搬大厂组织图过重，完全不设界面则等于裸奔——问题不是缺角色，而是缺「谁在哪个点上拦什么」的最小结构。

### 角色分层：先有边界，再谈协作

模板把 49 个角色按三层组织：总监层（创意、技术、美术、音频、叙事五条线的最高裁决）、主管层（游戏设计、主程、QA、本地化等部门口径）、专员层（玩法、引擎、网络、工具、关卡、经济、试玩平衡等具体执行）。层与层之间靠五条协调规则运转：

- **纵向委派**：总监委托主管、主管委托专员，复杂决策不跳层。
- **横向咨询**：同层可以互相问，但不得在对方领域做有约束力的决定。
- **冲突升级**：分歧上抛到共同上级；没有共同上级时，设计冲突找创意总监，技术冲突找技术总监。
- **变更传播**：跨部门的设计变更由制作人统一协调扩散，不靠当事人各自转达。
- **禁止跨域改动**：不经委托不改别人负责的目录与文件。

跨界时的标准动作是「陈述己方规则、承认对方目标正当、把取舍上抛」，而不是自行裁决。这套边界的价值在反方向更明显：几乎每个角色都带一张「不做什么」清单——制作人不做创意与技术决策、主程不单方面否决设计、QA 不因排期压力跳过测试（只能上报制作人）——职责边界靠禁项守住，不靠自觉。

### 阶段门禁：词表即纪律

生产分七个阶段：概念 → 系统设计 → 技术设置 → 预生产 → 量产 → 打磨 → 发布，相邻阶段之间设六道阶段门；阶段之内另设 28 道评审门禁，由七位把关人分工：创意总监 6 道（支柱压测、GDD 对齐、叙事一致性、试玩验证等）、技术总监 8 道（系统边界、可行性、架构签核、ADR 评审、变更影响等）、制作人 5 道（范围、冲刺、里程碑、Epic、阶段就绪）、美术总监 4 道、主程 2 道、QA 主管 2 道、叙事总监 1 道。门禁的可操作性全在词表上：

- 每道门禁有自己的裁决词表：范围门回答 REALISTIC / OPTIMISTIC / UNREALISTIC，里程碑门回答 ON TRACK / AT RISK / OFF TRACK，故事就绪门回答 ADEQUATE / GAPS / INADEQUATE。拿别家门禁的词回答是错误答案——调用方靠词分支。
- **NOT ASSESSED（未评估）是第四种裁决**，排序固定为：FAIL / CONCERNS > NOT ASSESSED > PASS。「无法检查」必须有自己的名字，否则缺数据会被渲染成干净——一份没有「未能评估」状态的报告，天然制造假的绿灯。
- 判定词永远放在第一行，不许埋进段落；缺失的必需产物是**发现**（FAIL 或 CONCERNS），不是「输入缺失」。
- 文档深度由三档档位控制：全档要求 GDD 八段（概述、玩家幻想、详细规则、公式、边界情况、依赖、调参旋钮、验收标准）与全部 ADR；标准档只要求五段（系统定义了数值规则时公式段强制）与关键 ADR；最小档不要求 GDD，一页 brief 顶替——档位决定「什么必须存在」，而不是「做好做坏」。

### 质量证据：完成的定义是可查验的产物

模板把「story 类型」和「关闭前必须交出的证据」绑死成一张矩阵：逻辑类（公式、AI、状态机）必须过自动化单测，阻塞；集成类必须过集成测试或有留档试玩，阻塞；视觉与手感类必须交**留档截图**加主管签字，阻塞；UI 类必须每一屏改过都留截图，阻塞；配置与数值类只需冒烟检查，仅建议。三条推论值得单独记：

- **「留档」是关键词**。截了又删的图是断言，不是证据——证据必须是关单时仍在磁盘上的文件；签核表没有真实签过就保持空着，预打勾的批准等于把缺失的签名伪造成已签。
- **解析通过不是运行过**。玩家可见的改动必须实机跑过、观察过、截图留档，最小档可以豁免自动化测试，不豁免「亲眼看一眼」。
- 不可测试的验收标准是黑名单：「手感平衡了」「运行正常」不是验收标准，必须改写成二元可测条件（如「任意界面两次按键内完成导航」「目标帧率下输入响应 ≤ 50ms」）。同时有四类东西明确**不自动化**：视觉保真、手感、平台渲染、完整对局——它们靠留证的人工验收，不靠假装能自动化的断言。

### 原型与切片：先证伪最险的假设

模板区分三种验证构建，各有硬时限：概念原型回答「这个核心交互好玩吗」，1 天上限，只测一个机制，不做任何打磨；技术探针回答「X 在技术上做得到吗」，约 4 小时，产出 YES / NO / PARTIAL；垂直切片回答「能不能按量产质量、按排期做出完整循环」，目标 3–5 分钟连续玩法，工期 1–3 周，超了是范围切错不是能力问题。配套纪律：

- **隔离律**：原型代码永不进生产库、永不 refactor 转正；切片通过后生产实现从零写。原型的产出是 REPORT（假设、最险假设、观察到的结果、建议 PROCEED / PIVOT / KILL），不是代码。
- 同一概念迭代 3 次 PIVOT 就强制考虑 KILL——「在两三个原型之间自然选择，胜过把一个概念迭代到死」。
- 切片只能砍范围不能砍质量：不像目标游戏的切片验证不了量产可行性。
- 网络游戏警告：本地 0ms 验证不了 80ms 延迟下的手感，本地原型只能证明「有意思」，证明不了网络手感。

### 可抄的数字

模板里的阈值大多可直接搬用：任务切到 1–3 天一个；冲刺固定留 20% 缓冲给计划外工作；里程碑风险提前 2 个冲刺上报；范围蔓延 ≤10% 视为正常，超 25% 必须砍范围或正式延期，超 50% 停下重规划；估时永远给乐观/期望/悲观三段数、按半天取整、超 10 天拆分；冲刺燃尽落后 10–25 个百分点算有风险、超 25 算落后，4 天没更新的 story 视为停滞；每次回顾的 action items 限 3–5 条，每条有负责人和期限；修完的 bug 必须有能抓住原 bug 的回归测试才算闭环。
