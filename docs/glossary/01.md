# Server Side

## Category

Glossary entry. Node role: "server side" is a collection of responsibilities, not a single process — the five kinds of responsibilities differ in change cadence, failure cost, and governance approach.

## Definition


In a game context, "server side" rarely refers to a single process; more often it means a collection of responsibilities: accepting connections, advancing authoritative logic, keeping long-term state, coordinating node scheduling, and supporting the operations back office. These responsibilities differ completely in change cadence, failure cost, and governance approach; mixing them up in discussion usually yields unusable conclusions.

## Problem

Mixing it up when discussing "the server side can't hold up" inevitably produces unusable conclusions: accepting connections, advancing logic, managing state, scheduling nodes, and supporting the back office have different bottlenecks, failure modes, and owners. Without layering the term, troubleshooting and division of labor have no shared language.


### Which responsibilities does this term usually cover

- Access and session: connection maintenance, login-state binding, message routing.
- Authoritative logic: adjudication and advancement of rooms, scenes, and combat.
- Assets and accounts: long-term state such as currency, inventory, orders, and quest progress.
- Coordination and governance: service discovery, migration, traffic drain and recovery — that is, the part carried by the control plane.
- Offline and analytics: settlement persisted to storage, report aggregation, audit archiving.

Different projects name these pieces differently and split them at different granularities, but the responsibilities themselves exist in every project. When discussing server-side architecture, the first step is usually to confirm where each of these five pieces lands in the current system.

### What layer is "the server side can't hold up" actually talking about

When someone says "the server side can't hold up", the effective move is to first ask which layer it is: the ingress layer queuing connection establishment, the logic layer exceeding its Tick budget, or the storage layer accumulating writes. Their fixes belong to different chapters, and mixing them in discussion usually converges into one line — "add machines" — while adding machines often only helps in one of those cases.

### It is not the same thing as the "back office"

Many teams use "server side" and "back office" interchangeably. In a game context they are usually distinguished: the game-logic server is the part that player requests flow through in real time, and cares about latency, concurrency, and adjudication; the operations back office is the control system for operations, customer support, and review actions, and cares about permissions, audit, and consistent definitions. The two share underlying data, but their paths, change cadence, and failure cost all differ, and folding them into one deployment and one workflow is often the starting point of many downstream governance problems.

### Server side is not a technology stack

Differences in language, framework, and storage matter far less than the impact of differences in responsibility division. Two projects written in different languages, with similar responsibility divisions, often meet isomorphic problems; two projects on the same technology stack with different responsibility divisions end up with completely different problem shapes. So when discussing the server side, first discuss where the responsibilities land, then discuss what to use to implement them; reversing the order usually amounts to comparing name recognition rather than comparing solutions.

### Where is the division between server and client

The common division is that the client is responsible for presentation and bounded prediction, and the server is responsible for authoritative state and final adjudication. The key to the division is not which side the code lives on, but which side is authoritative when something goes wrong. Hand-feel and immediate feedback go to the client, assets and settlement go to the server — that is the form most projects converge to; projects that also hand asset adjudication to the client often get forced to redo it after commercialization, and what they patch then is not just code but also an audit of historical data.

### Why "server side" inherently carries authoritative meaning

In synchronization-related discussion, "server side" is often taken to be the authoritative party by default: final positions, damage settlement, and asset changes are authoritative on the server. This default is not a technical necessity; it is the result of a long-running trade-off among anti-cheat, consistency, and audit. Host-owned rooms, client-authoritative plus after-the-fact auditing, and other forms also exist in specific categories, but once authority is ceded, you often have to pay a higher governance cost to make up for it.

### The server side different roles talk about is not the same thing

- The server side in a designer's mouth often means "final adjudication of numbers and outputs", and cares whether rules execute per the tables.
- The server side in a client engineer's mouth often means "interfaces and return values", and cares about protocol stability and integration efficiency.
- The server side in operations' mouth often means "a set of nodes and processes", and cares about deployment, capacity, and recovery.
- The server side in a data engineer's mouth often means "storage writes and the source of event tracking", and cares about consistent definitions and completeness.

All of these understandings are partially correct, and taken together they are the source of day-to-day miscommunication. The role of the term is not to unify naming, but to make sure every discussion first aligns on which piece of responsibility is being talked about.

### What the same word means in different sentences

- "Server restart" usually means a rolling restart of logic nodes; whether anyone disconnects depends on the ingress layer's session-recovery capability.
- "Server validation" means critical state is recomputed by the authoritative party, in contrast to surface validation that only checks format legality.
- "Server scale-out" has to distinguish logic-node scale-out from ingress-layer scale-out; their traffic-sharing mechanisms are completely different.
- "Server rollback" means restoring authoritative state to some point in time; the cost and feasibility depend on how the various kinds of state are partitioned in the data model.

When reading someone else's design or incident report, confirming which piece the "server side" in that sentence refers to is more useful than rushing to compare technology choices.

### What to pin down first when discussing server-side problems

- Which of the five pieces of responsibility is being discussed.
- Which class the relevant state belongs to, and where the authority is.
- What the change cadence is, and who shares the release window.
- Who catches it on failure, and what recovery relies on.

Once these four things are pinned down, most server-side arguments converge automatically, and what is left is genuine technical disagreement.

### Common pitfalls

- Treating the server side as one whole when discussing performance, so every optimization ends up as the single action of "add machines".
- Understanding a game server through web-back-office experience, underestimating the differences of long-lived connections, state residency, and Tick advancement.
- Assuming the server is authoritative by default, so no state division is done and every request hits the same store.
- Folding the operations back office and the game-logic server into one workflow, so their change cadence drags each other down.
