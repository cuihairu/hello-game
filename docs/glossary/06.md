# Hot Update

## Category

Glossary entry. Node role: hot update is a trade-off among fix window, iteration speed, and incident radius — every step that shortens the fix path also widens one entry point for production changes.

## Definition


Hot update means letting a change in live logic or resources take effect without going through the full release process. Discussion around it has never been only about technical feasibility; it is a trade-off among fix window, iteration speed, and incident radius: hot update shortens the fix path step by step, while at the same time widening one entry point for production changes.

## Problem

A hot-update discussion that only asks technical feasibility has already gone off track: the real trade-off is three things — how fast the window, how frequent the cadence, how large the radius. A hot-update system without tiering, rollback, and platform constraints bypasses the release process rather than optimizing it.


### How many tiers does hot update usually have

- Asset hot update: textures, audio, table content — relatively low risk, highest volume.
- Config hot update: parameter and rule values — fastest to take effect, potentially very wide blast radius.
- Script hot update: logic-layer code — highest flexibility, highest risk.
- Server logic hot update: replacing logic inside a node or hot-restarting, depending on runtime design.

The incident radius of different tiers is completely different. When discussing "whether to hot update", first confirm which tier is meant, otherwise the discussion degrades into an argument about positions.

### What it really determines

Once a project enters long-term operations, what is usually most expensive is not that a feature cannot be built, but that a problem is known yet cannot be changed, cannot be shipped, and cannot have its losses stopped. The hot-update system determines how short the fix window is, how fast the iteration cadence can go, and how large the blast radius of one bad change is. This is also why it comes up in discussion again and again: it is one of the most important architecture capabilities during the operations period.

### Hot update and release have different cost structures

Releases are slow but go through the full process, with a high per-change cost amortized across the batch; hot update is fast but every change must go through gray release, validation, and rollback, so the per-change cost does not come down. This determines their respective fit: high-frequency content and parameter changes suit hot update, while low-frequency structural changes suit releases. Squeezing structural changes into hot update means doing the most dangerous thing through the most expensive channel.

### What a hot-update system usually consists of

- Packaging and delta: turning a change into a distributable patch.
- Signing and checksum: confirming the patch's origin and integrity.
- Distribution and gray release: rolling out by ratio, device model, or channel.
- Compatibility matrix: matching rules among script versions, host versions, and config versions.
- Monitoring and rollback: observation points for crash rate and error rate, plus one-click rollback.

Miss any one of these five and the hot-update channel counts as incomplete. The most common gap in real projects is the compatibility matrix and rollback: the first four are being built, and it is only at incident time that people realize there is no way back.

### It must be viewed within the release path

Hot update is not a standalone switch but one link in the release system. Mismatches such as an old client pulling new config, or a hot-updated script running on host code that is not ready, are hot spots for version incidents — and the reason the version-release chapter keeps stressing the compatibility window. When evaluating a hot-update plan, treat it as an independent release pipeline, and the missing links usually surface immediately.

### Platform and channel constraints

Platforms differ greatly in their attitude toward hot update: mini-game platforms have explicit restrictions, channel review tolerates script hot update to varying degrees, and package size and resource updates may also be constrained by review windows. If hot-update capability design is divorced from the rules of the target platform, it is often forced to be restructured before launch, and restructuring a hot-update system is almost the same as restructuring the release system.

### Rollback matters as much as hot update itself

A hot-update channel without rollback means production changes have no undo button. Common practices are to lead with gray release, keep the previous hot-update package, state the version-matching rules between host and script, and give hot-update changes their own incident rollback plan. Assessing a team's hot-update capability often looks not at "can it hot update", but at how fast it recovered the last time a hot update went wrong.

### Which problems are frequently backstopped by hot update

Numerical imbalance, logic bugs, event switches, and emergency loss limiting are the four categories hot update most often carries. The first two test the validation process; the latter two test gray release and rollback. What deserves alert is a fifth category — new features also shipping through hot update, which usually means the release pipeline is broken and the team is using hot update to evade the release process, with the incident radius spiraling out of control as a result.

The order of backstopping matters too: stop losses first, then fix; small traffic first, then full rollout. Reverse these two orderings and hot update's speed advantage becomes a source of risk.

### Its relationship with gray release

Gray release is not only about ramping volume; it is also a validation means for hot update: tiered rollout by device model, channel, and online duration, observing crashes and errors, then deciding on full rollout. Hot-update gray release without tiered observation points is essentially still a full rollout, just spread over a few days. A common approach is to set observation metrics and dwell time for each kind of hot update, and not advance to the next batch until the threshold is met.

### Common pitfalls

- Treating hot update as a universal fix channel, expecting hot update for any problem, and letting release discipline collapse along with it.
- Building a hot-update channel without a compatibility matrix, so hot-update packages mismatch host versions and trigger batch incidents.
- Hot-updated code skipping tests, treating the production environment as a validation field.
- Ignoring platform rules and discovering before launch that core hot-update capability is unavailable.
- Having hot update but no rollback, so on failure the only option is to hot update once more to fix the previous hot update.
