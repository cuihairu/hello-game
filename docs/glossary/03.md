# Primary Path / Peripheral Path

## Category

Glossary entry. Node role: the division between primary path and peripheral path is a design action, not a factual description — core behavior passes through directly vs. supports but does not decide success or failure.

## Definition


This pair of terms appears frequently throughout the book, because the essence of many architecture disagreements is that the primary path and the peripheral path were not treated separately. The primary path is the stretch of path that the player's core behavior passes through directly, usually login, matchmaking, entering a room, in-match interaction, and settlement; the peripheral path is the part that supports these behaviors but does not directly decide success or failure, such as leaderboard refresh, achievement notifications, report aggregation, log collection, and push.

## Problem

The essence of many architecture disagreements is that the primary path and the peripheral path were not treated separately: wrapping peripheral paths in primary-path-grade guarantees is waste, and building the primary path to peripheral availability standards is an incident. The division must be set at design time; classifying after the fact gets pulled off course by vested interests.


### Why the division is a design action and not a factual description

Which paths count as the primary path depends on the problem model, not on the technical form. For competitive products, the primary path mostly lands on in-match sync and disconnect recovery; for long-horizon progression products, the primary path often lands on asset correctness, config safety, and event cadence. For the same system in these two kinds of products, the drawing of the primary path is completely different. So every use of this pair of terms should carry the context of "for which product", otherwise it becomes a slogan.

### The two kinds of path usually have different goals

- The primary path prioritizes latency and determinism: requests must be explainable, failures must be visible, adjudication must be authoritative.
- The peripheral path prioritizes throughput and decoupling: latency is allowed, retries are allowed, batching is allowed, even brief unavailability is allowed.

Different goals lead to different technical choices: the primary path suits synchronous calls with explicit timeouts, while the periphery suits events plus queues plus idempotent consumption. Using them the other way around is the source of many production problems.

### A few questions for judging which side a stretch of path belongs to

- Can the player directly perceive its latency or failure.
- Does its failure directly affect revenue, assets, or fairness.
- Does it require deterministic ordering and results.
- Can it accept batching and retries.

If all four questions point to the primary path, govern it as primary; if most point to the periphery, govern it as peripheral; if the two sides are mixed, it usually means this stretch of path should itself be split apart.

### Examples of classifying some common paths

- Login, entering a room, in-match interaction, settlement posting: primary path.
- Payment callback to asset crediting: primary path, and usually required to be reconcilable.
- Leaderboard refresh, achievement notifications, report aggregation: peripheral.
- Announcements and push: peripheral, but high-risk actions such as server-wide mail must be treated at the primary path's governance level.
- Compensation and customer-support actions: peripheral in normal times, treated as primary path during incidents.

The examples are only references; applying them to your own project still requires going back to the problem model to judge, and directly copying another project's list is the most common misuse.

### The practical payoff of the division

Keep the primary path simple and controllable, and let the peripheral path evolve independently. The typical approach is for settlement to first synchronously produce the authoritative result, then asynchronously broadcast to leaderboards, achievements, and reports: the primary path stays explainable, and the periphery gains decoupling. The other way around, if settlement synchronously waits for the leaderboard write during settlement, the jitter of one peripheral system directly drags down the whole server's settlement speed.

### The cost of mixing them up

- A peripheral system's jitter directly drags down the primary path, amplifying the failure surface from local to global.
- The primary path sacrifices explainability for throughput, and when something breaks nobody can say which step went wrong.
- All messages crowd into the same bus, and priority, ordering, and retry semantics pollute each other.
- Peripheral unavailability is treated as minor, and then reports and compensation fail together at event peak.

### How to land the division once made

The value of the division shows when it is landed. In deployment, primary and peripheral are deployed separately and scaled separately; in messaging, the two kinds of path use different reliability and ordering semantics; in observability, the primary path has an end-to-end evidence chain while the periphery allows aggregated metrics. Miss any one of these three things, and the division still stays at the level of an architecture diagram.

### A category that is easily misfiled: audit and reconciliation records

Event tracking, logs, and transaction streams look the most peripheral, but records used for reconciliation, audit, and appeals are evidence in the asset path, and when they are missing the primary path's disputes cannot be adjudicated. A common approach is to put high-volume analytics logs on the periphery and treat asset-related operation records at the primary path's reliability requirements, separating the two at the collection layer.

### The boundary moves with the phase

Before launch, the core gameplay loop is the primary path; after entering long-term operations, the paths for event configuration, asset compensation, and customer-support tools often get promoted into de facto primary paths, because the cost of their failure has become asset-loss grade. Periodically re-confirming the boundary fits reality better than dividing once and deciding forever.

### Common pitfalls

- Treating the primary path as a fixed list copied from other projects, without looking at your own problem model.
- Using one messaging semantics to cover both kinds of path, leaving the primary path unexplainable and the periphery without throughput.
- Piling monitoring only on the periphery while the primary path has no evidence retained, so incidents can only be guessed at.
- Not updating the boundary when the phase changes, so high-risk paths in the operations period are still governed to peripheral standards.
