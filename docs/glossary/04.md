# Authoritative State

## Category

Glossary entry. Node role: authoritative state is the copy of state that final adjudication depends on — having multiple sources of truth for the same state is the root of most confusion.

## Definition


Authoritative state refers to the copy of state that final adjudication depends on: position, damage, assets, progress — whoever is the standard when a dispute arises is the authority. This term comes up repeatedly in discussions of sync, data, and service splitting, because the root of much confusion is that the same state has multiple sources of truth.

## Problem

Without an authoritative definition for disputes over position, damage, and assets, sync, persistence, and troubleshooting all lose their basis for adjudication. Authority is not the same as performance-optimal, and authority transfer is a high-cost action — these two common misconceptions make the architecture swing back and forth repeatedly.


### The core question it answers

Not "where is the data stored", but "who is the standard". A piece of state can have multiple replicas, multiple cache layers, and multiple presentation views, but there is only one admission right. However fresh the leaderboard replica is, it is not the asset truth; however accurate the client prediction is, it holds no adjudication power. Whether a system's state design is clear is usually judged by exactly one thing: can it state in one sentence where the authority for each class of state is.

### The same state often has several names

A player's assets usually exist at the same time in memory objects, cache replicas, database rows, presentation API responses, and report aggregations. These forms derive from one another, each with its own update timing. What the term authoritative state answers is: which of these names has the final say, how the others keep up, and what to do when they diverge. If that cannot be stated clearly, the replicas going their own ways is only a matter of time.

### Its place in sync discussions

Server-authoritative state sync became mainstream precisely because putting authority on the server makes it easiest to adjudicate uniformly, constrain cheating, and support auditing. The client can usually predict and can play first, but the prediction is only provisional — once the server's authoritative result comes back, everything must be re-converged onto it. The whole set of mechanisms for prediction, compensation, and correction is built around the fact that "the authority is not local".

### Its place in data discussions

Authoritative source data and derived replicas must be told apart: who is the authoritative source, who is the performance replica, when the replica updates, and how it is rebuilt when invalidated. In long-running projects, the hardest structural problem to untangle is often derived data slowly reversing into the source of truth — reports get used for adjudication, presentation replicas get treated as asset truth, and errors seep from the presentation layer into the settlement layer.

### Its relationship with the single writer

Authority usually comes paired with a single writer: if a piece of state can be directly modified by multiple processes, the authority exists in name only. The common approach is to converge the write entry into one service or one unit of execution, with other systems reading and writing through it. A single writer is not for performance; it is to give the question "who has the last say" a unique answer, and to give auditing and rollback somewhere to land.

### Authority is not performance-optimal

Putting authority where adjudication is most solid usually means it is not where latency is lowest. Engineering practice usually compensates the experience with prediction, caching, and asynchronous acknowledgment, rather than moving the authority closer to the player. Once adjudication power is delegated for the sake of hand-feel, you have to be prepared to pay back the governance cost with after-the-fact auditing and compensation mechanisms, and that bill is usually not cheaper.

### Authority transfer is a high-cost action

Using client authority to trade for development speed early in a project, then switching to server authority after entering commercialization, is a common path — and a common cost amplifier: historical data lacks audit, protocols lack validation, and players have grown used to client behavior. If commercialization can be foreseen at project start, set the authority's location as early as possible; if that is impossible, at minimum record the transfer's migration cost as technical debt rather than treating it as a casual refactor.

### The relationship between authority and consistency

Authority answers who is the standard; consistency answers how much the replicas diverge and how fast they converge. Only in a project where authority is clear can the consistency strategy aim at a target: which states demand strong consistency and which allow eventual consistency are all decided around the authoritative source. The other way around, discussing consistency schemes when authority is unclear usually means patching a wrong state structure.

### A set of questions for testing the clarity of authority

- Pick any piece of critical state: can the team state where its authority is within three sentences.
- When fixing data, is there a single permitted entry point.
- When presentation data does not match, which copy is trusted first during troubleshooting.
- If a replica breaks, can it be rebuilt from the authoritative source, and how long does the rebuild take.

This set of questions works well in both inventories and reviews; every question that cannot be answered corresponds to a real risk.

### Common scenarios of misplaced authority

- Position inside a room: server-authoritative, the client only does predictive presentation.
- Parties and friend relationships: the common approach is that the social service is the authority, and the room keeps only a replica.
- Time-limited event progress: config side defines the rules, progress authority sits in the event service, and the client only displays.
- Cross-server power rating: the source server is authoritative, the target server keeps a read-only replica and does not compute it itself.

Scenarios differ, and authority ownership may differ; the multiple pieces of state within the same scenario also each have their own owner. Listing them one by one during review is far more useful than a vague line of "server-authoritative".

### Common pitfalls

- Treating "whoever computed it first" as the authority, with settlement and presentation each computing their own, and manual data fixes when they fail to line up.
- Authoritative state modified directly in many places, the audit chain broken, and no rollback possible when something goes wrong.
- Treating derived replicas as truth for performance's sake, so a broken replica becomes an asset-loss incident.
- Assuming that designating an authority service completes the design, while the actual write paths are still spread across multiple systems.
