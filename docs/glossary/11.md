# Characters, Entities and MMO Spatial Terms

## Category

Glossary tree node. Collects the English names of characters, distributed entities, spaces and service processes, giving each entry by entry the Chinese meaning, the responsibility boundary and the verifiable source. Focus on BigWorld and KBEngine, cross-referenced against the different usage in Unreal and Unity; project-custom class names are not packaged as industry standards.

## Definition

Reading a game server architecture, you should first separate four things: what object it is in business terms, what distributed parts it has, which spatial partition the simulation lives in, and which process hosts those parts. The same player character can have a Base part and a Cell part, but that is not a full copy of its data duplicated twice; the same Space can be allocated several Cells, and that is not one map resource corresponding to one process.

This page cites the **BigWorld 2.1 original vendor documentation archive** to explain the historical meaning of the terms, cites the **14.4.1 source archive** to verify the process/space structure, and cites the KBEngine official documentation and samples to explain implementation usage. Versions and sources are labeled separately; an old version's constraints on deployment are not a general constraint of every engine. A source proves how that project uses a term, not that it coined the term, and not that any project that adopts a type of the same name has implemented the same capability.

## Problem

What creates the understanding cost is not the length of the English names but conflating different layers into one thing: Avatar equals Cell entity, Base equals database, Cell equals CellApp, Instance equals process, Proxy equals standalone gateway. Another risk is deriving the lifecycle of a service from common single-player experience: a player being offline does not mean a long-lived object cannot be activated, and fixing a player identity does not mean fixing its hosting process.

## Algorithm

### 1. First judge which layer a name belongs to

| Layer | The question it answers | Examples |
|---|---|---|
| Business object | Is it an account, a participant, or a controllable character? | Account, Player, Avatar, Character |
| Entity parts and authority | Which part owns non-spatial business, and which part rules the simulation? | Base entity, Cell entity, Real, Ghost |
| Running space | Which coordinate space, which partition, which event does it belong to? | Space, Cell, Instance |
| Hosting and management processes | Who advances the simulation, and who allocates capacity and ownership? | BaseApp, CellApp, CellAppMgr |

Module names, class names and binary names may be related, but each must be explained separately. The same binary can launch different process roles with parameters; a role of the same class name can also be implemented separately in the Base and Cell modules.

### 3. Base, Cell and remote calls

| Original Term | Common Chinese | Meaning and boundary | Source |
|---|---|---|---|
| Base entity / Base part | The Base part of an entity, base part | Owns non-spatial logic and divides labor with the spatial simulation part; it is not a database process, and it does not guarantee that every Base entity is persistent. | [BigWorld Base source, 14.4.1](https://github.com/v2v3v4/BigWorld-Engine-14.4.1/blob/main/programming/bigworld/server/baseapp/base.hpp), [KBEngine property scopes](https://kbengine.github.io/docs/programming/entitydef.html) |
| Cell entity / Cell part | The Cell part of an entity, spatial simulation part | Advances position and other spatial simulation; the same logical character can have a Base part at the same time, and the two parts' state is divided by authority. | [BigWorld Cell Entity source](https://github.com/v2v3v4/BigWorld-Engine-14.4.1/blob/main/programming/bigworld/server/cellapp/entity.hpp), [KBEngine Cell Avatar](https://github.com/kbengine/kbengine_demos_assets/blob/master/scripts/cell/Avatar.py) |
| Real entity | Authoritative entity | The entity form that holds simulation authority within a partition; it is not "holding an object pointer means you may write." | [BigWorld Cell Entity source](https://github.com/v2v3v4/BigWorld-Engine-14.4.1/blob/main/programming/bigworld/server/cellapp/entity.hpp) |
| Ghost entity | Non-authoritative projection, shadow entity | A non-authoritative representation of an authoritative entity, used for cross-partition visibility and the like; it is not a second character that can grant rewards or modify data independently. A migration snapshot does not automatically equal a long-lived Ghost either. | [BigWorld glossary](https://howarduong.github.io/github.io/doc/html/glossary_of_terms/glossary_of_terms.html), [Cell Entity source](https://github.com/v2v3v4/BigWorld-Engine-14.4.1/blob/main/programming/bigworld/server/cellapp/entity.hpp) |
| Witness | Observer view context | In BigWorld this is the entity/visibility context related to client observation; it differs from the cross-partition replica meaning of Ghost. | [BigWorld Witness source](https://github.com/v2v3v4/BigWorld-Engine-14.4.1/blob/main/programming/bigworld/server/cellapp/witness.hpp) |
| Proxy | A Base entity with client association capability | The player Base part in the BigWorld/KBEngine samples can inherit Proxy; not every Base entity has a client, and it cannot be equated one-to-one with a standalone gateway. | [BigWorld Proxy source](https://github.com/v2v3v4/BigWorld-Engine-14.4.1/blob/main/programming/bigworld/server/baseapp/proxy.hpp), [KBEngine Base Avatar](https://github.com/kbengine/kbengine_demos_assets/blob/master/scripts/base/Avatar.py) |
| Mailbox / EntityCall | Entity remote call reference | A method reference for accessing an entity across parts/processes rather than a shared pointer; the two projects' concrete implementations differ, and you should not assume the reference is permanently bound to one IP. | [The mailbox in the BigWorld Base source](https://github.com/v2v3v4/BigWorld-Engine-14.4.1/blob/main/programming/bigworld/server/baseapp/base.hpp), [KBEngine EntityCall source](https://github.com/kbengine/kbengine/blob/master/kbe/src/lib/entitydef/entity_call.h) |

Base/Cell expresses the split of responsibilities; whether the Base part can migrate dynamically is the capability of a specific version and project. The BigWorld 2.1 glossary describes a model in which Base is fixed in place — that cannot be generalized into "no Base in the industry ever migrates," nor should you go the other way and assume the engine already supports automatic Base load migration.

### 4. Maps, spaces and the gameplay lifecycle

| Original Term | Common Chinese | Meaning and boundary | Source |
|---|---|---|---|
| Map resource | Map resource | A static resource, separate from one running space and one gameplay event; the same map can be used many times. | [The resources and Space example of the BigWorld tutorial](https://howarduong.github.io/github.io/doc/html/bigworld_tutorial/bigworld_tutorial.html) |
| Space | Running space | The spatial identity and coordinate context of BigWorld, managing the set of Cells; it is not a static map file or a process. | [BigWorld Space source](https://github.com/v2v3v4/BigWorld-Engine-14.4.1/blob/main/programming/bigworld/server/cellappmgr/space.hpp) |
| Cell | Spatial partition | A region of space within a Space and its local simulation; it must not be conflated with the CellApp process that hosts it. | [BigWorld Cell source](https://github.com/v2v3v4/BigWorld-Engine-14.4.1/blob/main/programming/bigworld/server/cellapp/cell.hpp) |
| Scene | Scene | The name alone cannot settle whether it is a resource scene, a running container, or gameplay. Unity Scene and BigWorld Space each have their own engine boundary; a project must spell out the correspondence. | [Unity Scenes manual](https://docs.unity3d.com/6000.0/Documentation/Manual/CreatingScenes.html), [BigWorld Space source](https://github.com/v2v3v4/BigWorld-Engine-14.4.1/blob/main/programming/bigworld/server/cellappmgr/space.hpp) |
| Instance / Dungeon instance | Running instance / dungeon instance | Instance is a reused word, so the object being instantiated must be stated explicitly. Dungeon gameplay can be associated with a standalone Space, but the concrete phase, settlement and destruction rules belong to gameplay; Unreal's GameInstance is a different kind of engine lifecycle object. | [Game Instance of the Unreal Gameplay Framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-framework-in-unreal-engine), [Blizzard's description of cross-faction instances](https://news.blizzard.com/en-us/article/23796742/shadowlands-a-look-at-cross-faction-instances) |

The typical relationship is: a map resource is consumed by a Space, the Space's simulation is carried by one or more Cells, and the CellApp hosts those Cells. One dungeon gameplay can be associated with a Space, but you cannot infer "one dungeon one process" from the word Instance alone. A single-Cell space also does not mean it already has partitioning, Ghosts, cross-boundary combat and seamless migration.

### 6. Same name does not mean the same lifecycle

Taking projects that adopt the Base/Cell split as an example, the following are design checkpoints, not claims that every engine provides these capabilities by default:

1. A client login establishes an authenticated session; loading/activating a character's Base part is a separate matter, and offline business can also trigger activation by project design.
2. Entering gameplay creates or associates a Cell part; leaving destroys the simulation object, without unloading the long-lived data.
3. A player character identity should be stable, and the current Base/Cell hosting address is a mutable route; a migration-capable system must hand over write rights, in-flight business and versions, not just change the IP.
4. Asynchronous orders bind to a stable player/character identity, not permanently to a Base process. Persistent to-dos are kept during migration or offline periods and resolved and delivered according to the current ownership.
5. A business write-up, a notification received, and a simulation executed are different confirmations; a duplicated payment notification must not double-ship, and an old simulation source must not keep writing because of a cached address.

For the mechanism expansion see [Service Discovery, Routing and Collaboration](/server/services/04), [Consistency, Recovery and Reconnection](/server/services/05), [Transactions, Payments and the Economy System](/system/services/03). The KBEngine routine charge path has one further verifiable detail: BaseApp requests interfaces through DBMgr, saves the order association, and then returns via DBMgr to the initiator — it is not that interfaces first maintains a full player-to-Base mapping; this in-memory request association also does not guarantee payment recovery across a restart. [interfaces request/receipt source](https://github.com/kbengine/kbengine/blob/master/kbe/src/server/tools/interfaces/interfaces.cpp#L717), [DBMgr forwarding source](https://github.com/kbengine/kbengine/blob/master/kbe/src/server/dbmgr/interfaces_handler.cpp#L544)

### 7. The method of judging a name

First state the object, the authority, the location and the host, then choose the name. If a project implements only a player's Cell part, Avatar is not unusable, but the scope must be stated; if a long-lived object is called Anchor or another project-specific name, list the correspondence between the existing types and the Base/Cell duties, rather than writing the name as an industry definition.

Implementing the same-named Avatar separately in the Base and Cell modules can express the different parts of the same character; this is a code-organization choice after adopting the model, not an industry-mandated C++ namespace, and it does not automatically gain cross-process entity calls and migration. A general knowledge base records only verifiable semantics; each project's specific naming and code migration stay in its own design documents and tasks.
