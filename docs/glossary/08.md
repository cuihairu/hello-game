# Operations

## Category

Glossary entry. Node role: here, "operations" means the systematic operating capability, not a job function — event orchestration, outreach, approvals, metric definitions and the retrospective chain all have to be carried by the system.

## Definition


In this knowledge base, "operations" most of the time does not mean a job function or a marketing action; it means a systematic operating capability: event orchestration, mail compensation, push outreach, approval flows, data definitions and the retrospective chain. Separating these two meanings is a prerequisite for many discussions: the former is a function, the latter is a set of capabilities that has to be carried by the system.

## Problem

Treating operations as a function (a job's concern) keeps this set of capabilities permanently in a state of bolted-together tooling: event orchestration done by hand, compensation done by editing the database directly, each table computing its own metric definition. Distinguishing "function" from "system capability" is the prerequisite for engineering operations.


### Why operations turns into a technical problem

Right after a game launches, operations actions happen at low frequency, and spreadsheets plus throwaway scripts can still cope. Once stable operations set in, the frequency of actions and the complexity of the data both rise, and two bottlenecks appear quickly: actions execute slowly and cannot keep up with the pace; actions are uncontrollable, so after doing something you cannot review whether the effect was real. At that point the operations capability has to be systematized, rather than "having a back office counts as done."

### What an operations system usually includes

- Events and monetization configuration: shelves, gift packs, quests, switches.
- Outreach channels: mail, announcements, pushes, compensation.
- Approvals and audit: who may perform which action, and whether it can be traced afterwards.
- Data definitions and reporting: retention, payments, output — one consistent set of definitions across the whole system.
- The retrospective chain: whether each action's true effect can be evaluated.

These systems do not need to be covered entirely by a single platform, but they must share consistent data definitions and approval flows; otherwise operations efficiency keeps getting cancelled out by inconsistencies between systems.

### How it relates to the primary path

Day to day the operations path looks peripheral, but when it goes wrong it is a primary-path-level failure: a wrong gift-pack price is direct financial loss, a wrong compensation is an economic incident, and a wrong server-wide mail is a PR event. So operations actions usually need gray release, approvals, audit and rollback; their governance level is in the same class as a code release, only the form of the change differs.

### How to set the governance level of an operations action

- Involves money: price changes, rebates, refunds — highest level, two-person approval plus gray release.
- Involves assets: compensation, recall, mail attachments — high level, traceable and rollable back.
- Server-wide outreach: announcements, pushes — medium-high level, both scope and copy need review.
- Routine switches: event switches, rate-limit adjustments — low level, but must be recorded.

Once the levels are set, the system knows which actions can be self-service and which must go through approval; if the levels are confused, the approval process is either a rubber stamp or it chokes even the small stuff.

### Two common ways to go off track

One treats operations as a pure business function, with the technical side only executing; the system has no capability to carry it, so actions depend entirely on manual labor. The other builds an operations middle platform outright, chasing comprehensive everything, so the business side cannot integrate and the platform ends up as a decoration. The more common and effective path is to tier by action: systematize high-frequency actions, make low-risk actions self-service, and route high-risk actions through approval plus gray release.

### The relationship between operations and data

Every operations action should have an evaluable expectation: what was done, which metric was meant to be influenced, and by how much it actually moved. This depends on two things: the action itself leaves a record, and the data definitions are consistent system-wide. The definition problem is expanded in data modeling; the key point here is that without unified definitions, an operations retrospective basically ends up with everyone telling a different story, and the retrospective loses its value as a corrective.

Unifying definitions is also not a once-and-for-all job; new metrics and new events bring new definitions, so periodically reconciling the definitions across systems is routine work worth scheduling during operations.

### Actions and cadence must be considered separately

An action is a single operation; cadence is how actions are organized — for example how events are scheduled between versions and how monetization points are distributed. What the system mainly carries is the action; cadence is more of a design decision, but it determines the frequency of actions and at what moments they occur concurrently, and therefore also how much pressure the system has to remain controllable under.

### Its relationship to other terms

Operations capability relies heavily on config-driven design and the version release chain; an event change is essentially a high-frequency release. Its effect evaluation depends on data definitions, which in turn depend on how authoritative state is divided in data modeling. Its execution requires approvals and audit, which belong to the same governance capability family as the control plane. Taken together, operations is not something outside technology — it is an extension of the primary path of a long-running project.

### The order in which to build operations capability

The common order starts with outreach capabilities such as mail compensation and announcements, because those are most urgent at launch; then event configuration and switches, to carry cadenced operations; and only later approvals, audit and the retrospective chain, upgrading actions from "can be done" to "controllable and evaluable." Projects that skip the middle step and build a big platform directly often end up feature-complete, yet actions still depend on manual labor.

### Common pitfalls

- Treating the number of back-office pages as operations capability — lots of fields, very poor controllability.
- Operations actions not entering approvals and audit, so when something goes wrong it cannot be traced or retrospected.
- Data definitions not unified, so reports from each system tell different stories and retrospective conclusions are distorted.
- Operations cadence completely disconnected from the development version, so event capability is forever behind the content plan.
- Treating the operations middle platform as a one-step solution — the platform is heavy and the business side cannot integrate.
