# Config-Driven / Script-Driven

## Category

Glossary entry. Node role: config-driven carries value changes, script-driven carries logic changes — both answer "which changes do not go through a full release", but neither can replace the other.

## Definition


These two terms often appear together, because they answer the same question: which changes should not go through the full code release path. The difference lies in the complexity and risk shape of the change: config-driven carries changes at the value level, script-driven carries changes at the logic level.

## Problem

Stuffing logic into config (tables growing if-else) and putting numbers into scripts (changing a value requires code review) are both misplaced: complexity and risk shape differ, and once the carrier mismatches, validation, permissions, and rollback all fail. Gray zones must be classified explicitly rather than dumped wherever is convenient.


### What config-driven is suited to carry

The value of config-driven is to separate changes out of the code release path, so that rule parameters, content combinations, and some static structures can be adjusted faster. Things that are structurally stable but vary in value — numerical curves, drop tables, shop shelves, event switches — usually suit being put into config. Its payoff is not just speed; it also makes changes auditable: every change is a config commit, not a code release.

### What script-driven is suited to carry

Script-driven suits cases where the logic itself is changing: condition combinations, process orchestration, expression evaluation. Describing these in tables would quickly spiral out of control, with a language growing inside the tables that nobody dares to touch. Scripts are more flexible than config, but they also break release discipline more easily, so they usually need extra version management, review process, and rollback mechanisms, rather than borrowing the inertia of "config does not need testing".

### The two cannot replace each other

Stuffing logic into config degrades the tables into a hard-to-read programming language; hard-coding parameters into scripts means every numerical tweak goes through a full release. Judging which side a class of change belongs to usually comes down to two questions: is the change in the value or the structure, and how short is the required loss-limiting window after a failure. Value changes that must be fast go to config; structure changes that allow review go to scripts.

### A practical classification test

When unsure which side a change belongs to, a common approach is to ask two questions: does this change need to be completed self-service by a non-programmer role, and does it have to be rolled back within minutes after a failure? Yes to both goes to config; no to the first means it is most likely scripts; no to the second means it should not even be config — it is a code change that goes through the full process.

The test misses some intermediate forms; when unsure, govern it on the higher-risk side first, which is usually cheaper than fixing it afterwards.

### How each carrier fails

- How config fails: fields keep accumulating, semantics live in comments, nobody can state the blast radius of changing one spot, and in the end nobody dares touch it.
- How scripts fail: they ship directly bypassing tests, are hard to locate after a crash, and host and script versions chase each other in fixes.
- The shared failure mode: no gray release and no rollback, so errors act directly on the full player base.

These failure modes remind us that the two have different governance priorities: config focuses on structure and validation, scripts focus on version and review, and governing them together usually leaves both half-done.

### Config-driven does not mean handing it to designers

A more accurate reading is that config-driven brings rule changes into formal engineering governance: tables need structure and validation, changes need gray release and rollback, rather than "changing a table needs no test". Once the config path bypasses quality process, the speed advantage it accumulates is all given back by one config incident, plus the loss of the team's trust in the config system.

### How to handle gray zones

Condition expressions, rule scripts, and programmable event templates sit between the two. The common approach is not to argue whether they count as config or as scripts, but to tier them by risk: read-only parameters are low risk, executable logic is high risk, and the higher the risk the more review, gray release, and rollback must be added. Tipping the standard onto engineering usually means looking at how many players' assets a given change can directly affect at worst.

### Its relationship with hot update

Config and scripts are worth discussing separately because they often take effect through the hot-update channel, which is also where their speed advantage comes from. Hot update solves how a change takes effect; config-driven and script-driven solve which changes are worth taking effect that way, and the two cannot define each other. The faster the channel, the stricter the entry governance must be.

### What to answer before introducing script-driven

- Who writes the scripts, who reviews them, and what testing they go through.
- How is a script crash located, and can logs and stack traces be reconstructed back to a script version.
- When the host upgrades, how are old scripts kept compatible.
- On a failure, which version is rolled back to, and how fast does it take effect.

Introducing a script layer without clear answers to these usually drags down overall release discipline, not just this one piece of scripts.

### Config forms beyond tables

Beyond tables, config has other common variants: structured descriptions of event orchestration, condition trees in rule engines, and remote parameters provided by the platform. The forms differ, but the judgment standard is the same: is the structure stable, does the value vary, can failures be rolled back quickly. Flashy forms do not equal good governance — many projects' remote parameters have no validation and no versioning, making incidents harder to investigate than tables.

### Common pitfalls

- Treating "anything can be configured" as flexibility, letting config tables pile up larger and larger until nobody dares touch them.
- Hot-updating scripts bypassing tests and review, becoming a channel for evading release discipline.
- Config without validation and gray release, so errors hit the full player base directly.
- Assuming config-driven means no release is needed, ignoring the compatibility window between config and code versions.
